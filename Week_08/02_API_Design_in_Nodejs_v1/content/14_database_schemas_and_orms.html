Database Schema และ ORM

ถึงตรงนี้ Habit Tracker ของเรามี Route ครบ มี Middleware ครบ มี Validation ครบ แต่ยังไม่มีข้อมูลจริงสักชิ้น ทุกอย่างหายไปหมดทันทีที่รีสตาร์ท Server บทนี้เราจะเริ่มแก้เรื่องนั้น

ข่าวดีคือคุณเพิ่งเรียนคอร์สฐานข้อมูลเบื้องต้น มาแล้ว คุณรู้จัก SQL, PostgreSQL, การเขียน SELECT กับ JOIN และรู้ว่า Index ทำงานอย่างไร คอร์สนี้จะไม่สอนเรื่องพวกนั้นซ้ำ แต่จะพาคุณเอาความรู้ชุดนั้นมาต่อเข้ากับ API โดยเขียนทุกอย่างเป็น TypeScript แทนที่จะเขียน SQL ดิบ

ก่อนจะแตะโค้ด ขอเตือนไว้ก่อนว่าการออกแบบ Schema เป็นศาสตร์ที่ลึกได้ไม่มีที่สิ้นสุด มีคนทั้งชุมชนที่แชร์ Schema สวย ๆ กันจนดูแล้วต้องยอมแพ้ แต่แนวทางที่ผมยึดคือยิ่งเรียบง่ายยิ่งดี และบทนี้จะพาคุณคิดแบบนั้น

เริ่มจาก Feature ไม่ใช่เริ่มจากตาราง

เวลาผมจะออกแบบข้อมูล ผมไม่เคยเริ่มจากการนั่งนึกว่าควรมีตารางอะไรบ้าง ผมเริ่มจากคำถามว่าผู้ใช้จะทำอะไรกับแอปนี้ บางคนเรียกวิธีคิดนี้ว่า Domain Driven Design ส่วนผมชอบเรียกว่า Critical User Journey คือการแตกแอปออกเป็นเส้นทางการใช้งานที่มีจุดเริ่มและจุดจบชัดเจน แล้วถามว่าเส้นทางนั้นต้องใช้ข้อมูลอะไรบ้าง

ของเรา Journey แรกคือ "ผมล็อกอินเข้ามาแล้วอยากเห็น Habit ของผม" แค่ประโยคเดียวนี้บอกเราแล้วว่ามี User และมี Habit และ User หนึ่งคนเป็นเจ้าของ Habit ได้หลายอัน นั่นคือความสัมพันธ์แบบ One-to-Many

หัวใจของการคิดเรื่อง Relational Data คือคำว่าความเป็นเจ้าของ ถามตัวเองว่าข้อมูลชิ้นไหนเป็นเจ้าของข้อมูลชิ้นไหน แล้วโครงสร้างจะโผล่ออกมาเอง ถ้าคิดไม่ออกจริง ๆ ลองสเก็ตช์หน้าจอที่อยากได้ก่อนก็ช่วยได้มาก เพราะพอเห็นภาพว่าแอปจะทำอะไร การจัดข้อมูลรอบ ๆ ภาพนั้นจะง่ายขึ้นเยอะ

แปลศัพท์ Database เป็นภาษา JavaScript

Relational Database คือฐานข้อมูลที่มีคอลัมน์ตายตัว เข้มงวด และนิยามไว้ชัดเจน แต่ถ้าคุณอ่านคำว่า Table, Row, Column แล้วยังรู้สึกห่างตัว ให้แปลเป็นของที่คุณใช้ทุกวันแบบนี้

  • Table คือ Array
  • Row คือ Object หนึ่งตัวใน Array นั้น
  • Column คือ Field บน Object
  • Primary Key คือ id ของ Object ตัวนั้น ห้ามซ้ำกับใคร
  • Foreign Key คือ id ของคนอื่นที่เรามาแปะไว้บน Object ของเรา
  • Relationship คือชนิดของการเชื่อม มีสามแบบคือ One-to-One, One-to-Many และ Many-to-Many

ผมมองแบบนี้จริง ๆ จนทุกวันนี้ผมแทบไม่เห็นคำว่า Table, Row, Column แล้ว ผมเห็นเป็น Array, Object, Field ล้วน ๆ

เรื่องที่คนใหม่มักสงสัยคือจะวาง Foreign Key ไว้ฝั่งไหน สมมติเป็นแอปชุมชนที่คนหนึ่งคนมีบ้านหลังเดียวและบ้านหลังหนึ่งมีคนเดียว นั่นคือ One-to-One คำตอบคือวางฝั่งที่เรา Query บ่อย ถ้าแอปเราเริ่มจากตาราง User เสมอ ก็เอา Key ของบ้านไปแปะบน User ถ้าเริ่มจากบ้านก็ทำกลับกัน หรือถ้าขี้เกียจเลือกจะแปะทั้งสองฝั่งก็ได้ แบบนั้นเรียกว่า Denormalize ซึ่งก็ไม่ผิดอะไร

ส่วน One-to-Many กฎง่าย ๆ คือ Foreign Key อยู่ฝั่ง Many เสมอ Habit หนึ่งอันเป็นของ User คนเดียว เพราะฉะนั้น user_id ไปอยู่บนตาราง Habit

ทำไมต้อง PostgreSQL

คอร์สนี้ใช้ PostgreSQL ซึ่งถ้าถามคนส่วนใหญ่ก็จะบอกว่าเป็น Database ที่นิยมที่สุดในโลก (ถ้าวัดกันด้วยจำนวนเครื่องที่ติดตั้งจริง SQLite น่าจะชนะ แต่คนละงานกัน) เหตุผลที่มันเข้ากับงาน API ได้ดี

  • รองรับ ACID เต็มรูปแบบ Transaction เชื่อถือได้
  • มี Data Type ให้เลือกเยอะมาก ทั้ง JSON, Array และ Custom Type ที่เราสร้างเองได้
  • มีของขั้นสูงติดมาให้ เช่น Full-text Search และ GIS ที่คำนวณระยะจากพิกัด Latitude/Longitude ได้
  • ทำ Query ซับซ้อนได้เก่ง และเป็น Open Source ไม่มีใครเป็นเจ้าของ ไม่มีค่า License
  • ฝั่ง Node.js มี Integration ให้เลือกมหาศาล และ Async/Await ทำให้การคุยกับ Database ไม่ Block งานอื่น
  • มี ORM ที่รองรับ TypeScript ดีมาก ซึ่งเป็นข้อที่ผมยอมแลกอะไรไม่ได้เลย

ORM คือ SDK ของ Database

ORM ย่อมาจาก Object-Relational Mapping ซึ่งเป็นศัพท์เก่าที่ฟังแล้วไม่ค่อยสื่ออะไร ให้จำสั้น ๆ ว่า ORM คือ SDK ของ Database มันคือวิธีที่เราคุยกับฐานข้อมูลจากในโค้ด และมี ORM ให้เลือกมากมายทั้งของ Database แต่ละเจ้า

ถ้าไม่มี ORM ชีวิตจะหน้าตาแบบนี้ คือได้ Client ระดับล่างมาตัวหนึ่งแล้วยัด SQL ดิบเข้าไปเอง

const result = await client.query(
  'SELECT u.*, h.* FROM users u LEFT JOIN habits h ON u.id = h.user_id WHERE u.id = $1',
  [userId]
)

// แล้วต้องมานั่งแกะผลลัพธ์เองทีละชั้น
const user = {
  id: result.rows[0].id,
  email: result.rows[0].email,
  habits: result.rows.map((row) => ({
    id: row.habit_id,
    name: row.habit_name,
  })),
}

ปัญหาคือไม่มี Type เลย ต้องแปลงชนิดข้อมูลเอง ต้องแกะผลลัพธ์เอง และ SQL ที่เขียนก็ผูกกับ Database เจ้านั้นเจ้าเดียว ถ้ามี ORM เรื่องเดียวกันจะเหลือแค่นี้

const user = await prisma.user.findFirst({
  where: { id: userId },
  include: {
    habits: true,
  },
})

user.email        // string
user.habits[0].id // string
user.nonExistent  // TypeScript ฟ้อง Error ให้ตั้งแต่ตอนพิมพ์

สิ่งที่เราได้กลับมามีหลายชั้น

  • Type Safety — จับพลาดตั้งแต่ตอนเขียน ไม่ใช่ตอน Production พัง
  • Query Building — ประกอบ Query ด้วยโค้ดได้ ทำ Filter หรือ Pagination แบบไดนามิกง่าย
  • Relationship Loading — สั่ง include ทีเดียวแล้ว ORM จัดการ JOIN ให้
  • Schema Management และ Migration — Schema อยู่ใน Git และเปลี่ยนแปลงได้อย่างเป็นระบบ ซึ่งเป็นหัวข้อของบทหน้า

หลายคนบอกว่า ORM ป้องกัน SQL Injection ให้ด้วย ซึ่งจริงบางส่วน แต่อยากให้เข้าใจให้ถูก ถ้าคุณยัด String ที่ผู้ใช้ส่งมาเข้าไปเป็น Raw SQL ผ่าน ORM คุณก็โดนเหมือนเดิม ความปลอดภัยมาจากการที่เราไม่ต่อ String เอง ไม่ได้มาจากยี่ห้อของ ORM

สำหรับผมเหตุผลที่ใหญ่ที่สุดคือผมไม่ต้องรู้ SQL ลึกขนาดนั้น SQL เป็นศาสตร์ที่ลึกจนมีคนเก่งระดับรับงานเขียน Query อย่างเดียวกินเงินเป็นล้าน ผมรู้ SQL พอทำงานได้และผมพอใจแค่นั้น

ทำไมคอร์สนี้เลือก Prisma

ORM ฝั่ง Node.js ที่ดังที่สุดคู่หนึ่งคือ Prisma กับ Drizzle ทั้งคู่เป็นของดีและมีคนใช้จริงในโปรดักชันมหาศาล คอร์สนี้เลือก Prisma และผมอยากให้เห็นว่าเลือกเพราะอะไร ไม่ใช่แค่เลือกตามกระแส

ความต่างหลักคือ Prisma ให้เราเขียน Schema ด้วยภาษาเฉพาะของมันเอง (เรียกว่า DSL ซึ่งหน้าตาได้อิทธิพลมาจาก GraphQL) แล้วรัน Code Generation เพื่อสร้าง Client ที่มี Type ครบทุกตารางออกมาให้เราใช้

// ฝั่ง Prisma — ไฟล์ schema.prisma เป็นภาษาของมันเอง
model User {
  id     String  @id @default(uuid())
  email  String  @unique
  habits Habit[]
}

ส่วน Drizzle ให้เราเขียน Schema เป็น TypeScript ธรรมดา ๆ

// ฝั่ง Drizzle — เป็น TypeScript ล้วน
export const users = pgTable('users', {
  id: uuid('id').primaryKey(),
  email: varchar('email', { length: 255 }).unique(),
})

เหตุผลที่ผมพาคุณไปทาง Prisma ในคอร์สนี้

  • Schema อ่านรู้เรื่องทั้งไฟล์ในไม่กี่วินาที — DSL ของ Prisma ถูกออกแบบมาเพื่องานนี้อย่างเดียว แม้แต่คนที่ไม่เขียน TypeScript ก็เปิดไฟล์แล้วเข้าใจโครงสร้างข้อมูลได้ทันที มันจึงกลายเป็นเอกสารกลางของทีมไปในตัว
  • Client ที่ Generate ออกมาอ่านเหมือนภาษาคน — prisma.user.findMany() อ่านแล้วรู้เลยว่าทำอะไร และทุกอย่างมี Type ครบโดยเราไม่ต้องเขียนเอง
  • ระบบ Migration ที่คิดมาครบ — เก็บประวัติเป็นไฟล์ SQL ที่รีวิวได้ ซึ่งเป็นหัวข้อใหญ่ของบทหน้า
  • Ecosystem ใหญ่ที่สุดในบรรดา ORM ฝั่ง Node.js — เอกสารดีมาก มี Prisma Studio ให้ส่องข้อมูลแบบภาพ และเจอปัญหาอะไรก็มีคนเคยเจอมาก่อนแล้วเกือบเสมอ

ราคาที่ต้องจ่ายก็มีจริง คือต้องเรียนภาษาเล็ก ๆ เพิ่มหนึ่งภาษา และมีขั้นตอน Generate ที่ต้องรันเมื่อ Schema เปลี่ยน ส่วน Drizzle ก็มีจุดแข็งของมัน คือเป็น TypeScript ล้วนและ API ใกล้เคียง SQL กว่า ถ้าวันหนึ่งคุณไปเจอโปรเจกต์ที่ใช้ Drizzle ความรู้จากคอร์สนี้ย้ายไปใช้ได้เกือบทั้งหมด เพราะแนวคิดเรื่อง Schema, ความสัมพันธ์ และ Migration เป็นเรื่องเดียวกันเป๊ะ

บทถัดไปเราจะคุยเรื่อง Migration ซึ่งเป็น Version Control ของ Database และเป็นหัวข้อที่ผมกล้าพูดเลยว่าน่าปวดหัวที่สุดในคอร์สนี้ แต่ผมจะย่อยมาให้ง่ายที่สุดแล้ว
