สร้างตารางและความสัมพันธ์ด้วย Prisma ORM

ทฤษฎีพอแล้ว บทนี้เราจะเขียน Schema ทั้งห้าตารางของ Habit Tracker กันจริง ๆ เริ่มจากติดตั้ง Package กันก่อน Prisma แบ่งเป็นสองส่วน คือ CLI ที่ใช้ตอนพัฒนา กับ Client ที่โค้ดเราเรียกใช้ตอนรันจริง สังเกตว่าเราระบุเวอร์ชันแบบเจาะจงไปเลย เพราะ CLI ของ Prisma ปรับพฤติกรรมระหว่างเวอร์ชันอยู่เรื่อย ๆ การล็อกเวอร์ชันทำให้ทุกคนที่เรียนคอร์สนี้เห็นผลลัพธ์เหมือนกันเป๊ะ

npm install @prisma/client@7.10.0
npm install -D prisma@7.10.0

แล้วสั่งให้ Prisma ตั้งโครงให้เรา

npx prisma init --no-skills

คำสั่งนี้สร้างของให้เราสองชิ้น คือโฟลเดอร์ prisma/ ที่มีไฟล์ schema.prisma อยู่ข้างใน กับไฟล์ prisma7.config.ts ที่รากโปรเจกต์ ตัวหลังคือไฟล์ตั้งค่าของ CLI ซึ่งเราจะกลับมาต่อสายมันเข้ากับ Database จริงในบทที่ 18 บทนี้โฟกัสที่ schema.prisma อย่างเดียว

ส่วน Flag --no-skills คือบอกว่าไม่ต้องติดตั้ง "Agent Skills" ซึ่งเป็นชุดไฟล์แนะนำการใช้ Prisma สำหรับ AI Coding Agent อย่าง Claude Code หรือ Cursor (ถ้ารันโดยไม่ใส่ Flag นี้ จะได้โฟลเดอร์ .claude/, .agents/, .windsurf/ และไฟล์ skills-lock.json แถมมาด้วย ซึ่งไม่เกี่ยวกับคอร์สนี้ แต่ถ้าคุณใช้เครื่องมือพวกนั้นอยู่จะเก็บไว้ก็ไม่เสียหาย)

รู้จักไฟล์ schema.prisma

Prisma ให้เราเขียน Schema ด้วยภาษาเฉพาะของมันเอง นามสกุลไฟล์คือ .prisma แนะนำให้ติดตั้ง Extension ชื่อ Prisma ใน VS Code ก่อนเลย จะได้ทั้ง Syntax Highlight, Autocomplete และ Format ไฟล์ให้อัตโนมัติ

เปิดไฟล์ขึ้นมาแล้วเริ่มจากสองบล็อกบนสุด

generator client {
  provider               = "prisma-client"
  output                 = "../src/generated/prisma"
  runtime                = "nodejs"
  moduleFormat           = "esm"
  generatedFileExtension = "ts"
  importFileExtension    = "ts"
}

datasource db {
  provider = "postgresql"
}

บล็อก generator คือการบอกว่า "เวลาสร้าง Client ให้ผม สร้างแบบไหน" — provider ที่ชื่อ prisma-client คือ Generator รุ่นปัจจุบันที่สร้างโค้ดออกมาเป็น TypeScript ตรง ๆ ส่วน output คือโฟลเดอร์ปลายทาง (Path นับจากโฟลเดอร์ prisma/ ดังนั้น ../src/generated/prisma คือไปโผล่ที่ src/generated/prisma) สามบรรทัดล่างคือการบอกว่าโปรเจกต์เราเป็น ESM และรันไฟล์ .ts ตรง ๆ ด้วย Node.js ซึ่งตรงกับที่เราตั้งโปรเจกต์ไว้ตั้งแต่ต้นคอร์สพอดี

ส่วน datasource บอกแค่ว่า Database ของเราเป็น PostgreSQL สังเกตว่าไม่มี Connection String อยู่ในนี้ เพราะค่านั้นเป็นความลับและเปลี่ยนตามสภาพแวดล้อม Prisma จึงให้ไปประกาศใน prisma7.config.ts แทน ซึ่งเดี๋ยวเราจะทำกันในบทที่ 18

ตาราง users

ต่อจากสองบล็อกนั้น เขียน Model แรกของเรา

model User {
  id        String   @id @default(uuid()) @db.Uuid
  email     String   @unique @db.VarChar(255)
  username  String   @unique @db.VarChar(50)
  password  String   @db.VarChar(255)
  firstName String?  @map("first_name") @db.VarChar(50)
  lastName  String?  @map("last_name") @db.VarChar(50)
  createdAt DateTime @default(now()) @map("created_at")
  updatedAt DateTime @default(now()) @updatedAt @map("updated_at")

  @@map("users")
}

มีรายละเอียดหลายจุดที่ควรเข้าใจ ไม่ใช่แค่ก๊อปวาง

  • หนึ่ง Model เท่ากับหนึ่งตาราง ธรรมเนียมของ Prisma คือตั้งชื่อ Model เป็นเอกพจน์ตัวใหญ่ (User) แล้วใช้ @@map("users") บอกชื่อตารางจริงในฐานข้อมูล ซึ่งธรรมเนียมฝั่งนั้นคือพหูพจน์ตัวเล็ก
  • เช่นเดียวกัน @map คือการบอกชื่อคอลัมน์จริง สังเกตว่า firstName ในโค้ดแมปไปเป็น first_name ในฐานข้อมูล เพราะธรรมเนียมของ Relational Database คือ Snake Case ส่วนธรรมเนียมของ JavaScript คือ Camel Case Prisma เลยให้เราเขียนสองชื่อคู่กันแบบนี้
  • @id @default(uuid()) @db.Uuid คือ Primary Key แบบ UUID โดย Prisma จะสุ่มค่าให้เองตอนสร้างแถวใหม่ ข้อดีของ UUID คือไม่ซ้ำกันข้ามระบบ ใส่ใน URL ได้ และไม่หลุดข้อมูลว่าเรามีผู้ใช้กี่คนเหมือนเลขรันนิ่ง ส่วน @db.Uuid คือให้คอลัมน์ในฐานข้อมูลเป็นชนิด UUID จริง ๆ ไม่ใช่ Text ธรรมดา
  • ทุก Field บังคับ (Not Null) โดยปริยาย ถ้าอยากให้เว้นว่างได้ต้องเติม ? ต่อท้ายชนิดข้อมูลเอง สังเกตว่า firstName กับ lastName เราใส่ ? ไว้ เพราะบางคนไม่อยากบอกชื่อจริง
  • @default(now()) บน createdAt คือให้เติมเวลาปัจจุบันให้เองตอนสร้างแถว ส่วน updatedAt เราแถม @updatedAt เข้าไปด้วย ซึ่งแปลว่า Prisma จะอัปเดตเวลาให้เองทุกครั้งที่แถวนั้นถูกแก้ไข โดยเราไม่ต้องเขียนโค้ดเติมเอง เรื่อง Timestamp นี้เป็น Best Practice ที่ผมจะย้ำอีกครั้งในบทหน้า

varchar กับ text ต่างกันอย่างไร

ชนิดข้อมูล String ของ Prisma บน PostgreSQL จะกลายเป็นคอลัมน์แบบ text คือข้อความยาวเท่าไรก็ได้ ถ้าอยากจำกัดความยาวให้เติม @db.VarChar(ความยาว) ซึ่ง varchar ก็คือ Text ธรรมดานี่แหละ แค่มันจำกัดความยาวได้

ผมใส่ @db.VarChar(255) ให้ email ไว้ ไม่ใช่เพราะเชื่อว่าเป็นวิธีที่ดีที่สุด แต่เพื่อให้คุณเห็นว่ามันทำอะไรได้ จะจำกัดความยาวอีเมลจริง ๆ หรือไม่ก็แล้วแต่คุณ ส่วนคอลัมน์อย่าง description ที่เราไม่อยากจำกัดอะไรเลย ใช้ String เปล่า ๆ ไปตรง ๆ ง่ายกว่า

@unique คือทางลัดของการสร้าง Unique Index

คุณเจอ Index มาแล้วในคอร์สฐานข้อมูลเบื้องต้น ขอทวนสั้น ๆ ในภาษาที่ใช้กับงานนี้ Index คือที่เก็บแยกอีกที่หนึ่งในฐานข้อมูล ที่จับคู่ Key ไว้กับตำแหน่งของข้อมูล พูดแบบ JavaScript มันคือ Object ที่ทำหน้าที่เป็น Hash Table นั่นเอง

ถ้าไม่มี Index การหาอะไรสักอย่างแปลว่าต้องไล่สแกนทั้งตาราง แต่ถ้ามี Index ฐานข้อมูลจะสแกนแค่ตัว Index ที่เล็กกว่ามาก (บางระบบเก็บไว้ใน Memory เลย) เจอ Key แล้วกระโดดไปที่ตำแหน่งของข้อมูลได้ทันที

การเติม @unique จึงหมายความสองอย่างพร้อมกัน คือห้ามมีอีเมลซ้ำในระบบ และสร้าง Index ให้คอลัมน์นี้ด้วย เพื่อให้ตอนมีคนสมัครใหม่ ฐานข้อมูลตอบได้ทันทีว่าอีเมลนี้มีคนใช้แล้วหรือยัง โดยไม่ต้องไล่สแกนผู้ใช้ทั้งตาราง

สังเกตว่า password เรา ไม่ ใส่ @unique ซึ่งฟังดูตลกแต่มีคนพลาดจริง ลองคิดดูว่าถ้ารหัสผ่านห้ามซ้ำ พอสมัครไม่ผ่านปุ๊บก็แปลว่ามีคนใช้รหัสนี้อยู่ เหลือแค่หาอีเมลให้เจอก็เข้าระบบได้เลย

อีกเรื่องที่อยากให้เห็นคือ Validation เกิดได้หลายชั้น ทั้งที่ Form ฝั่งหน้าบ้าน ที่ Middleware ที่เราเขียนไปในบทที่ 12 และที่ระดับ Database ตรงนี้ ชั้นนอกข้ามได้ง่าย แต่ชั้นในสุดข้ามไม่ได้เลย ยิ่งกฎตรงกันทุกชั้นยิ่งดี

ตาราง habits และ Foreign Key ตัวแรกของเรา

model Habit {
  id          String   @id @default(uuid()) @db.Uuid
  userId      String   @map("user_id") @db.Uuid
  user        User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  name        String   @db.VarChar(100)
  description String?
  frequency   String   @db.VarChar(20) // daily, weekly, monthly
  targetCount Int      @default(1) @map("target_count") // ทำกี่ครั้งต่อรอบ
  isActive    Boolean  @default(true) @map("is_active")
  createdAt   DateTime @default(now()) @map("created_at")
  updatedAt   DateTime @default(now()) @updatedAt @map("updated_at")

  @@map("habits")
}

userId คือ Foreign Key ตัวแรกของเรา กฎข้อแรกคือชนิดต้องตรงกับ Primary Key ที่มันชี้ไป ฝั่ง User.id เป็น String @db.Uuid ฝั่งนี้ก็ต้องเป็นแบบเดียวกัน

ตัวที่ทำงานจริงคือบรรทัด user User @relation(...) อ่านว่า "Habit หนึ่งอันผูกกับ User หนึ่งคน โดยใช้คอลัมน์ userId ฝั่งเราไปเทียบกับ id ฝั่งเขา" บรรทัดนี้แหละที่สั่งให้ฐานข้อมูลสร้าง Foreign Key Constraint จริง ๆ

จุดที่ต้องเข้าใจให้ชัดคือ Field ชื่อ user ไม่ใช่คอลัมน์ในตาราง ตาราง habits มีแค่ user_id เท่านั้น user เป็นของที่ Prisma เสกขึ้นมาให้ฝั่งโค้ด เพื่อให้เวลา Query เราขอ "Habit พร้อม User เจ้าของ" ได้ในคำสั่งเดียว ซึ่งเราจะได้ใช้จริงตอนเขียน Controller

onDelete: Cascade คือคำสั่งว่าถ้า User ที่ถูกอ้างถึงถูกลบ ให้ลบ Habit นี้ตามไปด้วย ซึ่งสมเหตุสมผล เพราะ Habit ที่ไม่มีเจ้าของก็ไม่มีความหมาย

และเพราะ userId ไม่มีเครื่องหมาย ? จึงสร้าง Habit โดยไม่ผูกกับ User ไม่ได้เลย ฐานข้อมูลจะปฏิเสธตั้งแต่ต้น ไม่ต้องรอให้โค้ดเราตรวจ

คอลัมน์ที่เหลือ frequency คือรอบการทำ เช่น daily, weekly, monthly ตรงนี้จริง ๆ ควรใช้ Enum จะดีกว่า แต่ผมยังไม่ใส่และจะกลับมาคุยเรื่องนี้ในบทหน้า targetCount คือเป้าหมายว่าต้องทำกี่ครั้งต่อรอบ เผื่อ Habit อย่าง "ดื่มน้ำแปดแก้วต่อวัน" และ isActive ให้ซ่อน Habit ที่เลิกทำแล้วโดยไม่ต้องลบประวัติทิ้ง

ความสัมพันธ์ต้องประกาศทั้งสองฝั่ง

ถ้าคุณเซฟไฟล์ตอนนี้ Prisma จะฟ้อง Error ทันที เพราะกฎของมันคือเมื่อประกาศความสัมพันธ์ฝั่งหนึ่ง ต้องประกาศอีกฝั่งด้วยเสมอ กลับขึ้นไปเติมบรรทัดเดียวใน Model User

model User {
  // ...field เดิมทั้งหมด
  habits Habit[]

  @@map("users")
}

habits Habit[] อ่านว่า "User หนึ่งคนมี Habit ได้หลายอัน" นี่คือหน้าตาของ One-to-Many ในภาษา Prisma — ฝั่ง Many ถือ Foreign Key ส่วนฝั่ง One ได้ Field ที่เป็น Array และเช่นเดียวกับ user เมื่อกี้ habits ไม่ใช่คอลัมน์จริงในตาราง users มันคือ Field ที่ Prisma เตรียมไว้ให้ตอน Query เท่านั้น

เกร็ดที่ช่วยชีวิตได้คือ ถ้าขี้เกียจเขียนฝั่งกลับเอง สั่ง npx prisma format แล้ว Prisma จะเติม Field ฝั่งที่ขาดให้อัตโนมัติ (Extension ใน VS Code ก็ทำให้ตอนเซฟไฟล์เช่นกัน)

ตาราง entries

model Entry {
  id              String   @id @default(uuid()) @db.Uuid
  habitId         String   @map("habit_id") @db.Uuid
  habit           Habit    @relation(fields: [habitId], references: [id], onDelete: Cascade)
  completion_date DateTime @default(now())
  note            String?
  createdAt       DateTime @default(now()) @map("created_at")

  @@map("entries")
}

รูปแบบเดิมทุกอย่าง Entry หนึ่งแถวคือ "ทำ Habit นี้สำเร็จหนึ่งครั้ง" ความสัมพันธ์เป็น One-to-Many อีกครั้ง Foreign Key จึงอยู่ฝั่ง Many ตามเคย และ Cascade ก็สมเหตุสมผล เพราะถ้า Habit ถูกลบ ประวัติการทำ Habit นั้นก็ไม่ควรค้างอยู่ (อย่าลืมไปเติม entries Entry[] ใน Model Habit ด้วย หรือให้ prisma format เติมให้)

completion_date ใส่ @default(now()) ไว้ เพราะปกติแถวนี้ถูกสร้างตอนที่คุณเพิ่งทำเสร็จพอดี ส่วน note เป็น Optional เผื่ออยากบันทึกอะไรไว้

สังเกตว่า Field นี้ชื่อ completion_date ทั้งฝั่งโค้ดและฝั่งฐานข้อมูล ไม่ได้เป็น Camel Case เหมือน Field อื่น อันนี้คือหน้าตาที่มันเป็นจริงในโปรเจกต์ ให้จำชื่อนี้ไว้ เพราะเราจะใช้มันตอนเขียน Seed และ Controller ในบทถัด ๆ ไป

ตาราง tags กับกับดักเรื่อง Unique

model Tag {
  id        String   @id @default(uuid()) @db.Uuid
  name      String   @unique @db.VarChar(50)
  color     String   @default("#6B7280") @db.VarChar(7) // hex color
  createdAt DateTime @default(now()) @map("created_at")
  updatedAt DateTime @default(now()) @updatedAt @map("updated_at")

  @@map("tags")
}

color ยาว 7 ตัวอักษรพอดีสำหรับ Hex Color อย่าง #6B7280 ตรงนี้ไม่มีอะไรซับซ้อน แต่บรรทัด name มีกับดักที่ผมอยากให้เห็น

การใส่ @unique ตรงนี้แปลว่าชื่อ Tag ห้ามซ้ำกันทั้งระบบ ซึ่งหมายความว่าถ้าผมสร้าง Tag ชื่อ Fitness ไปแล้ว คุณจะสร้าง Tag ชื่อเดียวกันบนบัญชีของคุณไม่ได้เลย ทั้งที่มันควรเป็นของใครของมัน

สิ่งที่ถูกต้องกว่าคือทำ Unique บนคู่ของ userId กับ name (ซึ่งต้องเพิ่มคอลัมน์ userId ให้ตาราง tags ก่อน) ซึ่ง Prisma รองรับผ่าน @@unique([userId, name]) แต่มันซับซ้อนขึ้นอีกระดับ ผมเลยขอคงไว้แบบนี้ก่อนในคอร์ส แล้วบอกให้คุณรู้ว่ามันเป็นข้อจำกัด

ที่ยกมาเล่าเพราะกับดักแบบนี้เกิดขึ้นได้จริง Server ตัวแรกในชีวิตผมเคยมีช่องโหว่ที่ใครก็เข้าไปดูข้อมูลของคนอื่นได้ ทั้งที่ตอนนั้นผมคิดว่าเขียนดีมากแล้ว และมันถูกใช้งานจริงด้วย ผิดแล้วก็จำไว้

ตาราง habit_tags ตัวเชื่อม Many-to-Many

model HabitTag {
  id        String   @id @default(uuid()) @db.Uuid
  habitId   String   @map("habit_id") @db.Uuid
  habit     Habit    @relation(fields: [habitId], references: [id], onDelete: Cascade)
  tagId     String   @map("tag_id") @db.Uuid
  tag       Tag      @relation(fields: [tagId], references: [id], onDelete: Cascade)
  createdAt DateTime @default(now()) @map("created_at")

  @@map("habit_tags")
}

ตารางนี้ไม่มีข้อมูลของตัวเองเลย หน้าที่เดียวของมันคือจับคู่ Habit หนึ่งอันเข้ากับ Tag หนึ่งอัน แล้วมี id ของตัวเองไว้อ้างถึงคู่นั้น สังเกตว่าจากมุมของตารางกลาง ความสัมพันธ์ทั้งสองขาเป็นแบบ "หนึ่งแถวผูกกับของหนึ่งชิ้น" ความเป็น Many-to-Many เกิดขึ้นเมื่อมองภาพรวมจากการที่มีหลายแถว

ให้เห็นภาพชัด ๆ หนึ่งความสัมพันธ์เท่ากับหนึ่งแถวในตารางนี้ ถ้า Habit หนึ่งอันติดยี่สิบ Tag จะมียี่สิบแถวที่ habit_id เหมือนกันหมดแต่ tag_id ต่างกัน ถ้า Tag หนึ่งอันไปเกาะยี่สิบ Habit ก็จะมียี่สิบแถวที่ tag_id เหมือนกันแต่ habit_id ต่างกัน

อย่าลืมเติมฝั่งกลับอีกสองที่ คือ habitTags HabitTag[] ใน Model Habit และใน Model Tag (Prisma มีระบบ Many-to-Many แบบที่มันสร้างตารางกลางให้เองโดยเราไม่ต้องเขียน Model นี้เลยด้วยนะครับ แต่ผมจงใจเขียนตารางกลางเองแบบนี้ เพราะอยากให้คุณเห็นกลไกจริงของมัน และเราอยากได้คอลัมน์ createdAt ของตัวเองด้วย)

Schema ฉบับเต็มเมื่อประกอบครบ

เมื่อเติมฝั่งกลับครบทุกที่ สาม Model หลักจะหน้าตาแบบนี้ (ตัดบรรทัดที่ไม่เปลี่ยนออกเพื่อความกระชับ)

model User {
  // ...
  habits Habit[]
}

model Habit {
  // ...
  user      User       @relation(fields: [userId], references: [id], onDelete: Cascade)
  entries   Entry[]
  habitTags HabitTag[]
}

model Tag {
  // ...
  habitTags HabitTag[]
}

วิธีอ่านมีแค่นี้ — Field ที่เป็นชนิด Model เดี่ยว (user User) คือ "ของชิ้นนี้เป็นของใคร" ส่วน Field ที่เป็น Array (habits Habit[]) คือ "ใครมีของพวกนี้บ้าง" ทั้งหมดนี้คือ Field ที่จะงอกขึ้นมาให้ตอน Query โดยที่ในฐานข้อมูลจริงมีแค่ Foreign Key ธรรมดา

จุดที่เก๋คือใน Prisma การบอกฐานข้อมูล (สร้าง Foreign Key) กับการบอก ORM (อยากได้ Field อะไรตอน Query) เป็นการประกาศครั้งเดียวจบที่ @relation — ORM บางตัวแยกสองเรื่องนี้เป็นคนละที่ ซึ่งเปิดช่องให้ประกาศไม่ครบหรือไม่ตรงกันได้

สามเรื่องที่ต้องระวัง

หนึ่ง ใช้ npx prisma validate ให้เป็นนิสัย คำสั่งนี้ตรวจว่า Schema ของเราถูกกฎครบทุกข้อ ทั้งชนิดของ Foreign Key ที่ต้องตรงกัน ความสัมพันธ์ที่ประกาศไม่ครบสองฝั่ง หรือชื่อที่ชนกัน โดยไม่ต้องแตะฐานข้อมูลเลย มันคือตาข่ายชั้นแรกก่อนที่อะไรจะถูกสร้างจริง

สอง Format แล้วอ่านซ้ำ npx prisma format ช่วยเติมฝั่งกลับของความสัมพันธ์ให้ก็จริง แต่มันเดาชื่อ Field ให้ตามชื่อ Model ถ้าคุณอยากได้ชื่ออื่นต้องแก้เอง และถ้าคุณเผลอชี้ fields ไปที่คอลัมน์ผิดตัวที่ชนิดบังเอิญตรงกัน เครื่องมือก็ช่วยไม่ได้ ให้อ่านสองรอบทุกครั้ง ผมเองเคยนั่งงงว่าทำไมข้อมูลไม่โผล่ ทั้งที่ตอนนั้นเปิด Note ที่ตัวเองเขียนไว้อยู่ตรงหน้า

สาม จะแยก Schema เป็นหลายไฟล์ก็ได้ เหมือนที่เราแยก Route ออกเป็นไฟล์ละ Resource Prisma ให้เราเปลี่ยนจากไฟล์เดียวเป็นโฟลเดอร์ prisma/schema/ ที่ข้างในมีหลายไฟล์ .prisma ได้ บางโปรเจกต์ของผมที่มีเกิน 50 ตารางก็ต้องแยก เพราะเปิดไฟล์เดียวแล้วมึน แต่ของเรามีร้อยกว่าบรรทัด ผมเลยรวมไว้ไฟล์เดียว

Schema ของเราครบแล้ว บทหน้าเราจะดึงประโยชน์จากมันต่อ ด้วยการ Generate Client ที่มี TypeScript Type ครบทุกตาราง แล้วประกอบ Zod Schema สำหรับ Validation ให้เข้าชุดกัน
