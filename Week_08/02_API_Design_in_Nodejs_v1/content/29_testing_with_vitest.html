ตั้งค่าการทดสอบด้วย Vitest

ตลอดคอร์สที่ผ่านมาเราทดสอบ API กันด้วยมือใน Postman ซึ่งได้ผลดีมากตอนกำลังเขียนโค้ดอยู่ แต่พอ Endpoint เริ่มเยอะขึ้น คำถามที่ตอบไม่ได้อีกต่อไปคือ "แก้ตรงนี้แล้วของเดิมยังทำงานอยู่ไหม" ไม่มีใครมานั่งยิงยี่สิบ Request ทุกครั้งที่แก้โค้ดหนึ่งบรรทัดหรอกครับ

บทนี้เราจะยังไม่เขียน Test จริงจัง แต่จะเตรียมพื้นให้พร้อมก่อน เพราะการทดสอบ API ที่แตะฐานข้อมูลมีเรื่องต้องจัดการมากกว่าการทดสอบฟังก์ชันธรรมดาพอสมควร

ทำไมถึงเป็น Vitest ไม่ใช่ Jest

ในคอร์ส Node.js เบื้องต้น เราเขียน Unit Test กันด้วย Jest มาแล้ว ข่าวดีคือสิ่งที่คุณเรียนไปไม่ได้หายไปไหนเลย เพราะ Vitest ออกแบบ API มาให้เข้ากันได้กับ Jest คุณยังใช้ describe, test, it, expect, toBe, toHaveProperty เหมือนเดิมทุกอย่าง แทบไม่ต้องเรียนใหม่

แล้วทำไมต้องเปลี่ยน คำตอบอยู่ที่โปรเจกต์นี้ครับ โปรเจกต์ในคอร์ส Node.js เบื้องต้น เป็น JavaScript ล้วน ส่วนโปรเจกต์นี้เป็น TypeScript ทั้งก้อนและใช้ ESM (import/export) ล้วน ๆ ซึ่งเป็นจุดที่ Jest ต้องต่อเครื่องมือเพิ่มอีกหลายชั้นถึงจะทำงานได้ ผู้สอนเล่าตรง ๆ ว่าเคยลองให้ Jest ทำงานกับ ESM บวก TypeScript แล้วเอาไม่อยู่ ส่วน Vitest รันไฟล์ .ts ได้ทันทีโดยไม่ต้อง Build ก่อน

เอาเป็นว่าถ้าจะสรุปให้สั้นที่สุด — Vitest เร็วกว่า รองรับ TypeScript และ ESM มาแต่กำเนิด และตั้งค่าน้อยกว่ามาก ส่วน Jest กับ Mocha ยังใช้ได้อยู่ เพียงแต่ต้องออกแรงกับการตั้งค่ามากกว่า

แยก Database สำหรับ Test ก่อนเป็นอย่างแรก

ก่อนจะรัน Test แม้แต่ตัวเดียว เราต้องมีฐานข้อมูลอีกตัวหนึ่งเสียก่อน เพราะ Test ของเราจะ สร้าง ลบ และล้างตารางทิ้ง ตลอดเวลา ถ้าปล่อยให้มันวิ่งบนฐานข้อมูลที่เราใช้พัฒนาอยู่ ข้อมูล Seed ที่เรานั่งเตรียมไว้ในบทที่ 19 จะหายเรียบในรอบเดียว

ขั้นตอนเหมือนบทที่ 18 ทุกอย่าง เข้าไปที่ neon.new สร้างฐานข้อมูลใหม่อีกอัน แล้วก๊อบ Connection String ออกมา ต่างกันแค่ครั้งนี้เราจะเอาไปใส่ไว้ในไฟล์ .env.test ที่ Root ของโปรเจกต์ ไม่ใช่ .env

PORT=3001
DATABASE_URL=postgresql://user:password@host/dbname?sslmode=require
JWT_SECRET=test-secret-key-for-testing-only

ค่าที่ใส่ต้องผ่าน Schema ของ env.ts ในบทที่ 6 เหมือนกันทุกประการ JWT_SECRET จึงยังต้องยาวอย่างน้อย 32 ตัวอักษร ส่วน Connection String ของ Neon ต้องมี ?sslmode=require ติดมาด้วยเสมอ สังเกตว่าเราไม่ได้ใส่ APP_STAGE ไว้ในไฟล์นี้ เพราะคนที่ตั้งค่านั้นคือคำสั่งรัน Test ซึ่งเราจะไปทำกันตอนท้ายบท

อย่าลืมว่า .env.test ต้องอยู่ใน .gitignore ด้วย นักพัฒนาแต่ละคนในทีมควรมีฐานข้อมูลทดสอบเป็นของตัวเอง จะได้ไม่ไปล้างตารางใส่กันเองตอนรัน Test พร้อมกัน

vitest.config.ts

ก่อนอื่นติดตั้งเครื่องมือที่บทนี้ต้องใช้

npm install -D vitest@4.1.11 cross-env

สร้างไฟล์ vitest.config.ts ไว้ที่ Root ของโปรเจกต์ ไฟล์นี้ปกติ CLI ของ Vitest สร้างให้ได้อยู่แล้ว คุณไม่จำเป็นต้องจำวิธีเขียนมันขึ้นมาเองจากศูนย์ แต่เราควรรู้ว่าแต่ละบรรทัดหมายถึงอะไร

import { defineConfig } from 'vitest/config'

export default defineConfig({
  test: {
    globals: true,
    globalSetup: ['./tests/setup/globalSetup.ts'],
    // Automatically clean up after each test to ensure isolation
    clearMocks: true,
    restoreMocks: true,
    // Ensure tests run sequentially to avoid database conflicts
    fileParallelism: false,
  },
  plugins: [],
})
  • globals: true — ยัด describe, test, it, expect, beforeAll, afterEach เข้าไปไว้ใน Global Scope ให้เลย เราจะได้ไม่ต้อง Import มันในทุกไฟล์ Test ซึ่งน่ารำคาญมาก ส่วนฝั่ง TypeScript เราใส่ "types": ["vitest/globals"] ไว้ใน tsconfig.json ให้แล้วตั้งแต่ต้นคอร์ส เอดิเตอร์จึงรู้จักฟังก์ชันพวกนี้เอง
  • globalSetup — "ก่อนจะรัน Test ทั้งหมด ให้รันไฟล์นี้ก่อนหนึ่งครั้ง" เดี๋ยวเราจะไปสร้างมันกัน
  • clearMocks และ restoreMocks — ล้าง Mock ที่สร้างไว้ให้อัตโนมัติทุกครั้งที่จบ Test แต่ละตัว เพราะการปล่อยให้ Mock ค้างข้ามไปยัง Test ตัวถัดไปคือ Anti-pattern ที่ทำให้ Test ผูกกันเอง หลักการคือผมต้องหยิบ Test ตัวไหนมารันเดี่ยว ๆ ก็ได้ แล้วผลต้องออกมาเหมือนตอนรันพร้อมกันทั้งชุด
  • fileParallelism: false — โดยปกติ Vitest รันไฟล์ Test พร้อมกันหลายไฟล์เพื่อความเร็ว แต่ Test ของเราทุกตัวใช้ฐานข้อมูลตัวเดียวกัน ถ้าสามตัววิ่งพร้อมกันแล้วต่างก็ Insert User อีเมลเดียวกัน มันจะชน Unique Constraint หรือตัวหนึ่งอาจลบข้อมูลที่อีกตัวเพิ่งสร้าง ผลคือ Test พังบ้างผ่านบ้างแบบไม่มีเหตุผล เราจึงสั่งให้รันทีละไฟล์เรียงกันไป (ถ้าไปเจอตัวอย่างเก่า ๆ ที่ใช้ poolOptions.threads.singleThread นั่นคือวิธีของ Vitest 3 ซึ่งถูกถอดออกใน Vitest 4 แล้ว — ใส่ไปมันจะถูกเมินเงียบ ๆ แล้ว Test จะกลับมาพังแบบสุ่มทันที)
  • plugins: [] — ว่างเปล่าเพราะเราไม่ต้องการอะไรเพิ่มเลย Vitest ทำงานกับโปรเจกต์ TypeScript ของเราได้ตั้งแต่แกะกล่อง

Global Setup — เตรียมฐานข้อมูลให้พร้อมทุกครั้ง

สร้างไฟล์ tests/setup/globalSetup.ts หน้าที่ของมันคือ ล้างของเก่าทิ้งแล้ว Push Schema ล่าสุดลงไปใหม่ ก่อน Test ทุกรอบ

import { prisma } from '../../src/db/connection.ts'
import { execSync } from 'child_process'

export default async function setup() {
  console.log('💾 Setting up the test db')
  try {
    console.log('🚀 Pushing schema using prisma db push...')
    execSync('npx prisma db push --force-reset', {
      stdio: 'inherit',
      cwd: process.cwd(),
    })

    console.log('✅ Test DB created')
  } catch (e) {
    console.error('❌ Fail to setup test db', e)
    throw e
  }

  return async () => {
    try {
      await prisma.$executeRaw`DROP TABLE IF EXISTS entries, habit_tags, habits, tags, users CASCADE`
      process.exit(0)
    } catch (e) {
      console.error('❌ Fail to clean up test db', e)
      throw e
    }
  }
}

execSync จาก Node.js คือการสั่งรันคำสั่ง Terminal จากในโค้ด เราใช้มันเรียก prisma db push เพราะฐานข้อมูลทดสอบของเราคงไม่ได้ตามทันการแก้ Schema ล่าสุดเสมอ แทนที่จะต้องมานั่งจำว่าต้อง Push เอง ก็ให้สคริปต์นี้ทำให้ทุกครั้งที่รัน Test เลย

Flag ที่เพิ่มเข้ามา — --force-reset คือสั่งให้ล้าง Database ทิ้งทั้งก้อนก่อนแล้วค่อยสร้างตารางตาม Schema ใหม่หมด เราจึงไม่ต้องเขียนคำสั่ง DROP TABLE เองสักบรรทัดในขาเข้า (Flag นี้อันตรายมากถ้าไปเจอกับ Database จริง แต่กับ Database ทดสอบมันคือสิ่งที่เราต้องการพอดี) ถ้าไปเจอตัวอย่างเก่าที่ใส่ --skip-generate มาด้วย ให้ตัดทิ้งได้เลย เพราะ Prisma 7 ถอด Flag นี้ออกไปแล้ว — db push รุ่นใหม่ไม่ Generate Client ซ้ำให้อยู่แล้ว จึงไม่มีอะไรต้อง Skip

แล้วมันรู้ได้อย่างไรว่าต้อง Push ใส่ Database ทดสอบ — จำได้ไหมว่า prisma7.config.ts ของเรา Import env.ts เข้ามาใช้ และ env.ts เลือกโหลด .env หรือ .env.test ตามค่า APP_STAGE เมื่อคำสั่ง npm test ของเราตั้ง APP_STAGE=test ไว้ (เดี๋ยวทำกันท้ายบท) Environment นั้นจะถูกส่งต่อไปยัง Process ลูกที่ execSync เปิดด้วย CLI ของ Prisma จึงชี้ไปที่ Database ทดสอบให้เองพอดี โดยเราไม่ต้องส่ง URL อะไรให้มันเลย

Flag ที่ส่งให้ execSync — stdio: 'inherit' แปลว่า "เอา Output ของ Terminal ลูกมาแสดงใน Terminal ของเราด้วย" เราจะได้เห็นว่า Prisma ทำอะไรอยู่ ส่วน cwd คือบอกว่าให้รันคำสั่งจากโฟลเดอร์ไหน

ค่าที่ Return ออกไปเป็น Function — Vitest จะเก็บฟังก์ชันที่เรา Return ไว้แล้วเรียกมันตอน Test ทั้งหมดจบลง นี่คือจังหวะเก็บกวาด เราล้างตารางทิ้งด้วยหลักคิดง่าย ๆ ว่า มายังไงก็ทิ้งไว้อย่างนั้น เผื่อวันหนึ่งมีโปรแกรมอื่นมาใช้ฐานข้อมูลนี้โดยไม่ผ่านสคริปต์ของเรา ตัวที่ใช้คือ prisma.$executeRaw ซึ่งเป็นช่องทางเขียน SQL ดิบ ๆ ผ่าน Prisma ที่เรายังไม่เคยใช้ในคอร์สนี้ เหมาะกับงานระดับโครงสร้างแบบนี้ที่ Method ปกติไม่มีให้ (CASCADE ต่อท้ายคือให้ลบความสัมพันธ์ที่ผูกอยู่ไปด้วย) ปิดท้ายด้วย process.exit(0) ไม่งั้นโปรเซสจะค้างอยู่อย่างนั้น ทั้งที่ Test จบไปแล้ว

Helper Functions สำหรับสร้างข้อมูลทดสอบ

เกือบทุก Test ของเราต้องมี User สักคนก่อนถึงจะทำอะไรได้ ถ้าต้องเขียนโค้ดสร้าง User ใหม่ในทุกไฟล์ Test คงไม่ไหว สร้างไฟล์ tests/helpers/dbHelpers.ts ขึ้นมาเก็บงานพวกนี้ หน้าตาของมันคล้ายสคริปต์ Seed ในบทที่ 19 อยู่พอสมควร

import { prisma } from '../../src/db/connection.ts'
import type { NewUser, NewHabit } from '../../src/db/types.ts'
import { hashPassword } from '../../src/utils/password.ts'
import { generateToken } from '../../src/utils/jwt.ts'

export const createTestUser = async (userData: Partial<NewUser> = {}) => {
  const defaultData = {
    email: `test-${Date.now()}-${Math.random()}@example.com`,
    username: `testuser-${Date.now()}-${Math.random()}`,
    password: 'adminpassword1234',
    firstName: 'Test',
    lastName: 'User',
    ...userData,
  }

  const hashedPassword = await hashPassword(defaultData.password)
  const user = await prisma.user.create({
    data: {
      ...defaultData,
      password: hashedPassword,
    },
  })

  const token = await generateToken({
    id: user.id,
    email: user.email,
    username: user.username,
  })

  return { token, user, rawPassword: defaultData.password }
}

export const createTestHabit = async (
  userId: string,
  habitData: Partial<NewHabit> = {}
) => {
  const defaultData = {
    name: `Test habit ${Date.now()}`,
    description: 'A test habit',
    frequency: 'daily',
    targetCount: 1,
    ...habitData,
  }

  const habit = await prisma.habit.create({
    data: {
      userId,
      ...defaultData,
    },
  })

  return habit
}

export const cleanupDatabase = async () => {
  await prisma.entry.deleteMany()
  await prisma.habit.deleteMany()
  await prisma.user.deleteMany()
  await prisma.habitTag.deleteMany()
  await prisma.tag.deleteMany()
}

รูปแบบ "ค่าตั้งต้นบวกค่าที่ส่งมาทับ" คือหัวใจของไฟล์นี้ ทุกฟังก์ชันรับ Object มาแบบ Partial ของ Type ที่เรา Export ไว้ในบทที่ 17 แล้ว Spread ทับค่าตั้งต้น ผลคือ Test ที่ไม่สนใจรายละเอียดก็เรียก createTestUser() เปล่า ๆ ได้เลย ส่วน Test ที่อยากได้อีเมลเจาะจงก็ส่งเฉพาะ Field นั้นมา รูปแบบนี้มีชื่อเรียกว่า Test Data Builder และคุณจะเจอมันในโปรเจกต์อื่น ๆ อีกเยอะ

Date.now() กับ Math.random() ต่อท้ายอีเมลและ Username เพื่อไม่ให้ข้อมูลชนกันเอง ถ้าฮาร์ดโค้ดเป็น test@example.com ไว้ Test ตัวที่สองจะพังทันทีเพราะอีเมลซ้ำ

เรา Hash รหัสผ่านเองในนี้ เพราะฐานข้อมูลจริงไม่เคยเก็บรหัสผ่านดิบ ถ้า Insert ดิบ ๆ ลงไป Test เรื่องการ Login จะพังทันทีเพราะ comparePassword เทียบไม่ผ่าน แล้วเรา Return rawPassword กลับออกไปด้วย เพราะ Test ที่จะลอง Login ต้องใช้รหัสผ่านตัวจริงส่งขึ้นไป

อาจมีคนสงสัยว่าทำไมไม่เรียก Controller register ที่เขียนไว้แล้วให้จบ ๆ ไป เพราะเรากำลังจะเขียน Test เพื่อทดสอบ Controller ตัวนั้นอยู่ไงครับ ถ้าเครื่องมือที่ใช้เตรียมข้อมูลเป็นตัวเดียวกับสิ่งที่กำลังถูกทดสอบ พอมันพัง เราจะแยกไม่ออกเลยว่าใครพัง

ลำดับการลบใน cleanupDatabase ปลอดภัย เพราะ Foreign Key ทุกตัวใน Schema ของเราตั้ง onDelete: Cascade ไว้ตั้งแต่บทที่ 16 การลบแถวฝั่งแม่จึงพาแถวลูกหายตามไปด้วยเสมอ ไม่มีทางค้าง Foreign Key Constraint

บอก Vitest ว่าให้ใช้ .env.test

เหลืออีกชิ้นเดียว เปิด package.json แล้วแก้สคริปต์ test

"scripts": {
  "test": "cross-env APP_STAGE=test vitest run",
  "test:watch": "vitest",
  "test:coverage": "vitest run --coverage"
}

cross-env คือ Package ที่ช่วยตั้ง Environment Variable ก่อนรันคำสั่ง โดยเขียนได้เหมือนกันทุกระบบปฏิบัติการ สิ่งที่เกิดขึ้นคือ APP_STAGE ถูกตั้งเป็น test ก่อน แล้ว vitest run ค่อยเริ่มทำงาน

จำ env.ts ในบทที่ 6 ได้ไหมครับ ที่มันดู APP_STAGE แล้วเลือกว่าจะโหลด .env หรือ .env.test — บรรทัดนี้แหละคือเหตุผลที่เราทำมันไว้ตั้งแต่ต้นคอร์ส ประเด็นสำคัญคือคนที่ต้องอ่านค่าให้ถูกไฟล์ไม่ใช่ตัว Vitest แต่เป็น โค้ดของแอปที่กำลังถูกทดสอบ ต่างหาก เพราะมันคือคนที่ Import env.ts เข้าไปใช้เชื่อมต่อฐานข้อมูลจริง ๆ

ทดสอบว่าที่ตั้งค่ามาทั้งหมดใช้ได้จริง

ก่อนจะไปเขียน Test จริงในบทหน้า เรามาพิสูจน์กันก่อนว่าทุกชิ้นต่อกันติด สร้างไฟล์ tests/setup.test.ts ที่ไม่ได้ทดสอบอะไรเลยนอกจากตัว Setup เอง

import { createTestUser, cleanupDatabase } from './helpers/dbHelpers.ts'

describe('Test Setup Verification', () => {
  test('should connect to test database', async () => {
    const { user, token } = await createTestUser()

    expect(user).toBeDefined()
    expect(user.email).toContain('@example.com')
    expect(token).toBeDefined()

    await cleanupDatabase()
  })
})

สังเกตว่าเราไม่ได้ Import describe, test หรือ expect เลยสักตัว เพราะ globals: true จัดการให้แล้ว จากนั้นสั่งรัน

npm test setup.test.ts

คำที่ต่อท้าย npm test ไม่จำเป็นต้องเป็นชื่อไฟล์เต็ม ๆ นะครับ Vitest ใช้มันเป็นคำค้นแล้วรันทุกไฟล์ที่ชื่อตรงกับรูปแบบนั้น พิมพ์แค่ npm test setup ก็ได้ผลเหมือนกัน ส่วน npm test เปล่า ๆ จะรันทุกไฟล์

สิ่งที่ควรเห็นใน Terminal คือข้อความว่ากำลังเตรียมฐานข้อมูล ตามด้วย Output ของ prisma db push ที่สร้างตารางให้ แล้วจบด้วย Test สีเขียวหนึ่งตัว ถ้าเห็นครบแปลว่าทั้ง Config, Global Setup, Helper และการโหลด .env.test ทำงานถูกต้องหมด

ลองรันซ้ำอีกรอบก็ได้ ผลจะเหมือนเดิมทุกครั้ง เพราะตารางถูกล้างแล้วสร้างใหม่ตั้งแต่ต้นเสมอ — ความคาดเดาได้แบบนี้แหละคือสิ่งที่เราลงทุนตั้งค่ากันมาทั้งบท บทหน้าเราจะเอาพื้นฐานนี้ไปเขียน Test ที่ยิงเข้า API ของเราจริง ๆ
