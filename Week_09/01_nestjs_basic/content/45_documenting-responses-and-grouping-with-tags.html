อธิบาย Responses และจัดกลุ่ม API ด้วย Tags

บทนี้เราจะทำอะไรบ้าง

  • เพิ่ม response documentation ให้ตรงกับ status code ที่ endpoint ส่งจริง
  • เลือกใช้ shorthand decorators เช่น @ApiNotFoundResponse() ได้เหมาะสม
  • ใช้ @ApiTags() จัดกลุ่ม endpoints ตาม business domain
  • ตรวจเอกสารของ coffees resource ได้ทั้งขาสำเร็จและขาผิดพลาด

เอกสารที่ดีบอกทั้งขาสำเร็จและขาพลาด

ตอนนี้ Swagger UI ของเราแสดง request ได้ครบ แต่ฝั่ง response ยังมีแค่ค่า default ที่ Nest ใส่ให้ (เช่น 200/201) ทั้งที่ endpoint จริงของเราตอบได้หลายแบบ — GET /coffees/:id อาจตอบ 404 เมื่อไม่พบ, endpoint ที่มี guard คุมอาจตอบ 403 การประกาศ response เหล่านี้ช่วยให้ผู้ใช้ API เขียนโค้ดฝั่ง client รองรับได้ตั้งแต่ยังไม่ยิงจริง

วิธีพื้นฐานคือ @ApiResponse ที่ระบุ status และ description ติดไว้บน handler method

// coffees.controller.ts
import { ApiResponse } from '@nestjs/swagger';

@ApiResponse({ status: 403, description: 'Forbidden.' }) // 👈 แบบเต็ม
@Post()
create(@Body() createCoffeeDto: CreateCoffeeDto) {
  return this.coffeesService.create(createCoffeeDto);
}

Shorthand decorators: อ่านง่ายกว่าเมื่อ status ชัดเจน

@nestjs/swagger มี decorator แบบย่อสำหรับ status ที่ใช้บ่อย ผลในเอกสารเหมือนกับ @ApiResponse() แต่ชื่อ decorator ช่วยให้เราอ่านโค้ดได้เร็วขึ้น

import { ApiForbiddenResponse } from '@nestjs/swagger';

@ApiForbiddenResponse({ description: 'Forbidden.' }) // 👈 แบบย่อ ให้ผลเหมือนด้านบน
@Post()
create() { /* ... */ }
รูปแบบตัวอย่างเหมาะเมื่อ
@ApiResponse@ApiResponse({ status: 403, description: 'Forbidden.' })ต้องการระบุ status เป็นตัวเลข หรือ status ที่ไม่มี shorthand
Shorthand@ApiForbiddenResponse({ description: 'Forbidden.' })status ที่ใช้บ่อย เช่น @ApiOkResponse, @ApiNotFoundResponse, @ApiCreatedResponse

Decorator เหล่านี้เปลี่ยนแค่เอกสาร ไม่ได้เปลี่ยนพฤติกรรมจริงของ endpoint — endpoint จะตอบ 403 ได้ก็ต่อเมื่อมี guard หรือ logic ที่ throw จริง อย่าประกาศ response ที่โค้ดไม่มีวันตอบ เพราะเอกสารที่โกหกแย่กว่าเอกสารที่ไม่ครบ

เอกสารที่โตขึ้นต้องการหมวดหมู่

ตอนนี้ทุก endpoint ของเรากองรวมกันในหมวด default ของ Swagger UI ซึ่งพออยู่ได้กับ resource เดียว แต่แอปจริงมักมีหลาย resource — coffees, users, orders — การไล่หา endpoint ในกองเดียวจะยากขึ้นเรื่อย ๆ OpenAPI แก้เรื่องนี้ด้วยแนวคิด tag: ป้ายกำกับที่ Swagger UI ใช้จัดกลุ่มและพับ/กาง endpoint เป็นหมวด

ใน NestJS แค่ติด @ApiTags ไว้บน controller ทุก endpoint ในนั้นก็ย้ายเข้าหมวดเดียวกันทั้งหมด

// coffees.controller.ts
import { ApiTags } from '@nestjs/swagger';

@ApiTags('coffees') // 👈 ทุก endpoint ใน controller นี้เข้าหมวด "coffees"
@Controller('coffees')
export class CoffeesController { /* ... */ }

ติดระดับ method ได้เช่นกันเมื่อบาง endpoint ควรไปอยู่หมวดอื่น เช่น endpoint รายงานภายใน controller เดียวกันอาจติด @ApiTags('reports') เฉพาะ method นั้น — endpoint หนึ่งมีได้หลาย tag และจะปรากฏในทุกหมวดที่ระบุ

ตั้งชื่อ tag ให้ตรง domain

ชื่อ tag ควรตรงกับ business domain และมักตรงกับ path ของ resource (coffees สำหรับ /coffees) เพื่อให้ผู้อ่านเอกสารเดา URL ได้จากชื่อหมวด แนวทางที่ใช้ได้ดี:

  • ใช้รูปพหูพจน์ตัวพิมพ์เล็กให้เหมือนกันทั้งแอป (coffees ไม่ใช่ Coffee ปน flavors)
  • หนึ่ง controller ต่อหนึ่ง tag เป็นค่าเริ่มต้น — ถ้าอยากได้หลาย tag ใน controller เดียว มักเป็นสัญญาณว่า controller นั้นทำหลาย domain แล้วควรแยก
  • ชื่อ tag เป็นส่วนหนึ่งของสัญญาเอกสาร: เปลี่ยนเมื่อจำเป็นเท่านั้น เพราะเครื่องมือ generate client บางตัวใช้ tag จัดกลุ่มโค้ดที่สร้าง

เติม response documentation และจัดกลุ่ม coffees endpoints

ขั้นที่ 1: ประกาศ response ให้ endpoint ของ coffees

เพิ่ม response ในเอกสารให้ตรงกับพฤติกรรมจริงของ CoffeesController: GET /coffees/:id ตอบ 404 ได้ (เรา throw NotFoundException ไว้แล้ว) และ endpoint ที่คุมด้วย ApiKeyGuard ตอบ 403 ได้ — ยกเว้น findAll เพราะบทที่ 38 ติด @Public() ไว้ ทำให้ guard ไม่ทำงานกับ endpoint นี้เลย และมันจะไม่มีวันตอบ 403 จริง (ตรงกับคำเตือนด้านบน) จึงใช้ create แทนเพราะยังถูก ApiKeyGuard คุมอยู่

# ใน coffees.controller.ts # 1) เพิ่ม @ApiNotFoundResponse({ description: 'Coffee not found.' }) บน findOne # 2) เพิ่ม @ApiForbiddenResponse({ description: 'Forbidden.' }) บน create (ไม่ใช่ findAll — findAll ติด @Public() มาตั้งแต่บทที่ 38) npm run start:dev # เปิด http://localhost:3000/api แล้วกางแต่ละ endpoint ดูส่วน Responses

ขั้นที่ 2: จัดหมวด endpoint ของ iluvcoffee

ติด @ApiTags('coffees') บน CoffeesController แล้วรีเฟรช Swagger UI ดูผล ถ้าโปรเจกต์ของคุณมี controller อื่น (เช่น coffee-rating) ให้ติด tag ของมันเองด้วย

# coffees.controller.ts → เพิ่ม @ApiTags('coffees') เหนือ @Controller('coffees') npm run start:dev # เปิด http://localhost:3000/api

ควรได้ผลลัพธ์แบบนี้

ใน Swagger UI ส่วน Responses ของ GET /coffees/{id} แสดงแถว 404 พร้อมคำอธิบาย Coffee not found. เพิ่มจากแถว default และ POST /coffees แสดงแถว 403 Forbidden.

Swagger UI แสดงหัวข้อหมวด coffees ที่พับ/กางได้ โดยมี endpoint ทั้ง 5 ของ CRUD อยู่ข้างใน แทนที่จะกองอยู่ในหมวด default

ลองเช็กให้แน่ใจ

  • กางแต่ละ endpoint ใน Swagger UI แล้วนับแถวในส่วน Responses ว่ามี status ที่เพิ่มครบ
  • ยิง GET /coffees/999 ด้วย Insomnia เพื่อยืนยันว่า 404 ในเอกสารตรงกับพฤติกรรมจริง
  • เปรียบเทียบสองรูปแบบ: เขียน endpoint หนึ่งด้วย @ApiResponse และอีกอันด้วย shorthand แล้วดูว่าเอกสารที่ได้เหมือนกัน
  • ตรวจว่าไม่ได้ประกาศ status ที่โค้ดไม่มีทางตอบจริง
  • เปิด http://localhost:3000/api — ต้องไม่เหลือ endpoint ของ coffees ในหมวด default
  • กด header ของหมวด coffees เพื่อยืนยันว่าพับ/กาง endpoint ทั้งกลุ่มได้
  • ดู JSON ของเอกสารที่ http://localhost:3000/api-json ว่าแต่ละ operation มี field "tags": ["coffees"]
  • ถ้ามีหลาย controller ตรวจว่าแต่ละหมวดตั้งชื่อตามแนวทางเดียวกัน
