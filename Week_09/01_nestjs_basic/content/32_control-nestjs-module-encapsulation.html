ควบคุม Module Encapsulation

เมื่อจบบทนี้ คุณจะสามารถ

  • อธิบายได้ว่าทำไม provider ของ module หนึ่งจึงมองไม่เห็นจาก module อื่นโดย default
  • ใช้ exports และ imports เปิดเผย provider ข้าม module อย่างตั้งใจ
  • อ่าน error Nest can't resolve dependencies แล้วรู้ทันทีว่าต้องแก้ที่ module ใด

Module ทุกตัวถูกห่อหุ้มโดย default

NestJS ตั้งใจให้แต่ละ module เป็นขอบเขตปิด (encapsulated): provider ที่ประกาศใน providers ของ module ใด ใช้ได้เฉพาะภายใน module นั้น ถ้า module อื่นอยากใช้ ต้องเกิดข้อตกลงสองฝั่งเสมอ — ฝั่งเจ้าของประกาศใน exports และฝั่งผู้ใช้เพิ่มเจ้าของเข้า imports ของตัวเอง หลักการนี้บังคับให้ dependency ระหว่าง domain ชัดเจน ไม่มี service ลอยข้าม boundary แบบเงียบ ๆ

เพื่อเห็น encapsulation ทำงานจริง เราจะสร้าง module ใหม่ชื่อ CoffeeRatingModule ที่ต้องพึ่ง CoffeesService จาก CoffeesModule

# สร้าง CoffeeRatingModule ใหม่
nest g mo coffee-rating

# สร้าง CoffeeRatingService ใหม่
nest g s coffee-rating

ทำให้ CoffeeRatingService ใช้ CoffeesService ได้

ลอง inject CoffeesService เข้า constructor ของ CoffeeRatingService ตรง ๆ แอปจะพังตอน start พร้อม error ว่า Nest resolve dependency ไม่ได้ เพราะ CoffeesService ยังถูกห่ออยู่ใน CoffeesModule การแก้ต้องทำครบสองขั้น

// coffees.module.ts — ฝั่งเจ้าของ: เปิดเผย service
@Module({
  controllers: [CoffeesController],
  providers: [CoffeesService],
  exports: [CoffeesService],
})
export class CoffeesModule {}

// coffee-rating.module.ts — ฝั่งผู้ใช้: import module เจ้าของ
@Module({
  imports: [CoffeesModule],
  providers: [CoffeeRatingService],
})
export class CoffeeRatingModule {}

// coffee-rating.service.ts — จากนั้นจึง inject ได้ตามปกติ
@Injectable()
export class CoffeeRatingService {
  constructor(private readonly coffeesService: CoffeesService) {}
}

สังเกตว่าเรา import module ไม่ใช่ตัว service: imports: [CoffeesModule] แปลว่า "ขอใช้ทุกอย่างที่ CoffeesModule ประกาศ export" การเพิ่ม CoffeesService ลง providers ของ CoffeeRatingModule ตรง ๆ เป็น anti-pattern เพราะจะได้ instance แยกอีกตัวแทนที่จะแชร์ตัวเดียวกัน

บทบาทของแต่ละ property ใน @Module

Propertyความหมายผลต่อการมองเห็น
providersสิ่งที่ Nest instantiate ให้ใน module นี้ใช้ได้เฉพาะภายใน module ตัวเอง
exportsprovider (หรือ module) ที่ยอมเปิดเผยออกไปmodule อื่นที่ import เราเห็นได้
importsmodule อื่นที่เราต้องพึ่งพาได้ทุกอย่างที่ module นั้น export
controllerscontroller ที่ผูก route ใน module นี้ไม่เกี่ยวกับการ export — route เป็น global อยู่แล้ว

สร้าง CoffeeRatingModule ที่พึ่ง CoffeesService

generate module และ service ใหม่ด้วย Nest CLI, inject CoffeesService เข้า CoffeeRatingService แล้วดู error ก่อนหนึ่งครั้งเพื่อรู้จักหน้าตาของมัน จากนั้นแก้ด้วย exports/imports ให้แอปกลับมา start ได้

nest g mo coffee-rating nest g s coffee-rating # inject CoffeesService แล้วสังเกต error ตอน start # จากนั้นเพิ่ม exports: [CoffeesService] ใน CoffeesModule # และ imports: [CoffeesModule] ใน CoffeeRatingModule npm run start:dev

ผลลัพธ์ที่คาดหวัง

ก่อนแก้: แอป crash พร้อมข้อความ Nest can't resolve dependencies of the CoffeeRatingService (?) ซึ่งบอกว่า argument ตัวแรกหาไม่เจอ หลังแก้: แอป start สะอาด และ CoffeeRatingService เรียกเมธอดของ CoffeesService ตัวเดียวกับที่ controller ใช้ได้ (singleton แชร์กัน)

ตรวจว่าใช้งานได้จริง

  • อ่าน error ตอนยังไม่ export ว่าชื่อ class และตำแหน่ง ? ใน constructor ชี้ถึง dependency ตัวไหน
  • ตรวจว่า CoffeesModule มี exports: [CoffeesService] และ CoffeeRatingModule มี imports: [CoffeesModule]
  • ลองลบ exports ออกชั่วคราว — แอปต้องพังแบบเดิม แสดงว่า encapsulation ยังทำงาน
  • ตรวจว่าไม่ได้เผลอใส่ CoffeesService ใน providers ของ CoffeeRatingModule ซึ่งจะสร้าง instance ซ้ำ
