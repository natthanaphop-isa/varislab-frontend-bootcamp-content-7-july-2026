Value-based Providers (useValue)

เมื่อจบบทนี้ คุณจะสามารถ

  • ผูกค่า (instance, object หรือ constant) ที่สร้างไว้แล้วเข้ากับ token ด้วย useValue
  • สลับ CoffeesService ตัวจริงเป็น mock implementation โดยไม่แก้ controller แม้แต่บรรทัดเดียว
  • บอกได้ว่าเมื่อไหร่ useValue เหมาะกว่า useClass

useValue: ส่งค่าที่พร้อมใช้ ไม่ให้ Nest สร้างให้

useValue คือ custom provider แบบที่ตรงไปตรงมาที่สุด: แทนที่จะบอก Nest ว่า "instantiate class นี้ให้หน่อย" เราส่งค่าที่สร้างเสร็จแล้วไปเลย Nest จะไม่เรียก constructor ใด ๆ เพิ่ม แค่จับค่านั้นผูกกับ token แล้วส่งให้ทุกคนที่ inject ค่านี้อาจเป็น instance ที่เรา new เอง, plain object หรือค่า constant ก็ได้

use case คลาสสิกคือการ override service จริงด้วย mock — ตรงกับข้อ "override ด้วย mock ตอนทดสอบ" จากบทที่แล้ว ลองสลับ CoffeesService ทั้งตัวใน module

// mock implementation ของเรา
export class MockCoffeesService { }

@Module({
  providers: [
    {
      provide: CoffeesService,
      useValue: new MockCoffeesService(), // ส่ง instance ที่สร้างเองเข้าไป
    }
  ]
})
export class CoffeesModule {}

สังเกตว่า token ยังเป็น CoffeesService เหมือนเดิม — controller และ service อื่นที่เขียน constructor(private readonly coffeesService: CoffeesService) ไม่รู้ด้วยซ้ำว่าเบื้องหลังถูกสลับเป็นของปลอมแล้ว นี่คือพลังของการแยก token ออกจาก implementation

เมื่อ mock ยังไม่มีเมธอดครบ (อย่าง MockCoffeesService ที่เป็น class เปล่า) endpoint ที่เรียกเมธอดเหล่านั้นจะพัง runtime แบบ this.coffeesService.findAll is not a function — ในโค้ดจริงควรให้ mock implement interface เดียวกับของจริง หรือใช้เฉพาะในเทสต์ที่ควบคุมขอบเขตชัดเจน อย่าลืมเอาการ override ออกก่อนไปบทถัดไป

useValue กับ useClass เลือกอย่างไร

ประเด็นuseValueuseClass
ใครสร้าง instanceเราสร้างเอง (หรือเป็นค่าอยู่แล้ว)Nest instantiate ให้
Dependency injection ใน constructorไม่ได้ — ค่าถูกสร้างก่อนถึงมือ Nestได้ตามปกติ
เหมาะกับmock, config object, ค่าคงที่สลับ implementation ที่ยังต้องการ DI

สลับ CoffeesService เป็น mock แล้วดูผลจริง

ใน coffees.module.ts ประกาศ MockCoffeesService แล้วผูกเข้า token CoffeesService ด้วย useValue ตามโค้ดข้างบน รันแอปแล้วยิง GET /coffees เพื่อดูว่าเกิดอะไรขึ้นเมื่อ mock ไม่มีเมธอด findAll จากนั้นถอดการ override ออกให้แอปกลับสู่สภาพเดิม

// 1) เพิ่ม provider object ใน coffees.module.ts ตามตัวอย่าง // 2) รันแอป npm run start:dev // 3) ยิงทดสอบ curl http://localhost:3000/coffees // 4) ถอด useValue ออก กลับไปใช้ providers: [CoffeesService]

ผลลัพธ์ที่คาดหวัง

แอป start ได้ปกติ (DI resolve สำเร็จเพราะ token มีค่าผูกอยู่) แต่เมื่อยิง GET /coffees จะได้ 500 Internal Server Error เพราะ handler เรียก findAll ที่ mock ไม่มี — พฤติกรรมนี้ยืนยันว่า instance ที่อยู่หลัง token ถูกเปลี่ยนเป็นของเราจริง เมื่อถอด override ออก endpoint กลับมาตอบข้อมูลกาแฟตามเดิม

ตรวจว่าใช้งานได้จริง

  • ตอน override: แอป start ผ่าน แต่ GET /coffees ได้ 500 พร้อม stack trace ชี้ว่าเมธอดหายไป
  • ลองเพิ่มเมธอด findAll() ที่ return array ปลอมใน MockCoffeesService แล้วเห็นข้อมูลปลอมนั้นออกทาง endpoint โดยไม่แตะ controller
  • หลังถอด override: GET /coffees กลับมาอ่านจากฐานข้อมูลจริง
  • อธิบายได้ว่าทำไม constructor ของ controller ไม่ต้องแก้เลยตลอดการทดลองนี้
