ดึง Models พร้อม Relations

เมื่อจบบทนี้ คุณจะสามารถ

  • อธิบายได้ว่าทำไม Prisma ไม่โหลด relation มาให้อัตโนมัติ และต้องขอเองอย่างไร
  • ใช้ option include ใน findMany() และ findUnique() เพื่อดึงข้อมูลที่ผูกกันมาด้วย
  • ตรวจสอบ response ว่ามี array flavors ติดมากับกาแฟแต่ละตัวจริง

Relation ไม่ถูกโหลดมาโดย default

หลังจากบทที่แล้ว ฐานข้อมูลของเรามี 3 ตาราง: coffee, flavor และ _CoffeeToFlavor ที่แทนความสัมพันธ์ many-to-many แต่ถ้ายิง GET /coffees ตอนนี้ จะพบว่า response ไม่มี flavors กลับมาเลย — Prisma จงใจไม่ join ตารางให้อัตโนมัติ เพราะการโหลด relation ทุกครั้งโดยไม่จำเป็นคือต้นทุน query ที่แพงโดยเปล่าประโยชน์ (และ type ที่ได้กลับมาจะบอกตรง ๆ ว่าไม่มี flavors ให้ใช้)

เมื่อไหร่ที่อยากได้ relation มาด้วย เราต้องระบุอย่างชัดเจนผ่าน option include

return this.prisma.coffee.findMany({
  include: {
    flavors: true,
  },
});

เพิ่ม include เข้า findAll และ findOne

ใน CoffeesService จุดที่อ่านข้อมูลมีสองแห่งคือ findAll() และ findOne() เพิ่ม option เดียวกันเข้าไปทั้งคู่ — สังเกตว่า type ของค่าที่คืนจะเปลี่ยนตาม: ตอนนี้ TypeScript รู้แล้วว่ากาแฟแต่ละตัวมี flavors: Flavor[] ติดมา

import { Injectable, NotFoundException } from '@nestjs/common';
import { PrismaService } from '../prisma/prisma.service.js';
import { CreateCoffeeDto } from './dto/create-coffee.dto.js';
import { UpdateCoffeeDto } from './dto/update-coffee.dto.js';

@Injectable()
export class CoffeesService {
  constructor(private readonly prisma: PrismaService) {}

  findAll() {
    return this.prisma.coffee.findMany({
      include: {
        flavors: true,
      },
    });
  }

  async findOne(id: string) {
    const coffee = await this.prisma.coffee.findUnique({
      where: {
        id: +id,
      },
      include: {
        flavors: true,
      },
    });
    if (!coffee) {
      throw new NotFoundException(`Coffee #${id} not found`);
    }
    return coffee;
  }

  create(createCoffeeDto: CreateCoffeeDto) {
    const { flavors, ...coffeeData } = createCoffeeDto;
    return this.prisma.coffee.create({
      data: {
        ...coffeeData,
        flavors: {
          connectOrCreate: this.connectOrCreateFlavors(flavors),
        },
      },
    });
  }

  async update(id: string, updateCoffeeDto: UpdateCoffeeDto) {
    await this.findOne(id); // ให้ id ที่ไม่มีจริงได้ 404 แบบเดียวกัน
    const { flavors, ...coffeeData } = updateCoffeeDto;
    return this.prisma.coffee.update({
      where: { id: +id },
      data: {
        ...coffeeData,
        flavors: flavors && {
          connectOrCreate: this.connectOrCreateFlavors(flavors),
        },
      },
    });
  }

  private connectOrCreateFlavors(names: string[]) {
    return names.map((name) => ({
      where: { name },
      create: { name },
    }));
  }

  // remove คงเดิมจากบทที่ 24
}

โค้ดนี้ทำให้ create()/update() คอมไพล์ผ่านและบันทึกความสัมพันธ์ลง _CoffeeToFlavor ได้จริง ด้วย connectOrCreate: ค้นหา Flavor จากชื่อ (ต้องใช้ฟิลด์ @unique) เจอก็ผูกของเดิม ไม่เจอก็สร้างใหม่แล้วผูกให้

เวอร์ชันนี้ยังไม่สมบูรณ์ — เหลือสองจุดที่บทที่ 27 จะแก้ให้ถูกต้อง: (1) update() ยังไม่มี set: [] ก่อน connectOrCreate จึงเป็นการเพิ่ม flavor เข้าไปเรื่อย ๆ ไม่ใช่แทนที่ทั้งชุดตามที่ PATCH ควรทำ (PATCH ด้วย flavors: ["caramel"] บนกาแฟที่มี chocolate, vanilla อยู่แล้ว จะได้ chocolate, vanilla, caramel ไม่ใช่ caramel เพียวๆ) และ (2) ทั้ง create() และ update() ยังไม่มี include: { flavors: true } ผลคือ response ของ POST/PATCH จะไม่มี field flavors ติดมา (ทั้งที่ข้อมูลถูกบันทึกลงฐานข้อมูลถูกต้องแล้ว — ต้องยิง GET แยกถึงจะเห็น) เก็บสองจุดนี้ไว้ในใจ เดี๋ยวบทที่ 27 จะอธิบายและแก้ให้ครบ

include ซ้อนกันได้ เช่น include: { flavors: { include: { coffees: true } } } เพื่อดึงกาแฟตัวอื่นที่มี flavor เดียวกันมาด้วย และถ้าต้องการเฉพาะบางคอลัมน์ให้ใช้ select แทน (select: { id: true, name: true, flavors: true }) — แต่อย่าใช้ include กับ select ในระดับเดียวกัน Prisma จะไม่ยอม ระบุเฉพาะเท่าที่หน้างานต้องใช้จริง response จะได้ไม่บวมและ query ไม่ join เกินจำเป็น

อย่าแก้ปัญหา "อยากได้ relation ทุกครั้ง" ด้วยการทำ helper ที่แอบใส่ include ให้ทุก query ทั้งระบบ — มันทำให้ทุก query ในแอปแบกการ join นั้นไปด้วยโดยมองไม่เห็นจากโค้ดที่เรียก การระบุที่จุดเรียกแบบนี้ชัดเจนกว่า และ type ที่ได้ก็ตรงกับข้อมูลจริงเสมอ

ทำให้ endpoint คืน flavors มาด้วย

เพิ่ม include ใน findAll() และ findOne() แล้วแทนที่ create()/update() ที่คอมเมนต์ไว้ตั้งแต่บทที่ 25 ด้วยโค้ดด้านบน ตอนนี้ POST/PATCH เริ่มบันทึกความสัมพันธ์ได้แล้ว (แม้จะยังไม่สมบูรณ์ตามที่เตือนไว้ข้างบน) ลองสร้างข้อมูลผ่าน POST ได้เลย หรือจะแทรกข้อมูลตรงในฐานข้อมูลเพื่อทดสอบ include แยกต่างหากก็ได้เช่นกัน

POST http://localhost:3000/coffees { "name": "Shipwreck Roast", "brand": "Buddy Brew", "flavors": ["chocolate", "vanilla"] } # หรือใส่ข้อมูลตรงใน pgAdmin Query Tool INSERT INTO flavor (name) VALUES ('chocolate'), ('vanilla'); INSERT INTO coffee (name, brand) VALUES ('Shipwreck Roast', 'Buddy Brew'); INSERT INTO "_CoffeeToFlavor" ("A", "B") VALUES (1, 1), (1, 2); # แล้วยิงทดสอบ GET http://localhost:3000/coffees GET http://localhost:3000/coffees/1

ผลลัพธ์ที่คาดหวัง

ทั้งสอง endpoint คืนกาแฟพร้อม property flavors เป็น array ของ object เต็ม ๆ เช่น [{ "id": 1, "name": "chocolate" }, { "id": 2, "name": "vanilla" }] ไม่ใช่ array ว่างหรือหายไปเหมือนก่อนหน้า

ตรวจว่าใช้งานได้จริง

  • GET /coffees คืนทุกแถวพร้อม flavors ที่ join มาจากตาราง _CoffeeToFlavor
  • GET /coffees/1 คืนกาแฟเดียวพร้อม flavors ครบทุกตัวที่ผูกไว้
  • id ที่ไม่มีจริงยังได้ 404 Coffee #id not found เหมือนเดิม
  • ลองเอา include ออกชั่วคราวแล้วยิงซ้ำ — flavors ต้องหายไป เพื่อยืนยันว่า option นี้คือตัวควบคุมจริง (แล้วใส่กลับ)
  • POST พร้อม flavors แล้วตัว response จะยังไม่มี field flavors ติดมา — ของปกติสำหรับตอนนี้ (ไม่มี include ใน create() อยู่) ยิง GET /coffees แยกแล้วจะเห็นว่าข้อมูลถูกบันทึกจริง
  • PATCH ด้วย flavors ชุดใหม่แล้วสังเกตว่าชุดเดิมไม่ถูกแทนที่ แต่ถูกบวกเพิ่มเข้าไป — ของปกติสำหรับตอนนี้เช่นกัน (ไม่มี set: []) บทที่ 27 จะแก้ให้ถูก
