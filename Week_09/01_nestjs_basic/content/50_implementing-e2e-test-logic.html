เขียน Logic ของ e2e Test

บทนี้เราจะทำอะไรบ้าง

  • ตั้ง ValidationPipe ใน test app ให้เหมือน production เพื่อทดสอบพฤติกรรมจริง
  • ใช้ expect.objectContaining/expect.arrayContaining ตรวจ response ที่มี field เกินกว่าที่สนใจ
  • แปลง it.todo ทั้ง 5 เป็น test จริงที่ครอบคลุม Create, Read, Update, Delete

ทำ test app ให้เหมือน production ก่อน

createNestApplication() ให้แอปเปล่า ๆ — แต่แอปจริงของเราใน main.ts เปิด ValidationPipe พร้อม options หลายตัว ถ้า test ไม่ตั้งให้เหมือนกัน เราจะทดสอบแอปคนละใบกับที่ deploy จึงต้องยกมาทั้งชุด

app = moduleFixture.createNestApplication();
app.useGlobalPipes(
  new ValidationPipe({
    whitelist: true,
    transform: true,
    forbidNonWhitelisted: true,
    transformOptions: {
      enableImplicitConversion: true,
    },
  }),
);
await app.init();
httpServer = app.getHttpServer(); // เก็บไว้ใช้ซ้ำทุก test

คอร์สต้นฉบับ (ยุค Jest) ใช้ jasmine.objectContaining() — ใน Vitest ไม่มี jasmine helpers ให้ใช้ matcher บน object expect โดยตรง เช่น expect.objectContaining() และ expect.arrayContaining() ซึ่งมีให้ครบ

ตรวจ response ที่มีมากกว่าที่เราส่งไป

เมื่อ POST coffee เข้าไป response จะมี field ที่เราไม่ได้ส่ง เช่น id และ flavors ที่กลายเป็น entity object ({ id, name }) แทน string เปล่า ๆ การ toEqual ตรง ๆ จึงไม่ผ่าน — ใช้ matcher แบบ partial แทน

const coffee = {
  name: 'Shipwreck Roast',
  brand: 'Buddy Brew',
  flavors: ['chocolate', 'vanilla'],
};
const expectedPartialCoffee = expect.objectContaining({
  ...coffee,
  flavors: expect.arrayContaining(
    coffee.flavors.map(name => expect.objectContaining({ name })),
  ),
});

CRUD ครบ 5 เส้น

it('Create [POST /]', () => {
  return request(httpServer)
    .post('/coffees')
    .send(coffee as CreateCoffeeDto)
    .expect(HttpStatus.CREATED)
    .then(({ body }) => {
      expect(body).toEqual(expectedPartialCoffee);
    });
});

it('Get all [GET /]', () => {
  return request(httpServer)
    .get('/coffees')
    .then(({ body }) => {
      expect(body.length).toBeGreaterThan(0);
      expect(body[0]).toEqual(expectedPartialCoffee);
    });
});

it('Get one [GET /:id]', () => {
  return request(httpServer)
    .get('/coffees/1')
    .then(({ body }) => {
      expect(body).toEqual(expectedPartialCoffee);
    });
});

it('Update one [PATCH /:id]', () => {
  const updateCoffeeDto: UpdateCoffeeDto = {
    ...coffee,
    name: 'New and Improved Shipwreck Roast'
  }
  return request(httpServer)
    .patch('/coffees/1')
    .send(updateCoffeeDto)
    .then(({ body }) => {
      expect(body.name).toEqual(updateCoffeeDto.name);

      return request(httpServer)
        .get('/coffees/1')
        .then(({ body }) => {
          expect(body.name).toEqual(updateCoffeeDto.name);
        });
    });
});

it('Delete one [DELETE /:id]', () => {
  return request(httpServer)
    .delete('/coffees/1')
    .expect(HttpStatus.OK)
    .then(() => {
      return request(httpServer)
        .get('/coffees/1')
        .expect(HttpStatus.NOT_FOUND);
    })
});

สังเกตว่า test เหล่านี้ต่อเนื่องกันโดยตั้งใจ: Create ใส่ข้อมูลที่ Get/Update/Delete ใช้ต่อ และสองเส้นท้ายยิง request ซ้ำเพื่อยืนยันผลข้างเคียง — Update แล้ว Get ต้องเห็นชื่อใหม่, Delete แล้ว Get ต้องได้ 404 นี่คือการทดสอบ ผลที่คงอยู่จริงใน database ไม่ใช่แค่เชื่อ response แรก

อย่าลืม import ที่ต้องใช้เพิ่ม: ValidationPipe, HttpStatus จาก @nestjs/common, import request from 'supertest' (default import) และ DTO ทั้งสองตัวจาก ../../src/coffees/dto/….js ส่วนตัวแปร httpServer (ประกาศคู่กับ let app: INestApplication; จากบทที่ 49) อย่า type ให้เป็น HttpServer จาก @nestjs/common แม้จะดูเข้าท่า — type ของ supertest คาดหวัง App ของตัวเอง (ใกล้เคียง Node http.Server) ซึ่ง HttpServer ของ Nest ไม่ตรงกัน ส่ง request(httpServer) จะเจอ TS2345 ตอน compile ปล่อยให้ TypeScript อนุมาน type จาก app.getHttpServer() เอง (หรือประกาศแบบไม่ระบุ type ก็ได้) แทน
