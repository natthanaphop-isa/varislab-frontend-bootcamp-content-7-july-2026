NestJS Fundamentals Workshop · บทที่ 17/58

ป้องกันข้อมูลคำขอที่ไม่พึงประสงค์

บทนี้เราจะทำอะไรบ้าง

  • อธิบายความเสี่ยงของการรับ property ที่ไม่ได้ประกาศไว้ใน DTO (mass assignment)
  • เปิด whitelist เพื่อให้ pipe ตัด property แปลกปลอมทิ้งอัตโนมัติ
  • เปิด forbidNonWhitelisted เมื่อต้องการปฏิเสธ request ที่มีของเกินมาแทนการตัดเงียบ ๆ

ปัญหา: Client ส่งอะไรมาก็รับหมด

ต่อให้เปิด ValidationPipe แล้ว payload ที่มี property เกินจากที่ DTO ประกาศก็ยังไหลผ่านเข้ามาได้ เช่น client แนบ {"name": "Roast", "brand": "Brew", "flavors": [], "isAdmin": true} — ถ้าโค้ดของเรานำ object นี้ไป save ตรง ๆ ค่า isAdmin ที่ไม่มีใครตั้งใจรับก็ติดเข้าไปด้วย ช่องโหว่ตระกูลนี้เรียกว่า mass assignment และเป็นสิ่งที่ต้องปิดตั้งแต่ชั้นรับข้อมูล

whitelist: ตัดของเกินทิ้งเงียบ ๆ

/* main.ts */
app.useGlobalPipes(new ValidationPipe({
    whitelist: true,
}));

เมื่อเปิด whitelist pipe จะลบทุก property ที่ไม่มี decorator ของ class-validator ประกาศไว้ใน DTO ออกจาก object ก่อนส่งถึง handler — client จะส่งอะไรเกินมาก็ตาม สิ่งที่โค้ดเราเห็นมีเฉพาะ field ในสัญญาเท่านั้น

forbidNonWhitelisted: ปฏิเสธไปเลยให้รู้ตัว

/* main.ts */
app.useGlobalPipes(new ValidationPipe({
   forbidNonWhitelisted: true,
   whitelist: true,
}));

บางระบบอยากได้พฤติกรรมที่เข้มกว่า: แทนที่จะตัดเงียบ ๆ ให้ตอบ 400 บอก client ตรง ๆ ว่าส่ง property ที่ไม่รู้จักมา ตัวเลือก forbidNonWhitelisted (ซึ่งต้องใช้คู่กับ whitelist) ทำแบบนั้น:

{
  "statusCode": 400,
  "message": ["property isAdmin should not exist"],
  "error": "Bad Request"
}
การตั้งค่าพฤติกรรมต่อ property เกินเหมาะกับ
ค่า defaultปล่อยผ่านเข้ามาทั้งก้อนไม่แนะนำสำหรับ API ที่รับข้อมูลจากภายนอก
whitelist: trueตัดทิ้งเงียบ ๆ handler เห็นเฉพาะ field ใน DTOAPI ทั่วไปที่อยากทนต่อ client รุ่นเก่า/ใหม่ปะปน
+ forbidNonWhitelisted: trueตอบ 400 พร้อมชื่อ property ที่เกินมาระบบที่ต้องการ contract เข้มงวดและอยากเห็น client ผิดตั้งแต่ dev

whitelist ตัดสินจาก decorator — property ใน DTO ที่ไม่มี validation decorator เลยจะถูกตัดทิ้งไปด้วย ถ้ามี field ที่ไม่ต้องตรวจอะไรจริง ๆ ให้ใส่ @Allow() จาก class-validator กำกับไว้

ลองแนบ property แปลกปลอมแล้วดูชะตากรรมของมัน

เปิด whitelist ก่อน ยิง payload ที่มีของเกิน แล้วเปิด forbidNonWhitelisted เพิ่มและยิงซ้ำ เปรียบเทียบผลทั้งสองแบบ

curl -X POST http://localhost:3000/coffees \ -H "Content-Type: application/json" \ -d '{"name": "Roast", "brand": "Brew", "flavors": ["mocha"], "isAdmin": true}'

ควรได้ผลลัพธ์แบบนี้

โหมด whitelist อย่างเดียว: สร้างสำเร็จ แต่ record ที่ได้ไม่มี isAdmin ติดมาด้วย เมื่อเพิ่ม forbidNonWhitelisted: ได้ 400 พร้อมข้อความ property isAdmin should not exist

ลองเช็กให้แน่ใจ

  • โหมด whitelist: GET /coffees ยืนยันว่ารายการใหม่ไม่มี field isAdmin
  • โหมดเข้ม: response 400 ระบุชื่อ property ที่เกินมาอย่างชัดเจน
  • payload ปกติที่มีเฉพาะ field ตาม DTO ยังผ่านได้ทั้งสองโหมด
  • การตั้งค่าอยู่ที่ main.ts ที่เดียว — มีผลกับทุก endpoint โดยไม่ต้องแก้ controller ใด
