Configuration Namespaces และ Partial Registration

เมื่อจบบทนี้ คุณจะสามารถ

  • สร้าง configuration namespace ด้วย registerAs และวางไว้ใกล้ feature ที่ใช้มัน
  • ลงทะเบียน config เฉพาะส่วนใน feature module ด้วย ConfigModule.forFeature()
  • Inject config แบบ strongly typed ด้วย KEY token และ ConfigType แทนการอ่านผ่าน string

registerAs: config ประจำ feature ที่มีชื่อกำกับ

เมื่อ config โตตามจำนวน feature การกองทุกอย่างไว้ใน app.config.ts เดียวเริ่มไม่ไหว NestJS ให้เราแตก config เป็น namespace ด้วยฟังก์ชัน registerAs — factory เดิมนั่นเอง แต่ผูกไว้ใต้ key ที่ตั้งชื่อให้ และวางไฟล์ไว้ในโฟลเดอร์ของ feature ได้เลย

// src/coffees/coffees.config.ts
import { registerAs } from '@nestjs/config';

export default registerAs('coffees', () => ({
  foo: 'bar',
}));

Partial registration: โหลดเฉพาะที่ module ใช้

แทนที่จะโหลด config ทุกก้อนที่ root เราลงทะเบียนเฉพาะ namespace ที่ module นั้นสนใจด้วย forFeature — แนวเดียวกับ forFeature() ที่ library modules ของ Nest นิยมใช้ (เช่น MongooseModule.forFeature ที่จะเจอในบทที่ 73)

// coffees.module.ts
import coffeesConfig from './coffees.config.js';

@Module({
  imports: [ConfigModule.forFeature(coffeesConfig)],
})
export class CoffeesModule {}

อ่านค่า: แบบ string กับแบบ strongly typed

อ่านผ่าน ConfigService ด้วย string ก็ได้ แต่เสีย type safety ทั้งหมด — พิมพ์ key ผิดก็ได้ undefined เงียบ ๆ:

// วิธีที่ยังไม่เหมาะที่สุด
const coffeesConfig = this.configService.get('coffees');
const foo = this.configService.get('coffees.foo');

วิธีที่คอร์สแนะนำคือ inject ทั้ง namespace ผ่าน token KEY ที่ registerAs สร้างให้ คู่กับ type helper ConfigType ซึ่ง infer ชนิดจาก factory โดยตรง:

import { Inject } from '@nestjs/common';
import type { ConfigType } from '@nestjs/config'; // 👈 import type — ConfigType เป็น type ล้วน และถูกใช้ใน constructor ที่มี decorator (ดูบทที่ 41)
import coffeesConfig from './coffees.config.js';

constructor(
  @Inject(coffeesConfig.KEY)
  private coffeesConfiguration: ConfigType<typeof coffeesConfig>,
) {
  console.log(coffeesConfiguration.foo); // strongly typed!
}

ตอนนี้ autocomplete รู้จัก coffeesConfiguration.foo และถ้าเปลี่ยนโครงสร้างใน factory คอมไพเลอร์จะฟ้องทุกจุดที่ใช้ทันที — ได้ refactoring safety ฟรีจาก TypeScript

แตก config ของ coffees เป็น namespace

สร้าง src/coffees/coffees.config.ts ด้วย registerAs('coffees', ...), ลงทะเบียนผ่าน forFeature ใน CoffeesModule แล้ว inject เข้า CoffeesService ด้วย coffeesConfig.KEY + ConfigType เพื่ออ่านค่าแบบ typed

// coffees.config.ts → registerAs('coffees', () => ({ foo: 'bar' })) // coffees.module.ts → imports: [ConfigModule.forFeature(coffeesConfig)] // coffees.service.ts → (import type { ConfigType } from '@nestjs/config') constructor( @Inject(coffeesConfig.KEY) private coffeesConfiguration: ConfigType<typeof coffeesConfig>, ) { console.log(coffeesConfiguration.foo); } npm run start:dev

ผลลัพธ์ที่คาดหวัง

เทอร์มินัลพิมพ์ bar เมื่อ service ถูกสร้าง และใน editor การพิมพ์ coffeesConfiguration. จะ autocomplete property foo ให้ — ยืนยันว่า config เป็น strongly typed ไม่ใช่ any

ตรวจว่าใช้งานได้จริง

  • Log แสดง bar ตอน start
  • ลองพิมพ์ property ที่ไม่มีอยู่ เช่น coffeesConfiguration.baz — TypeScript ฟ้อง compile error
  • ลบ ConfigModule.forFeature(coffeesConfig) ออกจาก module ชั่วคราว — Nest ฟ้อง dependency resolution error ตอน start (ใส่กลับหลังทดสอบ)
  • GET /coffees ยังทำงานปกติ
