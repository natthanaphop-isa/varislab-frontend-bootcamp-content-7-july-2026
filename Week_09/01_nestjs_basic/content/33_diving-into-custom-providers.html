เจาะลึก Custom Providers

เมื่อจบบทนี้ คุณจะสามารถ

  • อธิบายได้ว่า providers: [CoffeesService] เป็นแค่ shorthand ของ object อะไร
  • ระบุสถานการณ์จริง 4 แบบที่ต้องใช้ custom provider แทนการให้ Nest instantiate ให้
  • เลือกได้คร่าว ๆ ว่าแต่ละสถานการณ์ควรใช้ useValue, useClass หรือ useFactory

สิ่งที่ซ่อนอยู่หลัง providers: [CoffeesService]

ทุกครั้งที่เราเขียน providers: [CoffeesService] Nest ตีความให้เป็นรูปเต็มโดยอัตโนมัติ: token ที่ใช้ค้นหาคือตัว class เอง และวิธีสร้างคือ instantiate class นั้น

// shorthand ที่เราใช้มาตลอด
providers: [CoffeesService]

// ...คือรูปเต็มของ object นี้
providers: [
  {
    provide: CoffeesService,  // token
    useClass: CoffeesService, // วิธีได้มาซึ่ง instance
  },
]

การแยก token (กุญแจที่ใช้ inject) ออกจาก วิธีสร้างค่า คือหัวใจของ custom provider — เมื่อสองอย่างนี้แยกจากกันได้ เราจะสลับ implementation ที่อยู่หลัง token ได้อย่างอิสระโดยผู้ใช้งานไม่ต้องแก้โค้ดฝั่งตัวเอง

สี่สถานการณ์ที่ shorthand ไม่พอ

คอร์สต้นฉบับสรุป use case ขั้นสูงที่ทำให้ต้องเขียน provider แบบเต็มไว้สี่แบบ

  • สร้าง instance เอง — เราอยากคุมการ new ด้วยตัวเอง (เช่นต้องส่ง argument พิเศษ) แทนที่จะให้ Nest instantiate ให้
  • ใช้ class เดิมซ้ำใน dependency ที่สอง — ให้สอง token ชี้ instance เดียวกันเพื่อไม่ให้เกิดของซ้ำ
  • override ด้วย mock ตอนทดสอบ — สลับ service จริงเป็นเวอร์ชันปลอมโดยไม่แตะโค้ดผู้ใช้ ซึ่งจะได้ทำจริงในบทถัดไป
  • Strategy Pattern — ประกาศ abstract class เป็น token แล้วเลือก implementation จริงตามเงื่อนไข เช่น environment
รูปแบบได้ค่ามาจากเหมาะกับ
useValueค่าที่สร้างไว้แล้ว (object, array, constant)mock ตอนเทสต์, ค่า config คงที่ (บทที่ 34–35)
useClassclass ที่ให้ Nest instantiateเลือก implementation ตามเงื่อนไข (บทที่ 36)
useFactoryค่าที่ return จากฟังก์ชัน (inject dependency อื่นได้)การสร้างค่าที่มี logic หรือ async (บทที่ 37–38)
useExistingtoken อื่นที่มีอยู่แล้วทำ alias ให้ instance เดียวกันมีสองชื่อ

ยังไม่ต้องรีบจำ syntax ทุกแบบ — บทที่ 34 ถึง 38 จะพาลงมือทีละรูปแบบในโปรเจกต์ iluvcoffee บทนี้ขอแค่มองภาพรวมให้ออกว่าปัญหาแบบไหนเรียกหาเครื่องมือตัวไหน

แปลง shorthand เป็นรูปเต็มด้วยมือ

ใน coffees.module.ts ลองเขียน CoffeesService เป็น provider object แบบเต็ม (provide + useClass) แล้วรันแอปเพื่อยืนยันว่าพฤติกรรมเหมือนเดิมทุกประการ — นี่คือหลักฐานว่า shorthand กับรูปเต็มคือสิ่งเดียวกัน

// coffees.module.ts @Module({ controllers: [CoffeesController], providers: [ { provide: CoffeesService, useClass: CoffeesService }, ], }) export class CoffeesModule {} // แล้วรัน npm run start:dev

ผลลัพธ์ที่คาดหวัง

แอป start ได้ปกติ ทุก endpoint ของ /coffees ตอบเหมือนเดิม เพราะ Nest resolve token CoffeesService ไปยัง instance ที่สร้างจาก class เดิม ต่างกันเพียงว่าคราวนี้เราเป็นคนประกาศ mapping เองอย่างชัดเจน

ตรวจว่าใช้งานได้จริง

  • ยิง GET /coffees ด้วย Insomnia แล้วได้ผลเหมือนก่อนแก้ module
  • ลองเปลี่ยน useClass เป็น class อื่นชั่วคราว (เช่น class เปล่า) แล้วดูว่า endpoint พังแบบคาดเดาได้ — แสดงว่า token กับ implementation แยกจากกันจริง
  • ตอบตัวเองได้ว่า use case ทั้งสี่ (custom instance, reuse, mock, strategy) ต่างกันอย่างไร
  • ระบุได้ว่าบทถัดไปจะใช้ useValue แก้ปัญหาข้อไหนในสี่ข้อนั้น
