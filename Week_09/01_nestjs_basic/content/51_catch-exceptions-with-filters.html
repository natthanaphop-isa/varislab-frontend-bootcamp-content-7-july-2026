จับ Exceptions ด้วย Filters

เมื่อจบบทนี้ คุณจะสามารถ

  • อธิบายได้ว่า exception filter เข้ามาแทรกตรงไหนของ request lifecycle และต่างจาก exception layer เริ่มต้นของ NestJS อย่างไร
  • สร้าง filter ด้วย Nest CLI แล้วใช้ @Catch() จำกัดชนิด exception ที่ต้องการจับ
  • ปรับแต่งรูปแบบ error response กลาง เช่น เพิ่ม timestamp ให้ทุก error ของแอป

Exception filter คือด่านสุดท้ายก่อน error ออกไปหาผู้ใช้

NestJS มี exception layer ในตัวอยู่แล้ว: เมื่อโค้ดโยน HttpException (หรือคลาสลูกอย่าง NotFoundException) framework จะแปลงเป็น JSON response ที่มี statusCode กับ message ให้อัตโนมัติ แต่เมื่อเราอยากควบคุมรูปแบบนั้นเอง เช่น เพิ่มฟิลด์ timestamp, เปลี่ยนโครง payload หรือส่ง log ไประบบภายนอก เราต้องเขียน exception filter ของตัวเอง ซึ่งเป็น building block ที่ทำงาน หลัง route handler โยน exception และ ก่อน response จะถูกส่งกลับ

เริ่มจาก generate โครงไฟล์ด้วย Nest CLI โดยวางไว้ในโฟลเดอร์ common เพราะ filter แบบนี้ไม่ผูกกับ business domain ใดโดยเฉพาะ

nest g filter common/filters/http-exception

ใช้ @Catch() บอกว่าจะจับ exception ชนิดไหน

decorator @Catch(HttpException) บอก NestJS ว่า filter ตัวนี้รับผิดชอบเฉพาะ HttpException และคลาสลูกทั้งหมด ส่วน interface ExceptionFilter บังคับให้เรา implement เมธอด catch(exception, host) ซึ่งรับตัว exception ที่ถูกโยน กับ ArgumentsHost สำหรับเข้าถึง context ของ request นั้น

import { Catch, HttpException, ExceptionFilter, ArgumentsHost } from '@nestjs/common';
import { Response } from 'express';

@Catch(HttpException)
export class HttpExceptionFilter<T extends HttpException> implements ExceptionFilter {
  catch(exception: T, host: ArgumentsHost) {
    const ctx = host.switchToHttp();
    const response = ctx.getResponse<Response>();

    const status = exception.getStatus();
    const exceptionResponse = exception.getResponse();
    const error =
      typeof response === 'string'
        ? { message: exceptionResponse }
        : (exceptionResponse as object);

    response.status(status).json({
      ...error,
      timestamp: new Date().toISOString(),
    });
  }
}

ประเด็นสำคัญในโค้ด: host.switchToHttp() เปลี่ยน context ทั่วไปให้เป็น HTTP context เพื่อดึง Response ของ Express ออกมาใช้ตรง ๆ; exception.getStatus() ให้ HTTP status เดิมของ exception; และ exception.getResponse() คืน payload เดิม ซึ่งเป็นได้ทั้ง string (เมื่อสร้าง exception ด้วยข้อความสั้น ๆ) หรือ object (รูปแบบมาตรฐานของ NestJS) จากนั้นเรา spread payload เดิมแล้วเติม timestamp ลงไป — ผู้ใช้ยังได้ข้อมูลครบเหมือนเดิม แต่ทุก error มีเวลาเกิดเหตุแนบมาด้วย

บรรทัด typeof response === 'string' คงไว้ตามโค้ดต้นฉบับของคอร์ส แต่เจตนาจริงคือเช็กชนิดของ exceptionResponse (payload) ไม่ใช่ตัว response ของ Express — ถ้านำไปใช้งานจริง ให้เช็ก typeof exceptionResponse === 'string' เพื่อให้ branch แรกทำงานตามที่ตั้งใจ

ลงทะเบียน filter แบบ global

filter ผูกได้หลายระดับเช่นเดียวกับ building block อื่น: ระดับ method, ระดับ controller ด้วย @UseFilters() หรือระดับทั้งแอป ในคอร์สนี้เราต้องการให้ error ทุกจุดมีรูปแบบเดียวกัน จึงลงทะเบียนแบบ global ใน main.ts

app.useGlobalFilters(new HttpExceptionFilter());

การ instantiate เองแบบนี้ตรงไปตรงมา แต่ filter จะไม่ได้อยู่ใน DI container จึง inject dependency อื่นไม่ได้ — ถ้าต้องการ inject ให้ลงทะเบียนผ่าน APP_FILTER token แทน (แนวเดียวกับที่จะเห็นใน guard บทถัด ๆ ไป)

เพิ่ม timestamp ให้ทุก error ของ iluvcoffee

สร้าง HttpExceptionFilter ตามโค้ดด้านบน ลงทะเบียนแบบ global ใน main.ts แล้วลองยิง request ที่รู้ว่าต้อง error เช่น ขอ coffee ที่ไม่มีอยู่จริง

nest g filter common/filters/http-exception # main.ts app.useGlobalFilters(new HttpExceptionFilter()); # ทดสอบด้วย request ที่ควร 404 curl http://localhost:3000/coffees/999

ผลลัพธ์ที่คาดหวัง

response ของ error ยังมี statusCode และ message เหมือนเดิม (เช่น Coffee #999 not found) แต่เพิ่มฟิลด์ timestamp เป็นเวลา ISO string เข้ามาในทุก error — ทั้ง 404 จาก service และ 400 จาก ValidationPipe

ตรวจว่าใช้งานได้จริง

  • ยิง GET /coffees/999 ด้วย Insomnia หรือ curl แล้วดูว่า JSON มี timestamp และ status ยังเป็น 404
  • ยิง POST /coffees ด้วย payload ที่ผิด schema แล้วตรวจว่า error 400 ของ ValidationPipe ก็ผ่าน filter เดียวกัน (มี timestamp เช่นกัน)
  • ยิง endpoint ปกติที่สำเร็จ แล้วยืนยันว่า response ปกติไม่ถูก filter แตะต้อง
  • ลบ useGlobalFilters ชั่วคราวแล้วยิงซ้ำ เพื่อเห็นความต่างระหว่างรูปแบบ error เริ่มต้นกับรูปแบบที่ filter จัดให้
