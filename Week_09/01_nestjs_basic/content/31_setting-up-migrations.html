ตั้งค่า Migrations ด้วย Prisma Migrate

บทนี้เราจะทำอะไรบ้าง

  • อธิบายได้ว่าทำไม production ต้องใช้ migrations แทน prisma db push
  • สร้าง migration ด้วย migrate dev และใช้ --create-only เพื่ออ่านและแก้ SQL ก่อนรันจริง
  • ย้อนการเปลี่ยนแปลงแบบ forward-only และรู้ว่า migrate deploy คือคำสั่งที่ใช้บน production

ทำไมต้องมี Migrations

ตลอดบทที่ผ่านมาเราใช้ prisma db push ให้ Prisma ปรับ schema ของฐานข้อมูลตาม schema.prisma โดยตรง ซึ่งสะดวกมากตอนพัฒนา แต่มันไม่เก็บประวัติ ไม่มีอะไรให้ทีมรีวิว และพร้อมจะ drop column ทิ้งเมื่อเห็นว่าฟิลด์หายไปจาก schema — บน production นั่นคือข้อมูลจริงของผู้ใช้ที่หายทันที Prisma Migrate บันทึกการเปลี่ยนแปลง schema แต่ละครั้งเป็นไฟล์ SQL ใน prisma/migrations/<timestamp>_<ชื่อ>/migration.sql ซึ่ง commit ขึ้น git และจดว่าไฟล์ไหนถูก apply แล้วในตาราง _prisma_migrations ทำให้ทุก environment รันขั้นตอนชุดเดียวกัน ครั้งเดียว ตามลำดับ

คำสั่งใช้ที่ไหนเขียนไฟล์ migration?อาจลบข้อมูล?
prisma db pushเครื่อง dev ช่วง prototypeไม่ — แก้ฐานข้อมูลตรง ๆได้ (เตือนก่อน แต่ทำได้)
prisma migrate devเครื่อง dev เท่านั้นใช่ — สร้างและ applyได้ อาจสั่ง reset ฐานข้อมูลเมื่อเจอ drift
prisma migrate deploystaging / production / CIไม่ — apply ไฟล์ที่ค้างอยู่เท่านั้นเฉพาะที่ SQL ในไฟล์สั่งไว้

ห้ามรัน migrate dev หรือ migrate reset ชี้ไปที่ production เด็ดขาด — ทั้งคู่มีสิทธิ์ล้างฐานข้อมูลทิ้งแล้วสร้างใหม่ บน production มีเพียง migrate deploy เท่านั้น

ขั้นที่ 1: เปลี่ยนจาก push มาเป็น migrate

รัน migrate dev พร้อมตั้งชื่อ migration แรก ฐานข้อมูลของเราถูกสร้างด้วย db push จึงมีตารางครบแต่ไม่มีประวัติ migration Prisma จะตรวจพบว่า schema จริงกับประวัติไม่ตรงกัน (เรียกว่า drift) และถามว่าจะ reset ฐานข้อมูลไหม — บนเครื่อง dev ตอบ yes ได้เลย ข้อมูลกาแฟทดลองเดี๋ยว POST ใหม่ก็จบ

npx prisma migrate dev --name init

ผลลัพธ์คือโฟลเดอร์ prisma/migrations/<timestamp>_init/ ที่มี migration.sql บรรจุ CREATE TABLE และ CREATE INDEX ของ coffee, flavor, event และตารางเชื่อม _CoffeeToFlavor ทั้งหมด พร้อมตาราง _prisma_migrations ในฐานข้อมูลที่จดว่า init ถูก apply แล้ว จากนี้ไปทุกครั้งที่แก้ schema.prisma ให้ใช้ migrate dev แทน db push

ขั้นที่ 2: เปลี่ยนชื่อ column แบบไม่ทำข้อมูลหาย

ลองเปลี่ยนชื่อฟิลด์ name ของ Coffee เป็น title ใน schema.prisma แล้วสร้าง migration ด้วย flag --create-only ซึ่งบอกให้ Prisma เขียนไฟล์ SQL แต่ยังไม่รัน เพราะตารางมีข้อมูลอยู่ Prisma จะเตือนว่า Added the required column `title` … There are N rows in this table, it is not possible to execute this step แล้วถามว่าจะสร้างไฟล์ไหม — ตอบ y เพราะเรากำลังจะแก้ SQL นั้นเองอยู่แล้ว (ชื่อ migration ถูกแปลงเป็น coffee_refactor โดยอัตโนมัติ Prisma ใช้ underscore ในชื่อโฟลเดอร์เสมอ)

npx prisma migrate dev --name coffee-refactor --create-only

เปิดไฟล์ที่ได้มาอ่าน: Prisma มองเห็นแค่ว่าฟิลด์หนึ่งหายไปและอีกฟิลด์โผล่มา มันไม่มีทางรู้ว่านี่คือการเปลี่ยนชื่อ จึงเขียน SQL แบบทำลายข้อมูล พร้อมคอมเมนต์เตือนไว้ด้านบน

-- prisma/migrations/<timestamp>_coffee_refactor/migration.sql
-- สิ่งที่ Prisma generate ให้ (ห้ามรันแบบนี้)
/*
  Warnings:

  - You are about to drop the column `name` on the `coffee` table. All the data in the column will be lost.
  - Added the required column `title` to the `coffee` table without a default value. This is not possible if the table is not empty.

*/
-- AlterTable
ALTER TABLE "coffee" DROP COLUMN "name",
ADD COLUMN     "title" TEXT NOT NULL;

แก้เนื้อหาของ migration.sql ให้เป็นการเปลี่ยนชื่อจริง ๆ แล้วค่อยสั่ง apply และ generate client ใหม่ให้ type Coffee รู้จัก title

-- migration.sql ฉบับที่แก้แล้ว
ALTER TABLE "coffee" RENAME COLUMN "name" TO "title";
npx prisma migrate dev
npx prisma generate

--create-only คือ workflow มาตรฐานสำหรับทุกการเปลี่ยนแปลงที่ไม่ตรงไปตรงมา: ให้ Prisma ร่าง SQL ให้ก่อน แล้วเราอ่าน แก้ และรีวิวก่อนรันเสมอ โดยเฉพาะบรรทัดที่มีคำว่า DROP และตั้งแต่ Prisma 7 migrate dev จะไม่รัน prisma generate ให้อัตโนมัติ ต้องสั่งเองทุกครั้งหลัง apply

ขั้นที่ 3: ย้อนกลับแบบ forward-only

Prisma Migrate ไม่มีเมธอด down — ประวัติ migration เดินหน้าอย่างเดียว การ "ย้อน" จึงทำด้วยการเขียน migration ใหม่ที่ทำสิ่งตรงข้าม ข้อดีคือประวัติเป็นเส้นตรงและตรงกับสิ่งที่เกิดขึ้นจริงในทุก environment ไม่มีสถานะ "เคย apply แล้วถอนออก" ให้สับสน เนื่องจากบทที่เหลือของคอร์สยังใช้ชื่อ name อยู่ เราจะเปลี่ยนกลับด้วยวิธีนี้พอดี: แก้ title กลับเป็น name ใน schema, สร้าง migration ด้วย --create-only, แก้ SQL เป็น RENAME COLUMN "title" TO "name" แล้ว apply

npx prisma migrate dev --name coffee-refactor-revert --create-only
# แก้ migration.sql เป็น:
#   ALTER TABLE "coffee" RENAME COLUMN "title" TO "name";
npx prisma migrate dev
npx prisma generate

ขั้นที่ 4: บน production ใช้ migrate deploy

เมื่อโค้ดพร้อมไฟล์ migration ถูก deploy ไปยัง server ให้รัน migrate deploy ใน pipeline ก่อน start แอป — คำสั่งนี้อ่าน _prisma_migrations แล้ว apply เฉพาะไฟล์ที่ยังไม่เคยรัน ตามลำดับ ไม่ generate ไม่ reset และไม่ถามอะไร จึงปลอดภัยสำหรับ automation ส่วน migrate status ใช้ดูว่า environment นั้นค้าง migration ไหนอยู่บ้าง

# ใน deploy pipeline / CI
npx prisma migrate deploy

# ตรวจสถานะได้ทุกที่
npx prisma migrate status

เปลี่ยนชื่อ column แบบไม่ทำข้อมูลหาย

ในโปรเจกต์ iluvcoffee สร้าง migration แรกจาก schema ปัจจุบัน, POST กาแฟไว้สักตัว, แล้วทำ migration เปลี่ยนชื่อ name → title ด้วย SQL ที่แก้เอง จากนั้นย้อนกลับด้วย migration ที่สอง

npx prisma migrate dev --name init # POST กาแฟไว้ 1 ตัวเพื่อใช้พิสูจน์ว่าข้อมูลไม่หาย # แก้ schema: name → title npx prisma migrate dev --name coffee-refactor --create-only # แก้ SQL เป็น RENAME COLUMN แล้ว npx prisma migrate dev npx prisma generate # ย้อนกลับแบบ forward-only (แก้ schema: title → name) npx prisma migrate dev --name coffee-refactor-revert --create-only npx prisma migrate dev npx prisma generate npx prisma migrate status

ควรได้ผลลัพธ์แบบนี้

โฟลเดอร์ prisma/migrations/ มี 3 โฟลเดอร์ (<timestamp>_init, <timestamp>_coffee_refactor, <timestamp>_coffee_refactor_revert) และตาราง _prisma_migrations มี 3 แถวตรงกัน หลัง migration ที่สอง ตาราง coffee มี column title แทน name โดยกาแฟที่ POST ไว้ยังอยู่ครบพร้อมค่าเดิม และหลัง migration ที่สาม column กลับเป็น name เหมือนเดิม migrate status รายงานว่า database is up to date

ลองเช็กให้แน่ใจ

  • เปิด GUI จากบทที่ 21 แล้วดูตาราง coffee ว่า column เปลี่ยนตาม migration และแถวข้อมูลเดิมไม่หาย
  • ตาราง _prisma_migrations มีแถว …_init, …_coffee_refactor, …_coffee_refactor_revert พร้อม finished_at
  • รัน npx prisma migrate status — ต้องได้ 3 migrations found in prisma/migrations และ Database schema is up to date! ไม่มีอะไรค้าง
  • .env และ prisma7.config.ts ไม่ต้องแก้อะไรเลย — migrate ใช้ DATABASE_URL ชุดเดียวกับแอป
