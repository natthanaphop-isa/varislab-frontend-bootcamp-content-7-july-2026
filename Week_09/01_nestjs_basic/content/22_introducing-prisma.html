รู้จัก Prisma และ PrismaService

บทนี้เราจะทำอะไรบ้าง

  • ติดตั้ง dependencies ที่จำเป็นสำหรับใช้ Prisma กับ PostgreSQL ใน NestJS และอธิบายหน้าที่ของแต่ละแพ็กเกจ
  • ตั้งค่า schema.prisma, prisma7.config.ts และ .env ให้ชี้ไปยังฐานข้อมูลใน Docker ของบทที่ 20
  • สร้าง PrismaService ที่ห่อ PrismaClient ไว้ในระบบ dependency injection ของ Nest และเปิดให้ทุก module ใช้ผ่าน PrismaModule แบบ global

Prisma คือสะพานระหว่าง TypeScript กับ SQL

Prisma เป็น ORM สำหรับ Node.js/TypeScript ที่ให้เรานิยามโครงสร้างตารางในไฟล์ schema.prisma แล้ว generate Prisma Client ที่รู้จักทุกตารางและทุกคอลัมน์ของเราออกมาเป็น TypeScript — query จึงมี autocomplete และถูก type check ตั้งแต่ตอนเขียน ไม่ต้องพิมพ์ SQL ดิบทุกครั้ง NestJS ไม่ได้มีแพ็กเกจ integration แยกสำหรับ Prisma เพราะไม่จำเป็น: เราแค่ห่อ PrismaClient ไว้ใน provider ปกติของ Nest แล้วปล่อยให้ระบบ DI ฉีดมันไปยัง service ไหนก็ได้

เริ่มจากติดตั้ง 4 แพ็กเกจ โดยล็อกเวอร์ชันแบบเจาะจงเหมือนที่ทำในคอร์ส API Design in Node.js — CLI ของ Prisma ปรับพฤติกรรมระหว่างเวอร์ชันอยู่เรื่อย ๆ การล็อกเวอร์ชันทำให้ทุกคนที่เรียนคอร์สนี้ได้ผลลัพธ์เดียวกัน

npm install @prisma/client@7.10.0 @prisma/adapter-pg@7.10.0 dotenv
npm install -D prisma@7.10.0
แพ็กเกจหน้าที่ข้อควรระวัง
prismaCLI สำหรับงานตอนพัฒนา: init, generate, db push, migrateเป็น dev dependency ไม่ถูกใช้ตอนแอปรันจริง
@prisma/clientruntime ของ Prisma Client ที่โค้ดเราเรียกใช้ตอนแอปทำงานต้องเวอร์ชันเดียวกับ prisma เสมอ ไม่เช่นนั้น generate แล้วรันไม่ขึ้น
@prisma/adapter-pgdriver adapter ที่เชื่อม Prisma เข้ากับ driver pg และเปิด connection pool ของ PostgreSQL ให้ข้างในPrisma 7 ต้องมี adapter เสมอ — ถ้าลืมส่ง adapter ตอน new PrismaClient() จะ throw ทันที
dotenvอ่านไฟล์ .env เข้า process.envใช้ชั่วคราวจนถึงบทที่ 33 ที่เราจะย้ายหน้าที่นี้ให้ ConfigModule

สร้างโครงด้วย prisma init

สั่งให้ CLI วางโครงไฟล์ให้ทั้งหมดด้วยคำสั่งเดียว ธง --no-skills บอกว่าไม่ต้องติดตั้งไฟล์ "Agent Skills" สำหรับ AI coding agent ที่ไม่เกี่ยวกับคอร์สนี้

npx prisma init --no-skills

คำสั่งนี้สร้างของให้เราสามชิ้น: โฟลเดอร์ prisma/ ที่มี schema.prisma, ไฟล์ prisma7.config.ts ที่ root ของโปรเจกต์ และไฟล์ .env — และยังเติม .env กับ /src/generated/prisma ลง .gitignore ให้ด้วย เปิด prisma/schema.prisma จะเห็นสองบล็อกบนสุดที่ Prisma เตรียมไว้ให้ ซึ่งใช้ได้เลยโดยไม่ต้องแก้

// prisma/schema.prisma — สร้างโดย prisma init
generator client {
  provider = "prisma-client"
  output   = "../src/generated/prisma"
}

datasource db {
  provider = "postgresql"
}
  • provider = "prisma-client" คือ generator รุ่นปัจจุบันที่สร้าง Prisma Client ออกมาเป็นไฟล์ TypeScript ตรง ๆ ในโปรเจกต์ของเรา ไม่ใช่ซ่อนอยู่ใน node_modules และมันอ่าน package.json เพื่อเลือกให้เองว่าจะออกโค้ดแบบ ES module (โปรเจกต์ Nest 12 ของเรามี "type": "module") หรือ CommonJS — ไม่ต้องตั้งค่าเพิ่ม (ถ้าวันหนึ่งไปทำงานกับโปรเจกต์ CommonJS แล้วเจอ error exports is not defined ตอนรัน ให้ระบุ moduleFormat = "cjs" ในบล็อกนี้ตรง ๆ แล้ว generate ใหม่)
  • output = "../src/generated/prisma" (path นับจากโฟลเดอร์ prisma/) วางโค้ดที่ generate ไว้ใต้ src/ เพื่อให้ nest build compile มันไปพร้อมแอปโดยไม่ต้องตั้งค่าอะไรเพิ่ม — เป็นของที่สร้างใหม่ได้เสมอ จึงถูกใส่ใน .gitignore ไว้แล้ว
  • ไฟล์ที่ generate ออกมา import กันเองด้วยนามสกุล .js (เช่น ./enums.js) ตามกติกาของ ES module — แบบเดียวกับที่โค้ด Nest ของเราต้องเขียน js' ทั้งที่ไฟล์จริงเป็น .ts เพราะ TypeScript แก้ path ให้ตรงกับไฟล์ที่ compile แล้ว
  • สังเกตว่า datasource บอกแค่ว่าเป็น PostgreSQL ไม่มี connection string ในนี้ — ใน Prisma 7 ค่านั้นย้ายไปอยู่ที่ prisma7.config.ts

ค่าเชื่อมต่ออยู่ใน .env และ prisma7.config.ts

เปิดไฟล์ .env ที่ prisma init สร้างไว้ จะเห็นค่า DATABASE_URL ตัวอย่างที่ชี้ไป Prisma Postgres — ลบทิ้งแล้วแทนด้วย connection string ที่ประกอบจากค่าเดียวกับใน docker-compose.yml ของบทที่ 20 (user postgres, รหัสผ่าน pass123, พอร์ต 5432, database postgres)

# .env
DATABASE_URL="postgresql://postgres:pass123@localhost:5432/postgres"

ไฟล์ .env มี credentials จริง ห้าม commit ขึ้น repository — prisma init เพิ่ม .env ลง .gitignore ให้แล้ว แต่ให้ตรวจด้วย git status ว่าไฟล์ไม่โผล่ในรายการจริง ๆ ในบทที่ 33 เราจะย้ายการโหลด .env ไปให้ ConfigModule และบทที่ 34 จะ validate ว่าค่านี้มีอยู่จริงก่อนแอป start

ส่วน prisma7.config.ts คือไฟล์ตั้งค่าของ Prisma CLI: บอกว่า schema อยู่ไหน จะเก็บ migrations ไว้ที่ไหน และจะต่อฐานข้อมูลด้วย URL อะไร ไฟล์ที่ prisma init สร้างให้ใช้ได้เลยโดยไม่ต้องแก้ — สังเกตบรรทัดแรก import "dotenv/config" ที่ทำให้ค่าใน .env ถูกโหลดก่อน process.env["DATABASE_URL"] จะถูกอ่าน (Prisma CLI ไม่โหลด .env ให้เอง)

// prisma7.config.ts — สร้างโดย prisma init
import "dotenv/config";
import { defineConfig } from "prisma/config";

export default defineConfig({
  schema: "prisma/schema.prisma",
  migrations: {
    path: "prisma/migrations",
  },
  datasource: {
    url: process.env["DATABASE_URL"],
  },
});

ไฟล์นี้อยู่ที่ root ของโปรเจกต์ ไม่ใช่ใน src/ — ไม่เป็นไร เพราะ tsconfig.build.json ของ Nest 12 ระบุ "include": ["src"] ไว้ nest build จึงไม่แตะไฟล์นี้และ output ยังอยู่ที่ dist/main.js ตามเดิม

PrismaService: ห่อ PrismaClient ไว้ใน DI ของ Nest

ตอนแอปรันจริง Nest ไม่ได้อ่าน prisma7.config.ts — ไฟล์นั้นเป็นของ CLI เท่านั้น ฝั่งแอปเราต้องสร้าง PrismaClient เองและบอกมันว่าจะต่อฐานข้อมูลอย่างไร วิธีมาตรฐานคือสร้าง module กับ service ชื่อ prisma ด้วย Nest CLI แล้วให้ service สืบทอดจาก PrismaClient โดยตรง

nest g mo prisma
nest g s prisma --no-spec
// src/prisma/prisma.service.ts
import { Injectable, OnModuleInit, OnModuleDestroy } from '@nestjs/common';
import { PrismaPg } from '@prisma/adapter-pg';
import { PrismaClient } from '../generated/prisma/client.js';

@Injectable()
export class PrismaService extends PrismaClient implements OnModuleInit, OnModuleDestroy {
  constructor() {
    super({
      adapter: new PrismaPg({ connectionString: process.env.DATABASE_URL }),
    });
  }

  async onModuleInit() {
    await this.$connect();
  }

  async onModuleDestroy() {
    await this.$disconnect();
  }
}
  • PrismaClient import มาจาก src/generated/prisma/client ที่เราจะ generate ในอีกสักครู่ ไม่ใช่จาก npm ตรง ๆ เพราะ Client ตัวนี้ถูกสร้างมาเฉพาะสำหรับ schema ของเรา
  • PrismaPg คือ adapter ที่เปิด connection pool ของ pg ให้ข้างในตัวมันเอง โดยอ่าน URL จาก process.env.DATABASE_URL
  • onModuleInit เรียก $connect() ทันทีที่ module พร้อม — แต่กับ @prisma/adapter-pg connection pool ของ pg เป็นแบบ lazy ดังนั้นแม้ DATABASE_URL จะผิด $connect() ก็มักจะ resolve ได้ตามปกติ ปัญหาจะโผล่ตอนมี query แรกเข้ามาแทน (ดูรายละเอียดในส่วนตรวจผลด้านล่าง) ส่วน onModuleDestroy คืน connection ตอนแอปปิดตัวตามปกติ

แล้วประกาศ module ให้เป็น global: feature module ทุกตัว (เช่น CoffeesModule ในบทถัด ๆ ไป) จะ inject PrismaService ได้ทันทีโดยไม่ต้อง import PrismaModule ซ้ำทุกที่ — เราต้องการ Prisma Client เพียงตัวเดียวทั้งแอปอยู่แล้ว การประกาศครั้งเดียวที่ root จึงตรงกับความเป็นจริง

// src/prisma/prisma.module.ts
import { Global, Module } from '@nestjs/common';
import { PrismaService } from './prisma.service.js';

@Global()
@Module({
  providers: [PrismaService],
  exports: [PrismaService],
})
export class PrismaModule {}
// src/app.module.ts
import { Module } from '@nestjs/common';
import { AppController } from './app.controller.js';
import { AppService } from './app.service.js';
import { CoffeesModule } from './coffees/coffees.module.js';
import { PrismaModule } from './prisma/prisma.module.js';

@Module({
  imports: [CoffeesModule, PrismaModule],
  controllers: [AppController],
  providers: [AppService],
})
export class AppModule {}

เหลืออีกจุดเดียว: ตอนรัน Nest ไม่มีใครโหลด .env เข้า process.env ให้ จึงต้องเพิ่ม import 'dotenv/config'; ไว้เป็นบรรทัดแรกสุดของ src/main.ts ชั่วคราว (บทที่ 33 จะแทนที่บรรทัดนี้ด้วย ConfigModule.forRoot() ซึ่งเป็นวิธีของ Nest เอง)

// src/main.ts
import 'dotenv/config';
import { NestFactory } from '@nestjs/core';
// ...ที่เหลือคงเดิม

ก่อน start ต้องสั่ง npx prisma generate หนึ่งครั้ง เพื่อให้โฟลเดอร์ src/generated/prisma ที่ PrismaService import อยู่มีตัวตนจริง — ตอนนี้ยังไม่มี model ก็ generate ได้ ผลลัพธ์คือ Client เปล่า ๆ ที่ต่อฐานข้อมูลได้แต่ยังไม่รู้จักตารางใด

เชื่อม iluvcoffee เข้ากับ Postgres

ติดตั้ง dependencies, รัน prisma init, แก้ .env, สร้าง PrismaService กับ PrismaModule ตามโค้ดด้านบน แล้ว generate และรันแอปโดยที่ Docker container ยังเปิดอยู่

npm install @prisma/client@7.10.0 @prisma/adapter-pg@7.10.0 dotenv npm install -D prisma@7.10.0 npx prisma init --no-skills nest g mo prisma nest g s prisma --no-spec npx prisma generate docker-compose up -d npm run start:dev

ควรได้ผลลัพธ์แบบนี้

แอป start ขึ้นตามปกติโดยมี log ของ InstanceLoader แสดงว่า PrismaModule dependencies initialized และไม่มี error ใด ๆ จากการเชื่อมต่อ หากลืมเปิด Docker หรือรหัสผ่านใน DATABASE_URL ไม่ตรง แอปจะยัง start ได้ตามปกติ เพราะ connection pool ของ @prisma/adapter-pg เป็นแบบ lazy — $connect() ใน onModuleInit จะไม่ throw ทันที ปัญหาจะโผล่ก็ต่อเมื่อมี query แรกเข้ามาจริง ๆ (เช่นยิง GET /coffees) นี่เป็นพฤติกรรมที่ต่างจาก Prisma รุ่นก่อนหน้าที่ไม่ใช้ driver adapter

ลองเช็กให้แน่ใจ

  • package.json มี @prisma/client, @prisma/adapter-pg, dotenv ใน dependencies และ prisma ใน devDependencies ทุกตัวเป็นเวอร์ชัน 7.10.0
  • โฟลเดอร์ src/generated/prisma ถูกสร้างหลัง npx prisma generate และ .gitignore มีทั้ง .env และ /src/generated/prisma
  • npm run build แล้วได้ไฟล์ dist/main.js และมีโฟลเดอร์ dist/generated/prisma — ยืนยันว่า client ที่ generate ถูก compile ไปพร้อมแอป
  • npm run start:dev ขึ้นข้อความ initialize สำเร็จ ไม่มี ECONNREFUSED หรือ authentication error
  • ทดลอง docker-compose down แล้วรันแอปอีกครั้ง — แอปจะ start ผ่านตามปกติ (ไม่มี connection error ตอน start) แต่พอยิง GET /coffees จะได้ error ทันที ซึ่งยืนยันว่าแอปเชื่อมกับ container นี้จริง (อย่าลืม up -d กลับ)
  • endpoint เดิมของ coffees ยังตอบสนองได้ตามปกติ เพราะเรายังไม่ได้เปลี่ยน service ไปใช้ฐานข้อมูล
