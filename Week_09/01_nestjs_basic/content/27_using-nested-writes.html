ใช้ Nested Writes สร้างและอัปเดตพร้อม Relation

เมื่อจบบทนี้ คุณจะสามารถ

  • อธิบายได้ว่า nested write คืออะไร และแยกความต่างของ create, connect และ connectOrCreate ที่ใช้ไปแล้วในบทที่ 26
  • แก้ update() ให้ใช้ set: [] แทนที่ชุด relation เดิมทั้งหมด แทนที่จะบวกเพิ่มเรื่อย ๆ แบบเดิม
  • เพิ่ม include: { flavors: true } ให้ create()/update() เพื่อให้ response มี flavors ติดมาทันที ไม่ต้องยิง GET แยก

สิ่งที่ทำไปแล้วในบทที่ 26 กับสองจุดที่ยังไม่สมบูรณ์

บทที่ 26 ทำให้ create()/update() คอมไพล์ผ่านและบันทึกความสัมพันธ์ลงตารางเชื่อม _CoffeeToFlavor ได้แล้วด้วย nested write — สั่งใน data ของ create/update เดียวกันได้เลยว่าจะทำอะไรกับ model ปลายทาง (Flavor) โดย Prisma รวมทั้งหมดเป็นการเขียนก้อนเดียวที่สำเร็จหรือล้มไปพร้อมกัน แต่ยังเหลือสองจุดที่ทำงานไม่ตรงตามที่ควร: update() บวก flavor เพิ่มเรื่อย ๆ แทนที่จะแทนที่ทั้งชุด และทั้งคู่ไม่คืน flavors กลับมาใน response บทนี้จะแก้ทั้งสองจุดนั้น

คำสั่งทำอะไรเหมาะกับ
createสร้างแถวใหม่ใน model ปลายทางแล้วผูกให้ทันทีของที่ไม่มีทางซ้ำ เช่น comment ใหม่ของโพสต์
connectผูกกับแถวที่มีอยู่แล้ว โดยอ้างด้วยฟิลด์ unique (id หรือ @unique อื่น)เมื่อรู้แน่ว่าปลายทางมีอยู่ ไม่มีก็ให้ error
connectOrCreateค้นด้วยฟิลด์ unique ก่อน เจอก็ผูกตัวเดิม ไม่เจอจึงสร้างใหม่แล้วผูกข้อมูลอ้างอิงที่ใช้ซ้ำ เช่น tag หรือ flavor ของเรา

ทั้ง connect และ connectOrCreate ต้องค้นด้วยฟิลด์ที่ unique เท่านั้น — นี่คือเหตุผลที่บทที่ 25 เราใส่ @unique ให้ Flavor.name ไว้ล่วงหน้า ทำให้ไม่ต้องเขียน helper "หา flavor จากชื่อ ถ้าไม่มีค่อยสร้าง" เองอีกเลย

แก้ update() ให้แทนที่ชุด flavor แทนการบวกเพิ่ม

update() จากบทที่ 26 ยังไม่มีอะไรบอก Prisma ว่า "ตัดของเดิมทิ้งก่อน" — connectOrCreate เพียงอย่างเดียวจึงแค่เพิ่มความสัมพันธ์ใหม่เข้าไปในตารางเชื่อม โดยไม่แตะของเดิมเลย ทางแก้คือสั่ง set: [] ก่อน connectOrCreate ในบล็อกเดียวกัน — Prisma จะตัด join row เดิมของกาแฟตัวนี้ทั้งหมดออกก่อน แล้วค่อยผูกชุดใหม่เข้าไป ผลคือ "แทนที่ทั้งชุด" ไม่ใช่ "เพิ่มต่อท้าย" อีกต่อไป

เพิ่ม include ให้ create() และ update() คืน flavors กลับมาด้วย

อีกจุดที่ยังขาดคือ include: { flavors: true } — ไม่มี option นี้ Prisma จะคืนเฉพาะ column ของ Coffee เอง ไม่รวม flavors ที่เพิ่งผูกไป ทั้งที่ข้อมูลถูกบันทึกลงฐานข้อมูลถูกต้องแล้ว เพิ่ม option เดียวกับที่ findAll()/findOne() ใช้ไปแล้วในบทที่ 26 เข้าไปที่ create() และ update() ด้วย

/* coffees.service.ts — ต่อจากบทที่ 26 */
import { Injectable, NotFoundException } from '@nestjs/common';
import { PrismaService } from '../prisma/prisma.service.js';
import { CreateCoffeeDto } from './dto/create-coffee.dto.js';
import { UpdateCoffeeDto } from './dto/update-coffee.dto.js';

@Injectable()
export class CoffeesService {
  constructor(private readonly prisma: PrismaService) {}

  create(createCoffeeDto: CreateCoffeeDto) {
    const { flavors, ...coffeeData } = createCoffeeDto;
    return this.prisma.coffee.create({
      data: {
        ...coffeeData,
        flavors: {
          connectOrCreate: this.connectOrCreateFlavors(flavors),
        },
      },
      include: { flavors: true }, // 👈 ใหม่: ให้ response มี flavors ติดมาด้วย
    });
  }

  async update(id: string, updateCoffeeDto: UpdateCoffeeDto) {
    await this.findOne(id); // ให้ id ที่ไม่มีจริงได้ 404 แบบเดียวกัน
    const { flavors, ...coffeeData } = updateCoffeeDto;
    return this.prisma.coffee.update({
      where: { id: +id },
      data: {
        ...coffeeData,
        flavors: flavors && {
          set: [], // 👈 ใหม่: ตัดความสัมพันธ์เดิมทั้งหมดก่อนผูกชุดใหม่
          connectOrCreate: this.connectOrCreateFlavors(flavors),
        },
      },
      include: { flavors: true }, // 👈 ใหม่
    });
  }

  private connectOrCreateFlavors(names: string[]) {
    return names.map((name) => ({
      where: { name },
      create: { name },
    }));
  }

  // findAll / findOne / remove คงเดิมจากบทที่ 26
}

สังเกตว่าเงื่อนไข flavors && {...} ใน update ยังสำคัญเหมือนเดิม: PATCH ที่ไม่ได้ส่ง flavors มาจะได้ undefined ซึ่ง Prisma ปฏิบัติเหมือน field นี้ไม่ถูกส่งมาเลย (เท่ากับไม่ใส่ key นี้ใน data) — relation เดิมจึงไม่ถูกแตะ ต่อเมื่อ client ส่ง flavors มาจริงเท่านั้น set: [] จึงจะทำงานและแทนที่ทั้งชุด

set: [] ตัดแค่แถวในตารางเชื่อม _CoffeeToFlavor เท่านั้น ไม่เคยลบแถวในตาราง flavor — flavor ที่ไม่มีกาแฟตัวไหนใช้แล้วจะยังอยู่ ไม่มีเรื่อง orphan ถูกลบโดยไม่ตั้งใจให้ต้องกังวล และการใส่ include: { flavors: true } ท้าย create/update ทำให้ response คืน flavors ที่ผูกแล้วกลับมาทันทีโดยไม่ต้อง query ซ้ำ

connectOrCreate ทำงานเป็นสองขั้น (ค้นแล้วค่อยสร้าง) ดังนั้นถ้ามีคำขอจำนวนมากสร้าง flavor ชื่อเดียวกันพร้อมกันเป๊ะ อาจมีตัวหนึ่งชน unique constraint ได้ (Prisma docs ระบุไว้) สำหรับแอปนี้ไม่ใช่ปัญหา แต่ในระบบที่ concurrent สูงต้องเผื่อ retry หรือจัดการ error ตรงนั้น

แทนที่ทั้งชุด flavor แทนการบวกเพิ่ม แล้วให้ response มี flavors ติดมา

แก้ create/update ใน CoffeesService จากบทที่ 26 ตามโค้ดด้านบน (เพิ่ม set: [] ใน update และเพิ่ม include: { flavors: true } ให้ทั้งคู่) แล้วทดสอบ

POST http://localhost:3000/coffees { "name": "Shipwreck Roast", "brand": "Buddy Brew", "flavors": ["chocolate", "vanilla"] } # ยิงซ้ำอีกครั้งด้วย flavor เดิมบางตัว POST http://localhost:3000/coffees { "name": "Salemander Roast", "brand": "Buddy Brew", "flavors": ["chocolate", "caramel"] }

ผลลัพธ์ที่คาดหวัง

คำขอแรกสร้างกาแฟพร้อม flavor chocolate และ vanilla ในตาราง flavor คำขอที่สอง reuse แถว chocolate เดิม (id เดิม) และสร้างเฉพาะ caramel เพิ่ม — ตาราง flavor มี 3 แถว ไม่ใช่ 4 และ _CoffeeToFlavor ผูกความสัมพันธ์ครบทุกคู่ response ของทั้งสองคำขอมี flavors เป็น object พร้อม id กลับมาทันที

ตรวจว่าใช้งานได้จริง

  • POST พร้อม flavors แล้ว GET /coffees เห็น flavors กลับมาเป็น object ที่มี id จริง
  • ตาราง flavor ไม่มีชื่อซ้ำ แม้จะ POST ด้วย flavor เดิมหลายครั้ง
  • PATCH โดยไม่ส่ง flavors — relation เดิมต้องไม่หาย; PATCH พร้อม flavors ชุดใหม่ — ต้องแทนที่ชุดเดิม และแถวใน flavor ที่ถูกถอดออกยังอยู่
  • POST ตอนนี้ response มี field flavors ติดมาทันที ไม่ต้องยิง GET แยกเหมือนบทที่ 26
