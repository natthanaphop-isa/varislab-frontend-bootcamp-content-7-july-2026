โบนัส: เพิ่ม Request Logging ด้วย Middleware

เมื่อจบบทนี้ คุณจะสามารถ

  • อธิบายว่า middleware ต่างจาก building block อื่นอย่างไร: ผูกกับ route path ไม่ใช่ method และรันก่อนทุกอย่าง
  • บอกได้ว่าทำไมการลืมเรียก next() ทำให้ request ค้าง
  • สร้าง middleware วัดเวลา request-response แล้วผูกกับทุก route ผ่าน configure() ของ module

Middleware ผูกกับ path และรันก่อนใครทั้งหมด

Middleware เป็นฟังก์ชันที่เข้าถึง request และ response object ได้โดยตรง และไม่ผูกกับ method ใด ๆ — มันผูกกับ route path ที่ระบุไว้ ใน request lifecycle ของ NestJS middleware ทำงานก่อน guard, interceptor และ pipe ทั้งหมด สิ่งที่ middleware ทำได้ตามเอกสารต้นทางคือ

  • execute โค้ดใด ๆ
  • แก้ไข request และ response objects
  • จบ request-response cycle เองเลย
  • หรือเรียก middleware ตัวถัดไปใน call stack

กติกาเหล็กของ middleware: ถ้าไม่ได้จบ request-response cycle เอง ต้องเรียก next() เสมอเพื่อส่งต่อการควบคุม มิฉะนั้น request จะถูกทิ้งค้างไว้ — client รอไปเรื่อย ๆ โดยไม่มีวันได้ response

สร้าง LoggingMiddleware

nest g middleware common/middleware/logging

middleware แบบ class ใน NestJS ติด @Injectable() และ implement NestMiddleware ซึ่งบังคับเมธอด use(req, res, next) — โค้ดนี้ใช้ console.time/console.timeEnd จับเวลาตั้งแต่ request เข้า จนถึง event finish ของ response

import {
  Injectable,
  NestMiddleware,
} from '@nestjs/common';

@Injectable()
export class LoggingMiddleware implements NestMiddleware {
  use(req: any, res: any, next: () => void) {
    console.time('Request-response time');
    console.log('Hi from middleware!');

    res.on('finish', () => console.timeEnd('Request-response time'));
    next();
  }
}

สังเกตว่าเราไม่ได้จับเวลาแค่ถึงตอน next() คืนค่า แต่รอจน response ถูกส่งจริง (event finish) — ตัวเลขที่ได้จึงครอบคลุมทั้ง pipeline: guard, interceptor, pipe, handler และขากลับทั้งหมด

ผูก middleware ใน module ด้วย configure()

middleware ไม่ได้ลงทะเบียนใน @Module() decorator เหมือน provider แต่ผูกผ่านการ implement NestModule แล้วกำหนดใน configure(consumer) — ในที่นี้ผูกกับทุก path ด้วย '*'

consumer
  .apply(LoggingMiddleware)
  .forRoutes('*');

forRoutes รับได้ทั้ง string, ออบเจ็กต์ { path, method } หรือทั้ง controller class จึงจำกัดขอบเขตได้ละเอียดเท่าที่ต้องการ เช่น log เฉพาะ coffees ก็เปลี่ยนเป็น .forRoutes('coffees')

วัดเวลาทุก request ของ iluvcoffee

สร้าง LoggingMiddleware แล้วผูกกับทุก route ใน CommonModule (ให้ module implement NestModule และเพิ่ม configure()) จากนั้นยิง request แล้วดู log

nest g middleware common/middleware/logging # common.module.ts export class CommonModule implements NestModule { configure(consumer: MiddlewareConsumer) { consumer.apply(LoggingMiddleware).forRoutes('*'); } } # ทดสอบ curl http://localhost:3000/coffees

ผลลัพธ์ที่คาดหวัง

ทุกครั้งที่ยิง request ใน terminal ของ dev server จะเห็น Hi from middleware! ตามด้วย Request-response time: X ms เมื่อ response ส่งเสร็จ — และ log นี้ขึ้นก่อน Before... ของ interceptor เสมอ เพราะ middleware อยู่ต้นทางของ lifecycle

ตรวจว่าใช้งานได้จริง

  • ยิง GET /coffees แล้วเห็นทั้งข้อความทักทายและเวลารวมใน log
  • เทียบลำดับ log: Hi from middleware! ต้องมาก่อน Before... ของ WrapResponseInterceptor
  • ลองคอมเมนต์ next() ออกชั่วคราวแล้วยิงซ้ำ — request ต้องค้าง ไม่มี response กลับ (แล้วใส่คืนทันที)
  • เปลี่ยน forRoutes('*') เป็น forRoutes('coffees') แล้วยืนยันว่า route อื่นไม่ถูก log
