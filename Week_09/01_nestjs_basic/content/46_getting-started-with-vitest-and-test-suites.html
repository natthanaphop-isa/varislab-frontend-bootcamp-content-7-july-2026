เริ่มต้น Vitest และสร้าง Test Suite

บทนี้เราจะทำอะไรบ้าง

  • อธิบายบทบาทของ Vitest และความต่างระหว่าง unit กับ e2e configuration
  • เลือกใช้คำสั่ง test, watch และ coverage ให้ตรงกับงาน
  • เข้าใจ convention ของไฟล์ *.spec.ts และโครงสร้าง test suite
  • สร้าง TestingModule และ mock dependency ให้ service ถูกสร้างได้

ทำไมถึงเป็น Vitest

NestJS ไม่ได้บังคับว่าต้องใช้ testing framework ตัวไหน แต่ถ้าตั้งค่าเองทั้งหมด เราต้องเตรียมทั้ง test runner, assertions, mocks และการรองรับ TypeScript ตั้งแต่ NestJS 12 เป็นต้นมา โปรเจกต์จาก nest new จึงตั้งค่า Vitest มาให้พร้อมใช้ Vitest ทำงานบน Vite รองรับ TypeScript และ ES modules โดยตรง และรันไฟล์ทดสอบแยกกันในหลาย workers ได้

Vitest ให้ครบในแพ็กเกจเดียวเช่นกัน: เป็น test runner, มี assertion API (expect), มีระบบ mock ในตัว (vi.fn(), vi.spyOn(), vi.mock()) และรายงาน coverage ผ่าน @vitest/coverage-v8 ที่ Nest ติดตั้งไว้ให้แล้ว API ของมันจงใจออกแบบให้เข้ากันได้กับ Jest — ถ้าเคยเขียน Jest มาก่อน สิ่งที่ต้องจำแทบมีแค่ jest.fn() กลายเป็น vi.fn()

Nest เปิด globals: true ไว้ใน config และประกาศ "types": ["vitest/globals", "node"] ใน tsconfig.json — describe, it, expect, beforeEach, vi ฯลฯ จึงใช้ได้ทันทีในไฟล์ทดสอบโดยไม่ต้อง import (import เฉพาะ type เช่น import type { Mock } from 'vitest' เมื่อต้องการ)

สองไฟล์ config: unit กับ e2e

Nest แยก config ของ Vitest เป็นสองไฟล์ที่ root ของโปรเจกต์ ต่างกันแค่ว่าจะมองหาไฟล์ทดสอบชื่อแบบไหน

// vitest.config.ts — unit tests
import { defineConfig } from 'vitest/config';
import tsconfigPaths from 'vite-tsconfig-paths';

export default defineConfig({
  plugins: [tsconfigPaths()],
  test: {
    globals: true,
    root: './',
    include: ['**/*.spec.ts'],
  },
});

// vitest.config.e2e.ts — e2e tests
export default defineConfig({
  plugins: [tsconfigPaths()],
  test: {
    globals: true,
    root: './',
    include: ['**/*.e2e-spec.ts'],
  },
});

คำสั่งที่มีให้ตั้งแต่ scaffold

# รัน unit tests ทั้งหมดครั้งเดียวแล้วจบ
npm run test

# รันแบบ watch: แก้ไฟล์แล้วรันซ้ำให้อัตโนมัติ
npm run test:watch

# รัน unit tests พร้อมเก็บ coverage
npm run test:cov

# รัน e2e tests
npm run test:e2e
คำสั่งสิ่งที่รันจริงทดสอบอะไร / ไฟล์ที่มอง
npm run testvitest rununit tests: class/function เดี่ยว ๆ พร้อม mock dependencies — **/*.spec.ts
npm run test:watchvitestเหมือน test แต่ค้างอยู่และรันซ้ำทุกครั้งที่ save ไฟล์ — เหมาะกับตอนพัฒนา
npm run test:covvitest run --coverageเหมือน test แต่สรุปสัดส่วนโค้ดที่ถูกทดสอบเป็นตารางใน terminal และโฟลเดอร์ coverage/
npm run test:e2evitest run --config ./vitest.config.e2e.tsระบบทั้งเส้นทาง: boot แอปจริงแล้วยิง HTTP เข้าไป — **/*.e2e-spec.ts

ทุกคำสั่งรับชื่อไฟล์ (หรือบางส่วนของชื่อ) ต่อท้ายเพื่อรันเฉพาะไฟล์ที่สนใจ เช่น npm run test -- coffees.service หรือ npm run test:e2e -- coffees ซึ่งเราจะใช้ตลอดบทถัด ๆ ไป

ตอน scaffold Nest สร้างไฟล์ตัวอย่างให้แล้วสองแบบ: src/app.controller.spec.ts (unit) และ test/app.e2e-spec.ts (e2e) — เปิดอ่านสองไฟล์นี้ได้เลยเพื่อเห็นโครงก่อนเราลงลึกในบทถัด ๆ ไป สังเกตว่า import ในไฟล์ทดสอบก็ลงท้ายด้วย .js เหมือนโค้ดส่วนอื่นของแอป เพราะเป็น ES module เดียวกัน

Convention การวางไฟล์ทดสอบ

สำหรับ unit tests ธรรมเนียมของ Nest คือเก็บไฟล์ spec ไว้โฟลเดอร์เดียวกับไฟล์ที่มันทดสอบ — controller, provider, service แต่ละตัวมีไฟล์ทดสอบของตัวเอง และต้องลงท้ายด้วย .spec.ts เพื่อให้ tooling จับเป็นไฟล์ test อัตโนมัติ (เช่น coffees.service.ts คู่กับ coffees.service.spec.ts)

สำหรับ e2e tests ไฟล์อยู่ในโฟลเดอร์ test/ แยกต่างหาก จัดกลุ่มตาม feature ที่ทดสอบ และต้องลงท้ายด้วย .e2e-spec.ts

Unit testse2e tests
โฟกัสclass/function เดี่ยว แยกจาก dependencies ด้วย mockการทำงานร่วมกันของ classes/modules ในระดับใกล้ผู้ใช้จริง
ตำแหน่งไฟล์ข้าง source, *.spec.tsโฟลเดอร์ test/, *.e2e-spec.ts
ความเร็วเร็ว รันบ่อยระหว่างพัฒนาช้ากว่า boot แอปจริง มักต้องมี database

รันเฉพาะไฟล์ที่กำลังแก้ และ mock สิ่งที่ยังไม่เกี่ยว

ระหว่างพัฒนาไม่จำเป็นต้องรันทุก suite — ส่ง pattern ของชื่อไฟล์ต่อท้ายคำสั่งได้

# รัน unit test แบบ watch เฉพาะไฟล์ที่ชื่อเข้ากับ pattern
npm run test:watch -- coffees.service

เก็บกวาด constructor ก่อนเริ่มบทนี้: ในบทที่ 35 เรา inject ConfigService เข้า CoffeesService เพื่อลองอ่านและ log ค่า config ถ้ายังเก็บ dependency ทดลองนี้ไว้ test module ต้องมี mock ของ ConfigService เพิ่มด้วย วิธีที่ตรงกับโค้ดในบทนี้ที่สุดคือลบ injection และ log ที่ใช้ทดลองออก ให้ constructor เหลือ constructor(private readonly prisma: PrismaService) {} แล้วลบ import ที่ไม่ใช้แล้ว

พอเปิด coffees.service.spec.ts ที่ CLI สร้างให้ จะพบว่ามัน fail ทันที เพราะ CoffeesService ตอนนี้ inject PrismaService — TestingModule ที่สร้างขึ้นมาเปล่า ๆ ไม่มี PrismaModule จึงไม่รู้จะหา provider นี้จากไหน วิธีปลดล็อกขั้นแรกคือให้ mock ว่าง ไปก่อน แค่ให้ DI resolve ได้

// coffees.service.spec.ts — ภายใน Test.createTestingModule
providers: [
  CoffeesService,
  { provide: PrismaService, useValue: {} }, // 👈 mock ว่างแทน Prisma Client ตัวจริง
]

รูปแบบ { provide: Token, useValue: ... } นี้เรียกว่า custom provider: แทนที่จะบอก Nest ว่า สร้าง instance จาก class นี้ เราบอกว่า เมื่อมีใครขอ token นี้ ให้ส่งค่านี้ไปแทน — ในที่นี้ใช้ class PrismaService เป็น token แล้วส่ง object ว่างกลับไป นี่คือเหตุผลที่เราห่อ PrismaClient ไว้ใน service ของ Nest ตั้งแต่บทที่ 22: มันสลับตัวจริงกับ mock ได้ในบรรทัดเดียวโดยไม่ต้องต่อฐานข้อมูล

รัน Vitest และทำให้ CoffeesService suite ผ่าน

ขั้นที่ 1: รันชุดทดสอบที่มากับโปรเจกต์

ยังไม่ต้องเขียนอะไรใหม่ — รันคำสั่งใน iluvcoffee เพื่อดูว่าแต่ละแบบให้ผลอย่างไร และสังเกตว่าไฟล์ spec ตัวอย่างบางไฟล์อาจ fail ถ้าเราแก้ controller/service ไปมากแล้ว ซึ่งเป็นเรื่องปกติและเราจะแก้ในขั้นถัดไป

npm run test npm run test:cov npm run test:watch # ลองแก้ไฟล์ spec แล้ว save ดู จากนั้นกด q เพื่อออก # e2e จะ boot แอปจริง — ถ้า fail เพราะ dependency ของ database ให้จดไว้ก่อน npm run test:e2e

ขั้นที่ 2: ทำให้ CoffeesService suite กลับมาเขียว

เปิด watch mode เฉพาะ coffees.service แล้วเติม mock providers ว่างจนกว่า test should be defined จะผ่าน

npm run test:watch -- coffees.service # แก้ coffees.service.spec.ts: เพิ่ม providers mock ตามโค้ดด้านบน # (import PrismaService จาก '../prisma/prisma.service.js')

จากนั้นรันทั้ง suite ด้วย npm run test จะเห็นว่าอีกสองไฟล์ที่ CLI สร้างไว้ให้ก็ fail ด้วยเหตุผลเดียวกัน — coffees.controller.spec.ts ขาด CoffeesService และ coffee-rating.service.spec.ts ขาด CoffeesService เช่นกัน ใส่ mock ว่างด้วยวิธีเดียวกันให้ทั้งคู่ เพื่อให้ทั้ง suite กลับมาเขียวก่อนเข้าบทถัดไป

// coffees.controller.spec.ts
controllers: [CoffeesController],
providers: [{ provide: CoffeesService, useValue: {} }],

// coffee-rating.service.spec.ts
providers: [
  CoffeeRatingService,
  { provide: CoffeesService, useValue: {} },
],

ควรได้ผลลัพธ์แบบนี้

หลังเพิ่ม mocks ที่จำเป็นแล้ว npm run test ผ่านทุก suite โดยไม่มี error เรื่อง dependency ส่วน watch mode สามารถเลือกเฉพาะ coffees.service.spec.ts และรันซ้ำอัตโนมัติเมื่อไฟล์เปลี่ยนได้

ลองเช็กให้แน่ใจ

  • npm run test รันจบและทุก suite ผ่าน พร้อมสรุป Test Files และ Tests
  • npm run test:cov สร้าง coverage/index.html และเปิดดูรายงาน coverage รายไฟล์ได้
  • เปิด package.json ดูว่า scripts test, test:watch, test:cov, test:e2e ชี้ไปที่ vitest จริง
  • เปิด vitest.config.e2e.ts และสังเกต include ว่าจับเฉพาะ **/*.e2e-spec.ts ขณะที่ vitest.config.ts จับ **/*.spec.ts
  • ผลของ npm run test:watch -- coffees.service แสดงแค่ suite ของ coffees.service.spec.ts ไม่ใช่ทุกไฟล์
  • ลองลบ mock ของ PrismaService ออกแล้วดูว่า error dependency กลับมา — ยืนยันว่าเข้าใจว่า mock ตัวนี้แก้ปัญหาอะไร
  • แก้ไฟล์ service เล็กน้อยระหว่าง watch เปิดอยู่ แล้วเห็น Vitest รันซ้ำอัตโนมัติ
  • ตรวจว่าไฟล์ spec อยู่ข้างไฟล์ source ตาม convention ไม่ได้ย้ายไป test/
  • npm run test (ทั้ง suite) ผ่านครบทุกไฟล์ ไม่เหลือ error can't resolve dependencies ค้างอยู่
