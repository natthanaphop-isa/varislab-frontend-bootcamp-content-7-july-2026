สร้าง Relation ระหว่างสอง Models

บทนี้เราจะทำอะไรบ้าง

  • แยกความแตกต่างของ relation ทั้งสามแบบ: one-to-one, one-to-many/many-to-one และ many-to-many และรู้ว่าแต่ละแบบเขียนอย่างไรใน schema.prisma
  • ผูก Coffee กับ Flavor แบบ many-to-many ด้วย relation field Flavor[] / Coffee[] ทั้งสองฝั่ง
  • อธิบายได้ว่าตารางเชื่อม _CoffeeToFlavor เกิดขึ้นได้อย่างไร และทำไม Flavor.name ต้องเป็น @unique

Relation สามแบบที่ต้องรู้จัก

Relation คือความสัมพันธ์ระหว่างตารางที่ผูกกันด้วยฟิลด์ร่วม โดยทั่วไปคือ primary key กับ foreign key Prisma ให้เรานิยามความสัมพันธ์เหล่านี้เป็น relation field ใน schema.prisma โดยตรง แล้วสร้าง foreign key และตารางที่จำเป็นในฐานข้อมูลให้เอง

ชนิดความหมายหน้าตาใน schema.prisma
One-to-oneแถวในตารางหลักจับคู่กับแถวในตารางปลายทางได้แถวเดียวเท่านั้นฝั่งหนึ่ง profile Profile? อีกฝั่ง user User @relation(fields: [userId], references: [id]) พร้อม userId Int @unique
One-to-many / Many-to-oneแถวในตารางหลักมีแถวที่เกี่ยวข้องในตารางปลายทางได้หลายแถวฝั่ง one: posts Post[] ฝั่ง many: author User @relation(fields: [authorId], references: [id]) พร้อม authorId Int
Many-to-manyทั้งสองฝั่งต่างมีแถวที่เกี่ยวข้องกันได้หลายแถวflavors Flavor[] และ coffees Coffee[] — ไม่ต้องเขียน foreign key เอง Prisma สร้างตารางเชื่อมให้ (implicit many-to-many)

กาแฟหนึ่งตัวมีได้หลาย flavor และ flavor หนึ่ง (เช่น chocolate) ก็อยู่ในกาแฟได้หลายตัว — ความสัมพันธ์ระหว่าง Coffee กับ Flavor จึงเป็น many-to-many

เปลี่ยน flavors จาก scalar list เป็น model จริง

เพิ่ม model Flavor ใหม่ใน prisma/schema.prisma แล้วแก้ field flavors ของ Coffee ให้ชี้ไปหา model นั้นแทน String[] เดิม กติกาสำคัญของ Prisma คือต้องประกาศ relation ทั้งสองฝั่งเสมอ — ถ้าเขียนแค่ flavors Flavor[] ฝั่ง Coffee แต่ลืม coffees Coffee[] ฝั่ง Flavor Prisma จะ error ทันที (หรือสั่ง npx prisma format ให้เติมฝั่งที่ขาดให้อัตโนมัติ)

/* prisma/schema.prisma */
model Coffee {
  id      Int      @id @default(autoincrement())
  name    String
  brand   String
  flavors Flavor[] // "กาแฟตัวนี้มี flavor อะไรบ้าง"

  @@map("coffee")
}

model Flavor {
  id      Int      @id @default(autoincrement())
  name    String   @unique
  coffees Coffee[] // "flavor นี้อยู่ในกาแฟตัวไหนบ้าง"

  @@map("flavor")
}

เพราะทั้งสองฝั่งเป็น array และไม่มีฝั่งไหนถือ foreign key เอง Prisma จึงรู้ว่านี่คือ implicit many-to-many และจะสร้างตารางเชื่อมชื่อ _CoffeeToFlavor ให้เองโดยที่เราไม่ต้องเขียน model ของมันเลย ตารางนี้มีสองคอลัมน์คือ A (id ของ Coffee) และ B (id ของ Flavor) — ชื่อตารางและลำดับ A/B มาจากการเรียงชื่อ model ตามตัวอักษร

ส่วน @unique บน Flavor.name ทำสองหน้าที่: กันไม่ให้มี chocolate ซ้ำกันหลายแถวในตาราง flavor และเป็นฟิลด์ที่บทที่ 27 จะใช้ค้นหา flavor เดิมด้วย connectOrCreate ซึ่งบังคับว่าต้องค้นด้วยฟิลด์ที่ unique เท่านั้น ก่อน push ลองรัน npx prisma validate เพื่อให้ Prisma ตรวจว่า relation ครบทั้งสองฝั่งและชนิดตรงกัน

การเปลี่ยนคอลัมน์ flavors จาก array เป็น relation คือการ drop คอลัมน์พร้อมข้อมูลในนั้น — ถ้าตาราง coffee มีแถวอยู่ (จาก workshop บทที่ 24) npx prisma db push จะหยุดเตือนว่าข้อมูลในคอลัมน์จะหาย แล้วถามยืนยัน Do you want to ignore the warning(s)? ตอบ y ได้เฉพาะบนเครื่อง dev เท่านั้น (หรือใส่ flag --accept-data-loss เพื่อข้ามคำถาม) ถ้าตารางยังว่างจะ push ผ่านเงียบ ๆ เพราะไม่มีข้อมูลให้เสีย — นี่คือเหตุผลที่ production ต้องใช้ migrations (บทที่ 31) แทน

หลัง push อย่าลืม npx prisma generate — ตอนนี้ generated client จะมี type Flavor เพิ่มขึ้นมา และ CoffeesService.create() จะtype-check ไม่ผ่านชั่วคราว เพราะ flavors: string[] ใน DTO ไม่ตรงกับ relation field แล้ว ถือว่าถูกต้อง ให้คอมเมนต์ body ของ create/update ออกก่อน (หรือ cast เป็น any ชั่วคราว) แล้วเราจะเขียนใหม่ให้ถูกต้องในบทที่ 27

ผูก Coffee กับ Flavor เข้าด้วยกัน

เพิ่ม model Flavor และแก้ Coffee ใน schema.prisma ตามโค้ดด้านบน validate แล้ว push ลงฐานข้อมูล generate client ใหม่ จากนั้นไปดูตารางที่เกิดขึ้น

npx prisma validate npx prisma db push # ตอบ y เมื่อถูกถามเรื่อง data loss (dev เท่านั้น) npx prisma generate npm run start:dev # ใน pgAdmin ควรเห็น 3 ตาราง: # coffee - ข้อมูลกาแฟ (ไม่มีคอลัมน์ flavors แล้ว) # flavor - ข้อมูล flavor # _CoffeeToFlavor - ตารางเชื่อม many-to-many (คอลัมน์ A, B)

ควรได้ผลลัพธ์แบบนี้

ฐานข้อมูลมี 3 ตาราง: coffee (ไม่มีคอลัมน์ flavors แล้ว), flavor และตารางเชื่อม _CoffeeToFlavor ที่ถือ foreign key ของทั้งสองฝั่งในคอลัมน์ A และ B ตอนนี้ endpoint สร้างกาแฟพร้อม flavor จะยังทำงานไม่ครบ — เราจะแก้ให้บันทึกลง relation จริงในบทที่ 27 เรื่อง nested writes

ลองเช็กให้แน่ใจ

  • npx prisma validate ผ่านโดยไม่มี error เรื่อง relation ขาดฝั่ง — ทั้ง flavors Flavor[] และ coffees Coffee[] ประกาศครบ
  • เห็นตาราง _CoffeeToFlavor ใน pgAdmin พร้อมคอลัมน์ A/B ที่เป็น foreign key ไปยัง coffee.id และ flavor.id
  • คอลัมน์ flavors ชนิด array หายไปจากตาราง coffee แล้ว และ flavor.name มี unique constraint
  • เปิด src/generated/prisma/client แล้วเห็น type Flavor export ออกมา (แสดงว่า generate ใหม่สำเร็จ)
