ใช้ Prisma Client เข้าถึงฐานข้อมูล

เมื่อจบบทนี้ คุณจะสามารถ

  • ฉีด PrismaService เข้า service ผ่าน constructor injection ปกติของ Nest
  • แปลง CRUD ทั้ง 5 method จาก array ในหน่วยความจำมาเป็นการเรียกฐานข้อมูลจริง
  • เลือกใช้ findMany, findUnique, create, update, delete ให้ถูกกับสถานการณ์

ทุก model คือ property บน Prisma Client

หลัง generate ในบทที่แล้ว Prisma Client รู้จัก model Coffee แล้ว และเปิดให้เราเข้าถึงตารางผ่าน property ชื่อเดียวกับ model แบบ lowerCamelCase คือ prisma.coffee ซึ่งมี method ครบสำหรับ query ตารางนั้นโดยเฉพาะ ทุก argument และค่าที่คืนกลับถูก type จาก schema จึงได้ autocomplete ทั้งชื่อ field และชนิดข้อมูล เราขอ Client มาใช้ด้วยการฉีด PrismaService ผ่าน constructor — ไม่ต้องมี decorator พิเศษ เพราะ PrismaModule เป็น global ตั้งแต่บทที่ 22 นี่คือ pattern เดียวกับที่ฉีด provider อื่น ๆ ของ Nest จึงทดสอบและ mock ได้ง่ายในบทเรื่อง testing

import { Injectable, NotFoundException } from '@nestjs/common';
import { PrismaService } from '../prisma/prisma.service.js';
import { CreateCoffeeDto } from './dto/create-coffee.dto.js';
import { UpdateCoffeeDto } from './dto/update-coffee.dto.js';

@Injectable()
export class CoffeesService {
  constructor(private readonly prisma: PrismaService) {}

  findAll() {
    return this.prisma.coffee.findMany();
  }

  async findOne(id: string) {
    const coffee = await this.prisma.coffee.findUnique({ where: { id: +id } });
    if (!coffee) {
      throw new NotFoundException(`Coffee #${id} not found`);
    }
    return coffee;
  }

  create(createCoffeeDto: CreateCoffeeDto) {
    return this.prisma.coffee.create({ data: createCoffeeDto });
  }

  async update(id: string, updateCoffeeDto: UpdateCoffeeDto) {
    await this.findOne(id); // ให้ id ที่ไม่มีจริงได้ 404 แบบเดียวกัน
    return this.prisma.coffee.update({
      where: { id: +id },
      data: updateCoffeeDto,
    });
  }

  async remove(id: string) {
    await this.findOne(id);
    return this.prisma.coffee.delete({ where: { id: +id } });
  }
}

method ไหนทำอะไร

Methodทำอะไรจุดที่ควรสังเกต
findMany() / findUnique()ดึงหลายแถว / แถวเดียวตามเงื่อนไข wherefindUnique คืน null เมื่อไม่พบ — เราจึงต้อง throw NotFoundException เอง และ where ของมันรับได้เฉพาะ field ที่ unique เช่น id
create({ data })insert แถวใหม่ลงฐานข้อมูลทันทีคืนแถวที่บันทึกแล้วพร้อม id ที่ฐานข้อมูลรันให้ — ไม่มีขั้น "สร้างในหน่วยความจำก่อน" แยกต่างหาก
update({ where, data })แก้แถวที่ตรงกับ where ด้วยค่าใน dataถ้า id ไม่มีจริง Prisma throw error รหัส P2025 ซึ่งกลายเป็น 500 — เราจึงเรียก findOne ก่อนเพื่อให้ได้ 404 ที่สะอาด (อีกทางคือ map P2025 ใน exception filter บทที่ 51)
delete({ where })ลบแถวที่ตรงกับ where ออกจากตารางreuse findOne ก่อนด้วยเหตุผลเดียวกับ update — id ที่ไม่มีจริงต้องได้ 404 เหมือนกัน

สังเกตว่า id รับเข้ามาเป็น string จาก route parameter แล้วแปลงเป็นตัวเลขด้วย +id ก่อนใช้ query — Prisma จะไม่ยอมรับ string ในช่อง id ที่เป็น Int เลยแม้แต่ตอน compile ในบทที่ 56 เราจะเห็นวิธีที่สะอาดกว่าด้วย ParseIntPipe และ custom pipes

ย้าย CoffeesService ลงฐานข้อมูลจริง

แทนที่ array และ logic เดิมทั้งหมดใน CoffeesService ด้วยโค้ดด้านบน ตอนนี้ไม่มีที่ไหน import Coffee จาก entities/coffee.entity.ts อีกแล้ว (type Coffee มาจาก Prisma Client โดยตรงผ่าน this.prisma.coffee) ลบไฟล์ src/coffees/entities/coffee.entity.ts ทิ้งได้เลย แล้วทดสอบ CRUD ครบวงจรผ่าน Insomnia

POST http://localhost:3000/coffees { "name": "Shipwreck Roast", "brand": "Buddy Brew", "flavors": ["chocolate", "vanilla"] } GET http://localhost:3000/coffees GET http://localhost:3000/coffees/1 PATCH http://localhost:3000/coffees/1 { "name": "Updated Roast" } DELETE http://localhost:3000/coffees/1

ผลลัพธ์ที่คาดหวัง

ทุก endpoint ทำงานเหมือนเดิมจากมุมมองของ client แต่ข้อมูลถูกเก็บถาวรแล้ว — restart แอปแล้วข้อมูลไม่หาย และเห็นแถวจริงในตาราง coffee ผ่าน pgAdmin โดย flavors ถูกเก็บเป็น array ในคอลัมน์เดียว ส่วน id ที่ไม่มีจริงได้ response 404 พร้อมข้อความ Coffee #id not found

ตรวจว่าใช้งานได้จริง

  • POST แล้วเห็นแถวใหม่ในตาราง coffee ผ่าน pgAdmin หรือ SELECT * FROM coffee;
  • restart แอป (Ctrl+C แล้ว npm run start:dev ใหม่) แล้ว GET ยังเห็นข้อมูลเดิม
  • GET /coffees/9999 ได้ status 404 พร้อม message ที่อ่านรู้เรื่อง
  • PATCH ด้วย id จริงได้ค่าใหม่กลับมา และ PATCH ด้วย id ปลอมได้ 404 ไม่ใช่ 500 (พิสูจน์ว่า guard findOne ทำงานก่อน update)
