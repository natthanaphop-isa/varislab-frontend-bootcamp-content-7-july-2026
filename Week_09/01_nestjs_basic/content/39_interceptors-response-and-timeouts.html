สร้าง Interceptors สำหรับ Response และ Timeout

บทนี้เราจะทำอะไรบ้าง

  • อธิบายได้ว่า interceptor ทำงานรอบ route handler ทั้งขาเข้าและขาออกอย่างไร
  • สร้าง interceptor ที่จัดรูป response ด้วย RxJS map()
  • สร้าง timeout interceptor ด้วย timeout() และ catchError()
  • ผูก interceptor หลายตัวและอธิบายผลของลำดับการลงทะเบียนได้

Interceptor คือจุดแทรก (pointcut) รอบ ๆ handler

Interceptor ได้แรงบันดาลใจจาก Aspect-Oriented Programming: มันให้เรากำหนด pointcut — จุดที่ logic เสริมเข้าไปเกาะรอบการทำงานของ method โดยไม่ต้องแก้ method นั้นเลย ตามเอกสารต้นทาง interceptor ทำได้ทั้งหมดนี้

  • ผูก logic เพิ่มเติมก่อนหรือหลังการทำงานของ method
  • แปลงผลลัพธ์ที่ method คืนออกมา
  • แปลง exception ที่ถูกโยนจาก method
  • ขยายพฤติกรรมพื้นฐานของ method
  • หรือกระทั่งข้ามการทำงานของ method ไปเลยตามเงื่อนไข เช่น ตอบจาก cache แทนการเรียกจริง

ต่างจาก guard ที่ตอบแค่ผ่าน/ไม่ผ่าน interceptor เห็นทั้งขาเข้าและขาออก จึงเหมาะกับงานอย่าง logging, caching และการจัดรูป response

สร้าง WrapResponseInterceptor

nest g interceptor common/interceptors/wrap-response

interface NestInterceptor มีเมธอดเดียวคือ intercept(context, next) — โค้ดที่รันก่อน next.handle() คือ logic ก่อน handler ส่วน pipeline ของ RxJS ที่ต่อท้าย next.handle() คือ logic หลัง handler เพราะ handle() คืน Observable ของ response stream

import {
  CallHandler,
  ExecutionContext,
  Injectable,
  NestInterceptor,
} from '@nestjs/common';
import { Observable } from 'rxjs';
import { map } from 'rxjs/operators';

@Injectable()
export class WrapResponseInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    console.log('Before...');

    return next.handle().pipe(map(data => ({ data })));
  }
}

map(data => ({ data })) รับผลลัพธ์เดิมของ handler แล้วห่อไว้ใต้ key data — จาก [...] กลายเป็น { "data": [...] } ทุก endpoint โดยไม่ต้องแตะ controller แม้แต่บรรทัดเดียว ส่วน console.log('Before...') พิสูจน์ว่า interceptor ได้ทำงานก่อน handler จริง

ลงทะเบียนแบบ global

app.useGlobalInterceptors(new WrapResponseInterceptor());

เช่นเดียวกับ filter และ guard: interceptor ผูกได้ทั้งระดับ method/controller ด้วย @UseInterceptors() หรือผ่าน APP_INTERCEPTOR token เมื่อจำเป็นต้อง inject dependency — เวอร์ชันนี้ไม่มี dependency จึง new ใน main.ts ได้เลย

ขยาย response stream ด้วย RxJS operators

อีกเทคนิคที่ทรงพลังของ interceptor คือการต่อ RxJS operator เข้ากับ response stream เพื่อขยายพฤติกรรมพื้นฐานของ method ลองนึกภาพว่าเราต้องจัดการ timeout ให้กับทุก route: เมื่อ endpoint ไหนไม่ตอบภายในเวลาที่กำหนด เราต้องยุติ request นั้นและส่ง error message กลับไป แทนที่จะปล่อยให้ client ค้างรอไปเรื่อย ๆ — งานแบบนี้เขียนครั้งเดียวใน interceptor ตัวเดียวแล้วมีผลทั้งแอป

nest g interceptor common/interceptors/timeout

TimeoutInterceptor: timeout + catchError

import {
  CallHandler,
  ExecutionContext,
  Injectable,
  NestInterceptor,
  RequestTimeoutException,
} from '@nestjs/common';
import { Observable, throwError, TimeoutError } from 'rxjs';
import { catchError, timeout } from 'rxjs/operators';

@Injectable()
export class TimeoutInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    return next.handle().pipe(
      timeout(3000),
      catchError(err => {
        if (err instanceof TimeoutError) {
          return throwError(new RequestTimeoutException());
        }
        return throwError(err);
      }),
    );
  }
}

pipeline อ่านตรงตัว: timeout(3000) จะโยน TimeoutError ของ RxJS ถ้า handler ไม่ emit ค่าภายใน 3 วินาที จากนั้น catchError ดักทุก error ในสาย — ถ้าเป็น TimeoutError ก็แปลงเป็น RequestTimeoutException ของ NestJS (HTTP 408) เพื่อให้เข้าระบบ exception layer และ HttpExceptionFilter ของเราตามปกติ ส่วน error ชนิดอื่นถูกโยนต่อไม่แตะต้อง

ผูกหลาย interceptor พร้อมกัน

useGlobalInterceptors รับได้หลายตัวเรียงตามลำดับ — request ไหลผ่านจากซ้ายไปขวาขาเข้า และย้อนกลับขาออก

app.useGlobalInterceptors(
  new WrapResponseInterceptor(),
  new TimeoutInterceptor(),
);

ระหว่างทดสอบ เราบังคับให้ endpoint ช้าเกิน 3 วินาทีด้วยการหน่วงชั่วคราวใน handler เช่นใน findAll() ของ CoffeesController

await new Promise(resolve => setTimeout(resolve, 5000));

อย่าลืมลบบรรทัดหน่วงเวลานี้ออกหลังทดสอบเสร็จ — มันมีไว้เพียงเพื่อพิสูจน์ว่า interceptor ทำงาน ถ้าติดไปกับโค้ดจริงทุก request จะโดนตัดที่ 3 วินาทีทั้งหมด นอกจากนี้ throwError(value) เป็นรูปแบบเก่าของ RxJS — เวอร์ชันปัจจุบันแนะนำ throwError(() => new RequestTimeoutException())

ห่อ response และจำกัดเวลาของ request

ขั้นที่ 1: ห่อ response ของ iluvcoffee ทั้งแอป

สร้าง interceptor ตามโค้ดด้านบน ลงทะเบียนใน main.ts แล้วยิง endpoint ใดก็ได้เพื่อดูรูปแบบ response ใหม่

nest g interceptor common/interceptors/wrap-response # main.ts app.useGlobalInterceptors(new WrapResponseInterceptor()); # ทดสอบ curl http://localhost:3000/coffees

ขั้นที่ 2: บังคับ timeout ให้เกิดจริงใน iluvcoffee

สร้าง TimeoutInterceptor ผูกต่อจาก WrapResponseInterceptor ใน main.ts แล้วหน่วง findAll() 5 วินาทีเพื่อดู 408 ด้วยตาตัวเอง

nest g interceptor common/interceptors/timeout # coffees.controller.ts — ใน findAll() (ชั่วคราว) await new Promise(resolve => setTimeout(resolve, 5000)); # ทดสอบ curl -i http://localhost:3000/coffees

ควรได้ผลลัพธ์แบบนี้

ทุก response สำเร็จถูกห่อเป็น { "data": ... } เช่น GET /coffees คืน { "data": [ {...}, {...} ] } และใน terminal ของ dev server เห็น Before... ทุกครั้งที่มี request เข้า

request ค้างประมาณ 3 วินาที (ไม่ใช่ 5) แล้วได้ 408 Request Timeout พร้อม body รูปแบบกลางจาก filter เช่น { "statusCode": 408, "message": "Request Timeout", "timestamp": "..." } เมื่อลบบรรทัดหน่วงออก endpoint กลับมาตอบปกติ

ลองเช็กให้แน่ใจ

  • ยิง GET /coffees และ GET /coffees/1 แล้วดูว่า payload เดิมทั้งคู่ย้ายไปอยู่ใต้ key data
  • ดู log Before... ใน terminal เพื่อยืนยันว่า logic ก่อน handler ทำงาน
  • ยิง request ที่ error (เช่น 404) แล้วสังเกตว่า error ไม่ถูกห่อ เพราะ exception ไปเข้า filter ไม่ผ่าน map ของ interceptor
  • ตรวจว่า guard จากบทก่อนยังทำงานร่วมกันได้: request ที่ไม่มี key ถูกตัดก่อนถึง interceptor
  • จับเวลา request ที่หน่วงไว้ — ต้องถูกตัดที่ ~3 วินาทีตามค่า timeout(3000) ไม่ใช่รอครบ 5 วินาที
  • ตรวจ status code ว่าเป็น 408 และ body มี timestamp จาก HttpExceptionFilter
  • ลบบรรทัดหน่วงเวลาแล้วยิงซ้ำ — ต้องได้ 200 พร้อม response ที่ยังห่อใน data จาก interceptor ตัวแรก
  • ลองเปลี่ยนค่า timeout เป็น 100 ms เพื่อยืนยันว่า endpoint จริง ๆ ก็โดนตัดได้ แล้วปรับกลับ
