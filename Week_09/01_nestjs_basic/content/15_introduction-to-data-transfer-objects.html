รู้จัก Data Transfer Objects (DTO)

เมื่อจบบทนี้ คุณจะสามารถ

  • อธิบายได้ว่า DTO คืออะไรและต่างจาก entity อย่างไร
  • สร้าง DTO class ด้วย Nest CLI และใช้แทน any ใน @Body()
  • ให้เหตุผลได้ว่าทำไม property ของ DTO ควรเป็น readonly และทำไม update จึงใช้ optional

DTO คือสัญญาของข้อมูลที่วิ่งข้ามเส้น

ตอนนี้ create() และ update() ของเรารับ @Body() body เป็น type any — คอมไพเลอร์ช่วยอะไรไม่ได้เลย และไม่มีเอกสารว่า client ต้องส่งอะไรมา Data Transfer Object (DTO) คือ class ง่าย ๆ ที่ประกาศ "รูปร่าง" ของข้อมูลที่เดินทางเข้า (หรือออก) จาก API — ไม่มี logic มีแต่ property เพื่อเป็นสัญญาที่ทั้ง type system, เอกสาร และ (บทหน้า) ระบบ validation ใช้ร่วมกัน

สร้าง DTO ด้วย CLI โดยใส่ --no-spec เพราะ class เปล่า ๆ ไม่จำเป็นต้องมีไฟล์ test:

nest g class coffees/dto/create-coffee.dto --no-spec
/* dto/create-coffee.dto.ts */
export class CreateCoffeeDto {
  readonly name: string;
  readonly brand: string;
  readonly flavors: string[];
}
/* dto/update-coffee.dto.ts */
export class UpdateCoffeeDto {
  readonly name?: string;
  readonly brand?: string;
  readonly flavors?: string[];
}

สังเกตสองจุด: ทุก property เป็น readonly เพราะ DTO ควรเป็น snapshot ของข้อมูลขาเข้าที่ไม่ถูกแก้ระหว่างทาง (immutability ช่วยลด bug) และ UpdateCoffeeDto ใช้ ? ทุกตัวเพราะ PATCH เป็น partial update — client ส่งมาเฉพาะ field ที่อยากแก้

DTO ไม่ใช่ Entity

DTOEntity
บทบาทรูปร่างข้อมูลที่รับ-ส่งข้ามขอบเขต APIตัวแทนข้อมูลใน domain / ฐานข้อมูล
มี id ไหมไม่ — client ไม่ใช่คนกำหนด idมี — เป็น identity ของ record
เปลี่ยนตามอะไรความต้องการของแต่ละ endpointโครงสร้างข้อมูลจริงของระบบ

นำ DTO ไปใช้ใน controller แทน any ทันที:

@Post()
create(@Body() createCoffeeDto: CreateCoffeeDto) {
  return this.coffeesService.create(createCoffeeDto);
}

@Patch(':id')
update(@Param('id') id: string, @Body() updateCoffeeDto: UpdateCoffeeDto) {
  return this.coffeesService.update(id, updateCoffeeDto);
}

ณ จุดนี้ DTO ยังเป็นแค่สัญญาระดับ type — ตอน runtime ยังไม่มีอะไรบังคับว่า client ต้องส่งข้อมูลตามนี้จริง บทถัดไปเราจะเติม class-validator เพื่อให้สัญญานี้มีผลจริงตอนรับ request

อย่าลืมอัปเดต service ให้ตรงกับ DTO ใหม่

CreateCoffeeDto ไม่มี id (client ไม่ใช่คนกำหนด id) แต่ coffees.service.ts เดิมเก็บข้อมูลเป็น Coffee[] ที่ id เป็น field บังคับ ถ้าเปลี่ยน signature ของ create() เป็น CreateCoffeeDto โดยไม่แก้ตัว method ด้วย this.coffees.push(createCoffeeDto) เดิมจะคอมไพล์ไม่ผ่าน (property id ขาดหาย) — ต้องสร้าง id เพิ่มเองก่อน push:

/* coffees.service.ts */
create(createCoffeeDto: CreateCoffeeDto) {
  const coffee = { id: this.coffees.length + 1, ...createCoffeeDto };
  this.coffees.push(coffee);
  return coffee;
}

แทนที่ any ด้วย DTO ทั้งสองตัว

สร้าง CreateCoffeeDto และ UpdateCoffeeDto ในโฟลเดอร์ coffees/dto/ แล้วอัปเดต signature ของ create() และ update() ทั้งใน controller และ service ให้ใช้ type ใหม่ (ดูโค้ด create() ที่แก้แล้วด้านบน — ไม่งั้น TypeScript จะฟ้องว่า id ขาดหาย)

nest g class coffees/dto/create-coffee.dto --no-spec nest g class coffees/dto/update-coffee.dto --no-spec # แก้ controller + service ให้รับ CreateCoffeeDto / UpdateCoffeeDto

ผลลัพธ์ที่คาดหวัง

โค้ดคอมไพล์ผ่านและ editor เริ่มช่วย autocomplete ชื่อ property ของ payload ได้ พฤติกรรม runtime ยังเหมือนเดิมทุกอย่าง (ยังไม่มี validation) แต่ตอนนี้ทุกคนที่อ่านโค้ดรู้ทันทีว่า POST /coffees คาดหวัง name, brand และ flavors

ตรวจว่าใช้งานได้จริง

  • ไม่มี @Body() body ที่เป็น any เหลืออยู่ใน coffees.controller.ts
  • ลองพิมพ์ createCoffeeDto. ใน editor แล้วเห็น autocomplete ของ name, brand, flavors
  • ลอง assign ค่าใหม่ให้ property ของ DTO ใน service แล้ว TypeScript ฟ้องเพราะเป็น readonly
  • POST /coffees และ PATCH /coffees/1 ยังทำงานได้ตามปกติ
