ใช้ Transactions

บทนี้เราจะทำอะไรบ้าง

  • อธิบายได้ว่า transaction แก้ปัญหาอะไร และเมื่อไหร่ที่การเขียนสองครั้งติดกันไม่พอ
  • เพิ่ม Event model และคอลัมน์ recommendations ลงใน schema.prisma แล้ว push ขึ้นฐานข้อมูล
  • ใช้ this.prisma.$transaction(async (tx) => …) ให้หลาย query commit หรือ rollback พร้อมกันโดยไม่ต้องจัดการ connection เอง

งานที่ต้องสำเร็จด้วยกันหรือล้มด้วยกัน

Transaction คือหน่วยของงานฐานข้อมูลที่ต้องเกิดผลแบบ all-or-nothing สมมติเราเพิ่มฟีเจอร์ "แนะนำกาแฟ" ที่ต้องทำสองอย่าง: เพิ่มตัวนับ recommendations ของกาแฟ และบันทึกแถว event ลงอีกตารางเพื่อ analytics ถ้า query แรกสำเร็จแต่ตัวที่สองล้ม ข้อมูลจะค้างอยู่ในสภาพครึ่ง ๆ กลาง ๆ ที่เชื่อถือไม่ได้ — transaction ทำให้ทั้งคู่ commit พร้อมกัน หรือ rollback กลับทั้งหมด

เริ่มจากประกาศตารางใหม่ ใน Prisma ทุกตารางของโปรเจกต์ถูกนิยามในไฟล์ schema.prisma ไฟล์เดียว จึงไม่ต้องสร้างไฟล์ class แยกด้วย CLI — เพิ่ม Event model ต่อท้าย และเพิ่มฟิลด์ recommendations เข้า Coffee ด้วย @default(0)

model Coffee {
  id              Int      @id @default(autoincrement())
  name            String
  brand           String
  recommendations Int      @default(0)
  flavors         Flavor[]

  @@map("coffee")
}

model Event {
  id      Int    @id @default(autoincrement())
  type    String
  name    String
  payload Json

  @@map("event")
}
npx prisma db push
npx prisma generate

ชนิด Json กลายเป็นคอลัมน์ jsonb ใน PostgreSQL รับโครงสร้าง object อะไรก็ได้ และหลัง generate เราจะได้ type Event กับ property this.prisma.event มาใช้ทันที

Interactive transaction: ห่อทุกอย่างไว้ใน callback

PrismaService ที่เรา inject ไว้แล้วมีเมธอด $transaction() รับ callback ที่ได้ tx — Prisma Client อีกตัวที่ผูกกับ transaction นี้โดยเฉพาะ — ทุก query ภายในต้องเรียกผ่าน tx ไม่ใช่ this.prisma จึงจะอยู่ใน transaction เดียวกัน

@Injectable()
export class CoffeesService {
  constructor(private readonly prisma: PrismaService) {}

  async recommendCoffee(id: string) {
    return this.prisma.$transaction(async (tx) => {
      const coffee = await tx.coffee.update({
        where: { id: +id },
        data: { recommendations: { increment: 1 } },
      });

      await tx.event.create({
        data: {
          type: 'coffee',
          name: 'recommend_coffee',
          payload: { coffeeId: coffee.id },
        },
      });

      return coffee;
    });
  }
}

กติกาของ callback นี้คือหัวใจของบท:

  • ทุก query ข้างในเรียกผ่าน tx — ถ้าเผลอใช้ this.prisma query นั้นจะวิ่งนอก transaction และ rollback ไม่ได้
  • callback return เมื่อไหร่ Prisma COMMIT ให้ทันที
  • callback throw (หรือ query ใดล้ม) เมื่อไหร่ Prisma ROLLBACK ทุกอย่างที่ทำไปแล้วโดยอัตโนมัติ แล้วโยน error ต่อออกมาให้เรา
  • connection ถูกคืนกลับ pool ให้เองเสมอ — ไม่มี release() ให้ลืม

สังเกต { increment: 1 } ด้วย: นี่คือ atomic update operator ที่ให้ฐานข้อมูลบวกค่าเองใน SQL (SET recommendations = recommendations + 1) แทนการอ่านค่ามาบวกใน JavaScript แล้วเขียนกลับ ซึ่งจะพลาดได้เมื่อสองคำขอมาพร้อมกัน

รูปแบบหน้าตาเหมาะกับ
Interactive$transaction(async (tx) => { … })query หลังต้องใช้ผลของ query ก่อน หรือมี logic/เงื่อนไขคั่นกลาง (เช่นตัวอย่างนี้ที่ event ต้องรู้ coffee.id)
Batch$transaction([q1, q2, q3])query อิสระหลายตัวที่แค่อยากให้สำเร็จหรือล้มพร้อมกัน เช่นลบหลายตารางทีเดียว — สั้นกว่าและไม่ถือ connection นาน

Interactive transaction ถือ connection หนึ่งเส้นไว้ตลอดช่วง callback — ทำให้มันสั้นที่สุด อย่าเรียก API ภายนอกหรือรอ I/O ที่ไม่เกี่ยวข้องข้างใน Prisma ตั้ง timeout ไว้ 5 วินาทีโดย default (ปรับได้ผ่าน option { timeout }) ถ้าเกินจะ rollback ทิ้งทั้งก้อน

เพิ่ม endpoint ทดลองใน controller ที่เรียก this.coffeesService.recommendCoffee(id) ตามโค้ดด้านล่าง — ถ้า id ไม่มีจริง tx.coffee.update จะ throw error รหัส P2025 ภายใน transaction (ซึ่ง rollback ให้อยู่แล้ว) จะเรียก this.findOne(id) ก่อนเข้า transaction เพื่อให้ได้ 404 ที่อ่านรู้เรื่องเหมือน endpoint อื่นก็ได้

// coffees.controller.ts
@Post(':id/recommend')
recommend(@Param('id') id: string) {
  return this.coffeesService.recommendCoffee(id);
}

ทำให้การแนะนำกาแฟเป็น atomic

แก้ schema.prisma ตามด้านบน, push และ generate, เขียน recommendCoffee แล้วต่อ endpoint ทดลองใน controller จากนั้นทดสอบทั้งขาสำเร็จและขา rollback

# อัปเดต schema ลงฐานข้อมูล npx prisma db push npx prisma generate # ทดสอบ POST http://localhost:3000/coffees/1/recommend GET http://localhost:3000/coffees/1 # ดูในฐานข้อมูล SELECT * FROM event; # ทดสอบ rollback: เพิ่มบรรทัดนี้ชั่วคราวหลัง tx.event.create(...) # throw new Error('boom'); # แล้วยิง recommend อีกครั้ง

ควรได้ผลลัพธ์แบบนี้

ทุกครั้งที่ยิง recommend ค่า recommendations ของกาแฟเพิ่มขึ้น 1 และ ตาราง event ได้แถวใหม่ที่ payload ระบุ coffeeId เสมอ — สองตารางขยับพร้อมกันทุกครั้ง เมื่อใส่ throw new Error('boom') ไว้ท้าย callback ตัวนับต้องไม่เพิ่มและไม่มีแถว event ใหม่ แม้ว่า tx.coffee.update จะรันไปแล้วก็ตาม เพราะโดน rollback ทั้งก้อน (ลบบรรทัดทดลองออกเมื่อเสร็จ)

ลองเช็กให้แน่ใจ

  • ยิง recommend 3 ครั้ง — recommendations เป็น 3 และตาราง event มี 3 แถว เท่ากันเป๊ะ
  • ทดลอง sabotage ด้วย throw — ตัวนับไม่ขยับและไม่มีแถว event ใหม่ (แล้วแก้กลับ)
  • แอปยังรับคำขออื่นได้ปกติหลังทดลองหลายรอบ แสดงว่า connection ถูกคืน pool ครบ ไม่มีรั่ว
  • ทุก query ใน callback เรียกผ่าน tx ไม่มี this.prisma หลุดอยู่ข้างใน
