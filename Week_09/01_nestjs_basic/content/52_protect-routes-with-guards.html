ป้องกัน Routes ด้วย Guards

เมื่อจบบทนี้ คุณจะสามารถ

  • อธิบายหน้าที่ของ guard และตำแหน่งของมันใน request lifecycle (ทำงานก่อน interceptor และ pipe)
  • implement CanActivate เพื่อตัดสินใจอนุญาตหรือปฏิเสธ request จากข้อมูลใน ExecutionContext
  • ผูก guard แบบ global และทดสอบว่า request ที่ไม่มี key ถูกตอบกลับด้วย 403

Guard ตอบคำถามเดียว: request นี้ควรไปต่อหรือไม่

Guard เป็น building block ที่มีหน้าที่เดียวชัดเจน — คืนค่า boolean ว่า request ปัจจุบันได้รับอนุญาตให้ถึง route handler หรือไม่ ถ้าคืน false NestJS จะตัด request ทันทีและตอบ 403 Forbidden ให้เอง จึงเป็นที่ที่เหมาะกับงาน authentication และ authorization เช่น ตรวจ API key, ตรวจ token หรือตรวจ role ของผู้ใช้ ต่างจาก middleware ตรงที่ guard เข้าถึง ExecutionContext ได้ จึงรู้ว่า handler ไหนกำลังจะถูกเรียก — ความสามารถนี้จะสำคัญมากในบทถัดไปเมื่อเราอ่าน metadata ของ handler

generate โครงไฟล์ไว้ใน common/guards เพราะเป็น logic ที่ใช้ร่วมทั้งแอป

nest g guard common/guards/api-key

implement CanActivate

guard ทุกตัวเป็นคลาสที่ติด @Injectable() และ implement interface CanActivate ซึ่งมีเมธอดเดียวคือ canActivate(context) — คืนได้ทั้ง boolean ตรง ๆ, Promise หรือ Observable สำหรับการตรวจแบบ async ในเวอร์ชันแรกนี้เราเทียบ Authorization header กับค่า API_KEY จาก environment แบบตรงไปตรงมา

import { CanActivate, ExecutionContext, Injectable } from '@nestjs/common';
import { Request } from 'express';
import { Observable } from 'rxjs';

@Injectable()
export class ApiKeyGuard implements CanActivate {
  canActivate(
    context: ExecutionContext,
  ): boolean | Promise<boolean> | Observable<boolean> {
    const request = context.switchToHttp().getRequest<Request>();
    const authHeader = request.header('Authorization');
    return authHeader === process.env.API_KEY;
  }
}

context.switchToHttp().getRequest() คือ pattern เดียวกับที่เห็นใน exception filter: แปลง context กลางของ NestJS ให้เป็น HTTP request ของ Express เพื่ออ่าน header จากนั้นตั้งค่า API_KEY ในไฟล์ .env ให้เรียบร้อยก่อนทดสอบ

ผูกแบบ global ใน main.ts

app.useGlobalGuards(new ApiKeyGuard());

ตอนนี้ ทุก endpoint ของแอปต้องแนบ key จึงจะเข้าถึงได้ ซึ่งเข้มเกินไปสำหรับ endpoint สาธารณะอย่างหน้า list กาแฟ — ปัญหานี้ตั้งใจทิ้งไว้ให้บทถัดไปแก้ด้วย metadata (@Public() decorator)

guard ที่สร้างด้วย new ใน main.ts อยู่นอก DI container จึง inject อะไรไม่ได้เลย โค้ดเวอร์ชันนี้จึงต้องอ่านผ่าน process.env ตรง ๆ แทน ConfigService — บทถัดไปจะย้ายไปลงทะเบียนผ่าน APP_GUARD เพื่อปลดข้อจำกัดนี้

ล็อก iluvcoffee ทั้งแอปด้วย API key

สร้าง ApiKeyGuard ตามโค้ดด้านบน เพิ่ม API_KEY ลงใน .env ผูก guard แบบ global แล้วยิงทดสอบทั้งแบบมีและไม่มี key

nest g guard common/guards/api-key # .env API_KEY=iluvcoffeeSecretKey # main.ts app.useGlobalGuards(new ApiKeyGuard()); # ไม่มี key — ควรถูกปฏิเสธ curl -i http://localhost:3000/coffees # มี key — ควรผ่าน curl -i -H "Authorization: iluvcoffeeSecretKey" http://localhost:3000/coffees

ผลลัพธ์ที่คาดหวัง

request ที่ไม่แนบ Authorization header (หรือแนบค่าผิด) ได้ 403 Forbidden พร้อม error รูปแบบกลางจาก filter บทที่แล้ว ส่วน request ที่แนบ key ตรงกับใน .env ได้ข้อมูลกาแฟตามปกติ

ตรวจว่าใช้งานได้จริง

  • ยิง GET /coffees โดยไม่ใส่ header แล้วยืนยันว่าได้ 403 และ body มี timestamp จาก HttpExceptionFilter
  • ยิงซ้ำพร้อม Authorization ที่ตรงกับ API_KEY แล้วได้ 200
  • ลองเปลี่ยนค่าใน header ให้ผิดหนึ่งตัวอักษร เพื่อยืนยันว่าการเทียบเป็นแบบตรงตัว
  • ตรวจว่า restart dev server หลังแก้ .env แล้ว เพราะค่า environment โหลดตอน process เริ่ม
