ควบคุม Scope ของ Providers

เมื่อจบบทนี้ คุณจะสามารถ

  • อธิบายความต่างของ scope ทั้งสาม: DEFAULT, TRANSIENT และ REQUEST
  • กำหนด scope ให้ทั้ง class provider (@Injectable) และ custom provider
  • เลือก scope ที่เหมาะกับงานโดยเข้าใจต้นทุนด้าน performance ของแต่ละแบบ

Default: ทุก provider เป็น singleton

ปกติ Nest สร้าง provider หนึ่ง instance ต่อทั้งแอป แล้วแชร์ให้ทุกผู้บริโภค — instance ถูกสร้างตอน bootstrap และอยู่ยาวเท่าอายุแอป นี่คือ Scope.DEFAULT ซึ่งการเขียน @Injectable() เฉย ๆ ก็ได้ scope นี้อยู่แล้ว

// Scope DEFAULT — เท่ากับการเขียน @Injectable() เปล่า ๆ
@Injectable({ scope: Scope.DEFAULT })
export class CoffeesService {}

singleton เร็วที่สุดเพราะสร้างครั้งเดียวและ cache ได้เต็มที่ — ควรเป็นค่าเริ่มต้นเสมอ เว้นแต่มีเหตุผลจริง ๆ ที่ต้องการ instance ใหม่

TRANSIENT: instance ใหม่ต่อผู้บริโภคหนึ่งราย

provider แบบ transient ไม่ถูกแชร์ — ผู้บริโภคแต่ละรายที่ inject จะได้ instance เฉพาะของตัวเอง เหมาะกับของที่เก็บ state ต่อผู้ใช้งาน เช่น logger ที่จำ context ของ class แม่

/*
 * Scope TRANSIENT
 * provider ไม่ถูกแชร์ข้ามผู้บริโภค
 * แต่ละ class ที่ inject จะได้ instance ใหม่เฉพาะตัว
 */
@Injectable({ scope: Scope.TRANSIENT })
export class CoffeesService {}

// TRANSIENT กับ custom provider ก็กำหนดได้
{
  provide: 'COFFEE_BRANDS',
  useFactory: () => ['buddy brew', 'nescafe'],
  scope: Scope.TRANSIENT,
}

REQUEST: instance ใหม่ต่อหนึ่ง request

/*
 * Scope REQUEST
 * สร้าง instance ใหม่ให้แต่ละ incoming request โดยเฉพาะ
 */
@Injectable({ scope: Scope.REQUEST })
export class CoffeesService {}

request scope ทำให้ provider เข้าถึงข้อมูลเฉพาะ request ได้ (จะลงลึกบทถัดไป) โดย instance ถูกเก็บกวาดหลัง response เสร็จ — จ่ายราคาด้วยการ instantiate ทุก request และ scope นี้จะ "ไต่ขึ้น" ไปหาผู้บริโภค: controller ที่ inject request-scoped provider จะกลายเป็น request-scoped ไปด้วย

Scopeสร้าง instance เมื่อแชร์กับใครเหมาะกับ
DEFAULTตอน bootstrap ครั้งเดียวทั้งแอปเกือบทุกงาน — เร็วสุด, cache ได้
TRANSIENTต่อผู้บริโภคที่ injectไม่แชร์ของมี state ผูกกับ class แม่ เช่น contextual logger
REQUESTทุก incoming requestภายใน request เดียวกันlogic ที่ต้องอ่านข้อมูล request เช่น multi-tenancy

อย่าเปลี่ยน service เป็น REQUEST scope เพียงเพราะ "เผื่อไว้" — ทุก request ต้องจ่ายค่า instantiate ทั้ง chain ของผู้บริโภคที่ถูกไต่ scope ตามไปด้วย ให้ singleton เป็นค่าเริ่มต้น แล้วยกระดับเฉพาะตัวที่มีเหตุผลชัดเจน

พิสูจน์พฤติกรรมของแต่ละ scope ด้วย log

ใส่ console.log('CoffeesService created') ใน constructor ของ CoffeesService แล้วรันแอปสามรอบ โดยสลับ scope เป็น DEFAULT, TRANSIENT และ REQUEST ตามลำดับ ยิง GET /coffees สองสามครั้งในแต่ละรอบ แล้วนับจำนวน log

// รอบละหนึ่ง scope ใน coffees.service.ts @Injectable({ scope: Scope.DEFAULT }) // รอบที่ 1 @Injectable({ scope: Scope.TRANSIENT }) // รอบที่ 2 @Injectable({ scope: Scope.REQUEST }) // รอบที่ 3 npm run start:dev curl http://localhost:3000/coffees curl http://localhost:3000/coffees

ผลลัพธ์ที่คาดหวัง

DEFAULT: log ปรากฏครั้งเดียวตอน start ไม่เพิ่มตาม request; TRANSIENT: log ปรากฏตอน start เท่าจำนวนผู้บริโภคที่ inject service นี้ (เช่น controller และ CoffeeRatingService = 2 ครั้ง); REQUEST: ตอน start ไม่มี log แต่ปรากฏหนึ่งครั้งต่อทุก request ที่ยิงเข้ามา

ตรวจว่าใช้งานได้จริง

  • จำนวน log ตรงตามตารางในแต่ละรอบ และอธิบายเหตุผลของตัวเลขได้
  • รอบ REQUEST: สังเกตว่า instance ถูกสร้างแบบ lazy — ไม่มีตอน bootstrap เลย
  • ตอบได้ว่า endpoint ที่ traffic สูงควรหลีกเลี่ยง scope ไหนเพราะอะไร
  • คืน scope กลับเป็น default (ลบ option ออก) ก่อนไปบทถัดไป
