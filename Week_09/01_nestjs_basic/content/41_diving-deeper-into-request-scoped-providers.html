เจาะลึก Request-scoped Providers

เมื่อจบบทนี้ คุณจะสามารถ

  • Inject Request object ต้นฉบับเข้าไปใน request-scoped provider ได้
  • อธิบายพฤติกรรม scope bubbling ที่ทำให้ consumer ของ provider กลายเป็น request-scoped ตามไปด้วย
  • ชั่งน้ำหนักต้นทุนด้านประสิทธิภาพก่อนเลือกใช้ Scope.REQUEST ในงานจริง

เข้าถึง Request object ต้นฉบับจากภายใน provider

ประโยชน์หลักอย่างหนึ่งของ request-scoped provider คือแต่ละ instance ผูกกับ request เดียว เราจึงสามารถ inject Request object ต้นฉบับเข้ามาดูข้อมูลอย่าง headers, cookies, IP หรือ user ที่ authenticate แล้วได้โดยตรง ผ่าน token พิเศษ REQUEST ที่ export จาก @nestjs/core

import { Injectable, Inject, Scope } from '@nestjs/common';
import { REQUEST } from '@nestjs/core';
import type { Request } from 'express'; // 👈 ต้องเป็น import type เพราะ Request เป็น interface ที่ใช้ใน constructor ที่มี decorator

@Injectable({ scope: Scope.REQUEST })
export class CoffeesService {
  constructor(@Inject(REQUEST) private request: Request) {}
}

ทำไมต้อง import type? tsconfig ของ Nest 12 เปิด isolatedModules คู่กับ emitDecoratorMetadata — type ใด ๆ ที่ปรากฏใน signature ของ constructor/method ที่มี decorator ต้อง import แบบ type-only ไม่อย่างนั้น compiler จะฟ้อง TS1272: A type referenced in a decorated signature must be imported with 'import type' กฎนี้ใช้กับ interface/type ล้วน ๆ (เช่น Request ของ express, ConfigType ของ @nestjs/config) ส่วน class อย่าง ConfigService import ปกติได้

ลองใส่ console.log(this.request.url) ใน constructor แล้วยิง request ไปที่ /coffees หลาย ๆ ครั้ง จะเห็นว่า constructor ถูกเรียกใหม่ทุกครั้ง เพราะ Nest สร้าง CoffeesService ตัวใหม่ให้ทุก request แทนที่จะ reuse singleton เดิม

Scope bubbling: scope ลามขึ้นไปตาม chain ของผู้ใช้งาน

Scope จะ bubble up ตาม injection chain เสมอ: ถ้า CoffeesController inject CoffeesService ที่เป็น request-scoped ตัว controller เองก็จะกลายเป็น request-scoped ไปด้วยโดยอัตโนมัติ เพราะ Nest ต้องสร้าง controller ใหม่เพื่อส่ง service instance ประจำ request นั้นเข้าไป กฎนี้ไล่ขึ้นไปเรื่อย ๆ จนสุดสาย dependency

ข้อยกเว้นสำคัญคือ REQUEST token ใช้ไม่ได้ใน standalone application (เช่น microservice ที่ไม่มี HTTP) และใน GraphQL ให้ใช้ CONTEXT จาก @nestjs/graphql แทน

ต้นทุนที่ต้องจ่ายเมื่อเลือก Scope.REQUEST

ประเด็นScope.DEFAULT (singleton)Scope.REQUEST
การสร้าง instanceครั้งเดียวตอน bootstrapทุก request — มี overhead ของ GC และเวลาสร้าง
การเข้าถึงข้อมูล requestต้องส่งผ่าน parameter จาก controllerinject REQUEST ได้โดยตรง
ผลข้างเคียงต่อ consumerไม่มีทุกตัวที่ inject จะกลายเป็น request-scoped ตาม (bubbling)
เหมาะกับงานทั่วไป, stateless logicmulti-tenancy, per-request caching, request tracking

สำหรับ API ส่วนใหญ่ latency ที่เพิ่มขึ้นต่อ request นั้นน้อยจนรับได้ แต่ในระบบ throughput สูงควรวัดจริงก่อนตัดสินใจ และพิจารณาทางเลือกอื่นเช่นส่งข้อมูล request ผ่าน argument ของ method ตามปกติ ซึ่งคงความเป็น singleton ไว้ได้

ทดลอง inject REQUEST แล้วสังเกต scope bubbling

ใน iluvcoffee เปลี่ยน CoffeesService เป็น request-scoped พร้อม inject REQUEST แล้วเพิ่ม console.log ใน constructor ของทั้ง service และ controller เพื่อดูว่าถูกสร้างใหม่ทุก request จริง จากนั้นถอดกลับเป็น singleton เมื่อทดลองเสร็จ

// coffees.service.ts @Injectable({ scope: Scope.REQUEST }) export class CoffeesService { constructor(@Inject(REQUEST) private request: Request) { console.log('CoffeesService created for', request.url); } } // ยิงทดสอบหลายครั้ง curl http://localhost:3000/coffees curl http://localhost:3000/coffees

ผลลัพธ์ที่คาดหวัง

ทุกครั้งที่ยิง request จะเห็น log CoffeesService created for /coffees ใหม่ในเทอร์มินัล และถ้าใส่ log ใน CoffeesController ด้วย จะเห็นว่า controller ถูกสร้างใหม่ตามไปด้วยทั้งที่ไม่ได้ประกาศ scope เอง — นี่คือ scope bubbling ที่ทำงานจริง

ตรวจว่าใช้งานได้จริง

  • ยิง GET /coffees สองครั้ง แล้วเห็น log การสร้าง instance สองบรรทัด ไม่ใช่บรรทัดเดียว
  • this.request.url และ this.request.headers อ่านค่าได้ถูกต้องภายใน service
  • ลบ scope: Scope.REQUEST ออกแล้ว log เหลือครั้งเดียวตอน start — ยืนยันว่ากลับเป็น singleton
  • แอปยัง start ได้ปกติ ไม่มี dependency resolution error
