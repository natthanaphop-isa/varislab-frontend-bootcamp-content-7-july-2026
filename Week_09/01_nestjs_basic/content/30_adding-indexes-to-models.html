เพิ่ม Indexes ให้ Models

บทนี้เราจะทำอะไรบ้าง

  • อธิบายได้ว่า index ช่วยให้ query เร็วขึ้นอย่างไร และต้องแลกกับอะไร
  • ประกาศ @@index([...]) บนคอลัมน์เดียวที่ถูกใช้ค้นหาบ่อย
  • สร้าง composite index หลายคอลัมน์เมื่อ query ค้นด้วยหลายเงื่อนไขพร้อมกัน และแยกความต่างจาก @unique

Index คือสารบัญของตาราง

เวลา query ค้นหาจากคอลัมน์ที่ไม่มี index ฐานข้อมูลต้องไล่สแกนทุกแถว (full table scan) ซึ่งช้าลงเรื่อย ๆ ตามขนาดตาราง Index คือโครงสร้างข้อมูลเสริมที่ทำหน้าที่เหมือนสารบัญหนังสือ: แทนที่จะพลิกทุกหน้า ฐานข้อมูลกระโดดไปยังแถวที่ต้องการได้ทันที primary key อย่าง id (@id) ได้ index อัตโนมัติอยู่แล้ว และ @unique ที่เราติดให้ Flavor.name ในบทที่ 25 ก็สร้าง unique index ให้เช่นกัน แต่คอลัมน์อื่นที่เราค้นบ่อย — เช่น name ของ Event ที่ระบบ analytics ต้อง filter ตลอดเวลา — ต้องประกาศเอง

ใน Prisma index ประกาศที่ท้าย block ของ model ด้วย attribute ระดับ model (ขึ้นต้นด้วย @@) โดยส่ง array ของชื่อฟิลด์

model Event {
  id      Int    @id @default(autoincrement())
  type    String
  name    String
  payload Json

  @@index([name]) // สร้าง index ให้คอลัมน์ name
  @@map("event")
}

Composite index เมื่อค้นหลายคอลัมน์พร้อมกัน

ถ้า query ของเรามักค้นด้วยสองเงื่อนไขคู่กัน เช่น WHERE name = ... AND type = ... การมี index แยกสองอันยังไม่ optimal เท่า composite index ที่ครอบทั้งสองคอลัมน์ในโครงสร้างเดียว ซึ่งประกาศด้วย syntax เดิม เพียงใส่หลายฟิลด์ใน array

model Event {
  id      Int    @id @default(autoincrement())
  type    String
  name    String
  payload Json

  @@index([name])
  @@index([name, type]) // composite index ครอบสองคอลัมน์
  @@map("event")
}
Attributeสิ่งที่สร้างเหมาะกับ
@@index([a])index ธรรมดาบนคอลัมน์เดียวquery ที่ filter จากคอลัมน์นั้นเดี่ยว ๆ บ่อย
@@index([a, b])composite index ครอบหลายคอลัมน์ (ลำดับมีผล)query ที่ filter สองคอลัมน์นั้นร่วมกันเป็นประจำ
@unique บนฟิลด์unique index + constraint ห้ามค่าซ้ำคอลัมน์ที่ต้องไม่ซ้ำ เช่น Flavor.name, อีเมล
@@unique([a, b])unique index บนคู่ของคอลัมน์ห้ามซ้ำเฉพาะเมื่อทั้งคู่เหมือนกัน เช่น (userId, name)

Index ไม่ใช่ของฟรี: ทุก insert/update ต้องอัปเดต index ด้วย และแต่ละ index กินพื้นที่จัดเก็บเพิ่ม จึงควรเพิ่มเฉพาะคอลัมน์ที่มี query pattern รองรับจริง ไม่ใช่ติดทุกคอลัมน์กันเหนียว

Prisma ตั้งชื่อ index ให้เองตามรูปแบบ <ตาราง>_<คอลัมน์>_idx (เช่น event_name_type_idx) ถ้าต้องการชื่อเองให้ระบุ @@index([name], name: "event_name_idx") — บนเครื่อง dev db push จะสร้าง index ให้ทันที ส่วนใน production การเพิ่ม index คือการเปลี่ยน schema ที่ต้องทำผ่าน migration — บทถัดไปพอดี

ทำให้การค้น event เร็วขึ้น

เพิ่ม @@index([name]) และ composite index @@index([name, type]) ให้ Event model ใน schema.prisma แล้ว push ขึ้นฐานข้อมูล จากนั้นไปดู index ที่เกิดขึ้นจริง

npx prisma db push # ดู index ใน pgAdmin Query Tool SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'event';

ควรได้ผลลัพธ์แบบนี้

ผลของ query แสดง index ของตาราง event อย่างน้อย 3 รายการ: event_pkey ของ id, event_name_idx ของ name และ composite index event_name_type_idx ที่ครอบ name กับ type — ทั้งหมดถูกสร้างจาก attribute ใน schema.prisma โดยตรง

ลองเช็กให้แน่ใจ

  • pg_indexes ของตาราง event มี index ใหม่ปรากฏหลัง db push
  • indexdef ของ composite index ระบุทั้งสองคอลัมน์ (name, type)
  • ลองรัน EXPLAIN SELECT * FROM event WHERE name = 'recommend_coffee'; — plan ควรอ้างถึง index scan เมื่อตารางมีข้อมูลมากพอ
  • แอปยัง start และ CRUD ได้ตามปกติ ไม่มี error จากการประกาศ index
