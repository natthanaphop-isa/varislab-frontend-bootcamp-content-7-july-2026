สร้าง Guard และเปิด Public Routes ด้วย Metadata

บทนี้เราจะทำอะไรบ้าง

  • สร้าง guard ด้วย CanActivate เพื่อตัดสินใจว่า request ไปต่อได้หรือไม่
  • ผูก guard แบบ global เพื่อป้องกัน routes ของแอป
  • สร้าง @Public() decorator ด้วย metadata
  • ใช้ Reflector ให้ guard ข้าม endpoint ที่ประกาศเป็น public

Guard ตอบคำถามเดียว: request นี้ควรไปต่อหรือไม่

Guard เป็น building block ที่มีหน้าที่เดียวชัดเจน — คืนค่า boolean ว่า request ปัจจุบันได้รับอนุญาตให้ถึง route handler หรือไม่ ถ้าคืน false NestJS จะตัด request ทันทีและตอบ 403 Forbidden ให้เอง จึงเป็นที่ที่เหมาะกับงาน authentication และ authorization เช่น ตรวจ API key, ตรวจ token หรือตรวจ role ของผู้ใช้ ต่างจาก middleware ตรงที่ guard เข้าถึง ExecutionContext ได้ จึงรู้ว่า handler ไหนกำลังจะถูกเรียก — ความสามารถนี้จะสำคัญในช่วง metadata ถัดไปของบทนี้

generate โครงไฟล์ไว้ใน common/guards เพราะเป็น logic ที่ใช้ร่วมทั้งแอป

nest g guard common/guards/api-key

implement CanActivate

guard ทุกตัวเป็นคลาสที่ติด @Injectable() และ implement interface CanActivate ซึ่งมีเมธอดเดียวคือ canActivate(context) — คืนได้ทั้ง boolean ตรง ๆ, Promise หรือ Observable สำหรับการตรวจแบบ async ในเวอร์ชันแรกนี้เราเทียบ Authorization header กับค่า API_KEY จาก environment แบบตรงไปตรงมา

import { CanActivate, ExecutionContext, Injectable } from '@nestjs/common';
import { Request } from 'express';
import { Observable } from 'rxjs';

@Injectable()
export class ApiKeyGuard implements CanActivate {
  canActivate(
    context: ExecutionContext,
  ): boolean | Promise<boolean> | Observable<boolean> {
    const request = context.switchToHttp().getRequest<Request>();
    const authHeader = request.header('Authorization');
    const token = authHeader && authHeader.split(' ')[1];
    return token === process.env.API_KEY;
  }
}

context.switchToHttp().getRequest() คือ pattern เดียวกับที่เห็นใน exception filter: แปลง context กลางของ NestJS ให้เป็น HTTP request ของ Express เพื่ออ่าน header จากนั้นตั้งค่า API_KEY ในไฟล์ .env ให้เรียบร้อยก่อนทดสอบ เราอ่าน header ในรูปแบบ Authorization: Bearer <key> — split(' ')[1] ตัดเอาส่วนหลัง scheme Bearer ออกมา ซึ่งเป็นรูปแบบเดียวกับที่ Postman ใส่ให้อัตโนมัติเมื่อเลือก auth type เป็น Bearer Token จึงทดสอบผ่าน Postman ได้ตรงไปตรงมา

ผูกแบบ global ใน main.ts

app.useGlobalGuards(new ApiKeyGuard());

ตอนนี้ ทุก endpoint ของแอปต้องแนบ key จึงจะเข้าถึงได้ ซึ่งเข้มเกินไปสำหรับ endpoint สาธารณะอย่างหน้า list กาแฟ ช่วงถัดไปเราจะแก้ด้วย metadata และ @Public() decorator

guard ที่สร้างด้วย new ใน main.ts อยู่นอก DI container จึง inject อะไรไม่ได้เลย โค้ดเวอร์ชันนี้จึงต้องอ่านผ่าน process.env ตรง ๆ แทน ConfigService ช่วงถัดไปเราจะย้ายไปลงทะเบียนผ่าน APP_GUARD เพื่อปลดข้อจำกัดนี้

ปัญหาจากการ bind แบบ global: guard เหมารวมทุก route

ApiKeyGuard เวอร์ชันแรกบังคับ key กับทุก endpoint รวมถึงหน้า list กาแฟที่ควรเปิดสาธารณะ วิธีแก้ที่สวยคือให้แต่ละ route ประกาศตัวเอง ว่าเป็น public ผ่าน decorator แล้วให้ guard อ่านคำประกาศนั้นตอนตัดสินใจ — กลไกที่ NestJS เตรียมไว้ให้คือ custom metadata: ข้อมูลเสริมที่แนบกับ class หรือ method ด้วย SetMetadata แล้วอ่านกลับด้วย Reflector

สร้าง @Public() decorator

เราไม่เรียก SetMetadata ตรง ๆ ใน controller เพราะ key ที่เป็น string หลุดกระจายทั่วโค้ดได้ง่าย แนวทางที่ดีคือห่อไว้ใน decorator ของตัวเองไฟล์เดียวจบ

import { SetMetadata } from '@nestjs/common';

export const IS_PUBLIC_KEY = 'isPublic';

export const Public = () => SetMetadata(IS_PUBLIC_KEY, true);

จากนั้นติด @Public() ไว้เหนือ handler ที่ต้องการเปิด เช่น findAll() ของ CoffeesController — ตัว decorator แค่ฝัง key isPublic: true ไว้กับ handler นั้น ยังไม่มีผลอะไรจนกว่าจะมีคนอ่าน

อ่าน metadata ใน guard ด้วย Reflector

อัปเกรด ApiKeyGuard ให้ inject สองอย่าง: Reflector สำหรับอ่าน metadata และ ConfigService แทนการแตะ process.env ตรง ๆ

import { CanActivate, ExecutionContext, Injectable } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import { Reflector } from '@nestjs/core';
import { Request } from 'express';
import { Observable } from 'rxjs';
import { IS_PUBLIC_KEY } from '../decorators/public.decorator.js';

@Injectable()
export class ApiKeyGuard implements CanActivate {
  constructor(
    private readonly reflector: Reflector,
    private readonly configService: ConfigService,
  ) {}

  canActivate(
    context: ExecutionContext,
  ): boolean | Promise<boolean> | Observable<boolean> {
    const isPublic = this.reflector.get(IS_PUBLIC_KEY, context.getHandler());
    if (isPublic) {
      return true;
    }
    const request = context.switchToHttp().getRequest<Request>();
    const authHeader = request.header('Authorization');
    const token = authHeader && authHeader.split(' ')[1];
    return token === this.configService.get('API_KEY');
  }
}

หัวใจคือ context.getHandler() — guard รู้ว่า method ไหนกำลังจะถูกเรียก จึงส่งให้ reflector.get() ดึง metadata ของ method นั้นออกมาได้ ถ้าเจอ isPublic ก็ปล่อยผ่านทันที ไม่เจอจึงค่อยตรวจ key ตามปกติ pattern เดียวกันนี้ใช้สร้าง interceptor ที่อ่าน metadata ได้เช่นกัน เช่น decorator กำหนด cache key หรือ role ที่ต้องมี

เพราะตอนนี้ guard ต้อง inject dependency ได้ การ new ApiKeyGuard() ใน main.ts จึงใช้ไม่ได้แล้ว — ให้ลงทะเบียนผ่าน DI ด้วย APP_GUARD token ใน module (เช่น CommonModule) แทน: { provide: APP_GUARD, useClass: ApiKeyGuard } ส่วน ConfigModule ไม่ต้อง import ซ้ำเพราะประกาศเป็น isGlobal: true ไว้ตั้งแต่บทที่ 34 แล้ว

// common.module.ts
import { Module } from '@nestjs/common';
import { APP_GUARD } from '@nestjs/core';
import { ApiKeyGuard } from './guards/api-key.guard.js';

@Module({
  providers: [
    {
      provide: APP_GUARD,
      useClass: ApiKeyGuard,
    },
  ],
})
export class CommonModule {}

อย่าสับสนกับ app.useGlobalPipes(new ValidationPipe()) ที่เคยเขียนใน main.ts ตั้งแต่บทที่ 16 — นั่นคือการลงทะเบียนแบบ imperative นอก DI container ส่วน APP_GUARD เป็น DI token พิเศษที่ NestJS จองไว้ให้ ต้องประกาศใน providers array ของ module (ไม่ใช่ imports) จึงจะถูกสร้างผ่าน DI และ inject Reflector/ConfigService เข้าไปได้ตามปกติ — ถ้าลองเขียน app.useGlobalGuards(new ApiKeyGuard()) ต่อจาก main.ts แบบเดิม จะพังทันทีเพราะ guard สร้างนอก DI container จึง inject อะไรไม่ได้เลย เหมือนที่ note ด้านบนบอกไว้

ล็อก routes ด้วย API key แล้วเปิดเฉพาะ public endpoints

ขั้นที่ 1: ล็อก iluvcoffee ทั้งแอปด้วย API key

สร้าง ApiKeyGuard ตามโค้ดด้านบน เพิ่ม API_KEY ลงใน .env ผูก guard แบบ global แล้วยิงทดสอบทั้งแบบมีและไม่มี key

nest g guard common/guards/api-key # .env API_KEY=iluvcoffeeSecretKey # main.ts app.useGlobalGuards(new ApiKeyGuard()); # ไม่มี key — ควรถูกปฏิเสธ curl -i http://localhost:3000/coffees # มี key — ควรผ่าน curl -i -H "Authorization: Bearer iluvcoffeeSecretKey" http://localhost:3000/coffees

ขั้นที่ 2: เปิด GET /coffees ให้สาธารณะ แต่ล็อก route อื่นไว้

สร้าง public.decorator.ts ใน common/decorators อัปเกรด ApiKeyGuard ตามโค้ดด้านบน ย้ายการลงทะเบียนจาก main.ts ไปเป็น APP_GUARD แล้วติด @Public() ที่ findAll()

# coffees.controller.ts @Public() @Get() findAll(@Query() paginationQuery: PaginationQueryDto) { ... } # common.module.ts providers: [{ provide: APP_GUARD, useClass: ApiKeyGuard }] # ทดสอบ curl -i http://localhost:3000/coffees # ควรผ่านโดยไม่มี key curl -i -X POST http://localhost:3000/coffees # ควรได้ 403

ควรได้ผลลัพธ์แบบนี้

GET /coffees เข้าถึงได้โดยไม่ต้องแนบ key เพราะมี @Public() ส่วน POST, PATCH และ DELETE ยังตอบ 403 Forbidden เมื่อไม่มี key ที่ถูกต้อง และ guard อ่านค่า key ผ่าน ConfigService โดยไม่เรียก process.env ตรง ๆ

ลองเช็กให้แน่ใจ

  • ยิง GET /coffees โดยไม่มี header — ต้องได้ 200 เพราะติด @Public() แล้ว
  • ยิง POST /coffees โดยไม่มี header — ต้องได้ 403 เพราะ handler นี้ไม่มี metadata
  • ยิง POST /coffees พร้อม key ที่ถูกต้อง — ต้องทำงานปกติ
  • ลองย้าย @Public() ไป handler อื่นแล้วดูว่าพฤติกรรมตามไปทันที โดยไม่ต้องแก้ guard เลย — นี่คือความ generic ที่ metadata มอบให้
  • ตรวจว่าไม่มีการเรียก process.env เหลืออยู่ใน guard
