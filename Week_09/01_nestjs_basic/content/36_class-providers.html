Class Providers (useClass)

เมื่อจบบทนี้ คุณจะสามารถ

  • ใช้ useClass ผูก token หนึ่งเข้ากับ class implementation ที่เลือกได้ตามเงื่อนไข
  • สลับ implementation ตาม NODE_ENV โดยฝั่งผู้ inject ไม่ต้องแก้โค้ด
  • อธิบายได้ว่ารูปแบบนี้คือ Strategy Pattern ในเวอร์ชันของ DI container

useClass: token เดียว หลาย implementation

useClass ให้เราบอก Nest ว่า "เมื่อมีคนขอ token นี้ ให้ instantiate class นี้" จุดที่ทำให้มันทรงพลังคือค่า class ที่ส่งเข้าไปเป็น expression ธรรมดา — คำนวณตอน module ถูกโหลดได้ จึงเลือก implementation ตามเงื่อนไขอย่าง environment variable ได้ทันที ตัวอย่างคลาสสิกจากคอร์ส: config service คนละตัวระหว่างตอนพัฒนากับตอน deploy จริง

// ตัวอย่าง syntax "useClass"
{
  provide: AppConfigService,
  useClass:
    process.env.NODE_ENV === 'development'
      ? DevelopmentAppConfigService
      : ProductionAppConfigService,
},

token ยังคงเป็น AppConfigService ผู้ใช้ทุกคน inject ด้วย type นี้ตามปกติ ส่วนของจริงที่ได้รับจะเป็น DevelopmentAppConfigService หรือ ProductionAppConfigService ขึ้นกับสภาพแวดล้อมตอนแอป start — โค้ดฝั่งผู้ใช้ไม่ต้องมี if แม้แต่ตัวเดียว

ให้ DevelopmentAppConfigService และ ProductionAppConfigService extend หรือ implement interface ร่วมกับ AppConfigService เพื่อให้ method signature ตรงกัน มิฉะนั้น type จะบอกว่ามีเมธอดที่ runtime ไม่มีจริง ตั้งชื่อว่า AppConfigService (ไม่ใช่ ConfigService เฉย ๆ) โดยตั้งใจ — บทที่ 45 จะ import ConfigService ตัวจริงจาก @nestjs/config เข้ามาในโปรเจกต์เดียวกัน ถ้าตั้งชื่อชนกันจะเจอ TS2300: Duplicate identifier ทันทีที่ทั้งสองถูก import เข้าไฟล์เดียวกัน

นี่คือ Strategy Pattern ที่ container จัดการให้

ในบทที่ 33 เราลิสต์ use case "Strategy Pattern" ไว้ — useClass คือคำตอบของมัน: ประกาศ abstract class (หรือ base class) เป็นสัญญากลาง แล้วเลือก strategy จริงที่จุดประกอบ module เพียงจุดเดียว เงื่อนไขการเลือกจะซับซ้อนแค่ไหนก็กระจุกอยู่ที่ provider declaration ไม่รั่วไปทั่ว codebase

วิธีจุดตัดสินใจข้อสังเกต
if/else ในโค้ดผู้ใช้กระจายทุกจุดที่เรียกใช้ซ้ำซ้อน แก้ยาก ทดสอบยาก
useClassจุดเดียวตอนประกาศ providerผู้ใช้เห็นแค่ token เดียว สลับได้ทั้งระบบ
useFactory (บทถัดไป)ฟังก์ชันที่ inject dependency อื่นได้ใช้เมื่อการเลือก/สร้างต้องพึ่งค่า runtime มากขึ้น

สลับ AppConfigService ตาม NODE_ENV

สร้าง class AppConfigService, DevelopmentAppConfigService และ ProductionAppConfigService (ให้สองตัวหลังมี property หรือเมธอดที่ return ค่าบอกตัวตน เช่น getEnvName()) ประกาศ provider ด้วย useClass ตามตัวอย่าง แล้ว inject AppConfigService เข้า CoffeesService และ log ค่าออกมาดู

// รันแบบ development NODE_ENV=development npm run start:dev // รันแบบ production (เทอร์มินัลอีกครั้ง) NODE_ENV=production npm run start:dev

ผลลัพธ์ที่คาดหวัง

เมื่อรันด้วย NODE_ENV=development log บอกว่าได้ instance ของ DevelopmentAppConfigService; เมื่อสลับเป็น production ได้ ProductionAppConfigService โดยที่ CoffeesService ยัง inject ผ่าน type AppConfigService ตัวเดิมไม่มีการแก้ไข

ตรวจว่าใช้งานได้จริง

  • รันสองครั้งด้วย NODE_ENV ต่างกัน แล้วเห็น log ระบุ class คนละตัว
  • ค้นทั้งโปรเจกต์ว่าไม่มี process.env.NODE_ENV โผล่ในไฟล์ service/controller — เงื่อนไขอยู่ที่ module เท่านั้น
  • ลองเพิ่มเมธอดใหม่ใน interface กลางแล้วดูว่า TypeScript บังคับให้ทั้งสอง implementation มีครบ
  • อธิบายได้ว่าถ้าเพิ่ม StagingAppConfigService ต้องแก้กี่จุด (ควรตอบ: จุดเดียว)
