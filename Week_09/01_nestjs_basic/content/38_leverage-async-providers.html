ใช้ Async Providers

เมื่อจบบทนี้ คุณจะสามารถ

  • เขียน factory แบบ async ที่ return Promise และให้ Nest รอจน resolve
  • ผสม inject กับ async factory เพื่อดึงข้อมูลจริง (เช่น query ฐานข้อมูล) มาเป็นค่า provider
  • อธิบายผลของ async provider ต่อจังหวะ bootstrap ของแอป

เมื่อค่า provider ต้องรอของจริงจากภายนอก

factory ในบทที่แล้วเป็น synchronous ทั้งหมด แต่ค่าจำนวนมากในชีวิตจริงต้อง await: ผล query จากฐานข้อมูล, การเรียก API ภายนอก, การเปิด connection ฯลฯ NestJS รองรับตรง ๆ — เพียงทำให้ factory เป็น async function แล้ว Nest จะรอ Promise resolve ก่อนถือว่า provider ตัวนี้พร้อม และก่อนที่แอปจะเริ่มรับ request

// Asynchronous "useFactory" (ตัวอย่าง async provider)
{
  provide: 'COFFEE_BRANDS',
  // สังเกต "async" และการ await ภายใน factory
  // ของจริงอาจเป็น database connection / API call ฯลฯ
  // ที่นี่เรา mock เหตุการณ์นั้นด้วย Promise
  useFactory: async (prisma: PrismaService): Promise<string[]> => {
    // ของจริง: const rows = await prisma.coffee.findMany({
    //   select: { brand: true }, distinct: ['brand'],
    // });
    const coffeeBrands = await Promise.resolve(['buddy brew', 'nescafe']);
    return coffeeBrands;
  },
  inject: [PrismaService],
},

ตัวอย่างนี้รวมทุกอย่างที่เรียนมา: token เป็น string (บทที่ 35), ค่ามาจาก factory (บทที่ 37), factory ขอ inject PrismaService แล้วในสถานการณ์จริงจะใช้มัน query แบรนด์ที่ไม่ซ้ำกันจากตาราง coffee — โค้ดสาธิต mock ขั้นตอนนั้นด้วย Promise.resolve

ทุก class ที่ inject 'COFFEE_BRANDS' ไม่ต้องรู้เลยว่าค่านี้มาแบบ async — ตอนที่ CoffeesService ถูกสร้าง ค่าถูก resolve เสร็จแล้วเรียบร้อย ความซับซ้อนเรื่องเวลาถูกเก็บไว้ใน container ทั้งหมด

PrismaService inject ได้จากทุก module โดยไม่ต้อง import อะไรเพิ่ม เพราะ PrismaModule ที่เราสร้างในบทที่ 22 ติด @Global() ไว้ — และเพราะ PrismaService เชื่อมต่อฐานข้อมูลใน onModuleInit factory นี้จึงเรียก query ได้ทันทีที่ถูกเรียก

ผลต่อจังหวะ bootstrap

Nest สร้าง dependency graph แล้ว resolve ตามลำดับ ใครที่พึ่ง async provider จะถูกสร้างหลัง Promise resolve เสมอ ข้อดีคือแอปไม่มีสภาวะ "start แล้วแต่ข้อมูลยังไม่พร้อม" ข้อแลกคือถ้า Promise ช้า แอปทั้งแอปจะ start ช้าตาม และถ้า reject แอปจะไม่ start เลย — จึงควรมี timeout หรือ error handling ในการเชื่อมต่อของจริง

ทำ COFFEE_BRANDS ให้เป็น async

อัปเกรด provider COFFEE_BRANDS จากบทที่แล้วให้เป็น async factory ตามตัวอย่าง แล้วพิสูจน์จังหวะเวลาด้วยการหน่วง Promise สักสองวินาทีและ log ก่อน/หลัง await เทียบกับ log ใน constructor ของ CoffeesService

{ provide: COFFEE_BRANDS, useFactory: async (): Promise<string[]> => { console.log('factory: start'); const brands = await new Promise<string[]>((resolve) => setTimeout(() => resolve(['buddy brew', 'nescafe']), 2000), ); console.log('factory: resolved'); return brands; }, } npm run start:dev

ผลลัพธ์ที่คาดหวัง

ลำดับ log ตอน start คือ factory: start → (หน่วง ~2 วินาที) → factory: resolved → log จาก constructor ของ CoffeesService ที่พิมพ์ array แบรนด์ จากนั้นแอปจึงขึ้นข้อความพร้อมรับ request — ยืนยันว่า Nest รอ async provider ก่อนสร้างผู้บริโภคและก่อนเปิดพอร์ต

ตรวจว่าใช้งานได้จริง

  • เห็นแอป start ช้าลงประมาณเท่า delay ที่ใส่ และลำดับ log ตรงตามคาด
  • ยิง GET /coffees ระหว่างสองวินาทีแรก — ต้อง connect ไม่ได้ เพราะแอปยังไม่เปิดรับ
  • ลองให้ Promise reject — แอปต้องไม่ start และแสดง error ชัดเจน
  • ถอด delay ทดลองออกเมื่อเสร็จ เพื่อไม่ให้บทถัดไปช้าโดยไม่จำเป็น
