เจาะลึก e2e Tests

บทนี้เราจะทำอะไรบ้าง

  • อธิบายได้ว่า e2e test ต่างจาก unit test ตรงที่ boot แอปทั้งใบแล้วทดสอบผ่าน HTTP จริง
  • ใช้ createNestApplication() + supertest ยิง request เข้า in-memory HTTP server
  • จัดการ lifecycle ของแอปใน test ด้วย beforeAll/afterAll อย่างถูกต้อง

ทดสอบในระดับที่ผู้ใช้เจอจริง

Unit test บอกได้ว่า class หนึ่งทำงานถูก แต่ยังตอบไม่ได้ว่าเมื่อประกอบทุกส่วนเข้าด้วยกัน ระบบจะทำงานครบหรือไม่ เช่น route ถูกต้องไหม, pipe แปลงค่าจริงหรือเปล่า และ module import dependency ครบหรือยัง e2e test (End-to-End) จึงเปิดแอปขึ้นมาจริง แล้วส่ง HTTP request เข้าไปเหมือนที่ client ใช้งาน

โครงที่ Nest scaffold ให้ใน test/app.e2e-spec.ts มีครบทุกชิ้นที่ต้องรู้จัก

/* app.e2e-spec.ts - FINAL CODE */
import { Test, TestingModule } from '@nestjs/testing';
import { INestApplication } from '@nestjs/common';
import request from 'supertest';
import { AppModule } from './../src/app.module.js';

describe('AppController (e2e)', () => {
  let app: INestApplication;

  beforeAll(async () => {
    const moduleFixture: TestingModule = await Test.createTestingModule({
      imports: [AppModule],
    }).compile();

    app = moduleFixture.createNestApplication();
    await app.init();
  });

  it('/ (GET)', () => {
    return request(app.getHttpServer()) // 👈 ยิงเข้า server จริงของแอป
      .get('/')
      .set('Authorization', `Bearer ${process.env.API_KEY!}`) // 👈 แนบ header แบบ Bearer ให้ผ่าน ApiKeyGuard (! เพราะ strict mode มองว่าอาจ undefined)
      .expect(200)
      .expect('Hello World!');
  });

  afterAll(async () => {
    await app.close();
  });
});

สามชิ้นส่วนที่ต่างจาก unit test

  • createNestApplication() — แทนที่จะ module.get() ดึง class มาเรียกตรง ๆ เราสร้าง instance ของแอปเต็มรูปจาก AppModule แล้ว app.init() ให้ lifecycle hooks ทำงานเหมือน production
  • supertest — request(app.getHttpServer()) ยิง HTTP เข้า server ของแอปโดยไม่ต้อง listen บน port จริง แล้ว chain .expect() ตรวจทั้ง status และ body ได้
  • beforeAll/afterAll — boot แอปครั้งเดียวต่อ suite (ไม่ใช่ beforeEach แบบ unit test เพราะ boot แพง) และต้อง app.close() เสมอ ไม่งั้น Vitest จะค้างรอ (แล้วฟ้องว่า process ปิดไม่ลง) เพราะ connection ยังเปิดอยู่

ตั้งแต่บท guards เราคุม endpoint ด้วย ApiKeyGuard ซึ่งตอนนี้อ่าน header แบบ Authorization: Bearer <key> — e2e test จึงต้อง .set('Authorization', `Bearer ${process.env.API_KEY}`) แนบ header ไปด้วย นี่คือข้อดีของ e2e: มันบังคับให้เราทดสอบผ่านชั้น guard/pipe/filter จริงทั้งหมด ไม่ใช่ข้ามไป

ต่างจาก unit test ในบทที่ 46–47 ที่เรา mock PrismaService ทิ้ง e2e test boot AppModule ทั้งใบ จึงสร้าง PrismaService ตัวจริงและเรียก $connect() — database จึงต้องรันอยู่ก่อนเสมอ ส่วน Vitest รันไฟล์ทดสอบเป็น ES module เหมือนแอปจริง Prisma Client ที่ generate ไว้จึงโหลดได้โดยไม่ต้องตั้งค่าอะไรเพิ่ม และ script test:e2e ที่ Nest เตรียมให้ (vitest run --config ./vitest.config.e2e.ts) ใช้ได้ทันที

รันและอ่าน e2e test ที่มีอยู่

รัน e2e suite ของโปรเจกต์ ถ้า fail ให้อ่าน error แล้วแก้ให้ตรงสาเหตุ — ส่วนใหญ่มาจาก guard ที่เพิ่มระหว่างคอร์ส (ต้องแนบ API key) หรือ AppModule ที่ตอนนี้ต้องการ database

# ให้แน่ใจว่า database รันอยู่ เพราะ PrismaService เชื่อมต่อตอน onModuleInit docker-compose up -d npm run test:e2e

ควรได้ผลลัพธ์แบบนี้

test/app.e2e-spec.ts ผ่าน: แอป boot ขึ้นจริง, request GET / ที่แนบ Authorization header ได้ 200 พร้อม body Hello World! และ process จบสนิทหลัง app.close() โดย Vitest ไม่ค้าง

ลองเช็กให้แน่ใจ

  • npm run test:e2e จบด้วย exit code 0 และ process ปิดตัวทันที ไม่ค้างรอ handle ที่ยังเปิดอยู่
  • ลองลบบรรทัด .set('Authorization', …) ชั่วคราว → ต้องได้ 403 ยืนยันว่า guard ทำงานใน e2e จริง
  • ลองปิด database แล้วรันซ้ำ เพื่อเห็นว่า e2e ต่างจาก unit test อย่างไร (boot fail)
  • เปิด vitest.config.e2e.ts ยืนยันว่า include คือ ['**/*.e2e-spec.ts'] ต่างจาก vitest.config.ts ที่จับ *.spec.ts

  • Guards: เหตุที่ e2e ต้องแนบ credentials (NestJS)
