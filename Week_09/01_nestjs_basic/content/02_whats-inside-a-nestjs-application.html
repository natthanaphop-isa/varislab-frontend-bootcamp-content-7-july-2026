มีอะไรอยู่ในแอป NestJS

บทนี้เราจะทำอะไรบ้าง

  • อธิบายหน้าที่ของไฟล์หลักที่ nest new สร้างมาให้ได้ทีละไฟล์
  • ไล่เส้นทางของ request ตั้งแต่ main.ts จนถึง controller และ service
  • บอกได้ว่า separation of concerns ของ Nest ช่วยให้โฟกัสที่งานตรงหน้าได้อย่างไร

ทุกอย่างมีที่ทางของตัวเอง

จุดขายสำคัญของ NestJS คือ separation of concerns ที่แทบไม่ต้องออกแรงจัดเอง: ทุกอย่างในแอป Nest มีโครงสร้างและตำแหน่งที่ชัดเจน ทำให้เราใช้เวลากับ business logic ตรงหน้า แทนที่จะเสียเวลาถกเรื่องการจัดไฟล์หรือ convention กันเองในทีม โปรเจกต์ที่สร้างจาก nest new iluvcoffee จะมีโครงหน้าตาแบบนี้

iluvcoffee/
├── src/
│   ├── app.controller.spec.ts   # unit test ของ controller
│   ├── app.controller.ts        # controller ตัวอย่าง (จัดการ route)
│   ├── app.module.ts            # root module ของแอป
│   ├── app.service.ts           # service ตัวอย่าง (business logic)
│   └── main.ts                  # entry point — bootstrap แอป
├── test/
│   └── app.e2e-spec.ts          # e2e test ตัวอย่าง
├── .prettierrc                  # ค่าตั้งของ Prettier (จัด format โค้ด)
├── nest-cli.json                # ค่าตั้งของ Nest CLI
├── oxlint.json                  # ค่าตั้งของ oxlint (linter)
├── package.json
├── tsconfig.build.json          # tsconfig สำหรับ nest build (compile เฉพาะ src/)
├── tsconfig.json
├── vitest.config.ts             # ค่าตั้ง Vitest สำหรับ unit tests
└── vitest.config.e2e.ts         # ค่าตั้ง Vitest สำหรับ e2e tests

สังเกตว่า package.json มี "type": "module" — โปรเจกต์ NestJS 12 เป็น ES module ตั้งแต่ต้น เครื่องมือที่มากับ scaffold คือ oxlint (npm run lint), Prettier (npm run format) และ Vitest (npm test) ซึ่งเราจะได้ใช้ในบทเรื่องการทดสอบ

เส้นทางของ request: main.ts → module → controller → service

ทุกอย่างเริ่มที่ main.ts ซึ่งเรียก NestFactory.create() เพื่อสร้าง application instance จาก root module แล้วสั่งให้ฟังที่ port ที่กำหนด (อ่านจาก process.env.PORT ถ้าไม่ตั้งจะใช้ 3000)

import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module.js';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  await app.listen(process.env.PORT ?? 3000);
}
await bootstrap();

สองจุดที่ต่างจากโค้ด Node.js แบบเก่า: import ไฟล์ในโปรเจกต์ต้องลงท้ายด้วย .js เสมอ ('./app.module.js') เพราะใน ES module Node จะ resolve ไฟล์ที่ compile แล้ว TypeScript จึงบังคับให้ระบุนามสกุลแม้เราจะเขียนไฟล์ .ts อยู่ก็ตาม และ await bootstrap() เป็น top-level await ที่ ES module อนุญาตให้เขียนได้โดยไม่ต้องห่อใน function อีกชั้น — ทุก import ที่ nest g สร้างให้ตลอดคอร์สจะมี .js ติดมาให้เองอยู่แล้ว

จากนั้นแต่ละชิ้นส่วนแบ่งหน้าที่กันชัดเจน:

ไฟล์หน้าที่สิ่งที่ควรอยู่ / ไม่ควรอยู่
app.module.tsประกาศว่า module นี้มี controllers และ providers อะไรบ้างเป็นแค่ "สารบัญ" ของ dependency graph — ไม่ใส่ logic
app.controller.tsรับ HTTP request, แกะข้อมูล, ส่งต่อให้ service แล้วคืน responseบาง ๆ เสมอ — business logic ไม่ควรอยู่ที่นี่
app.service.tsเก็บ business logic ที่ controller เรียกใช้ผ่าน dependency injectionไม่รู้จัก HTTP เลย จึงทดสอบง่ายและนำไปใช้ซ้ำได้

โครงสร้างนี้คือแพตเทิร์นที่เราจะทำซ้ำตลอดคอร์ส: ทุก feature ใหม่ (เช่น coffees) จะได้ controller + service + module ของตัวเอง แล้วนำ module นั้นมา import เข้า AppModule

Scaffold โปรเจกต์แล้วไล่อ่านทีละไฟล์

สร้างโปรเจกต์ iluvcoffee ที่เราจะใช้ตลอดทั้งคอร์ส แล้วเปิดใน editor เพื่อไล่เส้นทางของ request ด้วยตัวเอง เริ่มจาก main.ts ตามไปที่ AppModule แล้วดูว่า AppController เรียก AppService ตรงไหน

nest new iluvcoffee cd iluvcoffee code . # หรือเปิดด้วย editor ที่ใช้อยู่

ควรได้ผลลัพธ์แบบนี้

ได้โปรเจกต์ที่มีโครงตาม tree ด้านบน และเมื่อไล่อ่านจะเห็นชัดว่า AppController รับ AppService เข้ามาทาง constructor (dependency injection) และ route GET / คืนข้อความ Hello World! ที่มาจาก service ไม่ใช่จาก controller เอง

ลองเช็กให้แน่ใจ

  • ใน main.ts ชี้ได้ว่า root module ที่ใช้ bootstrap คือ AppModule
  • ใน app.module.ts เห็น AppController ในช่อง controllers และ AppService ในช่อง providers
  • อธิบายได้ใน 1 ประโยคว่าทำไมข้อความ Hello World! ถึงอยู่ใน service ไม่ใช่ controller
  • ลองแก้ข้อความใน app.service.ts แล้วดูว่าผลลัพธ์ของ GET / เปลี่ยนตาม (จะได้ทดสอบจริงในบทที่ 5)
