Roles, RolesGuard และ e2e ของ auth

เมื่อจบบทนี้ คุณจะสามารถ

  • ซ้อน guard สองชั้นให้ทำงานตามลำดับ โดยชั้นที่สองใช้ข้อมูลที่ชั้นแรกเตรียมไว้
  • อธิบายได้ว่าทำไมการเปลี่ยน role ในฐานข้อมูลไม่ทำให้ token ที่ออกไปแล้วเปลี่ยนตาม และทำไมนั่นเป็นทั้งข้อดีและข้อเสีย
  • สั่งให้ AI เขียน e2e test ของสัญญา auth ทั้งชุด แล้วตรวจว่ามันทดสอบสิ่งที่ควรทดสอบจริง

บทนี้มี prompt สองอันในสองแชท: อันแรกเปิด endpoint ของ admin อันที่สองเขียน e2e test ของ auth — และเหมือนทุกครั้ง test ต้องมาจากแชทที่ไม่ใช่แชทที่เพิ่งเขียนโค้ดให้

guard ตัวที่สอง ที่ต้องมาทีหลัง

การตรวจสิทธิ์แยกออกจากการตรวจตัวตนอย่างชัดเจน: guard ตัวแรกตอบว่า "คุณเป็นใคร" ตัวที่สองตอบว่า "คนแบบคุณทำสิ่งนี้ได้ไหม" เราจึงเขียน guard เพิ่มอีกตัวแทนที่จะยัดเงื่อนไข role เข้าไปในตัวเดิม

ลำดับสำคัญมาก NestJS เรียก global guard ตามลำดับที่ลงทะเบียนไว้ และ RolesGuard ต้องอ่าน request.user ซึ่งเป็นของที่ JwtAuthGuard แปะไว้ ถ้าลงทะเบียนสลับกัน RolesGuard จะทำงานตอนที่ยังไม่มีใครอ่าน token เลย แล้วมันจะเจอ undefined

อีกเรื่องที่ต้องตัดสินใจคือ route ที่ไม่มี @Roles() ต้องเกิดอะไรขึ้น คำตอบคือปล่อยผ่าน — RolesGuard มีหน้าที่เดียวคือบังคับข้อกำหนดเรื่อง role ถ้า route ไหนไม่ได้กำหนดไว้ แปลว่ามันไม่มีข้อกำหนดนั้น ไม่ใช่ว่ามันห้ามทุกคน การตรวจว่าต้อง login หรือไม่เป็นงานของ guard ตัวแรกไปแล้ว

token คือภาพถ่าย ไม่ใช่กระจกเงา

เราใส่ role ลงไปใน payload ตั้งแต่ตอนออกแบบ login เพื่อให้ตรวจสิทธิ์ได้โดยไม่ต้องอ่านฐานข้อมูลทุก request ซึ่งเร็วและไม่มีภาระเพิ่ม แต่มันมาพร้อมผลที่ต้องเข้าใจให้ชัด

token บันทึกสภาพ ณ วินาทีที่ login แล้วแข็งตัวอยู่อย่างนั้นจนหมดอายุ ถ้าวันนี้เราเลื่อนใครขึ้นเป็น admin ในฐานข้อมูล token ที่เขาถืออยู่ยังบอกว่า USER เหมือนเดิม และเขาจะยังเข้า endpoint ของ admin ไม่ได้จนกว่าจะ login ใหม่ ในทางกลับกัน ถ้าเราถอดสิทธิ์ admin ของใครออก token ใบเดิมของเขาก็ยังใช้สิทธิ์ admin ได้จนหมดอายุ

ข้อหลังคือราคาที่จ่ายสำหรับความเร็ว และเป็นเหตุผลที่ access token ต้องอายุสั้น — ของเราตั้งไว้ 15 นาที นั่นคือขอบเขตความเสียหายสูงสุดถ้าต้องถอดสิทธิ์ใครกะทันหัน ระบบที่ต้องการให้การถอดสิทธิ์มีผลทันทีต้องแลกด้วยการอ่านฐานข้อมูลทุก request หรือทำรายการ token ที่ถูกยกเลิกไว้ตรวจ ซึ่งทั้งสองทางก็คือการเอา state กลับมาไว้ฝั่ง server อีกครั้ง

คุณจะได้เห็นเรื่องนี้เกิดขึ้นจริงในส่วนตรวจท้ายบท ตอนที่เลื่อนตัวเองเป็น admin แล้วพบว่ายังเข้าไม่ได้

ไม่มี endpoint ไหนในคอร์สนี้ที่แต่งตั้ง admin ได้ และนั่นตั้งใจ — endpoint ที่ให้ใครก็ได้ยกระดับสิทธิ์ตัวเองคือช่องโหว่ที่ร้ายแรงที่สุดแบบหนึ่ง การเปลี่ยน role จึงทำด้วย SQL โดยคนที่เข้าถึงฐานข้อมูลได้เท่านั้น ซึ่งตรงกับความเป็นจริงของระบบส่วนใหญ่

admin ไม่ใช่ domain

GET /admin/orders ฟังดูเหมือนควรมีโฟลเดอร์ src/admin/ ของตัวเอง แต่กติกาของโปรเจกต์เราเขียนไว้ว่าหนึ่งโฟลเดอร์ต่อหนึ่ง business domain — และ admin ไม่ใช่ domain มันคือกลุ่มผู้ใช้ สิ่งที่ endpoint นี้ทำงานด้วยยังเป็นคำสั่งซื้อเหมือนเดิมทุกประการ ต่างแค่ว่าเห็นได้กว้างกว่า

ถ้าแยกตามกลุ่มผู้ใช้ เราจะได้ logic ของคำสั่งซื้อกระจายอยู่สองที่ และวันที่แก้สูตรคิดเงินก็ต้องไล่แก้ทั้งคู่ โค้ดของบทนี้จึงอยู่ใน src/orders/ ต่อจากของเดิม

ตรวจโค้ดที่ AI สร้าง

  • RolesGuard ลงทะเบียนหลัง JwtAuthGuard ใน providers — สลับลำดับแล้วมันจะอ่าน request.user ไม่เจอ
  • route ที่ไม่มี @Roles() คืน true ทันที ไม่ใช่ตกไปเข้าเงื่อนไขที่ปฏิเสธ
  • โยน ForbiddenException (403) ไม่ใช่ UnauthorizedException (401) — ผู้ใช้คนนี้ระบุตัวตนได้แล้ว เขาแค่ไม่มีสิทธิ์
  • ใช้ Role ที่ import มาจาก client ที่ Prisma generate ให้ ไม่ใช่ประกาศ type Role = 'USER' | 'ADMIN' ขึ้นใหม่ซึ่งจะเพี้ยนจาก schema ได้ในอนาคต
  • controller ของ admin อยู่ใน src/orders/ และเรียก service ตัวเดิม ไม่ได้ copy logic การแปลงคำสั่งซื้อมาไว้เอง
  • ไม่มี endpoint ไหนที่เขียน role ลงฐานข้อมูลได้ — grep -rn "role" src/auth/auth.service.ts ต้องเจอแค่ตอนอ่านมาใส่ payload
  • git diff --stat test/ ว่างเปล่า

AI มักพลาดตรงนี้: ทำ RolesGuard ให้ปฏิเสธ route ที่ไม่มี @Roles() ซึ่งจะทำให้ทั้งแอปพังทันทีรวมถึง e2e ทั้งสิบเอ็ดข้อ อีกกรณีที่เงียบกว่าคือโยน UnauthorizedException แทน ForbiddenException เพราะทั้งคู่ "แปลว่าเข้าไม่ได้" เหมือนกัน — แต่ client ที่เจอ 401 จะพยายาม refresh token แล้วลองใหม่วนไปเรื่อย ๆ ทั้งที่ปัญหาคือสิทธิ์ไม่พอ ซึ่ง refresh กี่รอบก็ไม่ช่วย

โค้ดอ้างอิงของหัวข้อนี้ — เป็นหนึ่งในวิธีที่ถูก ของคุณไม่จำเป็นต้องเหมือนทุกบรรทัด ขอแค่ผ่านผลลัพธ์ที่ต้องได้:

// src/auth/roles.decorator.ts
import { SetMetadata } from '@nestjs/common';
import { Role } from '../generated/prisma/enums.js';

export const ROLES_KEY = 'roles';

export const Roles = (...roles: Role[]) => SetMetadata(ROLES_KEY, roles);
// src/auth/roles.guard.ts
import {
  CanActivate,
  ExecutionContext,
  ForbiddenException,
  Injectable,
} from '@nestjs/common';
import { Reflector } from '@nestjs/core';
import { Role } from '../generated/prisma/enums.js';
import { ROLES_KEY } from './roles.decorator.js';
import type { AuthenticatedRequest } from './jwt-payload.interface.js';

@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private readonly reflector: Reflector) {}

  canActivate(context: ExecutionContext): boolean {
    const required = this.reflector.getAllAndOverride<Role[] | undefined>(
      ROLES_KEY,
      [context.getHandler(), context.getClass()],
    );

    if (required === undefined) {
      return true;
    }

    const request = context.switchToHttp().getRequest<AuthenticatedRequest>();

    if (!required.some((role) => role === request.user.role)) {
      throw new ForbiddenException();
    }

    return true;
  }
}
// src/auth/auth.module.ts — เฉพาะส่วน providers
  providers: [
    AuthService,
    PasswordService,
    { provide: APP_GUARD, useClass: JwtAuthGuard },
    { provide: APP_GUARD, useClass: RolesGuard },
  ],

สองบรรทัดนี้สลับกันไม่ได้ และนี่เป็นหนึ่งในไม่กี่ที่ในโปรเจกต์ที่ลำดับของโค้ดมีผลต่อพฤติกรรมจริง

// src/orders/admin-orders.controller.ts
import { Controller, Get } from '@nestjs/common';
import { ApiBearerAuth, ApiOkResponse, ApiTags } from '@nestjs/swagger';
import { Roles } from '../auth/roles.decorator.js';
import { Role } from '../generated/prisma/enums.js';
import { CartResponseDto } from './dto/cart-response.dto.js';
import { OrdersService } from './orders.service.js';

@ApiTags('admin')
@ApiBearerAuth()
@Roles(Role.ADMIN)
@Controller('admin/orders')
export class AdminOrdersController {
  constructor(private readonly ordersService: OrdersService) {}

  @Get()
  @ApiOkResponse({ type: [CartResponseDto] })
  findAll() {
    return this.ordersService.findAll();
  }
}

Prompt ที่สอง: e2e test ของสัญญา auth

สัญญาใน docs/auth-spec.md ยังไม่มี test ตัวไหนคุ้มครองเลย ทุกอย่างที่ผ่านมาตรวจด้วย curl ทีละคำสั่ง ซึ่งแปลว่าวันที่มีคนแก้อะไรสักอย่างในโบนัสนี้ จะไม่มีอะไรบอกได้ว่าสัญญายังอยู่ครบหรือเปล่า

และเหมือนทุกครั้ง test ต้องมาจากแชทใหม่ ไม่ใช่แชทที่เพิ่งเขียน endpoint ให้ เพราะแชทที่เพิ่งเขียนโค้ดเสร็จจะเขียน test ที่ตรงกับโค้ดที่มันเพิ่งเขียน ไม่ใช่ตรงกับสัญญา

เขียน e2e test ของ auth ใน test/auth.e2e-spec.ts ให้ตรงกับสัญญาใน docs/auth-spec.md @docs/auth-spec.md ผลลัพธ์ที่ต้องได้: - ไฟล์ใหม่ test/auth.e2e-spec.ts ที่ npm run test:e2e เก็บไปรันด้วย (ไม่ต้องแก้ package.json — script นี้มีอยู่แล้ว) - boot แอปจริงด้วย Test.createTestingModule({ imports: [AppModule] }) แล้วยิงผ่าน supertest ที่ app.getHttpServer() และปิดด้วย app.close() ใน afterAll - beforeAll ตั้ง ValidationPipe แบบ global ให้ตรงกับ src/main.ts ทุกตัวเลือก เพราะ createNestApplication() ไม่ได้รัน main.ts ให้ - แปด test ตามนี้ 1. POST /auth/signup ด้วยอีเมลใหม่ → 201 และ body ไม่มีคีย์ที่เกี่ยวกับรหัสผ่านเลย 2. POST /auth/signup ด้วยอีเมลเดิมซ้ำ → 409 3. POST /auth/login รหัสผ่านผิด → 401 และ message ตรงกันเป๊ะกับกรณีอีเมลที่ไม่มีในระบบ 4. POST /auth/login ถูกต้อง → 200 และได้ทั้ง accessToken และ refreshToken 5. GET /auth/me ไม่มี token → 401 6. GET /auth/me พร้อม token → 200 และ email ตรงกับที่สมัครไว้ 7. POST /auth/refresh ด้วยใบที่เพิ่งใช้ไปแล้ว → 401 8. GET /admin/orders ด้วย token ของผู้ใช้ทั่วไป → 403 - test ต้องรันซ้ำได้เรื่อย ๆ: สมัครด้วยอีเมลที่ไม่ซ้ำกับรอบก่อน และลบผู้ใช้ที่ test สร้างขึ้นทิ้งใน afterAll ผ่าน app.get(PrismaService) - import ในไฟล์ test ลงท้ายด้วย .js ตามกติกา ESM ของโปรเจกต์ ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ — Vitest กับ supertest มากับ scaffold แล้ว - ห้ามแก้ไฟล์ใน src/ เด็ดขาด ถ้า test ไม่ผ่านให้บอกผมว่าไม่ผ่านข้อไหน ห้ามแก้โค้ดให้ test ผ่านเอง - ห้ามแก้ test/products.e2e-spec.ts, test/orders.e2e-spec.ts หรือ test/app.e2e-spec.ts - ห้ามเขียน test ที่เปลี่ยน role ของใครเป็น ADMIN — ตรวจแค่ฝั่ง 403 พอ - ห้ามรัน test ให้ ผมจะรันเอง

บรรทัดสุดท้ายของขอบเขตสำคัญกว่าที่เห็น: ถ้า test เลื่อน role ของตัวเองเป็น ADMIN ได้เพื่อจะทดสอบเคส 200 แปลว่า test suite กลายเป็นเครื่องมือยกระดับสิทธิ์ไปด้วย เราจึงทดสอบเฉพาะด้านที่ปฏิเสธ ส่วนด้านที่อนุญาตตรวจด้วยมือไปแล้วในส่วนก่อนหน้า

ตรวจ test ที่ AI เขียน

  • git status เห็นไฟล์ใหม่แค่ test/auth.e2e-spec.ts — ไม่มีไฟล์ใน src/ ถูกแก้ ถ้ามี แปลว่า agent ไปแก้โค้ดให้เข้ากับ test ของมันเอง ให้ย้อนกลับแล้วสั่งใหม่
  • อีเมลที่ใช้สมัครไม่ซ้ำกันทุกรอบ (เช่นต่อท้ายด้วย Date.now()) และ afterAll ลบผู้ใช้นั้นทิ้งจริง — ลองรัน npm run test:e2e สองครั้งติดกัน ต้องเขียวทั้งสองครั้ง
  • เคสที่ 3 เทียบ message ของสองกรณีว่าเท่ากัน ไม่ใช่แค่เช็คว่าทั้งคู่เป็น 401 — ถ้าเช็คแค่ status ข้อความที่รั่วข้อมูลจะผ่าน test ไปได้สบาย
  • เคสที่ 1 ตรวจว่าไม่มีคีย์ที่เกี่ยวกับรหัสผ่าน ไม่ใช่ตรวจว่ามีคีย์ที่ต้องการครบ — สองอย่างนี้ต่างกัน
  • ไม่มี UPDATE หรือ prisma.user.update ที่เปลี่ยน role อยู่ในไฟล์ test
  • ไม่มี URL หรือเลข port ฮาร์ดโค้ดในไฟล์ — ทุก request ยิงผ่าน request(app.getHttpServer())

AI มักพลาดตรงนี้: ใช้อีเมลคงที่อย่าง test@example.com ซึ่งทำให้เคสที่ 1 ผ่านครั้งแรกครั้งเดียว แล้วได้ 409 ตลอดไปในรอบถัด ๆ มา — test ที่รันซ้ำไม่ได้คือ test ที่จะถูกปิดทิ้งภายในสัปดาห์เดียว อีกกรณีคือเขียนเคสที่ 7 โดยไม่ได้ refresh ก่อนหนึ่งรอบ ทำให้ token ที่เอามาทดสอบยังเป็นใบที่ใช้ได้อยู่ แล้ว test จะแดงทั้งที่โค้ดถูก

โค้ดอ้างอิงของหัวข้อนี้ — เฉพาะโครงและสองเคสที่พลาดง่ายที่สุด ของคุณไม่จำเป็นต้องเหมือนทุกบรรทัด

import { Test, TestingModule } from '@nestjs/testing';
import { INestApplication, ValidationPipe } from '@nestjs/common';
import request from 'supertest';
import { AppModule } from './../src/app.module.js';
import { PrismaService } from './../src/prisma/prisma.service.js';

describe('Auth contract (e2e)', () => {
  let app: INestApplication;
  const email = `student-${Date.now()}@example.com`;
  const password = 'secret123';

  beforeAll(async () => {
    const moduleFixture: TestingModule = await Test.createTestingModule({
      imports: [AppModule],
    }).compile();

    app = moduleFixture.createNestApplication();
    app.useGlobalPipes(
      new ValidationPipe({
        whitelist: true,
        transform: true,
        transformOptions: { enableImplicitConversion: true },
      }),
    );
    await app.init();
  });

  afterAll(async () => {
    await app.get(PrismaService).user.deleteMany({ where: { email } });
    await app.close();
  });

  it('POST /auth/signup → 201 without any password field', async () => {
    const response = await request(app.getHttpServer())
      .post('/auth/signup')
      .send({ email, password, name: 'Student' })
      .expect(201);

    expect(Object.keys(response.body)).not.toContain('passwordHash');
    expect(Object.keys(response.body)).not.toContain('password');
  });
  it('POST /auth/login → same message for wrong password and unknown email', async () => {
    const wrongPassword = await request(app.getHttpServer())
      .post('/auth/login')
      .send({ email, password: 'not-the-password' })
      .expect(401);

    const unknownEmail = await request(app.getHttpServer())
      .post('/auth/login')
      .send({ email: 'nobody@example.com', password })
      .expect(401);

    expect(wrongPassword.body.message).toBe(unknownEmail.body.message);
  });
});

เคสที่สองในตัวอย่างนี้คือเคสที่พิสูจน์สิ่งที่ curl พิสูจน์ได้ยาก: ไม่ใช่ว่าแต่ละกรณีตอบ 401 แต่คือทั้งสองกรณีตอบเหมือนกัน — ซึ่งเป็นข้อกำหนดที่เขียนไว้ในสัญญาตั้งแต่บทแรกของโบนัส และสังเกตว่ามันต้องมาหลังเคสสมัคร เพราะ Vitest รัน it ตามลำดับที่เขียนในไฟล์ ถ้าสลับที่กัน ตอนทดสอบรหัสผ่านผิดจะยังไม่มีอีเมลนั้นอยู่จริง ทั้งสองกรณีจึงกลายเป็น “อีเมลไม่มีในระบบ” เหมือนกัน และการเทียบก็จะผ่านโดยไม่ได้ทดสอบอะไรเลย

ถ้าอธิบายบรรทัดไหนไม่ได้ ยังไม่ผ่านบทนี้ — กลับไปอ่านส่วนแนวคิดก่อน
