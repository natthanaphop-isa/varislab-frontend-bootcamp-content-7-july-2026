และของที่ใช้งานได้จริงห้าอย่างนี้

  • ห้า endpoint ที่รูปทรง response ตรงกับสัญญาใน docs/api-spec.md: GET /products/categories, GET /products, GET /products/{id}, GET /products/category/{slug} และ POST /carts/add
  • สัญญาที่ตรวจอัตโนมัติ — npm run test:e2e boot แอปจริงขึ้นมาแล้วตรวจ status และรูปทรงของ response ครบสิบเคส รวมถึงเคส 404, หมวดที่ไม่มีจริง และ POST /carts/add
  • validation ที่กันขยะ — ValidationPipe แบบ global พร้อม whitelist และ DTO ที่ประกาศกฎไว้ครบ ทำให้ payload ผิดรูปได้ 400 พร้อมข้อความที่อ่านรู้เรื่อง
  • คำสั่งซื้อที่ atomic — POST /carts/add เขียน Order กับ OrderItem ในทรานแซกชันเดียว
  • เอกสารและการเชื่อมต่อ — Swagger UI ที่ /api พร้อม response schema ทุก endpoint, CORS ที่เปิดให้เฉพาะ origin ของ Vite และ React app ของจริงที่รันบน API นี้ได้ครบวงจรโดยแก้แค่ base URL หนึ่งบรรทัด

และถ้าคุณเรียนเจ็ดบทโบนัสต่อจนจบ จะมีของเพิ่มอีกสี่อย่าง — ทั้งหมดนี้ไม่กระทบห้าข้อข้างบนเลยแม้แต่ข้อเดียว React app ยังทำงานเหมือนเดิมทุกประการ

  • สัญญาชุดที่สองที่คุณออกแบบเอง — docs/auth-spec.md ต่างจาก docs/api-spec.md ตรงที่ไม่มี client ตัวไหนมาบังคับรูปทรง คุณจึงเป็นคนตัดสินใจทั้งหมดเอง
  • เจ็ด endpoint ของผู้ใช้ — สมัคร, เข้าสู่ระบบ, ดูข้อมูลตัวเอง, ดูคำสั่งซื้อของตัวเอง, แลก token ใบใหม่, ออกจากระบบ และ endpoint ของ admin ที่เห็นคำสั่งซื้อทุกใบ
  • guard สองชั้นที่ปิดเป็นค่าปริยาย — ทุก route ต้องมี token เว้นแต่จะติด @Public() ไว้ ส่วนชั้นที่สองตรวจ role และตอบ 403 แยกจาก 401 อย่างชัดเจน
  • e2e อีกแปดเคส — npm run test:e2e รวมเป็น Tests 19 passed (19) จากสี่ไฟล์ โดยสิบเคสแรกคุ้มครองสัญญาที่ React app พึ่งพา และแปดเคสใหม่คุ้มครองสัญญาที่คุณเขียนเอง

สิ่งที่คุณควรอธิบายได้ตอนนี้

ตอบทีละข้อโดยยังไม่เปิดโค้ด ข้อไหนตอบไม่ได้ให้กลับไปอ่านบทนั้นอีกครั้ง — นี่คือมาตรวัดเดียวที่บอกว่าคุณเป็นเจ้าของโค้ดนี้จริงหรือเปล่า

  • ทำไม price, rating และ discountPercentage ประกาศเป็น Float ใน schema.prisma (ตอนออกแบบ schema)
  • ทำไม id ของ Product ไม่ใช่ @default(autoincrement()) (ตอนออกแบบ schema และตอน seed ข้อมูล)
  • whitelist: true ใน ValidationPipe ตัดอะไรทิ้ง และทำไมการตัดทิ้งเงียบ ๆ ปลอดภัยกว่าปล่อยผ่าน (ตอนทำ pagination และตอน validate ตะกร้า)
  • ทำไม @Get('categories') ต้องประกาศก่อน @Get(':id') และจะเกิดอะไรถ้าสลับกัน (ตอนทำ endpoint หมวดหมู่และสินค้ารายชิ้น)
  • ทำไม limit ที่เกิน 100 หรือต่ำกว่า 1 ต้องได้ 400 แทนที่จะถูกปัดให้อยู่ในช่วงเงียบ ๆ (ตอนทำ pagination)
  • ทำไม mapper ไม่ใส่ key discountPercentage เลยเมื่อค่าในฐานข้อมูลเป็น null แต่ยังใส่ brand เสมอ (ตอนทำ mapper)
  • callback ที่ส่งให้ $transaction rollback อะไรเมื่อมีการ throw ข้างใน และ client ที่ควรใช้ข้างในคือตัวไหน (ตอนสร้างคำสั่งซื้อใน transaction)
  • ทำไม endpoint ของคำสั่งซื้อชื่อ /carts/add ไม่ใช่ /orders ที่ดูถูกหลักกว่า (ตอนเปิด POST /carts/add)
  • origin ที่ใส่ใน enableCors ป้องกันอะไร และไม่ป้องกันอะไร (ตอนเปิด CORS)
  • ทำไม response DTO ต้องเป็น class ไม่ใช่ interface (ตอนทำ mapper และตอนเขียนเอกสาร DTO)
  • ทำไม refresh token ต้อง hash ด้วย SHA-256 ไม่ใช่ bcrypt ทั้งที่ bcrypt ปลอดภัยกว่าสำหรับรหัสผ่าน (โบนัส — ตอนทำ refresh token)
  • ทำไม guard ต้องอ่าน metadata ทั้งระดับ handler และระดับ class ไม่ใช่แค่ระดับ handler (โบนัส — ตอนใส่ JWT guard)
  • ทำไม Order.userId ยังไม่ผูก foreign key ไปหา User ทั้งที่มีตาราง User แล้ว (โบนัส — ตอนออกแบบ model ของผู้ใช้)

ก้าวต่อไป

  • ย้าย refresh token ไปไว้ใน httpOnly cookie — ตอนเปิด CORS เราตั้งข้อสังเกตไว้ว่า * ใช้ร่วมกับ cookie ไม่ได้ตามสเปก และโบนัสก็เลือกส่ง refresh token ทาง body ด้วยเหตุผลนั้นพอดี แต่ token ที่อยู่ใน JavaScript อ่านได้ก็ถูกขโมยด้วยสคริปต์ที่หลุดเข้ามาได้ cookie แบบ httpOnly ปิดช่องนั้น แลกกับการต้องเปิด credentials ใน CORS ระบุ origin ให้ชัด และรับมือกับ CSRF ที่ตามมาเป็นแพ็กเกจ — เป็นแบบฝึกหัดที่ดีเพราะมันบังคับให้กลับไปแก้การตัดสินใจเก่าสองข้อพร้อมกัน
  • พา test suite ขึ้น CI — npm run test:e2e ที่เรามีตอนนี้ยิงใส่ฐานข้อมูลตัวเดียวกับที่ใช้พัฒนา ซึ่งสะดวกตอนทำ workshop แต่ใช้บน CI ไม่ได้: test จะเห็นข้อมูลที่ใครก็ไม่รู้ทิ้งค้างไว้ และเคสสั่งซื้อก็เขียนแถวจริงเพิ่มทุกครั้งที่รัน ทางออกคือฐานข้อมูลแยกที่ยกขึ้นก่อนรันแล้วทิ้งทีหลัง ตาม NestJS Fundamentals — สร้าง e2e Test แรก ที่ผูก pretest:e2e กับ posttest:e2e ไว้กับ service test-db ใน Docker
  • ขึ้น production ด้วย migrate deploy — บนเครื่องเราใช้ prisma migrate dev แต่บน server ต้องใช้ prisma migrate deploy ซึ่งรัน migration ที่ commit ไว้เท่านั้นและไม่สร้างไฟล์ใหม่ ลองย้ายฐานข้อมูลขึ้น Postgres แบบ hosted ตาม API Design in Node.js — Hosted PostgreSQL กับ Neon แล้วเปลี่ยนแค่ DATABASE_URL กับ CORS_ORIGIN
  • ตัด stock ในทรานแซกชันของคำสั่งซื้อ — ตอนนี้สั่งซื้อแล้ว stock ไม่ลด เพราะคอร์สนี้ยังไม่ทำในเวอร์ชันแรก แต่ของจริงต้องลด และต้องลดใน $transaction เดียวกับที่สร้าง Order พร้อมปฏิเสธเมื่อของไม่พอ — เป็นแบบฝึกหัดที่ดีเรื่อง business rule กับ atomicity
  • เพิ่ม endpoint ค้นหาสินค้า — ตอนนี้ client กรองสินค้าได้แค่ตาม category กับ pagination ลองเพิ่ม query param อย่าง q สำหรับค้นหาชื่อสินค้า โดยเริ่มจากการเพิ่ม field นี้ลงใน docs/api-spec.md ก่อนเขียนโค้ดสักบรรทัด — ฝึก workflow contract-first แบบเดียวกับที่ใช้มาทั้งคอร์สด้วยตัวเองอีกครั้ง

ปิดท้าย

สิ่งที่คอร์สนี้ฝึกจริง ๆ ไม่ใช่การพิมพ์โค้ด NestJS ให้เร็วขึ้น แต่เป็นการสั่งงานให้แคบพอจะตรวจได้: จับสัญญาก่อนเขียนโค้ด แปลงสัญญาเป็น prompt สามส่วนที่ระบุผลลัพธ์และข้อห้ามชัดเจน แล้วอ่านผลลัพธ์ทีละบรรทัดเทียบกับสัญญานั้น ยิ่ง AI พิมพ์ได้เร็วเท่าไร ความสามารถในการตรวจของคุณยิ่งเป็นตัวตัดสินคุณภาพงานมากขึ้นเท่านั้น เก็บกติกาข้อเดียวนี้ไปใช้กับทุกโปรเจกต์ต่อจากนี้

AI พิมพ์แทนคุณได้ แต่คุณต้องอธิบายทุกบรรทัดได้ — ถ้าอธิบายไม่ได้ แปลว่ายังไม่ผ่านบทนี้
