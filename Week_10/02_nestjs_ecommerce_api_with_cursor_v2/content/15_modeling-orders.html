NestJS E-commerce API Workshop

ออกแบบ Model และ DTO ของคำสั่งซื้อ

เมื่อจบบทนี้ คุณจะสามารถ

  • อ่าน body ที่ React app ส่งมาตอน checkout แล้วแปลงเป็นตาราง Order และ OrderItem ได้
  • อธิบายได้ว่าทำไม OrderItem ต้องคัดลอก title, price, discountPercentage, thumbnail เก็บไว้เอง
  • เลือกใส่ onDelete: Cascade ให้ถูกฝั่ง และบอกได้ว่าทำไม seed ต้องเปลี่ยนลำดับการลบข้อมูล
  • เขียน DTO ที่มี object และ array ซ้อนอยู่ข้างใน ให้ ValidationPipe ตรวจได้จริงทุกชั้น และอธิบายได้ว่าทำไม nested object ต้องมีทั้ง @ValidateNested() และ @Type(() => Class)
  • เทียบ zod schema ฝั่ง React กับ DTO ฝั่ง API และบอกได้ว่าทำไมต้องตรวจซ้ำทั้งสองฝั่ง

บทนี้มี prompt สองอันในสองแชท: อันแรกออกแบบตารางที่เก็บคำสั่งซื้อไว้ในฐานข้อมูล อันที่สองออกแบบ DTO ที่ตรวจ body ตอนคำสั่งซื้อเดินทางเข้ามา — รูปทรงเดียวกันคนละด้านของแอป และทั้งคู่ต้องเสร็จก่อนจะเปิด route POST /carts/add ได้ในบทถัดไป

สองฝั่งของคำสั่งซื้อ: body ที่รับ กับ response ที่ต้องคืน

ถึงตอนนี้ API ของเราอ่านสินค้าได้ครบแล้ว จากนี้ไปจะเพิ่มฝั่ง เขียน ตัวเดียวที่ React app ต้องใช้ คือตอนกดสั่งซื้อ ก่อนออกแบบตารางต้องรู้สองอย่างให้แน่ชัด: client ส่งอะไรมา และ client คาดหวัง response หน้าตาแบบไหน

ฝั่งที่ส่งมาคือ hook useCheckout ของ React app มันประกอบ body จากตะกร้าแบบนี้เสมอ (userId ยังเป็นค่าคงที่ 1 เพราะแอปตัวอย่างยังไม่มีระบบ login)

{
  "userId": 1,
  "products": [{ "id": 1, "quantity": 2 }],
  "address": {
    "address": "1 Sukhumvit Rd",
    "email": "a@b.com",
    "phone": "0812345678"
  }
}

ฝั่งที่ต้องคืนคือ response shape ที่เราออกแบบเอง ไว้ใน docs/api-spec.md ส่วน order receipt — client ของจริง (PlaceOrderResponse) อ่านแค่ { id } แล้วทิ้งที่เหลือ แต่ endpoint ที่คืนแค่ id เดียวใช้ตรวจสอบอะไรไม่ได้เลย เราจึงออกแบบใบเสร็จเต็มรูปแบบ ตัวอย่างสั่งซื้อสินค้า id 1 (Velvet Matte Lipstick ราคา 9.99 ส่วนลด 10.48%) จำนวน 2 ชิ้น — id ของ order เริ่มนับจาก 1 เองเพราะเป็นตารางคนละใบกับ Product

{"id":1,"userId":1,"products":[{"id":1,"title":"Velvet Matte Lipstick","price":9.99,"quantity":2,"total":19.98,"discountPercentage":10.48,"discountedPrice":17.89,"thumbnail":"https://picsum.photos/seed/product-1-thumb/300/300"}],"total":19.98,"discountedTotal":17.89,"totalProducts":1,"totalQuantity":2}

discountedPrice ได้ 17.89 เพราะ 19.98 × (1 − 10.48/100) ปัดสองตำแหน่ง (สูตรและตัวอย่างแบบทีละขั้นอยู่ในขั้นคิดเงินถัดไป) สังเกตความไม่สมมาตรสองจุด: address ที่ส่งไปไม่ถูกส่งกลับมาใน response เลย และ products[] ที่กลับมามี field มากกว่าที่ส่งไปเยอะ (title, price, total, discountPercentage, discountedPrice, thumbnail) นั่นคือหน้าที่ของเรา — รับ id กับ quantity แล้วเติมข้อมูลสินค้าและยอดเงินให้ครบ

Order หนึ่งใบ มีหลาย OrderItem

คำสั่งซื้อหนึ่งใบมีสินค้าได้หลายรายการ จึงเป็นความสัมพันธ์ one-to-many ตรงตัว: Order เก็บสิ่งที่เป็นของทั้งใบ (userId, ที่อยู่จัดส่ง, ยอดรวม, เวลาที่สั่ง) และ OrderItem เก็บสิ่งที่เป็นของแต่ละบรรทัด (สินค้าตัวไหน กี่ชิ้น ราคาเท่าไร) — pattern เดียวกับ Product กับ Review ที่ทำไว้ตอนออกแบบตารางสินค้า

ที่อยู่จัดส่ง (address, email, phone) เก็บไว้ที่ Order แม้ response จะไม่คืนออกไป เพราะข้อมูลนี้จำเป็นต่อการจัดส่ง และเป็นค่าของใบนั้นใบเดียว ไม่ใช่ของ user (user คนเดียวสั่งไปหลายที่อยู่ได้)

snapshot: ใบเสร็จของเมื่อวานต้องไม่เปลี่ยนเพราะราคาของวันนี้

จุดตัดสินใจสำคัญที่สุดของบทนี้: OrderItem มี productId อยู่แล้ว ทำไมยังต้องเก็บ title, price, discountPercentage, thumbnail ซ้ำอีก ทั้งที่ join กลับไปที่ Product ก็อ่านได้

เพราะ Product เปลี่ยนได้ พรุ่งนี้ร้านลดราคาจาก 9.99 เป็น 7.99 หรือเปลี่ยนชื่อสินค้า ถ้าใบเสร็จอ่านราคาจากตาราง Product ทุกครั้ง ใบเสร็จของเมื่อวานจะเปลี่ยนตัวเลขตามไปด้วย — ลูกค้าจ่ายไป 19.98 แต่ประวัติกลับโชว์ 15.98 นี่คือบั๊กทางบัญชี ไม่ใช่เรื่องความสวยงามของ schema

เราจึง คัดลอก ค่าที่ใช้คิดเงินลงมาเก็บใน OrderItem ตอนสั่งซื้อ (เรียกว่า snapshot หรือ denormalization ที่ตั้งใจทำ) ส่วน productId ยังเก็บไว้เพื่อให้ลิงก์กลับไปหน้าสินค้าได้ แต่ตัวเลขบนใบเสร็จไม่พึ่งมันแล้ว ด้วยเหตุผลเดียวกัน total, discountedTotal, totalProducts, totalQuantity ก็ถูกเก็บเป็น column ไม่ใช่คำนวณใหม่ตอนอ่าน

ลบอะไรได้ ลบอะไรไม่ได้

สองความสัมพันธ์ของ OrderItem ต้องตั้ง onDelete ต่างกัน และนี่คือจุดที่ AI มักทำเหมือนกันทั้งคู่

ความสัมพันธ์onDeleteเหตุผล
OrderItem → OrderCascadeรายการสินค้าไม่มีความหมายถ้าไม่มีใบคำสั่งซื้อ ลบใบทิ้ง รายการต้องหายตามไปด้วย
OrderItem → Productค่า default (Restrict)ห้ามลบสินค้าที่ยังมีคำสั่งซื้ออ้างถึง ไม่งั้นเราจะทำใบเสร็จหายเพราะลบสินค้าตัวเดียว

ผลข้างเคียงตามมาทันทีที่ prisma/seed.ts ปัจจุบัน seed ลบข้อมูลตามลำดับ review → product → category ใน transaction พอมี OrderItem อ้างถึง Product แบบ Restrict คำสั่ง tx.product.deleteMany() จะพังทันทีถ้ายังมีคำสั่งซื้อค้างอยู่ในฐานข้อมูล จึงต้องลบ orderItem และ order ขึ้นไปเป็นสองบรรทัดแรกของ transaction

ลำดับต้องเป็น orderItem ก่อน order เสมอ ไม่ใช่เพราะ Cascade ใช้ไม่ได้ (ใช้ได้) แต่เพราะการเขียนลำดับลูกก่อนแม่ให้ชัดเจนทำให้อ่าน seed แล้วเห็น dependency graph ทันที และไม่ต้องพึ่งพฤติกรรมของ FK

ตารางพร้อมรับข้อมูลแล้ว ทีนี้ถึงคิวประตูทางเข้า: body ที่ React app ส่งมาต้องถูกตรวจให้ครบทุกชั้นก่อน ไม่ใช่ปล่อยให้เดินเข้าไปถึงตารางที่เพิ่งออกแบบเสร็จ

ทวนของเดิม: DTO + whitelist

คอร์ส NestJS Fundamentals วางกติกาไว้แล้วว่า body ที่เข้ามาต้องผ่าน DTO ที่เป็น class ไม่ใช่ interface เพราะ decorator ของ class-validator ต้องเกาะอยู่กับ metadata ของ class จริงตอน runtime ส่วน interface หายไปหมดตอน compile และตั้งแต่ตอนทำ pagination src/main.ts ก็เปิด ValidationPipe แบบ global ไว้แล้ว

app.useGlobalPipes(
  new ValidationPipe({
    whitelist: true,
    transform: true,
    transformOptions: { enableImplicitConversion: true },
  }),
);

สามตัวเลือกนี้มีผลกับบทนี้ตรง ๆ: whitelist: true ตัด field ที่ไม่มี decorator ออกจาก body ทิ้งเงียบ ๆ (client แนบ isAdmin: true มาก็ไม่มีทางไหลเข้า service), transform: true สั่งให้ pipe แปลง body ดิบเป็น instance ของ DTO และ enableImplicitConversion แปลง string เป็น number ตามชนิดที่ประกาศไว้ให้ — สะดวกกับ query string ของ pagination แต่ body ของบทนี้เป็น JSON ที่มีชนิดข้อมูลมาถูกต้องแล้ว

nested object ไม่ถูกตรวจเอง

กับดักใหญ่ที่สุดของ DTO ซ้อนชั้นคือ: class-validator ตรวจได้เฉพาะ instance ของ class เท่านั้น แต่ JSON.parse คืน plain object ธรรมดาที่ไม่มี constructor ผูกอยู่ ดังนั้นถึงเราประกาศชนิดว่า address: AddressDto ตัว pipe ก็ยังไม่รู้ว่าจะต้องเอา rule ของ class ไหนไปตรวจ object ก้อนนั้น เพราะ type annotation ของ TypeScript หายไปตอน compile

จึงต้องใช้สอง decorator คู่กัน

Decoratorมาจากทำอะไร
@Type(() => AddressDto)class-transformerบอกว่าจะ สร้าง ก้อน JSON นี้เป็น instance ของ class ไหน ถ้าไม่มีบรรทัดนี้ object จะยังเป็น plain object
@ValidateNested()class-validatorบอกว่าให้ไล่ตรวจ rule ข้างใน instance นั้นต่อ ไม่ใช่ตรวจแค่ว่ามี field นี้
@ValidateNested({ each: true })class-validatorรูปแบบสำหรับ array — ไล่ตรวจทุกสมาชิก ไม่ใช่ตรวจตัว array เป็นก้อนเดียว
@ArrayMinSize(1)class-validatorตะกร้าว่างต้องไม่กลายเป็นคำสั่งซื้อ — products: [] ต้องได้ 400 ไม่ใช่ order ยอด 0 บาท

ถ้าลืม @Type(() => AddressDto) จะไม่มี error อะไรเลย แต่ validation ของ address จะผ่านทุกอย่าง — ส่ง {"address": {}} ก็ผ่าน นี่คือความพลาดที่อันตรายที่สุดในบทนี้ เพราะเงียบสนิทจนกว่าจะมีข้อมูลเสียลงฐานข้อมูล

เราเรียง class เล็กไปใหญ่เพื่ออ่านง่าย: CartProductDto → AddressDto → AddCartDto — arrow function ใน @Type(() => CartProductDto) ถูกเรียกตอน class-transformer แปลง payload จริง (คือตอนมี request เข้ามา) ไม่ใช่ตอนประกาศ class จึงไม่ผูกกับลำดับการประกาศ นั่นคือเหตุผลที่ @Type รับ function ไม่ใช่รับ class ตรง ๆ

ตรวจสองฝั่งไม่ใช่ความซ้ำซ้อน

ฝั่ง React app ตรวจ address ด้วย zod อยู่แล้ว (src/features/checkout/schema.ts)

export const checkoutAddressSchema = z.object({
  address: z.string().min(1, "Address is required"),
  email: z
    .string()
    .min(1, "Email is required")
    .pipe(z.email("Enter a valid email address")),
  phone: z.string().min(1, "Phone number is required"),
});

DTO ของเราจะสะท้อนกฎเดียวกันทีละข้อ: address ไม่ว่าง → @IsString() @IsNotEmpty(), email ต้องเป็นอีเมล → @IsEmail(), phone ไม่ว่าง → @IsString() @IsNotEmpty() ที่ต้องตรวจซ้ำเพราะ validation ฝั่ง client เป็นเรื่องของ ประสบการณ์ผู้ใช้ ไม่ใช่ความปลอดภัย — ใครก็ยิง curl ตรงเข้า API ข้าม React ไปได้ กฎง่าย ๆ คือข้อมูลจากภายนอกไม่เชื่อถือได้เลย จนกว่า API จะตรวจเอง

รูปแบบ error ที่ตอบออกไปเป็นมาตรฐานของ Nest: message เป็น array ของทุกข้อที่ผิดพร้อมกัน ไม่ใช่ string เดี่ยว — ApiError ของ React app อ่านค่าจาก data.message ได้อยู่แล้วไม่ว่าจะเป็น string หรือ array และการบอกครบทุกข้อในรอบเดียวมีประโยชน์กับคนใช้ API มากกว่าการต้องยิงซ้ำทีละข้อ

เป้าหมายของบทนี้

รายการด้านล่างคือไฟล์ที่เปลี่ยนในโค้ดอ้างอิงของคอร์ส — ใช้เป็นแผนที่ตอนเทียบงาน ไม่ใช่ข้อบังคับ Cursor ของคุณอาจวางไฟล์หรือตั้งชื่อต่างไปได้ ขอแค่ผ่านผลลัพธ์ที่ต้องได้ใน prompt

ecommerce-api/
├── prisma/
│   ├── schema.prisma          (แก้ไข: เพิ่ม model Order, OrderItem และ relation ฝั่ง Product)
│   └── seed.ts                (แก้ไข: ลบ orderItem และ order ก่อนลบ review)
└── src/
    └── orders/
        └── dto/
            └── add-cart.dto.ts   (สร้างใหม่)
  • prisma/schema.prisma — ในโค้ดอ้างอิง: มี model Order และ model OrderItem ครบ field ตาม order receipt ใน docs/api-spec.md บวกที่อยู่จัดส่ง, มี orderItems OrderItem[] ฝั่ง Product, มี @@index([orderId]) และ @@index([productId]) · ไม่แตะ model Category, Review หรือ field เดิมของ Product
  • prisma/seed.ts — ในโค้ดอ้างอิง: เพิ่ม tx.orderItem.deleteMany() แล้ว tx.order.deleteMany() ก่อน tx.review.deleteMany() · ไม่แก้ส่วน fetch, ส่วน createMany หรือข้อความ log
  • src/orders/dto/add-cart.dto.ts — ในโค้ดอ้างอิง: export class สามตัวในไฟล์เดียว เรียง CartProductDto → AddressDto → AddCartDto, ทุก field มี decorator, products มีทั้ง @IsArray(), @ArrayMinSize(1), @ValidateNested({ each: true }) และ @Type() · ไม่มี field ที่เป็น optional, ไม่มีค่า default, ไม่ติดตั้ง package ใหม่ (class-validator และ class-transformer ติดตั้งไว้แล้วตั้งแต่ตอนเปิด ValidationPipe)
  • ยังไม่มี service, controller หรือ module ของคำสั่งซื้อในบทนี้ — DTO ตัวนี้จะถูกใช้ครั้งแรกในบทถัดไปตอนคิดเงิน แล้วจึงถูกผูกเข้ากับ route POST /carts/add

สั่ง Cursor เพิ่มสอง model แล้วรัน migration ด้วยมือ

commit งานก่อน แล้วเปิดแชทใหม่ใน Cursor โหมด Agent — commit ไว้เพื่อให้เทียบ diff ของ AI ได้ทีละบรรทัด และแชทใหม่ทำให้ context ไม่ปนกับบทก่อน (git add -A && git commit -m "chore: before order schema") จากนั้นส่ง prompt นี้ทั้งก้อน

ก่อนส่ง อ่านกติกาของคอร์สอีกครั้ง: AI พิมพ์แทนคุณได้ แต่คุณต้องอธิบายทุกบรรทัดได้ — ถ้าอธิบายไม่ได้ แปลว่ายังไม่ผ่านบทนี้

เพิ่ม Prisma model ชื่อ Order และ OrderItem และอัปเดต seed ให้ล้างคำสั่งซื้อก่อนล้างสินค้า @prisma/schema.prisma @prisma/seed.ts (ชื่อไฟล์ตามโค้ดอ้างอิง ถ้า seed ของคุณอยู่คนละที่ ให้ @ ไฟล์ seed ที่คุณมีจริง) ผลลัพธ์ที่ต้องได้: - หลังผมรัน npx prisma migrate dev --name add-orders ฐานข้อมูลมีตารางใหม่ Order และ OrderItem (\dt ได้ 6 แถว) โดย migration ไม่ถามยืนยันและไม่ทำข้อมูลเดิมหาย - Order เก็บของทั้งใบตาม order receipt ใน docs/api-spec.md: userId, total, discountedTotal, totalProducts, totalQuantity, เวลาที่สั่ง และที่อยู่จัดส่งที่ React app ส่งมา (address, email, phone) — ใบเสร็จแก้ไม่ได้ จึงไม่มีเวลาแก้ไข - OrderItem เก็บของแต่ละบรรทัด: สินค้าตัวไหน, quantity, total, discountedPrice และ snapshot ของ title, thumbnail, price, discountPercentage ณ ตอนสั่ง เพราะสินค้าอาจเปลี่ยนราคาภายหลัง (discountPercentage ว่างได้ ฟิลด์อื่นห้ามว่าง) - ลบ Order → OrderItem ของใบนั้นหายตามไปด้วย แต่ลบ Product ที่ยังมี OrderItem อ้างถึง → ฐานข้อมูลปฏิเสธ (ใน migration.sql: orderId เป็น ON DELETE CASCADE ส่วน productId เป็น ON DELETE RESTRICT) - ค้นรายการตาม order และตามสินค้าได้เร็ว (มี index ของทั้งสองคอลัมน์) - npm run db:seed ยังได้ Seeded 24 categories, 208 products, 624 reviews เท่าเดิม และรันซ้ำได้แม้มีคำสั่งซื้อค้างอยู่ในฐานข้อมูล - model Category, Review และ field เดิมของ Product ไม่เปลี่ยน, ไม่มีไฟล์ใน src/ ถูกแก้ และ npm run build ผ่าน ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ - ห้ามรัน migrate หรือ generate ให้ผมรันเอง - ยังไม่ต้องสร้าง DTO, service หรือ controller ของคำสั่งซื้อ — DTO เป็น prompt แยกในแชทถัดไป

prompt สั่งห้าม AI รัน migrate หรือ generate เอง เพราะสองคำสั่งนี้แก้ฐานข้อมูลจริงและสร้างไฟล์ migration ที่ commit ลง repo — เราต้องอ่าน schema ที่ AI เขียนให้จบก่อน แล้วจึงรันสามคำสั่งนี้ด้วยมือตามลำดับ

prisma migrate dev ของ Prisma 7 ไม่รัน generate ให้อัตโนมัติ ถ้าข้ามคำสั่งที่สอง tx.orderItem และ tx.order จะยังไม่มีใน Prisma Client และ seed จะพังด้วย type error

ตรวจโค้ดที่ AI สร้าง

  • Order เก็บครบทุกค่าของทั้งใบ (userId, ที่อยู่จัดส่งสามค่า, ยอดรวมสี่ค่า, เวลาที่สั่ง) และไม่มีเวลาแก้ไข — ใบเสร็จไม่ถูกแก้
  • OrderItem เก็บ snapshot ครบสี่ค่า (title, thumbnail, price, discountPercentage) บวก quantity, total, discountedPrice — ไม่ได้อ่านราคาย้อนกลับจาก Product
  • migration.sql ที่สร้างขึ้น: FK ฝั่ง order เป็น ON DELETE CASCADE ส่วนฝั่ง product เป็น ON DELETE RESTRICT และมี index ของทั้งสองคอลัมน์
  • field เดิมของ Product, Category, Review ไม่เปลี่ยน (git diff prisma/schema.prisma เห็นแค่บรรทัดที่เพิ่ม)
  • seed ล้างคำสั่งซื้อก่อนล้างสินค้า และอยู่ใน transaction เดียวกับการลบเดิม — ตัวเลข seed เท่าเดิม และส่วน fetch/createMany/log ไม่ถูกแก้
  • git status ไม่มีไฟล์ใน src/ และไม่มีไฟล์ที่ไม่เกี่ยวกับ schema หรือ seed ถูกแก้

AI มักพลาดตรงนี้: ใส่ onDelete: Cascade ให้ relation ฝั่ง product ด้วย (ลบสินค้าตัวเดียวแล้วใบเสร็จเก่าหายไปเงียบ ๆ) หรือแถม @updatedAt ให้ Order ทั้งที่ไม่มีใน requirement และผิดความหมายของใบเสร็จ อีกกรณีที่เจอบ่อยคือเอาบรรทัด deleteMany ไปวางไว้นอก transaction หรือวางไว้หลัง tx.product.deleteMany() ซึ่งพังตอนรัน

สั่ง Cursor เขียน DTO ของ POST /carts/add

commit งานของครึ่งแรกให้เรียบร้อยก่อน — git add -A && git commit -m "feat: order schema" โดย commit ไฟล์ migration ที่เพิ่งสร้างไปด้วย commit นี้ยังทำหน้าที่เป็นจุดตั้งต้นให้เทียบ diff ของ prompt ถัดไปได้ด้วย จากนั้นเปิดแชทใหม่ใน Cursor โหมด Agent — ไม่ต้อง @-mention ไฟล์ตัวอย่าง Cursor Agent อ่านสไตล์ DTO ที่มีอยู่แล้วในโปรเจกต์และการตั้งค่า ValidationPipe ใน main.ts ได้เอง

สร้าง DTO สำหรับ validate body ของ POST /carts/add ตามที่ React app ส่งมา ผลลัพธ์ที่ต้องได้ (ยังยิง curl ไม่ได้จนกว่าจะผูก route ในขั้นถัดไป — ตอนนี้ตรวจด้วย build และอ่านโค้ด): - body รูปนี้ผ่าน validation ครบทุกชั้น: { "userId": 1, "products": [{ "id": 1, "quantity": 2 }], "address": { "address": "...", "email": "...", "phone": "..." } } - ทุก field required: ขาด userId, products หรือ address ตัวใดตัวหนึ่ง → 400 - userId, products[].id, products[].quantity ต้องเป็นจำนวนเต็มตั้งแต่ 1 ขึ้นไป — 0, ติดลบ หรือทศนิยม → 400 - products: [] (ตะกร้าว่าง) → 400 - ทุกสมาชิกใน products ถูกตรวจ: { "products": [{ "id": 1 }] } ที่ขาด quantity → 400 - address ถูกตรวจข้างในตามกฎเดียวกับฟอร์มฝั่ง React (address ไม่ว่าง, email เป็นอีเมล, phone ไม่ว่าง): "address": {} → 400 และ email ผิดรูป → 400 ด้วย message ที่มีคำนำหน้า address. เช่น "address.email must be an email" - error 400 ใช้รูปแบบมาตรฐานของ ValidationPipe ใน Nest (message เป็น array ของทุกข้อที่ผิด) ไม่ต้องเขียนรูปแบบเอง - field ที่ไม่ได้ประกาศ (เช่น isAdmin) ถูกตัดทิ้ง ไม่ไหลเข้า service - DTO ของ body ถูก export ไว้ให้ service ที่คิดเงินและ route POST /carts/add import ไปใช้ในขั้นถัดไป - npm run build และ npm run lint ผ่าน ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ - ยังไม่ต้องสร้าง service, controller หรือ module ของ orders

ตรวจโค้ดที่ AI สร้าง

  • body ของ request เป็น class ไม่ใช่ interface — ไม่งั้น ValidationPipe ไม่มี rule ให้ตรวจเลย
  • address และสมาชิกทุกตัวของ products ถูกแปลงเป็น instance และถูกไล่ตรวจข้างในจริง — อ่านโค้ดแล้วชี้ได้ว่าบรรทัดไหนทำให้ "address": {} ได้ 400 (ถ้าชี้ไม่ได้ มักแปลว่าขาดตัวแปลงชนิดของ nested object)
  • ตะกร้าว่าง (products: []) ไม่ผ่าน
  • email ถูกตรวจว่าเป็นอีเมลจริง ไม่ใช่แค่เป็น string และไม่มี regex เขียนเองมาแทนตัวตรวจของ library
  • ไม่มี field ไหนเป็น optional หรือมีค่า default
  • userId, id, quantity ปฏิเสธ 0, ค่าติดลบ และทศนิยม
  • git status ไม่มีไฟล์ที่ไม่เกี่ยวกับ DTO ตัวนี้ถูกแก้, package.json ไม่เปลี่ยน และไม่มี any, as หรือ !

AI มักพลาดตรงนี้: ลืม @Type(() => AddressDto) ที่ field address เพราะมันดู "ไม่ใช่ array" จึงรู้สึกว่าไม่ต้องมี ผลคือ address กลายเป็น plain object ที่ validation ผ่านทุกค่า รวมถึง object ว่าง ตรวจง่าย ๆ ด้วยการนับจำนวน @Type ในไฟล์ว่าได้ 2 จริง อีกกรณีคือใส่ @IsObject() แทน @ValidateNested() ซึ่งตรวจแค่ว่า "เป็น object" แล้วจบ

โค้ดอ้างอิงของบทนี้ — เป็นหนึ่งในวิธีที่ถูก ของคุณไม่จำเป็นต้องเหมือนทุกบรรทัด ขอแค่ผ่านผลลัพธ์ที่ต้องได้ (ขั้นถัดไปอ้างชื่อ AddCartDto และ path src/orders/dto/add-cart.dto.ts ถ้าของคุณต่างไปก็ไม่เป็นไร Cursor ในขั้นนั้นจะอ่านจากโค้ดของคุณเอง):

// src/orders/dto/add-cart.dto.ts
import { Type } from 'class-transformer';
import {
  ArrayMinSize,
  IsArray,
  IsEmail,
  IsInt,
  IsNotEmpty,
  IsString,
  Min,
  ValidateNested,
} from 'class-validator';

export class CartProductDto {
  @IsInt()
  @Min(1)
  id: number;

  @IsInt()
  @Min(1)
  quantity: number;
}

export class AddressDto {
  @IsString()
  @IsNotEmpty()
  address: string;

  @IsEmail()
  email: string;

  @IsString()
  @IsNotEmpty()
  phone: string;
}

export class AddCartDto {
  @IsInt()
  @Min(1)
  userId: number;

  @IsArray()
  @ArrayMinSize(1)
  @ValidateNested({ each: true })
  @Type(() => CartProductDto)
  products: CartProductDto[];

  @ValidateNested()
  @Type(() => AddressDto)
  address: AddressDto;
}

ผลลัพธ์ที่คาดหวัง

ได้ไฟล์ใหม่ไฟล์เดียวคือ src/orders/dto/add-cart.dto.ts และ npm run build ผ่านโดยไม่มี error — โฟลเดอร์ src/orders/ ยังไม่มี module ลงทะเบียนใน AppModule ดังนั้นการ build จะแค่ compile ไฟล์นี้ผ่าน type check ไม่มี route ใหม่โผล่ใน log ของ npm run start:dev และยังไม่มีอะไรให้ curl ทดสอบในบทนี้

ข้อความ error ที่ DTO ชุดนี้จะผลิตออกมา จะได้เห็นของจริงตอนเปิด route POST /carts/add — เช่น userId ที่ไม่ได้ส่งมาให้ {"message":["userId must not be less than 1","userId must be an integer number"],"error":"Bad Request","statusCode":400} และ email ผิดรูปให้ {"message":["address.email must be an email"],"error":"Bad Request","statusCode":400} สังเกตคำนำหน้า address. — นั่นคือหลักฐานว่า @ValidateNested() ไล่ตรวจเข้าไปข้างในจริง

  • git diff --stat HEAD เห็นแค่ไฟล์ DTO ที่สร้างใหม่ (ในโค้ดอ้างอิงคือ src/orders/dto/) และ package.json กับ package-lock.json ไม่อยู่ในรายการ
  • commit ผลงานครึ่งหลัง: git add -A && git commit -m "feat: add-cart dto"
