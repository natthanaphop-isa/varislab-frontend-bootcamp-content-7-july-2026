Rules คือความจำถาวรของ Cursor

ใน Week_05_06 บทที่ 7 เราเห็นแล้วว่าไฟล์ใน .cursor/rules/ คือข้อความที่ Cursor แนบไปกับ ทุก คำขอโดยที่เราไม่ต้องพิมพ์ซ้ำ และไฟล์ที่ตั้ง alwaysApply: true จะถูกแนบเสมอไม่ว่าจะเปิดแชทใหม่กี่ครั้ง พูดง่าย ๆ คือกติกาที่คุณเบื่อจะพูดทุกครั้ง ให้ย้ายมาอยู่ในไฟล์นี้ แล้ว prompt ในแต่ละบทจะเหลือแต่เรื่องของบทนั้นจริง ๆ

โปรเจกต์นี้มีไฟล์เดียวชื่อ .cursor/rules/project.mdc พิมพ์ด้วยมือ ไม่ให้ AI เขียนให้ — เพราะนี่คือกติกาที่ คุณ ตั้งให้มัน ไม่ใช่กติกาที่มันตั้งให้ตัวเอง

# Stack
- NestJS 12 แบบ ES module ("type": "module") + TypeScript strict บน Node.js 24
- PostgreSQL ผ่าน Prisma 7 เท่านั้น และเข้าถึงผ่าน PrismaService ที่ inject มา ห้าม new PrismaClient ในไฟล์อื่น
- Validation ด้วย class-validator + class-transformer ผ่าน DTO class (ห้ามใช้ interface เป็น body)

# โครงสร้างไฟล์
- src/<domain>/ หนึ่งโฟลเดอร์ต่อหนึ่ง business domain (products, orders) มี *.module.ts, *.controller.ts, *.service.ts และ dto/
- src/prisma/ มี PrismaModule (global) และ PrismaService
- src/generated/prisma/ คือโค้ดที่ Prisma generate ห้ามแก้ด้วยมือ
- docs/contract/ คือ payload จริงของ dummyjson (README.md คือสรุปสัญญาทั้งหมด) — response ของทุก endpoint ต้องมีรูปทรงตรงกับไฟล์เหล่านี้

# กติกาการเขียนโค้ด
- import ไฟล์ในโปรเจกต์ต้องลงท้ายด้วย .js เสมอ (เช่น './products.service.js') แม้ไฟล์จริงจะเป็น .ts
- ใช้ import type สำหรับ interface/type ที่ปรากฏใน signature ของ method หรือ constructor ที่มี decorator
- ห้ามใช้ any ห้ามใช้ as เพื่อกลบ type error ห้าม non-null assertion (!) และทุกพารามิเตอร์ที่มี decorator ต้องระบุ type
- error ที่ต้องตอบ client ให้ throw HttpException ของ Nest (NotFoundException, BadRequestException) ห้าม throw Error ธรรมดา
- ตั้งชื่อไฟล์ kebab-case.<role>.ts เช่น products.controller.ts, add-cart.dto.ts
- response ต้องเป็น JSON ธรรมดา (number, string, array, object) ห้ามส่ง Date object หรือ Decimal ออกไปโดยไม่แปลง

# ขอบเขต
- ห้ามติดตั้ง dependency ใหม่ถ้าไม่ได้สั่ง
- ห้ามแก้ไฟล์ที่ไม่ได้ระบุในคำสั่ง
- ห้ามสร้าง index.ts หรือ barrel file
- ห้ามเขียน comment อธิบายสิ่งที่โค้ดบอกอยู่แล้ว
- ห้ามรันคำสั่ง prisma migrate, db push, generate หรือ docker เอง ให้บอกผู้ใช้รัน

แต่ละกลุ่มมีเหตุผลเฉพาะของโปรเจกต์นี้ ไม่ได้ลอกมาจากเทมเพลตทั่วไป

  • Stack — บอกความจริงที่เราเห็นด้วยตาในบทที่ 2 ว่าโปรเจกต์เป็น ESM และ strict โมเดลภาษาโดยธรรมชาติจะเขียนโค้ด Nest แบบ CommonJS (ซึ่งเป็นตัวอย่างส่วนใหญ่บนอินเทอร์เน็ต) ประโยคนี้จึงกันปัญหาไว้ตั้งแต่ต้น ส่วนข้อ ห้าม new PrismaClient ในไฟล์อื่น มีไว้เพราะการเปิด connection pool ซ้อนกันหลายชุดคือ bug ที่ไม่แสดงอาการตอน dev แต่ล้มตอนรันจริง
  • โครงสร้างไฟล์ — หนึ่งโฟลเดอร์ต่อหนึ่ง domain ทำให้ diff ของแต่ละบทอยู่ในโฟลเดอร์เดียวและอ่านจบได้ ส่วนบรรทัด docs/contract/ เป็นหัวใจ: มันบอก Cursor ว่า แหล่งความจริงเรื่องรูปทรง response ไม่ใช่ความรู้ของมัน แต่เป็นไฟล์ในโปรเจกต์ และบรรทัด src/generated/prisma/ กัน AI ไม่ให้ "แก้ type error" ด้วยการไปแก้โค้ดที่ generate มา
  • กติกาการเขียนโค้ด — สามข้อแรกคือรอยแผลจาก Nest 12 + TS 6 โดยตรง: import ไม่ลงท้าย .js จะพังตอนรัน (ไม่ใช่ตอน compile), import type จำเป็นเพราะ isolatedModules ทำงานร่วมกับ decorator ที่ต้องมี metadata ของ type จริงตอน runtime และการห้าม any / as / ! ปิดทางออกที่ AI ชอบใช้ที่สุดเมื่อมัน compile ไม่ผ่าน — เราต้องการโค้ดที่ถูก ไม่ใช่โค้ดที่เงียบ ส่วนข้อสุดท้ายเรื่อง Date/Decimal มาจากสัญญาในบทที่ 3 ที่ระบุว่าวันเวลาเป็น string และตัวเลขเป็น number
  • ขอบเขต — สามข้อแรกคุมขนาดของ diff ข้อ barrel file กัน index.ts ที่ทำให้ import สับสนใน ESM และข้อสุดท้ายสำคัญที่สุดในคอร์สนี้: ห้ามรัน migrate, db push, generate หรือ docker เอง เพราะคำสั่งเหล่านั้นแตะฐานข้อมูลจริง และ prisma migrate reset ที่หลุดมาหนึ่งครั้งคือข้อมูล seed ทั้งหมดหายไป เราจะรันคำสั่งพวกนี้ด้วยมือในบทที่ 8 เสมอ

แม่แบบ Prompt ห้าส่วน

ทุก prompt ในคอร์สนี้มีรูปเดียวกัน รูปเดียวกับที่ใช้ใน Week_05_06 บทที่ 8 เพื่อให้คุณจำโครงได้แล้วเขียนเองได้ในโปรเจกต์ของตัวเองต่อไป

<เป้าหมายหนึ่งบรรทัด เขียนเป็นประโยคคำสั่ง> บริบท: @<ไฟล์> @<โฟลเดอร์> … <ข้อเท็จจริงที่ Cursor รู้เองไม่ได้: มีอะไรอยู่ในโปรเจกต์แล้ว, payload ของ dummyjson ที่จับมา, เวอร์ชันของแพ็กเกจ, กติกาใน .cursor/rules ที่เกี่ยวกับบทนี้> โครงสร้าง: สร้าง/แก้ไฟล์ตามนี้ ไม่มากไม่น้อยกว่านี้ - <path> (สร้างใหม่ | แก้ไข) ข้อกำหนดทางเทคนิค: - <ชื่อ, signature, decorator, รูปทรง response, พฤติกรรมเมื่อ error — ระบุให้เป๊ะ> ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ (ยกเว้นตัวที่บทนั้นระบุ) - ห้ามแก้ไฟล์อื่นนอกจากที่ระบุ - ห้ามสร้าง index.ts / barrel - ยังไม่ต้อง <สิ่งที่เป็นงานของบทถัดไป>

เป้าหมาย (บรรทัดแรก) — หนึ่งประโยค เป็นคำสั่ง เช่น "สร้าง endpoint GET /products/categories" ถ้าเขียนได้ไม่จบในหนึ่งประโยค แปลว่าบทนี้ใหญ่เกินไปและควรแยกเป็นสอง prompt ประโยคนี้ยังเป็นเกณฑ์ตัดสินตอนรีวิวด้วย: อะไรที่ AI ทำเกินจากประโยคนี้คือของที่ต้องเอาออก

บริบท — ส่วนที่ยาวที่สุดและเป็นตัวตัดสินคุณภาพของผลลัพธ์ มีสองอย่างในนี้: (1) @-mention ไฟล์หรือโฟลเดอร์ที่ Cursor ต้องอ่านก่อนลงมือ และ (2) ข้อเท็จจริงที่มันรู้เองไม่ได้ เช่น "PrismaService ถูก export จาก PrismaModule ที่เป็น global แล้ว" หรือข้อความ error ที่ต้องตรงตัวอักษร ทุกครั้งที่ผลลัพธ์ออกมาผิด ให้ถามตัวเองก่อนว่า ข้อเท็จจริงที่หายไปคืออะไร แล้วเติมลงส่วนนี้ — ไม่ใช่ไปดุ AI ให้ทำใหม่

โครงสร้าง — ระบุ path ทุกไฟล์พร้อมวงเล็บว่า สร้างใหม่ หรือ แก้ไข และปิดท้ายด้วย "ไม่มากไม่น้อยกว่านี้" ประโยคสั้น ๆ นี้กันพฤติกรรมที่เจอบ่อยที่สุดของ Agent คือสร้างไฟล์แถมมาให้ (interface ซ้ำ, service ที่ยังไม่ต้องใช้, เทสต์ที่คอร์สนี้ไม่ได้ขอ) และมันทำให้ git status หลังรันเป็น checklist ได้ทันที: มีไฟล์เกินจากลิสต์ = ผิด

ข้อกำหนดทางเทคนิค — ชื่อ class ชื่อ method signature decorator รูปทรง response และพฤติกรรมเมื่อเกิด error เขียนแบบชี้ชัด เช่น "findOne(id: number) โยน NotFoundException ด้วยข้อความ Product with id '9999' not found" ยิ่งข้อนี้ละเอียด ผลลัพธ์ยิ่งเดาได้ และเวลารีวิวก็ยิ่งสั้น เพราะคุณเทียบข้อต่อข้อได้เลย

ขอบเขต — บอกสิ่งที่ ห้าม ทำ สามบรรทัดแรกจะซ้ำ ๆ กันแทบทุกบทจนกลายเป็นพิมพ์นิสัย และข้อห้ามที่เขียนไว้ใน .cursor/rules แล้ว (เช่น "ห้ามสร้าง index.ts / barrel") ไม่ต้องเขียนซ้ำในทุก prompt ก็ได้ บรรทัดที่สำคัญที่สุดคือ "ยังไม่ต้อง…" ซึ่งกันงานของบทถัดไปไม่ให้ถูกทำล่วงหน้า เช่นในบทที่ 10 เราเขียน "ยังไม่ต้องแปลงแถวเป็นรูปทรงของ dummyjson" เพราะนั่นคืองานของบทที่ 11 ถ้าไม่เขียน AI จะทำทั้งสองบทรวดเดียว แล้วคุณจะเสียโอกาสตรวจแต่ละส่วนแยกกัน

วงจรตรวจงาน

หลังกด send แล้ว Cursor แก้ไฟล์เสร็จ อย่ารีบ commit ให้เดินเจ็ดขั้นนี้ทุกครั้ง จนจำได้เอง

  1. อ่าน diff ในแผงรีวิวของ Cursor ทีละไฟล์ — ไฟล์ที่ไม่อยู่ในส่วน "โครงสร้าง" ของ prompt คือสัญญาณผิดข้อแรก (เทียบกับ git status ได้ด้วย)
  2. npm run build — ให้ TypeScript ตรวจ ผ่านตรงนี้หมายความว่า import ลงท้าย .js ถูก และไม่มี type ที่หายไป
  3. npm run lint — oxlint จับของที่ compile ผ่านแต่ไม่ควรอยู่ เช่นตัวแปรที่ไม่ได้ใช้
  4. ดู log ของ dev server ว่ามีบรรทัด Mapped {…} route ของ endpoint ที่เพิ่งสร้างขึ้นมาจริง — ถ้าไม่มี แปลว่า controller ยังไม่ถูกลงทะเบียนใน module (เป็นความผิดที่ build ไม่ฟ้อง)
  5. curl ยิง endpoint นั้นด้วยข้อมูลจริง ทั้งกรณีปกติและกรณีพัง (id ที่ไม่มี, หมวดที่ไม่มี)
  6. เทียบ response กับไฟล์ใน docs/contract/ — ชื่อ field ครบไหม, ตัวเลขเป็น number ไม่ใช่ string ไหม, status code ตรงไหม
  7. ถามตัวเองว่า "อธิบายได้ไหม" ทุกบรรทัดที่เพิ่มเข้ามา ถ้ามีบรรทัดที่ตอบไม่ได้ ให้ถาม Cursor ว่าบรรทัดนั้นทำอะไรและทำไมต้องมี แล้วอ่านคำตอบเทียบกับเอกสารจริง เสร็จแล้วจึง git add -A && git commit หรือถ้าไม่ผ่าน ให้ git checkout -- . แล้วส่ง prompt ใหม่ที่เติมข้อเท็จจริงที่ขาดไปลงในส่วนบริบท

เส้นแบ่งระหว่าง refine กับ revert: ถ้าโครงสร้างถูกแล้วแต่ขาดข้อกำหนดไปข้อเดียว (ลืมโยน NotFoundException, ลืมตัด brand ที่เป็น null) ให้ส่ง prompt ต่อท้ายสั้น ๆ ในแชทเดิม แต่ถ้าไฟล์ผิดที่ ผิดชื่อ หรือมีของแถมมาเยอะ ให้ git checkout -- . (และ git clean -fd ถ้ามีไฟล์ใหม่) แล้วเริ่มแชทใหม่ — การแก้โครงสร้างที่ผิดด้วยการต่อ prompt มักได้โค้ดที่ทั้งผิดและซ้อนกันหลายชั้น

เขียนไฟล์ rules ด้วยมือแล้ว commit

สร้างโฟลเดอร์และไฟล์ตามนี้ แล้ว พิมพ์ เนื้อหาจากบล็อกด้านบนลงไปเอง (อย่า copy ทั้งก้อนโดยไม่อ่าน — กติกาที่คุณไม่ได้อ่านคือกติกาที่คุณจะไม่ตรวจ) จากนั้นเปิด Cursor ที่โฟลเดอร์ ecommerce-api แล้ว commit

mkdir -p .cursor/rules # สร้างไฟล์ .cursor/rules/project.mdc แล้วพิมพ์เนื้อหาตามบทเรียน git add .cursor git commit -m "chore: add cursor rules"

เสร็จแล้วลองถาม Cursor ด้วยแชทโหมด Ask (ไม่ใช่ Agent) เพื่อทดสอบว่า rules ถูกอ่านจริง คำถามสั้น ๆ หนึ่งข้อ: โปรเจกต์นี้ import ไฟล์อย่างไร

ผลลัพธ์ที่คาดหวัง

Cursor Settings → Rules แสดงไฟล์ project.mdc พร้อมป้าย Always (มาจาก alwaysApply: true ใน frontmatter) และคำตอบของแชท Ask ต้องบอกว่า import ไฟล์ในโปรเจกต์ต้องลงท้ายด้วย .js แม้ไฟล์จริงเป็น .ts — ถ้ามันตอบแบบทั่ว ๆ ไปโดยไม่พูดถึง .js แปลว่าไฟล์ยังไม่ถูกอ่าน (มักเป็นเพราะวางไฟล์ผิดที่ หรือเปิด Cursor ที่โฟลเดอร์แม่ ไม่ใช่ที่ ecommerce-api)

ตอนนี้ git log --oneline มีสาม commit: scaffold, contract และ rules — โปรเจกต์พร้อมสำหรับ prompt แรกจริงในบทที่ 5

ตรวจว่าใช้งานได้จริง

  • head -4 .cursor/rules/project.mdc เห็น frontmatter ที่มี alwaysApply: true คร่อมด้วย --- ทั้งบนและล่าง
  • Cursor Settings → Rules แสดง project.mdc เป็น Always
  • แชท Ask คำถาม โปรเจกต์นี้ import ไฟล์อย่างไร ได้คำตอบที่พูดถึงนามสกุล .js
  • git log --oneline มีสาม commit และ git status สะอาด
