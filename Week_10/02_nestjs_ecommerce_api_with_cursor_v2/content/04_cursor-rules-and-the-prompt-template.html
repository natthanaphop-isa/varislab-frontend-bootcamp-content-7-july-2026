Rules คือความจำถาวรของ Cursor

ใน React E-commerce + Cursor AI — เขียน .cursor/rules ของโปรเจกต์ เราเห็นแล้วว่าไฟล์ใน .cursor/rules/ คือข้อความที่ Cursor แนบไปกับ ทุก คำขอโดยที่เราไม่ต้องพิมพ์ซ้ำ และไฟล์ที่ตั้ง alwaysApply: true จะถูกแนบเสมอไม่ว่าจะเปิดแชทใหม่กี่ครั้ง พูดง่าย ๆ คือกติกาที่คุณเบื่อจะพูดทุกครั้ง ให้ย้ายมาอยู่ในไฟล์นี้ แล้ว prompt ในแต่ละบทจะเหลือแต่เรื่องของบทนั้นจริง ๆ

โปรเจกต์นี้มีไฟล์เดียวชื่อ .cursor/rules/project.mdc พิมพ์ด้วยมือ ไม่ให้ AI เขียนให้ — เพราะนี่คือกติกาที่ คุณ ตั้งให้มัน ไม่ใช่กติกาที่มันตั้งให้ตัวเอง

# Stack
- NestJS 12 as an ES module ("type": "module") + TypeScript strict on Node.js 24
- PostgreSQL via Prisma 7 only, accessed through the injected PrismaService — never `new PrismaClient` in another file
- Validation with class-validator + class-transformer via DTO classes (never use an interface as a body)

# File structure
- src/<domain>/ one folder per business domain (products, orders), containing *.module.ts, *.controller.ts, *.service.ts and dto/
- src/prisma/ contains PrismaModule (global) and PrismaService
- src/generated/prisma/ is Prisma-generated code — never edit it by hand
- docs/api-spec.md is the API contract we designed ourselves from the client code — every endpoint's response must match this file's shape

# Coding rules
- Imports of project files must always end in .js (e.g. './products.service.js'), even though the actual file is .ts
- Use `import type` for interfaces/types that appear in the signature of a method or constructor that has a decorator
- Never use `any`, never use `as` to silence a type error, never use the non-null assertion (!), and every decorated parameter must declare a type
- Errors returned to the client must be thrown as Nest's HttpException (NotFoundException, BadRequestException) — never throw a plain Error
- Name files kebab-case.<role>.ts, e.g. products.controller.ts, add-cart.dto.ts
- Responses must be plain JSON (number, string, array, object) — never send a Date object or Decimal without converting it first

# Scope
- Never install a new dependency unless asked
- Keep changes limited to what the request's goal needs — never touch unrelated files
- Never create index.ts or a barrel file
- Never write a comment that just explains what the code already says
- Never run prisma migrate, db push, generate, or docker yourself — tell the user to run it

แต่ละกลุ่มมีเหตุผลเฉพาะของโปรเจกต์นี้ ไม่ได้ลอกมาจากเทมเพลตทั่วไป

  • Stack — บอกความจริงที่เราเห็นด้วยตาตอน scaffold ว่าโปรเจกต์เป็น ESM และ strict โมเดลภาษาโดยธรรมชาติจะเขียนโค้ด Nest แบบ CommonJS (ซึ่งเป็นตัวอย่างส่วนใหญ่บนอินเทอร์เน็ต) ประโยคนี้จึงกันปัญหาไว้ตั้งแต่ต้น ส่วนข้อ ห้าม new PrismaClient ในไฟล์อื่น มีไว้เพราะการเปิด connection pool ซ้อนกันหลายชุดคือ bug ที่ไม่แสดงอาการตอน dev แต่ล้มตอนรันจริง
  • โครงสร้างไฟล์ — หนึ่งโฟลเดอร์ต่อหนึ่ง domain ทำให้ diff ของแต่ละบทอยู่ในโฟลเดอร์เดียวและอ่านจบได้ ส่วนบรรทัด docs/api-spec.md เป็นหัวใจ: มันบอก Cursor ว่า แหล่งความจริงเรื่องรูปทรง response ไม่ใช่ความรู้ของมัน แต่เป็นไฟล์ในโปรเจกต์ และบรรทัด src/generated/prisma/ กัน AI ไม่ให้ "แก้ type error" ด้วยการไปแก้โค้ดที่ generate มา
  • กติกาการเขียนโค้ด — สามข้อแรกคือรอยแผลจาก Nest 12 + TS 6 โดยตรง: import ไม่ลงท้าย .js จะพังตอนรัน (ไม่ใช่ตอน compile), import type จำเป็นเพราะ isolatedModules ทำงานร่วมกับ decorator ที่ต้องมี metadata ของ type จริงตอน runtime และการห้าม any / as / ! ปิดทางออกที่ AI ชอบใช้ที่สุดเมื่อมัน compile ไม่ผ่าน — เราต้องการโค้ดที่ถูก ไม่ใช่โค้ดที่เงียบ ส่วนข้อสุดท้ายเรื่อง Date/Decimal มาจากสัญญาใน docs/api-spec.md ที่ระบุว่าวันเวลาเป็น string และตัวเลขเป็น number
  • ขอบเขต — สามข้อแรกคุมขนาดของ diff ข้อ barrel file กัน index.ts ที่ทำให้ import สับสนใน ESM และข้อสุดท้ายสำคัญที่สุดในคอร์สนี้: ห้ามรัน migrate, db push, generate หรือ docker เอง เพราะคำสั่งเหล่านั้นแตะฐานข้อมูลจริง และ prisma migrate reset ที่หลุดมาหนึ่งครั้งคือข้อมูล seed ทั้งหมดหายไป เราจะรันคำสั่งพวกนี้ด้วยมือเองเสมอ

แม่แบบ Prompt สามส่วน

ทุก prompt ในคอร์สนี้มีรูปเดียวกัน ต่อยอดจากแม่แบบใน React E-commerce + Cursor AI — Prompt สำหรับ Codebase และวงจรตรวจงาน แต่ต่างกันตรงที่คอร์สนี้ไม่สั่งว่าโค้ดต้องหน้าตาอย่างไร (ชื่อ method, signature, query ที่ใช้ หรือไฟล์ใหม่ต้องไปวางตรงไหน) — เราบอกแค่ว่าต้องได้ผลลัพธ์อะไรและวัดได้อย่างไร แล้วปล่อยให้ Cursor Agent อ่านโปรเจกต์ เลือกที่วางไฟล์ และเลือกวิธีเขียนเอง จำโครงนี้ไว้แล้วใช้ต่อในโปรเจกต์ของตัวเองได้เลย

<เป้าหมายหนึ่งบรรทัด เขียนเป็นประโยคคำสั่ง> <ใส่บรรทัดนี้เฉพาะบทที่แก้ของเดิม: @<ไฟล์ที่มีอยู่แล้วและต้องถูกแก้>> ผลลัพธ์ที่ต้องได้: - <พฤติกรรมที่วัดได้จากภายนอก: request นี้ → status + รูปทรง response ตาม docs/api-spec.md> - <กรณีพัง: input ผิด → status + ข้อความ error ที่ต้องตรงตัวอักษร> ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ (ยกเว้นตัวที่บทนั้นระบุ) - ยังไม่ต้อง <สิ่งที่เป็นงานของบทถัดไป>

เป้าหมาย (บรรทัดแรก) — หนึ่งประโยค เป็นคำสั่ง เช่น "สร้าง endpoint GET /products/categories" ถ้าเขียนได้ไม่จบในหนึ่งประโยค แปลว่าบทนี้ใหญ่เกินไปและควรแยกเป็นสอง prompt ประโยคนี้ยังเป็นเกณฑ์ตัดสินตอนรีวิวด้วย: อะไรที่ AI ทำเกินจากประโยคนี้คือของที่ต้องเอาออก

ผลลัพธ์ที่ต้องได้ — ส่วนที่มาแทนการสั่งว่าโค้ดต้องหน้าตาอย่างไรและต้องอยู่ไฟล์ไหน เขียนเป็นพฤติกรรมที่วัดได้จากภายนอก เช่น "GET /products/9999 ตอบ 404 และ message เป็น Product 9999 not found" หรือ "GET /products/abc ตอบ 400" ไม่ใช่ "ใช้ findUnique" หรือ "handler ชื่อ findOne" ส่วนใหญ่ลอกมาจากสัญญาใน docs/api-spec.md ได้เลย และมันคือ checklist เดียวกับที่คุณใช้ยิง curl ตอนตรวจงาน — Cursor จะเขียนวิธีไหนก็ได้ ขอแค่ผ่านทุกข้อในส่วนนี้

บรรทัด @ไฟล์ (ใส่เมื่อจำเป็น) — เอกสารของ Cursor แนะนำว่า ให้ @-mention เมื่อคุณรู้อยู่แล้วว่าไฟล์ไหนเกี่ยวข้อง ถ้าไม่รู้ให้ข้ามไป เพราะ Agent ค้นเองได้ และการแท็กไฟล์มั่ว ๆ ทุกไฟล์กลับทำให้ผลแย่ลงเพราะกลายเป็น noise กติกาของคอร์สนี้จึงเป็น: บทที่แก้ของเดิมให้ @-mention เฉพาะไฟล์ที่ต้องถูกแก้จริง ๆ ส่วนบทที่สร้างของใหม่ไม่ต้องใส่เลย ให้ Cursor เลือกที่วางไฟล์เอง

ทำไมไม่มีส่วน บริบท ยาว ๆ หรือส่วน โครงสร้าง ไฟล์? เพราะไฟล์ .cursor/rules/project.mdc ถูกแนบไปกับทุกคำขออยู่แล้ว (รวมถึงบรรทัดที่ชี้ไปที่ docs/api-spec.md) และ Cursor Agent ค้นโค้ดในโปรเจกต์เองได้ว่ามีอะไรอยู่แล้ว แนวทางเรื่อง context engineering ของ Anthropic สรุปเป้าหมายไว้ว่าให้หา "ชุด token ที่สัญญาณแรงที่สุดในจำนวนที่น้อยที่สุด" ไม่ใช่ยัดทุกอย่างที่นึกออกลงไป ถ้ามีการตัดสินใจที่โปรเจกต์ยังบอกเองไม่ได้ (เช่นข้อความ error ที่ต้องตรงตัวอักษร หรือปัดทศนิยมสองตำแหน่ง) ให้เขียนเป็นข้อหนึ่งในผลลัพธ์ที่ต้องได้ ชื่อไฟล์ที่เห็นในโค้ดอ้างอิงของแต่ละบทจึงเป็นแค่ตัวอย่าง ของคุณอาจต่างออกไปได้

ขอบเขต — บอกสิ่งที่ ห้าม ทำ ข้อห้ามที่เขียนไว้ใน .cursor/rules แล้ว (เช่น ห้ามสร้าง index.ts / barrel, ห้ามแตะไฟล์ที่ไม่เกี่ยวกับเป้าหมาย) ไม่ต้องเขียนซ้ำใน prompt บรรทัดที่สำคัญที่สุดคือ "ยังไม่ต้อง…" ซึ่งกันงานของบทถัดไปไม่ให้ถูกทำล่วงหน้า เช่นในขั้นที่เปิด endpoint แรก เราเขียน "ยังไม่ต้องแปลงแถวเป็นรูปทรงของ Product ใน docs/api-spec.md" เพราะนั่นคืองานของขั้นถัดไป ถ้าไม่เขียน AI จะทำทั้งสองบทรวดเดียว แล้วคุณจะเสียโอกาสตรวจแต่ละส่วนแยกกัน

วงจรตรวจงาน

หลังกด send แล้ว Cursor แก้ไฟล์เสร็จ อย่ารีบ commit ให้เดินเจ็ดขั้นนี้ทุกครั้ง จนจำได้เอง

  1. อ่าน diff ในแผงรีวิวของ Cursor ทีละไฟล์ — ไฟล์ที่ไม่เกี่ยวกับเป้าหมายของ prompt เลยคือสัญญาณผิดข้อแรก (เทียบกับ git status ได้ด้วย)
  2. npm run build — ให้ TypeScript ตรวจ ผ่านตรงนี้หมายความว่า import ลงท้าย .js ถูก และไม่มี type ที่หายไป
  3. npm run lint — oxlint จับของที่ compile ผ่านแต่ไม่ควรอยู่ เช่นตัวแปรที่ไม่ได้ใช้
  4. ดู log ของ dev server ว่ามีบรรทัด Mapped {…} route ของ endpoint ที่เพิ่งสร้างขึ้นมาจริง — ถ้าไม่มี แปลว่า controller ยังไม่ถูกลงทะเบียนใน module (เป็นความผิดที่ build ไม่ฟ้อง)
  5. curl ยิง endpoint นั้นด้วยข้อมูลจริง ทั้งกรณีปกติและกรณีพัง (id ที่ไม่มี, หมวดที่ไม่มี)
  6. เทียบ response กับส่วน "ผลลัพธ์ที่ต้องได้" ของ prompt และสัญญาใน docs/api-spec.md — ชื่อ field ครบไหม, ตัวเลขเป็น number ไม่ใช่ string ไหม, status code ตรงไหม
  7. ถามตัวเองว่า "อธิบายได้ไหม" ทุกบรรทัดที่เพิ่มเข้ามา ถ้ามีบรรทัดที่ตอบไม่ได้ ให้ถาม Cursor ว่าบรรทัดนั้นทำอะไรและทำไมต้องมี แล้วอ่านคำตอบเทียบกับเอกสารจริง เสร็จแล้วจึง git add -A && git commit หรือถ้าไม่ผ่าน ให้ git checkout -- . แล้วส่ง prompt ใหม่ที่เติมผลลัพธ์ที่ขาดไปลงในส่วนผลลัพธ์ที่ต้องได้

เส้นแบ่งระหว่าง refine กับ revert: ถ้าโค้ดอยู่ถูกที่แล้วแต่ยังไม่ผ่านผลลัพธ์ที่ต้องได้ข้อเดียว (ลืมโยน NotFoundException, ลืมตัด discountPercentage ที่เป็น null) ให้ส่ง prompt ต่อท้ายสั้น ๆ ในแชทเดิม แต่ถ้าแก้ไฟล์ที่ไม่เกี่ยวข้อง หรือมีของแถมมาเยอะ ให้ git checkout -- . (และ git clean -fd ถ้ามีไฟล์ใหม่) แล้วเริ่มแชทใหม่ — การแก้โครงสร้างที่ผิดด้วยการต่อ prompt มักได้โค้ดที่ทั้งผิดและซ้อนกันหลายชั้น

เขียนไฟล์ rules ด้วยมือแล้ว commit

สร้างโฟลเดอร์และไฟล์ตามนี้ แล้ว พิมพ์ เนื้อหาจากบล็อกด้านบนลงไปเอง (อย่า copy ทั้งก้อนโดยไม่อ่าน — กติกาที่คุณไม่ได้อ่านคือกติกาที่คุณจะไม่ตรวจ) จากนั้นเปิด Cursor ที่โฟลเดอร์ ecommerce-api แล้ว commit

mkdir -p .cursor/rules # สร้างไฟล์ .cursor/rules/project.mdc แล้วพิมพ์เนื้อหาตามบทเรียน git add .cursor git commit -m "chore: add cursor rules"

เสร็จแล้วลองถาม Cursor ด้วยแชทโหมด Ask (ไม่ใช่ Agent) เพื่อทดสอบว่า rules ถูกอ่านจริง คำถามสั้น ๆ หนึ่งข้อ: โปรเจกต์นี้ import ไฟล์อย่างไร

ผลลัพธ์ที่คาดหวัง

Cursor Settings → Rules แสดงไฟล์ project.mdc พร้อมป้าย Always (มาจาก alwaysApply: true ใน frontmatter) และคำตอบของแชท Ask ต้องบอกว่า import ไฟล์ในโปรเจกต์ต้องลงท้ายด้วย .js แม้ไฟล์จริงเป็น .ts — ถ้ามันตอบแบบทั่ว ๆ ไปโดยไม่พูดถึง .js แปลว่าไฟล์ยังไม่ถูกอ่าน (มักเป็นเพราะวางไฟล์ผิดที่ หรือเปิด Cursor ที่โฟลเดอร์แม่ ไม่ใช่ที่ ecommerce-api)

ตอนนี้ git log --oneline มีสาม commit: scaffold, api-spec.md และ rules — โปรเจกต์พร้อมสำหรับ prompt แรกจริงในขั้นถัดไป

ตรวจว่าใช้งานได้จริง

  • head -4 .cursor/rules/project.mdc เห็น frontmatter ที่มี alwaysApply: true คร่อมด้วย --- ทั้งบนและล่าง
  • Cursor Settings → Rules แสดง project.mdc เป็น Always
  • แชท Ask คำถาม โปรเจกต์นี้ import ไฟล์อย่างไร ได้คำตอบที่พูดถึงนามสกุล .js
  • git log --oneline มีสาม commit และ git status สะอาด
