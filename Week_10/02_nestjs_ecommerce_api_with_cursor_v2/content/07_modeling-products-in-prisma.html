เมื่อจบบทนี้ คุณจะสามารถ

  • อ่าน interface ใน docs/api-spec.md แล้วแปลงเป็นคอลัมน์ของ Prisma ได้ทีละ field
  • อธิบายได้ว่าทำไมใช้ Float ไม่ใช่ Decimal และทำไม Product.id ไม่มี autoincrement()
  • แตก object ซ้อน (dimensions, meta) และ array ของ object (reviews) ออกเป็นคอลัมน์และ relation

ต้นแบบไม่ใช่จินตนาการ แต่เป็นไฟล์ใน docs/api-spec.md

ก่อนหน้านี้เราอ่านโค้ดฝั่ง client แล้วเขียนสัญญาไว้ใน docs/api-spec.md แล้ว บทนี้เราจะไม่เดาว่าสินค้า ควร มี field อะไร แต่เปิด docs/api-spec.md แล้วไล่ทุก field ในหัวข้อ Product ที่มันระบุ — เพราะเป้าหมายของคอร์สนี้คือ API ที่ตอบตรงกับสิ่งที่ React app ต้องการจริง ถ้าฐานข้อมูลเก็บ field ไม่ครบ response ก็จะขาด และ React app จะแสดงผลเพี้ยน

Float ไม่ใช่ Decimal — เพราะ contract ต้องเป็นตัวเลข

ปกติหนังสือเรื่องฐานข้อมูลจะสอนว่าราคาสินค้าควรใช้ชนิด Decimal เพื่อไม่ให้เกิดความคลาดเคลื่อนของ floating point และนั่นถูกต้องสำหรับระบบบัญชี แต่โปรเจกต์นี้มีข้อผูกมัดที่แรงกว่า: Prisma แปลงค่า Decimal ออกมาเป็น string ใน JSON (เพื่อรักษาความแม่นยำ) ดังนั้น response จะกลายเป็น "price": "9.99" ขณะที่ docs/api-spec.md ประกาศ price: number ไว้ชัดเจน (ตรงกับที่ client เขียนไว้ใน src/features/products/types.ts) — React app ที่เอาค่าไปคูณจำนวนชิ้นจะได้ผลเพี้ยนทันที เราจึงเลือก Float ซึ่งออกมาเป็น number ตรงตาม contract

กติกาในไฟล์ .cursor/rules/project.mdc ของเราเขียนไว้ว่า response ต้องเป็น JSON ธรรมดา ห้ามส่ง Date object หรือ Decimal ออกไปโดยไม่แปลง — บทนี้คือตัวอย่างว่ากฎข้อนั้นมีผลถึงการออกแบบตาราง ไม่ใช่แค่ชั้น controller

ทำไม Product.id ไม่มี autoincrement()

ตัวอย่าง cart-add ที่ใช้เป็นเคสทำงานตลอดขั้นสั่งซื้อ และเกณฑ์ตรวจ มี 22 key ตอนแปลงแถวเป็นรูปทรงตามสัญญา ต่างอ้างถึงสินค้า id 1 ด้วยเลขเจาะจงตรง ๆ ถ้าเราปล่อยให้ PostgreSQL แจก id เองด้วย autoincrement() การ seed ซ้ำแต่ละรอบอาจสลับลำดับแถว แล้ว id 1 ของรอบนี้กับรอบหน้าอาจไม่ใช่สินค้าชิ้นเดียวกัน ทำให้ตัวอย่างและเกณฑ์ตรวจที่ผูกกับเลขนั้นพังแบบเงียบ ๆ เราจึงประกาศ id Int @id เฉย ๆ (ไม่ใส่ autoincrement()) แล้วกำหนด id ให้ตรงกันทุกครั้งตอน seed เอง — นี่คือสิ่งที่ทำให้เลข id คงที่ไม่ว่าจะ reseed กี่รอบ ตรงกันข้าม Category.id และ Review.id ใช้ @default(autoincrement()) ได้สบาย เพราะไม่มีใครอ้างอิงเลขสองตัวนั้นจากนอกระบบ — หมวดหมู่ถูกอ้างด้วย slug เท่านั้น

ทำไมไม่เก็บ dimensions/meta/reviews เป็นคอลัมน์ Json

PostgreSQL เก็บ JSON ได้ และ Prisma ก็มีชนิด Json ให้ใช้ ทางนั้นสั้นกว่าจริง แต่เราไม่เอา ด้วยเหตุผลสามข้อ

  • ค้นและ index ลำบาก — GET /products/category/:slug ต้องกรองตามหมวดหมู่ ถ้าหมวดหมู่ฝังอยู่ใน JSON เราจะ index ตรง ๆ แบบ @@index([categoryId]) ไม่ได้
  • ฐานข้อมูลไม่ช่วยตรวจ — คอลัมน์ Json รับอะไรเข้าไปก็ได้ พิมพ์ widht ผิดก็ยังบันทึกผ่าน แต่คอลัมน์ width Float จะปฏิเสธทันที
  • เราอยากได้ relation จริง — Review เป็นตารางลูกทำให้ฝึกสิ่งที่เรียนมาใน NestJS Fundamentals บทสร้าง Relation ระหว่างสอง Models ต่อได้ และ onDelete: Cascade ทำให้ลบสินค้าแล้วรีวิวหายตามเองโดยไม่ต้องเขียนโค้ดลบ

ส่วน @@index([categoryId]) และ @@index([productId]) ที่เราใส่ไว้คือเหตุผลเดียวกับ NestJS Fundamentals บทเพิ่ม Indexes ให้ Models: คอลัมน์ที่ถูกใช้เป็นเงื่อนไข where บ่อย ๆ ควรมี index — ที่นี่คือทุกครั้งที่ดึงสินค้าตามหมวด หรือดึงรีวิวของสินค้าหนึ่งชิ้น

ให้ Cursor เขียน schema จาก docs/api-spec.md

commit งานก่อน แล้วเปิดแชทใหม่ใน Cursor โหมด Agent สังเกตว่า prompt นี้แนบแค่ @prisma/schema.prisma ซึ่งเป็นไฟล์เดิมที่ต้องถูกแก้ แต่ไม่ต้องแนบ @docs/api-spec.md — บรรทัดเป้าหมายชี้ไปที่ไฟล์นั้นตรง ๆ และ .cursor/rules บอก Cursor ไว้แล้วว่ามันคือสัญญา นั่นคือหัวใจ: เราไม่ได้ให้ AI เดารูปทรงของสินค้า แต่ให้มันอ่าน interface Product และ Category ที่เราออกแบบเองจากโค้ดฝั่ง client

เพิ่ม Prisma model ของ Category, Product และ Review ให้ตรงกับ interface ใน docs/api-spec.md @prisma/schema.prisma ผลลัพธ์ที่ต้องได้: - npx prisma validate ได้ The schema at prisma/schema.prisma is valid 🚀 และ npx prisma format ไม่เปลี่ยนอะไรเพิ่ม - มีสาม model: Category, Product, Review — ไม่มี model อื่น - ทุก field ของ interface Product (ยกเว้น object ซ้อน) มีคอลัมน์ชื่อเดียวกัน dimensions และ meta แบนเป็นคอลัมน์ width, height, depth, barcode, qrCode, createdAt, updatedAt (ชื่อตาม key ใน interface เพราะขั้นต่อไปจะประกอบกลับเป็น object ซ้อนตามสัญญา) ไม่ใช้ Json - ค่าทศนิยมทุกตัวออกมาเป็น number ใน JSON (ห้าม Decimal เพราะ Prisma serialize เป็น string) - discountPercentage เป็นคอลัมน์เดียวที่ nullable ส่วน brand บังคับมีค่า - id ของ Product ไม่ถูกฐานข้อมูลแจกให้เอง และ createdAt/updatedAt ไม่มีค่า default หรืออัปเดตเอง (seed script กำหนดค่าเหล่านี้เอง) - Category.slug ไม่ซ้ำกัน และไม่เก็บ url (url คำนวณจาก slug) - ลบสินค้าแล้วรีวิวของมันหายตาม แต่ลบหมวดหมู่ที่ยังมีสินค้าไม่ได้ - คอลัมน์ที่ใช้ดึงสินค้าตามหมวดและดึงรีวิวตามสินค้ามี index - บล็อก generator และ datasource ไม่เปลี่ยนเลย ขอบเขต: - ห้ามรัน prisma migrate, db push หรือ generate ให้ผมรันเอง - ยังไม่ต้องเขียน seed หรือ service

เมื่อ Agent แก้ไฟล์เสร็จ ตรวจตามหัวข้อถัดไป แล้วรันสองคำสั่งนี้เอง (ยังไม่ migrate — ขั้นถัดไปค่อยทำ)

ตรวจโค้ดที่ AI สร้าง

  • id ของ Product ไม่ถูกฐานข้อมูลแจกเอง — seed script ต้องกำหนดได้
  • discountPercentage เป็น field เดียวในทั้งสาม model ที่ nullable ส่วน brand บังคับมีค่า
  • createdAt/updatedAt ไม่มีค่า default และไม่อัปเดตตัวเอง — ค่าทั้งคู่ต้องมาจาก seed script
  • ลบสินค้าแล้วรีวิวหายตาม แต่ลบหมวดหมู่ที่ยังมีสินค้าอยู่ไม่ได้
  • คอลัมน์ที่ใช้ดึงสินค้าตามหมวดและดึงรีวิวตามสินค้ามี index
  • ไม่มีชนิด Decimal หรือ Json ในไฟล์เลย
  • บล็อก generator client และ datasource db ยังเหมือนเดิม ไม่มี model แถมมา (เช่น User, Order) และ git status เห็นแค่ prisma/schema.prisma
  • ทุก field ของ Product มีอยู่จริงใน interface Product ของ docs/api-spec.md — ไล่เทียบทีละบรรทัด ไม่ใช่ไล่ด้วยความรู้สึก

AI มักพลาดตรงนี้: ใส่ @updatedAt ให้ updatedAt เพราะเป็นแบบแผนที่พบเจอทั่วไป (ผลคือค่าที่ seed script กำหนดไว้จะถูกเขียนทับด้วยเวลาปัจจุบันทุกครั้งที่แถวถูก update) หรือเลือก Decimal ให้ price ตามตำราบัญชี ซึ่งทำให้ราคาถูกส่งออกไปเป็น string และผิด contract ทันที

โค้ดอ้างอิงของบทนี้ — เป็นหนึ่งในวิธีที่ถูก ของคุณไม่จำเป็นต้องเหมือนทุกบรรทัด ขอแค่ผ่านผลลัพธ์ที่ต้องได้:

// prisma/schema.prisma
generator client {
  provider = "prisma-client"
  output   = "../src/generated/prisma"
}

datasource db {
  provider = "postgresql"
}

model Category {
  id       Int       @id @default(autoincrement())
  slug     String    @unique
  name     String
  products Product[]
}

model Product {
  id                   Int      @id
  title                String
  description          String
  price                Float
  discountPercentage   Float?
  rating               Float
  stock                Int
  tags                 String[]
  brand                String
  sku                  String
  weight               Float
  width                Float
  height               Float
  depth                Float
  warrantyInformation  String
  shippingInformation  String
  availabilityStatus   String
  returnPolicy         String
  minimumOrderQuantity Int
  barcode              String
  qrCode               String
  images               String[]
  thumbnail            String
  createdAt            DateTime
  updatedAt            DateTime
  categoryId           Int
  category             Category @relation(fields: [categoryId], references: [id])
  reviews              Review[]

  @@index([categoryId])
}

model Review {
  id            Int      @id @default(autoincrement())
  rating        Int
  comment       String
  date          DateTime
  reviewerName  String
  reviewerEmail String
  productId     Int
  product       Product  @relation(fields: [productId], references: [id], onDelete: Cascade)

  @@index([productId])
}

brand เปลี่ยนเป็นบังคับมีค่า (String ไม่มี ?) เพราะแคตตาล็อกของเราเองกำหนดยี่ห้อให้สินค้าทุกชิ้นเสมอ ส่วน discountPercentage เปลี่ยนเป็น nullable (Float?) เพราะสินค้าบางชิ้นในข้อมูล seed ของเราไม่มีส่วนลด และฝั่ง client ก็ประกาศ discountPercentage?: number ไว้ใน src/features/products/types.ts อยู่แล้ว — schema ของเราแค่ตรงกับสิ่งที่ client คาดหวังจริง ๆ

ถ้าอธิบายบรรทัดไหนไม่ได้ ยังไม่ผ่านบทนี้ — กลับไปอ่านส่วนแนวคิดก่อน
