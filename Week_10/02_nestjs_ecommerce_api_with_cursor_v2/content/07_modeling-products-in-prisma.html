ออกแบบ Prisma Model ของสินค้า

เมื่อจบบทนี้ คุณจะสามารถ

  • อ่าน payload จริงของ dummyjson แล้วแปลงเป็นคอลัมน์ของ Prisma ได้ทีละ field
  • อธิบายได้ว่าทำไมใช้ Float ไม่ใช่ Decimal และทำไม Product.id ไม่มี autoincrement()
  • แตก object ซ้อน (dimensions, meta) และ array ของ object (reviews) ออกเป็นคอลัมน์และ relation

ต้นแบบไม่ใช่จินตนาการ แต่เป็นไฟล์ใน docs/contract

บทที่ 3 เราเก็บ response จริงของ dummyjson ไว้ใน docs/contract/ แล้ว บทนี้เราจะไม่เดาว่าสินค้า ควร มี field อะไร แต่เปิด docs/contract/product-1.json แล้วไล่ทุก key ที่มันมี — เพราะเป้าหมายของคอร์สนี้คือ API ที่สลับแทน dummyjson ได้โดย React app ไม่รู้ตัว ถ้าฐานข้อมูลเก็บ field ไม่ครบ response ก็จะขาด และ React app จะแสดงผลเพี้ยน

Float ไม่ใช่ Decimal — เพราะ contract ต้องเป็นตัวเลข

ปกติหนังสือเรื่องฐานข้อมูลจะสอนว่าราคาสินค้าควรใช้ชนิด Decimal เพื่อไม่ให้เกิดความคลาดเคลื่อนของ floating point และนั่นถูกต้องสำหรับระบบบัญชี แต่โปรเจกต์นี้มีข้อผูกมัดที่แรงกว่า: Prisma แปลงค่า Decimal ออกมาเป็น string ใน JSON (เพื่อรักษาความแม่นยำ) ดังนั้น response จะกลายเป็น "price": "9.99" ขณะที่ dummyjson ส่ง "price": 9.99 — React app ที่เอาค่าไปคูณจำนวนชิ้นจะได้ผลเพี้ยนทันที เราจึงเลือก Float ซึ่งออกมาเป็น number ตรงตาม contract

กติกาในไฟล์ .cursor/rules/project.mdc ของเราเขียนไว้ว่า response ต้องเป็น JSON ธรรมดา ห้ามส่ง Date object หรือ Decimal ออกไปโดยไม่แปลง — บทนี้คือตัวอย่างว่ากฎข้อนั้นมีผลถึงการออกแบบตาราง ไม่ใช่แค่ชั้น controller

ทำไม Product.id ไม่มี autoincrement()

React app ลิงก์ไปหน้าสินค้าด้วย id ตรง ๆ (/products/1) และ docs/contract/product-1.json คือของสินค้า id 1 ถ้าเราให้ PostgreSQL แจก id เอง ลำดับอาจไม่ตรงกับของ dummyjson แล้วลิงก์เดิม ๆ จะชี้ไปสินค้าผิดชิ้น เราจึงประกาศ id Int @id เฉย ๆ แล้วส่ง id มาเองตอน seed (บทที่ 9) ตรงกันข้าม Category.id และ Review.id ใช้ @default(autoincrement()) ได้สบาย เพราะไม่มีใครอ้างอิงเลขสองตัวนั้นจากนอกระบบ — หมวดหมู่ถูกอ้างด้วย slug เท่านั้น

ทำไมไม่เก็บ dimensions/meta/reviews เป็นคอลัมน์ Json

PostgreSQL เก็บ JSON ได้ และ Prisma ก็มีชนิด Json ให้ใช้ ทางนั้นสั้นกว่าจริง แต่เราไม่เอา ด้วยเหตุผลสามข้อ

  • ค้นและ index ลำบาก — GET /products/category/:slug ในบทที่ 14 ต้องกรองตามหมวดหมู่ ถ้าหมวดหมู่ฝังอยู่ใน JSON เราจะ index ตรง ๆ แบบ @@index([categoryId]) ไม่ได้
  • ฐานข้อมูลไม่ช่วยตรวจ — คอลัมน์ Json รับอะไรเข้าไปก็ได้ พิมพ์ widht ผิดก็ยังบันทึกผ่าน แต่คอลัมน์ width Float จะปฏิเสธทันที
  • เราอยากได้ relation จริง — Review เป็นตารางลูกทำให้ฝึกสิ่งที่เรียนมาใน Week_09 บทที่ 25 ต่อได้ และ onDelete: Cascade ทำให้ลบสินค้าแล้วรีวิวหายตามเองโดยไม่ต้องเขียนโค้ดลบ

ส่วน @@index([categoryId]) และ @@index([productId]) ที่เราใส่ไว้คือเหตุผลเดียวกับ Week_09 บทที่ 30: คอลัมน์ที่ถูกใช้เป็นเงื่อนไข where บ่อย ๆ ควรมี index — ที่นี่คือทุกครั้งที่ดึงสินค้าตามหมวด หรือดึงรีวิวของสินค้าหนึ่งชิ้น

ให้ Cursor เขียน schema จาก payload จริง

commit งานก่อน แล้วเปิดแชทใหม่ใน Cursor โหมด Agent สังเกตว่า prompt นี้แนบ @docs/contract/product-1.json กับ @docs/contract/categories.json ไปด้วย — นั่นคือหัวใจ: เราไม่ได้ให้ AI เดารูปทรงของสินค้า แต่ให้มันอ่านจากไฟล์สัญญาที่วางไว้ในโปรเจกต์

เพิ่ม Prisma model ของ Category, Product และ Review ให้ตรงกับ payload ของ dummyjson บริบท: @prisma/schema.prisma @docs/contract/product-1.json @docs/contract/categories.json @.cursor/rules/project.mdc schema.prisma ตอนนี้มีแค่ generator กับ datasource ห้ามแก้สองบล็อกนั้น docs/contract/product-1.json คือ response จริงของ GET https://dummyjson.com/products/1 — ทุก field ของ Product ต้องมาจากไฟล์นี้ docs/contract/categories.json คือ response จริงของ GET /products/categories แต่ละรายการมี slug, name, url — url ไม่ต้องเก็บเพราะคำนวณจาก slug ได้ สินค้าบางชิ้น (92 จาก 194) ไม่มี field brand ฐานข้อมูลคือ PostgreSQL 17 โครงสร้าง: แก้ไฟล์เดียว - prisma/schema.prisma (แก้ไข: เพิ่มสาม model ต่อท้าย) ข้อกำหนดทางเทคนิค: - model Category: id Int @id @default(autoincrement()), slug String @unique, name String, products Product[] - model Product: id Int @id (ไม่ใส่ autoincrement เพราะเราจะ seed ด้วย id เดิมของ dummyjson) field ตามลำดับนี้: title String, description String, price Float, discountPercentage Float, rating Float, stock Int, tags String[], brand String?, sku String, weight Float, width Float, height Float, depth Float, warrantyInformation String, shippingInformation String, availabilityStatus String, returnPolicy String, minimumOrderQuantity Int, barcode String, qrCode String, images String[], thumbnail String, createdAt DateTime, updatedAt DateTime (ไม่ใส่ @default หรือ @updatedAt เพราะค่ามาจาก meta ของ dummyjson) categoryId Int, category Category @relation(fields: [categoryId], references: [id]), reviews Review[] และ @@index([categoryId]) - model Review: id Int @id @default(autoincrement()), rating Int, comment String, date DateTime, reviewerName String, reviewerEmail String, productId Int, product Product @relation(fields: [productId], references: [id], onDelete: Cascade) และ @@index([productId]) - ใช้ Float สำหรับทุกค่าที่เป็นทศนิยม ห้ามใช้ Decimal (Prisma serialize Decimal เป็น string ซึ่งผิด contract) - dimensions และ meta ของ dummyjson เป็น object ซ้อน ให้แบนเป็นคอลัมน์ตามที่ระบุด้านบน ห้ามใช้ Json - ห้ามสร้าง model อื่น ห้ามใส่ @@map หรือ @map ขอบเขต: - ห้ามแก้ไฟล์อื่น - ห้ามรัน prisma migrate, db push หรือ generate ให้ผมรันเอง - ยังไม่ต้องเขียน seed หรือ service

ตรวจโค้ดที่ AI สร้าง

  • Product.id เป็น Int @id เฉย ๆ — ไม่มี @default(autoincrement())
  • brand String? เป็น field เดียวในทั้งสาม model ที่มีเครื่องหมาย ? (ค้นหา ? ในไฟล์แล้วต้องเจอที่เดียว)
  • updatedAt DateTime ไม่มี @updatedAt และ createdAt ไม่มี @default(now()) — ค่าทั้งคู่ต้องมาจาก meta ของ dummyjson
  • Review.product มี onDelete: Cascade ส่วน Product.category ไม่มี (ปล่อยเป็น restrict ตามค่าปริยาย — ห้ามลบหมวดหมู่ที่ยังมีสินค้าอยู่)
  • มี @@index([categoryId]) ใน Product และ @@index([productId]) ใน Review ครบทั้งสองตัว
  • ไม่มีคำว่า Decimal, Json, @map หรือ @@map ในไฟล์เลย
  • บล็อก generator client และ datasource db ยังเหมือนเดิมทุกตัวอักษร และไม่มี model ที่เราไม่ได้สั่ง (เช่น User, Order) แถมมา
  • ทุก field ของ Product มีอยู่จริงใน docs/contract/product-1.json — ไล่เทียบทีละบรรทัด ไม่ใช่ไล่ด้วยความรู้สึก

AI มักพลาดตรงนี้: ใส่ @updatedAt ให้ updatedAt เพราะเป็นแบบแผนที่พบเจอทั่วไป (ผลคือค่าจาก dummyjson จะถูกเขียนทับด้วยเวลาปัจจุบันทุกครั้งที่แถวถูก update) หรือเลือก Decimal ให้ price ตามตำราบัญชี ซึ่งทำให้ราคาถูกส่งออกไปเป็น string และผิด contract ทันที

โค้ดอ้างอิงของบทนี้ (เทียบกับของคุณทีละบรรทัด):

// prisma/schema.prisma
generator client {
  provider = "prisma-client"
  output   = "../src/generated/prisma"
}

datasource db {
  provider = "postgresql"
}

model Category {
  id       Int       @id @default(autoincrement())
  slug     String    @unique
  name     String
  products Product[]
}

model Product {
  id                   Int      @id
  title                String
  description          String
  price                Float
  discountPercentage   Float
  rating               Float
  stock                Int
  tags                 String[]
  brand                String?
  sku                  String
  weight               Float
  width                Float
  height               Float
  depth                Float
  warrantyInformation  String
  shippingInformation  String
  availabilityStatus   String
  returnPolicy         String
  minimumOrderQuantity Int
  barcode              String
  qrCode               String
  images               String[]
  thumbnail            String
  createdAt            DateTime
  updatedAt            DateTime
  categoryId           Int
  category             Category @relation(fields: [categoryId], references: [id])
  reviews              Review[]

  @@index([categoryId])
}

model Review {
  id            Int      @id @default(autoincrement())
  rating        Int
  comment       String
  date          DateTime
  reviewerName  String
  reviewerEmail String
  productId     Int
  product       Product  @relation(fields: [productId], references: [id], onDelete: Cascade)

  @@index([productId])
}

ตรวจว่าใช้งานได้จริง

  • npx prisma validate ได้ The schema at prisma/schema.prisma is valid 🚀
  • npx prisma format แล้ว git diff prisma/schema.prisma ไม่มีบรรทัดที่เปลี่ยนเพิ่มจากของที่ AI เขียน
