แปลงแถวจากฐานข้อมูลเป็นรูปทรงของ dummyjson

เมื่อจบบทนี้ คุณจะสามารถ

  • อธิบายความต่างระหว่าง รูปทรงที่เก็บ (แถวใน Postgres) กับ รูปทรงที่ตอบ (JSON ของ dummyjson) ได้ทีละคีย์
  • เขียน mapper บริสุทธิ์ที่เป็นที่เดียวในโปรเจกต์ที่รู้จักทั้งสองรูปทรง
  • จัดการคีย์ที่ต้องหายไปทั้งคีย์ (ไม่ใช่เป็น null) ด้วย conditional spread ได้อย่างถูก type

สองรูปทรงที่ไม่เหมือนกัน และไม่ควรทำให้เหมือนกัน

ฐานข้อมูลกับ API มีเป้าหมายต่างกัน ตารางอยากได้คอลัมน์แบน ๆ ที่ index ได้ ส่วน client อยากได้ JSON ที่อ่านง่ายและซ้อนเป็นชั้น ลองดูจุดที่ทั้งสองไม่ตรงกันใน schema.prisma ของเรา

ในฐานข้อมูลใน contract ของ dummyjsonงานที่ mapper ต้องทำ
คอลัมน์ width, height, depthobject dimensions { width, height, depth }ห่อสามคอลัมน์เป็น object เดียว
คอลัมน์ barcode, qrCode, createdAt, updatedAtobject meta { createdAt, updatedAt, barcode, qrCode }ห่อสี่คอลัมน์เป็น meta
categoryId + relation category (ทั้ง object)category เป็น string เช่น "beauty"ดึงแค่ category.slug ออกมา
DateTime → JavaScript DateISO string เช่น "2025-04-30T09:41:02.053Z"เรียก .toISOString() ทั้งสามจุด
brand String? → ค่า null ได้ถ้าไม่มี brand จะไม่มีคีย์ brand เลยใส่คีย์เฉพาะเมื่อไม่ใช่ null
Review มี id และ productIdreview มีเพียงห้าคีย์เลือกเฉพาะห้าคีย์ ตัด id/productId ออก

ถ้าเราปล่อยให้แต่ละ endpoint แปลงเอง ความรู้เรื่อง 22 คีย์นี้จะกระจายไปทั้งโปรเจกต์ แล้ววันหนึ่งจะมี endpoint ที่ลืมแปลง date เราจึงรวบไว้ที่ฟังก์ชันเดียวชื่อ toProductResponse

ทำไม mapper ต้องเป็นฟังก์ชันบริสุทธิ์ ไม่ใช่ method ใน service

toProductResponse(product) รับค่าเข้า คืนค่าออก ไม่แตะฐานข้อมูล ไม่แตะ config ไม่มี state — เรียก export function ธรรมดาก็พอ ไม่ต้อง @Injectable() ผลที่ได้คือ

  • เทสได้โดยไม่ต้องยก Nest ขึ้นมาเลย: ประกอบ object เข้าไปตรง ๆ แล้วเทียบผลลัพธ์ ไม่ต้องมี Test.createTestingModule ไม่ต้องมีฐานข้อมูล
  • ทุก endpoint ที่คืนสินค้า (บทที่ 12, 13, 14) เรียกฟังก์ชันเดียวกัน จึงตอบรูปทรงเดียวกันแน่นอน
  • เวลา contract เปลี่ยน มีที่เดียวที่ต้องแก้

ทำไมใช้ class ไม่ใช่ interface สำหรับ response DTO

interface หายไปตอน compile จึงไม่เหลือข้อมูลอะไรให้ tool อ่านตอน runtime ในบทที่ 21 เราจะเปิด Swagger CLI plugin ซึ่งอ่าน field ของ class เพื่อสร้าง schema ของเอกสาร API ให้อัตโนมัติ ถ้าเราประกาศเป็น interface ไว้ตอนนี้ ก็ต้องมาเขียนใหม่ทั้งหมดในบทนั้น

ข้อกังวลปกติของการใช้ class คือ TypeScript จะบ่นว่า field ไม่ถูก assign ใน constructor (strictPropertyInitialization) แต่ tsconfig.json ของ scaffold Nest 12 ตั้ง "strictPropertyInitialization": false ไว้ให้แล้ว ดังนั้นการประกาศเปล่า ๆ แบบ title: string; จึง compile ผ่าน โดยที่ "strict": true ยังเปิดอยู่ตามปกติ

คีย์ที่ต้องหายไปทั้งคีย์: conditional spread

dummyjson ไม่ส่ง "brand": null มา — มันไม่ส่งคีย์ brand มาเลยสำหรับสินค้าที่ไม่มีแบรนด์ นี่คือความต่างที่ diff จับได้ วิธีที่เราใช้คือ spread แบบมีเงื่อนไข

...(product.brand !== null ? { brand: product.brand } : {}),

ถ้าเงื่อนไขเป็นเท็จ เรา spread object ว่าง คีย์จึงไม่เกิดขึ้นเลย ทั้งใน object จริงและใน type ที่ TypeScript อนุมาน

ทางเลือกที่ดูสั้นกว่าคือ brand: product.brand ?? undefined — ผล JSON เหมือนกัน เพราะ JSON.stringify ตัดคีย์ที่เป็น undefined ทิ้งอยู่แล้ว แต่มันเปิดช่องให้เขียน type ของ DTO เป็น brand: string | null ตามไปด้วย ซึ่งจะกลายเป็นการประกาศว่า API ของเราส่ง null ได้ (ทั้งที่ไม่เคยส่ง) เราจึงเลือก spread แบบมีเงื่อนไข คู่กับ DTO ที่ประกาศ brand?: string — ? ตัวเดียวในไฟล์ทั้งไฟล์

type ของแถวที่มี relation ติดมาด้วย

Product ที่ Prisma export ให้คือแถวเปล่า ๆ ของตาราง Product เท่านั้น — ไม่มี category ไม่มี reviews ค่าพวกนี้จะติดมาเฉพาะเมื่อ query สั่ง include เราจึงประกาศ type ของ input ให้ตรงกับที่สั่ง

export type ProductWithRelations = Product & { category: Category; reviews: Review[] };

type สามตัวนี้มาจาก Prisma Client ที่เรา generate ไว้ที่ src/generated/prisma/client.ts (ตามที่ตั้ง output ไว้ใน schema.prisma) ไฟล์นั้น export Product, Category, Review ให้พร้อมใช้ และเราเรียกด้วย import type เพราะต้องการเฉพาะ type ไม่ต้องการโค้ดตอน runtime

ตรวจโค้ดที่ AI สร้าง

  • ใน DTO มีหกคลาสครบ และมีเครื่องหมาย ? เพียงจุดเดียวคือ brand?: string — ค้นหาคำว่า null ในไฟล์นี้ ต้องไม่เจอเลย
  • ProductResponseDto มี 22 field เรียงตามลำดับของ contract (นับเทียบกับ docs/contract/product-1.json ทีละบรรทัด)
  • type ของ model นำเข้าด้วย import type ไม่ใช่ import ธรรมดา และ path ลงท้าย .js
  • brand ใช้ conditional spread ไม่ใช่ ?? undefined หรือ || ''
  • เรียก .toISOString() ครบสามจุด: review.date, product.createdAt, product.updatedAt — และไม่มี Date object ไหนหลุดออกไปเป็น field
  • object ของ review ที่ map ออกมามีห้าคีย์เท่านั้น ไม่มี id ไม่มี productId
  • npm run build ผ่าน และในไฟล์ทั้งสองไม่มีคำว่า any หรือ as

AI มักพลาดตรงนี้: เขียน brand: product.brand ?? undefined — runtime ยังถูก (JSON ตัด undefined ทิ้ง) แต่เมื่อเขียนแบบนี้ Cursor มักไปประกาศใน DTO เป็น brand: string | null หรือ brand: string | undefined ตามด้วย ให้เปิด DTO เช็กเสมอ อีกข้อที่พลาดบ่อยคือ category: product.category (ยัด object ทั้งก้อนเข้าไป) แทนที่จะเป็น product.category.slug — TypeScript จะฟ้องให้ ถ้า DTO ประกาศ category: string ไว้ถูก ซึ่งเป็นอีกเหตุผลที่เราเขียน DTO ก่อน mapper

src/products/product.mapper.ts

import type { Category, Product, Review } from '../generated/prisma/client.js';
import { ProductResponseDto } from './dto/product-response.dto.js';

export type ProductWithRelations = Product & { category: Category; reviews: Review[] };

export function toProductResponse(product: ProductWithRelations): ProductResponseDto {
  return {
    id: product.id,
    title: product.title,
    description: product.description,
    category: product.category.slug,
    price: product.price,
    discountPercentage: product.discountPercentage,
    rating: product.rating,
    stock: product.stock,
    tags: product.tags,
    ...(product.brand !== null ? { brand: product.brand } : {}),
    sku: product.sku,
    weight: product.weight,
    dimensions: { width: product.width, height: product.height, depth: product.depth },
    warrantyInformation: product.warrantyInformation,
    shippingInformation: product.shippingInformation,
    availabilityStatus: product.availabilityStatus,
    reviews: product.reviews.map((review) => ({
      rating: review.rating,
      comment: review.comment,
      date: review.date.toISOString(),
      reviewerName: review.reviewerName,
      reviewerEmail: review.reviewerEmail,
    })),
    returnPolicy: product.returnPolicy,
    minimumOrderQuantity: product.minimumOrderQuantity,
    meta: {
      createdAt: product.createdAt.toISOString(),
      updatedAt: product.updatedAt.toISOString(),
      barcode: product.barcode,
      qrCode: product.qrCode,
    },
    images: product.images,
    thumbnail: product.thumbnail,
  };
}

ถ้าอธิบายบรรทัดไหนไม่ได้ ยังไม่ผ่านบทนี้ — กลับไปอ่านส่วนแนวคิดก่อน

ผลลัพธ์ที่คาดหวัง

มีไฟล์ใหม่สองไฟล์ และ npm run build จบด้วย exit 0 โดยไม่มี error ตามด้วย npm run lint ที่เงียบสนิท — ยังไม่มีอะไรให้ยิง curl ในบทนี้ เพราะไม่มี endpoint ไหนเรียก toProductResponse เลย คนที่พิสูจน์ว่า mapper ถูกจริงคือบทถัดไป

การที่ build ผ่านไม่ได้แค่บอกว่า syntax ถูก — มันบอกว่า type ของทุกคอลัมน์ที่ mapper หยิบมามีอยู่จริงใน Prisma Client ที่ generate ไว้ และรูปทรงที่ประกอบขึ้นตรงกับ ProductResponseDto ทุกคีย์

ตรวจว่าใช้งานได้จริง

  • npm run build ได้ exit 0 (ไม่มี error TS ใด ๆ) และ npm run lint ไม่พิมพ์อะไรออกมา
  • นับคีย์: node -e "const d=require('./docs/contract/product-1.json');console.log(Object.keys(d).length)" ต้องได้ 22 เท่ากับจำนวน field ใน ProductResponseDto
  • ลองแก้ category: product.category.slug เป็น category: product.category ชั่วคราวแล้ว npm run build — ต้องได้ error ทันที (ยืนยันว่า DTO ทำหน้าที่เป็นยาม) แล้วแก้กลับ
  • grep -n "any\|as " src/products/product.mapper.ts src/products/dto/product-response.dto.ts — ต้องไม่เจอ
  • commit ผลงานด้วย git add -A && git commit -m "feat: product response dto and mapper"
