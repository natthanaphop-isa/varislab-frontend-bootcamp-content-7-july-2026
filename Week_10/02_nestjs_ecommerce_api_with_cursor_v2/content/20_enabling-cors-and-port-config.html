เปิด CORS และตั้งค่า PORT

เมื่อจบบทนี้ คุณจะสามารถ

  • อธิบายได้ว่า CORS ถูกบังคับที่ browser ไม่ใช่ที่ server และ preflight OPTIONS เกิดขึ้นเมื่อไร
  • เปิด CORS ด้วย app.enableCors() โดยอ่าน origin จาก environment แทนการใส่ *
  • อ่านผลของ curl -H 'Origin: …' ได้ถูกต้อง — รวมถึงกรณีที่ header ไม่ได้หายไปอย่างที่หลายคนคาด

CORS เป็นกฎของ browser ไม่ใช่ของ server

ทุกวันนี้ API ของเรารันที่ http://localhost:3000 ส่วน React app รันที่ http://localhost:5173 — พอร์ตต่างกันก็นับเป็น origin ต่างกันแล้ว (origin = scheme + host + port) เมื่อโค้ดในหน้าเว็บหนึ่งยิง request ข้าม origin browser จะยอมให้ JavaScript อ่าน response ได้เฉพาะเมื่อ response นั้นมี header Access-Control-Allow-Origin ที่ค่าตรงกับ origin ของหน้าเว็บที่ยิงมา ถ้าไม่ตรง request มักถูกส่งไปถึง server เรียบร้อยแล้ว แต่ browser จะทิ้ง response แล้วขึ้น error ใน console — นี่คือเหตุผลที่ปัญหา CORS มักดู งง เพราะ log ฝั่ง server บอกว่า 200

request บางแบบยังมีขั้น preflight ก่อนด้วย: ถ้าไม่ใช่ request แบบง่าย (เช่น POST ที่ส่ง Content-Type: application/json ซึ่งตรงกับ POST /carts/add ของเรา) browser จะยิง OPTIONS ไปที่ path เดียวกันก่อน พร้อม header Access-Control-Request-Method เพื่อถามว่า อนุญาตไหม ถ้า server ไม่ตอบให้ถูก request จริงจะไม่ถูกส่งเลย — app.enableCors() จัดการทั้ง preflight และ header ของ response จริงให้ในบรรทัดเดียว

ที่สำคัญ: curl ไม่ได้บังคับกฎนี้ มันพิมพ์ทุกอย่างที่ server ส่งมาให้เสมอ ดังนั้น ยิง curl ผ่าน ไม่ได้พิสูจน์ว่า React app จะเรียกได้ สิ่งที่เราตรวจด้วย curl ได้คือ header ที่ server ส่งออกมา เท่านั้น

ทำไมไม่ใช้ origin: '*'

ค่า origin: '*' คือทางที่ง่ายที่สุดและเป็นทางที่เราจะไม่ใช้ ด้วยเหตุผลสามข้อ

  • * เปิดให้ทุกเว็บในอินเทอร์เน็ตเรียก API ของเราจาก browser ของผู้ใช้ได้ ซึ่งเกินความจำเป็น เพราะเรารู้อยู่แล้วว่ามี client เดียวคือ Vite ที่ http://localhost:5173
  • * ใช้ร่วมกับ cookie ไม่ได้ตามสเปก — ถ้าวันหน้าเพิ่ม auth ด้วย cookie ก็ต้องกลับมาแก้อยู่ดี ตั้ง origin ให้ตรงตัวไว้ตั้งแต่ต้นจึงประหยัดกว่า
  • เราเก็บค่าไว้ใน .env (CORS_ORIGIN=http://localhost:5173) เพื่อให้ตอน deploy เปลี่ยนเป็นโดเมนจริงได้โดยไม่แตะโค้ด — รูปแบบเดียวกับ PORT

ส่วน PORT นั้น scaffold ทำไว้ให้แล้วตั้งแต่บทที่ 2: บรรทัดสุดท้ายของ main.ts คือ await app.listen(process.env.PORT ?? 3000) และ ConfigModule.forRoot({ isGlobal: true }) ที่เราใส่ใน AppModule ตอนบทที่ 6 เป็นตัวโหลด .env เข้า process.env ให้ตอน module ถูก import — บทนี้จึงไม่ต้องแก้อะไรเรื่องพอร์ต แค่รู้ว่ามันมาจากไหน

เป้าหมายของบทนี้

ecommerce-api/

สั่ง Cursor เปิด CORS ให้ origin เดียว

commit งานก่อน แล้วเปิดแชทใหม่ใน Cursor โหมด Agent (git add -A && git commit -m "chore: checkpoint before cors") จากนั้นส่ง prompt นี้ — และจำกติกาของคอร์สไว้: AI พิมพ์แทนคุณได้ แต่คุณต้องอธิบายทุกบรรทัดได้

เปิด CORS ให้ React app ที่ localhost:5173 เรียก API ได้ โดยอ่าน origin จาก environment บริบท: @src/main.ts @.env @.cursor/rules/project.mdc .env มี PORT=3000 และ CORS_ORIGIN=http://localhost:5173 อยู่แล้ว และ ConfigModule.forRoot({ isGlobal: true }) โหลด .env เข้า process.env ตอน AppModule ถูก import React app รันด้วย Vite ที่ http://localhost:5173 และเรียก API ด้วย axios แบบไม่ส่ง cookie main.ts ตอนนี้มี ValidationPipe แบบ global และ app.listen(process.env.PORT ?? 3000) อยู่แล้ว โครงสร้าง: แก้ไฟล์เดียว - src/main.ts (แก้ไข) ข้อกำหนดทางเทคนิค: - หลัง useGlobalPipes เพิ่ม app.enableCors({ origin: process.env.CORS_ORIGIN ?? 'http://localhost:5173' }) - ห้ามใช้ origin: '*' หรือ origin: true - ห้ามเปิด credentials - คง ValidationPipe และ app.listen ไว้ตามเดิม ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ - ห้ามแก้ไฟล์อื่น - ยังไม่ต้องตั้งค่า Swagger

ตรวจโค้ดที่ AI สร้าง

  • app.enableCors(...) อยู่หลัง app.useGlobalPipes(...) และก่อน await app.listen(...)
  • origin อ่านจาก process.env.CORS_ORIGIN และมี fallback เป็น 'http://localhost:5173' ด้วย ??
  • ไม่มี origin: '*' ไม่มี origin: true และไม่มี enableCors() แบบไม่ส่ง option
  • ไม่มี credentials: true และไม่มี methods / allowedHeaders ที่เราไม่ได้สั่ง
  • บล็อก ValidationPipe ทั้งก้อน (whitelist, transform, transformOptions) และ app.listen(process.env.PORT ?? 3000) ยังเหมือนเดิมทุกตัวอักษร
  • git status แสดงไฟล์ที่เปลี่ยนแค่ src/main.ts — ไม่มี dependency ใหม่ใน package.json

AI มักพลาดตรงนี้: เขียน app.enableCors() เปล่า ๆ ซึ่งเท่ากับ origin: '*' — ผลลัพธ์ใน browser ใช้งานได้ เหมือนกัน จึงหลอกตาง่ายมาก ให้เปิดไฟล์ดูด้วยตาทุกครั้งว่ามี { origin: ... } อยู่จริง อีกท่าที่เจอบ่อยคือแถม credentials: true มาให้ (เราไม่ส่ง cookie จึงไม่ต้องใช้) หรือย้าย enableCors ไปไว้หลัง app.listen ซึ่งสายเกินไปเพราะ server เริ่มรับ request ไปแล้ว

โค้ดอ้างอิงของบทนี้ (เทียบกับของคุณทีละบรรทัด):

/* src/main.ts */
import { ValidationPipe } from '@nestjs/common';
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module.js';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  app.useGlobalPipes(
    new ValidationPipe({
      whitelist: true,
      transform: true,
      transformOptions: { enableImplicitConversion: true },
    }),
  );
  app.enableCors({ origin: process.env.CORS_ORIGIN ?? 'http://localhost:5173' });

  await app.listen(process.env.PORT ?? 3000);
}
await bootstrap();

ถ้าอธิบายบรรทัดไหนไม่ได้ ยังไม่ผ่านบทนี้ — กลับไปอ่านส่วนแนวคิดก่อน

ผลลัพธ์ที่คาดหวัง

src/main.ts เพิ่มขึ้นหนึ่งบรรทัด (git diff ควรอ่านจบในสิบวินาที) watch mode ของ npm run start:dev recompile แล้วขึ้น Nest application successfully started ตามเดิม — ไม่มี log ใหม่เรื่อง CORS เพราะ enableCors ไม่ได้พิมพ์อะไรตอน bootstrap มันแค่ติด middleware ไว้ สิ่งที่เปลี่ยนคือ response ทุกตัวมี header Access-Control-Allow-Origin: http://localhost:5173 เพิ่มเข้ามา

ตรวจว่าใช้งานได้จริง

  • ยิงสองคำสั่งนี้ (ทั้งคู่ต้องพิมพ์บรรทัดเดียวกัน)
curl -s -i -H 'Origin: http://localhost:5173' http://localhost:3000/products/categories | grep -i access-control-allow-origin
curl -s -i -H 'Origin: http://evil.test' http://localhost:3000/products/categories | grep -i access-control-allow-origin
  • ทั้งสองบรรทัดได้ผลเหมือนกันคือ Access-Control-Allow-Origin: http://localhost:5173
  • สังเกตว่าค่าใน header ไม่เคย เป็น http://evil.test — server ส่งค่าที่เราตั้งไว้ค่าเดียวเสมอ
  • ไม่มี option ใหม่หลุดเข้ามา: grep -n 'enableCors' src/main.ts ได้บรรทัดเดียว
  • commit งานนี้ด้วย git add -A && git commit -m "feat: cors"

ตอนตรวจของจริงเราพบว่า request จาก http://evil.test ก็ยังได้ header กลับ ไม่ใช่หายไป เพราะเมื่อตั้ง origin เป็น string ตัวเดียว middleware cors ที่อยู่ใต้ enableCors จะส่งค่านั้นออกมาแบบคงที่ โดยไม่อ่าน header Origin ของ request เลย — คนที่บล็อกคือ browser ไม่ใช่ server: หน้าเว็บที่อยู่บน http://evil.test เห็นว่าค่าใน Access-Control-Allow-Origin ไม่ตรงกับ origin ของตัวเอง จึงทิ้ง response นั้นทิ้ง ส่วน curl ไม่ได้ตรวจข้อนี้ให้ จึงพิมพ์ header ออกมาตามปกติ นี่คือเหตุผลที่บทนี้ให้คุณอ่าน ค่า ของ header ไม่ใช่แค่นับว่ามีหรือไม่มี
