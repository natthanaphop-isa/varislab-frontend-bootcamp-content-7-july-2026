GET /products/category/:slug

เมื่อจบบทนี้ คุณจะสามารถ

  • กรองสินค้าด้วยเงื่อนไขที่อยู่บน relation ({ category: { slug } }) โดยไม่ต้อง query ตาราง category แยก
  • อธิบายว่าทำไม slug ที่ไม่มีอยู่จริงต้องได้ 200 พร้อม list ว่าง ไม่ใช่ 404
  • เห็นผลตอบแทนของการแยก paginate ออกมาก่อนหน้านี้: endpoint ใหม่ใช้โค้ดสองบรรทัด

บทนี้สั้นมาก และนั่นคือประเด็น

ก่อนหน้านี้เราไม่ได้เขียนแค่ findAll — เราเขียน paginate(where, skip, limit) ที่รับ เงื่อนไขอะไรก็ได้ เข้ามา แล้วให้ findAll ส่ง {} (ไม่กรองอะไร) เข้าไป บทนี้จึงเหลืองานแค่หาว่า "เงื่อนไขของหมวดหมู่" เขียนอย่างไร

findByCategory(slug: string, query: PaginationQueryDto) {
  return this.paginate({ category: { slug } }, query.skip, query.limit);
}

เท่านี้ก็ได้ pagination, total ที่นับเฉพาะหมวดนั้น, orderBy, include และการ map เป็น contract มาครบ โดยไม่ต้อง copy อะไรเลย ถ้าตอนนั้นเราปล่อยให้ findAll เขียน $transaction ไว้ในตัวเอง บทนี้จะกลายเป็นการ copy สามสิบบรรทัดมาแก้คำเดียว — ซึ่งคือจุดเริ่มของความไม่ตรงกันในอนาคต

กรองผ่าน relation ไม่ใช่ผ่าน categoryId

ในฐานข้อมูล สินค้าอ้างหมวดหมู่ด้วยคอลัมน์ categoryId ที่เป็นตัวเลข แต่ client ส่ง slug มาให้ ทางที่คิดขึ้นมาก่อนคือสองขั้น: หา category จาก slug ก่อน ได้ id แล้วค่อยกรองสินค้า — แต่ Prisma ให้เราเขียนเงื่อนไขข้าม relation ได้ในครั้งเดียว (ทบทวน NestJS Fundamentals ตอน relation queries)

where: { category: { slug } }

Prisma แปลงก้อนนี้เป็น SQL ที่ join ไปที่ตาราง Category แล้วกรองด้วย slug ในคำสั่งเดียว ผลคือไป-กลับฐานข้อมูลครั้งเดียวแทนสองครั้ง และไม่มีช่องให้ข้อมูลเปลี่ยนระหว่างสอง query

slug ที่ไม่มีอยู่: 200 ไม่ใช่ 404

นี่คือจุดที่ความรู้สึกเรื่อง REST จะขัดกับสัญญา เปิด docs/api-spec.md ดู section List envelope + pagination — เราออกแบบให้ slug ที่ไม่มีอยู่ตอบ status 200 พร้อม (ตัวอย่างนี้ยิง ?limit=2&skip=0)

{"products":[],"total":0,"skip":0,"limit":2}

เหตุผลที่มันสมเหตุสมผล: endpoint นี้ตอบ ผลการค้นหา ไม่ใช่ ตัว resource การค้นหาที่ไม่พบอะไรคือการค้นหาที่สำเร็จแต่ได้ศูนย์รายการ ต่างจาก GET /products/9999 ที่ขอ resource ชิ้นหนึ่งซึ่งไม่มีอยู่ — อันนั้น 404 ถูกต้อง

และเหตุผลที่สำคัญกว่า: Category.tsx ยิง useQuery ทันทีที่หมวดหมู่เปลี่ยน โดยไม่มีการ์ดพิเศษสำหรับ "หมวดที่ว่างเปล่า" เลย — component เช็คแค่ isError กับ isLoading ถ้า endpoint ตอบ 404 ตอนหมวดนั้นไม่มีสินค้า isError จะเป็น true ทันที แล้วหน้า Category เด้งไปโชว์ <ErrorMessage /> เต็มหน้า แทนที่จะโชว์ตะแกรงสินค้าที่ว่างเปล่าตามที่ควรเป็น

สังเกต limit ด้วย — ตามกติกา pagination ที่ตกลงไว้ก่อนหน้านี้ คือ limit ต้อง echo ค่าที่ client ขอมาเสมอ แม้หมวดนั้นจะไม่มีสินค้าเลย เช่นยิง ?limit=5 กับหมวดที่ว่างเปล่าก็ต้องได้ limit: 5 (ไม่ใช่ 0) เพราะ paginate ของเราคืน limit ตามที่รับเข้ามาตรง ๆ อยู่แล้ว (ไม่ใช่ rows.length) ข้อนี้จึงถูกต้องโดยอัตโนมัติ ไม่ต้องเขียนกรณีพิเศษ

ผลลัพธ์ที่ต้องได้ในรอบนี้จึงเขียนไว้ชัดว่า slug ที่ไม่มีอยู่ต้องได้ 200 ห้ามตอบ 404 — เป็นการปิดทางที่ AI (และคนส่วนใหญ่) จะเลือกโดยสัญชาตญาณ

ลำดับ route: ปลอดภัยอยู่แล้ว แต่ยังต้องวางให้ถูก

category/:slug มีสอง segment ส่วน :id มีหนึ่ง segment จึงชนกันไม่ได้ทางเทคนิค — /products/category/beauty ไม่มีทางถูกจับด้วย /products/:id แต่เราก็ยังวาง handler ใหม่ไว้ก่อน @Get() และ @Get(':id') ด้วยเหตุผลสองข้อ

  • รักษากฎเดียวที่จำง่าย: คำตายตัวมาก่อน parameter ตลอดทั้งไฟล์ ไม่ต้องมานั่งคิดเป็นราย route ว่าอันนี้ชนไหม
  • อ่าน controller จากบนลงล่างแล้วเห็นลำดับจากเฉพาะเจาะจงไปกว้าง ซึ่งตรงกับลำดับที่ router ลองจับจริง

ลำดับสุดท้ายของ ProductsController คือ findCategories → findByCategory → findAll → findOne

เป้าหมายของบทนี้

รายการด้านล่างคือไฟล์ที่เปลี่ยนในโค้ดอ้างอิงของคอร์ส — ใช้เป็นแผนที่ตอนเทียบงาน ไม่ใช่ข้อบังคับ Cursor ของคุณอาจวางไฟล์หรือตั้งชื่อต่างไปได้ ขอแค่ผ่านผลลัพธ์ที่ต้องได้ใน prompt

src/products/
├── products.controller.ts            (แก้ไข: เพิ่ม handler เดียว)
└── products.service.ts               (แก้ไข: เพิ่ม method เดียว)
  • src/products/products.service.ts — ในโค้ดอ้างอิง: เพิ่ม findByCategory(slug, query) ที่เรียก this.paginate({ category: { slug } }, …) / ไม่ query ตาราง Category แยก และไม่ throw เมื่อไม่พบหมวดหมู่
  • src/products/products.controller.ts — ในโค้ดอ้างอิง: เพิ่ม @Get('category/:slug') ไว้ถัดจาก findCategories และก่อน findAll / ไม่แก้ handler อื่น

ในโค้ดอ้างอิง diff ของบทนี้ไม่ถึงสิบบรรทัดและไม่แตะ paginate, findAll, findOne หรือ productInclude — ถ้าของคุณยาวกว่านั้นมาก ให้ดูว่ามีอะไรเกินจากเป้าหมายหรือเปล่า

สั่ง Cursor เพิ่ม endpoint ตามหมวดหมู่

commit งานก่อน แล้วเปิดแชทใหม่ใน Cursor โหมด Agent (git add -A && git commit -m "chore: before category endpoint") จากนั้นส่ง prompt นี้

เพิ่ม endpoint GET /products/category/:slug ที่ใช้ pagination เดิม และตอบ list ว่างเมื่อไม่พบหมวดหมู่ @src/products/products.controller.ts @src/products/products.service.ts (สองไฟล์นี้คือชื่อในโค้ดอ้างอิง ถ้าโปรเจกต์ของคุณตั้งชื่อต่างออกไป ให้ @ ไฟล์ controller กับ service ของ products ที่คุณมีจริง) ผลลัพธ์ที่ต้องได้: - GET /products/category/beauty?limit=2&skip=1 ตอบ 200 envelope { products, total, skip, limit } ได้ total 5, skip 1, limit 2 และสินค้า id 2 กับ 3 - GET /products/category/groceries?limit=2&skip=0 ได้ total 27 (นับเฉพาะสินค้าในหมวดนั้น) และ key ของ envelope มีแค่ products, total, skip, limit - slug ที่ไม่มีอยู่จริง เช่น GET /products/category/nope?limit=2&skip=0 ตอบ 200 body {"products":[],"total":0,"skip":0,"limit":2} พอดี — ห้ามตอบ 404 - limit/skip ผิดช่วงตอบ 400 เหมือน GET /products - GET /products/categories, GET /products และ GET /products/:id ยังตอบเหมือนเดิมทุกอย่าง ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ - ห้ามแตะไฟล์ใน test/ — e2e test เป็น prompt แยกในแชทถัดไป

ตรวจโค้ดที่ AI สร้าง

  • slug ที่ไม่มีอยู่ตอบ 200 กับ envelope ว่าง — ไม่มีทางไหนในโค้ดที่ทำให้ endpoint นี้ตอบ 404
  • total นับเฉพาะสินค้าในหมวดนั้น (beauty ได้ 5, groceries ได้ 27) ไม่ใช่ 208
  • limit ใน response echo ค่าที่ขอมาเสมอ แม้หมวดจะว่าง
  • GET /products/category/beauty ไม่ถูก route /products/:id แย่งจับ (log ตอน start มี route /products/category/:slug)
  • ไม่มีการ copy logic แบ่งหน้าซ้ำ — ถ้าโปรเจกต์มีตัวช่วยแบ่งหน้าอยู่แล้ว endpoint ใหม่ควรใช้ตัวเดิม
  • ไม่มีไฟล์ที่ไม่เกี่ยวกับเป้าหมายถูกแก้ (ดูจาก git status), endpoint เดิมสามตัวยังตอบเหมือนเดิม และไม่มี any, as หรือ ! เพิ่มเข้ามา

AI มักพลาดตรงนี้: หา category จาก slug ก่อนแล้วโยน 404 ถ้าไม่พบ — เป็นพฤติกรรมที่ดูถูกหลักการ REST และเป็นสิ่งที่ทุกคอร์สสอน แต่มันผิดสัญญาที่เราออกแบบไว้ใน docs/api-spec.md และทำให้หน้า Category ของ React app เด้งไปหน้า error ตอนที่ควรจะโชว์ข้อความ "ไม่พบสินค้า" ถ้าเจอโค้ดแบบนี้ ให้ลบทั้งก้อนทิ้ง ไม่ใช่แก้ status code

โค้ดอ้างอิงของบทนี้ — เป็นหนึ่งในวิธีที่ถูก ของคุณไม่จำเป็นต้องเหมือนทุกบรรทัด ขอแค่ผ่านผลลัพธ์ที่ต้องได้:

src/products/products.service.ts

import { Injectable, NotFoundException } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import type { Prisma } from '../generated/prisma/client.js';
import { PrismaService } from '../prisma/prisma.service.js';
import { PaginationQueryDto } from './dto/pagination-query.dto.js';
import { ProductListResponseDto, ProductResponseDto } from './dto/product-response.dto.js';
import { toProductResponse } from './product.mapper.js';

const productInclude = {
  category: true,
  reviews: { orderBy: { id: 'asc' } },
} satisfies Prisma.ProductInclude;

@Injectable()
export class ProductsService {
  constructor(
    private readonly prisma: PrismaService,
    private readonly config: ConfigService,
  ) {}

  async findCategories() {
    const appUrl = this.config.getOrThrow<string>('APP_URL');
    const categories = await this.prisma.category.findMany({ orderBy: { id: 'asc' } });
    return categories.map(({ slug, name }) => ({
      slug,
      name,
      url: `${appUrl}/products/category/${slug}`,
    }));
  }

  findAll(query: PaginationQueryDto) {
    return this.paginate({}, query.skip, query.limit);
  }

  findByCategory(slug: string, query: PaginationQueryDto) {
    return this.paginate({ category: { slug } }, query.skip, query.limit);
  }

  async findOne(id: number): Promise<ProductResponseDto> {
    const product = await this.prisma.product.findUnique({
      where: { id },
      include: productInclude,
    });
    if (!product) {
      throw new NotFoundException(`Product ${id} not found`);
    }
    return toProductResponse(product);
  }

  private async paginate(
    where: Prisma.ProductWhereInput,
    skip: number,
    limit: number,
  ): Promise<ProductListResponseDto> {
    const [rows, total] = await this.prisma.$transaction([
      this.prisma.product.findMany({
        where,
        skip,
        take: limit,
        orderBy: { id: 'asc' },
        include: productInclude,
      }),
      this.prisma.product.count({ where }),
    ]);
    return { products: rows.map(toProductResponse), total, skip, limit };
  }
}

src/products/products.controller.ts

import { Controller, Get, Param, ParseIntPipe, Query } from '@nestjs/common';
import { PaginationQueryDto } from './dto/pagination-query.dto.js';
import { ProductsService } from './products.service.js';

@Controller('products')
export class ProductsController {
  constructor(private readonly productsService: ProductsService) {}

  @Get('categories')
  findCategories() {
    return this.productsService.findCategories();
  }

  @Get('category/:slug')
  findByCategory(@Param('slug') slug: string, @Query() query: PaginationQueryDto) {
    return this.productsService.findByCategory(slug, query);
  }

  @Get()
  findAll(@Query() query: PaginationQueryDto) {
    return this.productsService.findAll(query);
  }

  @Get(':id')
  findOne(@Param('id', ParseIntPipe) id: number) {
    return this.productsService.findOne(id);
  }
}

เพิ่มสอง test ของหมวดหมู่ลงในไฟล์เดิม

ไฟล์ test/products.e2e-spec.ts ตอนนี้มีเจ็ด test แล้ว ขั้นนี้เพิ่มอีกสองข้อของ endpoint ใหม่ลงไปในไฟล์เดิม รวมเป็นเก้า — เปิดแชทใหม่แล้วสั่ง Cursor เขียนให้เหมือนตอน test ชุดแรก ด้วยเหตุผลเดียวกัน: สิ่งที่ทำให้ test เชื่อถือได้คือความเป็นอิสระของมัน (แชทใหม่ + ผลลัพธ์ที่มาจากสัญญา + ห้ามมันแก้ src/) ไม่ใช่ว่าใครเป็นคนพิมพ์

เพิ่ม test ของ endpoint ตามหมวดหมู่ลงในไฟล์ e2e ที่มีอยู่แล้ว @test/products.e2e-spec.ts @docs/api-spec.md ผลลัพธ์ที่ต้องได้: - เพิ่มสอง it() ต่อท้ายไฟล์เดิม ใช้ app ตัวเดิมที่ beforeAll boot ไว้แล้ว — ห้ามสร้างไฟล์ test ใหม่ และห้ามแก้เจ็ด test ที่มีอยู่ 1. ชื่อ test: GET /products/category/groceries → total 27 — ยิง /products/category/groceries?limit=20&skip=0 ได้ 200 และ total เป็น 27 2. ชื่อ test: GET /products/category/nope → 200, empty envelope — ยิง /products/category/nope?limit=5&skip=0 ได้ 200, products เป็น array ว่าง และ total เป็น 0 (สัญญาข้อนี้คือ 200 ไม่ใช่ 404) - ยิงผ่าน request(app.getHttpServer()) — ไม่ mock อะไรเลย และไม่ยิงไป URL หรือ port ภายนอก - import ในไฟล์ test ลงท้ายด้วย .js ตามกติกา ESM ของโปรเจกต์ ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ - ห้ามแก้ไฟล์ใน src/ เด็ดขาด ถ้า test ไม่ผ่านให้บอกผมว่าไม่ผ่านข้อไหน ห้ามแก้โค้ดให้ test ผ่านเอง - ห้ามรัน test ให้ ผมจะรันเอง

อ่าน diff ที่ได้ก่อนรัน สามข้อนี้คือจุดที่ agent พลาดบ่อยที่สุดในไฟล์ test

  • git status ต้องเห็นไฟล์ที่ถูกแก้แค่ test/products.e2e-spec.ts — ไม่มีไฟล์ใน src/ ถูกแตะ ถ้ามี แปลว่า agent ไปแก้ endpoint ให้เข้ากับ test ของมันเอง ให้ย้อนกลับแล้วสั่งใหม่
  • git diff ของไฟล์ test ต้องมีแต่บรรทัดที่เพิ่มเข้ามา เจ็ด test เดิมต้องอยู่ครบและไม่ถูกเขียนใหม่ — วิธีเร็วที่สุดคือดูว่า npm run test:e2e นับได้เก้า ไม่ใช่สอง
  • test ของ slug ที่ไม่มีจริงต้องคาดหวัง 200 พร้อม envelope ว่าง ไม่ใช่ 404 — ข้อนี้คือสัญญาที่เราออกแบบไว้เอง และเป็นจุดที่ AI มักเขียนผิดเพราะ 404 คือสิ่งที่ API ส่วนใหญ่ในโลกทำกัน ถ้ามันเขียน .expect(404) มา แปลว่ามันเดาจากความเคยชิน ไม่ได้อ่าน docs/api-spec.md

reporter ปริยายของ Vitest ยุบไฟล์ที่ผ่านให้เหลือบรรทัดเดียว ถ้าอยากเห็นชื่อ test ทีละข้อให้เติม --reporter=verbose ต่อท้าย (npm run test:e2e -- --reporter=verbose) และอย่าลืมว่า test ชุดนี้ boot แอปของตัวเอง ฐานข้อมูลจึงต้องรันอยู่ แต่ไม่ต้องเปิด npm run start:dev ค้างไว้ก็ได้ — ต่างจาก curl ทุกข้อด้านบนที่ต้องมี dev server จริง
