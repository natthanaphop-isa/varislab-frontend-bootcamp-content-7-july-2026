NestJS E-commerce API Workshop

สิ่งที่เราจะสร้างและกติกาของคอร์ส

เมื่อจบบทนี้ คุณจะสามารถ

  • บอกได้ว่า React app จากคอร์ส React E-commerce เรียก dummyjson ที่ endpoint ไหน และคำว่า drop-in replacement หมายถึงอะไร
  • อ่านโครงสร้างสุดท้ายของโปรเจกต์ ecommerce-api ได้ว่าไฟล์ไหนทำหน้าที่อะไร
  • ตรวจความพร้อมของเครื่องตัวเอง (Node, Docker, Cursor, React app) ก่อนลงมือสร้างโปรเจกต์

เราจะแทนที่ dummyjson ด้วย API ของเราเอง

React e-commerce app ที่เราสร้างไว้ในคอร์ส React E-commerce ไม่มีฐานข้อมูลของตัวเอง มันดึงข้อมูลสินค้าทั้งหมดจาก dummyjson.com ผ่าน endpoint เพียง 5 เส้น เป้าหมายของคอร์สนี้คือสร้าง API ของเราเองที่ตอบ 5 เส้นนี้ได้ ด้วย path เดิมและรูปทรง JSON เดิม เพื่อให้ React app ไม่ต้องแก้โค้ดแม้แต่บรรทัดเดียว — เปลี่ยนแค่ค่า VITE_API_BASE_URL จาก https://dummyjson.com เป็น http://localhost:3000 ก็ใช้งานได้ทันที นี่คือความหมายของคำว่า drop-in replacement

Method + PathReact ใช้ที่ไหนตอบอะไร
GET /products/categoriesหน้า Home และเมนูหมวดสินค้าarray ของ {slug, name, url} จำนวน 24 รายการ
GET /products?limit&skipแถบดีลบนหน้า Homeซอง {products, total, skip, limit}
GET /products/category/:slug?limit&skipหน้า Home และหน้า Category ที่มีการแบ่งหน้าซองเดียวกับด้านบน แต่กรองด้วย slug
GET /products/:idหน้ารายละเอียดสินค้าproduct เต็มรูปแบบ พร้อม reviews
POST /carts/addหน้า Checkoutcart ที่คิดส่วนลดแล้ว พร้อม id ของคำสั่งซื้อ

ข้อผูกมัดจึงชัดเจนมาก: ทุกชื่อ field ทุก status code และทุกพฤติกรรมขอบ ๆ (เช่น หมวดที่ไม่มีจริงตอบอะไร) ต้องตรงกับสิ่งที่โค้ดฝั่ง client (type, API client, MSW fixtures) คาดหวังจริง เพราะถ้าไม่ตรง หน้าจอของ React จะพังโดยที่ API ของเราไม่ฟ้อง error อะไรเลย ขั้นถัดไปเราจะอ่านโค้ดเหล่านั้นแล้วออกแบบ สัญญา (contract) นี้เก็บไว้เป็นไฟล์จริงในโปรเจกต์ แล้วทุกขั้นหลังจากนั้นจะอ้างถึงไฟล์นั้นเสมอ

สังเกตว่าไฟล์ที่เราเขียนเองมีไม่ถึงสามสิบไฟล์ และแต่ละขั้นเพิ่มหรือแก้เพียงไม่กี่ไฟล์ — นั่นตั้งใจไว้ตั้งแต่ต้น เพราะการตรวจงานที่ AI เขียนจะทำได้จริงก็ต่อเมื่อ diff ของแต่ละรอบสั้นพอที่คุณจะอ่านจบ

กติกาของคอร์ส: เข้าใจก่อน แล้วค่อยสั่ง

AI พิมพ์แทนคุณได้ แต่คุณต้องอธิบายทุกบรรทัดได้ — ถ้าอธิบายไม่ได้ แปลว่ายังไม่ผ่านบทนี้

ทุกบทที่ใช้ Cursor เดินตามลำดับเดียวกันห้าขั้น: แนวคิด (ทำความเข้าใจว่า endpoint นี้ต้องทำอะไร และข้อเท็จจริงจาก docs/api-spec.md ข้อไหนบังคับมันอยู่) → เป้าหมายของบทนี้ (ไฟล์ที่จะเกิดขึ้นและสัญญาของแต่ละไฟล์) → 🤖 prompt (คำสั่งสามส่วนที่ส่งให้ Cursor Agent) → ✅ review (ตรวจโค้ดที่ AI สร้างทีละข้อ เทียบกับโค้ดอ้างอิงของบทนั้น) → ตรวจว่าใช้งานได้จริง (ยิง curl แล้วเทียบกับสัญญาใน docs/api-spec.md) ลำดับนี้ไม่สลับ เพราะ prompt ที่ดีเขียนได้เฉพาะเมื่อคุณรู้คำตอบคร่าว ๆ อยู่ก่อนแล้ว

มีห้าขั้นที่เรา ไม่ ใช้ Cursor แต่พิมพ์ด้วยมือ (การ scaffold โปรเจกต์, การออกแบบสัญญาใน docs/api-spec.md, การเขียน .cursor/rules, การรัน migration ครั้งแรก และการสลับ React app มาใช้ API ของเรา) ด้วยเหตุผลสามข้อ

  • การออกแบบสัญญาใน docs/api-spec.md คือ งานออกแบบที่ AI ทำแทนไม่ได้ — สัญญาต้องมาจากการอ่านโค้ดฝั่ง client ของคุณเองแล้วตัดสินใจเอง ถ้าให้ AI ออกแบบสัญญาให้ มันจะเดารูปทรงที่ดูสมเหตุสมผลแต่ไม่ตรงกับที่ client ต้องการจริง
  • การ scaffold โปรเจกต์และการรัน migration ครั้งแรกคือ งานที่รัน ไม่ใช่งานที่เขียน — nest new และ prisma migrate dev เป็นคำสั่งที่คุณต้องเห็นผลลัพธ์ด้วยตาตัวเอง (และ Cursor rules ที่เราเขียนเองก็สั่งห้าม AI รัน migration เองอยู่แล้ว)
  • การเขียน .cursor/rules คือ กติกาที่คุณตั้งให้ AI และการสลับ React app มาใช้ API ของเราคือ หลักฐาน ว่างานทั้งหมดใช้ได้จริง — สองอย่างนี้เป็นความรับผิดชอบของคน ไม่ใช่ของเครื่องมือ

พร้อมเริ่มหรือยัง

  • เรียน NestJS Fundamentals จบแล้ว และอธิบายได้ว่า module, controller, service, DTO และ PrismaService แต่ละอย่างทำหน้าที่อะไร — คอร์สนี้ทบทวนให้สั้น ๆ เท่านั้น ไม่ได้สอนใหม่
  • ติดตั้ง Cursor แล้วและ sign in เรียบร้อย เปิดแชทโหมด Agent ได้ (ทบทวนวิธีใช้ได้จากคอร์ส React E-commerce + Cursor AI)
  • node --version ได้เลข 24 หรือมากกว่า
  • docker --version ตอบเวอร์ชันได้ และ Docker Desktop กำลังรันอยู่
  • เปิดโปรเจกต์ React e-commerce จากคอร์ส React E-commerce แล้ว npm run dev ขึ้นหน้า Home ที่เห็นสินค้าจาก dummyjson จริง — นี่คือหลักฐานตั้งต้นที่เราจะเอากลับมาเทียบตอนสลับ React app มาใช้ API ของเรา
