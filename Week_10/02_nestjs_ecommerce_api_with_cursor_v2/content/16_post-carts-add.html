สร้างคำสั่งซื้อและเปิด POST /carts/add

เมื่อจบบทนี้ คุณจะสามารถ

  • คำนวณ total, discountedPrice และ discountedTotal ด้วยกติกาเดียวกันทุก field (ปัดทศนิยม 2 ตำแหน่งเสมอ ไม่มีข้อยกเว้น)
  • ใช้ interactive transaction อ่านสินค้าและเขียนคำสั่งซื้อในก้อนเดียว และอธิบายได้ว่า rollback เกิดตอนไหน
  • เขียน mapper แปลง Order + OrderItem เป็น response ตามสัญญา โดยไม่ปล่อยข้อมูลส่วนตัวหลุดออกไป
  • เปิด route POST /carts/add ให้ตรงกับ path ที่ React app เรียกโดยไม่แก้ฝั่ง frontend และอธิบายได้ว่าทำไมไฟล์ controller ชื่อ carts แต่ module และ service ใช้คำว่า orders
  • พิสูจน์ทั้งสี่พฤติกรรมด้วย curl (201, 400 ขาด userId, 404 สินค้าไม่มีจริงพร้อม rollback, 400 email ผิดรูป) แล้วปิดท้ายด้วย e2e test ที่สั่ง Cursor เขียนให้ในแชทแยก

บทนี้ยาวกว่าบทอื่นเพราะมันคือ endpoint เดียวที่เขียนข้อมูลลงฐานข้อมูล และการแยกส่วนคิดเงินออกจากส่วนเปิด route ทำให้ตรวจงานยากขึ้นโดยไม่ได้อะไรกลับมา เราจึงทำทั้งเส้นในบทเดียว แต่แบ่งเป็น prompt สามอันในสามแชท: service ที่คิดเงิน → controller ที่เปิด route → e2e test ที่ตัดสินว่าทั้งสองอันถูกตามสัญญาหรือไม่

เลขทุกตัวใน response มาจากไหน

ก่อนเขียนโค้ด ต้องถอดสูตรจาก docs/api-spec.md ให้ครบก่อน ตัวอย่างที่ใช้อ้างอิงตลอดบทนี้คือสินค้า id 1 (Velvet Matte Lipstick) ราคา 9.99 ส่วนลด 10.48 เปอร์เซ็นต์ จำนวน 2 ชิ้น

Fieldสูตรตัวอย่าง
products[].totalprice × quantity ปัด 2 ตำแหน่ง9.99 × 2 = 19.98
products[].discountedPriceround2(total × (1 − discountPercentage / 100))19.98 × 0.8952 = 17.886096 → 17.89
totalผลรวม total ของทุกรายการ ปัด 2 ตำแหน่ง19.98
discountedTotalผลรวม discountedPrice ของทุกรายการ17.89
totalProductsจำนวนรายการ ใน products[]1
totalQuantityผลรวม quantity ของทุกรายการ2

จุดที่ต้องระวังที่สุดคือบรรทัดที่สอง: discountedPrice ปัดด้วย round2 เหมือน field ตัวเงินอื่น ๆ ทุกตัว ไม่มี field ไหนปัดเป็นจำนวนเต็มเป็นกรณีพิเศษ ค่าที่ถูกคือ 17.89 ไม่ใช่ 18 — เราออกแบบระบบเงินของเราเองให้สม่ำเสมอในทุก field ไม่ได้ลอกพฤติกรรมจากที่อื่นมา ถ้าใครเคยเห็นตัวอย่างที่ปัดเป็นจำนวนเต็มมาก่อน (จาก API อื่นที่เคยใช้) ต้องเปลี่ยนความเคยชินตรงนี้

ส่วน total ใช้การปัดสองตำแหน่งผ่าน helper round2 เพราะเลขทศนิยมแบบ floating point ทำให้การบวกราคาสะสมเพี้ยนได้ (เช่น 0.1 + 0.2 ได้ 0.30000000000000004) และ totalProducts นับจำนวนบรรทัด ไม่ใช่จำนวนชิ้น — สั่งสินค้าตัวเดียว 2 ชิ้นจะได้ totalProducts: 1 กับ totalQuantity: 2 — และ discountedPrice ก็เรียก round2 ตัวเดียวกันนี้ ไม่มี helper แยกสำหรับมันเอง

อ่านและเขียนในก้อนเดียวด้วย interactive transaction

การสร้างคำสั่งซื้อต้องทำสองอย่าง: อ่านราคาสินค้าจากตาราง Product แล้วเขียน Order พร้อมรายการลงไป ถ้าปล่อยสองอย่างนี้อยู่นอก transaction จะเกิดปัญหาสองแบบ — ราคาถูกแก้ระหว่างที่เราอ่านเสร็จแต่ยังไม่เขียน (ใบเสร็จได้ราคาผีที่ไม่มีอยู่จริงในช่วงเวลาใดเลย) และถ้าการเขียนพังกลางทางก็จะเหลือข้อมูลค้างครึ่ง ๆ

คำตอบคือ interactive transaction แบบเดียวกับบทเรื่องทรานแซกชันของคอร์ส NestJS Fundamentals: this.prisma.$transaction(async (tx) => { … }) ทุก query ข้างในต้องเรียกผ่าน tx ไม่ใช่ this.prisma ไม่งั้น query นั้นจะหลุดออกไปอยู่นอก transaction เงียบ ๆ

สิ่งที่ทำให้ pattern นี้สวยคือการจัดการ error: ถ้ามี id สินค้าที่ไม่มีจริง เรา throw new NotFoundException(...) ข้างใน callback ได้เลย Prisma จะ rollback ทุกอย่างให้อัตโนมัติเพราะ callback reject และ Nest จะแปลง exception ตัวนั้นเป็น response 404 ให้เอง เราจึงไม่ต้องเขียนโค้ดลบข้อมูลที่เพิ่งสร้างเลยแม้แต่บรรทัดเดียว

การเขียน Order กับ OrderItem ใช้ nested write (บทเรื่องความสัมพันธ์ของคอร์ส NestJS Fundamentals) คือ items: { create: items } ข้างใน tx.order.create() — Prisma ออก INSERT ให้ทั้งใบและทุกบรรทัดในคำสั่งเดียว โดยเติม orderId ให้เองหลังได้ id ของ Order ส่วน include: { items: { orderBy: { id: 'asc' } } } ทำให้ได้รายการกลับมาพร้อมกันในลำดับที่เขียนลงไป — ไม่ต้อง query ซ้ำ และ products[] ใน response เรียงตรงกับที่ client ส่งมา

เราอ่านสินค้าทั้งหมดด้วย findMany({ where: { id: { in: ids } } }) ครั้งเดียวแล้วทำ Map จาก id ไปหา product ไม่ใช่ loop findUnique ทีละตัว — ตะกร้า 10 รายการจึงเป็น 1 query ไม่ใช่ 10 query ส่วนการวน dto.products.map(...) ต่อจากนั้นทำให้ลำดับของ response ตรงกับลำดับที่ client ส่งมาเสมอ ไม่ใช่ลำดับที่ฐานข้อมูลคืนแถวมา

อีกเรื่องที่ตั้งใจไม่ทำ: เราไม่ลด stock ของสินค้า เพราะ React app อ่าน stock จาก GET /products/:id ใหม่ทุกครั้งที่เปิดหน้าสินค้า ถ้าเราลด stock ขึ้นมาเอง พฤติกรรมของแอปจะเปลี่ยนไปจากเดิมทันทีทั้งที่เราไม่ได้แก้ frontend — ขัดกับเป้าหมายของคอร์สนี้

mapper กันข้อมูลส่วนตัวหลุด

แถวที่ Prisma คืนมามีมากกว่าที่สัญญาอนุญาตให้ส่งออก: Order มี address, email, phone, createdAt ที่สัญญาของเรา (docs/api-spec.md) ไม่ได้กำหนดให้ส่งออกไป และ OrderItem มี id ของตัวเองซึ่งไม่ใช่ products[].id ที่ client ต้องการ — client ต้องการ productId เพราะมันใช้ค่านั้นลิงก์ไปหน้าสินค้า

เราจึงใช้ mapper แบบเดียวกับตอนแปลงแถวสินค้าเป็นรูปทรงตามสัญญา คือฟังก์ชันบริสุทธิ์ที่แปลงแถวเป็น response DTO ทีละ field อย่างชัดเจน ข้อดีคือ field ที่เพิ่มใน schema วันหลังจะไม่รั่วออก API เอง เพราะถ้าไม่เขียนไว้ใน mapper มันก็ไม่ถูกส่ง

path มาจาก client ไม่ใช่จากเรา

ถ้าออกแบบ API ใหม่ตั้งแต่ต้น การสั่งซื้อควรเป็น POST /orders แต่คอร์สนี้มีข้อจำกัดที่ชัดเจน: React app เรียก POST /carts/add และเราสัญญาว่าจะไม่แก้โค้ด frontend นอกจาก base URL ดังนั้น path ต้องเป็น /carts/add เป๊ะ ๆ — พลาดตัวเดียวก็ได้ 404 ทุกครั้งที่กดสั่งซื้อ

ทางออกคือแยกสองเรื่องนี้ออกจากกัน: path เป็นเรื่องของสัญญากับ client จึงตั้งชื่อไฟล์ controller ตาม path (carts.controller.ts + @Controller('carts')) ส่วน module และ service เป็นเรื่องของ domain คือการสั่งซื้อ จึงใช้คำว่า orders (orders.module.ts, orders.service.ts) โครงสร้างนี้บอกคนอ่านโค้ดคนต่อไปได้ทันทีว่า "ชื่อ carts มาจากข้อจำกัดภายนอก ไม่ใช่จากวิธีที่เราคิดเรื่องธุรกิจ"

ทั้งสองไฟล์อยู่ในโฟลเดอร์ src/orders/ เดียวกัน ตามหลักการรวม domain ไว้ใน module เดียวจากคอร์ส NestJS Fundamentals — คนหาโค้ดเรื่องคำสั่งซื้อจะเจอทุกอย่างในที่เดียว แม้ route จะชื่อ /carts

ทวนของเดิม: @Body และ status 201

คอร์ส NestJS Fundamentals วางพื้นไว้แล้วสองข้อที่ใช้ตรง ๆ ในบทนี้ ข้อแรก @Body() dto: AddCartDto — การประกาศชนิดของ parameter ให้เป็น class ของ DTO คือสิ่งที่ทำให้ ValidationPipe รู้ว่าต้องเอา rule ชุดไหนมาตรวจ ถ้าเขียนเป็น @Body() dto: any หรือลืมใส่ชนิด DTO ทั้งชุดที่เขียน validation ไว้จะไม่ทำงานเลยแม้แต่ข้อเดียว และไม่มี error ใด ๆ เตือน

ข้อสอง handler ที่เป็น @Post() ของ Nest ตอบ 201 Created เป็นค่าเริ่มต้นอยู่แล้ว ตรงกับสัญญาที่เราออกแบบไว้ใน docs/api-spec.md พอดี จึงไม่ต้องใส่ @HttpCode() — ใส่ @HttpCode(200) ไปจะกลายเป็นการทำสัญญาเสียเอง

สุดท้าย OrdersModule ต้องถูก import เข้า AppModule ไม่ทำขั้นนี้ Nest จะไม่รู้จัก controller ตัวใหม่ และจะไม่มีบรรทัด Mapped {/carts/add, POST} ใน log ตอน start — ซึ่งเป็นวิธีตรวจที่เร็วที่สุดว่าลืมหรือไม่ลืม

  • src/orders/dto/cart-response.dto.ts — สัญญา: ต้องมีแค่ชนิดข้อมูลของ response ตามสัญญา (CartProductResponseDto, CartResponseDto) · ต้องไม่มี decorator และไม่มี method
  • src/orders/cart.mapper.ts — สัญญา: ต้อง export toCartResponse() ที่ map products[].id จาก item.productId · ต้องไม่ส่ง address, email, phone, createdAt ออกไป และไม่แตะฐานข้อมูล
  • src/orders/orders.service.ts — สัญญา: ต้องทำทั้งการอ่านสินค้าและการเขียนคำสั่งซื้อใน $transaction เดียว, ต้อง throw NotFoundException ด้วยข้อความเดียวกับ ProductsService · ต้องไม่แก้ stock, ไม่ใช้ any, ไม่ใช้ as
  • src/orders/carts.controller.ts — สัญญา: ต้องเป็น @Controller('carts') กับ @Post('add') และรับ body ด้วย @Body() dto: AddCartDto · ต้องไม่ใส่ @HttpCode(), ไม่คิดเลขหรือแตะ Prisma ใน controller
  • src/orders/orders.module.ts — สัญญา: ต้องประกาศ controllers: [CartsController] และ providers: [OrdersService] · ต้องไม่ import PrismaModule ซ้ำ (ตอนตั้งค่า Prisma ทำให้มันเป็น global module แล้ว)
  • src/app.module.ts — สัญญา: ต้องเพิ่ม OrdersModule ต่อจาก ProductsModule ใน imports · ต้องไม่แตะ ConfigModule, controllers หรือ providers เดิม
  • test/orders.e2e-spec.ts — สัญญา: ไฟล์ใหม่ที่มี it() เดียวสำหรับ POST /carts/add และเทียบ receipt ทั้งก้อนด้วย toEqual · test/products.e2e-spec.ts ไม่ถูกแตะเลย · ไฟล์นี้มาจาก prompt แยกในแชทที่สาม ไม่ใช่สองแชทแรก เพราะ agent ที่เขียน endpoint ไม่ควรเป็นตัวเดียวกับที่เขียน test ซึ่งใช้ตัดสินว่า endpoint นั้นถูกหรือผิด

สั่ง Cursor เขียน OrdersService

commit งานก่อน แล้วเปิดแชทใหม่ใน Cursor โหมด Agent (git add -A && git commit -m "chore: before orders service") — prompt แรกของบทนี้ยาวที่สุดในคอร์ส เพราะมันต้องบอกทั้งสูตรคำนวณ ทั้งผลลัพธ์ที่ต้องได้เมื่อ transaction ล้ม และยกไฟล์ @src/products/products.service.ts กับ @src/products/product.mapper.ts เป็นแบบอย่างของสไตล์โปรเจกต์ ให้ AI ไม่ต้องเดา

ก่อนส่ง อ่านกติกาของคอร์สอีกครั้ง: AI พิมพ์แทนคุณได้ แต่คุณต้องอธิบายทุกบรรทัดได้ — ถ้าอธิบายไม่ได้ แปลว่ายังไม่ผ่านบทนี้

สร้าง OrdersService ที่บันทึกคำสั่งซื้อใน transaction และคืน cart ตามรูปทรงใน docs/api-spec.md ผลลัพธ์ที่ต้องได้: - มี service ที่รับ AddCartDto แล้วคืน receipt ตามรูปทรง "Order receipt" ใน docs/api-spec.md — สินค้า id 1 จำนวน 2 ชิ้นต้องได้ total 19.98, discountedPrice 17.89 (ไม่ใช่ 18), discountedTotal 17.89, totalProducts 1, totalQuantity 2 - total ของรายการ = price × quantity และ discountedPrice = total × (1 − discountPercentage / 100) สินค้าที่ไม่มีส่วนลดให้ถือว่าส่วนลดเป็น 0 (discountedPrice เท่ากับ total) - total ของ cart = ผลรวม total ทุกรายการ, discountedTotal = ผลรวม discountedPrice, totalProducts = จำนวนรายการ, totalQuantity = ผลรวม quantity - ตัวเลขเงินทุก field ปัดทศนิยม 2 ตำแหน่งเหมือนกันหมด ไม่มี field ไหนปัดเป็นจำนวนเต็ม - products[].id ใน receipt คือ id ของสินค้า (ไม่ใช่ id ของแถว OrderItem) และเรียงตามลำดับที่ client ส่งมา - สินค้าที่ไม่มีส่วนลด → ไม่มี key discountPercentage ในรายการนั้นเลย (ไม่ใช่ null) - receipt ไม่มี address, email, phone หรือ createdAt - ถ้ามี id สินค้าที่ไม่มีจริงแม้แต่ตัวเดียว → NotFoundException ข้อความ Product ${id} not found (ตรงตัวอักษรเหมือน GET /products/:id) และไม่มีแถว Order หรือ OrderItem ถูกบันทึกเลย (การอ่านสินค้าและการเขียนคำสั่งซื้อต้องอยู่ใน transaction เดียวกัน) - stock ของสินค้าไม่เปลี่ยน - npm run build และ npm run lint ผ่าน ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ - ยังไม่ต้องสร้าง controller หรือ module — เป็น prompt ถัดไปในแชทใหม่ - ห้ามเขียน test — e2e test เป็น prompt แยกอีกอันในแชทถัดไป

ตรวจโค้ดที่ AI สร้าง

  • การอ่านสินค้าและการเขียนคำสั่งซื้ออยู่ใน transaction เดียวกัน และทุก query ข้างในวิ่งผ่าน client ของ transaction นั้น — ไม่มี query ไหนหลุดออกไปใช้ this.prisma ตรง ๆ
  • ตัวอย่าง 9.99 × 2 ที่ 10.48% ให้ discountedPrice เป็น 17.89 ไม่ใช่ 18 และ field เงินทุกตัวปัด 2 ตำแหน่งด้วยกติกาเดียวกัน
  • ลำดับของ products[] ใน receipt ตรงกับลำดับที่ client ส่งมา ไม่ใช่ลำดับที่ฐานข้อมูลคืนแถว
  • ข้อความ 404 ตรงกับ ProductsService ทุกตัวอักษร: Product ${id} not found
  • address, email, phone ถูกบันทึกลงคอลัมน์ของ Order แยกกัน (ไม่ใช่เก็บ object ทั้งก้อนเป็น JSON)
  • products[].id ใน receipt คือ id ของสินค้า ไม่ใช่ id ของ OrderItem และ receipt ไม่มี address, email, phone, createdAt
  • สินค้าที่ไม่มีส่วนลดไม่มี key discountPercentage เลย (ไม่ใช่ null)
  • ไฟล์ที่เปลี่ยนอยู่ใน src/orders/ ทั้งหมด ไม่มีโค้ดแก้ stock ไม่มี any, as หรือ ! และ import ทุกตัวลงท้ายด้วย .js

AI มักพลาดตรงนี้: คำนวณ discountedPrice เป็นจำนวนเต็มด้วย Math.round(...) เฉย ๆ (ได้ 18 ทั้งที่สัญญาของเราต้องการ 17.89) เพราะเคยเห็นสไตล์การปัดแบบนี้จาก API ตัวอย่างอื่นมาก่อน ให้ตรวจว่าปัด 2 ตำแหน่งเหมือน field เงินตัวอื่นทุกตัว ไม่มีข้อยกเว้น อีกกรณีคือดึงสินค้าด้วย this.prisma.product.findMany ไว้ก่อน เปิด transaction แล้วค่อยเปิด transaction เพื่อ create — แบบนั้นการอ่านไม่ได้อยู่ใน snapshot เดียวกับการเขียน และถ้า throw 404 ก็ไม่มีอะไรต้อง rollback จริง (ดูเหมือนทำงานถูก แต่ผิดเจตนา) กรณีที่สามคือ mapper ส่ง item.id ออกไปเป็น products[].id ซึ่งจะทำให้ลิงก์ไปหน้าสินค้าของ React พาไปสินค้าผิดตัว

// src/orders/dto/cart-response.dto.ts
export class CartProductResponseDto {
  id: number;
  title: string;
  price: number;
  quantity: number;
  total: number;
  discountPercentage?: number;
  discountedPrice: number;
  thumbnail: string;

export class CartResponseDto {
  id: number;
  userId: number;
  products: CartProductResponseDto[];
  total: number;
  discountedTotal: number;
  totalProducts: number;
  totalQuantity: number;
}
// src/orders/cart.mapper.ts
import type { Order, OrderItem } from '../generated/prisma/client.js';
import { CartResponseDto } from './dto/cart-response.dto.js';

export type OrderWithItems = Order & { items: OrderItem[] };

export function toCartResponse(order: OrderWithItems): CartResponseDto {
  return {
    id: order.id,
    userId: order.userId,
    products: order.items.map((item) => ({
      id: item.productId,
      title: item.title,
      price: item.price,
      quantity: item.quantity,
      total: item.total,
      ...(item.discountPercentage !== null ? { discountPercentage: item.discountPercentage } : {}),
      discountedPrice: item.discountedPrice,
      thumbnail: item.thumbnail,
    })),
    total: order.total,
    discountedTotal: order.discountedTotal,
    totalProducts: order.totalProducts,
    totalQuantity: order.totalQuantity,
  };
}
// src/orders/orders.service.ts
import { Injectable, NotFoundException } from '@nestjs/common';
import { PrismaService } from '../prisma/prisma.service.js';
import { toCartResponse } from './cart.mapper.js';
import { AddCartDto } from './dto/add-cart.dto.js';
import { CartResponseDto } from './dto/cart-response.dto.js';

function round2(value: number): number {
  return Math.round(value * 100) / 100;
}

@Injectable()
export class OrdersService {
  constructor(private readonly prisma: PrismaService) {}

  async create(dto: AddCartDto): Promise<CartResponseDto> {
    const order = await this.prisma.$transaction(async (tx) => {
      const ids = dto.products.map((product) => product.id);
      const products = await tx.product.findMany({ where: { id: { in: ids } } });
      const productById = new Map(products.map((product) => [product.id, product]));

      const items = dto.products.map(({ id, quantity }) => {
        const product = productById.get(id);
        if (!product) {
          throw new NotFoundException(`Product ${id} not found`);
        }
        const total = round2(product.price * quantity);
        const discountedPrice = round2(total * (1 - (product.discountPercentage ?? 0) / 100));
        return {
          productId: product.id,
          title: product.title,
          thumbnail: product.thumbnail,
          price: product.price,
          discountPercentage: product.discountPercentage,
          quantity,
          total,
          discountedPrice,
        };
      });

      return tx.order.create({
        data: {
          userId: dto.userId,
          address: dto.address.address,
          email: dto.address.email,
          phone: dto.address.phone,
          total: round2(items.reduce((sum, item) => sum + item.total, 0)),
          discountedTotal: round2(items.reduce((sum, item) => sum + item.discountedPrice, 0)),
          totalProducts: items.length,
          totalQuantity: items.reduce((sum, item) => sum + item.quantity, 0),
          items: { create: items },
        },
        include: { items: { orderBy: { id: 'asc' } } },
      });
    });

    return toCartResponse(order);
  }
}

  • log ตอน start มี Mapped {/carts/add, POST} route — path รวมกันได้ POST /carts/add ไม่มี /orders โผล่ที่ไหน

เขียน e2e test ของ POST /carts/add ให้ตรงกับสัญญาใน docs/api-spec.md @docs/api-spec.md ผลลัพธ์ที่ต้องได้: - ไฟล์ใหม่ test/orders.e2e-spec.ts ที่ npm run test:e2e เก็บไปรันด้วย (ไม่ต้องแก้ package.json — script นี้มีอยู่แล้ว) - boot แอปจริงด้วย Test.createTestingModule({ imports: [AppModule] }) แล้วยิงผ่าน supertest ที่ app.getHttpServer() — ไม่ mock อะไรเลย ไม่ยิงไป URL หรือ port ภายนอก และปิดแอปด้วย app.close() ใน afterAll - beforeAll ตั้ง ValidationPipe แบบ global ให้ตรงกับ src/main.ts ทุกตัวเลือก (whitelist, transform, transformOptions.enableImplicitConversion) เพราะ createNestApplication() ไม่ได้รัน main.ts ให้ - หนึ่ง test: POST /carts/add ด้วย body {"userId":1,"products":[{"id":1,"quantity":2}],"address":{"address":"1 Sukhumvit Rd","email":"a@b.com","phone":"0812345678"}} → 201 - เทียบ body ทั้งก้อนด้วย expect(response.body).toEqual({...}) กับ receipt ที่คิดเลขเองจาก docs/api-spec.md: userId 1, totalProducts 1, totalQuantity 2, total 19.98, discountedTotal 17.89 และ products ชิ้นเดียวที่ id 1 title "Velvet Matte Lipstick" price 9.99 quantity 2 total 19.98 discountPercentage 10.48 discountedPrice 17.89 - ต้องเป็น toEqual กับ body ทั้งก้อน ไม่ใช่ toMatchObject และไม่ใช่ไล่ expect ทีละ field — field ที่เกินมาหรือถูกเปลี่ยนชื่อต้องทำให้ test ล้ม ไม่ใช่ผ่านไปเงียบ ๆ - id ของคำสั่งซื้อใช้ expect.any(Number) เพราะ test นี้สร้างคำสั่งซื้อจริงทุกครั้งที่รัน เลขจึงเปลี่ยนทุกรอบ ส่วน thumbnail ใช้ expect.any(String) - import ในไฟล์ test ลงท้ายด้วย .js ตามกติกา ESM ของโปรเจกต์ ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ — Vitest กับ supertest มากับ scaffold แล้ว - ห้ามแก้ไฟล์ใน src/ เด็ดขาด ถ้า test ไม่ผ่านให้บอกผมว่าไม่ผ่านข้อไหน ห้ามแก้โค้ดให้ test ผ่านเอง - ห้ามแตะ test/products.e2e-spec.ts - ห้ามรัน test ให้ ผมจะรันเอง

ตรวจ test ที่ AI เขียนก่อนจะเชื่อมัน — ข้อที่สองด้านล่างคือข้อที่พลาดง่ายที่สุดในบทนี้ และเป็นข้อที่ทำให้ test เขียวทั้งที่สัญญาพังไปแล้ว

  • git status ต้องเห็นไฟล์ใหม่แค่ test/orders.e2e-spec.ts ไฟล์เดียว — ไม่มีไฟล์ใน src/ ถูกแก้ ถ้ามี แปลว่า agent ไปแก้โค้ดให้เข้ากับ test ของมันเอง ให้ย้อนกลับแล้วสั่งใหม่
  • receipt ถูกเทียบด้วย toEqual กับ object ทั้งก้อน — ไม่ใช่ toMatchObject และไม่ใช่ expect(body.total).toBe(19.98) ไล่ทีละบรรทัด สองแบบหลังมองไม่เห็น field ที่เกินมาหรือถูกเปลี่ยนชื่อ: ถ้าวันหนึ่ง mapper เปลี่ยน thumbnail เป็น thumbnailUrl test จะยังเขียวทั้งที่ React app พังไปแล้ว ส่วน toEqual จะล้มพร้อมบอกทั้ง field ที่หายไปและ field ที่เกินมา
  • test/products.e2e-spec.ts ไม่ถูกแก้แม้แต่บรรทัดเดียว
  • ทุก request ยิงผ่าน request(app.getHttpServer()) — ไม่มี http://localhost:3000 หรือเลข port โผล่ในไฟล์ และไม่มีการ mock PrismaService ทิ้ง
  • beforeAll มี app.useGlobalPipes(...) ที่ค่าตรงกับ src/main.ts ทั้งสามตัว และ afterAll เรียก app.close()

โค้ดอ้างอิงของหัวข้อนี้ — เป็นหนึ่งในวิธีที่ถูก ของคุณไม่จำเป็นต้องเหมือนทุกบรรทัด ขอแค่ผ่านผลลัพธ์ที่ต้องได้ข้างบน

import { Test, TestingModule } from '@nestjs/testing';
import { INestApplication, ValidationPipe } from '@nestjs/common';
import request from 'supertest';
import { AppModule } from './../src/app.module.js';

describe('Orders contract (e2e)', () => {
  let app: INestApplication;

  beforeAll(async () => {
    const moduleFixture: TestingModule = await Test.createTestingModule({
      imports: [AppModule],
    }).compile();

    app = moduleFixture.createNestApplication();
    app.useGlobalPipes(
      new ValidationPipe({
        whitelist: true,
        transform: true,
        transformOptions: { enableImplicitConversion: true },
      }),
    );
    await app.init();
  });

  afterAll(async () => {
    await app.close();
  });

  it('POST /carts/add → 201, discountedPrice rounds to 2dp', async () => {
    const response = await request(app.getHttpServer())
      .post('/carts/add')
      .send({
        userId: 1,
        products: [{ id: 1, quantity: 2 }],
        address: { address: '1 Sukhumvit Rd', email: 'a@b.com', phone: '0812345678' },
      })
      .expect(201);

    expect(response.body).toEqual({
      id: expect.any(Number),
      userId: 1,
      products: [
        {
          id: 1,
          title: 'Velvet Matte Lipstick',
          price: 9.99,
          quantity: 2,
          total: 19.98,
          discountPercentage: 10.48,
          discountedPrice: 17.89,
          thumbnail: expect.any(String),
        },
      ],
      total: 19.98,
      discountedTotal: 17.89,
      totalProducts: 1,
      totalQuantity: 2,
    });
  });
});

บรรทัด app.useGlobalPipes(...) ต้องอยู่ที่นี่ด้วยเหตุผลเดียวกับใน spec ของ products: createNestApplication() สร้างแอปจาก AppModule เท่านั้น ไม่ได้รัน src/main.ts ให้ ค่าทั้งสามจึงต้องตรงกับใน main.ts ทุกตัว — ไม่อย่างนั้น spec นี้จะทดสอบแอปคนละตัวกับที่ผู้ใช้จริงเจอ และวันที่มีคนเพิ่ม test ของเคส 400 เข้ามา มันจะผ่านทั้งที่ไม่ควรผ่าน เพราะไม่มี pipe ตัวไหนตรวจ body เลย

ส่วน .send({...}) ของ supertest แปลง object เป็น JSON แล้วใส่ header Content-Type: application/json ให้เอง จึงไม่ต้องเขียน JSON.stringify หรือ header เองเหมือนตอนยิงด้วย curl

test นี้ยิง POST /carts/add จริง แปลว่ารันหนึ่งครั้งเท่ากับสร้างคำสั่งซื้อเพิ่มอีกหนึ่งใบในฐานข้อมูล — ถ้ารัน npm run test:e2e หลังจากยิง curl ทั้งสี่กรณีไปแล้ว แล้วย้อนไปนับแถวใน Order อีกครั้ง จำนวนจะเพิ่มจาก 1 เป็น 2 นั่นไม่ใช่ transaction รั่ว แต่เป็นเพราะ test นี้เองที่สั่งซื้อเพิ่ม และเพราะรันซ้ำได้เรื่อย ๆ แบบนี้ id ของคำสั่งซื้อจึงต้องปล่อยเป็น expect.any(Number) คู่กับ thumbnail ที่เป็น expect.any(String) เพราะ URL ของรูปมาจาก seed ส่วนตัวเลขที่เหลือคิดจากสัญญาได้หมดจึงถูกตรึงไว้ทุกตัว — toEqual ยังจับ field ที่เกินมาหรือถูกเปลี่ยนชื่อได้เหมือนเดิม เพราะสอง expect.any(...) นี้ผ่อนแค่ค่า ไม่ได้ผ่อนว่า key ไหนมีได้บ้าง

รันเฉพาะไฟล์นี้ได้ด้วย npm run test:e2e -- orders เมื่อไม่อยากรอ spec ของ products ทั้งเก้าข้อ
