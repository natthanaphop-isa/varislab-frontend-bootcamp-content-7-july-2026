POST /auth/login และ Access Token

เมื่อจบบทนี้ คุณจะสามารถ

  • อ่าน JWT ออกทีละส่วน และอธิบายได้ว่าทำไมสิ่งที่อยู่ใน payload ถือว่าเปิดเผย ไม่ใช่ความลับ
  • ตั้งค่า JwtModule ให้อ่าน secret จาก .env ผ่าน ConfigService โดยแอปจะไม่ยอม boot ถ้าลืมตั้งค่า
  • ออกแบบข้อความ error ของการ login ที่ไม่บอกใบ้ว่าอีเมลไหนมีอยู่ในระบบ

JWT คืออะไร และมันไม่ได้ปกปิดอะไรเลย

JWT คือสตริงสามท่อนคั่นด้วยจุด header.payload.signature สองท่อนแรกเป็น JSON ที่เข้ารหัสด้วย base64url เฉย ๆ — ใครก็ตามที่ถือ token อยู่ถอดอ่านได้ทันทีโดยไม่ต้องมีกุญแจอะไร ลองเองได้ในส่วนตรวจท้ายบท

นี่คือจุดที่เข้าใจผิดกันบ่อยที่สุด: signature ไม่ได้ปิดบังข้อมูล มันรับประกันว่าข้อมูลไม่ถูกแก้ ท่อนที่สามคือลายเซ็นที่คำนวณจากสองท่อนแรกรวมกับ secret ที่มีแต่ server รู้ ถ้าใครแก้ role ใน payload จาก USER เป็น ADMIN ลายเซ็นเดิมจะไม่ตรงกับเนื้อหาใหม่อีกต่อไป และ server จะปฏิเสธ token นั้น — แต่เขาอ่าน role เดิมได้ตั้งแต่แรกอยู่ดี

ผลที่ตามมาเป็นกฎข้อเดียวที่ต้องจำ: อย่าใส่อะไรที่เป็นความลับลงใน payload ไม่ใส่รหัสผ่าน ไม่ใส่ hash ไม่ใส่เลขบัตร สิ่งที่ใส่ได้คือข้อมูลที่ถ้าเจ้าของ token อ่านเองก็ไม่เป็นไร ซึ่งสำหรับเราคือ sub (เลข id ของผู้ใช้ตามธรรมเนียมของ JWT), email และ role

ที่ต้องมี role อยู่ใน payload เพราะเราอยากให้การตรวจสิทธิ์ทำได้โดยไม่ต้องแตะฐานข้อมูลทุก request — นั่นคือข้อดีหลักของ token แบบนี้ และเป็นข้อเสียหลักของมันพร้อมกัน เพราะ token ที่ออกไปแล้วจะถือข้อมูลเก่าติดตัวไปจนหมดอายุ เรื่องนี้จะกลับมาเป็นประเด็นจริง ๆ ในบทที่ทำ role

สองใบ แต่บทนี้ทำใบแรกก่อน

สัญญาใน docs/auth-spec.md บอกว่า POST /auth/login ต้องคืน token สองใบ คือ accessToken กับ refreshToken บทนี้จะทำแค่ใบแรก แล้วบทที่ว่าด้วย refresh จะมาเติมใบที่สองให้ครบสัญญา — เหมือนตอนต้นคอร์สที่เราเขียนสัญญาของสินค้าครบทุก endpoint ก่อน แล้วค่อยทยอยสร้างทีละตัว

เหตุผลที่แยกสองใบตั้งแต่ในสัญญา: access token ต้องอายุสั้นเพราะมันเดินทางไปกับทุก request จึงมีโอกาสรั่วสูงที่สุด ส่วน refresh token อายุยาวแต่ถูกใช้นาน ๆ ครั้งและเก็บไว้ที่เดียว ถ้าใช้ token ใบเดียวอายุยาวทำทั้งสองหน้าที่ เราจะได้ของที่รั่วง่ายและอยู่ได้นานพร้อมกัน ซึ่งเป็นส่วนผสมที่แย่ที่สุด

secret ที่ลืมตั้งค่าต้องทำให้แอปไม่ยอม start

.env ของเรามีสี่บรรทัดมาตั้งแต่ตอนตั้งค่าฐานข้อมูล บทนี้เพิ่มเป็นหก

JWT_SECRET=dev-only-change-me-in-production
JWT_EXPIRES_IN=900

สองเรื่องที่ตั้งใจเลือกไว้แบบนี้

อายุเก็บเป็นวินาทีล้วน ๆ ไม่ใช่ "15m" — @nestjs/jwt รับได้ทั้งตัวเลขและสตริงอย่าง "15m" แต่ชนิดของสตริงที่มันรับเป็น template literal type แบบเฉพาะเจาะจง ไม่ใช่ string ทั่วไป แปลว่าค่าที่อ่านมาจาก .env (ซึ่งเป็น string) จะใส่ลงไปตรง ๆ ไม่ได้ และทางลัดที่คนส่วนใหญ่ใช้คือ as ซึ่งกติกาของโปรเจกต์เราห้ามไว้ การเก็บเป็นวินาทีแล้วแปลงด้วย Number() เลี่ยงปัญหานี้ทั้งก้อน แถมทำให้ตรวจได้แม่นว่า exp − iat เท่ากับ 900 พอดี

อ่านด้วย getOrThrow ไม่ใช่ get — เหตุผลเดียวกับตอนอ่าน APP_URL: get คืน undefined เงียบ ๆ ถ้าไม่มีคีย์นั้น ซึ่งสำหรับ secret แปลว่าแอปจะ start ขึ้นมาได้ตามปกติแล้วเซ็น token ด้วยค่าว่าง กลายเป็นระบบที่ดูเหมือนทำงานแต่ใครก็ปลอม token ได้ ส่วน getOrThrow ทำให้แอปพังตั้งแต่ตอน boot ซึ่งเป็นเวลาที่ถูกต้องที่สุดที่จะพัง

ค่า JWT_SECRET ในไฟล์ตัวอย่างนี้เป็นค่าสำหรับเครื่องเราเท่านั้น ของจริงต้องเป็นค่าสุ่มยาว ๆ ที่ไม่มีใครเดาได้ และต้องไม่ใช่ค่าเดียวกับที่ commit ลง repo — .env ถูก gitignore ไว้แล้วตั้งแต่ต้นคอร์ส ส่วน .env.example ที่ commit ไปด้วยนั้นถือเป็นแบบฟอร์ม ไม่ใช่ที่เก็บค่าจริง

ข้อความ error ที่ช่วยเหลือมากเกินไป

ตอน login มีสองทางที่พลาดได้: ไม่มีอีเมลนั้นในระบบ กับมีอีเมลแต่รหัสผ่านผิด สัญชาตญาณของคนเขียน API คือแยกสองข้อความให้ชัดเพื่อให้ผู้ใช้แก้ถูกจุด และนั่นคือการเปิดช่องให้ใครก็ได้ไล่ตรวจว่าอีเมลไหนสมัครไว้กับเราบ้าง โดยไม่ต้องรู้รหัสผ่านสักตัว

ข้อมูลนั้นมีค่าจริงสำหรับคนที่ตั้งใจไม่ดี: รายชื่ออีเมลที่ยืนยันแล้วว่ามีบัญชีอยู่ คือรายชื่อเป้าหมายสำหรับการลองรหัสผ่านที่รั่วมาจากที่อื่น สัญญาของเราจึงบังคับว่าทั้งสองกรณีต้องได้ 401 พร้อมข้อความ Invalid credentials เหมือนกันเป๊ะ

สร้าง endpoint POST /auth/login ที่คืน access token แบบ JWT ตาม docs/auth-spec.md @docs/auth-spec.md @src/auth/auth.service.ts @src/auth/auth.module.ts ผลลัพธ์ที่ต้องได้: - POST /auth/login ด้วยอีเมลกับรหัสผ่านที่ถูกต้อง → 200 และ body เป็น { "accessToken": "<JWT>" } - payload ของ token ถอดออกมามี sub (id ของผู้ใช้), email และ role และ exp ลบ iat ได้เท่ากับ JWT_EXPIRES_IN พอดี - payload ต้องไม่มีรหัสผ่านหรือ hash อยู่เลย - secret และอายุอ่านจาก .env ผ่าน ConfigService ด้วย getOrThrow — ถ้าลบบรรทัด JWT_SECRET ทิ้งแล้ว start ใหม่ แอปต้อง boot ไม่ขึ้น ไม่ใช่ boot ขึ้นแล้วค่อยพังตอนมีคนยิง login - อายุเก็บใน .env เป็นจำนวนวินาที และแปลงเป็น number ก่อนส่งให้ JwtModule ห้ามใช้ as เพื่อให้ผ่าน type - รหัสผ่านผิด กับ อีเมลที่ไม่มีในระบบ → 401 ทั้งคู่ โดย message เป็นข้อความเดียวกันคือ Invalid credentials — ต้องแยกไม่ออกว่าอีเมลนั้นมีอยู่จริงหรือไม่ - ใช้ PasswordService ตัวที่มีอยู่แล้วในการเทียบรหัสผ่าน ห้าม import bcrypt เพิ่มที่ไฟล์อื่น - POST /auth/signup ไม่เปลี่ยนพฤติกรรม และ npm run test:e2e ยังได้ Tests 11 passed (11) ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ (@nestjs/jwt ติดตั้งแล้ว) - ห้ามใช้ passport หรือ @nestjs/passport - ห้ามแตะไฟล์ใน test/ และห้ามแก้อะไรใน prisma/ - ห้ามแก้ .env หรือ .env.example — ผมเติมสองบรรทัดนั้นเองแล้ว - ยังไม่ต้องทำ guard, refresh token, logout หรือ GET /auth/me - ห้ามใช้ any, as หรือ !

ตรวจโค้ดที่ AI สร้าง

  • ทั้งสองทางที่ล้มเหลวโยน exception ตัวเดียวกันพร้อมข้อความเดียวกัน — อ่านโค้ดแล้วชี้ได้ว่าไม่มีทางแยกแยะจากภายนอก
  • มี getOrThrow ไม่ใช่ get และไม่มีค่า fallback แบบ ?? 'secret' แอบอยู่ (fallback แบบนั้นทำให้บรรทัด getOrThrow ไร้ความหมายทันที)
  • อายุถูกแปลงเป็นตัวเลขด้วย Number() และไม่มี as ที่ไหนเลยในไฟล์
  • payload มีแค่ sub, email, role — ไม่มีแถมอย่าง passwordHash หรือ object ผู้ใช้ทั้งก้อน
  • JwtModule.registerAsync ไม่ได้ import ConfigModule ซ้ำเข้ามา — มันเป็น global อยู่แล้ว
  • การเทียบรหัสผ่านเรียกผ่าน PasswordService — grep -rn "bcrypt" src/ ยังเจอไฟล์เดียวเหมือนเดิม
  • git status ไม่มี .env โผล่มา (มันถูก gitignore ไว้) แต่ .env.example ต้องมีบรรทัดใหม่ที่ commit ไปด้วย

AI มักพลาดตรงนี้: เขียน config.get<string>('JWT_SECRET') ซึ่ง compile ผ่านและทำงานได้ตราบใดที่ค่ามีอยู่ — แล้ววันที่ deploy ขึ้น server ที่ลืมตั้ง env แอปจะ start ขึ้นตามปกติและเซ็น token ด้วย undefined อีกกรณีที่เจอบ่อยคือแยกข้อความ error เป็น "User not found" กับ "Wrong password" เพราะมันดูเป็นมิตรกับผู้ใช้กว่า ทั้งที่มันคือการยืนยันให้คนนอกฟรี ๆ ว่าอีเมลไหนมีบัญชีอยู่

โค้ดอ้างอิงของบทนี้ — เป็นหนึ่งในวิธีที่ถูก ของคุณไม่จำเป็นต้องเหมือนทุกบรรทัด ขอแค่ผ่านผลลัพธ์ที่ต้องได้:

// src/auth/auth.module.ts
import { Module } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import { JwtModule } from '@nestjs/jwt';
import { AuthController } from './auth.controller.js';
import { AuthService } from './auth.service.js';
import { PasswordService } from './password.service.js';

@Module({
  imports: [
    JwtModule.registerAsync({
      useFactory: (config: ConfigService) => ({
        secret: config.getOrThrow<string>('JWT_SECRET'),
        signOptions: {
          expiresIn: Number(config.getOrThrow<string>('JWT_EXPIRES_IN')),
        },
      }),
      inject: [ConfigService],
    }),
  ],
  controllers: [AuthController],
  providers: [AuthService, PasswordService],
})
export class AuthModule {}
// src/auth/auth.service.ts — เฉพาะส่วนที่เพิ่ม
// (JwtService เข้ามาอยู่ใน constructor เพิ่มจาก PrismaService และ PasswordService)
  async login(dto: LoginDto): Promise<AuthResponseDto> {
    const user = await this.prisma.user.findUnique({
      where: { email: dto.email },
    });

    if (user === null) {
      throw new UnauthorizedException('Invalid credentials');
    }

    const matches = await this.passwords.compare(dto.password, user.passwordHash);

    if (!matches) {
      throw new UnauthorizedException('Invalid credentials');
    }

    const payload = { sub: user.id, email: user.email, role: user.role };

    return { accessToken: await this.jwt.signAsync(payload) };
  }

สองกรณีนี้เขียนแยก if กันเพื่อให้อ่านง่าย แต่ทั้งคู่โยนของชิ้นเดียวกัน จากภายนอกจึงแยกไม่ออก ถ้าวันหนึ่งมีคนมาแก้ให้ข้อความต่างกัน "เพื่อ debug ง่ายขึ้น" นั่นคือการเปิดช่องโหว่กลับเข้ามา

// src/auth/dto/login.dto.ts
import { IsEmail, IsString, MinLength } from 'class-validator';

export class LoginDto {
  @IsEmail()
  email: string;

  @IsString()
  @MinLength(8)
  password: string;
}
