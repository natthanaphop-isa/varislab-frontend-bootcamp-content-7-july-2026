และของที่ใช้งานได้จริงห้าอย่างนี้

  • ห้า endpoint ที่รูปทรง response ตรงกับ dummyjson: GET /products/categories, GET /products, GET /products/{id}, GET /products/category/{slug} และ POST /carts/add
  • สัญญาที่ตรวจอัตโนมัติ — npm run contract:check เทียบ key ของ response เราเทียบกับ dummyjson ทั้งแปดเคส รวมถึงเคส 404 และหมวดที่ไม่มีจริง
  • validation ที่กันขยะ — ValidationPipe แบบ global พร้อม whitelist และ DTO ที่ประกาศกฎไว้ครบ ทำให้ payload ผิดรูปได้ 400 พร้อมข้อความที่อ่านรู้เรื่อง
  • คำสั่งซื้อที่ atomic — POST /carts/add เขียน Order กับ OrderItem ในทรานแซกชันเดียว
  • เอกสารและการเชื่อมต่อ — Swagger UI ที่ /api พร้อม response schema ทุก endpoint, CORS ที่เปิดให้เฉพาะ origin ของ Vite และ React app ของจริงที่รันบน API นี้ได้ครบวงจรโดยแก้แค่ base URL หนึ่งบรรทัด

สิ่งที่คุณควรอธิบายได้ตอนนี้

ตอบทีละข้อโดยยังไม่เปิดโค้ด ข้อไหนตอบไม่ได้ให้กลับไปอ่านบทนั้นอีกครั้ง — นี่คือมาตรวัดเดียวที่บอกว่าคุณเป็นเจ้าของโค้ดนี้จริงหรือเปล่า

  • ทำไม price, rating และ discountPercentage ประกาศเป็น Float ใน schema.prisma (บทที่ 7)
  • ทำไม id ของ Product ไม่ใช่ @default(autoincrement()) (บทที่ 7 และ 9)
  • whitelist: true ใน ValidationPipe ตัดอะไรทิ้ง และทำไมการตัดทิ้งเงียบ ๆ ปลอดภัยกว่าปล่อยผ่าน (บทที่ 13 และ 17)
  • ทำไม @Get('categories') ต้องประกาศก่อน @Get(':id') และจะเกิดอะไรถ้าสลับกัน (บทที่ 10 และ 12)
  • ทำไม limit=0 ถูกแปลเป็น take: undefined แทนที่จะเป็น take: 0 (บทที่ 13)
  • ทำไม mapper ไม่ใส่ key brand เลยเมื่อค่าในฐานข้อมูลเป็น null (บทที่ 11)
  • callback ที่ส่งให้ $transaction rollback อะไรเมื่อมีการ throw ข้างใน และ client ที่ควรใช้ข้างในคือตัวไหน (บทที่ 18)
  • ทำไม endpoint ของคำสั่งซื้อชื่อ /carts/add ไม่ใช่ /orders ที่ดูถูกหลักกว่า (บทที่ 19)
  • origin ที่ใส่ใน enableCors ป้องกันอะไร และไม่ป้องกันอะไร (บทที่ 20)
  • ทำไม response DTO ต้องเป็น class ไม่ใช่ interface (บทที่ 11 และ 22)

ก้าวต่อไป

  • ใส่ auth ด้วย Guards — ตอนนี้ใครก็ยิง POST /carts/add ได้ ถ้าจะผูกคำสั่งซื้อกับผู้ใช้จริงต้องมี token และ guard มาคั่น ทบทวนได้จาก Week_09 บทที่ 52 — ป้องกัน Route ด้วย Guards แล้วเขียน prompt ในรูปแบบห้าส่วนเดิมให้ Cursor ทำ
  • เขียน e2e test ด้วย Vitest — contract:check ตรวจรูปทรง response แต่ยังไม่ใช่ test suite ที่รันใน CI ได้ ต่อยอดจาก Week_09 บทที่ 67–69 โดยเริ่มจากเคสที่เจ็บที่สุดก่อน: limit=abc ต้องได้ 400 และ /products/9999 ต้องได้ 404
  • ขึ้น production ด้วย migrate deploy — บนเครื่องเราใช้ prisma migrate dev แต่บน server ต้องใช้ prisma migrate deploy ซึ่งรัน migration ที่ commit ไว้เท่านั้นและไม่สร้างไฟล์ใหม่ ลองย้ายฐานข้อมูลขึ้น Postgres แบบ hosted ตาม Week_08 บทที่ 18 — Hosted PostgreSQL กับ Neon แล้วเปลี่ยนแค่ DATABASE_URL กับ CORS_ORIGIN
  • ตัด stock ในทรานแซกชันของคำสั่งซื้อ — ตอนนี้สั่งซื้อแล้ว stock ไม่ลด เพราะ dummyjson ไม่ได้ทำ แต่ของจริงต้องลด และต้องลดใน $transaction เดียวกับที่สร้าง Order พร้อมปฏิเสธเมื่อของไม่พอ — เป็นแบบฝึกหัดที่ดีเรื่อง business rule กับ atomicity
  • เลิกพึ่ง dummyjson ตอน seed — prisma/seed.ts ยัง fetch สดจากอินเทอร์เน็ต ซึ่งหมายถึง seed พังได้เมื่อ API ต้นทางล่มหรือเปลี่ยนข้อมูล ย้ายไปอ่านจากไฟล์ JSON ที่ commit ไว้ในโปรเจกต์ แล้ว seed จะได้ผลเหมือนกันทุกครั้งและทำงานแบบ offline ได้

ปิดท้าย

สิ่งที่คอร์สนี้ฝึกจริง ๆ ไม่ใช่การพิมพ์โค้ด NestJS ให้เร็วขึ้น แต่เป็นการสั่งงานให้แคบพอจะตรวจได้: จับสัญญาก่อนเขียนโค้ด แปลงสัญญาเป็น prompt ห้าส่วนที่ระบุไฟล์และข้อห้ามชัดเจน แล้วอ่านผลลัพธ์ทีละบรรทัดเทียบกับสัญญานั้น ยิ่ง AI พิมพ์ได้เร็วเท่าไร ความสามารถในการตรวจของคุณยิ่งเป็นตัวตัดสินคุณภาพงานมากขึ้นเท่านั้น เก็บกติกาข้อเดียวนี้ไปใช้กับทุกโปรเจกต์ต่อจากนี้

AI พิมพ์แทนคุณได้ แต่คุณต้องอธิบายทุกบรรทัดได้ — ถ้าอธิบายไม่ได้ แปลว่ายังไม่ผ่านบทนี้
