JWT Guard และ @Public()

เมื่อจบบทนี้ คุณจะสามารถ

  • ผูก guard แบบ global ด้วย APP_GUARD และอธิบายได้ว่าทำไมวิธีนี้ทำให้ e2e test มองเห็น guard ส่วน useGlobalGuards ใน main.ts ไม่ทำให้เห็น
  • บอกความต่างระหว่าง 401 กับ 403 ได้ และเลือกโยนตัวที่ถูกจาก guard
  • ใช้ test ชุดที่สะสมมาทั้งคอร์สเป็นเครื่องมือพิสูจน์ว่าการเปิด route สาธารณะกลับคืนนั้นครบถ้วนจริง

บทนี้มี prompt สองอันในสองแชท และ prompt แรกจะทำให้ e2e test แดงทั้งสิบเอ็ดข้อ — นั่นคือผลลัพธ์ที่ถูกต้องของขั้นนั้น ไม่ใช่ความผิดพลาดของคุณ prompt ที่สองจะทำให้มันกลับมาเขียวครบ ถ้าอ่านถึงตรงกลางแล้วรู้สึกว่าทำพัง ให้กลับมาอ่านย่อหน้านี้อีกครั้ง

guard ที่ผูกผิดที่ จะหายไปตอน test

โปรเจกต์นี้มีของที่ผูกแบบ global อยู่แล้วหนึ่งตัวคือ ValidationPipe ซึ่งประกาศไว้ใน src/main.ts และเราเจอผลข้างเคียงของมันมาแล้วตอนเขียน e2e test: createNestApplication() ไม่ได้รัน main.ts ให้ ทุก spec จึงต้องประกาศ useGlobalPipes(...) ซ้ำเองในไฟล์ test

ถ้าเราผูก guard ด้วยวิธีเดียวกัน คือ app.useGlobalGuards(...) ใน main.ts ผลจะเป็นแบบนี้: แอปจริงถูกป้องกัน แต่ e2e test ทั้งสิบเอ็ดข้อจะไม่เห็น guard เลยและยังเขียวสบายใจ ซึ่งแปลว่า test ชุดที่เราอุตส่าห์สะสมมาทั้งคอร์สจะบอกอะไรเกี่ยวกับ auth ไม่ได้สักอย่าง

เราจึงผูกอีกแบบ: ประกาศเป็น provider ที่ใช้ token พิเศษ APP_GUARD ใน providers ของ module ข้อแตกต่างคือ guard ตัวนี้เกิดจาก DI container และเดินทางมากับ module graph แปลว่า Test.createTestingModule({ imports: [AppModule] }) ได้มันติดมาด้วยโดยอัตโนมัติ — ไม่ต้องประกาศซ้ำในไฟล์ test และที่สำคัญกว่าคือลืมประกาศไม่ได้

ผลพลอยได้ที่เราต้องใช้จริงคือ guard ตัวนี้ inject อะไรก็ได้ ซึ่งจำเป็น เพราะมันต้องใช้ JwtService ตรวจลายเซ็น และ Reflector อ่าน metadata

ปิดทุกอย่างก่อน แล้วค่อยเปิดทีละเส้น

มีสองทางให้เลือกตอนตัดสินใจว่า route ไหนต้องมี token

วิธีลืมแล้วเกิดอะไรใครเจอก่อน
ติด guard ทีละเส้นที่ต้องป้องกันเส้นที่ลืมจะเปิดโล่งอยู่เงียบ ๆคนที่เจอช่องโหว่ — อาจไม่ใช่ฝ่ายเรา
ปิดทุกเส้นเป็นค่าปริยาย แล้วเปิดเฉพาะที่ตั้งใจเส้นที่ลืมจะปิดตายและพังทันทีเราเอง ตอนรัน test

ความผิดพลาดเกิดได้ทั้งสองทาง ต่างกันที่ว่าความผิดพลาดนั้นดังหรือเงียบ เราเลือกทางที่มันดัง และบทนี้จะทำให้ได้ยินเสียงนั้นจริง ๆ

เครื่องมือที่ใช้เปิดกลับคือ metadata: ติด @Public() ไว้กับ controller หรือ handler แล้วให้ guard อ่านค่านั้นก่อนตัดสินใจ จุดที่ต้องระวังคือ อ่านให้ครบทั้งสองระดับ — getAllAndOverride รับรายการมาสองอย่างคือ handler กับ class ถ้าอ่านแค่ระดับ handler การติด @Public() ไว้บนตัว controller ทั้งก้อนจะไม่มีผลเลย ซึ่งเป็นวิธีที่เราอยากใช้เปิด ProductsController ทั้งสี่เส้นในครั้งเดียว

401 หรือ 403

guard ที่คืน false เฉย ๆ จะทำให้ NestJS ตอบ 403 Forbidden ซึ่งเป็นคำตอบที่ผิดสำหรับกรณีไม่มี token

Statusความหมายในระบบของเรา
401 Unauthorized"ฉันไม่รู้ว่าคุณเป็นใคร"ไม่มี token, token ผิดรูป, ลายเซ็นไม่ตรง หรือหมดอายุ
403 Forbidden"ฉันรู้ว่าคุณเป็นใคร และคุณไม่ได้รับอนุญาต"token ถูกต้องทุกอย่าง แต่ role ไม่พอ — จะได้เจอในบทที่ทำ role

guard ของบทนี้จึง throw new UnauthorizedException() แทนการ return false ความต่างนี้ไม่ใช่เรื่องความสวยงามของตัวเลข: client ที่เจอ 401 รู้ว่าต้อง login ใหม่หรือ refresh token ส่วน 403 บอกว่าอย่าเสียเวลาลองอีก บัญชีนี้ทำสิ่งนี้ไม่ได้

Prompt แรก: ปิดทุกอย่าง

commit งานก่อน แล้วเปิดแชทใหม่ใน Cursor โหมด Agent (git add -A && git commit -m "chore: before jwt guard") — commit นี้สำคัญกว่าปกติ เพราะปลาย prompt นี้แอปจะอยู่ในสภาพที่ endpoint เดิมทั้งหมดเรียกไม่ได้ ถ้าอยากถอยกลับ git reset --hard ได้ทันที

ปิดทุก route ด้วย JWT guard แบบ global แล้วเปิด GET /auth/me ให้อ่านข้อมูลผู้ใช้จาก token @docs/auth-spec.md @src/auth/auth.module.ts @src/auth/auth.controller.ts ผลลัพธ์ที่ต้องได้: - GET /auth/me พร้อม header Authorization: Bearer <access token> → 200 และ body เป็น { id, email, role } ที่อ่านจาก payload ของ token ตรง ๆ ไม่ query ฐานข้อมูลซ้ำ - ไม่มี header, header ผิดรูป, token หมดอายุ หรือ token ที่เซ็นด้วย secret อื่น → 401 ทุกกรณี ไม่ใช่ 403 - POST /auth/signup และ POST /auth/login ยังเรียกได้โดยไม่ต้องมี token - guard ผูกแบบ global ผ่าน APP_GUARD ใน providers ของ module ไม่ใช่ app.useGlobalGuards() ใน main.ts เพราะมันต้อง inject JwtService กับ Reflector ได้ และเพราะ e2e test ที่ boot AppModule ต้องมองเห็น guard ตัวนี้ด้วย - guard อ่าน metadata ของ @Public ทั้งระดับ handler และระดับ class - request ที่ผ่าน guard มี payload แปะไว้ให้ handler อ่านต่อได้ โดยประกาศ type ของ request ให้ชัด ห้ามใช้ index signature หรือ any - ยังไม่ต้องเปิด route เดิม — ตอนจบ prompt นี้ GET /products/categories ต้องตอบ 401 ซึ่งถูกต้องแล้วสำหรับขั้นนี้ ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ - ห้ามใช้ passport หรือ @nestjs/passport - ห้ามแตะไฟล์ใน test/ เด็ดขาด - ห้ามแก้ src/products/, src/orders/ หรือ src/app.controller.ts ในรอบนี้ - ห้ามใช้ any, as หรือ !

ตรวจโค้ดที่ AI สร้าง

  • guard ลงทะเบียนด้วย { provide: APP_GUARD, useClass: ... } ใน providers — ไม่ใช่ app.useGlobalGuards() และไม่ใช่ @UseGuards() แปะทีละ controller
  • อ่าน metadata ด้วย getAllAndOverride พร้อมรายการ [context.getHandler(), context.getClass()] — ถ้าอ่านแค่ handler ตัวเดียว prompt ถัดไปจะเปิด route ไม่ได้และคุณจะหาสาเหตุนาน
  • getRequest<AuthenticatedRequest>() มี type argument จริง — ไม่ใช่ getRequest() เปล่า ๆ แล้วเขียน request['user'] = payload ซึ่งเป็น any ที่ปลอมตัวมา
  • verifyAsync<JwtPayload>(token) มี type argument — ไม่งั้น payload ที่ได้คือ any และมันจะไหลต่อไปทั้งแอป
  • โยน UnauthorizedException ทุกทางที่ล้มเหลว ไม่มี return false หลงเหลือ
  • แยก scheme ออกจาก token จริง — header ที่เขียนว่า Basic abc ต้องไม่ผ่าน ไม่ใช่แค่ตัด split(' ')[1] มาใช้โดยไม่ดูคำหน้า
  • git diff --stat test/ ว่างเปล่า

AI มักพลาดตรงนี้: คัดลอกตัวอย่างจากเอกสารของ NestJS มาตรง ๆ ซึ่งเขียนว่า request['user'] = payload บน request ที่ไม่ได้ประกาศ type — มันผ่าน compiler ได้เพราะ index signature ทำให้กลายเป็น any เงียบ ๆ ซึ่งขัดกับกติกาข้อ "ห้ามใช้ any" ของโปรเจกต์นี้ตรง ๆ อีกกรณีคือลืม context.getClass() ใน getAllAndOverride ซึ่งจะไม่มีอาการอะไรเลยจนกว่าจะถึง prompt ถัดไป แล้ว test จะยังแดงทั้งที่ติด @Public() ครบแล้ว

โค้ดอ้างอิงของหัวข้อนี้ — เป็นหนึ่งในวิธีที่ถูก ของคุณไม่จำเป็นต้องเหมือนทุกบรรทัด ขอแค่ผ่านผลลัพธ์ที่ต้องได้:

// src/auth/jwt-payload.interface.ts
import type { Request } from 'express';

export interface JwtPayload {
  sub: number;
  email: string;
  role: string;
  iat: number;
  exp: number;
}

export interface AuthenticatedRequest extends Request {
  user: JwtPayload;
}
// src/auth/public.decorator.ts
import { SetMetadata } from '@nestjs/common';

export const IS_PUBLIC_KEY = 'isPublic';

export const Public = () => SetMetadata(IS_PUBLIC_KEY, true);
// src/auth/jwt-auth.guard.ts
import {
  CanActivate,
  ExecutionContext,
  Injectable,
  UnauthorizedException,
} from '@nestjs/common';
import { Reflector } from '@nestjs/core';
import { JwtService } from '@nestjs/jwt';
import { IS_PUBLIC_KEY } from './public.decorator.js';
import type { AuthenticatedRequest, JwtPayload } from './jwt-payload.interface.js';

@Injectable()
export class JwtAuthGuard implements CanActivate {
  constructor(
    private readonly reflector: Reflector,
    private readonly jwt: JwtService,
  ) {}

  async canActivate(context: ExecutionContext): Promise<boolean> {
    const isPublic = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC_KEY, [
      context.getHandler(),
      context.getClass(),
    ]);

    if (isPublic) {
      return true;
    }

    const request = context.switchToHttp().getRequest<AuthenticatedRequest>();
    const [scheme, token] = request.header('Authorization')?.split(' ') ?? [];

    if (scheme !== 'Bearer' || token === undefined) {
      throw new UnauthorizedException();
    }

    try {
      request.user = await this.jwt.verifyAsync<JwtPayload>(token);
    } catch {
      throw new UnauthorizedException();
    }

    return true;
  }
}

ท่อน catch ที่ไม่รับตัวแปร error เลยเป็นความตั้งใจ: เราไม่อยากส่งรายละเอียดว่า token พังเพราะอะไรกลับไปให้ client เพราะนั่นคือข้อมูลที่ช่วยคนที่กำลังลองเดาอยู่ ส่วนถ้าอยาก debug ตอน dev ให้ log ไว้ฝั่ง server ไม่ใช่ใส่ลงใน response

// src/auth/auth.module.ts — เฉพาะส่วนที่เพิ่ม
import { APP_GUARD } from '@nestjs/core';
import { JwtAuthGuard } from './jwt-auth.guard.js';

  providers: [
    AuthService,
    PasswordService,
    { provide: APP_GUARD, useClass: JwtAuthGuard },
  ],

ถ้าอธิบายบรรทัดไหนไม่ได้ ยังไปต่อไม่ได้ — กลับไปอ่านส่วนแนวคิดก่อน

ผลลัพธ์ที่คาดหวัง — ทุกอย่างพัง และนั่นถูกแล้ว

เอา token จากบทที่แล้วมายิง GET /auth/me ได้ข้อมูลผู้ใช้กลับมา

{"id":1,"email":"student@example.com","role":"USER"}

แต่ endpoint ที่ทำมาทั้งคอร์สตอบ 401 กันหมด รวมถึง GET / ที่มากับ scaffold ตั้งแต่วันแรกและเราไม่เคยเขียนเองสักบรรทัด

{"message":"Unauthorized","error":"Unauthorized","statusCode":401}

สังเกตว่า GET /products/abc ที่เคยคาดหวัง 400 จาก ParseIntPipe ก็แดงด้วย เพราะในลำดับการทำงานของ NestJS guard ทำงานก่อน pipe request จึงถูกตัดตั้งแต่ก่อนถึงขั้นแปลงชนิดข้อมูล ถ้าของคุณแดงไม่ครบสิบเอ็ด แปลว่ามีอะไรต่างจากที่คาดไว้ ให้กลับไปอ่านโค้ดก่อนไปต่อ

ส่วนที่ ไม่ พังคือ Swagger — http://localhost:3000/api ยังเปิดได้ตามปกติ เพราะ SwaggerModule.setup() ติดตั้งตัวเองเป็น middleware ของ Express ไม่ใช่ route handler ของ NestJS จึงไม่มี handler ให้ guard ไปตรวจ และไม่มีที่ให้ติด @Public() ด้วย

นี่คือจุดที่ test ชุดที่สะสมมาตั้งแต่ต้นคอร์สพิสูจน์คุณค่าของตัวเอง มันไม่ได้บอกแค่ว่า "โค้ดใหม่ทำงานไหม" แต่บอกว่า "โค้ดใหม่ไปทำอะไรของเก่าพังหรือเปล่า" — และคำตอบตอนนี้คือพังหมด ซึ่งเราตั้งใจ ขั้นถัดไปคือทำให้มันเขียวกลับมาโดยไม่แตะไฟล์ test แม้แต่บรรทัดเดียว

Prompt ที่สอง: เปิด route เดิมกลับคืน

commit งานของ prompt แรกไว้ก่อน (git add -A && git commit -m "feat: jwt auth guard") แล้วเปิดแชทใหม่อีกครั้ง

เปิด route เดิมทั้งหกเส้นให้เรียกได้โดยไม่ต้องมี token ด้วย @Public() @src/auth/public.decorator.ts @src/products/products.controller.ts @src/orders/carts.controller.ts @src/app.controller.ts ผลลัพธ์ที่ต้องได้: - หกเส้นนี้กลับมาทำงานเหมือนก่อนใส่ guard ทุกประการโดยไม่ต้องส่ง token: GET /, GET /products/categories, GET /products, GET /products/:id, GET /products/category/:slug และ POST /carts/add - npm run test:e2e กลับมาได้ Test Files 3 passed (3) และ Tests 11 passed (11) — ข้อไหนยังแดงแปลว่ายังมี route ที่ลืมเปิด - POST /carts/add ต้องยิงได้โดยไม่มี token เพราะ React app ที่สลับมาใช้ API ของเราไม่รู้จัก token และต้องใช้งานได้เหมือนเดิม - GET /auth/me ยังต้องตอบ 401 เมื่อไม่มี token — การเปิด route เดิมต้องไม่เผลอเปิดทั้งแอป - ไฟล์ที่แก้มีแค่ decorator กับ import ที่เพิ่มเข้ามา ไม่มี logic ไหนเปลี่ยน ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ - ห้ามแตะไฟล์ใน test/ เด็ดขาด ถ้า test ไม่ผ่านให้บอกผมว่าไม่ผ่านข้อไหน ห้ามแก้ test ให้ผ่านเอง - ห้ามแก้ logic ใน service หรือ mapper - ห้ามถอด guard ออก หรือทำให้ APP_GUARD ไม่ทำงาน - ห้ามใช้ any, as หรือ !

บรรทัด "ห้ามแตะไฟล์ใน test/ เด็ดขาด" คือประโยคที่สำคัญที่สุดในบทนี้ เพราะทางที่เร็วที่สุดในการทำให้ test เขียวคือไปแก้ app.e2e-spec.ts ให้คาดหวัง 401 แทน 200 ซึ่งจะทำให้ test ผ่านครบโดยที่แอปยังพังอยู่ทั้งใบ — และเราจะสูญเสียสิ่งเดียวที่ใช้ตรวจงานชิ้นนี้ได้ไปพร้อมกัน

ตรวจโค้ดที่ AI สร้าง

  • git diff --stat test/ ว่างเปล่า — ไม่มีไฟล์ test ไหนถูกแตะ นี่คือข้อแรกที่ต้องตรวจ ก่อนดูด้วยซ้ำว่า test เขียวหรือไม่
  • type ที่โผล่ในลายเซ็นของ method ที่มี decorator ต้อง import ด้วย import type ตามกติกาใน .cursor/rules — @Req() request: AuthenticatedRequest ใน GET /auth/me คือกรณีแรกของโบนัสนี้ ถ้าใช้ import ธรรมดา nest start จะพังด้วย TS1272
  • @Public() ติดที่ระดับ class ทั้งสามตัว ไม่ใช่ไล่ติดทีละ handler สี่ครั้งใน ProductsController
  • git diff src/products/ src/orders/ src/app.controller.ts เห็นแค่บรรทัด import กับบรรทัด decorator — ไม่มี logic ไหนขยับ
  • APP_GUARD ยังอยู่ครบใน auth.module.ts และไม่มีใครเติม @Public() ให้ AuthController ทั้งก้อน (ซึ่งจะเปิด /auth/me ทิ้งไว้ด้วย)
  • รัน npm run test:e2e ได้ Tests 11 passed (11) ครบ

AI มักพลาดตรงนี้: ติด @Public() ที่ AuthController ทั้ง class เพราะเห็นว่า signup กับ login เป็น endpoint สาธารณะทั้งคู่ — ซึ่งจะพา GET /auth/me เปิดโล่งไปด้วยโดยไม่มี test ไหนจับได้ เพราะยังไม่มี test ของ /auth/me ในสิบเอ็ดข้อนั้น นี่คือเหตุผลที่ข้อ "GET /auth/me ยังต้องตอบ 401" ถูกใส่ไว้ใน ผลลัพธ์ที่ต้องได้ และต้องตรวจด้วยมือ

โค้ดอ้างอิงของหัวข้อนี้ — เป็นหนึ่งในวิธีที่ถูก ของคุณไม่จำเป็นต้องเหมือนทุกบรรทัด ขอแค่ผ่านผลลัพธ์ที่ต้องได้:

// src/products/products.controller.ts — เฉพาะสองบรรทัดที่เพิ่ม
import { Public } from '../auth/public.decorator.js';

@Public()
@ApiTags('products')
@Controller('products')
export class ProductsController {
// src/auth/auth.controller.ts — เฉพาะส่วนที่เพิ่ม
import type { AuthenticatedRequest } from './jwt-payload.interface.js';

  @Public()
  @Post('signup')
  signup(@Body() dto: SignupDto) {
    return this.authService.signup(dto);
  }

  @Public()
  @Post('login')
  login(@Body() dto: LoginDto) {
    return this.authService.login(dto);
  }

  @Get('me')
  me(@Req() request: AuthenticatedRequest) {
    const { sub, email, role } = request.user;
    return { id: sub, email, role };
  }

สังเกตว่า AuthController ติด @Public() ที่ระดับ handler ทีละเส้น ต่างจากอีกสาม controller ที่ติดระดับ class — เพราะ controller นี้มีทั้งเส้นที่เปิดและเส้นที่ปิดปนกันอยู่ การติดที่ระดับ class จะเปิด /auth/me ไปด้วย

ถ้าอธิบายบรรทัดไหนไม่ได้ ยังไม่ผ่านบทนี้ — กลับไปอ่านส่วนแนวคิดก่อน

ตัวเลขชุดนี้คือตัวเดียวกับที่เห็นตอนจบบทคำสั่งซื้อ — แปลว่า API ที่ React app ใช้อยู่ไม่ได้เปลี่ยนพฤติกรรมแม้แต่จุดเดียว ทั้งที่ตอนนี้ทุก request วิ่งผ่าน guard ก่อนเสมอ

ตรวจว่าใช้งานได้จริง

  • สี่เส้นสาธารณะยังเรียกได้โดยไม่มี token ต้องได้ 200 ทุกบรรทัด 
    for p in "/" "/products/categories" "/products?limit=2" "/products/1"; do
  curl -s -o /dev/null -w "%{http_code} $p\n" "http://localhost:3000$p"
done
  • สั่งซื้อได้โดยไม่ต้องมี token — นี่คือข้อที่ทำให้ React app ยังทำงาน 
    curl -s -o /dev/null -w '%{http_code}\n' -X POST http://localhost:3000/carts/add \
  -H 'Content-Type: application/json' \
  -d '{"userId":1,"products":[{"id":1,"quantity":2}],"address":{"address":"1 Main","email":"a@b.com","phone":"0812345678"}}'
  • GET /auth/me ต้องได้ 401 เมื่อไม่มี token และ 200 เมื่อมี 
    curl -s -o /dev/null -w '%{http_code}\n' http://localhost:3000/auth/me
curl -s -H "Authorization: Bearer $TOKEN" http://localhost:3000/auth/me
  • token ที่ถูกแก้ payload ต้องใช้ไม่ได้ — ตัดตัวอักษรท้ายลายเซ็นออกหนึ่งตัวแล้วยิงใหม่ ต้องได้ 401 
    curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer ${TOKEN%?}" http://localhost:3000/auth/me
  • scheme ที่ไม่ใช่ Bearer ต้องไม่ผ่าน 
    curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Basic $TOKEN" http://localhost:3000/auth/me
  • Swagger ยังเปิดได้ทั้งที่ guard ปิดทุก route — เพราะมันเป็น middleware ไม่ใช่ route 
    curl -s -o /dev/null -w '%{http_code}\n' http://localhost:3000/api
  • npm run test:e2e ได้ Tests 11 passed (11) และ git diff --stat test/ ว่างเปล่า
  • commit ผลงานของบทนี้: git add -A && git commit -m "feat: public routes and auth/me"
