ติดตั้ง Prisma และ PrismaModule

เมื่อจบบทนี้ คุณจะสามารถ

  • อธิบายได้ว่าทำไม Prisma 7 ต้องสร้าง PrismaClient พร้อม driver adapter เสมอ
  • แยกได้ว่า prisma7.config.ts เป็นไฟล์ของ CLI ส่วน PrismaService เป็นของแอป
  • ทำให้ PrismaService ถูก inject ได้ทุกโมดูลด้วย @Global() และอ่าน .env ผ่าน ConfigModule

Prisma 7 ไม่มี default engine ต้องบอก driver adapter ทุกครั้ง

ใน NestJS Fundamentals บทรู้จัก Prisma และ PrismaService เราเห็นรูปแบบนี้มาแล้ว: Prisma 7 ไม่ต่อฐานข้อมูลด้วย engine binary ของตัวเองอีกต่อไป แต่ต่อผ่าน driver adapter ซึ่งเป็น driver ของภาษา JavaScript จริง ๆ สำหรับ PostgreSQL คือแพ็กเกจ @prisma/adapter-pg ที่ครอบ pg ไว้ ผลคือทุกครั้งที่ new PrismaClient() เราต้องส่ง adapter เข้าไปด้วย

// รูปแบบที่ Prisma 7 ต้องการ
new PrismaClient({ adapter: new PrismaPg({ connectionString: process.env.DATABASE_URL }) });

ถ้าเขียนแบบ Prisma 5 (new PrismaClient() เปล่า ๆ แล้ว import จาก @prisma/client) โค้ดจะ compile ผ่านแต่พังตอนรันด้วย error ว่าต้องมี adapter — เป็นจุดที่ AI พลาดบ่อยที่สุดในบทนี้ เพราะตัวอย่างบนอินเทอร์เน็ตส่วนใหญ่ยังเป็นของ Prisma 5

prisma init สร้างสองไฟล์ ไฟล์ละหน้าที่

npx prisma init จะสร้าง prisma/schema.prisma (พิมพ์เขียวของฐานข้อมูล) และ prisma7.config.ts (ไฟล์ตั้งค่าของ CLI) ไฟล์แรกเราจะเติม model ในขั้นถัดไป ไฟล์ที่สองปล่อยไว้เฉย ๆ ตลอดคอร์ส

// prisma/schema.prisma ที่ prisma init สร้างให้
generator client {
  provider = "prisma-client"
  output   = "../src/generated/prisma"
}

datasource db {
  provider = "postgresql"
}
  • provider = "prisma-client" คือ generator รุ่นใหม่ที่ออกมาเป็นไฟล์ TypeScript ธรรมดา (รุ่นเก่าชื่อ prisma-client-js และซ่อนตัวไว้ใน node_modules)
  • output = "../src/generated/prisma" แปลว่า client ที่ generate จะมาโผล่เป็นโค้ดในโปรเจกต์เราที่ src/generated/prisma/ — เราจึง import จาก path นั้น ไม่ใช่จาก @prisma/client
  • datasource db ไม่มี url เพราะ Prisma 7 ย้ายการอ่าน connection string ไปไว้ใน prisma7.config.ts
// prisma7.config.ts — ไฟล์นี้ CLI ใช้เท่านั้น แอปที่รันอยู่ไม่ได้อ่าน
import "dotenv/config";
import { defineConfig } from "prisma/config";

export default defineConfig({
  schema: "prisma/schema.prisma",
  migrations: {
    path: "prisma/migrations",
  },
  datasource: {
    url: process.env["DATABASE_URL"],
  },
});

บรรทัด import "dotenv/config" ในไฟล์นี้มีเพื่อให้คำสั่งอย่าง npx prisma migrate dev อ่าน .env เองได้ เพราะ CLI รันนอก NestJS — ไม่มี ConfigModule มาช่วย นี่คือเหตุผลเดียวที่โปรเจกต์นี้ยังต้องติดตั้ง dotenv

PrismaService คือ PrismaClient ที่ผูกกับ lifecycle ของ Nest

เราไม่เรียก new PrismaClient() กระจายทั่วโปรเจกต์ (กติกาใน .cursor/rules/project.mdc ห้ามไว้) แต่ห่อไว้ใน provider เดียวที่ extends PrismaClient แล้วใช้ hook ของ Nest สองตัว: onModuleInit เรียก $connect() ตอนแอปเริ่ม และ onModuleDestroy เรียก $disconnect() ตอนแอปปิด เพื่อให้ connection pool ถูกคืนอย่างเรียบร้อย

จากนั้น PrismaModule ติด @Global() เพื่อให้โมดูลอื่น (products และ orders ที่จะสร้างภายหลัง) inject PrismaService ได้ทันทีโดยไม่ต้อง import PrismaModule ซ้ำในทุกโมดูล — เทคนิคเดียวกับ NestJS Fundamentals บทควบคุม Module Encapsulation

เปิด ConfigModule ตั้งแต่วันแรก

เราใส่ ConfigModule.forRoot({ isGlobal: true }) เป็นรายการแรกของ imports ตั้งแต่บทนี้ แม้ยังไม่มีใครใช้ ConfigService เลย เหตุผลสองข้อ

  • ConfigModule โหลด .env เข้า process.env ให้เอง เราจึงไม่ต้องเขียน import 'dotenv/config' ไว้หัว main.ts — รายละเอียดเรื่องนี้อยู่ใน NestJS Fundamentals บทตั้งค่า ConfigModule และ Environment Files
  • isGlobal: true ทำให้ ConfigService ถูก inject ได้ทุกที่ ภายหลังจะใช้อ่าน APP_URL ตอนสร้าง endpoint หมวดหมู่ และใช้อ่าน PORT กับ CORS_ORIGIN ตอนเปิด CORS

ConfigModule.forRoot() โหลด .env เข้า process.env ทันทีตอนที่ array imports ถูกประเมิน จึงมีค่าก่อนที่ provider ตัวไหนจะถูกสร้าง — การวางไว้ตัวแรกเป็นธรรมเนียมที่ช่วยตอนมี module อื่นอ่าน process.env ในตัวเลือกของ forRoot() ของมันเอง

บทนี้ยังติดตั้ง tsx เป็น devDependency ไปด้วย แม้จะยังไม่ได้ใช้ เพราะ seed script ที่จะเขียนภายหลังรัน นอก NestJS: มันเป็นไฟล์ TypeScript ที่ต้องรันตรง ๆ และต้อง import ไฟล์ที่ Prisma generate มาได้ tsx ทำสองอย่างนั้นให้ในคำสั่งเดียว

ตำแหน่งและชื่อไฟล์ข้างบนมาจากโค้ดอ้างอิง prompt ไม่ได้สั่งว่าต้องวางไฟล์ที่ไหน Cursor อาจเลือกต่างออกไปได้ สิ่งที่ต้องตรงคือข้อในส่วน "ผลลัพธ์ที่ต้องได้" ของ prompt (ยกเว้นชื่อ class PrismaService ที่บทหลังใช้ inject)

  • src/prisma/prisma.service.ts — สัญญา: ต้อง extends PrismaClient ที่ import จาก '../generated/prisma/client.js' และส่ง adapter เข้า super() / ต้องไม่ import dotenv และต้องไม่ import จาก @prisma/client
  • src/prisma/prisma.module.ts — สัญญา: ต้องเป็น @Global() และ exports: [PrismaService] / ต้องไม่มี controllers
  • src/app.module.ts — สัญญา: ต้องมี ConfigModule.forRoot({ isGlobal: true }) เป็นรายการแรกแล้วตามด้วย PrismaModule / ต้องไม่ลบ AppController กับ AppService

ติดตั้ง Prisma แล้วให้ Cursor ต่อสายเข้า Nest

commit งานก่อน แล้วเปิดแชทใหม่ใน Cursor โหมด Agent แต่ก่อนจะส่ง prompt ให้ติดตั้งแพ็กเกจและรัน prisma init ด้วยมือเอง เพราะเราอยากเห็นไฟล์ที่ CLI สร้างด้วยตาตัวเอง (และ prompt จะอ้างอิงไฟล์เหล่านั้น)

npm install @prisma/client@7.10.0 @prisma/adapter-pg@7.10.0 dotenv @nestjs/config npm install -D prisma@7.10.0 tsx npx prisma init --no-skills

คำเตือนสองบรรทัดนี้ปกติ: บรรทัดแรกบอกว่ามันเจอ DATABASE_URL ใน .env ที่เราสร้างไว้แล้ว แล้วจึงไม่เติมบรรทัดซ้ำให้ (เปิด .env ดูก็ยังมีสี่บรรทัดเดิม — ถ้า CLI ของคุณเผลอเติมบรรทัด DATABASE_URL ตัวอย่างเข้ามา ให้ลบออกจนเหลือสี่บรรทัด) บรรทัดที่สองเป็นคำเตือนแบบเหมารวม ทั้งที่ .env ถูก ignore อยู่แล้ว ส่วนสิ่งที่ prisma init แก้จริง ใน .gitignore คือเติมบรรทัด /src/generated/prisma ต่อท้าย — ตั้งใจให้เป็นอย่างนั้น เพราะโค้ดที่ generate ได้ไม่ควรเข้า git

ถ้า npm install ขึ้นข้อความว่า N packages have install scripts not yet covered by allowScripts แปลว่า npm ของคุณกัน install script ไว้ ซึ่งจะทำให้ Prisma ไม่ได้ติดตั้ง engine ของตัวเอง ให้อนุญาตเฉพาะแพ็กเกจที่ต้องใช้แล้ว rebuild ก่อน รัน prisma generate ด้วย npm install-scripts approve @prisma/engines esbuild prisma fsevents ตามด้วย npm rebuild หลังทำแล้ว package.json จะมีบล็อก allowScripts เพิ่มขึ้นมา — เป็นผลที่ถูกต้อง ไม่ต้องลบออก

เมื่อไฟล์จาก prisma init อยู่ครบแล้ว ส่ง prompt นี้ทั้งก้อน

สร้าง PrismaModule กับ PrismaService แบบ global และเปิดใช้ ConfigModule ใน AppModule @src/app.module.ts ผลลัพธ์ที่ต้องได้: - หลังผมรัน npx prisma generate แล้ว npm run build และ npm run lint ผ่านโดยไม่มี error - npm run start:dev boot ผ่าน log มีบรรทัด PrismaModule dependencies initialized และ ConfigModule dependencies initialized - มี class ชื่อ PrismaService (บทถัดไปจะ inject ด้วยชื่อนี้) ที่ inject ได้จากโมดูลไหนก็ได้โดยไม่ต้อง import PrismaModule ซ้ำ - แอปเชื่อมต่อฐานข้อมูลตอนเริ่มและปิดการเชื่อมต่อตอนแอปปิด - ค่าใน .env อ่านได้ผ่าน ConfigService ทุกโมดูล และ grep -r dotenv src/ ไม่มีผลลัพธ์ - curl -s http://localhost:3000 ยังได้ Hello World! เหมือนเดิม ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ - ห้ามรัน prisma generate หรือ migrate ให้ผมรันเอง - ยังไม่ต้องเพิ่ม model ใน schema.prisma และยังไม่ต้องสร้าง service หรือ controller ของสินค้า

รีวิวโค้ดตามหัวข้อถัดไปให้จบก่อน แล้วจึงรันสองคำสั่งนี้เอง (prompt สั่งห้าม Agent รันให้)

npx prisma generate npm run start:dev

ตรวจโค้ดที่ AI สร้าง

  • PrismaService inject ได้จากทุกโมดูลโดยไม่ต้อง import PrismaModule ซ้ำ — ถ้าไม่ global โมดูลที่สร้างภายหลังจะ inject ไม่ได้
  • PrismaClient มาจาก client ที่ generate ใน src/generated/prisma ไม่ใช่ @prisma/client
  • client ถูกสร้างพร้อม driver adapter จริง — ไม่ใช่ PrismaClient เปล่า ๆ ที่ compile ผ่านแต่พังตอนรัน
  • ConfigModule เปิดแบบ global และ AppController/AppService ยังอยู่ (curl ยังได้ Hello World!)
  • grep -r dotenv src/ ต้องไม่มีผลลัพธ์
  • import ไฟล์ในโปรเจกต์ทุกบรรทัดลงท้าย .js และไม่มี any / as / !
  • git status ไม่มีไฟล์ที่ไม่เกี่ยวกับเป้าหมายถูกแก้ — ไม่มี index.ts และไม่มีการแก้ main.ts, schema.prisma, .env

AI มักพลาดตรงนี้: import PrismaClient จาก '@prisma/client' (ถูกต้องสำหรับ Prisma 5 แต่ที่นี่จะพังตอนรันด้วย error ว่าต้องมี adapter) หรือลืม .js ท้าย path ทำให้โปรเจกต์ ES module หาไฟล์ไม่เจอตอนรัน อีกท่าที่เจอคือแอบเติม import 'dotenv/config' ใน main.ts ซึ่งซ้ำซ้อนกับ ConfigModule

โค้ดอ้างอิงของบทนี้ — เป็นหนึ่งในวิธีที่ถูก ของคุณไม่จำเป็นต้องเหมือนทุกบรรทัด ขอแค่ผ่านผลลัพธ์ที่ต้องได้:

// src/prisma/prisma.service.ts
import { Injectable, OnModuleInit, OnModuleDestroy } from '@nestjs/common';
import { PrismaPg } from '@prisma/adapter-pg';
import { PrismaClient } from '../generated/prisma/client.js';

@Injectable()
export class PrismaService extends PrismaClient implements OnModuleInit, OnModuleDestroy {
  constructor() {
    super({
      adapter: new PrismaPg({ connectionString: process.env.DATABASE_URL }),
    });
  }

  async onModuleInit() {
    await this.$connect();
  }

  async onModuleDestroy() {
    await this.$disconnect();
  }
}
// src/prisma/prisma.module.ts
import { Global, Module } from '@nestjs/common';
import { PrismaService } from './prisma.service.js';

@Global()
@Module({
  providers: [PrismaService],
  exports: [PrismaService],
})
export class PrismaModule {}
// src/app.module.ts
import { Module } from '@nestjs/common';
import { ConfigModule } from '@nestjs/config';
import { AppController } from './app.controller.js';
import { AppService } from './app.service.js';
import { PrismaModule } from './prisma/prisma.module.js';

@Module({
  imports: [ConfigModule.forRoot({ isGlobal: true }), PrismaModule],
  controllers: [AppController],
  providers: [AppService],
})
export class AppModule {}

ถ้าอธิบายบรรทัดไหนไม่ได้ ยังไม่ผ่านบทนี้ — กลับไปอ่านส่วนแนวคิดก่อน

ผลลัพธ์ที่คาดหวัง

เวอร์ชันที่ติดตั้งได้ตอนตรวจทานคอร์สนี้: @prisma/client 7.10.0, @prisma/adapter-pg 7.10.0, prisma (CLI) 7.10.0, @nestjs/config 12.0.0, dotenv 17.4.2 และ tsx 4.23.13 — ตรวจของคุณด้วย npm ls @prisma/client @prisma/adapter-pg prisma @nestjs/config tsx

ถ้าลืมรัน npx prisma generate ก่อน start:dev จะได้ error ตอน compile ว่าหาโมดูล ../generated/prisma/client.js ไม่เจอ — เพราะ Prisma 7 ไม่ generate client ให้อัตโนมัติ ต้องสั่งเอง (และต้องสั่งซ้ำทุกครั้งที่แก้ schema.prisma)

ตรวจว่าใช้งานได้จริง

  • ls src/generated/prisma เห็น client.ts (พร้อม models.ts, enums.ts และโฟลเดอร์ models/) — นี่คือ client ที่ generate ออกมาเป็นโค้ดในโปรเจกต์เราจริง ๆ
  • grep -r dotenv src/ ไม่มีผลลัพธ์ — ยืนยันว่า .env ถูกโหลดโดย ConfigModule ไม่ใช่โดยมือเรา
  • npm run build และ npm run lint ผ่านแบบไม่มี output
  • curl -s http://localhost:3000 ยังได้ Hello World! — โมดูลใหม่ไม่ทำให้ route เดิมพัง
  • commit ด้วย git add -A && git commit -m "feat: prisma service and config module" แล้วเช็คว่า src/generated/ ไม่ติดไปใน commit

อย่าใช้การปิดฐานข้อมูลเป็นวิธีทดสอบในบทนี้ ถ้าคุณลอง docker compose stop db แล้ว start แอปใหม่ คุณจะพบว่ามัน boot ผ่านและตอบ Hello World! ได้เหมือนเดิม โดยไม่มี error ใน log เลย นั่นไม่ใช่ความผิดพลาดของโค้ด: driver adapter ต่อฐานข้อมูลแบบ lazy — $connect() ยังไม่เปิด socket จริงจนกว่าจะมี query แรกเกิดขึ้น และตอนนี้ schema ยังไม่มี model ใด ๆ ให้ query DATABASE_URL ที่ผิดจะโผล่เป็น error ตอนรัน migrate dev และตอนที่แอปยิง query แรกต่างหาก
