GET /products พร้อม skip และ limit

เมื่อจบบทนี้ คุณจะสามารถ

  • รับ query parameter ด้วย DTO ที่มีค่าเริ่มต้นในตัว แล้วเปิด ValidationPipe แบบ global
  • อธิบายได้ว่าทำไม limit ใน response ต้อง echo ค่าที่ client ขอมาเสมอ แม้ query จะเลยขอบข้อมูลแล้วได้สินค้าน้อยกว่าที่ขอ
  • ดึงหน้าข้อมูลกับ total จาก snapshot เดียวด้วย $transaction ใน method กลางชื่อ paginate ที่ทำให้ endpoint กรองตามหมวดในขั้นถัดไปเพิ่มได้ด้วยโค้ดสองบรรทัด

กติกา pagination ของเราเอง

โปรเจกต์นี้ไม่มี API อ้างอิงให้ก็อปปี้ กติกาข้างล่างมาจาก docs/api-spec.md ซึ่งอ่านมาจากโค้ดจริงของ React app — และแถวสุดท้ายเป็นข้อที่คนเดาผิดบ่อยที่สุด

กรณีกติกาของเรา
ไม่ส่ง limitค่าเริ่มต้น limit = 20 (ตรงกับค่าเริ่มต้นของ client เองใน src/features/products/api.ts)
ไม่ส่ง skipค่าเริ่มต้น skip = 0
limit นอกช่วง 1–100 หรือไม่ใช่ integer400 — ไม่มีค่าไหน "มีความหมายพิเศษ" อีกแล้ว เพราะจุดเรียกจริงทุกจุดของ client (Home.tsx ส่ง 5 กับ 12, Category.tsx ส่ง 20) อยู่ในช่วงนี้อย่างปลอดภัยอยู่แล้ว
ลำดับสินค้าเรียงตาม id น้อยไปมาก — orderBy: { id: 'asc' }
?limit=10&skip=200 (เหลือของแค่ 8 ชิ้น จาก total 208)ตอบ limit: 10 (ค่าที่ขอมา) พร้อม products แค่ 8 ชิ้น

limit ใน envelope สะท้อนค่าที่ request ขอมาเสมอ ตามที่ docs/api-spec.md ระบุไว้ตรง ๆ ("limit: echoes the request") ไม่เกี่ยวกับจำนวนแถวที่ส่งกลับจริง เขียน limit: rows.length คือบั๊กคลาสสิกของบทนี้ — curl หน้าแรกจะยังดูถูกต้องทุกอย่าง แล้วจะพังเฉพาะตอนที่ query วิ่งเลยขอบข้อมูลไปแล้วเท่านั้น

ค่าเริ่มต้นอยู่ที่ field ของ DTO ไม่ใช่ที่ ?? ใน service

ใน NestJS Fundamentals ตอนแรก ๆ เราอ่าน query parameter แบบดิบ ๆ แล้วเติมค่าเริ่มต้นเอง ตอนที่ว่าด้วย DTO และ pipe พาเราไปถึงวิธีที่สะอาดกว่า: ประกาศ DTO แล้วปล่อยให้ pipe จัดการ

export class PaginationQueryDto {
  @IsInt()
  @Min(0)
  skip: number = 0;

  @IsInt()
  @Min(1)
  @Max(100)
  limit: number = 20;
}

ค่าเริ่มต้นเขียนเป็น field initialiser ธรรมดา ไม่ต้องมี @IsOptional() และไม่ต้องมี ? เหตุผลคือ option transform: true ทำให้ ValidationPipe สร้าง instance ของ class ขึ้นมาจริง ก่อนส่งเข้า handler — เมื่อ instance เกิดขึ้น initialiser ก็ทำงาน ดังนั้น request ที่ไม่ส่ง limit มาจะได้ 20 ติดมาโดยอัตโนมัติ

ผลพลอยได้คือใน service เราเขียน query.limit ได้ตรง ๆ โดยไม่ต้องมี ?? 20 โปรยอยู่ทั่วไฟล์ และ type ก็เป็น number ไม่ใช่ number | undefined

app.useGlobalPipes(
  new ValidationPipe({
    whitelist: true,
    transform: true,
    transformOptions: { enableImplicitConversion: true },
  }),
);
  • enableImplicitConversion: true — query string เป็น string เสมอ ("2") option นี้แปลงเป็น number ตาม type ที่ประกาศไว้ให้ก่อน validate จึงไม่ต้องใส่ @Type(() => Number) ทีละ field
  • whitelist: true — คีย์ที่ไม่มีใน DTO ถูกตัดออกเงียบ ๆ ใครยิง ?sort=price&skip=0 มาก็ได้แค่ skip ส่วน React app ส่งมาแค่ skip กับ limit อยู่แล้ว
  • transform: true — ทำให้ handler ได้ instance ของ PaginationQueryDto จริง (จุดที่ทำให้ค่าเริ่มต้นทำงาน)

total กับหน้าข้อมูลต้องมาจาก snapshot เดียว

response envelope ต้องมี total คือจำนวนสินค้าทั้งหมด ซึ่งเป็นอีก query หนึ่ง (count) ถ้ายิงสอง query แยกกัน มีช่องให้ข้อมูลเปลี่ยนระหว่างนั้น แล้ว client จะได้ total: 208 พร้อมหน้าข้อมูลที่มาจากโลกที่มี 209 ชิ้น เราจึงห่อทั้งคู่ไว้ใน transaction เดียว (ทบทวน NestJS Fundamentals ตอน transaction)

const [rows, total] = await this.prisma.$transaction([
  this.prisma.product.findMany({ /* … */ }),
  this.prisma.product.count({ where }),
]);

รูปแบบ array ของ $transaction รับ list ของ query แล้วคืน array ของผลลัพธ์ตามลำดับเดิม — เขียนสั้นกว่าแบบ callback และเพียงพอเพราะสอง query นี้ไม่ต้องพึ่งผลของกันและกัน

productInclude ที่ใช้ร่วมกันระหว่าง findOne และ list

เขียน take: limit ตรง ๆ ได้เลย ไม่ต้องมี ternary พิเศษ เพราะ DTO ผ่าน @Min(1) @Max(100) ไปแล้วก่อนที่ request จะมาถึง service — limit ที่เข้ามาถึงจุดนี้จึงเป็นจำนวนเต็มบวกที่อยู่ในช่วง 1–100 เสมอ ไม่มีเคส "0 แปลว่าอะไรเป็นพิเศษ" ให้ต้องดักในตัว query เลย

อีกอย่างคือ include ก้อนเดียวกันตอนนี้ต้องใช้ทั้งใน findOne และใน list ถ้าปล่อยให้ copy กันไว้สองที่ วันหนึ่งจะแก้ที่เดียวแล้ว list กับ detail ตอบไม่เหมือนกัน เราจึงยกขึ้นมาเป็นค่าคงที่ระดับไฟล์

const productInclude = {
  category: true,
  reviews: { orderBy: { id: 'asc' } },
} satisfies Prisma.ProductInclude;

satisfies สำคัญกว่าที่เห็น: ถ้าเขียน const productInclude: Prisma.ProductInclude = {...} TypeScript จะกว้างเกินไป และถ้าไม่ใส่อะไรเลย 'asc' จะถูกอนุมานเป็น string ซึ่ง Prisma ไม่รับ satisfies ตรวจว่าก้อนนี้เข้ากับ Prisma.ProductInclude จริง โดยยังคง literal type 'asc' ไว้ให้

เป้าหมายของบทนี้

ในโค้ดอ้างอิงคือ query DTO ใหม่ + list endpoint ใน src/products/ และการเปิด validation แบบ global ใน src/main.ts — Cursor เลือกที่วางเองได้ โดยต้องได้ผลลัพธ์นี้

  • GET /products ตอบ envelope { products, total, skip, limit } ตามกติกาในตารางข้างบนทุกแถว รวมถึง limit ที่ echo ค่าที่ขอมาเสมอ
  • query ผิดช่วงหรือผิดรูปได้ 400 ก่อนถึงฐานข้อมูล ส่วน query ที่ไม่รู้จักถูกตัดทิ้ง
  • total กับหน้าข้อมูลมาจาก snapshot เดียว และ logic pagination พร้อมให้ endpoint ถัดไปใช้ซ้ำ
  • GET /products/categories และ GET /products/:id ยังทำงานเหมือนเดิม

ติดตั้ง validator ก่อน (ทำด้วยมือ)

สองแพ็กเกจนี้เป็น peer dependency ของ ValidationPipe ติดตั้งเองก่อนเปิดแชท เพื่อไม่ให้ Cursor ต้องเดาว่าจะลงอะไร

npm install class-validator class-transformer

เวอร์ชันที่ได้ตอนตรวจทานคอร์สนี้คือ class-validator@0.15.1 และ class-transformer@0.5.1 — ทั้งคู่เป็น transitive dependency ของ @nestjs/common อยู่แล้ว การติดตั้งตรง ๆ จึง dedupe ไปที่เวอร์ชันเดียวกันและ package-lock.json เปลี่ยนเพียงเล็กน้อย

สั่ง Cursor ทำ list endpoint พร้อม pagination

commit งานก่อน แล้วเปิดแชทใหม่ใน Cursor โหมด Agent (git add -A && git commit -m "chore: install validators") จากนั้นส่ง prompt นี้

เพิ่ม endpoint GET /products พร้อม skip/limit ที่ validate ตาม docs/api-spec.md และเปิด validation ของ query แบบ global @<controller และ service ของ products ที่คุณมีอยู่แล้ว> @src/main.ts — โค้ดอ้างอิงของ products คือ src/products/products.controller.ts กับ src/products/products.service.ts ผลลัพธ์ที่ต้องได้: - GET /products?limit=2&skip=0 ตอบ 200 envelope ที่มีคีย์ products, total, skip, limit เท่านั้น: total 208, skip 0, limit 2, products คือ id 1 และ 2 (เรียงตาม id น้อยไปมาก) - สินค้าในรายการมีรูปทรงเดียวกับ GET /products/:id ทุกคีย์ - GET /products (ไม่ส่ง query) ได้ skip 0, limit 20 และ products 20 ชิ้น - GET /products?limit=10&skip=200 ได้ total 208, limit 10 (echo ค่าที่ขอมา ไม่ใช่จำนวนแถวที่ได้จริง) และ products แค่ 8 ชิ้น - limit=0, limit=101, limit=-1, limit=abc และ skip=-1 ตอบ 400 ก่อนถึง query ฐานข้อมูล (limit ต้องเป็น integer 1–100, skip ต้องเป็น integer ≥ 0) - query ที่ไม่รู้จัก เช่น ?limit=2&sort=price ถูกตัดทิ้งเงียบ ๆ ได้ 200 ปกติ - total กับหน้าข้อมูลมาจาก snapshot เดียวกัน (ไม่ใช่สอง query ที่ข้อมูลเปลี่ยนระหว่างกันได้) - กติกา pagination ชุดนี้ใช้ซ้ำได้ เพราะ endpoint ที่กรองตามหมวด (GET /products/category/:slug) จะใช้กติกาเดียวกันทุกข้อ - GET /products/categories และ GET /products/:id ยังทำงานเหมือนเดิม ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ (class-validator และ class-transformer ติดตั้งไว้แล้ว) - ห้ามแตะไฟล์ใน test/ — e2e test เป็น prompt แยกในแชทถัดไป - ยังไม่ต้องทำ GET /products/category/:slug

ตรวจโค้ดที่ AI สร้าง

  • ค่าเริ่มต้นทำงานโดยไม่ส่ง query: limit 20 และ skip 0 — และค่าเริ่มต้นประกาศไว้ที่เดียว ไม่ได้โปรย ?? 20 ไว้หลายจุด
  • ?limit=10&skip=200 ได้ limit: 10 ไม่ใช่ 8 — ต้องทดสอบ query ที่เลยขอบข้อมูลจริง ไม่ใช่แค่หน้าแรก
  • limit นอกช่วง 1–100, ไม่ใช่ integer หรือ skip ติดลบ ได้ 400 ทุกกรณี และ query ที่ไม่รู้จักถูกตัดทิ้งได้ 200
  • total กับรายการสินค้าดึงมาใน transaction เดียวกัน ไม่ใช่สอง query แยกอิสระ
  • สินค้าในรายการมีรูปทรงเดียวกับ GET /products/:id ทุกคีย์ และการดึง relation ไม่ได้ถูก copy ไว้สองที่จนวันหนึ่ง list กับ detail ตอบไม่เหมือนกัน
  • GET /products/categories และ GET /products/1 ยังตอบเหมือนเดิม, ไม่มีไฟล์ที่ไม่เกี่ยวกับเป้าหมายถูกแก้ และไม่มี any / as / !

AI มักพลาดตรงนี้: ประกาศ skip?: number คู่กับ @IsOptional() แล้วไปโปรย query.skip ?? 0 ตามจุดต่าง ๆ ใน service — ใช้งานได้ แต่ย้ายกฎเรื่องค่าเริ่มต้นออกจาก DTO ไปกระจายในโค้ด ซึ่งตอนทำเอกสาร Swagger จะอ่านค่าเริ่มต้นไม่เจอ อีกข้อที่พลาดบ่อยกว่าคือเขียน limit: rows.length ตรงบรรทัด return — ดูถูกต้องทุกอย่างในหน้าแรก เพราะ rows.length เท่ากับ limit ที่ขอมาพอดีตราบใดที่ยังมีข้อมูลเหลือพอ แล้วจะพังเงียบ ๆ เฉพาะตอนที่ query วิ่งเลยขอบข้อมูลไปแล้วเท่านั้น การทดสอบจึงต้องมี query ที่วิ่งเลยขอบข้อมูลจริง ๆ ด้วย ไม่ใช่เช็คแค่หน้าแรก

โค้ดอ้างอิงของบทนี้ — เป็นหนึ่งในวิธีที่ถูก ของคุณไม่จำเป็นต้องเหมือนทุกบรรทัด ขอแค่ผ่านผลลัพธ์ที่ต้องได้:

src/products/dto/pagination-query.dto.ts

import { IsInt, Max, Min } from 'class-validator';

export class PaginationQueryDto {
  @IsInt()
  @Min(0)
  skip: number = 0;

  @IsInt()
  @Min(1)
  @Max(100)
  limit: number = 20;
}

src/main.ts

import { ValidationPipe } from '@nestjs/common';
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module.js';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  app.useGlobalPipes(
    new ValidationPipe({
      whitelist: true,

      transformOptions: { enableImplicitConversion: true },

src/products/products.service.ts

import { Injectable, NotFoundException } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import type { Prisma } from '../generated/prisma/client.js';
import { PrismaService } from '../prisma/prisma.service.js';
import { PaginationQueryDto } from './dto/pagination-query.dto.js';
import { ProductListResponseDto, ProductResponseDto } from './dto/product-response.dto.js';
import { toProductResponse } from './product.mapper.js';

const productInclude = {
  category: true,
  reviews: { orderBy: { id: 'asc' } },
} satisfies Prisma.ProductInclude;

@Injectable()
export class ProductsService {
  constructor(
    private readonly prisma: PrismaService,
    private readonly config: ConfigService,
  ) {}

  async findCategories() {
    const appUrl = this.config.getOrThrow<string>('APP_URL');
    const categories = await this.prisma.category.findMany({ orderBy: { id: 'asc' } });
    return categories.map(({ slug, name }) => ({
      slug,
      name,
      url: `${appUrl}/products/category/${slug}`,
    }));
  }

  findAll(query: PaginationQueryDto) {
    return this.paginate({}, query.skip, query.limit);
  }

  async findOne(id: number): Promise<ProductResponseDto> {
    const product = await this.prisma.product.findUnique({
      where: { id },
      include: productInclude,
    });
    if (!product) {
      throw new NotFoundException(`Product ${id} not found`);
    }
    return toProductResponse(product);
  }

  private async paginate(
    where: Prisma.ProductWhereInput,
    skip: number,
    limit: number,
  ): Promise<ProductListResponseDto> {
    const [rows, total] = await this.prisma.$transaction([
      this.prisma.product.findMany({
        where,
        skip,
        take: limit,
        orderBy: { id: 'asc' },
        include: productInclude,
      }),
      this.prisma.product.count({ where }),
    ]);
    return { products: rows.map(toProductResponse), total, skip, limit };
  }
}

src/products/products.controller.ts

import { Controller, Get, Param, ParseIntPipe, Query } from '@nestjs/common';
import { PaginationQueryDto } from './dto/pagination-query.dto.js';
import { ProductsService } from './products.service.js';

@Controller('products')
export class ProductsController {
  constructor(private readonly productsService: ProductsService) {}

  @Get('categories')
  findCategories() {
    return this.productsService.findCategories();
  }

  @Get()
  findAll(@Query() query: PaginationQueryDto) {
    return this.productsService.findAll(query);
  }

  @Get(':id')
  findOne(@Param('id', ParseIntPipe) id: number) {
    return this.productsService.findOne(id);
  }
}

ผลลัพธ์ที่คาดหวัง

log ตอน start มีสาม route เรียงตามนี้

[RouterExplorer] Mapped {/products/categories, GET} route
[RouterExplorer] Mapped {/products, GET} route

GET /products?limit=2&skip=0 ตอบ envelope สี่คีย์ { products, total, skip, limit } โดย total เป็น 208 และ products มีสองชิ้นคือ id 1 และ 2 ส่วน GET /products เปล่า ๆ ได้ 20 ชิ้น และ ?limit=0 ตอบ 400 (นอกช่วง 1–100 ที่กำหนดไว้)

query ที่ผิดรูปจะได้ 400 ตั้งแต่ก่อนเข้า handler เช่น ?limit=abc

HTTP/1.1 400 Bad Request
{"message":["limit must not be greater than 100","limit must not be less than 1","limit must be an integer number"],"error":"Bad Request","statusCode":400}

สังเกตว่า message เป็น array สามข้อความ ไม่ใช่ข้อความเดียว — เพราะ Number('abc') คือ NaN และการเทียบค่ากับ NaN ทุกทิศทางเป็น false เสมอ ทำให้ @IsInt(), @Min(1) และ @Max(100) ถือว่าไม่ผ่านพร้อมกันทั้งสามตัว

ตรวจว่าใช้งานได้จริง

  • หน้าแรกสองชิ้น — ต้องพิมพ์ 208 0 2 [ 1, 2 ] 
    curl -s "http://localhost:3000/products?limit=2&skip=0" \
  | node -e "let d='';process.stdin.on('data',c=>d+=c).on('end',()=>{const j=JSON.parse(d);console.log(j.total,j.skip,j.limit,j.products.map(p=>p.id))})"
  • ค่าเริ่มต้นทำงาน — curl -s "http://localhost:3000/products" แล้วอ่าน limit กับ products.length ต้องได้ 20 20
  • limit=0 ถูกปฏิเสธ — curl -s -i "http://localhost:3000/products?limit=0" | sed -n '1p' ต้องได้ HTTP/1.1 400 Bad Request (ไม่ใช่ "คืนทั้งหมด" อีกต่อไป เพราะ limit=0 อยู่นอกช่วง 1–100)
  • curl -s -i "http://localhost:3000/products?limit=abc" | sed -n '1p;$p' ได้ 400 พร้อม limit must be an integer number อยู่ใน array message
  • curl -s -i "http://localhost:3000/products?limit=-1" | sed -n '1p' ได้ HTTP/1.1 400 Bad Request
  • เทียบ envelope กับ docs/api-spec.md — ต้องมีคีย์ตรงกันเป๊ะ ไม่ขาดไม่เกิน 
    curl -s "http://localhost:3000/products?limit=2&skip=0" \
  | node -e "let d='';process.stdin.on('data',c=>d+=c).on('end',()=>{const j=JSON.parse(d);const keys=Object.keys(j).sort();console.log(JSON.stringify(keys)===JSON.stringify(['limit','products','skip','total']))})"
    ต้องพิมพ์ true
  • ขอเลยขอบข้อมูล — curl -s "http://localhost:3000/products?limit=10&skip=200" ต้องได้ limit: 10 (ค่าที่ขอมา ไม่ใช่ 8) พร้อม products.length: 8 และ total: 208 (208 - 200 = 8 ซึ่งน้อยกว่า 10 ที่ขอ)
  • whitelist ทำงาน — curl -s "http://localhost:3000/products?limit=2&sort=price" ต้องได้ 200 ปกติ ไม่ใช่ 400
  • commit ผลงานด้วย git add -A && git commit -m "feat: GET /products with pagination"

สั่ง Cursor เพิ่มสาม test ของ pagination ลงในไฟล์เดิม

ไฟล์ test/products.e2e-spec.ts ที่ได้มาตอนต่อ GET /products/:id ตอนนี้มีสี่ test แล้ว ขั้นนี้เพิ่มอีกสามข้อของ endpoint ใหม่ลงไปในไฟล์เดิม รวมเป็นเจ็ด — สั่งในแชทใหม่อีกครั้ง ด้วยเหตุผลเดียวกับตอนเขียน test ชุดแรก

รอบนี้มีกับดักหนึ่งข้อที่ต้องเขียนลงไปใน prompt ตรง ๆ แล้วตามไปตรวจในส่วน review: test ใหม่สองข้อของ limit=0 และ limit=101 จะผ่านก็ต่อเมื่อ beforeAll ตั้ง ValidationPipe ไว้ด้วย ถ้า agent ลืมข้อนี้ สอง test นั้นจะได้ status ที่ไม่ใช่ 400 แล้วคุณจะนั่งหาสาเหตุอยู่นานว่าทำไม curl ได้ 400 แต่ test ไม่ได้ ทั้งที่ยิง URL เดียวกัน

เหตุผลคือ createNestApplication() สร้างแอปขึ้นจาก AppModule เท่านั้น มันไม่ได้รัน src/main.ts ให้ ทุกอย่างที่คุณเพิ่งตั้งค่าไว้ใน bootstrap() — รวมถึง app.useGlobalPipes(...) ที่เป็นหัวใจของบทนี้ — จึงไม่ติดมาเอง ต้องมีคนเขียนซ้ำใน beforeAll ให้ตรงกับ main.ts ทุกตัวเลือก

นี่คือสิ่งที่เราได้กลับมาจากการที่ test boot แอปเอง: pipe, guard และ filter ที่แอปใช้จริงต้องถูกประกาศออกมาให้เห็นครบในไฟล์ test ถ้าเราไปยิง server ที่เปิดค้างไว้แทน ของพวกนี้จะติดมาเองโดยที่เราไม่เคยต้องรู้ว่ามีอะไรบ้าง และวันที่ main.ts เปลี่ยน test ก็จะไม่บอกอะไรเราเลย

commit งานก่อน แล้วเปิดแชทใหม่ใน Cursor โหมด Agent แล้วส่ง prompt นี้

เพิ่ม test ของ GET /products แบบแบ่งหน้า ลงใน e2e test ของสัญญาที่มีอยู่แล้ว @docs/api-spec.md @test/products.e2e-spec.ts ผลลัพธ์ที่ต้องได้: - เพิ่มสาม test ต่อท้าย describe เดิมใน test/products.e2e-spec.ts โดยสี่ test เดิมยังอยู่ครบและไม่ถูกแก้ข้อความหรือเงื่อนไข 1. GET /products?limit=5&skip=0 → 200 และ envelope มีสี่คีย์พอดีคือ products, total, skip, limit โดย limit เป็น 5 skip เป็น 0 และ products มี 5 ชิ้น 2. GET /products?limit=0 → 400 และ body มี message 3. GET /products?limit=101 → 400 และ body มี message - สอง test ของ limit=0 และ limit=101 ต้องได้ 400 จริง ซึ่งแปลว่า beforeAll ต้องตั้ง ValidationPipe ด้วยตัวเลือกชุดเดียวกับใน src/main.ts (whitelist, transform, enableImplicitConversion) เพราะ createNestApplication() ไม่ได้รัน main.ts ให้ - import ในไฟล์ test ลงท้ายด้วย .js ตามกติกา ESM ของโปรเจกต์ ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ — Vitest กับ supertest มากับ scaffold แล้ว - ห้ามแก้ไฟล์ใน src/ เด็ดขาด ถ้า test ไม่ผ่านให้บอกผมว่าไม่ผ่านข้อไหน ห้ามแก้โค้ดให้ test ผ่านเอง - ห้ามรัน test ให้ ผมจะรันเอง

โค้ดอ้างอิงของหัวข้อนี้ — เป็นหนึ่งในวิธีที่ถูก ของคุณไม่จำเป็นต้องเหมือนทุกบรรทัด ขอแค่ผ่านผลลัพธ์ที่ต้องได้ข้างบน เริ่มที่ beforeAll ที่ต้องมี ValidationPipe เพิ่มเข้ามา

import { Test, TestingModule } from '@nestjs/testing';
import { INestApplication, ValidationPipe } from '@nestjs/common';
import request from 'supertest';
import { AppModule } from './../src/app.module.js';

describe('Products contract (e2e)', () => {
  let app: INestApplication;

  beforeAll(async () => {
    const moduleFixture: TestingModule = await Test.createTestingModule({
      imports: [AppModule],
    }).compile();

    app = moduleFixture.createNestApplication();
    app.useGlobalPipes(
      new ValidationPipe({
        whitelist: true,
        transform: true,
        transformOptions: { enableImplicitConversion: true },
      }),
    );
    await app.init();
  });

แล้วสาม it() ที่ต่อท้ายข้อที่มีอยู่เดิม

  it('GET /products?limit=5&skip=0 → limit and skip echo the request', async () => {
    const response = await request(app.getHttpServer())
      .get('/products?limit=5&skip=0')
      .expect(200);

    expect(Object.keys(response.body).sort()).toEqual(['limit', 'products', 'skip', 'total']);
    expect(response.body.limit).toBe(5);
    expect(response.body.skip).toBe(0);
    expect(response.body.products).toHaveLength(5);
  });

  it('GET /products?limit=0 → 400 (out of range)', async () => {
    const response = await request(app.getHttpServer())
      .get('/products?limit=0')
      .expect(400);

    expect(response.body.message).toBeDefined();
  });

  it('GET /products?limit=101 → 400 (out of range)', async () => {
    const response = await request(app.getHttpServer())
      .get('/products?limit=101')
      .expect(400);

    expect(response.body.message).toBeDefined();
  });

ตรวจ test ที่ AI เขียนก่อนจะเชื่อมัน — รอบนี้มีสองอย่างที่ต้องดูเป็นพิเศษ: กับดัก ValidationPipe ที่เราเตือนไว้ตั้งแต่ต้นหัวข้อ กับการที่ agent อาจ "จัดระเบียบ" ไฟล์เดิมทิ้งไปด้วย

  • git status ต้องเห็นไฟล์ที่ถูกแก้แค่ test/products.e2e-spec.ts ไฟล์เดียว — ไม่มีไฟล์ใน src/ ถูกแก้ ถ้ามี แปลว่า agent ไปแก้โค้ดให้เข้ากับ test ของมันเอง ให้ย้อนกลับแล้วสั่งใหม่
  • git diff test/products.e2e-spec.ts ต้องเห็นแค่ ส่วนที่เพิ่ม — สี่ it() เดิมยังอยู่ครบและข้อความในนั้นไม่ถูกแก้ ถ้า diff แสดงว่าไฟล์ถูกเขียนใหม่ทั้งไฟล์ ให้ไล่อ่านว่ามีเงื่อนไขไหนหายไปบ้าง
  • beforeAll มี app.useGlobalPipes(...) พร้อมตัวเลือกครบสามข้อตรงกับ src/main.ts — นี่คือกับดักคลาสสิกของ e2e test ใน Nest ถ้า agent ลืมข้อนี้ สอง test ของ limit=0 และ limit=101 จะไม่ผ่าน และคุณจะจับได้ตั้งแต่รันครั้งแรก
  • สาม it() ใหม่ยิงผ่าน request(app.getHttpServer()) เหมือนเดิม — ไม่มี http://localhost:3000 หรือเลข port โผล่ในไฟล์ และไม่มีการ mock PrismaService ทิ้ง
  • พิสูจน์ว่าบรรทัด useGlobalPipes มีผลจริง: ลบมันออกจาก beforeAll ชั่วคราวแล้วรัน npm run test:e2e -- products — สอง test ของ limit=0 และ limit=101 ต้องล้มทั้งคู่เพราะ status ที่ได้ไม่ใช่ 400 อีกต่อไป (ไม่มี pipe ตัวไหนตรวจ query เลย — ค่าที่ไหลเข้าไปจะเป็น string ดิบ ไม่ใช่ number ที่ผ่านการตรวจช่วงแล้ว) ใส่กลับคืนแล้วต้องเขียวครบเจ็ด
  • commit ด้วย git add -A && git commit -m "test: contract e2e for pagination"
