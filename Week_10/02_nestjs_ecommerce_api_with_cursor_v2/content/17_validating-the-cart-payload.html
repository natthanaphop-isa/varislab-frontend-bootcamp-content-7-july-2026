Validate Payload ของ POST /carts/add

เมื่อจบบทนี้ คุณจะสามารถ

  • เขียน DTO ที่มี object และ array ซ้อนอยู่ข้างใน ให้ ValidationPipe ตรวจได้จริงทุกชั้น
  • อธิบายได้ว่าทำไม nested object ต้องมีทั้ง @ValidateNested() และ @Type(() => Class)
  • เทียบ zod schema ฝั่ง React กับ DTO ฝั่ง API และบอกได้ว่าทำไมต้องตรวจซ้ำทั้งสองฝั่ง

ทวนของเดิม: DTO + whitelist

บทที่ 15–17 ของคอร์ส NestJS Fundamentals วางกติกาไว้แล้วว่า body ที่เข้ามาต้องผ่าน DTO ที่เป็น class ไม่ใช่ interface เพราะ decorator ของ class-validator ต้องเกาะอยู่กับ metadata ของ class จริงตอน runtime ส่วน interface หายไปหมดตอน compile และตั้งแต่บทที่ 13 ของคอร์สนี้ src/main.ts ก็เปิด ValidationPipe แบบ global ไว้แล้ว

app.useGlobalPipes(
  new ValidationPipe({
    whitelist: true,
    transform: true,
    transformOptions: { enableImplicitConversion: true },
  }),
);

สามตัวเลือกนี้มีผลกับบทนี้ตรง ๆ: whitelist: true ตัด field ที่ไม่มี decorator ออกจาก body ทิ้งเงียบ ๆ (client แนบ isAdmin: true มาก็ไม่มีทางไหลเข้า service), transform: true สั่งให้ pipe แปลง body ดิบเป็น instance ของ DTO และ enableImplicitConversion แปลง string เป็น number ตามชนิดที่ประกาศไว้ให้ — สะดวกกับ query string ในบทที่ 13 แต่ body ของบทนี้เป็น JSON ที่มีชนิดข้อมูลมาถูกต้องแล้ว

nested object ไม่ถูกตรวจเอง

กับดักใหญ่ที่สุดของ DTO ซ้อนชั้นคือ: class-validator ตรวจได้เฉพาะ instance ของ class เท่านั้น แต่ JSON.parse คืน plain object ธรรมดาที่ไม่มี constructor ผูกอยู่ ดังนั้นถึงเราประกาศชนิดว่า address: AddressDto ตัว pipe ก็ยังไม่รู้ว่าจะต้องเอา rule ของ class ไหนไปตรวจ object ก้อนนั้น เพราะ type annotation ของ TypeScript หายไปตอน compile

จึงต้องใช้สอง decorator คู่กัน

Decoratorมาจากทำอะไร
@Type(() => AddressDto)class-transformerบอกว่าจะ สร้าง ก้อน JSON นี้เป็น instance ของ class ไหน ถ้าไม่มีบรรทัดนี้ object จะยังเป็น plain object
@ValidateNested()class-validatorบอกว่าให้ไล่ตรวจ rule ข้างใน instance นั้นต่อ ไม่ใช่ตรวจแค่ว่ามี field นี้
@ValidateNested({ each: true })class-validatorรูปแบบสำหรับ array — ไล่ตรวจทุกสมาชิก ไม่ใช่ตรวจตัว array เป็นก้อนเดียว
@ArrayMinSize(1)class-validatorตะกร้าว่างต้องไม่กลายเป็นคำสั่งซื้อ — products: [] ต้องได้ 400 ไม่ใช่ order ยอด 0 บาท

ถ้าลืม @Type(() => AddressDto) จะไม่มี error อะไรเลย แต่ validation ของ address จะผ่านทุกอย่าง — ส่ง {"address": {}} ก็ผ่าน นี่คือความพลาดที่อันตรายที่สุดในบทนี้ เพราะเงียบสนิทจนกว่าจะมีข้อมูลเสียลงฐานข้อมูล

เราเรียง class เล็กไปใหญ่เพื่ออ่านง่าย: CartProductDto → AddressDto → AddCartDto — arrow function ใน @Type(() => CartProductDto) ถูกเรียกตอน class-transformer แปลง payload จริง (คือตอนมี request เข้ามา) ไม่ใช่ตอนประกาศ class จึงไม่ผูกกับลำดับการประกาศ นั่นคือเหตุผลที่ @Type รับ function ไม่ใช่รับ class ตรง ๆ

ตรวจสองฝั่งไม่ใช่ความซ้ำซ้อน

ฝั่ง React app ตรวจ address ด้วย zod อยู่แล้ว (src/features/checkout/schema.ts)

export const checkoutAddressSchema = z.object({
  address: z.string().min(1, "Address is required"),
  email: z
    .string()
    .min(1, "Email is required")
    .pipe(z.email("Enter a valid email address")),
  phone: z.string().min(1, "Phone number is required"),
});

DTO ของเราจะสะท้อนกฎเดียวกันทีละข้อ: address ไม่ว่าง → @IsString() @IsNotEmpty(), email ต้องเป็นอีเมล → @IsEmail(), phone ไม่ว่าง → @IsString() @IsNotEmpty() ที่ต้องตรวจซ้ำเพราะ validation ฝั่ง client เป็นเรื่องของ ประสบการณ์ผู้ใช้ ไม่ใช่ความปลอดภัย — ใครก็ยิง curl ตรงเข้า API ข้าม React ไปได้ กฎง่าย ๆ คือข้อมูลจากภายนอกไม่เชื่อถือได้เลย จนกว่า API จะตรวจเอง

ส่วนรูปแบบ error ที่ตอบออกไปจะไม่เหมือน dummyjson: dummyjson ตอบ 400 พร้อม {"message": "User id is required"} เป็น string เดี่ยว ของเราตอบตามมาตรฐาน Nest คือ message เป็น array ของทุกข้อที่ผิด นี่เป็นความต่างที่เรายอมรับ เพราะ ApiError ของ React app อ่านค่าจาก data.message ได้ทั้งสองแบบ และการบอกครบทุกข้อในรอบเดียวมีประโยชน์กับคนใช้ API มากกว่า

สั่ง Cursor เขียน DTO ของ POST /carts/add

commit งานก่อน แล้วเปิดแชทใหม่ใน Cursor โหมด Agent (git add -A && git commit -m "chore: before add-cart dto") — prompt ให้ @src/products/dto/pagination-query.dto.ts เป็นตัวอย่างสไตล์ DTO ของโปรเจกต์ และให้ @src/main.ts เพื่อให้ AI เห็นว่า ValidationPipe ตั้งค่าไว้แบบไหนแล้ว

ก่อนส่ง อ่านกติกาของคอร์สอีกครั้ง: AI พิมพ์แทนคุณได้ แต่คุณต้องอธิบายทุกบรรทัดได้ — ถ้าอธิบายไม่ได้ แปลว่ายังไม่ผ่านบทนี้

สร้าง DTO สำหรับ validate body ของ POST /carts/add ตามที่ React app ส่งมา บริบท: @src/products/dto/pagination-query.dto.ts @src/main.ts @docs/contract/cart-add.txt @.cursor/rules/project.mdc ValidationPipe แบบ global เปิด whitelist และ transform อยู่แล้ว (ดูใน main.ts) React app ส่ง body รูปนี้เสมอ: { "userId": 1, "products": [{ "id": 1, "quantity": 2 }], "address": { "address": "...", "email": "...", "phone": "..." } } address ฝั่ง React ถูก validate ด้วย zod: address ต้องไม่ว่าง, email ต้องเป็นอีเมล, phone ต้องไม่ว่าง — ฝั่ง API ต้องตรวจซ้ำ dummyjson ตอบ 400 { "message": "User id is required" } เมื่อไม่มี userId ของเราให้ ValidationPipe ตอบ 400 ตามรูปแบบมาตรฐานของ Nest ได้เลย โครงสร้าง: สร้างไฟล์เดียว - src/orders/dto/add-cart.dto.ts (สร้างใหม่) ข้อกำหนดทางเทคนิค: - export class สามตัวในไฟล์เดียว เรียงตามลำดับนี้ CartProductDto: @IsInt() @Min(1) id: number และ @IsInt() @Min(1) quantity: number AddressDto: @IsString() @IsNotEmpty() address: string, @IsEmail() email: string, @IsString() @IsNotEmpty() phone: string AddCartDto: @IsInt() @Min(1) userId: number, @IsArray() @ArrayMinSize(1) @ValidateNested({ each: true }) @Type(() => CartProductDto) products: CartProductDto[], @ValidateNested() @Type(() => AddressDto) address: AddressDto - @Type มาจาก class-transformer ที่เหลือมาจาก class-validator - ไม่มี field ใดเป็น optional ไม่มี default - ห้ามใช้ interface สำหรับ body เพราะ ValidationPipe ต้องการ class ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ - ห้ามแก้ไฟล์อื่น - ยังไม่ต้องสร้าง service, controller หรือ module ของ orders

ตรวจโค้ดที่ AI สร้าง

  • ลำดับ class ในไฟล์คือ CartProductDto, AddressDto แล้วค่อย AddCartDto — เป็นเรื่องความอ่านง่าย ไม่ใช่ข้อบังคับทางเทคนิค (thunk ใน @Type() ทำให้ลำดับไม่สำคัญ) แต่ให้จัดให้ตรงกันเพื่อเทียบกับโค้ดอ้างอิงทีละบรรทัดได้
  • @Type() ปรากฏ สองครั้ง คือที่ products และที่ address (ค้นด้วย grep -c "@Type" src/orders/dto/add-cart.dto.ts ต้องได้ 2)
  • Type import มาจาก class-transformer ส่วน decorator ที่เหลือมาจาก class-validator — สอง package ไม่ปนกัน
  • products มี @ArrayMinSize(1) และ @ValidateNested({ each: true }) ครบ
  • email ใช้ @IsEmail() ไม่ใช่ @IsString() เปล่า ๆ และไม่มี regex เขียนเองมาแทน
  • ไม่มี @IsOptional(), ไม่มีค่า default, ไม่มี ? หลังชื่อ field ตัวใดเลย
  • id, quantity, userId ใช้ @IsInt() คู่กับ @Min(1) — id 0 หรือจำนวน 0 ชิ้นไม่ใช่ค่าที่ถูกต้อง
  • ไม่มีไฟล์อื่นถูกแก้ (git status เห็นไฟล์ใหม่ไฟล์เดียว) และ package.json ไม่เปลี่ยน

AI มักพลาดตรงนี้: ลืม @Type(() => AddressDto) ที่ field address เพราะมันดู "ไม่ใช่ array" จึงรู้สึกว่าไม่ต้องมี ผลคือ address กลายเป็น plain object ที่ validation ผ่านทุกค่า รวมถึง object ว่าง ตรวจง่าย ๆ ด้วยการนับจำนวน @Type ในไฟล์ว่าได้ 2 จริง อีกกรณีคือใส่ @IsObject() แทน @ValidateNested() ซึ่งตรวจแค่ว่า "เป็น object" แล้วจบ

โค้ดอ้างอิงของบทนี้ (เทียบกับของคุณทีละบรรทัด):

// src/orders/dto/add-cart.dto.ts
import { Type } from 'class-transformer';
import {
  ArrayMinSize,
  IsArray,
  IsEmail,
  IsInt,
  IsNotEmpty,
  IsString,
  Min,
  ValidateNested,
} from 'class-validator';

export class CartProductDto {
  @IsInt()
  @Min(1)
  id: number;

  @IsInt()
  @Min(1)
  quantity: number;
}

export class AddressDto {
  @IsString()
  @IsNotEmpty()
  address: string;

  @IsEmail()
  email: string;

  @IsString()
  @IsNotEmpty()
  phone: string;
}

export class AddCartDto {
  @IsInt()
  @Min(1)
  userId: number;

  @IsArray()
  @ArrayMinSize(1)
  @ValidateNested({ each: true })
  @Type(() => CartProductDto)
  products: CartProductDto[];

  @ValidateNested()
  @Type(() => AddressDto)
  address: AddressDto;
}

ถ้าอธิบายบรรทัดไหนไม่ได้ ยังไม่ผ่านบทนี้ — กลับไปอ่านส่วนแนวคิดก่อน

ผลลัพธ์ที่คาดหวัง

ได้ไฟล์ใหม่ไฟล์เดียวคือ src/orders/dto/add-cart.dto.ts และ npm run build ผ่านโดยไม่มี error — โฟลเดอร์ src/orders/ ยังไม่มี module ลงทะเบียนใน AppModule ดังนั้นการ build จะแค่ compile ไฟล์นี้ผ่าน type check ไม่มี route ใหม่โผล่ใน log ของ npm run start:dev และยังไม่มีอะไรให้ curl ทดสอบในบทนี้

ข้อความ error ที่ DTO ชุดนี้จะผลิตออกมา จะได้เห็นของจริงในบทที่ 19 — เช่น userId ที่ไม่ได้ส่งมาให้ {"message":["userId must not be less than 1","userId must be an integer number"],"error":"Bad Request","statusCode":400} และ email ผิดรูปให้ {"message":["address.email must be an email"],"error":"Bad Request","statusCode":400} สังเกตคำนำหน้า address. — นั่นคือหลักฐานว่า @ValidateNested() ไล่ตรวจเข้าไปข้างในจริง

ตรวจว่าใช้งานได้จริง

  • npm run build ผ่าน ไม่มี error
  • npm run lint ผ่าน (oxlint ดู src/ จึงครอบไฟล์นี้แล้ว)
  • grep -c "@Type" src/orders/dto/add-cart.dto.ts ได้ 2
  • grep -n "IsOptional\|?:" src/orders/dto/add-cart.dto.ts ไม่เจออะไรเลย — ยืนยันว่าไม่มี field optional หลุดมา
  • git diff --stat HEAD เห็นไฟล์เดียว และ package.json กับ package-lock.json ไม่อยู่ในรายการ
  • commit ผลงานของบทนี้: git add -A && git commit -m "feat: add-cart dto"
