Refresh Token ที่หมุนได้ และ Logout

เมื่อจบบทนี้ คุณจะสามารถ

  • อธิบายได้ว่าทำไม refresh token ต้องใช้ได้ครั้งเดียว และการหมุนมันช่วยจับกรณี token ถูกขโมยได้อย่างไร
  • เลือกวิธี hash ให้เหมาะกับสิ่งที่ hash — และบอกได้ว่าทำไมการใช้ bcrypt กับ JWT เป็นบั๊กที่เงียบสนิท
  • ทำให้ logout มีผลจริงในระบบที่ไม่มี session ฝั่ง server

ทำไมต้องหมุน

access token ของเราอายุ 15 นาที พอหมดอายุ ผู้ใช้ไม่ควรต้องพิมพ์รหัสผ่านใหม่ — นั่นคืองานของ refresh token ที่อายุ 7 วัน แลกใบใหม่ให้โดยไม่ต้อง login ซ้ำ

คำถามที่ตามมาคือ ถ้า refresh token อยู่ได้ 7 วันและใช้ซ้ำได้เรื่อย ๆ แล้วมันต่างอะไรกับ access token อายุ 7 วัน คำตอบคือไม่ต่าง ถ้าเราปล่อยให้ใช้ซ้ำได้ เราก็แค่เปลี่ยนชื่อของที่รั่วแล้วอันตรายยาวนานเท่าเดิม

การหมุน (rotation) ทำให้มันต่างจริง: ทุกครั้งที่แลก เราออก refresh token ใบใหม่และทำให้ใบเดิมใช้ไม่ได้ทันที ผลที่ได้คือกลไกจับขโมยฟรี ๆ สมมติมีคนขโมย refresh token ของผู้ใช้ไป จะเกิดหนึ่งในสองกรณีนี้เสมอ

ใครใช้ก่อนเกิดอะไรขึ้น
ขโมยใช้ก่อนขโมยได้ใบใหม่ไป แต่ใบที่ผู้ใช้จริงถืออยู่กลายเป็นใบเก่าทันที — ผู้ใช้จริงจะโดนเด้งออกจากระบบแบบไม่มีสาเหตุ ซึ่งเป็นสัญญาณที่สังเกตได้
ผู้ใช้จริงใช้ก่อนใบที่ขโมยถืออยู่กลายเป็นใบเก่าและใช้ไม่ได้ทันที ขโมยหลุดออกจากระบบเอง

ถ้าไม่หมุน ทั้งสองฝ่ายจะใช้ใบเดียวกันต่อไปได้พร้อมกันเป็นสัปดาห์โดยไม่มีใครรู้เลย

ระบบจริงมักเดินต่ออีกขั้น: ถ้าเจอคนเอา refresh token ใบที่ถูกหมุนไปแล้วมาใช้ ให้ถือว่ามีการขโมยเกิดขึ้นแน่นอน แล้วยกเลิก token ทั้งสายของผู้ใช้คนนั้นทันที เราจะไม่ทำขั้นนั้นในคอร์สนี้ แต่โครงสร้างที่สร้างในบทนี้รองรับมันได้แล้ว

เก็บอะไรไว้ฝั่ง server

การจะบอกได้ว่า "ใบนี้ใบเก่าแล้ว" แปลว่า server ต้องจำได้ว่าใบล่าสุดคือใบไหน เราจึงเพิ่มคอลัมน์หนึ่งช่องใน User ไว้เก็บ refresh token ใบปัจจุบัน — แต่เก็บเป็น hash ไม่ใช่ตัว token เอง ด้วยเหตุผลเดียวกับรหัสผ่าน: ถ้าฐานข้อมูลหลุด คนที่ได้ไปต้องสวมรอยเป็นผู้ใช้ไม่ได้

ทีนี้คำถามสำคัญของบทนี้ — hash ด้วยอะไร

ห้าม bcrypt กับ JWT เด็ดขาด

คำตอบที่ดูสมเหตุสมผลที่สุดคือใช้ PasswordService ตัวเดิมที่เขียนไว้แล้ว มันก็ hash เหมือนกัน และเราก็มีมันอยู่แล้ว — และมันจะพังแบบเงียบสนิท

เอกสารของ bcrypt เขียนไว้ตรง ๆ ว่า "Only the first 72 bytes of input are used" — มันอ่านแค่ 72 ไบต์แรกของสิ่งที่ป้อนเข้าไป ส่วนที่เหลือถูกทิ้ง ซึ่งไม่เคยเป็นปัญหากับรหัสผ่านเพราะแทบไม่มีใครตั้งรหัสผ่านยาวขนาดนั้น

แต่ JWT ยาวกว่านั้นมาก และที่แย่กว่าคือ 72 ไบต์แรกของ refresh token ทุกใบของผู้ใช้คนเดียวกันเหมือนกันหมด เพราะมันคือ header ที่คงที่ (eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9) ต่อด้วยต้น payload ที่ขึ้นด้วย {"sub":1,... เหมือนเดิมทุกครั้ง ส่วนที่ทำให้แต่ละใบต่างกันคือ iat, exp และลายเซ็น ซึ่งอยู่หลังไบต์ที่ 72 ทั้งหมด

ผลคือ bcrypt.compare(ใบเก่า, hashของใบใหม่) จะคืน true — การหมุนไม่เกิดขึ้นจริง ใบเก่ายังใช้ได้ และ logout ก็ไม่มีผล ทั้งหมดนี้โดยที่โค้ดดูถูกต้องทุกบรรทัด ไม่มี error ไม่มี warning ไม่มี test ไหนแดงถ้าไม่ได้ตั้งใจทดสอบกรณีนี้โดยเฉพาะ คุณจะได้เห็นมันกับตาในส่วนตรวจท้ายบท

ทางที่ถูกคือ SHA-256 จาก node:crypto ที่มากับ Node อยู่แล้ว

รหัสผ่านrefresh token
ความสุ่มของต้นทางต่ำ — คนเลือกเอง เดาได้สูงมาก — เครื่องสร้าง มีลายเซ็นเข้ารหัสกำกับ
สิ่งที่ต้องกันการไล่เดาจำนวนมหาศาลการอ่านค่าดิบจากฐานข้อมูลที่หลุด
จึงต้องการhash ที่ช้าโดยตั้งใจ + salt → bcrypthash ที่เร็วและไม่ตัดความยาว → SHA-256

การทำ bcrypt กับของที่สุ่มมาอยู่แล้วไม่ได้เพิ่มความปลอดภัยเลย เพราะไม่มีใครไล่เดา JWT ทีละใบได้อยู่แล้ว มันแค่ทำให้ทุก request ที่ refresh ช้าลง — และในกรณีนี้ยังพาบั๊กร้ายแรงมาด้วย

ทำไม refresh ไม่ต้องมี token แต่ logout ต้องมี

POST /auth/refresh ต้องติด @Public() ซึ่งฟังดูขัดความรู้สึก แต่เป็นสิ่งที่ถูก: หน้าที่ของมันคือทำงานตอน access token หมดอายุไปแล้ว ถ้า guard บังคับให้ต้องมี access token ที่ยังไม่หมดอายุก่อน มันก็จะใช้ไม่ได้ในสถานการณ์เดียวที่มันมีไว้เพื่อรับมือ สิ่งที่พิสูจน์ตัวตนของ request นี้คือ refresh token ใน body ไม่ใช่ header

ส่วน POST /auth/logout ยังต้องมี access token ตามปกติ เพราะมันคือคำสั่งที่ผู้ใช้ตั้งใจส่งจาก session ที่ยังทำงานอยู่ ถ้า access token หมดอายุไปแล้วก็ให้ refresh ก่อนแล้วค่อย logout — และถ้าไม่ทำอะไรเลย refresh token ก็จะหมดอายุไปเองใน 7 วันอยู่ดี

ตรวจโค้ดที่ AI สร้าง

  • hash ของ refresh token มาจาก createHash('sha256') — grep -rn "bcrypt" src/ ยังต้องเจอไฟล์เดียวคือ password.service.ts
  • POST /auth/refresh ติด @Public() ส่วน POST /auth/logout ไม่ติด
  • การเทียบ hash ทำกับค่าที่ hash แล้ว ทั้งสองฝั่ง ไม่ได้เอา token ดิบไปเทียบกับ hash ตรง ๆ
  • refresh ตรวจสองอย่างเสมอ: ลายเซ็นของ token ถูกต้อง และ hash ตรงกับที่เก็บไว้ — ถ้าตรวจแค่ลายเซ็น การหมุนจะไม่มีความหมายเลย เพราะใบเก่าก็ลายเซ็นถูกเหมือนกัน
  • คอลัมน์ใหม่เป็น optional (String?) และ migration.sql ไม่มี NOT NULL ที่จะทำให้แถวเดิมพัง
  • logout ตอบ 204 ด้วย @HttpCode(204) และไม่มี body
  • diff .env .env.example ไม่มีผลต่าง และ git status ไม่มี prisma/seed.ts

AI มักพลาดตรงนี้: ใช้ PasswordService ที่มีอยู่แล้วมา hash refresh token เพราะมันดูเป็นการนำโค้ดกลับมาใช้ซ้ำที่ดี — ผลคือ compare คืน true ให้ refresh token ทุกใบของผู้ใช้คนนั้น การหมุนและ logout จึงไม่ทำงาน โดยที่ทุกอย่างดูปกติดี อีกกรณีคือตรวจแค่ลายเซ็นของ refresh token แล้วออกใบใหม่ให้เลยโดยไม่เทียบกับ hash ที่เก็บไว้ ซึ่งแปลว่าใบเก่าทุกใบที่ยังไม่หมดอายุยังใช้ได้อยู่ทั้งหมด

โค้ดอ้างอิงของบทนี้ — เป็นหนึ่งในวิธีที่ถูก ของคุณไม่จำเป็นต้องเหมือนทุกบรรทัด ขอแค่ผ่านผลลัพธ์ที่ต้องได้:

// prisma/schema.prisma — เฉพาะบรรทัดที่เพิ่มใน model User
  refreshTokenHash String?
// src/auth/auth.service.ts — เฉพาะส่วนที่เกี่ยวกับ refresh
// (ConfigService เข้ามาอยู่ใน constructor เพิ่มจาก PrismaService, PasswordService และ JwtService)
import { createHash } from 'node:crypto';

  private hashToken(token: string): string {
    return createHash('sha256').update(token).digest('hex');
  }

  private async issueTokens(user: {
    id: number;
    email: string;
    role: string;
  }): Promise<AuthResponseDto> {
    const payload = { sub: user.id, email: user.email, role: user.role };

    const accessToken = await this.jwt.signAsync(payload);
    const refreshToken = await this.jwt.signAsync(payload, {
      secret: this.config.getOrThrow<string>('JWT_REFRESH_SECRET'),
      expiresIn: Number(this.config.getOrThrow<string>('JWT_REFRESH_EXPIRES_IN')),
    });

    await this.prisma.user.update({
      where: { id: user.id },
      data: { refreshTokenHash: this.hashToken(refreshToken) },
    });

    return { accessToken, refreshToken };
  }

  async refresh(dto: RefreshDto): Promise<AuthResponseDto> {
    let payload: JwtPayload;

    try {
      payload = await this.jwt.verifyAsync<JwtPayload>(dto.refreshToken, {
        secret: this.config.getOrThrow<string>('JWT_REFRESH_SECRET'),
      });
    } catch {
      throw new UnauthorizedException();
    }

    const user = await this.prisma.user.findUnique({ where: { id: payload.sub } });

    if (
      user === null ||
      user.refreshTokenHash !== this.hashToken(dto.refreshToken)
    ) {
      throw new UnauthorizedException();
    }

    return this.issueTokens(user);
  }

  async logout(userId: number): Promise<void> {
    await this.prisma.user.update({
      where: { id: userId },
      data: { refreshTokenHash: null },
    });
  }

เงื่อนไขสองข้อใน if ของ refresh คือหัวใจของบทนี้ ข้อแรกตรวจว่า token เป็นของจริงที่เราเซ็นเอง ข้อสองตรวจว่ามันเป็นใบล่าสุด ถ้าขาดข้อสอง ใบเก่าทุกใบที่ยังไม่หมดอายุจะใช้ได้หมด และการหมุนจะกลายเป็นพิธีกรรมที่ไม่ได้ป้องกันอะไร

// src/auth/auth.controller.ts — เฉพาะส่วนที่เพิ่ม
  @Public()
  @Post('refresh')
  refresh(@Body() dto: RefreshDto) {
    return this.authService.refresh(dto);
  }

  @Post('logout')
  @HttpCode(204)
  logout(@CurrentUser() user: JwtPayload) {
    return this.authService.logout(user.sub);
  }

[RouterExplorer] Mapped {/auth/refresh, POST} route
[RouterExplorer] Mapped {/auth/logout, POST} route

login ครั้งนี้ได้สองใบครบตามสัญญา

{"accessToken":"eyJhbGciOiJIUzI1NiIs...","refreshToken":"eyJhbGciOiJIUzI1NiIs..."}

แลกใบใหม่ได้สองใบใหม่ แล้วพอเอาใบเดิมมาแลกซ้ำจะได้

{"message":"Unauthorized","error":"Unauthorized","statusCode":401}

ส่วน POST /auth/logout ตอบ 204 โดยไม่มี body ซึ่งเป็นสถานะที่ถูกต้องสำหรับ "ทำสำเร็จแล้วและไม่มีอะไรจะบอก"

ตรวจว่าใช้งานได้จริง

  • คอลัมน์ใหม่มีจริงและว่างได้ 
    docker compose exec db psql -U postgres -d ecommerce -c '\d "User"'
  • login แล้วเก็บ refresh token ใบแรกไว้ 
    R1=$(curl -s -X POST http://localhost:3000/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"student@example.com","password":"secret123"}' \
  | node -e "let d='';process.stdin.on('data',c=>d+=c).on('end',()=>console.log(JSON.parse(d).refreshToken))")
  • hash ที่เก็บไว้ยาว 64 ตัวอักษร — นั่นคือลายเซ็นของ SHA-256 ไม่ใช่ bcrypt (ซึ่งจะได้ 60 และขึ้นต้น $2b$) 
    docker compose exec db psql -U postgres -d ecommerce \
  -c 'SELECT id, length("refreshTokenHash") AS len, left("refreshTokenHash", 8) AS head FROM "User";'
  • แลกใบใหม่ได้ แล้วใบเดิมใช้ไม่ได้อีก — สองบรรทัดนี้ต้องได้ 200 แล้ว 401 ตามลำดับ 
    curl -s -o /dev/null -w '%{http_code}\n' -X POST http://localhost:3000/auth/refresh \
  -H 'Content-Type: application/json' -d "{\"refreshToken\":\"$R1\"}"
curl -s -o /dev/null -w '%{http_code}\n' -X POST http://localhost:3000/auth/refresh \
  -H 'Content-Type: application/json' -d "{\"refreshToken\":\"$R1\"}"
  • ดูบั๊กของ bcrypt ด้วยตาตัวเอง — คำสั่งนี้ hash สตริงหนึ่ง แล้วเอาอีกสตริงที่ต่างกันจริงไปเทียบ สองสตริงนี้เหมือนกัน 72 ไบต์แรกและต่างกันหลังจากนั้น เหมือนกับที่ refresh token สองใบของผู้ใช้คนเดียวกันเป็น 
    node --input-type=commonjs -e "
const b = require('bcrypt');
const a = 'x'.repeat(72) + 'AAA';
const c = 'x'.repeat(72) + 'BBB';
b.hash(a, 10).then(h => b.compare(c, h)).then(r => console.log('bcrypt says they match:', r));
"
    ต้องพิมพ์ bcrypt says they match: true — สองสตริงที่ต่างกันแต่ bcrypt บอกว่าตรงกัน นี่คือเหตุผลทั้งหมดที่เราไม่ใช้มันกับ JWT
  • logout แล้ว refresh ต้องใช้ไม่ได้ (ใช้ access token ใบล่าสุดที่ได้จากการ refresh) 
    curl -s -o /dev/null -w '%{http_code}\n' -X POST http://localhost:3000/auth/logout \
  -H "Authorization: Bearer $TOKEN"
docker compose exec db psql -U postgres -d ecommerce \
  -c 'SELECT id, "refreshTokenHash" IS NULL AS logged_out FROM "User";'
    ต้องได้ 204 แล้ว logged_out เป็น t
  • diff .env .env.example ยังไม่มีผลต่าง (ตอนนี้ไฟล์ละแปดบรรทัด)
  • npm run test:e2e ยังได้ Tests 11 passed (11)
  • commit ผลงานของบทนี้: git add -A && git commit -m "feat: refresh token rotation and logout"
