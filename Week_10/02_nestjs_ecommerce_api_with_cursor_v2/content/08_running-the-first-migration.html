รัน Migration แรกและดูตารางจริง

เมื่อจบบทนี้ คุณจะสามารถ

  • อธิบายได้ว่า prisma migrate dev ทำสามอย่างอะไรในคำสั่งเดียว
  • อ่าน SQL ที่ Prisma สร้างให้ แล้วจับคู่กลับไปยังบรรทัดใน schema.prisma ได้
  • เปิด psql ในคอนเทนเนอร์เพื่อพิสูจน์ว่าคอลัมน์ nullable, array และ index เป็นอย่างที่ออกแบบไว้

บทนี้ไม่มี prompt — เราพิมพ์คำสั่งเองทั้งหมด เพราะเป็นคำสั่งที่แก้ฐานข้อมูลจริง กติกาใน .cursor/rules/project.mdc เขียนห้าม Agent รัน prisma migrate, db push, generate หรือ docker เอาไว้ตั้งแต่บทที่ 4 แล้ว ด้วยเหตุผลข้อนี้

migrate dev ทำสามอย่างในคำสั่งเดียว

เราเคยเห็น migration ครั้งแรกใน Week_09 บทที่ 31 แล้ว ทบทวนว่า prisma migrate dev --name init ทำอะไร

  • เขียนไฟล์ SQL — เทียบ schema.prisma กับสถานะฐานข้อมูลปัจจุบัน แล้วสร้าง prisma/migrations/<timestamp>_init/migration.sql ที่เป็น SQL ธรรมดา อ่านได้ แก้ได้ และ commit ขึ้น git ได้
  • รัน SQL นั้นกับฐานข้อมูล — ตารางเกิดขึ้นจริงหลังคำสั่งนี้
  • บันทึกว่าทำไปแล้ว — เพิ่มแถวในตาราง _prisma_migrations ที่ Prisma ดูแลเอง คราวหน้าจะรู้ว่าไฟล์ไหนรันไปแล้ว ไม่รันซ้ำ

สิ่งที่มันไม่ทำคือ generate Prisma Client — Prisma 7 แยกสองเรื่องนี้ออกจากกัน เราจึงต้องสั่ง npx prisma generate ต่อท้ายทุกครั้งที่ schema เปลี่ยน ไม่อย่างนั้น this.prisma.product จะยังไม่มีอยู่ในสายตาของ TypeScript

migrate dev เป็นคำสั่งของ เครื่องนักพัฒนาเท่านั้น เพราะมันเปรียบเทียบสถานะแล้วอาจเสนอรีเซ็ตฐานข้อมูลเมื่อเจอความไม่ตรงกัน บน production ใช้ prisma migrate deploy ซึ่งรันไฟล์ที่ commit มาแล้วเท่านั้น ไม่สร้างไฟล์ใหม่และไม่ลบข้อมูล

สร้างตารางแล้วเปิดดูของจริง

ตรวจก่อนว่าฐานข้อมูลจากบทที่ 5 ยังรันอยู่ (docker compose ps เห็น db เป็น Up) แล้วรันสี่คำสั่งนี้ตามลำดับ อ่านผลลัพธ์ทุกคำสั่งก่อนไปคำสั่งถัดไป

# 1) สร้างและรัน migration แรก npx prisma migrate dev --name init # 2) generate client ใหม่ให้รู้จัก model ทั้งสาม (Prisma 7 ไม่ทำให้อัตโนมัติ) npx prisma generate # 3) ดูรายชื่อตารางในฐานข้อมูล docker compose exec db psql -U postgres -d ecommerce -c '\dt' # 4) ดูโครงสร้างตาราง Product (ต้องใส่เครื่องหมายคำพูดคร่อมชื่อตาราง) docker compose exec db psql -U postgres -d ecommerce -c '\d "Product"'

ชื่อตารางต้องใส่เครื่องหมายคำพูดคร่อมเพราะ Prisma สร้างตารางด้วยตัวพิมพ์ใหญ่นำ (Product) ขณะที่ PostgreSQL จะแปลงชื่อที่ไม่ได้คร่อมให้เป็นตัวพิมพ์เล็กทั้งหมด — \d Product เฉย ๆ จะหาไม่เจอ

SQL ที่ Prisma เขียนให้ อ่านได้ทุกบรรทัด

เปิด prisma/migrations/<timestamp>_init/migration.sql ขึ้นมาดู นี่คือส่วนต้นของไฟล์ (ทั้งไฟล์มี 68 บรรทัด: CREATE TABLE สามครั้ง, CREATE INDEX สามครั้ง และ ALTER TABLE … ADD CONSTRAINT สองครั้งสำหรับ foreign key)

-- CreateTable
CREATE TABLE "Category" (
    "id" SERIAL NOT NULL,
    "slug" TEXT NOT NULL,
    "name" TEXT NOT NULL,

    CONSTRAINT "Category_pkey" PRIMARY KEY ("id")
);

-- CreateTable
CREATE TABLE "Product" (
    "id" INTEGER NOT NULL,
    "title" TEXT NOT NULL,
    "description" TEXT NOT NULL,
    "price" DOUBLE PRECISION NOT NULL,
    "discountPercentage" DOUBLE PRECISION NOT NULL,
    "rating" DOUBLE PRECISION NOT NULL,
    "stock" INTEGER NOT NULL,
    "tags" TEXT[],
    "brand" TEXT,
    "sku" TEXT NOT NULL,
    "weight" DOUBLE PRECISION NOT NULL,
    "width" DOUBLE PRECISION NOT NULL,
    "height" DOUBLE PRECISION NOT NULL,
    "depth" DOUBLE PRECISION NOT NULL,
    "warrantyInformation" TEXT NOT NULL,
    "shippingInformation" TEXT NOT NULL,
    "availabilityStatus" TEXT NOT NULL,
    "returnPolicy" TEXT NOT NULL,
    "minimumOrderQuantity" INTEGER NOT NULL,
    "barcode" TEXT NOT NULL,
    "qrCode" TEXT NOT NULL,
    "images" TEXT[],
    "thumbnail" TEXT NOT NULL,
    "createdAt" TIMESTAMP(3) NOT NULL,
    "updatedAt" TIMESTAMP(3) NOT NULL,
    "categoryId" INTEGER NOT NULL,

    CONSTRAINT "Product_pkey" PRIMARY KEY ("id")
);

เทียบกับ schema.prisma ของบทที่ 7 จะเห็นการตัดสินใจของเราแปลงเป็น SQL ตรง ๆ: Category.id เป็น SERIAL (คือ integer ที่มี sequence แจกเลขให้) แต่ Product.id เป็น INTEGER ธรรมดาเพราะเราไม่ได้ใส่ autoincrement() ส่วน Float กลายเป็น DOUBLE PRECISION และ DateTime กลายเป็น TIMESTAMP(3)

สามบรรทัดใน \d "Product" ที่พิสูจน์การออกแบบ

ผลของคำสั่งที่สี่คือตารางยาวหนึ่งหน้าจอ ให้มองหาสามจุดนี้

        Column        |              Type              | Collation | Nullable | Default
----------------------+--------------------------------+-----------+----------+---------
 id                   | integer                        |           | not null |
 tags                 | text[]                         |           |          |
 brand                | text                           |           |          |
 categoryId           | integer                        |           | not null |
Indexes:
    "Product_pkey" PRIMARY KEY, btree (id)
    "Product_categoryId_idx" btree ("categoryId")
Foreign-key constraints:
    "Product_categoryId_fkey" FOREIGN KEY ("categoryId") REFERENCES "Category"(id) ON UPDATE CASCADE ON DELETE RESTRICT
  • brand | text | | — ช่อง Nullable ว่าง แปลว่าคอลัมน์นี้ยอมให้เป็น NULL ได้ ตรงกับ brand String? และรองรับสินค้า 92 ชิ้นที่ไม่มียี่ห้อ เทียบกับ sku ที่เขียน not null ไว้ชัดเจน
  • tags | text[] — PostgreSQL เก็บ array ของ text ในคอลัมน์เดียวได้จริง ไม่ต้องมีตาราง ProductTag แยก (คอลัมน์ images ก็เป็น text[] เหมือนกัน)
  • "categoryId" integer not null คู่กับบรรทัด "Product_categoryId_idx" btree ("categoryId") ในส่วน Indexes — นี่คือ @@index([categoryId]) ที่กลายเป็น index จริง และเป็นเหตุผลว่าทำไม GET /products/category/:slug ในบทที่ 14 จะเร็วแม้สินค้าเยอะ

ท้ายผลลัพธ์ยังมีส่วน Referenced by: ที่บอกว่า Review ชี้กลับมาที่ตารางนี้ด้วย ON DELETE CASCADE — ผลของ onDelete: Cascade ที่เราใส่ไว้ใน model Review

docker compose exec db psql … คือวิธีดูฐานข้อมูลแบบไม่ต้องติดตั้งอะไรเพิ่ม (เรายืม psql ที่อยู่ในคอนเทนเนอร์มาใช้) ถ้าถนัด GUI จะต่อ pgAdmin ตามวิธีใน Week_09 บทที่ 21 ก็ได้ — host localhost, port 5432, user postgres, password pass123, database ecommerce คอร์สนี้จะใช้ psql ตลอดเพราะคัดลอกคำสั่งไปวางได้ตรง ๆ

ตรวจว่าใช้งานได้จริง

  • ls prisma/migrations เห็นโฟลเดอร์ <timestamp>_init ที่มี migration.sql อยู่ข้างใน และมีไฟล์ migration_lock.toml ระบุ provider เป็น postgresql
  • ตาราง _prisma_migrations มีหนึ่งแถว: docker compose exec db psql -U postgres -d ecommerce -c 'SELECT migration_name FROM _prisma_migrations;' ต้องคืนชื่อ migration ของคุณแถวเดียว
  • grep -c Product src/generated/prisma/client.ts ได้ค่ามากกว่า 0 — client ที่ generate ใหม่รู้จัก model Product แล้ว (ไฟล์นี้ export ชนิด Category, Product, Review ให้บทหลัง ๆ import ไปใช้)
  • npm run build ผ่าน — ยืนยันว่า client ที่ generate ใหม่ยังเข้ากันได้กับโค้ดเดิม
  • git status เห็นเฉพาะโฟลเดอร์ prisma/migrations/ เป็นของใหม่ (src/generated/prisma ถูก ignore ไว้แล้วตั้งแต่บทที่ 6)
  • commit ด้วย git add -A && git commit -m "chore: init migration"
