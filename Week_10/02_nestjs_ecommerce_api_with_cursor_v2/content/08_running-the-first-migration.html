รัน Migration แรกและดูตารางจริง

เมื่อจบบทนี้ คุณจะสามารถ

  • อธิบายได้ว่า prisma migrate dev ทำสามอย่างอะไรในคำสั่งเดียว
  • อ่าน SQL ที่ Prisma สร้างให้ แล้วจับคู่กลับไปยังบรรทัดใน schema.prisma ได้ — รวมถึงคอลัมน์ nullable, array, index และ foreign key
  • เปิด Prisma Studio ดูตารางทั้งสามที่เพิ่งเกิดขึ้นจริง และอธิบายได้ว่าทำไม _prisma_migrations ไม่อยู่ในรายการ

บทนี้ไม่มี prompt — เราพิมพ์คำสั่งเองทั้งหมด เพราะเป็นคำสั่งที่แก้ฐานข้อมูลจริง กติกาใน .cursor/rules/project.mdc เขียนห้าม Agent รัน prisma migrate, db push, generate หรือ docker เอาไว้ตั้งแต่ตอนเขียนไฟล์ rules แล้ว ด้วยเหตุผลข้อนี้

migrate dev ทำสามอย่างในคำสั่งเดียว

เราเคยเห็น migration ครั้งแรกใน NestJS Fundamentals บทตั้งค่า Migrations ด้วย Prisma Migrate แล้ว ทบทวนว่า prisma migrate dev --name init ทำอะไร

  • เขียนไฟล์ SQL — เทียบ schema.prisma กับสถานะฐานข้อมูลปัจจุบัน แล้วสร้าง prisma/migrations/<timestamp>_init/migration.sql ที่เป็น SQL ธรรมดา อ่านได้ แก้ได้ และ commit ขึ้น git ได้
  • รัน SQL นั้นกับฐานข้อมูล — ตารางเกิดขึ้นจริงหลังคำสั่งนี้
  • บันทึกว่าทำไปแล้ว — เพิ่มแถวในตาราง _prisma_migrations ที่ Prisma ดูแลเอง คราวหน้าจะรู้ว่าไฟล์ไหนรันไปแล้ว ไม่รันซ้ำ

สิ่งที่มันไม่ทำคือ generate Prisma Client — Prisma 7 แยกสองเรื่องนี้ออกจากกัน เราจึงต้องสั่ง npx prisma generate ต่อท้ายทุกครั้งที่ schema เปลี่ยน ไม่อย่างนั้น this.prisma.product จะยังไม่มีอยู่ในสายตาของ TypeScript

migrate dev เป็นคำสั่งของ เครื่องนักพัฒนาเท่านั้น เพราะมันเปรียบเทียบสถานะแล้วอาจเสนอรีเซ็ตฐานข้อมูลเมื่อเจอความไม่ตรงกัน บน production ใช้ prisma migrate deploy ซึ่งรันไฟล์ที่ commit มาแล้วเท่านั้น ไม่สร้างไฟล์ใหม่และไม่ลบข้อมูล

สร้างตารางแล้วเปิดดูของจริง

ตรวจก่อนว่าฐานข้อมูลที่ยกขึ้นด้วย Docker ยังรันอยู่ (docker compose ps เห็น db เป็น Up) แล้วรันสามคำสั่งนี้ตามลำดับ อ่านผลลัพธ์ทุกคำสั่งก่อนไปคำสั่งถัดไป

# 1) สร้างและรัน migration แรก npx prisma migrate dev --name init # 2) generate client ใหม่ให้รู้จัก model ทั้งสาม (Prisma 7 ไม่ทำให้อัตโนมัติ) npx prisma generate # 3) เปิด Prisma Studio ดูตารางที่เพิ่งเกิด npx prisma studio

คำสั่งที่สามจะเปิดเบราว์เซอร์ไปที่ http://localhost:5555 ให้เอง และยึดเทอร์มินัลไว้ตราบใดที่ Studio ยังเปิดอยู่ ดังนั้นให้เปิดแท็บเทอร์มินัลใหม่สำหรับคำสั่งถัดไป หรือกด Ctrl+C ปิด Studio ก่อนก็ได้

ส่วน npx prisma studio จะเปิดหน้าเว็บที่มีแถบด้านซ้ายไล่ชื่อ model ทั้งสามของเรา — Category, Product, Review — คลิกเข้าไปตัวไหนก็ได้จะเห็นหัวคอลัมน์ครบตามที่ออกแบบไว้ แต่ยังไม่มีแถวข้อมูลสักแถว ซึ่งถูกแล้ว เพราะ migration สร้างแค่โครงตาราง ข้อมูลจะเข้ามาตอนเขียน seed ในขั้นถัดไป

สังเกตว่าแถบซ้ายไม่มี _prisma_migrations ทั้งที่ตารางนั้นมีอยู่จริงในฐานข้อมูล เพราะ Studio อ่านรายชื่อจาก schema.prisma ของเรา ไม่ได้ไล่ดูทุกตารางในฐานข้อมูล — และ _prisma_migrations เป็นสมุดบัญชีที่ Prisma ดูแลเอง ไม่ใช่ model ที่เราเขียน ถ้าอยากตรวจว่ามันบันทึก migration ไว้จริงไหม ใช้ npx prisma migrate status ซึ่งอ่านตารางนั้นให้เราอยู่แล้ว

SQL ที่ Prisma เขียนให้ อ่านได้ทุกบรรทัด

เปิด prisma/migrations/<timestamp>_init/migration.sql ขึ้นมาดู นี่คือส่วนต้นของไฟล์ (ทั้งไฟล์มี 68 บรรทัด: CREATE TABLE สามครั้ง, CREATE INDEX สามครั้ง และ ALTER TABLE … ADD CONSTRAINT สองครั้งสำหรับ foreign key)

-- CreateTable
CREATE TABLE "Category" (
    "id" SERIAL NOT NULL,
    "slug" TEXT NOT NULL,
    "name" TEXT NOT NULL,

    CONSTRAINT "Category_pkey" PRIMARY KEY ("id")
);

-- CreateTable
CREATE TABLE "Product" (
    "id" INTEGER NOT NULL,
    "title" TEXT NOT NULL,
    "description" TEXT NOT NULL,
    "price" DOUBLE PRECISION NOT NULL,
    "discountPercentage" DOUBLE PRECISION,
    "rating" DOUBLE PRECISION NOT NULL,
    "stock" INTEGER NOT NULL,
    "tags" TEXT[],
    "brand" TEXT NOT NULL,
    "sku" TEXT NOT NULL,
    "weight" DOUBLE PRECISION NOT NULL,
    "width" DOUBLE PRECISION NOT NULL,
    "height" DOUBLE PRECISION NOT NULL,
    "depth" DOUBLE PRECISION NOT NULL,
    "warrantyInformation" TEXT NOT NULL,
    "shippingInformation" TEXT NOT NULL,
    "availabilityStatus" TEXT NOT NULL,
    "returnPolicy" TEXT NOT NULL,
    "minimumOrderQuantity" INTEGER NOT NULL,
    "barcode" TEXT NOT NULL,
    "qrCode" TEXT NOT NULL,
    "images" TEXT[],
    "thumbnail" TEXT NOT NULL,
    "createdAt" TIMESTAMP(3) NOT NULL,
    "updatedAt" TIMESTAMP(3) NOT NULL,
    "categoryId" INTEGER NOT NULL,

    CONSTRAINT "Product_pkey" PRIMARY KEY ("id")
);

เทียบกับ schema.prisma ที่เขียนไว้ จะเห็นการตัดสินใจของเราแปลงเป็น SQL ตรง ๆ: Category.id เป็น SERIAL (คือ integer ที่มี sequence แจกเลขให้) แต่ Product.id เป็น INTEGER ธรรมดาเพราะเราไม่ได้ใส่ autoincrement() ส่วน Float กลายเป็น DOUBLE PRECISION และ DateTime กลายเป็น TIMESTAMP(3)

สามจุดท้ายไฟล์ที่พิสูจน์การออกแบบ

Studio ตอบได้แค่ว่าตารางมีอยู่จริง แต่ไม่ได้บอกว่าคอลัมน์ไหน nullable หรือมี index อะไรบ้าง หลักฐานของเรื่องพวกนั้นอยู่ในไฟล์เดียวกัน — migration.sql นี่แหละ เลื่อนลงไปท้ายไฟล์ ถัดจาก CREATE TABLE ทั้งสามจะเจอ index และ foreign key

-- CreateIndex
CREATE UNIQUE INDEX "Category_slug_key" ON "Category"("slug");

-- CreateIndex
CREATE INDEX "Product_categoryId_idx" ON "Product"("categoryId");

-- CreateIndex
CREATE INDEX "Review_productId_idx" ON "Review"("productId");

-- AddForeignKey
ALTER TABLE "Product" ADD CONSTRAINT "Product_categoryId_fkey" FOREIGN KEY ("categoryId") REFERENCES "Category"("id") ON DELETE RESTRICT ON UPDATE CASCADE;

-- AddForeignKey
ALTER TABLE "Review" ADD CONSTRAINT "Review_productId_fkey" FOREIGN KEY ("productId") REFERENCES "Product"("id") ON DELETE CASCADE ON UPDATE CASCADE;
  • "discountPercentage" DOUBLE PRECISION, ใน CREATE TABLE "Product" — ไม่มี NOT NULL ต่อท้าย แปลว่าคอลัมน์นี้ยอมให้เป็น NULL ได้ ตรงกับ discountPercentage Float? เพราะสินค้าบางชิ้นของเราไม่มีส่วนลด เทียบกับบรรทัด "brand" TEXT NOT NULL ที่บังคับไว้ชัดเจน เพราะเราออกแบบให้สินค้าทุกชิ้นต้องมียี่ห้อ
  • "tags" TEXT[], — PostgreSQL เก็บ array ของ text ในคอลัมน์เดียวได้จริง ไม่ต้องมีตาราง ProductTag แยก (คอลัมน์ images ก็เป็น TEXT[] เหมือนกัน)
  • CREATE INDEX "Product_categoryId_idx" — นี่คือ @@index([categoryId]) ที่กลายเป็น index จริง และเป็นเหตุผลว่าทำไม GET /products/category/:slug จะเร็วแม้สินค้าเยอะ ส่วน CREATE UNIQUE INDEX "Category_slug_key" มาจาก @unique ที่เราใส่ไว้บน Category.slug — เป็นคำสั่งคนละตัวกัน เพราะ unique คือกติกาที่ห้ามค่าซ้ำ ไม่ใช่แค่ทางลัดในการค้น

สอง ALTER TABLE ท้ายไฟล์คือ relation ที่เราเขียนไว้ และท่อนท้ายของแต่ละบรรทัดคือคำตอบว่าถ้าแถวแม่ถูกลบจะเกิดอะไรขึ้น — Review ได้ ON DELETE CASCADE ตาม onDelete: Cascade ที่เราใส่ไว้ (ลบสินค้า รีวิวของสินค้านั้นหายตามไปด้วย) ขณะที่ Product ได้ ON DELETE RESTRICT ซึ่งเป็นค่าปริยายของ relation ที่บังคับมีค่า (ลบหมวดที่ยังมีสินค้าอยู่ไม่ได้ ต้องจัดการสินค้าก่อน)

Prisma Studio คือ GUI ที่มากับ Prisma อยู่แล้ว ไม่ต้องติดตั้งอะไรเพิ่มและไม่ต้องกรอก connection string เพราะมันอ่าน prisma7.config.ts เอง ถ้าถนัด pgAdmin จะต่อตามวิธีใน NestJS Fundamentals บทดูฐานข้อมูล Postgres ด้วย GUI ก็ได้ — host localhost, port 5432, user postgres, password pass123, database ecommerce ส่วนบทหลัง ๆ ที่ต้องตรวจผลด้วยคำสั่ง SQL ตรง ๆ (เช่น นับสินค้าต่อหมวด) จะใช้ psql ในคอนเทนเนอร์ เพราะคัดลอกคำสั่งไปวางได้ทันที

ตรวจว่าใช้งานได้จริง

  • ls prisma/migrations เห็นโฟลเดอร์ <timestamp>_init ที่มี migration.sql อยู่ข้างใน และมีไฟล์ migration_lock.toml ระบุ provider เป็น postgresql
  • npx prisma migrate status รายงานว่า migration ที่เพิ่งสร้างถูก apply ลงฐานข้อมูลแล้ว และไม่มี migration ค้างรอ — คำสั่งนี้อ่านจากตาราง _prisma_migrations ให้เรา
  • grep -c Product src/generated/prisma/client.ts ได้ค่ามากกว่า 0 — client ที่ generate ใหม่รู้จัก model Product แล้ว (ไฟล์นี้ export ชนิด Category, Product, Review ให้บทหลัง ๆ import ไปใช้)
  • npm run build ผ่าน — ยืนยันว่า client ที่ generate ใหม่ยังเข้ากันได้กับโค้ดเดิม
  • git status เห็นเฉพาะโฟลเดอร์ prisma/migrations/ เป็นของใหม่ (src/generated/prisma ถูก ignore ไว้แล้วตั้งแต่ตอนตั้งค่า Prisma)
  • commit ด้วย git add -A && git commit -m "chore: init migration"
