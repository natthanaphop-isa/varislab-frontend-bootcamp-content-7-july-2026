@CurrentUser() และ GET /orders/me

เมื่อจบบทนี้ คุณจะสามารถ

  • สร้าง parameter decorator ของตัวเองด้วย createParamDecorator เพื่อดึงผู้ใช้ปัจจุบันออกมาใช้ใน handler
  • ออกแบบ endpoint ที่รู้ว่า "ของใคร" จาก token เท่านั้น จนไม่มีทางที่ client จะขอดูข้อมูลของคนอื่นได้
  • เปิดปุ่ม Authorize ใน Swagger UI แล้วทดสอบ endpoint ที่ต้องใช้ token ได้จากหน้าเอกสาร

บทนี้มี prompt สองอันในสองแชท อันแรกเปิด endpoint อันที่สองทำให้หน้าเอกสารใช้ทดสอบ endpoint นั้นได้ — ทั้งคู่สั้นกว่าบทที่แล้วมาก

request.user ใช้ได้ แต่ไม่ควรใช้ตรง ๆ

หลังผ่าน guard มาแล้ว payload ถูกแปะไว้ที่ request.user เรียบร้อย handler จึงอ่านได้ด้วย @Req() ซึ่งก็ทำงานได้จริง — แบบที่เห็นใน GET /auth/me ของบทที่แล้ว

ปัญหาของวิธีนั้นมีสองข้อเมื่อเริ่มมี endpoint หลายเส้นที่ต้องใช้ผู้ใช้ปัจจุบัน ข้อแรก handler ได้ object Request ทั้งก้อนมาทั้งที่ต้องการแค่ฟิลด์เดียว ซึ่งเปิดช่องให้ไปหยิบ header หรือ query จากใน handler ตามสะดวก จนเส้นแบ่งหน้าที่เลือนไป ข้อสองคือทุก handler ต้องรู้ว่า payload อยู่ที่ request.user — ถ้าวันหนึ่งย้ายไปอยู่ที่อื่น ต้องไล่แก้ทุกจุด

NestJS มีทางที่ตรงกว่า: createParamDecorator ให้เราประกาศ decorator ของตัวเองที่ทำหน้าที่ดึงค่าออกมาจาก context แล้วส่งเข้า parameter โดยตรง ผลคือ handler เขียนว่ามันต้องการอะไรไว้ในลายเซ็นของตัวเอง และความรู้เรื่อง "payload เก็บไว้ตรงไหน" ถูกรวบไว้ที่ไฟล์เดียว

ความเป็นเจ้าของต้องมาจาก token เท่านั้น

endpoint ที่คืน "ของฉัน" มีวิธีเขียนที่ผิดอยู่วิธีหนึ่งซึ่งดูสมเหตุสมผลมากจนเผลอทำกันบ่อย คือรับ userId เป็น query แล้วกรองตามนั้น

GET /orders/me?userId=1     ← ผิด
GET /orders/me              ← ถูก  (เลข id มาจาก token)

แบบแรกแปลว่าใครที่ login แล้วก็เปลี่ยนเลขเป็นอะไรก็ได้เพื่อดูคำสั่งซื้อของคนอื่น — ช่องโหว่ชนิดนี้เรียกว่า IDOR (insecure direct object reference) และเป็นหนึ่งในบั๊กด้านสิทธิ์ที่พบบ่อยที่สุดในระบบจริง มันไม่ได้เกิดจากการลืมใส่ guard เพราะ guard ทำงานถูกต้องทุกประการ ผู้ใช้ login จริง token ถูกต้องจริง แต่ระบบดันเชื่อข้อมูลที่ผู้ใช้พิมพ์มาแทนที่จะเชื่อข้อมูลที่ตัวเองเซ็นไว้

กฎง่าย ๆ คือ: อะไรที่เกี่ยวกับ "คุณเป็นใคร" ต้องอ่านจาก token เสมอ ห้ามรับจาก client แม้แต่ทางเดียว ในโค้ดของเราแปลว่า GET /orders/me ต้องไม่มี parameter ใด ๆ ที่เกี่ยวกับตัวตนเลย

POST /carts/add ยังรับ userId จาก body อยู่เหมือนเดิม และนั่นถูกต้องสำหรับสัญญาฉบับนั้น เพราะมันเป็น endpoint สาธารณะที่ออกแบบไว้ก่อนจะมีระบบผู้ใช้ — React app ที่เรียกมันก็ไม่มี token จะส่งอยู่แล้ว ความต่างคือ POST /carts/add ไม่เคยอ้างว่ารู้ว่าคุณเป็นใคร ส่วน /orders/me อ้าง จึงต้องพิสูจน์ให้ได้

Authorize ใน Swagger: ของแถมที่ตอนนี้ไม่ใช่ของแถมแล้ว

ตอนเพิ่ม Swagger เข้าโปรเจกต์ เราเคยบอกว่า .addBearerAuth() เป็นตัวอย่างของสิ่งที่ AI ชอบเติมให้โดยไม่ได้ขอ และควรถามตัวเองว่าต้องการจริงไหม ตอนนั้นคำตอบที่ซื่อสัตย์คือไม่ — ไม่มี endpoint ไหนต้องใช้ token สักเส้น ปุ่มที่กดแล้วไม่มีอะไรเปลี่ยนคือความรกบนหน้าจอ

ตอนนี้มีสองเส้นที่ต้องใช้ token แล้ว คำตอบจึงเปลี่ยน นี่คือความต่างระหว่าง "ของแถมที่ไม่ได้ขอ" กับ "ของที่ขอเพราะมีเหตุผลรองรับ" — ตัวโค้ดเหมือนกันทุกตัวอักษร ต่างกันที่ว่าตอบคำถามว่า "ทำไมต้องมี" ได้หรือเปล่า

Prompt แรก: เปิด GET /orders/me

commit งานก่อน แล้วเปิดแชทใหม่ใน Cursor โหมด Agent (git add -A && git commit -m "chore: before orders/me")

สร้าง endpoint GET /orders/me ที่คืนเฉพาะคำสั่งซื้อของผู้ใช้ที่ token ระบุ @docs/auth-spec.md @src/orders/orders.service.ts @src/orders/orders.module.ts ผลลัพธ์ที่ต้องได้: - GET /orders/me พร้อม token → 200 และเป็น array ของคำสั่งซื้อที่ userId ตรงกับ sub ใน token เท่านั้น เรียงจากใหม่ไปเก่า - ไม่มี token → 401 - เลข userId มาจาก token เท่านั้น — ต้องไม่มีทางส่ง userId เข้ามาทาง query, body หรือ path เพื่อดูคำสั่งซื้อของคนอื่นได้เลย - รูปทรงของคำสั่งซื้อแต่ละใบตรงกับ order receipt ใน docs/api-spec.md โดยใช้ mapper ตัวเดิมที่มีอยู่ ไม่เขียนรูปทรงขึ้นใหม่ - ผู้ใช้ที่ยังไม่เคยสั่งซื้อ → 200 พร้อม [] ไม่ใช่ 404 - สร้าง decorator ของตัวเองสำหรับดึงผู้ใช้ปัจจุบันจาก request มาใช้ใน handler แทนการรับ Request ทั้งก้อน แล้วเอาไปใช้กับ GET /auth/me ที่มีอยู่แล้วด้วย - POST /carts/add ไม่เปลี่ยนเลย ยังเป็น public และยังรับ userId จาก body เหมือนเดิม - npm run test:e2e ยังได้ Tests 11 passed (11) ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ - ห้ามแตะไฟล์ใน test/ - ห้ามแก้ prisma/schema.prisma — Order.userId ยังเป็น Int เปล่า ๆ ไม่มี relation ไปหา User - ห้ามแก้ POST /carts/add หรือ cart.mapper.ts - ห้ามใช้ any, as หรือ !

ตรวจโค้ดที่ AI สร้าง

  • orders.controller.ts ไม่มี @Public() ทั้งระดับ class และระดับ handler — ถ้ามี endpoint นี้จะเปิดโล่งและคืนคำสั่งซื้อโดยไม่ตรวจอะไรเลย
  • ลายเซ็นของ handler ไม่มี @Query(), @Param() หรือ @Body() ที่เกี่ยวกับตัวตนเลย — อ่านแล้วต้องเห็นได้ทันทีว่าไม่มีทางส่งเลขคนอื่นเข้ามา
  • where: { userId } ใช้ค่าที่มาจาก token ตรง ๆ ไม่ได้ผ่านตัวแปรที่รับมาจาก request ที่อื่น
  • decorator ตัวใหม่ประกาศ type ของค่าที่คืนไว้ชัด ไม่ใช่ any และ GET /auth/me ถูกแก้ให้ใช้ตัวนี้แทน @Req() ด้วย
  • ใช้ mapper ของคำสั่งซื้อตัวเดิม (toCartResponse) — grep -rn "discountedPrice" src/orders/ ต้องไม่เจอการคำนวณซ้ำที่ไหนใหม่
  • controller ใช้ import type กับ JwtPayload ไม่ใช่ import ธรรมดา — มันอยู่ในลายเซ็นของ method ที่มี decorator จึงเข้าเงื่อนไขของกติกาข้อนั้นใน .cursor/rules พอดี ถ้าผิด nest start จะพังด้วย TS1272
  • git diff src/orders/carts.controller.ts ว่างเปล่า และ git diff --stat test/ prisma/ ว่างเปล่า

AI มักพลาดตรงนี้: เพิ่ม @Query('userId') ให้ handler เพราะมันทำให้ทดสอบง่ายและ "ยืดหยุ่นกว่า" ซึ่งเปลี่ยน endpoint ส่วนตัวให้กลายเป็นช่องดูข้อมูลของทุกคนในระบบทันที อีกกรณีที่เจอคือ query คำสั่งซื้อทั้งหมดออกมาก่อนแล้วค่อย filter ใน JavaScript — ผลลัพธ์ถูกต้อง แต่ฐานข้อมูลต้องส่งคำสั่งซื้อของทุกคนข้ามเครือข่ายมาให้แอปทุกครั้ง และวันที่ข้อมูลเยอะขึ้นมันจะช้าลงเรื่อย ๆ โดยไม่มีใครสังเกต

โค้ดอ้างอิงของหัวข้อนี้ — เป็นหนึ่งในวิธีที่ถูก ของคุณไม่จำเป็นต้องเหมือนทุกบรรทัด ขอแค่ผ่านผลลัพธ์ที่ต้องได้:

// src/auth/current-user.decorator.ts
import { createParamDecorator, ExecutionContext } from '@nestjs/common';
import type { AuthenticatedRequest, JwtPayload } from './jwt-payload.interface.js';

export const CurrentUser = createParamDecorator(
  (_data: unknown, context: ExecutionContext): JwtPayload => {
    return context.switchToHttp().getRequest<AuthenticatedRequest>().user;
  },
);

พารามิเตอร์ตัวแรกชื่อ _data คือค่าที่ส่งเข้ามาตอนเรียก decorator เช่น @CurrentUser('email') เราไม่ได้ใช้มันในคอร์สนี้ จึงประกาศเป็น unknown แล้วขึ้นต้นชื่อด้วยขีดล่างเพื่อบอก linter ว่าตั้งใจไม่ใช้

// src/orders/orders.controller.ts
import { Controller, Get } from '@nestjs/common';
import { ApiOkResponse, ApiTags } from '@nestjs/swagger';
import { CurrentUser } from '../auth/current-user.decorator.js';
import type { JwtPayload } from '../auth/jwt-payload.interface.js';
import { CartResponseDto } from './dto/cart-response.dto.js';
import { OrdersService } from './orders.service.js';

@ApiTags('orders')
@Controller('orders')
export class OrdersController {
  constructor(private readonly ordersService: OrdersService) {}

  @Get('me')
  @ApiOkResponse({ type: [CartResponseDto] })
  findMine(@CurrentUser() user: JwtPayload) {
    return this.ordersService.findMine(user.sub);
  }
}

ลายเซ็นบรรทัดนี้คือหลักฐานทั้งหมดที่ต้องใช้ตรวจว่า endpoint นี้ปลอดภัยจาก IDOR: มันรับค่าเดียวคือผู้ใช้ปัจจุบัน และค่านั้นมาจาก token ไม่ได้มาจาก request ที่ client ควบคุมได้

// src/orders/orders.service.ts — เฉพาะส่วนที่เพิ่ม
  async findMine(userId: number): Promise<CartResponseDto[]> {
    const orders = await this.prisma.order.findMany({
      where: { userId },
      orderBy: { id: 'desc' },
      include: { items: { orderBy: { id: 'asc' } } },
    });

    return orders.map(toCartResponse);
  }

Prompt ที่สอง: เปิดปุ่ม Authorize ใน Swagger

commit งานของ prompt แรกไว้ก่อน (git add -A && git commit -m "feat: orders/me and current user decorator") แล้วเปิดแชทใหม่

เปิดปุ่ม Authorize ใน Swagger UI ให้ทดสอบ endpoint ที่ต้องใช้ token ได้ @src/main.ts @src/auth/auth.controller.ts @src/orders/orders.controller.ts ผลลัพธ์ที่ต้องได้: - Swagger UI ที่ /api มีปุ่ม Authorize — วาง access token ลงไปแล้วกด Try it out ที่ GET /auth/me และ GET /orders/me ได้ 200 - /api-json มี components.securitySchemes แบบ type: http, scheme: bearer, bearerFormat: JWT - ณ ตอนนี้มีเฉพาะ /auth/me กับ /orders/me เท่านั้นที่มี security กำกับไว้ ส่วนหกเส้นที่เป็น public ต้องไม่มี - endpoint สาธารณะยังกด Try it out ได้โดยไม่ต้อง Authorize - npm run test:e2e ยังได้ Tests 11 passed (11) ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ (@nestjs/swagger ติดตั้งแล้ว) - ห้ามแก้ logic ของ endpoint ไหนเลย เพิ่มได้แค่การตั้งค่า Swagger กับ decorator - ห้ามใส่ addApiKey, addOAuth2, addTag หรือ scheme อื่นที่ไม่ได้ขอ - ห้ามแตะไฟล์ใน test/

ตรวจโค้ดที่ AI สร้าง

  • .addBearerAuth() ถูกเพิ่มต่อจาก .setVersion() และก่อน .build() — ไม่มี .addTag() หรือ scheme อื่นแถมมาด้วย
  • @ApiBearerAuth() ติดเฉพาะสองเส้นที่ต้องใช้ token ไม่ได้เหมาเอาไปติดที่ @Controller ของ AuthController ซึ่งจะทำให้ signup กับ login ขึ้นรูปกุญแจทั้งที่ไม่ต้องใช้
  • ชื่อ scheme ที่ใช้ตอน .addBearerAuth() กับตอน @ApiBearerAuth() ตรงกัน (หรือใช้ค่าปริยายทั้งคู่) — ถ้าไม่ตรง ปุ่มจะกดได้แต่ token จะไม่ถูกแนบไปจริง
  • src/main.ts ไม่มีอะไรเปลี่ยนนอกจากบรรทัดของ Swagger

AI มักพลาดตรงนี้: ตั้งชื่อ scheme ตอนประกาศเป็น 'JWT-auth' แล้วใช้ @ApiBearerAuth() เปล่า ๆ ที่ handler ซึ่งอ้างถึงชื่อปริยาย 'bearer' ผลคือหน้า Swagger มีปุ่มให้กด กรอก token ได้ แต่เวลากด Try it out จริง header ไม่ถูกแนบไป แล้วได้ 401 กลับมาโดยไม่มีอะไรบอกว่าเพราะอะไร

โค้ดอ้างอิงของหัวข้อนี้ — เป็นหนึ่งในวิธีที่ถูก ของคุณไม่จำเป็นต้องเหมือนทุกบรรทัด ขอแค่ผ่านผลลัพธ์ที่ต้องได้:

// src/main.ts — เฉพาะส่วนที่เปลี่ยน
  const config = new DocumentBuilder()

    .setVersion('1.0')
    .addBearerAuth()
    .build();

ถ้าอธิบายบรรทัดไหนไม่ได้ ยังไม่ผ่านบทนี้ — กลับไปอ่านส่วนแนวคิดก่อน

ผลลัพธ์ที่คาดหวัง

เปิด http://localhost:3000/api จะเห็นปุ่ม Authorize มุมขวาบน กดแล้ววาง access token ลงไป (เฉพาะตัว token ไม่ต้องพิมพ์คำว่า Bearer นำหน้า Swagger ใส่ให้เอง) จากนั้นสองเส้นที่มีรูปกุญแจจะกด Try it out ได้

ใน /api-json จะมีก้อนนี้เพิ่มเข้ามา

"securitySchemes": {
  "bearer": { "scheme": "bearer", "bearerFormat": "JWT", "type": "http" }
}

และเฉพาะสองเส้นที่ต้องใช้ token เท่านั้นที่มีบรรทัด "security" กำกับ — ส่วน /products/categories และเพื่อน ๆ ต้องไม่มี

ตรวจว่าใช้งานได้จริง

  • สั่งซื้อด้วยเลขผู้ใช้ของคุณเองหนึ่งใบ (ใช้เลข sub ที่ถอดจาก token ได้ในบทที่แล้ว) 
    curl -s -o /dev/null -w '%{http_code}\n' -X POST http://localhost:3000/carts/add \
  -H 'Content-Type: application/json' \
  -d '{"userId":1,"products":[{"id":1,"quantity":2}],"address":{"address":"1 Main","email":"student@example.com","phone":"0812345678"}}'
  • เรียก /orders/me แล้วตรวจสามอย่างพร้อมกัน: จำนวนใบ, ทุกใบเป็นของเรา, และใบล่าสุดคือใบที่เพิ่งสั่ง 
    curl -s -H "Authorization: Bearer $TOKEN" http://localhost:3000/orders/me \
  | node -e "let d='';process.stdin.on('data',c=>d+=c).on('end',()=>{const a=JSON.parse(d);console.log('count =',a.length);console.log('all mine =',a.every(o=>o.userId===1));console.log('latest id =',a[0].id)})"
  • เทียบจำนวนกับความจริงในฐานข้อมูล — ตัวเลข count ข้างบนต้องตรงกับแถวของ userId นั้น 
    docker compose exec db psql -U postgres -d ecommerce \
  -c 'SELECT "userId", count(*) FROM "Order" GROUP BY "userId" ORDER BY "userId";'
    ถ้ามี userId อื่นอยู่ในตารางด้วย แต่ /orders/me คืนมาเฉพาะของเรา นั่นคือหลักฐานว่าการกรองทำงานจริง
  • ไม่มี token → 401 
    curl -s -o /dev/null -w '%{http_code}\n' http://localhost:3000/orders/me
  • ลองแอบส่ง userId ของคนอื่นเข้าไป — ต้องไม่มีผลใด ๆ ผลลัพธ์ต้องเท่าเดิมทุกประการ 
    curl -s -H "Authorization: Bearer $TOKEN" 'http://localhost:3000/orders/me?userId=2' \
  | node -e "let d='';process.stdin.on('data',c=>d+=c).on('end',()=>console.log(JSON.parse(d).every(o=>o.userId===1)))"
    ต้องได้ true — query string ถูกเพิกเฉยเพราะ handler ไม่ได้อ่านมันเลย
  • เอกสารมี security scheme และเฉพาะเส้นที่ควรมีเท่านั้นที่ถูกกำกับ 
    curl -s http://localhost:3000/api-json | grep -c securitySchemes
