NestJS E-commerce API Workshop

ออกแบบสัญญาของ auth และ Model ของผู้ใช้

เมื่อจบบทนี้ คุณจะสามารถ

  • ออกแบบสัญญาของ endpoint ชุดใหม่ขึ้นมาเองทั้งชุด ในสถานการณ์ที่ไม่มี client ตัวไหนมาบังคับรูปทรงให้
  • ออกแบบตาราง User ที่เก็บรหัสผ่านแบบ hash และบังคับความไม่ซ้ำของอีเมลที่ระดับฐานข้อมูล ไม่ใช่ที่ระดับโค้ด
  • อธิบายได้ว่าทำไม Order.userId ถึงยังไม่ผูก foreign key ไปที่ User ทั้งที่ตอนนี้มีตาราง User แล้ว

เจ็ดบทจากนี้เป็นโบนัส — React app ที่เราสลับมาใช้ API ตัวนี้ไปแล้วไม่ต้องการ auth เลย และจะทำงานได้เหมือนเดิมทุกประการตลอดทั้งโบนัส ถ้าคุณหยุดอ่านตรงนี้แล้วข้ามไปบทสรุป งานที่ทำมาทั้งหมดก็ยังสมบูรณ์ สิ่งที่เจ็ดบทนี้เพิ่มให้คือชั้นของผู้ใช้: สมัคร เข้าสู่ระบบ ถือ token แล้วเรียก endpoint ที่คนอื่นเรียกไม่ได้

สัญญาที่ไม่มีใครบังคับ เราจึงต้องออกแบบเอง

ตลอดคอร์สที่ผ่านมา docs/api-spec.md ทำหน้าที่เดียว: บันทึกสัญญาที่ React app พึ่งพาอยู่แล้ว ทุกหัวข้อในไฟล์นั้นจึงมีวงเล็บกำกับว่าถอดมาจากไฟล์ไหนของ client — (from src/features/products/types.ts) และเพื่อน ๆ นั่นคือเหตุผลที่เราแก้มันไม่ได้: มีคนใช้อยู่ปลายทาง

auth ไม่มีเงื่อนไขนั้นเลย ไม่มีหน้าจอ login ไม่มี client ตัวไหนรอเรียก POST /auth/signup เราจึงไม่ได้ถอดสัญญามาจากใคร แต่ออกแบบมันขึ้นมาเอง ซึ่งเป็นงานคนละชนิดและต้องอยู่คนละไฟล์: docs/auth-spec.md

การแยกสองไฟล์นี้ไม่ใช่เรื่องความเป็นระเบียบ มันคือการแยก "สิ่งที่เปลี่ยนไม่ได้" ออกจาก "สิ่งที่เรายังตัดสินใจได้" ซึ่งจะมีผลตรง ๆ ในบทที่เราใส่ guard: e2e test สิบเอ็ดข้อที่มีอยู่คุ้มครองสัญญาที่คนอื่นพึ่งพา ถ้าโบนัสนี้ทำให้ข้อไหนแดง นั่นไม่ใช่ trade-off ที่ยอมรับได้ แต่เป็นการทำของพังโดยตรง

ไฟล์นี้เขียนด้วยมือ ไม่ใช้ Cursor เขียนให้ ด้วยเหตุผลเดียวกับที่ docs/api-spec.md เขียนเอง: สัญญาคือการตัดสินใจ ไม่ใช่โค้ด ถ้า AI ตัดสินใจแทนคุณว่า endpoint ไหนตอบอะไร คุณจะไม่มีอะไรเอาไว้ตรวจงานของมันเลย ตอนต้นคอร์สเราบอกว่ามีห้าขั้นที่พิมพ์เอง — โบนัสนี้เพิ่มขั้นที่หก ด้วยเหตุผลข้อแรกของทั้งห้าข้อนั้น

เจ็ด endpoint ที่โบนัสนี้จะสร้าง

เขียนสัญญาให้ครบทั้งเจ็ดตั้งแต่ตอนนี้ แม้ห้าเส้นสุดท้ายจะยังไม่ได้สร้างไปอีกหลายบท — เหมือนที่ตอนออกแบบสัญญาของสินค้า เราเขียนครบทุก endpoint ก่อนจะลงมือสร้างตัวแรก การเห็นปลายทางทั้งหมดพร้อมกันคือสิ่งที่ทำให้ตัดสินใจเรื่องรูปทรงได้ถูกตั้งแต่ต้น

Method + Pathต้องมี token?ตอบอะไร
POST /auth/signupไม่201 + ข้อมูลผู้ใช้ (ไม่มีรหัสผ่าน)
POST /auth/loginไม่200 + accessToken และ refreshToken
POST /auth/refreshไม่ (ใช้ refresh token ใน body)200 + token คู่ใหม่
POST /auth/logoutใช่204 ไม่มี body
GET /auth/meใช่200 + ข้อมูลผู้ใช้จาก token
GET /orders/meใช่200 + คำสั่งซื้อของผู้ใช้คนนั้น
GET /admin/ordersใช่ และต้องเป็น ADMIN200 + คำสั่งซื้อทุกใบในระบบ

สังเกตว่า POST /auth/refresh อยู่ในกลุ่ม "ไม่ต้องมี token" ทั้งที่ชื่อฟังดูเหมือนต้องมี — เหตุผลอยู่ในบทที่เราทำ refresh: หน้าที่ของมันคือทำงานตอน access token หมดอายุไปแล้ว ถ้ามันเองต้องใช้ access token ที่ยังไม่หมดอายุ มันก็ไม่มีประโยชน์อะไรเลย

User เก็บอะไร และเก็บอย่างไร

สามเรื่องที่ตัดสินใจตอนนี้แล้วจะส่งผลไปอีกหกบท

ชื่อฟิลด์ของรหัสผ่านต้องบอกความจริง — เราเก็บ passwordHash ไม่ใช่ password เพราะสิ่งที่อยู่ในนั้นไม่ใช่รหัสผ่าน มันคือผลลัพธ์ของฟังก์ชันทางเดียวที่ย้อนกลับไม่ได้ ชื่อที่ตรงกับความจริงทำให้วันที่มีคนเผลอเขียน user.password ในโค้ด มันจะ compile ไม่ผ่านทันทีแทนที่จะเงียบ ๆ ส่งรหัสผ่านออกไป

ความไม่ซ้ำของอีเมลต้องอยู่ที่ฐานข้อมูล — ไม่ใช่แค่ findUnique เช็คก่อน insert เพราะระหว่างสองคำสั่งนั้นมีช่องว่างที่ request อีกอันแทรกเข้ามาสมัครอีเมลเดียวกันได้พอดี (race condition) @unique ใน Prisma กลายเป็น CREATE UNIQUE INDEX จริงใน SQL ซึ่งฐานข้อมูลบังคับให้เสมอไม่ว่าจะมีกี่ request พร้อมกัน

บทบาทเป็น enum ไม่ใช่ string — role String รับค่าอะไรก็ได้รวมถึง "admni" ที่พิมพ์ผิด ส่วน enum Role กลายเป็น type จริงใน PostgreSQL ที่ปฏิเสธค่านอกรายการตั้งแต่ระดับฐานข้อมูล และฝั่ง TypeScript ก็ได้ union type มาให้ตรวจตอน compile ด้วย นี่เป็น enum ตัวแรกของคอร์สนี้

ทำไม Order.userId ยังไม่ผูกกับ User

พอมีตาราง User แล้ว สัญชาตญาณแรกคือเติม relation ให้ Order.userId ชี้ไปหามันเสีย — และนั่นคือสิ่งที่บทนี้ห้ามทำ

เหตุผลอยู่ที่สัญญาเดิม POST /carts/add รับ userId มาจาก body ที่ client ส่ง และ React app ส่งเลข 1 คงที่มาเสมอเพราะมันไม่มีระบบ login ถ้าเราเติม foreign key ตอนนี้ ฐานข้อมูลจะปฏิเสธทุกคำสั่งซื้อที่ userId ไม่มีแถวคู่กันในตาราง User — แปลว่า React app ที่เราเพิ่งพิสูจน์ว่าใช้งานได้ครบวงจรจะพังทันที และ e2e test ข้อที่สิบก็พังตาม

นี่คือรูปร่างของงานจริงที่เจอบ่อยกว่าที่คิด: สัญญาถูก freeze ไปแล้วเพราะมีคนใช้อยู่ เราจึงเพิ่มความสามารถรอบ ๆ มันแทนที่จะแก้ตัวมันเอง คำสั่งซื้อที่ผูกกับผู้ใช้จริงจะทำได้ในวันที่ client ยอมเปลี่ยน ไม่ใช่วันนี้ ส่วน GET /orders/me ที่จะมาในบทถัด ๆ ไปนั้นทำงานได้โดยไม่ต้องมี foreign key อยู่แล้ว เพราะมันแค่กรอง userId ให้ตรงกับเลขใน token

เป้าหมายของบทนี้

รายการด้านล่างคือไฟล์ที่เปลี่ยนในโค้ดอ้างอิงของคอร์ส — ใช้เป็นแผนที่ตอนเทียบงาน ไม่ใช่ข้อบังคับ Cursor ของคุณอาจวางไฟล์หรือตั้งชื่อต่างไปได้ ขอแค่ผ่านผลลัพธ์ที่ต้องได้ใน prompt

เขียน docs/auth-spec.md ด้วยมือ

สร้างไฟล์ docs/auth-spec.md แล้วพิมพ์สัญญาลงไปเอง ไม่ต้องเปิดแชท Cursor สำหรับขั้นนี้ ข้างล่างคือฉบับของโค้ดอ้างอิง — ของคุณไม่จำเป็นต้องเหมือนทุกบรรทัด แต่ทุกอย่างที่คุณเขียนไว้จะกลายเป็น ผลลัพธ์ที่ต้องได้ ของ prompt ในหกบทถัดไป เขียนสิ่งที่คุณตั้งใจจะตรวจจริง

# Auth Spec — สัญญาที่เราออกแบบเอง (ไม่มี client ตัวไหนบังคับ)

ต่างจาก api-spec.md ตรงที่ไฟล์นั้นถอดมาจากโค้ดของ React app
ส่วนไฟล์นี้เราออกแบบเองทั้งหมด เพราะยังไม่มี client ตัวไหนใช้ auth

## Endpoints

| Method | Path           | ต้องมี token | Body ที่รับ                    |
| ------ | -------------- | ------------ | ------------------------------ |
| POST   | /auth/signup   | ไม่           | { email, password, name }      |
| POST   | /auth/login    | ไม่           | { email, password }            |
| POST   | /auth/refresh  | ไม่           | { refreshToken }               |
| POST   | /auth/logout   | ใช่          | (ไม่มี)                         |
| GET    | /auth/me       | ใช่          | (ไม่มี)                         |
| GET    | /orders/me     | ใช่          | (ไม่มี)                         |
| GET    | /admin/orders  | ใช่ + ADMIN  | (ไม่มี)                         |

## User

ใช้เป็น response ของ POST /auth/signup (201) และ GET /auth/me (200)

interface User {
  id: number;
  email: string;
  name: string;
  role: "USER" | "ADMIN";
  createdAt: string;   // ISO 8601
}

ห้ามมี password หรือ passwordHash ใน response ของ endpoint ใดทั้งสิ้น

## Tokens

ใช้เป็น response ของ POST /auth/login (200) และ POST /auth/refresh (200)

interface TokenPair {
  accessToken: string;    // JWT อายุสั้น payload = { sub, email, role }
  refreshToken: string;   // JWT อายุยาว เซ็นด้วย secret คนละตัว
}

- access token อายุ 900 วินาที (15 นาที)
- refresh token อายุ 604800 วินาที (7 วัน) และใช้ได้ครั้งเดียว
  พอ refresh สำเร็จ ใบเดิมต้องใช้ไม่ได้อีก

## กฎของรหัสผ่าน

- อย่างน้อย 8 ตัวอักษร
- เก็บแบบ hash เท่านั้น ห้ามเก็บรหัสผ่านดิบในฐานข้อมูลหรือใน log

## Errors

- ไม่มี token, token ผิด หรือ token หมดอายุ → 401
  { "message": "Unauthorized", "error": "Unauthorized", "statusCode": 401 }
- token ถูกต้องแต่ role ไม่พอ → 403
  { "message": "Forbidden resource", "error": "Forbidden", "statusCode": 403 }
- อีเมลหรือรหัสผ่านผิดตอน login → 401 message "Invalid credentials"
  ทั้งสองกรณีต้องได้ข้อความเดียวกัน ห้ามบอกว่าอีเมลนั้นมีอยู่จริงหรือไม่
- สมัครด้วยอีเมลที่มีอยู่แล้ว → 409 message "Email already registered"
- body ผิดรูป → 400 message เป็น array ตามรูปแบบเดิมของ ValidationPipe

บรรทัดที่ทำงานหนักที่สุดในไฟล์นี้คือ "ทั้งสองกรณีต้องได้ข้อความเดียวกัน" ถ้า login ตอบ "ไม่พบอีเมลนี้" กับ "รหัสผ่านไม่ถูกต้อง" แยกกัน ใครก็ตามที่ยิง API ได้จะไล่เดาได้ว่าอีเมลไหนสมัครไว้แล้วบ้าง โดยไม่ต้องรู้รหัสผ่านสักตัว — ช่องโหว่ชนิดนี้เรียกว่า user enumeration และมันเกิดจากความพยายามจะช่วยผู้ใช้ให้ข้อความ error ที่ "เป็นประโยชน์" มากเกินไป

สั่ง Cursor เพิ่ม model User แล้วรัน migration ด้วยมือ

commit งานก่อน แล้วเปิดแชทใหม่ใน Cursor โหมด Agent (git add -A && git commit -m "docs: auth spec") — และจำกติกาของคอร์สไว้: AI พิมพ์แทนคุณได้ แต่คุณต้องอธิบายทุกบรรทัดได้

เพิ่ม Prisma model ชื่อ User และ enum ชื่อ Role ตาม docs/auth-spec.md @prisma/schema.prisma @docs/auth-spec.md ผลลัพธ์ที่ต้องได้: - หลังผมรัน npx prisma migrate dev --name add-users ฐานข้อมูลมีตารางใหม่ User (\dt ได้ 7 แถว จากเดิม 6) โดย migration ไม่ถามยืนยันและไม่ทำข้อมูลเดิมหาย - User เก็บ: อีเมลที่ซ้ำกันไม่ได้, รหัสผ่านที่ hash แล้ว (ชื่อฟิลด์ต้องบอกชัดว่าเป็น hash ไม่ใช่รหัสผ่านดิบ), ชื่อที่ใช้แสดง, บทบาท และเวลาที่สมัคร - บทบาทเป็น enum ของ Prisma สองค่า USER กับ ADMIN ค่าปริยายเป็น USER — ใน migration.sql ต้องเห็น CREATE TYPE "Role" AS ENUM ('USER', 'ADMIN'); - migration.sql มี CREATE UNIQUE INDEX "User_email_key" ON "User"("email"); — ความซ้ำของอีเมลถูกกันที่ฐานข้อมูล ไม่ใช่แค่ที่โค้ด - Order.userId ยังเป็น Int เปล่า ๆ ไม่มี relation ไปหา User — model Order ต้องไม่มีบรรทัดไหนเปลี่ยน และ migration.sql ต้องไม่มี ALTER TABLE "Order" เลย - npm run db:seed ยังได้ Seeded 24 categories, 208 products, 624 reviews เท่าเดิม - model Category, Product, Review, Order, OrderItem ไม่เปลี่ยน และ npm run build ผ่าน ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ - ห้ามรัน migrate หรือ generate ให้ผมรันเอง - ห้ามแก้ prisma/seed.ts และห้ามแตะไฟล์ใน src/ หรือ test/ - ยังไม่ต้องสร้าง DTO, service, controller หรือ module ของ auth

บรรทัดที่ห้ามแก้ prisma/seed.ts ไม่ใช่ของแถม: ถ้า AI เติม tx.user.deleteMany() เข้าไปในลำดับการล้างข้อมูลตามสัญชาตญาณ บัญชีที่คุณสมัครไว้จะหายทุกครั้งที่ seed ใหม่ แล้วบทที่ทำ refresh token กับ role จะพังด้วยอาการที่ไม่มีอะไรชี้กลับมาที่ seed เลย

อ่าน schema ที่ AI เขียนให้จบก่อน แล้วจึงรันสองคำสั่งนี้ด้วยมือ

npx prisma migrate dev --name add-users npx prisma generate

เหมือนทุกครั้งที่ schema เปลี่ยน: prisma migrate dev ของ Prisma 7 ไม่ได้ generate client ให้ ถ้าข้ามคำสั่งที่สอง tx.user จะยังไม่มีใน Prisma Client และบทถัดไปจะพังด้วย type error ส่วน npm run db:seed รอบนี้ไม่ต้องรันก็ได้ เพราะเราไม่ได้แตะ seed — แต่ถ้ารันก็ต้องได้ตัวเลขเดิมทุกตัว

ตรวจโค้ดที่ AI สร้าง

  • ฟิลด์รหัสผ่านชื่อ passwordHash (หรือชื่ออื่นที่บอกชัดว่าเป็น hash) — ไม่ใช่ password
  • email มี @unique และ migration.sql มี CREATE UNIQUE INDEX จริง ไม่ใช่แค่ @@index ธรรมดาที่ยอมให้ซ้ำได้
  • role เป็น Role ไม่ใช่ String และมี @default(USER) — ผู้ใช้ใหม่ต้องไม่ได้สิทธิ์ admin มาฟรี ๆ
  • model Order ไม่มีบรรทัดไหนเปลี่ยน และไม่มี users User[] หรือ relation ใด ๆ งอกขึ้นมา (git diff prisma/schema.prisma ต้องเห็นแค่บรรทัดที่เพิ่มท้ายไฟล์)
  • prisma/seed.ts ไม่ถูกแตะ — git status ต้องไม่มีชื่อไฟล์นี้
  • ไม่มี @updatedAt ใน User ถ้าไม่ได้ขอ และไม่มีฟิลด์แถมอย่าง isActive หรือ lastLoginAt ที่สัญญาไม่ได้พูดถึง

AI มักพลาดตรงนี้: เติม relation ระหว่าง User กับ Order ให้เองเพราะ "มันควรจะผูกกัน" — สัญชาตญาณนี้ถูกในโปรเจกต์ที่เริ่มจากศูนย์ แต่ผิดที่นี่ และจะทำให้ POST /carts/add พังทันทีที่มี userId ที่ไม่มีแถวคู่กัน อีกกรณีคือประกาศ role String @default("USER") ซึ่ง compile ผ่านและดูเหมือนทำงานได้ แต่ฐานข้อมูลจะยอมรับค่าอะไรก็ได้ที่พิมพ์เข้ามา

โค้ดอ้างอิงของบทนี้ — เป็นหนึ่งในวิธีที่ถูก ของคุณไม่จำเป็นต้องเหมือนทุกบรรทัด ขอแค่ผ่านผลลัพธ์ที่ต้องได้:

// prisma/schema.prisma — ต่อท้ายไฟล์ (model เดิมทั้งหมดไม่เปลี่ยน)
enum Role {
  USER
  ADMIN
}

model User {
  id           Int      @id @default(autoincrement())
  email        String   @unique
  passwordHash String
  name         String
  role         Role     @default(USER)
  createdAt    DateTime @default(now())
}

ถ้าอธิบายบรรทัดไหนไม่ได้ ยังไม่ผ่านบทนี้ — กลับไปอ่านส่วนแนวคิดก่อน

ผลลัพธ์ที่คาดหวัง

npx prisma migrate dev --name add-users สร้าง migration ใหม่และ apply ให้เลยโดยไม่ถามยืนยัน เพราะการเพิ่มตารางใหม่ไม่ทำข้อมูลเดิมหาย

เปิด prisma/migrations/…_add_users/migration.sql แล้วอ่านให้ครบ นี่คือหลักฐานสามอย่างพร้อมกัน: enum กลายเป็น type จริงของ PostgreSQL, อีเมลถูกกันซ้ำด้วย unique index และไม่มีบรรทัดไหนแตะตาราง Order

-- CreateEnum
CREATE TYPE "Role" AS ENUM ('USER', 'ADMIN');

-- CreateTable
CREATE TABLE "User" (
    "id" SERIAL NOT NULL,
    "email" TEXT NOT NULL,
    "passwordHash" TEXT NOT NULL,
    "name" TEXT NOT NULL,
    "role" "Role" NOT NULL DEFAULT 'USER',
    "createdAt" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT "User_pkey" PRIMARY KEY ("id")
);

-- CreateIndex
CREATE UNIQUE INDEX "User_email_key" ON "User"("email");

ไฟล์นี้จบแค่นี้ — ถ้าของคุณมี ALTER TABLE "Order" ต่อท้าย แปลว่า AI เติม relation ให้โดยไม่ได้ขอ ให้ย้อน migration ทิ้ง แก้ schema แล้วสั่งใหม่

ตรวจว่าใช้งานได้จริง

  • มีตารางใหม่หนึ่งตัว รวมเป็น 7 แถว (ตอนทำคำสั่งซื้อเราเห็น 6) 
    docker compose exec db psql -U postgres -d ecommerce -c '\dt'
  • คอลัมน์ role มีชนิดเป็น "Role" และมีค่าปริยาย ส่วน email มี unique index 
    docker compose exec db psql -U postgres -d ecommerce -c '\d "User"'
    ท้ายผลลัพธ์ต้องเห็นสองบรรทัดนี้ 
     role         | "Role"       | not null default 'USER'::"Role"
Indexes:
    "User_email_key" UNIQUE, btree (email)
  • enum มีสองค่าจริงในฐานข้อมูล ไม่ใช่แค่ในไฟล์ schema (ส่วนการพิสูจน์ว่ามันปฏิเสธอีเมลซ้ำจริง จะทำในบทถัดไปตอนสมัครซ้ำ — อย่าเพิ่ง INSERT เองตอนนี้ เพราะจะกิน id ของตารางไป แล้วเลขผู้ใช้ในบทถัด ๆ ไปจะไม่ตรงกับตัวอย่าง) 
    docker compose exec db psql -U postgres -d ecommerce -c '\dT+ "Role"'
  • git diff --stat เห็นแค่ prisma/schema.prisma กับไฟล์ migration ที่สร้างใหม่ — ไม่มี prisma/seed.ts และไม่มีอะไรใน src/ หรือ test/
  • npm run build ผ่าน และ npm run test:e2e ยังได้ Tests 11 passed (11) เท่าเดิม — บทนี้ไม่ได้แตะ endpoint ไหนเลย
  • commit ผลงานของบทนี้: git add -A && git commit -m "feat: user model and role enum" (commit ไฟล์ migration ไปด้วย)
