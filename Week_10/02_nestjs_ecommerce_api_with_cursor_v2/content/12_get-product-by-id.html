GET /products/:id

เมื่อจบบทนี้ คุณจะสามารถ

  • รับ route parameter ด้วย @Param('id', ParseIntPipe) แล้วส่งต่อเป็น number ให้ service
  • อธิบายว่าทำไม @Get('categories') ต้องประกาศไว้ก่อน @Get(':id') เสมอ
  • พิสูจน์ว่า response ของสินค้าชิ้นที่ 1 ตรงกับ docs/api-spec.md ทุกคีย์ และข้อความใน NotFoundException ตรงตัวอักษรต่ออักษรกับที่เราออกแบบไว้
  • ย้าย checklist ของบทนี้ลงไปอยู่ใน e2e test ที่รันด้วย npm run test:e2e — คำสั่งเดียวที่ตัดสินถูก/ผิดได้เองและคืน exit code ให้ทั้งคุณและ AI ใช้ตรวจซ้ำได้

บทนี้คือบทที่ mapper ได้ทำงานจริง

ขั้นก่อนหน้าเขียน toProductResponse ไว้แต่ยังไม่มีใครเรียก บทนี้เราต่อสายให้ครบ: controller รับ id → service query สินค้าพร้อม relation → ส่งแถวเข้า mapper → คืน JSON ที่ตรงกับ section Product ใน docs/api-spec.md

รูปแบบการรับ parameter เป็นแบบเดียวกับ NestJS Fundamentals ตอน route parameters และการโยน error เป็นแบบเดียวกับตอนที่ว่าด้วยข้อความ error ที่อ่านรู้เรื่อง ต่างกันที่คราวนี้ข้อความไม่ใช่เรื่องรสนิยม — มันคือส่วนหนึ่งของสัญญา

ข้อความ 404 คือสัญญา ไม่ใช่ข้อความประกอบ

เปิด docs/api-spec.md ดู section Errors — เราออกแบบให้ product ที่ไม่มีอยู่ตอบ status 404 พร้อม body

{ "message": "Product 9999 not found" }

React app ที่เราจะต่อในตอนท้ายของ workshop อ่าน data.message มาโชว์ให้ผู้ใช้เห็นตรง ๆ ผ่าน ApiError ของมัน ข้อความจึงต้องตรงตามที่เราออกแบบไว้ทุกตัวอักษร ถ้าเขียนเป็น Product #9999 not found แบบที่เคยทำในคอร์ส NestJS Fundamentals หน้าเว็บก็ยังไม่พัง (เพราะ client อ่านแค่ field message ไม่สนใจเนื้อหา) แต่ผิดสัญญาที่เราเขียนไว้ใน docs/api-spec.md และ test ตรวจสัญญาที่เราจะเขียนท้ายบทนี้จะจับได้ทันที

throw new NotFoundException(`Product ${id} not found`);

include และเหตุผลที่ต้องสั่ง orderBy ให้ reviews

แถว Product เปล่า ๆ ไม่มี category และไม่มี reviews ติดมา เราจึงต้องสั่ง include (ทบทวน NestJS Fundamentals ตอนดึง model พร้อม relation)

include: { category: true, reviews: { orderBy: { id: 'asc' } } }

ทำไมต้องมี orderBy ให้ reviews ด้วย? เพราะ array ที่ลำดับไม่ตรงกันจะทำให้การตรวจสัญญาในบทถัด ๆ ไปไม่ผ่าน และ Postgres ไม่รับประกันลำดับของแถวที่คืนมาถ้าไม่มี ORDER BY — มันจะเรียงตามที่สะดวกที่สุดในแผนการ query นั้น ๆ ซึ่งอาจเปลี่ยนเมื่อข้อมูลโตขึ้นหรือมี index ใหม่ seed script ใส่ review ของสินค้าแต่ละชิ้นตามลำดับที่เขียนไว้ในสคริปต์ ดังนั้น id น้อยไปมากคือลำดับเดียวกับที่ seed ใส่ไว้

ลำดับการประกาศ route คือลำดับที่ Nest ลองจับ

Nest ลงทะเบียน handler ตามลำดับที่ประกาศไว้ใน class และ router จะจับ pattern แรกที่ตรง ถ้าเราเผลอวาง @Get(':id') ไว้ก่อน

GET /products/categories
  → ตรงกับ pattern /products/:id  (id = "categories")
  → ParseIntPipe แปลง "categories" ไม่ได้
  → 400 Bad Request

endpoint หมวดสินค้าที่เคยทำงานอยู่จะตายเงียบ ๆ ทั้งที่เราไม่ได้แตะโค้ดของมันเลย กฎง่าย ๆ คือ route ที่เป็นคำตายตัวต้องมาก่อน route ที่มี parameter เสมอ ดังนั้นใน ProductsController เราวาง findOne เป็น handler สุดท้ายของ class ตั้งแต่วันนี้ แล้ว endpoint ที่เพิ่มทีหลังจะแทรก handler ใหม่ไว้ก่อนมันทุกครั้ง

ทำไม id ที่ไม่ใช่ตัวเลขได้ 400 ไม่ใช่ 404

ถ้ายิง GET /products/abc เราตอบ 400 พร้อมข้อความ Validation failed (numeric string is expected) เพราะ ParseIntPipe ดักไว้ก่อนที่ handler จะทำงาน — เป็นพฤติกรรมมาตรฐานของ Nest ไม่ต้องเขียนโค้ดเพิ่ม

เราเลือกที่จะปล่อยให้เป็น 400 เพราะ React app ไม่เคยยิง id ที่ไม่ใช่ตัวเลข (มันได้ id มาจาก list ที่ API ตอบไป) และ 400 เป็นคำตอบที่ตรงความจริงกว่า: request นั้นผิดรูป ไม่ใช่ resource ไม่มีอยู่ พฤติกรรมนี้จะถูกตรวจซ้ำทุกครั้งด้วย e2e test ที่เราเขียนท้ายบทนี้

เป้าหมายของบทนี้

ในโค้ดอ้างอิงคือการเพิ่ม handler ใน controller กับ method ใน service เดิมของ src/products/ — Cursor เลือกวิธีเองได้ โดยต้องได้ผลลัพธ์นี้

  • GET /products/:id ตอบสินค้าหนึ่งชิ้นครบ 22 คีย์ผ่าน mapper ที่มีอยู่แล้ว
  • id ที่ไม่มีอยู่ → 404 Product 9999 not found ตรงตัวอักษร / id ที่ไม่ใช่ตัวเลข → 400
  • GET /products/categories ยังทำงานเหมือนเดิม

บทนี้ไม่แตะ mapper และ DTO ที่มีอยู่แล้วเลย

สั่ง Cursor ต่อ endpoint สินค้าหนึ่งชิ้น

commit งานก่อน แล้วเปิดแชทใหม่ใน Cursor โหมด Agent (git add -A && git commit -m "chore: before product by id") จากนั้นส่ง prompt นี้

เพิ่ม endpoint GET /products/:id ที่ตอบสินค้าหนึ่งชิ้นตามรูปทรงใน docs/api-spec.md และ 404 ด้วยข้อความที่เราออกแบบไว้ @<controller และ service ของ products ที่คุณมีอยู่แล้ว> — โค้ดอ้างอิงคือ src/products/products.controller.ts กับ src/products/products.service.ts ผลลัพธ์ที่ต้องได้: - GET /products/1 ตอบ 200 เป็นสินค้าครบ 22 คีย์ตาม section Product ใน docs/api-spec.md ผ่าน mapper ที่มีอยู่แล้ว (title "Velvet Matte Lipstick", price 9.99, discountPercentage 10.48, brand "Lumina") - reviews ของสินค้าเรียงตาม id ของ review (ลำดับที่ seed ใส่ไว้) และคงที่ทุกครั้งที่ยิง - GET /products/3 (ไม่มีส่วนลด) ไม่มีคีย์ discountPercentage เลย - GET /products/9999 ตอบ 404 และ message เป็น "Product 9999 not found" ตรงตัวอักษรต่ออักษร - GET /products/abc ตอบ 400 พร้อมข้อความ "Validation failed (numeric string is expected)" - GET /products/categories ยังตอบรายการหมวด 24 รายการเหมือนเดิม ไม่ถูกจับเป็น id ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ - ห้ามแก้ mapper/DTO - ห้ามเขียน test — e2e test เป็น prompt แยกในแชทถัดไป - ยังไม่ต้องทำ GET /products (list) หรือ pagination

ตรวจโค้ดที่ AI สร้าง

  • GET /products/abc ได้ 400 — ไม่ใช่ 404 หรือ 500 (ถ้าได้ 500 แปลว่า id ที่ไม่ใช่ตัวเลขหลุดเข้าไปถึง query)
  • GET /products/9999 ได้ 404 และข้อความตรงตัวอักษรต่ออักษร: Product 9999 not found
  • GET /products/categories ยังตอบรายการหมวด ไม่ถูกจับเป็น id (log ตอน start ต้องเห็น route categories ก่อน :id)
  • สินค้ามี category เป็น slug และมี reviews ครบ — ถ้าได้ category เป็น undefined หรือ reviews ว่าง แปลว่า query ไม่ได้ดึง relation มาด้วย
  • response ผ่าน mapper ตัวเดิมที่มีอยู่แล้ว ไม่ได้ประกอบรูปทรงใหม่ขึ้นมาเองใน service
  • ไม่มีไฟล์ที่ไม่เกี่ยวกับเป้าหมายถูกแก้, mapper/DTO ไม่ถูกแก้, และไม่มี any / as / !

AI มักพลาดตรงนี้: เขียนข้อความเป็น Product #9999 not found ตามสไตล์ที่เคยเห็นในคอร์ส NestJS Fundamentals (ซึ่งเป็นข้อความที่ถูกต้องในคอร์สนั้น แต่ผิดสัญญาในคอร์สนี้) อีกแบบคือใช้ findFirst({ where: { id } }) โดยลืม include ทั้งก้อน — TypeScript จะฟ้องเมื่อส่งเข้า toProductResponse เพราะ type ProductWithRelations ไม่ยอม แต่บางครั้ง Cursor จะแก้ปัญหาด้วยการเติม as เข้าไปกลบ ให้ค้นคำว่า as ในไฟล์แล้วลบออก แก้ที่ include แทน

โค้ดอ้างอิงของบทนี้ — เป็นหนึ่งในวิธีที่ถูก ของคุณไม่จำเป็นต้องเหมือนทุกบรรทัด ขอแค่ผ่านผลลัพธ์ที่ต้องได้:

src/products/products.service.ts

import { Injectable, NotFoundException } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import { PrismaService } from '../prisma/prisma.service.js';
import { toProductResponse } from './product.mapper.js';
import { ProductResponseDto } from './dto/product-response.dto.js';

@Injectable()
export class ProductsService {
  constructor(
    private readonly prisma: PrismaService,
    private readonly config: ConfigService,
  ) {}

  async findCategories() {
    const appUrl = this.config.getOrThrow<string>('APP_URL');
    const categories = await this.prisma.category.findMany({ orderBy: { id: 'asc' } });
    return categories.map(({ slug, name }) => ({
      slug,
      name,
      url: `${appUrl}/products/category/${slug}`,
    }));
  }

  async findOne(id: number): Promise<ProductResponseDto> {
    const product = await this.prisma.product.findUnique({
      where: { id },
      include: { category: true, reviews: { orderBy: { id: 'asc' } } },
    });
    if (!product) {
      throw new NotFoundException(`Product ${id} not found`);
    }
    return toProductResponse(product);
  }
}

src/products/products.controller.ts

import { Controller, Get, Param, ParseIntPipe } from '@nestjs/common';
import { ProductsService } from './products.service.js';

@Controller('products')
export class ProductsController {
  constructor(private readonly productsService: ProductsService) {}

  @Get('categories')
  findCategories() {
    return this.productsService.findCategories();
  }

  @Get(':id')
  findOne(@Param('id', ParseIntPipe) id: number) {
    return this.productsService.findOne(id);
  }
}

ผลลัพธ์ที่คาดหวัง

log ตอน start มีสองบรรทัดนี้ ตามลำดับนี้

[RouterExplorer] Mapped {/products/categories, GET} route

GET /products/1 ตอบ 200 พร้อมสินค้าครบ 22 คีย์รวม dimensions, meta และ array reviews ส่วน GET /products/9999 ตอบ

HTTP/1.1 404 Not Found
{"message":"Product 9999 not found","error":"Not Found","statusCode":404}

สังเกตว่า body มีคีย์ error และ statusCode เพิ่มจาก message — นี่คือรูปแบบมาตรฐานของ HttpException ใน Nest ซึ่งไม่มีผลกับ React app เพราะ client อ่านแค่ message

เปลี่ยน checklist ให้เป็น test ที่รันได้

ทุกข้อในส่วน "ตรวจว่าใช้งานได้จริง" ด้านบนคือสัญญาที่ต้องเป็นจริงตลอดไป ไม่ใช่แค่วันนี้ — ขั้นถัด ๆ ไปจะกลับมาแก้ controller ตัวเดิมนี้อีก และจะไม่มีใครไล่ยิง curl ห้าคำสั่งแล้วอ่านผลด้วยตาทุกครั้งที่ AI แก้โค้ดให้ วิธีที่ใช้ได้จริงคือย้าย checklist ทั้งอันลงไปอยู่ในไฟล์ที่รันได้ แล้วตัดสินด้วยคำสั่งเดียวว่า npm run test:e2e ผ่านหรือไม่ผ่าน

เหตุผลที่ลึกกว่านั้นคือ check ที่รันได้คือสิ่งที่ AI เอาไปใช้เองได้ คู่มือของเครื่องมือ agent ทุกตัวพูดตรงกันข้อหนึ่ง: ให้คำสั่งที่ตัดสินถูก/ผิดได้เองกับมัน แล้วมันจะรัน อ่านผล และแก้ซ้ำจนผ่านได้โดยไม่ต้องรอคุณอ่าน output ให้ทีละบรรทัด ส่วน checklist ที่เป็นข้อความเฉย ๆ มีแต่คุณเท่านั้นที่ตรวจได้ และเป็นงานที่คนเลิกทำเป็นคนแรกเมื่อรีบ

เครื่องมือสำหรับงานนี้มีอยู่ในโปรเจกต์แล้วตั้งแต่วันแรก ไม่ต้องประดิษฐ์เอง: nest new แถม Vitest, supertest, ไฟล์ตัวอย่าง test/app.e2e-spec.ts, ไฟล์ตั้งค่า vitest.config.e2e.ts (จับเฉพาะไฟล์ *.e2e-spec.ts) และ script test:e2e มาให้ครบตั้งแต่ตอน scaffold และคุณเขียน e2e test แบบนี้มาแล้วใน NestJS Fundamentals บทรู้จัก e2e Test — Test.createTestingModule boot AppModule ทั้งใบ แล้ว supertest ยิง HTTP เข้าไปที่แอปนั้นตรง ๆ บทนี้แค่เอาสิ่งที่คุณมีอยู่แล้วมาใช้กับสัญญาของเรา

e2e test boot แอปของตัวเองขึ้นมาในโปรเซสเดียวกับ Vitest ไม่ได้ยิงไปที่ npm run start:dev ที่คุณเปิดค้างไว้ และไม่ต้องจอง port จริง จะเปิด dev server ค้างไว้หรือไม่ก็ได้ ผลเท่ากัน — แต่ ฐานข้อมูลต้องรันอยู่ เพราะแอปที่ boot ขึ้นมาสร้าง PrismaService ตัวจริงและ query ข้อมูลที่ seed ไว้จริง ๆ

แล้วให้ AI เขียน test ที่เอาไว้ตรวจงานของ AI เองได้จริงหรือ? ได้ — แต่ต้องรักษาความเป็นอิสระของ test ไว้ ไม่ใช่ความเป็นเจ้าของบรรทัดโค้ด สิ่งที่ทำให้ test เชื่อถือได้ไม่ใช่ว่าใครพิมพ์มัน แต่เป็นสามข้อนี้ต่างหาก และทั้งสามข้ออยู่ในมือคุณทั้งหมด

  • แชทใหม่ — สั่งเขียน test ในแชทที่ไม่เห็นบทสนทนาที่เพิ่งเขียน endpoint ไป ถ้าใช้แชทเดิม มันจะเขียน test ที่ตรงกับโค้ดที่มันเพิ่งเขียน ไม่ใช่ตรงกับสัญญา — รวมถึงบั๊กที่มันเพิ่งใส่ไว้ด้วย
  • ผลลัพธ์ที่ต้องได้มาจาก docs/api-spec.md — บรรทัดพวกนั้นคุณ เป็นคนตัดสินใจ ไม่ใช่ AI มันแค่แปลสิ่งที่คุณตัดสินใจไว้แล้วให้เป็นโค้ด เหมือนที่มันแปล endpoint ให้เมื่อกี้
  • ห้ามมันแก้ src/ — ข้อนี้สำคัญที่สุด ถ้า agent แก้โค้ดได้ด้วยและเขียน test ได้ด้วยในคำสั่งเดียว มันจะทำให้ test ผ่านด้วยการแก้ฝั่งที่ง่ายกว่าเสมอ ซึ่งมักเป็นฝั่ง test

และข้อพิสูจน์สุดท้ายที่ไม่มีใครทำแทนคุณได้คือ ทำให้มันพังให้เห็นกับตา — test ที่คุณไม่เคยเห็นมันขึ้นสีแดงเลย ยังไม่นับว่าเป็น test เพราะคุณยังไม่รู้ว่ามันตรวจอะไรอยู่จริง ๆ หรือเปล่า แบบฝึกหัดท้ายหัวข้อนี้บังคับข้อนั้นไว้แล้ว

commit งานก่อน แล้วเปิดแชทใหม่ใน Cursor โหมด Agent แล้วส่ง prompt นี้

เขียน e2e test ของ endpoint สินค้าให้ตรงกับสัญญาใน docs/api-spec.md @docs/api-spec.md ผลลัพธ์ที่ต้องได้: - ไฟล์ test/products.e2e-spec.ts ที่ npm run test:e2e เก็บไปรันด้วย (ไม่ต้องแก้ package.json — script นี้มีอยู่แล้ว) - boot แอปจริงด้วย Test.createTestingModule({ imports: [AppModule] }) แล้วยิงผ่าน supertest ที่ app.getHttpServer() — ไม่ mock อะไรเลย ไม่ยิงไป URL หรือ port ภายนอก และปิดแอปด้วย app.close() ใน afterAll - สี่ test ตามนี้ 1. GET /products/categories → 200 และได้ category 24 รายการ แต่ละก้อนมีคีย์ name, slug, url 2. GET /products/1 → 200 และสินค้ามี 22 คีย์ ชื่อ "Velvet Matte Lipstick" category เป็น string และ reviews เป็น array 3. GET /products/9999 → 404 และ message เป็น "Product 9999 not found" ตรงตัวอักษร 4. GET /products/abc → 400 และ body มี message - import ในไฟล์ test ลงท้ายด้วย .js ตามกติกา ESM ของโปรเจกต์ ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ — Vitest กับ supertest มากับ scaffold แล้ว - ห้ามแก้ไฟล์ใน src/ เด็ดขาด ถ้า test ไม่ผ่านให้บอกผมว่าไม่ผ่านข้อไหน ห้ามแก้โค้ดให้ test ผ่านเอง - ห้ามรัน test ให้ ผมจะรันเอง

โค้ดอ้างอิงของหัวข้อนี้ — เป็นหนึ่งในวิธีที่ถูก ของคุณไม่จำเป็นต้องเหมือนทุกบรรทัด ขอแค่ผ่านผลลัพธ์ที่ต้องได้ข้างบน

import { Test, TestingModule } from '@nestjs/testing';
import { INestApplication } from '@nestjs/common';
import request from 'supertest';
import { AppModule } from './../src/app.module.js';

describe('Products contract (e2e)', () => {
  let app: INestApplication;

  beforeAll(async () => {
    const moduleFixture: TestingModule = await Test.createTestingModule({
      imports: [AppModule],
    }).compile();

    app = moduleFixture.createNestApplication();
    await app.init();
  });

  afterAll(async () => {
    await app.close();
  });

  it('GET /products/categories → 200, 24 categories', async () => {
    const response = await request(app.getHttpServer())
      .get('/products/categories')
      .expect(200);

    expect(response.body).toHaveLength(24);
    expect(Object.keys(response.body[0]).sort()).toEqual(['name', 'slug', 'url']);
  });

  it('GET /products/1 → 200, product with 22 keys', async () => {
    const response = await request(app.getHttpServer())
      .get('/products/1')
      .expect(200);

    expect(Object.keys(response.body)).toHaveLength(22);
    expect(response.body.title).toBe('Velvet Matte Lipstick');
    expect(typeof response.body.category).toBe('string');
    expect(Array.isArray(response.body.reviews)).toBe(true);
  });

  it('GET /products/9999 → 404 with the exact message', async () => {
    const response = await request(app.getHttpServer())
      .get('/products/9999')
      .expect(404);

    expect(response.body.message).toBe('Product 9999 not found');
  });

  it('GET /products/abc → 400 with message', async () => {
    const response = await request(app.getHttpServer())
      .get('/products/abc')
      .expect(400);

    expect(response.body.message).toBeDefined();
  });
});

สังเกตสองอย่างในไฟล์นี้ อย่างแรก import ลงท้ายด้วย .js ทั้งที่ไฟล์จริงเป็น .ts — ธรรมเนียมเดิมของ ESM+TypeScript ที่ใช้ทั่วโปรเจกต์นี้ อย่างที่สอง .expect(404) ของ supertest ตรวจ status ให้ในบรรทัดเดียว ถ้า status ไม่ตรง test จะล้มตรงนั้นทันทีโดยไม่ต้องเขียน if เอง ส่วน expect(...) ที่เหลือคือของ Vitest ซึ่งพิมพ์ค่าที่ได้จริงเทียบกับค่าที่คาดไว้ให้เองเมื่อไม่ตรง

เปิดฐานข้อมูลไว้แล้วรัน npm run test:e2e จะเห็นรายงานของ Vitest — ไฟล์ที่ผ่านขึ้นต้นด้วย ✓ และปิดท้ายด้วยสรุปจำนวน (ตัวเลขเวลาเป็นของเครื่องคุณเอง ไม่ต้องตรงกับที่นี่)

test/app.e2e-spec.ts คือไฟล์ตัวอย่างที่ scaffold ให้มา (ยิง GET / แล้วคาดว่าได้ Hello World!) ปล่อยไว้ได้ ไม่ต้องลบ — มันเป็นสัญญาณว่าแอป boot ขึ้นจริง

ตรวจ test ที่ AI เขียนก่อนจะเชื่อมัน — test ที่อ่านแล้วดูดีแต่ไม่ได้ตรวจอะไรเลยคือสิ่งที่อันตรายที่สุดในไฟล์นี้ เพราะมันขึ้นเขียวตลอดไป

  • git status ต้องเห็นไฟล์ใหม่แค่ test/products.e2e-spec.ts ไฟล์เดียว — ไม่มีไฟล์ใน src/ ถูกแก้ ถ้ามี แปลว่า agent ไปแก้โค้ดให้เข้ากับ test ของมันเอง ให้ย้อนกลับแล้วสั่งใหม่
  • ทุก test ยิงผ่าน request(app.getHttpServer()) — ไม่มี http://localhost:3000 หรือเลข port โผล่ในไฟล์ และไม่มีการ mock PrismaService ทิ้ง (ถ้า mock แปลว่ามันกลายเป็น unit test ที่ไม่ได้แตะฐานข้อมูลจริง)
  • ข้อความ 404 ถูกเทียบแบบ ตรงตัวอักษร ด้วย toBe('Product 9999 not found') ไม่ใช่แค่ toContain('not found') หรือเช็คว่า message มีค่าอยู่เฉย ๆ
  • มี afterAll ที่เรียก app.close() — ถ้าลืม Vitest จะค้างไม่ยอมจบเพราะ connection ยังเปิดอยู่
  • ลองทำให้พังก่อนจะเชื่อมัน: แก้ข้อความใน NotFoundException เป็น Product #9999 not found ชั่วคราว แล้วรัน npm run test:e2e ซ้ำ — test ที่สามต้องล้มพร้อมบรรทัดเทียบค่าที่ได้จริงกับค่าที่คาดไว้ และ echo $? ต้องไม่ใช่ 0 จากนั้นย้อนกลับด้วย git checkout -- . (ไม่ต้องรอ watch mode เพราะ test ไม่ได้ยิงไปที่ dev server — มัน compile และ boot แอปจากซอร์สปัจจุบันเองทุกครั้งที่รัน)
  • พิสูจน์ว่ามันไม่ได้แอบพึ่ง dev server: ปิด npm run start:dev (Ctrl+C) แล้วรัน npm run test:e2e อีกครั้ง — ต้องผ่านเขียวครบเหมือนเดิม ถ้าพังแปลว่าคุณยิงผิดที่
  • รันเฉพาะไฟล์เดียวได้ด้วย npm run test:e2e -- products เมื่อไม่อยากรอไฟล์อื่น
  • commit ด้วย git add -A && git commit -m "test: contract e2e for the products endpoints"

สี่ test นี้จะโตขึ้นทีละขั้น: ขั้น pagination เพิ่มสามข้อของ GET /products ขั้นกรองตามหมวดเพิ่มอีกสองข้อ รวมเป็นเก้าข้อที่คุ้มครอง endpoint ฝั่งอ่านทั้งหมด แล้วข้อที่สิบจะมาพร้อม POST /carts/add ในไฟล์ spec ของตัวเอง — ทุกครั้งที่เพิ่ม endpoint ใหม่ ให้เพิ่ม test ของมันด้วย prompt แยกเสมอ
