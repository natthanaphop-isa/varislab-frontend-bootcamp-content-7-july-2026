POST /auth/signup และการเก็บรหัสผ่าน

เมื่อจบบทนี้ คุณจะสามารถ

  • อธิบายได้ว่าทำไมรหัสผ่านต้อง hash ไม่ใช่ เข้ารหัส และ salt กับ cost factor ทำหน้าที่อะไรคนละอย่างกัน
  • เขียน mapper ที่กันไม่ให้ฟิลด์ลับหลุดออกไปกับ response โดยไม่ต้องพึ่งความจำของคนเขียนโค้ด
  • แปลง error ของฐานข้อมูลตอนอีเมลซ้ำให้กลายเป็น 409 ที่ client อ่านรู้เรื่อง แทนที่จะปล่อยเป็น 500

hash ไม่ใช่การเข้ารหัส

การเข้ารหัส (encryption) ออกแบบมาให้ถอดกลับได้ ถ้าเราเก็บรหัสผ่านแบบเข้ารหัส แปลว่าที่ไหนสักแห่งต้องมีกุญแจที่ถอดมันกลับเป็นข้อความเดิมได้ และวันที่ฐานข้อมูลหลุด กุญแจก็มักหลุดไปด้วย

hash เดินทางเดียว: จากรหัสผ่านไปเป็นค่าที่อ่านไม่ออก แล้วไม่มีทางย้อนกลับ เวลาผู้ใช้ login เราไม่ได้ถอด hash ออกมาเทียบ แต่เอารหัสผ่านที่เพิ่งกรอกมา hash ใหม่ด้วยวิธีเดียวกันแล้วดูว่าได้ค่าเดียวกันไหม แปลว่าต่อให้ฐานข้อมูลทั้งก้อนหลุดออกไป คนที่ได้มันไปก็ยังไม่รู้รหัสผ่านของใครเลย

bcrypt เพิ่มอีกสองชั้นบนความคิดนี้

ส่วนประกอบกันอะไรถ้าไม่มี
salt — ค่าสุ่มที่ต่างกันทุกครั้งกันการเทียบ hash กับตารางที่คำนวณไว้ล่วงหน้า และกันการรู้ว่าสองคนใช้รหัสผ่านเดียวกันคนที่ได้ฐานข้อมูลไปเทียบ hash กับ rainbow table ได้ทันที และเห็นว่าใครใช้รหัสผ่านซ้ำกันบ้าง
cost factor — จำนวนรอบการคำนวณกันการเดาสุ่มจำนวนมาก โดยทำให้การ hash หนึ่งครั้งช้าโดยตั้งใจการ์ดจอหนึ่งใบเดารหัสผ่านได้หลายพันล้านครั้งต่อวินาที

bcrypt เก็บทั้ง salt และ cost ไว้ในตัว hash เอง ค่าที่ออกมาจึงยาว 60 ตัวอักษรและหน้าตาแบบนี้ $2b$10$N9qo8uLOickgx2ZMRZoMye... — 2b คือเวอร์ชันของอัลกอริทึม 10 คือ cost ส่วนที่เหลือคือ salt ต่อด้วย hash ตอนเทียบรหัสผ่าน compare จึงอ่าน salt กับ cost ออกมาจากค่าที่เก็บไว้ได้เอง เราไม่ต้องเก็บคอลัมน์ salt แยกต่างหาก

cost 10 แปลว่า 210 รอบ ขยับขึ้นหนึ่งหน่วยคือช้าขึ้นเท่าตัว ตัวเลขนี้ควรปรับขึ้นตามความเร็วเครื่องในอนาคต และเพราะ cost ฝังอยู่ในตัว hash ของเก่าที่ cost ต่ำกว่าจึงยัง verify ได้ตามปกติ — ปรับขึ้นได้โดยไม่ทำให้บัญชีเดิมใช้ไม่ได้

ฟิลด์ลับรั่วออกทาง response ได้ง่ายกว่าที่คิด

prisma.user.create() คืนแถวที่สร้างทั้งแถว รวม passwordHash ด้วย ถ้า service ส่งค่านั้นกลับไปตรง ๆ NestJS ก็จะ serialize มันออกไปให้ client อย่างซื่อสัตย์ นี่ไม่ใช่กรณีสมมติ — มันคือพฤติกรรมปริยายของโค้ดที่สั้นที่สุดและเขียนง่ายที่สุด

ทางกันที่ใช้ในคอร์สนี้คือตัวเดิมกับที่ใช้แปลงสินค้า: mapper ที่รับแถวจากฐานข้อมูลแล้วคืน object ที่ประกอบขึ้นใหม่ทีละฟิลด์ ข้อดีคือมันเป็น allow-list โดยธรรมชาติ — ฟิลด์ใหม่ที่เพิ่มเข้า schema ในอนาคตจะไม่ไหลออกไปเองจนกว่าจะมีคนตั้งใจเพิ่มบรรทัดให้มัน ตรงข้ามกับการเขียน delete user.passwordHash ซึ่งเป็น deny-list ที่ต้องมีคนจำให้ได้ทุกครั้งที่เพิ่มฟิลด์ลับตัวใหม่

อีเมลซ้ำ: จับที่ไหน

บทก่อนหน้าเราใส่ unique index ไว้ที่ฐานข้อมูลแล้ว แปลว่าการสมัครด้วยอีเมลซ้ำจะถูกปฏิเสธแน่นอน — แต่ถูกปฏิเสธในรูปของ exception จาก Prisma ซึ่งถ้าไม่มีใครจับ NestJS จะแปลงเป็น 500 Internal Server Error และนั่นเป็นคำตอบที่ผิด เพราะความผิดอยู่ที่ข้อมูลที่ client ส่งมา ไม่ใช่ที่ server

Prisma แยกความผิดพลาดชนิดนี้ไว้เป็น PrismaClientKnownRequestError พร้อมรหัส P2002 ที่แปลว่า "ชนกับ unique constraint" เราจึงจับเฉพาะกรณีนั้นแล้วโยน ConflictException ออกไปแทน ได้ 409 ตามสัญญา

อย่าดักด้วยการ findUnique ก่อนแล้วค่อย create เป็นทางเลือกแทนการจับ P2002 — ระหว่างสองคำสั่งนั้นมีช่องให้ request อีกอันสมัครอีเมลเดียวกันแทรกเข้ามาได้พอดี แล้วคุณจะได้ 500 อยู่ดีในวันที่มีคนใช้งานพร้อมกันเยอะ ๆ ซึ่งเป็นวันที่คุณอยากให้มันทำงานถูกที่สุด จะเช็คก่อนเพื่อให้ข้อความสวยก็ได้ แต่ต้องจับ P2002 ไว้ด้วยเสมอ

สั่ง Cursor เปิด POST /auth/signup

ติดตั้ง bcrypt ด้วยมือก่อน แล้วค่อยส่ง prompt

npm install bcrypt npm install -D @types/bcrypt

bcrypt เป็น native module ที่ต้อง build ตอนติดตั้ง ถ้า npm ขึ้นข้อความว่ามี install script ที่ยังไม่ได้อนุมัติ ให้อนุมัติแล้ว build ใหม่ด้วย npm install-scripts approve bcrypt ตามด้วย npm rebuild bcrypt — ถ้า build ไม่ผ่านบนเครื่องของคุณจริง ๆ (มักเป็นเพราะไม่มี toolchain ของ C++) ใช้ bcryptjs แทนได้ มันเป็น JavaScript ล้วน ไม่ต้อง build และมี API ชื่อเดียวกันทุกตัว แลกกับความเร็วที่ช้ากว่า

commit งานก่อน แล้วเปิดแชทใหม่ใน Cursor โหมด Agent (git add -A && git commit -m "chore: before signup")

สร้าง endpoint POST /auth/signup ที่รับอีเมลกับรหัสผ่านแล้วสร้างผู้ใช้ใหม่ ตาม docs/auth-spec.md @docs/auth-spec.md @prisma/schema.prisma ผลลัพธ์ที่ต้องได้: - POST /auth/signup ด้วย {"email":"student@example.com","password":"secret123","name":"Student"} → 201 และ body เป็น { id, email, name, role, createdAt } ตาม docs/auth-spec.md - body ที่ตอบกลับต้องไม่มีรหัสผ่านหรือ hash ไม่ว่าจะชื่อฟิลด์อะไร — และต้องกันด้วยการประกอบ object ขึ้นใหม่ทีละฟิลด์ ไม่ใช่ลบฟิลด์ทิ้งทีหลัง - รหัสผ่านถูกเก็บแบบ hash ด้วย bcrypt cost 10 — ค่าในฐานข้อมูลขึ้นต้นด้วย $2b$10$ และยาว 60 ตัวอักษร ห้ามเก็บรหัสผ่านดิบ - สมัครด้วยอีเมลที่มีอยู่แล้ว → 409 message "Email already registered" โดยจับ error รหัส P2002 ของ Prisma ไม่ใช่ปล่อยให้กลายเป็น 500 - email ผิดรูป, password สั้นกว่า 8 ตัว หรือ field ไหนขาด → 400 message เป็น array ตามรูปแบบเดิมของ ValidationPipe - โค้ดที่เรียก bcrypt อยู่ที่เดียวในโปรเจกต์ ที่อื่นเรียกผ่าน service ตัวนั้น เพราะบทถัดไปจะใช้ตอน login ด้วย - endpoint เดิมทั้งหกเส้นไม่เปลี่ยน — npm run test:e2e ยังได้ Tests 11 passed (11) ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ (bcrypt ติดตั้งแล้ว) - ห้ามแตะไฟล์ใน test/ และห้ามแก้อะไรใน prisma/ - ยังไม่ต้องทำ login, token, guard หรือ GET /auth/me - ห้าม console.log ค่า password หรือ hash - ห้ามใช้ any, as หรือ !

บรรทัด "ห้าม console.log ค่า password" มีไว้จริงจัง ไม่ใช่กันเผื่อ: log ของแอปมักถูกส่งต่อไปที่ระบบเก็บ log ที่คนเข้าถึงได้กว้างกว่าฐานข้อมูลมาก รหัสผ่านที่ hash อย่างดีแล้วแต่ไปโผล่ดิบ ๆ ใน log ก็เท่ากับไม่ได้ hash เลย

ตรวจโค้ดที่ AI สร้าง

  • response ถูกประกอบขึ้นใหม่ทีละฟิลด์ใน mapper — ไม่ใช่ delete user.passwordHash หรือ const { passwordHash, ...rest } = user ซึ่งทั้งคู่เป็น deny-list ที่ลืมได้ตอนเพิ่มฟิลด์ลับตัวถัดไป
  • มีที่เดียวในโปรเจกต์ที่ import bcrypt — ตรวจด้วย grep -rn "bcrypt" src/ ต้องเจอไฟล์เดียว
  • การจับอีเมลซ้ำจับที่ P2002 ไม่ใช่จับ Error ทุกชนิดแล้วตอบ 409 เหมา ๆ (ซึ่งจะกลบ error จริงอย่างฐานข้อมูลล่มให้กลายเป็น "อีเมลซ้ำ")
  • ตรวจชนิดของ error ด้วย instanceof ไม่ใช่ as หรือเช็ค error.code บน any
  • SignupDto เป็น class ที่ทุกฟิลด์มี decorator และรหัสผ่านมีความยาวขั้นต่ำตามสัญญา
  • git status ไม่มีไฟล์ใน test/ หรือ prisma/ และ package.json เปลี่ยนแค่บรรทัดของ bcrypt

AI มักพลาดตรงนี้: ส่งแถวที่ prisma.user.create() คืนมากลับไปตรง ๆ เพราะมันมีฟิลด์ที่ต้องการครบอยู่แล้ว — โค้ดสั้นกว่า ทำงานได้ และ passwordHash ไหลออกไปหา client ทุก request อีกกรณีคือใส่ @Exclude() ของ class-transformer ที่ฟิลด์นั้นแทน ซึ่งจะได้ผลก็ต่อเมื่อเปิด ClassSerializerInterceptor ไว้ด้วย — โปรเจกต์นี้ไม่ได้เปิด มันจึงเงียบสนิทและไม่กันอะไรเลย

โค้ดอ้างอิงของบทนี้ — เป็นหนึ่งในวิธีที่ถูก ของคุณไม่จำเป็นต้องเหมือนทุกบรรทัด ขอแค่ผ่านผลลัพธ์ที่ต้องได้ (บทถัดไปจะอ้างชื่อ PasswordService และ AuthService ถ้าของคุณต่างไปก็ไม่เป็นไร Cursor ในบทนั้นจะอ่านจากโค้ดของคุณเอง):

// src/auth/password.service.ts
import { Injectable } from '@nestjs/common';
import bcrypt from 'bcrypt';

const COST = 10;

@Injectable()
export class PasswordService {
  hash(plain: string): Promise<string> {
    return bcrypt.hash(plain, COST);
  }

  compare(plain: string, hash: string): Promise<boolean> {
    return bcrypt.compare(plain, hash);
  }
}

import bcrypt from 'bcrypt' เป็น default import ไม่ใช่ import { hash } from 'bcrypt' เพราะ bcrypt เป็นแพ็กเกจแบบ CommonJS ส่วนโปรเจกต์เราเป็น ESM การดึงชื่อออกมาตรง ๆ อาจพังตอนรัน ทั้งที่ compile ผ่าน ซึ่งเป็นอาการที่หาสาเหตุยากที่สุดแบบหนึ่ง

// src/auth/user.mapper.ts
import { UserResponseDto } from './dto/user-response.dto.js';

type UserRow = {
  id: number;
  email: string;
  name: string;
  role: string;
  createdAt: Date;
};

export function toUserResponse(user: UserRow): UserResponseDto {
  return {
    id: user.id,
    email: user.email,
    name: user.name,
    role: user.role,
    createdAt: user.createdAt.toISOString(),
  };
}
// src/auth/auth.service.ts
import { ConflictException, Injectable } from '@nestjs/common';
import { Prisma } from '../generated/prisma/client.js';
import { PrismaService } from '../prisma/prisma.service.js';
import { PasswordService } from './password.service.js';
import { SignupDto } from './dto/signup.dto.js';
import { UserResponseDto } from './dto/user-response.dto.js';
import { toUserResponse } from './user.mapper.js';

@Injectable()
export class AuthService {
  constructor(
    private readonly prisma: PrismaService,
    private readonly passwords: PasswordService,
  ) {}

  async signup(dto: SignupDto): Promise<UserResponseDto> {
    const passwordHash = await this.passwords.hash(dto.password);

    try {
      const user = await this.prisma.user.create({
        data: { email: dto.email, name: dto.name, passwordHash },
      });
      return toUserResponse(user);
    } catch (error) {
      if (error instanceof Prisma.PrismaClientKnownRequestError && error.code === 'P2002') {
        throw new ConflictException('Email already registered');
      }
      throw error;
    }
  }
}

ท่อน throw error ท้าย catch สำคัญพอ ๆ กับท่อนที่จับ: มันคือการบอกว่าเราจัดการเฉพาะกรณีที่รู้จัก ส่วนที่เหลือปล่อยให้ขึ้นไปตามปกติ ถ้าลืมบรรทัดนี้ ฐานข้อมูลล่มจะกลายเป็น "สมัครสำเร็จแต่ไม่มีอะไรเกิดขึ้น"

// src/auth/auth.controller.ts
import { Body, Controller, Post } from '@nestjs/common';
import { AuthService } from './auth.service.js';
import { SignupDto } from './dto/signup.dto.js';

@Controller('auth')
export class AuthController {
  constructor(private readonly authService: AuthService) {}

  @Post('signup')
  signup(@Body() dto: SignupDto) {
    return this.authService.signup(dto);
  }
}

{"message":["password must be longer than or equal to 8 characters"],"error":"Bad Request","statusCode":400}

ตรวจว่าใช้งานได้จริง

  • สมัครสำเร็จได้ 201 และไม่มีคำว่า password โผล่ใน body 
    curl -s -X POST http://localhost:3000/auth/signup \
  -H 'Content-Type: application/json' \
  -d '{"email":"student@example.com","password":"secret123","name":"Student"}'
  • ยิงซ้ำคำสั่งเดิมได้ 409 
    curl -s -o /dev/null -w '%{http_code}\n' -X POST http://localhost:3000/auth/signup \
  -H 'Content-Type: application/json' \
  -d '{"email":"student@example.com","password":"secret123","name":"Student"}'
  • สิ่งที่อยู่ในฐานข้อมูลเป็น hash ของ bcrypt จริง — ขึ้นต้น $2b$10$ และยาว 60 
    docker compose exec db psql -U postgres -d ecommerce -c \
  'SELECT id, email, role, left("passwordHash", 7) AS prefix, length("passwordHash") AS len FROM "User";'
  • เอกสาร API ไม่มีคำว่า passwordHash เลยแม้แต่ที่เดียว 
    curl -s http://localhost:3000/api-json | grep -c passwordHash
    ต้องได้ 0 พอดี — ส่วนคำว่า password เฉย ๆ จะ เจอ และนั่นถูกต้อง เพราะ SignupDto มีฟิลด์นั้นจริงในฐานะ body ที่รับเข้ามา สิ่งที่ต้องไม่มีคือ hash ไม่ใช่ชื่อฟิลด์ที่ client ส่งมา
  • bcrypt ถูกเรียกจากที่เดียว — grep -rn "bcrypt" src/ เจอไฟล์เดียวคือ password.service.ts
  • grep -rn "any\|as \| !" src/auth/ ไม่เจอการปิดปาก type checker
  • npm run build และ npm run lint ผ่าน และ npm run test:e2e ยังได้ Tests 11 passed (11)
  • commit ผลงานของบทนี้: git add -A && git commit -m "feat: signup endpoint"

สังเกตว่าเราไม่ได้แก้ .cursor/rules/project.mdc ทั้งที่ src/auth/ เป็น domain ที่สามต่อจาก products กับ orders — บรรทัดเรื่องโครงสร้างไฟล์ในกฎเขียนว่า "(products, orders)" ในฐานะตัวอย่าง ไม่ใช่รายการปิด และกฎชุดนั้นเป็นของที่ตกลงกันไว้ตั้งแต่ต้นคอร์ส ส่วนกฎเฉพาะของ auth อย่าง "ห้ามส่ง passwordHash ออกไป" อยู่ใน ผลลัพธ์ที่ต้องได้ ของ prompt ซึ่งเป็นที่ของมันอยู่แล้ว
