เขียน Seed Generator ด้วย Faker

เมื่อจบบทนี้ คุณจะสามารถ

  • ติดตั้งและ pin เวอร์ชัน @faker-js/faker แล้วสั่งให้ Cursor เขียน seed script ที่ deterministic จากข้อมูลที่คุณให้
  • อธิบายได้ว่าทำไม product id 1 ต้องเป็นค่าคงที่ ไม่ปล่อยให้ faker สุ่ม
  • ยืนยันด้วย SQL ว่าจำนวนสินค้าต่อหมวดตรงกับที่ตั้งใจไว้ (beauty=5, groceries=27, อื่น ๆ=8)

ไม่มี dummyjson ให้ดึงอีกแล้ว

docs/api-spec.md ที่เราเขียนเองจากโค้ดฝั่ง client กลายเป็นสัญญาเดียวของเราที่มาจากโค้ดฝั่ง client ไม่ใช่จาก dummyjson.com บทนี้พาไปอีกขั้น: ไม่มีการดึงข้อมูลจากที่ไหนเลย แคตตาล็อกทั้ง 208 ชิ้นถูกสร้างขึ้นในเครื่องของเราเองด้วย @faker-js/faker แล้วเขียนลง PostgreSQL ตรง ๆ ไม่มี fetch ไม่มี network เลยสักบรรทัด ต่างจากเวอร์ชันเดิมของคอร์สที่ยังต้องพึ่ง GET https://dummyjson.com/products?limit=0 อยู่

ผลที่ได้คือ seed รันได้แม้ไม่มีอินเทอร์เน็ต ไม่มีวันพังเพราะ dummyjson เปลี่ยนข้อมูลหรือ endpoint ล่ม และที่สำคัญที่สุดสำหรับคอร์สนี้: ทำซ้ำได้เป๊ะทุกครั้ง — สิ่งที่ dummyjson ให้เราไม่ได้เลย เพราะเราไม่ได้เป็นเจ้าของข้อมูลนั้น

ทำไมต้อง pin @faker-js/faker@10.6.0 ให้แน่น

เราพิน Prisma ไว้ที่ 7.10.0 และพิน image postgres:17 มาตั้งแต่ตอนยก PostgreSQL ขึ้น ด้วยเหตุผลเดียวกันทุกครั้ง: เวอร์ชันถัดไปอาจเปลี่ยนพฤติกรรมโดยไม่ประกาศว่าเป็น breaking change faker ก็เหมือนกัน — รายการคำในแต่ละ locale (ชื่อสินค้า, ชื่อบริษัท, ชื่อวัตถุดิบอาหาร) แก้ไขได้ระหว่าง minor version เสมอ และเพราะเราเรียก faker.seed(20260913) แล้วอ่านผลลัพธ์ที่ได้แบบ deterministic ค่าที่สุ่มออกมาจึงผูกกับเวอร์ชันที่ติดตั้งจริง ไม่ใช่แค่กับตัวเลข seed

บทนี้ (และขั้นถัดไปที่จะยกตัวอย่างค่าจริงจากสินค้า id 1 หรือจากหมวด groceries) อ้างค่าที่สุ่มมาโดยพิมพ์ตรง ๆ ในเนื้อหา ถ้าใครติดตั้ง faker เวอร์ชันอื่น ต่อให้โค้ดเหมือนกันทุกบรรทัด ค่าที่ได้จะไม่ตรงกับที่คอร์สพิมพ์ไว้เลย คำสั่ง npm i -D @faker-js/faker@10.6.0 ติดตั้งเวอร์ชันที่ระบุเป๊ะ ๆ (ตรวจได้จาก node_modules/@faker-js/faker/package.json) แต่ package.json จะบันทึกเป็น ^10.6.0 ตามธรรมเนียมเดิมของโปรเจกต์นี้ (Prisma และ @prisma/client ก็เขียนด้วย ^ เหมือนกัน) ตัวที่รับประกันจริง ๆ ว่าใครมา npm ci ต่อจะได้เวอร์ชันเดียวกันคือ package-lock.json ที่ต้อง commit คู่กันเสมอ

รวมทั้งหมด: 5 + 27 + (22 × 8) = 208 ชิ้น — ตัวเลขนี้ปรากฏซ้ำในหัวข้อ "ผลลัพธ์ที่คาดหวัง" ด้านล่าง ถ้านับได้ไม่ตรง แปลว่ามีหมวดใดหมวดหนึ่งเพี้ยนจากตารางนี้

product id 1 เป็นค่าคงที่ ไม่ปล่อยให้ faker สุ่ม

ทุกชิ้นในแคตตาล็อกสุ่มด้วย faker ยกเว้นชิ้นเดียว: id 1 ขั้นถัดไปจะยกตัวอย่าง mapper output จากสินค้าชิ้นนี้ตรง ๆ และขั้นสั่งซื้อจะคำนวณราคารวมตะกร้าจากราคาชิ้นนี้ — ทุกจุดพิมพ์ค่าตรง ๆ ไว้ในเนื้อหา ถ้าปล่อยให้ faker สุ่มชิ้นนี้ด้วย ค่าที่พิมพ์ไว้ในทุกขั้นถัดไปจะผูกติดกับลำดับการเรียก faker แบบเปราะบางมาก — สลับลำดับ field แค่บรรทัดเดียวในไฟล์ก็ทำให้ค่าที่ได้เปลี่ยนไปทั้งหมด สินค้าชิ้นนี้จึงต้องเป็นค่าคงที่ที่ไม่ขึ้นกับ faker เลย

ชื่อสินค้าต้องไม่ซ้ำกันภายในหมวดเดียวกัน

สินค้าอีก 207 ชิ้นสุ่มชื่อด้วย faker แต่มีเงื่อนไขหนึ่งข้อที่ต้องรักษาไว้: ภายในหมวดเดียวกันห้ามมีชื่อซ้ำ (คนละหมวดชื่อซ้ำกันได้ ไม่ใช่ปัญหา) เพราะหน้าแสดงรายการสินค้าของ React app จะดูเหมือนข้อมูลพังทันทีถ้ามีสินค้าชื่อเดียวกันสองชิ้นวางติดกันในหมวดเดียว วิธีที่ตรงไปตรงมาที่สุดคือเก็บชื่อที่ใช้ไปแล้วของหมวดนั้นไว้ แล้วสุ่มใหม่เมื่อได้ชื่อซ้ำ — จะเขียนด้วยวิธีไหนก็ได้ ขอแค่ผลลัพธ์ในฐานข้อมูลไม่มีชื่อซ้ำในหมวดเดียวกัน

หมวด groceries ต้องสุ่มชื่อจากคำศัพท์อาหาร (วัตถุดิบ ผลไม้ ผัก) ไม่ใช่ชื่อสินค้าทั่วไป เพราะหมวดนี้คือหมวดที่ใช้เดิน pagination ตอนต่อ React app ให้เห็นของจริงสองหน้า ถ้าชื่อในหมวดของชำกลายเป็นชื่อเฟอร์นิเจอร์หรือเครื่องมือช่าง หน้าจอที่นักเรียนเปิดดูจะดูไม่น่าเชื่อถือทันที ส่วนหมวดอื่นทั้งหมดใช้ชื่อสินค้าทั่วไปได้ และทุกชื่อไม่ว่าหมวดไหนต้องเป็น Title Case (ขึ้นต้นด้วยตัวใหญ่ทุกคำ) ให้เหมือนกันทั้งแคตตาล็อก

กติกาของสินค้าอีก 207 ชิ้นที่สุ่ม

สินค้าที่เหลือสุ่มทุก field แต่ไม่ใช่สุ่มแบบปล่อยอิสระ — มีสามข้อที่ต้องคุมไว้ เพราะมันผูกกับสัญญาใน docs/api-spec.md และกับบทถัดไป ๆ

  • ส่วนลดมีประมาณ 2 ใน 3 — ราว 1 ใน 3 ของสินค้าต้องไม่มีส่วนลดเลย คือ discountPercentage เป็น null ตรงกับคอลัมน์ Float? ใน schema ส่วนที่เหลือได้ตัวเลข 1–25 ข้อนี้สำคัญเพราะ mapper ต้องตัดคีย์นี้ทิ้งทั้งคีย์เมื่อเป็น null ถ้าทุกชิ้นมีส่วนลดหมด จะไม่มีข้อมูลให้ทดสอบพฤติกรรมนั้นเลย
  • ทศนิยมต้องไม่เกินสองตำแหน่ง — ราคา, rating, ส่วนลด และขนาดทั้งสามด้านต้องปัดให้เหลือทศนิยมสองตำแหน่ง ไม่ใช่ค่าที่ลอยมาแบบ 12.340000000000002 จาก floating-point เพราะค่าพวกนี้ถูกส่งออกไปให้ client ตรง ๆ และ React app เอาไปคูณกับจำนวนชิ้นในตะกร้าต่อ
  • รีวิวชิ้นละ 3 รายการเสมอ — ทุกชิ้นมีรีวิวสามรายการเท่ากันหมด (rating 1–5, คอมเมนต์สั้น ๆ, วันที่ย้อนหลังไม่เกิน 180 วัน, ชื่อและอีเมลผู้รีวิว) รวมทั้งแคตตาล็อกจึงได้ 624 รีวิวพอดี ซึ่งเป็นตัวเลขที่ใช้ตรวจว่า seed ทำงานครบ

อีกสี่ field ต้องสุ่มจากชุดตัวเลือกคงที่ ไม่ใช่ข้อความอิสระ เพราะ React app แสดงค่าพวกนี้เป็นป้ายสถานะ ถ้าได้ประโยคยาว ๆ ที่สุ่มมาแบบอิสระ หน้าจอจะเพี้ยนทันที

ข้อสังเกตเรื่อง availabilityStatus: ตัวช่วยสุ่มของ faker หยิบสมาชิกจาก array แบบ uniform ทุกตัวมีโอกาสเท่ากัน ไม่มี parameter ให้ใส่น้ำหนัก ถ้าอยากให้ “มีสินค้า” เกิดบ่อยกว่า “สินค้าหมด” ต้องใส่ 'In Stock' ซ้ำหลายครั้งในชุดตัวเลือกเอง — เป็นจุดที่ควรดูตอนรีวิวว่า Cursor ทำหรือเปล่า

ที่มาของความ deterministic ทั้งหมด

หัวใจของบทนี้คือ faker.seed(20260913) ต้องถูกเรียกครั้งเดียว ก่อนการสุ่มค่าแรก จากนั้นไล่สร้างสินค้าไปตามลำดับหมวดใน CATEGORIES ทีละหมวด หมวดละเท่าจำนวนที่กำหนดไว้ในตารางด้านบน โดย id ไล่ต่อเนื่องจาก 1 ไปเรื่อย ๆ ไม่ข้ามเลข — เมื่อจุดเริ่มต้นของ RNG เหมือนเดิมและลำดับการหยิบค่าเหมือนเดิม ผลลัพธ์ทุกแถวก็เหมือนเดิมทุกครั้งที่รัน

ผลพลอยได้ที่ต้องรู้ไว้: ลำดับของ CATEGORIES และจำนวนต่อหมวดเปลี่ยนไม่ได้หลังจากนี้ สลับสองหมวด เพิ่มการสุ่มอีกหนึ่งครั้ง หรือสลับลำดับ field ที่เรียก faker — ทุกอย่างหลังจุดนั้นจะได้ค่าคนละชุดทันที (เป็นคนละลำดับการหยิบจาก RNG ตัวเดิม) นี่คือเหตุผลที่ค่าที่สุ่มของสินค้าชิ้นอื่นในเครื่องคุณอาจไม่ตรงกับตัวอย่างในบทหลัง ๆ ถ้า Cursor เรียก faker คนละลำดับกับโค้ดอ้างอิง — และเป็นเหตุผลที่สินค้า id 1 ถึงต้องเป็นค่าคงที่

ลบ–เติมใหม่ทั้งชุดในทรานแซกชันเดียว

seed script ต้องรันซ้ำได้ทุกเมื่อ จึงต้องล้างของเดิมก่อนเติมของใหม่เสมอ ลำดับสำคัญเพราะ foreign key: ลบจากลูกไปหาแม่ (Review → Product → Category) แล้วแทรกจากแม่ไปหาลูก (Category → Product → Review) สลับลำดับเมื่อไรจะติด constraint ที่ตั้งไว้ใน schema ทันที

ตอนเขียนสินค้าลงตาราง เรารู้แค่ slug ของหมวด แต่คอลัมน์จริงคือ categoryId จึงต้องอ่านหมวดที่เพิ่งแทรกกลับมาก่อน แล้วแปลง slug เป็น id ให้ทุกชิ้น ถ้าเจอ slug ที่ไม่มีอยู่จริงต้องโยน error ที่บอกชื่อ slug นั้น ไม่ใช่ปล่อยให้เขียนค่าว่างลงฐานข้อมูล

ทั้งหมดนี้ต้องอยู่ในทรานแซกชันเดียว — สำเร็จทั้งชุดหรือไม่เปลี่ยนอะไรเลย ถ้าล้มตอนแทรกสินค้าชิ้นที่ 150 แล้วข้อมูลเก่าถูกลบไปแล้ว ฐานข้อมูลจะเหลือของครึ่ง ๆ กลาง ๆ ที่ไม่ตรงกับสัญญาและไม่มีใครรู้ว่าพังตรงไหน จุดที่ต่างจาก seed เวอร์ชันที่ต้องพึ่ง API ภายนอกคือ: ข้อมูลทั้ง 208 ชิ้นถูกสร้างเสร็จในหน่วยความจำก่อนเปิดทรานแซกชันด้วยซ้ำ ไม่มี fetch ไม่มี network อยู่ในนั้นเลย

ตำแหน่งและชื่อไฟล์ข้างบนมาจากโค้ดอ้างอิง prompt ไม่ได้สั่งว่าต้องวางไฟล์ที่ไหน Cursor อาจเลือกต่างออกไปได้ สิ่งที่ต้องตรงคือข้อในส่วน "ผลลัพธ์ที่ต้องได้" ของ prompt — บทนี้ไม่มีโค้ดอ้างอิงของ seed ให้ลอก มีแต่ข้อมูลกับเงื่อนไข เพราะการเขียน generator เองทีละบรรทัดไม่ใช่สิ่งที่คอร์สนี้ฝึก

  • package.json — สัญญา: devDependencies ต้องมี @faker-js/faker ที่ resolve เป็น 10.6.0 เป๊ะ (ดูใน package-lock.json) และ scripts ต้องมี "db:seed": "tsx prisma/seed.ts"
  • prisma/seed.ts — สัญญา: รันสองรอบได้ข้อมูลเหมือนกันทุกแถว, หมวดหมู่และจำนวนสินค้าต่อหมวดต้องตรงกับที่บทนี้กำหนด, product id 1 ต้องเป็นค่าคงที่ไม่ใช่ค่าที่สุ่ม, ลบ–เติมใหม่ต้องสำเร็จทั้งชุดหรือไม่เปลี่ยนเลย / ต้องไม่ใช้ any, as และ !

commit งานก่อน แล้วเปิดแชทใหม่ใน Cursor โหมด Agent prompt นี้ยาวเพราะต้องยกข้อมูลจากตารางด้านบนให้ครบทุกค่า (หมวดหมู่ จำนวนต่อหมวด สินค้า id 1) แต่ไม่ได้สั่งว่าโค้ดต้องเขียนอย่างไร ไม่มีชื่อฟังก์ชัน ไม่มี signature — สิ่งที่ตรวจคือผลลัพธ์ที่ต้องได้ โดยเฉพาะการรันสองรอบแล้วได้ข้อมูลเหมือนเดิม

ถ้า Cursor เรียก faker ในลำดับต่างจากโค้ดอ้างอิง ค่าที่สุ่มได้ของสินค้าชิ้นอื่น ๆ จะไม่ตรงกับตัวอย่างที่พิมพ์ไว้ในบทหลัง ๆ — เป็นเรื่องปกติ ให้เทียบกับข้อมูลในฐานข้อมูลของคุณเอง ค่าที่ต้องตรงเป๊ะมีแค่จำนวนแถวและสินค้า id 1

ตรวจโค้ดที่ AI สร้าง

  • หมวดหมู่ 24 หมวดเรียงตามลำดับที่ระบุ และจำนวนสินค้าต่อหมวดตรงตาม prompt
  • faker ถูก seed ด้วยค่าคงที่ก่อนสุ่มทุกค่า — รัน seed สองรอบแล้วข้อมูลสินค้าเหมือนกันทุกแถว
  • product id 1 เป็นค่าคงที่ ไม่มีค่าไหนของมันมาจาก faker
  • ลบและเติมข้อมูลใหม่อยู่ใน transaction เดียว — ล้มกลางทางแล้วฐานข้อมูลไม่เหลือข้อมูลครึ่ง ๆ กลาง ๆ
  • warranty/shipping/availability/returnPolicy มาจากชุดตัวเลือกคงที่ ไม่ใช่ข้อความอิสระจาก faker
  • ไม่มี any, as และ non-null assertion (!) — slug ที่หาไม่เจอต้อง throw error ที่บอกชื่อ slug
  • package.json มี @faker-js/faker ใน devDependencies และ script db:seed ที่รัน seed script ด้วย tsx
  • git status ไม่มีไฟล์ที่ไม่เกี่ยวกับ seed ถูกแก้ (เช่น schema.prisma หรือไฟล์ใน src/)

AI มักพลาดตรงนี้: ปล่อยให้สินค้า id 1 สุ่มไปด้วยแทนที่จะใช้ค่าคงที่จากตารางใน prompt (ได้ผลรันแต่ค่าจะไม่ตรงกับที่บทถัดไปพิมพ์ไว้เลย) หรือสุ่มข้อความอิสระให้ warrantyInformation/returnPolicy แทนการสุ่มจาก array ตัวเลือกที่กำหนด (ทำให้ค่าไม่อยู่ในเซตที่คาดไว้)

ถ้าอธิบายบรรทัดไหนไม่ได้ ยังไม่ผ่านบทนี้ — กลับไปอ่านส่วนแนวคิดก่อน
