ออกแบบ Model ของคำสั่งซื้อ

เมื่อจบบทนี้ คุณจะสามารถ

  • อ่าน body ที่ React app ส่งมาตอน checkout แล้วแปลงเป็นตาราง Order และ OrderItem ได้
  • อธิบายได้ว่าทำไม OrderItem ต้องคัดลอก title, price, discountPercentage, thumbnail เก็บไว้เอง
  • เลือกใส่ onDelete: Cascade ให้ถูกฝั่ง และบอกได้ว่าทำไม seed ต้องเปลี่ยนลำดับการลบข้อมูล

สองฝั่งของคำสั่งซื้อ: body ที่รับ กับ response ที่ต้องคืน

ถึงตอนนี้ API ของเราอ่านสินค้าได้ครบแล้ว บทที่ 16–19 จะเพิ่มฝั่ง เขียน ตัวเดียวที่ React app ต้องใช้ คือตอนกดสั่งซื้อ ก่อนออกแบบตารางต้องรู้สองอย่างให้แน่ชัด: client ส่งอะไรมา และ client คาดหวัง response หน้าตาแบบไหน

ฝั่งที่ส่งมาคือ hook useCheckout ของ React app มันประกอบ body จากตะกร้าแบบนี้เสมอ (userId ยังเป็นค่าคงที่ 1 เพราะแอปตัวอย่างยังไม่มีระบบ login)

{
  "userId": 1,
  "products": [{ "id": 1, "quantity": 2 }],
  "address": {
    "address": "1 Sukhumvit Rd",
    "email": "a@b.com",
    "phone": "0812345678"
  }
}

ฝั่งที่ต้องคืนคือสัญญาที่วางไว้ในโปรเจกต์ตั้งแต่บทที่ 3 ไฟล์ docs/contract/cart-add.txt คือ response จริงของ POST https://dummyjson.com/carts/add status 201

{"id":209,"products":[{"id":1,"title":"Essence Mascara Lash Princess","price":9.99,"quantity":2,"total":19.98,"discountPercentage":10.48,"discountedPrice":18,"thumbnail":"https://cdn.dummyjson.com/product-images/beauty/essence-mascara-lash-princess/thumbnail.webp"}],"total":19.98,"discountedTotal":18,"userId":1,"totalProducts":1,"totalQuantity":2}

สังเกตความไม่สมมาตรสองจุด: address ที่ส่งไปไม่ถูกส่งกลับมาใน response เลย และ products[] ที่กลับมามี field มากกว่าที่ส่งไปเยอะ (title, price, total, discountPercentage, discountedPrice, thumbnail) นั่นคือหน้าที่ของเรา — รับ id กับ quantity แล้วเติมข้อมูลสินค้าและยอดเงินให้ครบ

Order หนึ่งใบ มีหลาย OrderItem

คำสั่งซื้อหนึ่งใบมีสินค้าได้หลายรายการ จึงเป็นความสัมพันธ์ one-to-many ตรงตัว: Order เก็บสิ่งที่เป็นของทั้งใบ (userId, ที่อยู่จัดส่ง, ยอดรวม, เวลาที่สั่ง) และ OrderItem เก็บสิ่งที่เป็นของแต่ละบรรทัด (สินค้าตัวไหน กี่ชิ้น ราคาเท่าไร) — pattern เดียวกับ Product กับ Review ในบทที่ 7

ที่อยู่จัดส่ง (address, email, phone) เก็บไว้ที่ Order แม้ response จะไม่คืนออกไป เพราะข้อมูลนี้จำเป็นต่อการจัดส่ง และเป็นค่าของใบนั้นใบเดียว ไม่ใช่ของ user (user คนเดียวสั่งไปหลายที่อยู่ได้)

snapshot: ใบเสร็จของเมื่อวานต้องไม่เปลี่ยนเพราะราคาของวันนี้

จุดตัดสินใจสำคัญที่สุดของบทนี้: OrderItem มี productId อยู่แล้ว ทำไมยังต้องเก็บ title, price, discountPercentage, thumbnail ซ้ำอีก ทั้งที่ join กลับไปที่ Product ก็อ่านได้

เพราะ Product เปลี่ยนได้ พรุ่งนี้ร้านลดราคาจาก 9.99 เป็น 7.99 หรือเปลี่ยนชื่อสินค้า ถ้าใบเสร็จอ่านราคาจากตาราง Product ทุกครั้ง ใบเสร็จของเมื่อวานจะเปลี่ยนตัวเลขตามไปด้วย — ลูกค้าจ่ายไป 19.98 แต่ประวัติกลับโชว์ 15.98 นี่คือบั๊กทางบัญชี ไม่ใช่เรื่องความสวยงามของ schema

เราจึง คัดลอก ค่าที่ใช้คิดเงินลงมาเก็บใน OrderItem ตอนสั่งซื้อ (เรียกว่า snapshot หรือ denormalization ที่ตั้งใจทำ) ส่วน productId ยังเก็บไว้เพื่อให้ลิงก์กลับไปหน้าสินค้าได้ แต่ตัวเลขบนใบเสร็จไม่พึ่งมันแล้ว ด้วยเหตุผลเดียวกัน total, discountedTotal, totalProducts, totalQuantity ก็ถูกเก็บเป็น column ไม่ใช่คำนวณใหม่ตอนอ่าน

ลบอะไรได้ ลบอะไรไม่ได้

สองความสัมพันธ์ของ OrderItem ต้องตั้ง onDelete ต่างกัน และนี่คือจุดที่ AI มักทำเหมือนกันทั้งคู่

ความสัมพันธ์onDeleteเหตุผล
OrderItem → OrderCascadeรายการสินค้าไม่มีความหมายถ้าไม่มีใบคำสั่งซื้อ ลบใบทิ้ง รายการต้องหายตามไปด้วย
OrderItem → Productค่า default (Restrict)ห้ามลบสินค้าที่ยังมีคำสั่งซื้ออ้างถึง ไม่งั้นเราจะทำใบเสร็จหายเพราะลบสินค้าตัวเดียว

ผลข้างเคียงตามมาทันทีที่ prisma/seed.ts ปัจจุบัน seed ลบข้อมูลตามลำดับ review → product → category ใน transaction พอมี OrderItem อ้างถึง Product แบบ Restrict คำสั่ง tx.product.deleteMany() จะพังทันทีถ้ายังมีคำสั่งซื้อค้างอยู่ในฐานข้อมูล จึงต้องลบ orderItem และ order ขึ้นไปเป็นสองบรรทัดแรกของ transaction

ลำดับต้องเป็น orderItem ก่อน order เสมอ ไม่ใช่เพราะ Cascade ใช้ไม่ได้ (ใช้ได้) แต่เพราะการเขียนลำดับลูกก่อนแม่ให้ชัดเจนทำให้อ่าน seed แล้วเห็น dependency graph ทันที และไม่ต้องพึ่งพฤติกรรมของ FK

เป้าหมายของบทนี้

ecommerce-api/
└── prisma/
    ├── schema.prisma   (แก้ไข: เพิ่ม model Order, OrderItem และ relation ฝั่ง Product)
    └── seed.ts         (แก้ไข: ลบ orderItem และ order ก่อนลบ review)
  • prisma/schema.prisma — สัญญา: ต้องมี model Order และ model OrderItem ครบ field ตามสัญญาของ cart-add.txt บวกที่อยู่จัดส่ง, ต้องมี orderItems OrderItem[] ฝั่ง Product, ต้องมี @@index([orderId]) และ @@index([productId]) · ต้องไม่แตะ model Category, Review หรือ field เดิมของ Product
  • prisma/seed.ts — สัญญา: ต้องเพิ่ม tx.orderItem.deleteMany() แล้ว tx.order.deleteMany() ก่อน tx.review.deleteMany() · ต้องไม่แก้ส่วน fetch, ส่วน createMany หรือข้อความ log
  • ไม่มีไฟล์ใน src/ เปลี่ยนในบทนี้ — DTO, service และ controller ของคำสั่งซื้ออยู่ในบทที่ 17–19

สั่ง Cursor เพิ่มสอง model แล้วรัน migration ด้วยมือ

commit งานก่อน แล้วเปิดแชทใหม่ใน Cursor โหมด Agent — commit ไว้เพื่อให้เทียบ diff ของ AI ได้ทีละบรรทัด และแชทใหม่ทำให้ context ไม่ปนกับบทก่อน (git add -A && git commit -m "chore: before order schema") จากนั้นส่ง prompt นี้ทั้งก้อน

ก่อนส่ง อ่านกติกาของคอร์สอีกครั้ง: AI พิมพ์แทนคุณได้ แต่คุณต้องอธิบายทุกบรรทัดได้ — ถ้าอธิบายไม่ได้ แปลว่ายังไม่ผ่านบทนี้

เพิ่ม Prisma model ของ Order และ OrderItem และอัปเดต seed ให้ล้างคำสั่งซื้อก่อนล้างสินค้า บริบท: @prisma/schema.prisma @prisma/seed.ts @docs/contract/cart-add.txt @.cursor/rules/project.mdc docs/contract/cart-add.txt คือ response จริงของ POST https://dummyjson.com/carts/add (status 201): { id, products: [{ id, title, price, quantity, total, discountPercentage, discountedPrice, thumbnail }], total, discountedTotal, userId, totalProducts, totalQuantity } React app ส่ง body { userId, products: [{ id, quantity }], address: { address, email, phone } } — เราจะเก็บ address ไว้ที่ Order ด้วย schema มี Category, Product, Review แล้ว seed.ts ลบข้อมูลตามลำดับ review, product, category ใน transaction เมื่อมี OrderItem อ้างถึง Product แล้ว seed จะลบ product ไม่ได้ถ้ายังมีคำสั่งซื้อค้างอยู่ โครงสร้าง: แก้ไฟล์ตามนี้ ไม่มากไม่น้อยกว่านี้ - prisma/schema.prisma (แก้ไข: เพิ่มสอง model ต่อท้าย และเพิ่ม relation ฝั่ง Product) - prisma/seed.ts (แก้ไข: เพิ่มการลบ orderItem และ order) ข้อกำหนดทางเทคนิค: - model Order: id Int @id @default(autoincrement()), userId Int, address String, email String, phone String, total Float, discountedTotal Float, totalProducts Int, totalQuantity Int, createdAt DateTime @default(now()), items OrderItem[] - model OrderItem: id Int @id @default(autoincrement()), orderId Int, order Order @relation(fields: [orderId], references: [id], onDelete: Cascade), productId Int, product Product @relation(fields: [productId], references: [id]), title String, thumbnail String, price Float, discountPercentage Float, quantity Int, total Float, discountedPrice Float และ @@index([orderId]) @@index([productId]) - Product เพิ่ม field orderItems OrderItem[] ต่อท้าย - ราคาและชื่อสินค้าถูกคัดลอกลง OrderItem ตอนสั่งซื้อ (snapshot) เพราะสินค้าอาจเปลี่ยนราคาภายหลัง ห้ามตัด field เหล่านี้ออก - seed.ts: ใน transaction ก่อน tx.review.deleteMany() เพิ่ม await tx.orderItem.deleteMany() แล้ว await tx.order.deleteMany() ตามลำดับ ห้ามแก้ส่วนอื่น ขอบเขต: - ห้ามแก้ไฟล์ใน src/ - ห้ามรัน migrate หรือ generate ให้ผมรันเอง - ยังไม่ต้องสร้าง DTO, service หรือ controller ของคำสั่งซื้อ

prompt สั่งห้าม AI รัน migrate หรือ generate เอง เพราะสองคำสั่งนี้แก้ฐานข้อมูลจริงและสร้างไฟล์ migration ที่ commit ลง repo — เราต้องอ่าน schema ที่ AI เขียนให้จบก่อน แล้วจึงรันสามคำสั่งนี้ด้วยมือตามลำดับ

npx prisma migrate dev --name add-orders npx prisma generate npm run db:seed

prisma migrate dev ของ Prisma 7 ไม่รัน generate ให้อัตโนมัติ ถ้าข้ามคำสั่งที่สอง tx.orderItem และ tx.order จะยังไม่มีใน Prisma Client และ seed จะพังด้วย type error

ตรวจโค้ดที่ AI สร้าง

  • model Order มี 10 field: id, userId, address, email, phone, total, discountedTotal, totalProducts, totalQuantity, createdAt บวก relation items OrderItem[]
  • createdAt เป็น DateTime @default(now()) และไม่มี updatedAt — ใบเสร็จไม่ถูกแก้
  • model OrderItem เก็บ snapshot ครบสี่ตัว (title, thumbnail, price, discountPercentage) บวก quantity, total, discountedPrice
  • relation ฝั่ง order มี onDelete: Cascade ส่วนฝั่ง product ไม่มี onDelete
  • มี @@index([orderId]) และ @@index([productId]) ทั้งสองบรรทัด
  • Product ได้ field orderItems OrderItem[] ต่อท้าย และ field เดิมไม่ถูกแตะ (git diff prisma/schema.prisma ต้องเห็นแค่บรรทัดที่เพิ่ม)
  • seed.ts เพิ่มแค่สองบรรทัด และอยู่ข้างใน prisma.$transaction ก่อน tx.review.deleteMany()

AI มักพลาดตรงนี้: ใส่ onDelete: Cascade ให้ relation ฝั่ง product ด้วย (ลบสินค้าตัวเดียวแล้วใบเสร็จเก่าหายไปเงียบ ๆ) หรือแถม @updatedAt ให้ Order ทั้งที่ไม่มีใน requirement และผิดความหมายของใบเสร็จ อีกกรณีที่เจอบ่อยคือเอาบรรทัด deleteMany ไปวางไว้นอก transaction หรือวางไว้หลัง tx.product.deleteMany() ซึ่งพังตอนรัน

// prisma/schema.prisma — ท้าย model Product (field อื่นทั้งหมดไม่เปลี่ยน)
  categoryId           Int
  category             Category @relation(fields: [categoryId], references: [id])
  reviews              Review[]
  orderItems           OrderItem[]

  @@index([categoryId])
}
// prisma/schema.prisma — สอง model ใหม่ต่อท้ายไฟล์
model Order {
  id              Int         @id @default(autoincrement())
  userId          Int
  address         String
  email           String
  phone           String
  total           Float
  discountedTotal Float
  totalProducts   Int
  totalQuantity   Int
  createdAt       DateTime    @default(now())
  items           OrderItem[]
}

model OrderItem {
  id                 Int     @id @default(autoincrement())
  orderId            Int
  order              Order   @relation(fields: [orderId], references: [id], onDelete: Cascade)
  productId          Int
  product            Product @relation(fields: [productId], references: [id])
  title              String
  thumbnail          String
  price              Float
  discountPercentage Float
  quantity           Int
  total              Float
  discountedPrice    Float

  @@index([orderId])
  @@index([productId])
}

    await tx.orderItem.deleteMany();
    await tx.order.deleteMany();
    await tx.review.deleteMany();
    await tx.product.deleteMany();
    await tx.category.deleteMany();
