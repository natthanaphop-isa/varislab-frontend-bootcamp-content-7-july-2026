Providers และ QueryClient

Providers & QueryClient

บทนี้เป็นชิ้นสุดท้ายของโครงแอป: วางระบบจัดการข้อมูลจาก server ให้พร้อมใช้ทั่วทั้งแอป ก่อนลงมือ ทวนแนวคิดสำคัญจากคอร์ส React พื้นฐาน กันหนึ่งย่อหน้า — state ในแอปเรามีสองพันธุ์ที่ต้องจัดการคนละวิธี:

  • Server state — ข้อมูลที่เจ้าของตัวจริงอยู่บน server เช่น รายการสินค้า ราคา รีวิว เราเป็นแค่ผู้ยืมมาแสดง มันเลยมีปัญหาเฉพาะตัว: ต้องโหลด อาจโหลดพลาด อาจหมดอายุ ต้อง cache — ทั้งหมดนี้คือหน้าที่ของ TanStack Query
  • Client state — ข้อมูลที่เกิดและจบในเบราว์เซอร์ เช่น ของในตะกร้า modal เปิดอยู่ไหม — อันนี้เป็นหน้าที่ของ React เอง (ในโปรเจกต์นี้คือ Context + useReducer ซึ่งจะสร้างกันในบทที่ 19)

บทเรียนราคาแพงที่สุดข้อหนึ่งของมือใหม่คือการเอา useEffect + useState ไปจัดการ server state เอง — ได้โค้ดที่ไม่มี cache, โหลดซ้ำซ้อน และ race condition เพียบ เราจะไม่ทำแบบนั้นแม้แต่บรรทัดเดียวในโปรเจกต์นี้

ติดตั้ง TanStack Query

ตัว library หลักเป็น dependency ปกติ ส่วน Devtools ติดตั้งเป็น -D (devDependency) เพราะเป็นเครื่องมือของนักพัฒนา ไม่ใช่ของที่ผู้ใช้จริงต้องได้รับ:

npm i @tanstack/react-query
npm i -D @tanstack/react-query-devtools

queryClient.ts: หัวใจของ cache

ทุกอย่างใน TanStack Query หมุนรอบ object ตัวเดียวชื่อ QueryClient — มันคือทั้งตัว cache และศูนย์ตั้งค่าพฤติกรรมของทุก query ในแอป สร้าง src/app/queryClient.ts:

import { QueryClient } from "@tanstack/react-query";

export const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 60 * 1000,
      retry: 1,
    },
  },
});

ค่า default สองตัวที่เราตั้ง คือการตัดสินใจที่คิดมาแล้วสำหรับแอปแบบนี้โดยเฉพาะ:

  • staleTime: 60 * 1000 — ข้อมูลที่โหลดมาแล้วถือว่า "ยังสด" อยู่ 60 วินาที ระหว่างนั้นถ้า component ไหนขอข้อมูลก้อนเดิม TanStack Query จะส่งของจาก cache ให้ทันทีโดยไม่ยิง API ซ้ำ (ค่า default ของ library คือ 0 — สลับหน้าไปมาทีเดียวยิงใหม่ทุกครั้ง) ข้อมูลสินค้าของเราไม่ได้เปลี่ยนวินาทีต่อวินาที หนึ่งนาทีจึงเป็นจุดสมดุลที่ดีระหว่างความสดกับจำนวน request — เขียน 60 * 1000 แทน 60000 เพื่อให้อ่านออกทันทีว่าหน่วยคือ "60 วินาที คูณเป็น milliseconds"
  • retry: 1 — query ที่ล้มเหลวจะถูกลองใหม่อีก 1 ครั้งก่อนประกาศว่า error จริง (default คือ 3 ครั้งพร้อม delay ที่เพิ่มขึ้นเรื่อย ๆ ซึ่งแปลว่าผู้ใช้ต้องจ้องหน้า loading นานหลายวินาทีกว่าจะเห็นข้อความ error) ลองหนึ่งครั้งพอกันเหตุ network สะดุดชั่วขณะ แต่ถ้าพังจริงก็บอกผู้ใช้ให้เร็ว

สังเกตว่าเราสร้าง client ไว้นอก component ที่ระดับ module — ไฟล์นี้ถูกประมวลผลครั้งเดียวตอนแอปเริ่ม เราจึงได้ singleton: cache หนึ่งก้อนต่อหนึ่งแอปตลอดอายุของมัน ถ้าเผลอไปเขียน new QueryClient() ข้างในตัว component จะเสี่ยงได้ client ตัวใหม่ (cache เปล่า ๆ) ทุกครั้งที่ component นั้นถูก render ใหม่ — เท่ากับ cache ที่ลืมทุกอย่างตลอดเวลา อีกเหตุผลที่แยกเป็นไฟล์ของตัวเอง: ตอนเขียนเทสต์ในบทที่ 26 เราจะสร้าง client คนละตัวสำหรับเทสต์โดยเฉพาะ การที่ "ตัว client" กับ "ตัว provider" แยกจากกันทำให้สลับได้ง่าย

providers.tsx: รวมทุก provider ไว้ประตูเดียว

แอปจริงมักมี provider หลายตัวซ้อนกันเป็นหัวหอม: query client, theme, auth, cart ฯลฯ ถ้าซ้อนกันสด ๆ ใน App.tsx ไฟล์นั้นจะรกขึ้นเรื่อย ๆ ทุกครั้งที่มีของใหม่ pattern ที่โปรเจกต์นี้ใช้คือสร้าง component AppProviders ที่เดียวจบ — ใครอยากรู้ว่าแอปนี้มี provider อะไรบ้าง ลำดับไหน เปิดไฟล์เดียวเห็นครบ สร้าง src/app/providers.tsx:

import { ReactNode } from "react";
import { QueryClientProvider } from "@tanstack/react-query";
import { ReactQueryDevtools } from "@tanstack/react-query-devtools";
import { queryClient } from "./queryClient";

export function AppProviders({ children }: { children: ReactNode }) {
  return (
    <QueryClientProvider client={queryClient}>
      {children}
      {import.meta.env.DEV && <ReactQueryDevtools initialIsOpen={false} />}
    </QueryClientProvider>
  );
}
💡 นี่คือ providers.tsx เวอร์ชันแรก — ในบทที่ 19 เมื่อเราสร้างระบบตะกร้าสินค้าเสร็จ จะมี <CartProvider> เข้ามาห่อ {children} เพิ่มอีกหนึ่งชั้นตรงนี้ และนั่นแหละคือจุดขายของ pattern นี้: วันนั้นเราจะแก้แค่ไฟล์นี้ไฟล์เดียว App.tsx ไม่ต้องรู้เรื่องเลย

ไล่ดูของในไฟล์:

  • children: ReactNode — pattern เดียวกับที่เรียนในคอร์ส React พื้นฐาน: component ที่รับ "อะไรก็ได้ที่ render ได้" มาห่อ ทำให้ AppProviders ไม่ต้องรู้จักเนื้อในของแอปแม้แต่นิดเดียว
  • QueryClientProvider — ส่ง queryClient ของเราลงไปผ่าน context ให้ทุก component ใต้ต้นไม้เรียกใช้ useQuery ได้ ตัว client อยู่ไฟล์หนึ่ง ตัว provider อยู่อีกไฟล์ — แยกหน้าที่ "สร้างของ" กับ "แจกของ" ออกจากกัน
  • import.meta.env.DEV — ตัวแปรพิเศษที่ Vite แทนค่าให้ตอน build: ระหว่าง npm run dev มันคือ true แต่ใน production build มันคือ false ทั้งบรรทัดจึงกลายเป็น dead code ที่ถูกตัดทิ้งจาก bundle ไปเลย — Devtools จึงไม่มีทางหลุดไปถึงหน้าจอผู้ใช้จริงแม้แต่ byte เดียว สอดคล้องกับที่เราติดตั้งมันเป็น devDependency
  • initialIsOpen={false} — ให้ Devtools เริ่มแบบหุบอยู่ เหลือแค่ปุ่มลอยเล็ก ๆ ไว้กดเปิดเมื่ออยากดู

อัปเกรด App.tsx เป็นเวอร์ชันสมบูรณ์

เปิด src/app/App.tsx แล้วเอา AppProviders เข้าไปห่อ RouterProvider — และนี่คือหน้าตาฉบับสมบูรณ์ของไฟล์นี้ มันจะไม่เปลี่ยนอีกแล้วตลอดทั้งคอร์ส:

import { RouterProvider } from "react-router/dom";
import { AppProviders } from "./providers";
import { router } from "./router";

function App() {
  return (
    <AppProviders>
      <RouterProvider router={router} />
    </AppProviders>
  );
}

export default App;

อ่านจากนอกเข้าใน: providers ห่อ router, router เลือกหน้า, หน้าถูกวางใน layout — สามบรรทัดนี้เล่าโครงสร้างทั้งแอปจบ การที่ providers อยู่นอก RouterProvider สำคัญนะ: มันแปลว่าทุกหน้า ทุก layout รวมถึง RouteErrorFallback ล้วนอยู่ใต้ QueryClientProvider และใช้ query ได้หมด ไม่มีมุมอับ

Checkpoint

💡 รัน npm run dev — แอปต้องขึ้นเหมือนเดิมทุกประการ (Header, Footer, หน้า stub ครบ) แต่มีของใหม่หนึ่งชิ้น: ปุ่มลอยของ TanStack Query Devtools ที่มุมล่างของจอ กดเปิดดูได้เลย — ตอนนี้แผง queries ยังว่างเปล่าเพราะเรายังไม่ได้เขียน query สักตัว (ตัวแรกจะมาในบทที่ 14) ปิดท้ายด้วย npm run lint และ npm run build ให้ผ่านทั้งคู่ — ถ้า build ผ่าน แปลว่าโครงแอปทั้งสามบทของช่วงนี้ประกอบกันสนิทดีแล้ว

โครงแอปเสร็จสมบูรณ์: มี router, มี layout, มี providers ช่วงถัดไปเราจะลงมือสร้างกล่องเครื่องมือของตัวเอง — คอมโพเนนต์กลางอย่าง Button, Input และ RadioInput ที่ทุกหน้าจะหยิบไปใช้ซ้ำตลอดทั้งโปรเจกต์

ก่อนหน้า: Header และ Footer สารบัญบทเรียน ถัดไป: Button, Input และ RadioInput
