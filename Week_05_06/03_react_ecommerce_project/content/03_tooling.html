บทเรียน 03 · ติดตั้งโปรเจกต์ (Project Setup)

ESLint, Prettier และ Path Alias

Tooling

ก่อนเขียนโค้ดจริงสักบรรทัด เราจะติดอาวุธคุณภาพโค้ดให้ครบมือก่อน: ESLint จับบั๊กเชิงตรรกะและบังคับกติกาของ React, Prettier จัดรูปแบบโค้ดให้เหมือนกันทั้งโปรเจกต์โดยไม่ต้องเถียงกันเรื่อง style และ path alias ที่ทำให้ import อ่านง่ายไม่ว่าไฟล์จะอยู่ลึกแค่ไหน ทั้งหมดนี้ทำตอนนี้เพราะเครื่องมือพวกนี้มีค่าที่สุดเมื่อทำงานตั้งแต่ commit แรก — ติดตั้งทีหลังเมื่อโค้ดมีเป็นพันบรรทัดแล้ว คุณจะเจอ warning ท่วมจอจนอยากปิดมันทิ้ง

ติดตั้งแพ็กเกจ

รันคำสั่งเดียวยาว ๆ นี้ (template ของ Vite ให้บางตัวมาแล้ว การรันซ้ำไม่เสียหาย — npm จะเช็กและติดตั้งเฉพาะที่ขาด):

npm i -D @eslint/js globals typescript-eslint eslint eslint-plugin-react-hooks eslint-plugin-react-refresh eslint-plugin-import-x eslint-config-prettier prettier

ทุกตัวติดตั้งด้วย -D (devDependencies) เพราะเป็นเครื่องมือตอนพัฒนา ไม่ได้ถูก bundle ไปกับแอป ไล่ดูทีละตัว:

  • eslint, @eslint/js — ตัว linter หลัก และชุดกฎมาตรฐานของ JavaScript
  • typescript-eslint — สอน ESLint ให้อ่าน TypeScript ออก พร้อมชุดกฎเฉพาะ TS
  • globals — รายชื่อตัวแปร global ของแต่ละสภาพแวดล้อม (เช่น window, document ของเบราว์เซอร์) เพื่อไม่ให้ ESLint ฟ้องว่าเป็นตัวแปรที่ไม่รู้จัก
  • eslint-plugin-react-hooks — บังคับ Rules of Hooks ที่เราท่องกันมาตั้งแต่คอร์ส React พื้นฐาน
  • eslint-plugin-react-refresh — คุ้มครองให้ hot reload (HMR) ทำงานได้เต็มประสิทธิภาพ
  • eslint-plugin-import-x — จัดระเบียบลำดับการ import
  • prettier, eslint-config-prettier — ตัวจัดรูปแบบโค้ด และตัวเชื่อมที่ทำให้ ESLint กับ Prettier ไม่ตีกัน

เขียน eslint.config.js ของเราเอง

ESLint ยุคใหม่ใช้ระบบตั้งค่าที่เรียกว่า flat config: ไฟล์ JavaScript ไฟล์เดียวชื่อ eslint.config.js ที่ export array ของ config object — อ่านจากบนลงล่าง ตัวหลังทับตัวหน้า จบในไฟล์เดียว (ต่างจากระบบเก่าที่มี .eslintrc หลายรูปแบบซ้อนกันหลายชั้นจนตามหาที่มาของกฎแทบไม่เจอ) template ของ Vite มีไฟล์นี้อยู่แล้ว แต่เราจะเขียนทับทั้งไฟล์ด้วยเวอร์ชันของเราเอง:

import js from "@eslint/js";
import globals from "globals";
import reactHooks from "eslint-plugin-react-hooks";
import reactRefresh from "eslint-plugin-react-refresh";
import tseslint from "typescript-eslint";
import importX from "eslint-plugin-import-x";
import prettierConfig from "eslint-config-prettier";

export default tseslint.config(
  { ignores: ["dist", "coverage"] },
  {
    extends: [js.configs.recommended, ...tseslint.configs.recommended],
    files: ["**/*.{ts,tsx}"],
    languageOptions: {
      ecmaVersion: 2022,
      globals: globals.browser,
    },
    plugins: {
      "react-hooks": reactHooks,
      "react-refresh": reactRefresh,
      "import-x": importX,
    },
    rules: {
      "react-hooks/rules-of-hooks": "error",
      "react-hooks/exhaustive-deps": "warn",
      "react-refresh/only-export-components": [
        "warn",
        { allowConstantExport: true },
      ],
      "import-x/order": "error",
    },
  },
  prettierConfig,
);

ไล่ดูการตัดสินใจสำคัญทีละจุด:

  • ignores: ["dist", "coverage"] — ไม่ lint โฟลเดอร์ผลลัพธ์: dist คือไฟล์ build ส่วน coverage คือรายงานความครอบคลุมของเทสต์ (จะโผล่มาในช่วงบทการทดสอบ) ทั้งคู่เป็นโค้ดที่เครื่องสร้าง ไม่ใช่ของที่เราต้องตรวจ
  • extends — เริ่มจากชุดกฎ recommended ของ JavaScript และ TypeScript เป็นฐาน แล้วค่อยเติมกฎเฉพาะทางทับลงไป
  • files: ["**/*.{ts,tsx}"] — กฎชุดนี้ใช้กับไฟล์ TypeScript ทั้งหมดในโปรเจกต์
  • react-hooks/rules-of-hooks: "error" — เรียก hook ใน if หรือ loop เมื่อไหร่ ตกม้าตายทันที นี่คือกฎที่จับบั๊กประเภท "useState คืน state ผิดชิ้น" ก่อนที่คุณจะเสียเวลาครึ่งวันไล่หา ส่วน exhaustive-deps เป็นแค่ warn เพราะบางกรณี (ที่เข้าใจดีแล้วจริง ๆ) เราตั้งใจไม่ใส่ dependency ครบ
  • react-refresh/only-export-components — HMR ของ Vite จะ swap component แบบไม่รีเฟรชทั้งหน้าได้ ก็ต่อเมื่อไฟล์นั้น export แต่ component กฎนี้เตือนเมื่อเราแอบ export อย่างอื่นปนไปด้วย (allowConstantExport ผ่อนผันให้ค่าคงที่)
  • import-x/order: "error" — บังคับให้เรียง import เป็นกลุ่มตามชนิด: ของ Node ก่อน ตามด้วย external packages แล้วจึงไฟล์ในโปรเจกต์ ทุกไฟล์ทั้งโปรเจกต์จะอ่านหัวไฟล์ได้เป็นจังหวะเดียวกันหมด และกฎนี้แก้ให้อัตโนมัติได้ด้วย eslint --fix
  • prettierConfig อยู่ท้ายสุด — ตำแหน่งนี้สำคัญ: มันคือชุด "ปิดสวิตช์" กฎเชิงรูปแบบทั้งหมดของ ESLint (เว้นวรรค, comma, quote ฯลฯ) เพราะงานจัดรูปแบบเป็นหน้าที่ของ Prettier และใน flat config ตัวที่มาทีหลังชนะ — ถ้าเอาไปวางก่อน กฎ format ของชุด recommended จะกลับมามีผลและสองเครื่องมือจะแย่งกันแก้โค้ดคนละทาง
💡 ไฟล์นี้ยังไม่ใช่เวอร์ชันสุดท้าย — ในบทที่ 14 เมื่อเราเริ่มใช้ TanStack Query เราจะกลับมาเพิ่ม @tanstack/eslint-plugin-query อีกสองบรรทัด เพื่อให้ ESLint ช่วยจับการใช้ query ผิดท่าด้วย

ตั้งค่า Prettier

สร้างไฟล์ .prettierrc.json ที่ root ของโปรเจกต์:

{}

ใช่ครับ object ว่าง — และนั่นคือความตั้งใจ ค่า default ของ Prettier (double quote, semicolon, trailing comma ฯลฯ) คือ style ที่คนส่วนใหญ่ในวงการใช้ตรงกันอยู่แล้ว การไม่ปรับแต่งอะไรเลยคือการประกาศว่า "เราใช้มาตรฐานกลาง จบ ไม่เถียงกันเรื่องนี้อีก" ส่วนตัวไฟล์ต้องมีอยู่แม้จะว่าง เพราะมันคือสัญญาณให้ editor และเครื่องมือต่าง ๆ รู้ว่าโปรเจกต์นี้ใช้ Prettier

ตามด้วย .prettierignore บอกว่าไฟล์ไหนไม่ต้องจัดรูปแบบ:

dist
coverage
package-lock.json
.superpowers

dist กับ coverage คือผลลัพธ์ที่เครื่องสร้างเช่นเดิม package-lock.json เป็นไฟล์ที่ npm เขียนเองและยาวหลักหมื่นบรรทัด — อย่าไปยุ่งกับมัน ส่วน .superpowers เป็นโฟลเดอร์เครื่องมือภายในของ repo ต้นฉบับ ใส่ตามไว้ให้ตรงกัน ไม่มีผลข้างเคียงอะไร

เพิ่ม npm scripts

เครื่องมือจะถูกใช้จริงก็ต่อเมื่อเรียกได้ง่าย แก้ส่วน scripts ใน package.json ให้เป็นแบบนี้:

"scripts": {
  "dev": "vite",
  "build": "tsc -b && vite build",
  "lint": "eslint .",
  "format": "prettier --write .",
  "format:check": "prettier --check .",
  "typecheck": "tsc -b",
  "preview": "vite preview"
},

ของใหม่สามตัวคือ format (ให้ Prettier จัดรูปแบบทุกไฟล์แล้วเขียนทับ), format:check (แค่ตรวจว่ามีไฟล์ไหนยังไม่ถูกจัด — เหมาะกับใช้ใน CI ที่ไม่ควรแก้ไฟล์เอง) และ typecheck (รัน TypeScript compiler ตรวจ type ทั้งโปรเจกต์โดยไม่ build อะไรออกมา) ส่วน scripts ของการเทสต์จะตามมาในบทที่ 26

ได้ scripts แล้วก็ใช้เลย — จัดรูปแบบไฟล์ทั้งโปรเจกต์หนึ่งรอบ แล้วตรวจว่า lint ผ่าน:

npm run format
npm run lint
⚠️ อยากให้เครื่องมือทำงานแบบไม่ต้องนึกถึงมันเลย ให้ตั้ง editor ช่วย: ใน VS Code ติดตั้ง extension ESLint กับ Prettier - Code formatter แล้วเปิด "Format On Save" เท่านี้ทุกครั้งที่กด save โค้ดจะเรียงสวยเองและเส้นแดง/เหลืองของ ESLint จะโผล่ตั้งแต่ตอนพิมพ์

Path alias: จบปัญหา ../../../

อีกไม่กี่บทข้างหน้า โปรเจกต์เราจะมีโฟลเดอร์ซ้อนกันหลายชั้น และ component ที่อยู่ลึก ๆ จะต้อง import ของกลางด้วยเส้นทางสยอง ๆ อย่าง import { Pagination } from "../../../shared/types/generic.type"; — นับจุดผิดทีเดียวก็พังแล้ว และย้ายไฟล์ทีหนึ่งก็ต้องไล่แก้กันระนาว เราจะตั้ง alias ให้ @/ แปลว่า "จาก src/ เสมอ" เพื่อให้เขียนแบบนี้แทนได้:

import { Pagination } from "@/shared/types/generic.type";

ต้องตั้งค่าสองที่ เพราะมีเครื่องมือสองตัวที่ต้อง resolve เส้นทางไฟล์: Vite ตอน bundle จริง และ TypeScript ตอนตรวจ type กับตอน editor ช่วย autocomplete ตั้งที่เดียวอีกตัวจะมองไม่เห็น

ที่แรก — เขียน vite.config.ts ให้เป็นแบบนี้:

import { fileURLToPath, URL } from "node:url";
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

// https://vite.dev/config/
export default defineConfig({
  plugins: [react()],
  resolve: {
    alias: {
      "@": fileURLToPath(new URL("./src", import.meta.url)),
    },
  },
});

ท่อนที่หน้าตาแปลกคือ fileURLToPath(new URL("./src", import.meta.url)) — มันคือวิธีสร้าง absolute path ไปยังโฟลเดอร์ src ในแบบที่ ES Modules รองรับ: import.meta.url คือตำแหน่งของไฟล์ config นี้เอง, new URL("./src", ...) ต่อเส้นทางแบบ relative จากตรงนั้น แล้ว fileURLToPath แปลงกลับเป็น path ปกติของระบบไฟล์ (สมัยก่อนใช้ __dirname ทำแบบนี้ แต่ตัวแปรนั้นไม่มีในไฟล์แบบ ES Module อย่างของเรา)

💡 vite.config.ts จะถูกเติมอีกสองรอบในคอร์สนี้: บทที่ 09 เพิ่มบล็อก legacy เพื่อแก้เรื่อง CJS interop ของ Vite 8 และบทที่ 26 เพิ่มบล็อก test สำหรับ Vitest — ตอนนี้ไฟล์มีแค่นี้ ถูกต้องแล้ว

ที่ที่สอง — เปิด tsconfig.app.json แล้วเพิ่ม paths เข้าไปใน compilerOptions (ค่าอื่นที่ template ให้มา คงไว้ทั้งหมด):

{
  "compilerOptions": {
    // ...ค่าเดิมจาก template คงไว้ทั้งหมด...

    "paths": {
      "@/*": ["./src/*"]
    }
  },
  "include": ["src"]
}

อ่านว่า: import ใดที่ขึ้นต้นด้วย @/ ให้ TypeScript ตามไปหาไฟล์ใน ./src/ — ตรงกันเป๊ะกับที่บอก Vite ไว้ เราจะได้เริ่มใช้ @/ จริงจังตั้งแต่บทที่ 06 เมื่อโครงโฟลเดอร์เต็มรูปแบบมาถึง

💡 Checkpoint: รันสามคำสั่งนี้แล้วทุกตัวต้องจบแบบไม่มี error: npm run lint, npm run format:check และ npm run typecheck จากนั้น npm run dev — หน้า React E-commerce App ต้องยังขึ้นเหมือนเดิม ถ้า lint ฟ้องเรื่องลำดับ import ในไฟล์ไหน ลอง npx eslint . --fix ให้มันจัดเรียงให้อัตโนมัติ
ก่อนหน้า: สร้างโปรเจกต์ด้วย Vite สารบัญบทเรียน ถัดไป: โครงสร้าง SCSS
