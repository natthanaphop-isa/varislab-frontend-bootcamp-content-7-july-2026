บทเรียน 14 · ชั้นข้อมูลสินค้า (Products Data Layer)

Query Key Factory และ queryOptions

Query Factories

ชิ้นสุดท้ายของชั้นข้อมูลสินค้ามาถึงแล้ว เรามีฟังก์ชัน typed ครบสี่ตัวจากบทที่แล้ว และมี QueryClientProvider ครอบแอปไว้ตั้งแต่บทเรียน 08 — เหลือแค่ตอบคำถามเดียว: หน้าเพจควรเรียก useQuery อย่างไร? คำตอบแบบที่เราเรียนมาจากคอร์ส React พื้นฐาน คือเขียน queryKey กับ queryFn สด ๆ ในคอมโพเนนต์ ซึ่งใช้ได้ดีในแอปที่มี query สองสามตัว แต่แอปของเรากำลังจะมี query กระจายอยู่หลายหน้า และวิธีนั้นมีกับดักซ่อนอยู่

ปัญหา: query key ที่เขียนด้วยมือจะค่อย ๆ เพี้ยน

ลองดูสถานการณ์สมมติที่เกิดจริงในทุกทีม — สองหน้าต้องการข้อมูลชุดเดียวกัน แต่เขียนคนละวัน:

// หน้า Home — เขียนวันจันทร์
useQuery({
  queryKey: ["products", page],
  queryFn: () => getProducts({ page }),
});

// หน้า Category — เขียนวันพฤหัส
useQuery({
  queryKey: ["product-list", category, page],
  queryFn: () => getProductsByCategory({ category, page }),
});

โค้ดนี้รันได้ ไม่มี error ไม่มี warning แต่มันป่วยแล้ว:

  • ข้อมูลชนิดเดียวกัน สะกด key คนละแบบ — "products" กับ "product-list" ทำให้คำสั่งกวาดล้าง cache อย่าง invalidateQueries({ queryKey: ["products"] }) โดนแค่ตัวแรก ตัวที่สองรอดไปหน้าตาเฉย แสดงข้อมูลเก่าต่อไปเงียบ ๆ
  • สะกดผิดคือ cache ใหม่ ไม่ใช่ error — พิมพ์ "prodcuts" ที่ไหนสักแห่ง TypeScript ไม่ว่าอะไรเลย เพราะ key เป็นแค่ array ธรรมดา ผลคือได้ cache แยกอีกก้อน ยิง request ซ้ำโดยไม่มีใครรู้
  • ลืมใส่ตัวแปรใน key — ถ้า queryFn ใช้ page แต่ key ไม่มี page การเปลี่ยนหน้าจะไม่ refetch เพราะ TanStack Query มองว่า key เดิม = ข้อมูลเดิม นี่คือ bug คลาสสิกที่ debug ยากที่สุดตระกูลหนึ่ง

ต้นตอของทั้งหมดคือ query key เป็น "ข้อความอิสระ" ที่ไม่มีแหล่งความจริงกลาง วิธีแก้แบบมืออาชีพมีสองท่อนประกอบกัน:

  • Query key factory — object เดียวที่เป็นเจ้าของ key ทุกตัวของฟีเจอร์ ใครอยากได้ key ต้องมาขอจากที่นี่ จะไม่มีการสะกดมือกระจายตามหน้าอีกเลย
  • queryOptions() — helper ของ TanStack Query v5 ที่มัด queryKey + queryFn + option อื่น ๆ เป็นก้อนเดียวที่ type ครบสมบูรณ์ หน้าเพจแค่ useQuery(productQueries.list()) แล้วได้ data ที่ TypeScript รู้ type เป๊ะ ๆ โดยไม่ต้องประกาศอะไรเพิ่ม

สร้าง src/features/products/queries.ts

สร้างไฟล์ queries.ts ใน src/features/products:

import { keepPreviousData, queryOptions } from "@tanstack/react-query";
import {
  CategoryProductsParams,
  ProductListParams,
  getCategories,
  getProduct,
  getProducts,
  getProductsByCategory,
} from "./api";

export const productKeys = {
  all: ["products"] as const,
  lists: () => [...productKeys.all, "list"] as const,
  list: (params: ProductListParams) =>
    [...productKeys.lists(), params] as const,
  byCategory: (params: CategoryProductsParams) =>
    [...productKeys.lists(), "category", params] as const,
  categories: () => [...productKeys.all, "categories"] as const,
  details: () => [...productKeys.all, "detail"] as const,
  detail: (id: string | number) =>
    [...productKeys.details(), String(id)] as const,
};

export const productQueries = {
  list: (params: ProductListParams = {}) =>
    queryOptions({
      queryKey: productKeys.list(params),
      queryFn: () => getProducts(params),
    }),

  byCategory: (params: CategoryProductsParams) =>
    queryOptions({
      queryKey: productKeys.byCategory(params),
      queryFn: () => getProductsByCategory(params),
      placeholderData: keepPreviousData,
    }),

  categories: () =>
    queryOptions({
      queryKey: productKeys.categories(),
      queryFn: getCategories,
      staleTime: 5 * 60 * 1000,
    }),

  detail: (id: string | number) =>
    queryOptions({
      queryKey: productKeys.detail(id),
      queryFn: () => getProduct(id),
    }),
};

productKeys — ลำดับชั้นของ key

สังเกตว่าแต่ละ key ไม่ได้เขียนขึ้นมาลอย ๆ แต่ต่อยอดจาก key ชั้นบนด้วย spread (...) เสมอ ทำให้ key ทั้งหมดเรียงเป็นต้นไม้:

  • productKeys.all → ["products"] — รากของทุกอย่างเกี่ยวกับสินค้า
  • productKeys.lists() → ["products", "list"] — กิ่ง "รายการสินค้า" ทุกแบบ
  • productKeys.list({ page: 1 }) → ["products", "list", { page: 1 }] — รายการรวม หน้า 1
  • productKeys.byCategory({ category: "beauty", page: 2 }) → ["products", "list", "category", { category: "beauty", page: 2 }] — รายการตามหมวด
  • productKeys.categories() → ["products", "categories"] — รายชื่อหมวดหมู่
  • productKeys.details() → ["products", "detail"] — กิ่ง "รายละเอียดสินค้า"
  • productKeys.detail(42) → ["products", "detail", "42"] — สินค้าชิ้นเดียว

โครงต้นไม้นี้ไม่ใช่ความสวยงามเปล่า ๆ — มันคือกลไก เพราะเวลา TanStack Query จับคู่ key มันจับแบบ prefix: สั่ง invalidateQueries({ queryKey: productKeys.lists() }) ครั้งเดียว รายการทุกแบบทุกหน้าโดนหมด (ทั้ง list และ byCategory เพราะขึ้นต้นด้วย ["products", "list"] เหมือนกัน) แต่ cache ของหน้ารายละเอียดสินค้าไม่ถูกแตะเลย อยากล้างทุกอย่างของฟีเจอร์นี้ก็ productKeys.all จบ — ระดับความละเอียดของการ invalidate ออกแบบไว้ล่วงหน้าแล้วในโครงต้นไม้

ส่วน as const ที่ห้อยท้ายทุกบรรทัด บอก TypeScript ว่า array เหล่านี้เป็น tuple ค่าตายตัว ไม่ใช่ string[] กว้าง ๆ ซึ่งทำให้ type ของแต่ละ key แม่นยำและ queryOptions นำไป infer ต่อได้เต็มที่

productQueries — เมนูสำเร็จรูปสี่จาน

productQueries คือชั้นที่หน้าเพจจะใช้จริง แต่ละตัว return ผลของ queryOptions() ซึ่งมัด key (จาก factory) + ฟังก์ชัน (จาก api.ts) + พฤติกรรมเฉพาะตัว เป็นก้อนเดียว มาดูการตัดสินใจในแต่ละจาน:

list — จานพื้นฐานที่สุด: key คู่กับ getProducts ตรง ๆ ให้ default = {} เพื่อให้หน้า Home เรียก productQueries.list() เปล่า ๆ ได้เลย สังเกตว่า params ก้อนเดียวกันถูกส่งเข้าทั้ง key และ queryFn — ตัวแปรที่มีผลต่อข้อมูลอยู่ใน key ครบเสมอโดยโครงสร้าง ไม่ใช่โดยความจำของคนเขียน bug "ลืมใส่ตัวแปรใน key" ตายตั้งแต่เกิด

byCategory กับ placeholderData: keepPreviousData — จานนี้แก้ปัญหา UX ที่ชื่อว่า pagination flash: ลองนึกภาพหน้า Category ตอนผู้ใช้กดไปหน้า 2 — เลขหน้าที่เปลี่ยนทำให้ query key เปลี่ยน กลายเป็น query ใหม่เอี่ยมที่ยังไม่มีข้อมูลใน cache ผลคือ data เป็น undefined ชั่วขณะ รายการสินค้าทั้งกริดหายวับกลายเป็น spinner แล้วค่อยเด้งกลับมา — จอกะพริบ ความสูงหน้ากระโดด scroll หลุด ทุกครั้งที่เปลี่ยนหน้า keepPreviousData สั่งว่า "ระหว่างรอข้อมูลหน้าใหม่ ให้โชว์ข้อมูลหน้าเก่าไปพลาง ๆ" หน้าจอเลยนิ่งสนิท พอของใหม่มาถึงค่อยสลับเนียน ๆ (ข้อมูลเก่าที่ยืมมาโชว์เป็นแค่ placeholder — ไม่ได้ถูกบันทึกเป็น cache ของ key ใหม่) ในบทเรียน 17 เราจะใช้ flag isPlaceholderData หรี่ความทึบของกริดระหว่างรอ เพื่อบอกผู้ใช้ว่ากำลังโหลดอยู่นะ โดยไม่ต้องพรากเนื้อหาไปจากตา

categories กับ staleTime: 5 * 60 * 1000 — รายชื่อหมวดหมู่เป็นข้อมูลที่แทบไม่เคยเปลี่ยน แต่ถูกใช้แสดงเมนูซึ่งโผล่บ่อยมาก ถ้าปล่อยตาม default ของแอป (60 วินาที ที่ตั้งไว้ใน queryClient.ts บทเรียน 08) เราจะ refetch รายชื่อหมวดหมู่ถี่เกินเหตุ จานนี้จึง override เป็น 5 นาที: ภายในช่วงนั้นทุกหน้าที่ mount ขึ้นมาได้ข้อมูลจาก cache ทันทีโดยไม่ยิง network เลย นี่คือความสวยของ queryOptions — นโยบาย cache ของข้อมูลแต่ละชนิดถูกประกาศไว้ที่เดียวคู่กับตัว query ไม่ใช่ให้แต่ละหน้าไปตั้งกันเอง

detail กับ String(id) — จำที่ getProduct รับ string | number ได้ไหม? id จาก URL param เป็น string "42" แต่ id จาก object สินค้าเป็น number 42 สำหรับ TanStack Query สองค่านี้คือ key คนละตัว! ถ้าไม่จัดการ เราจะได้ cache สองก้อนของสินค้าชิ้นเดียวกัน และยิง request ซ้ำฟรี ๆ factory จึง normalize ด้วย String(id) ตรงชั้น key — ไม่ว่าใครส่งอะไรมา key ลงเอยเป็น ["products", "detail", "42"] ก้อนเดียวเสมอ ปัญหาทั้งตระกูลถูกปิดที่บรรทัดเดียว

💡 ตำแหน่งของไฟล์นี้ก็สื่อสารเจตนา: queries.ts อยู่ใน features/products ประกบ api.ts และ types.ts — ฟีเจอร์สินค้าเป็นเจ้าของข้อมูลของตัวเองครบวงจร ตั้งแต่รูปร่างข้อมูล การเรียก ยันนโยบาย cache ภายหลังถ้าเพิ่มฟีเจอร์ที่มีข้อมูลฝั่ง server ของตัวเอง ก็ทำซ้ำแพตเทิร์นเดิมนี้ได้เลย

ติดตั้งยามเฝ้าระวัง: ESLint plugin ของ TanStack Query

factory ป้องกัน key เพี้ยนได้เกือบหมด แต่ "เกือบ" ยังไม่พอสำหรับเรา — TanStack ทำ ESLint plugin ที่ตรวจจับการใช้ query ผิดท่าให้ตั้งแต่ตอนเขียน ติดตั้งเป็น dev dependency:

npm i -D @tanstack/eslint-plugin-query

แล้วเปิด eslint.config.js ที่เราตั้งไว้ตั้งแต่บทเรียน 03 มาเพิ่มของสองจุด: import ตัว plugin และ spread config แนะนำของมันเข้าไปใน extends ไฟล์ฉบับสมบูรณ์เป็นแบบนี้ (สองบรรทัดที่เพิ่มคือบรรทัด import pluginQuery กับบรรทัด ...pluginQuery.configs["flat/recommended"] — ที่เหลือเหมือนเดิมทุกตัวอักษร):

import js from "@eslint/js";
import globals from "globals";
import reactHooks from "eslint-plugin-react-hooks";
import reactRefresh from "eslint-plugin-react-refresh";
import tseslint from "typescript-eslint";
import importX from "eslint-plugin-import-x";
import pluginQuery from "@tanstack/eslint-plugin-query";
import prettierConfig from "eslint-config-prettier";

export default tseslint.config(
  { ignores: ["dist", "coverage"] },
  {
    extends: [
      js.configs.recommended,
      ...tseslint.configs.recommended,
      ...pluginQuery.configs["flat/recommended"],
    ],
    files: ["**/*.{ts,tsx}"],
    languageOptions: {
      ecmaVersion: 2022,
      globals: globals.browser,
    },
    plugins: {
      "react-hooks": reactHooks,
      "react-refresh": reactRefresh,
      "import-x": importX,
    },
    rules: {
      "react-hooks/rules-of-hooks": "error",
      "react-hooks/exhaustive-deps": "warn",
      "react-refresh/only-export-components": [
        "warn",
        { allowConstantExport: true },
      ],
      "import-x/order": "error",
    },
  },
  prettierConfig,
);

ตัวอย่างกฎที่ได้มา:

  • @tanstack/query/exhaustive-deps — ตัวจับ bug คลาสสิกที่เล่าไว้ต้นบท: ถ้า queryFn ใช้ตัวแปรที่ไม่อยู่ใน queryKey จะโดนขีดเส้นเตือนทันทีตั้งแต่ใน editor ไม่ต้องรอไปงงตอนหน้าเว็บไม่ refetch
  • @tanstack/query/stable-query-client — เตือนถ้าเผลอสร้าง QueryClient ข้างในคอมโพเนนต์ ซึ่งจะทำให้ cache ถูกโยนทิ้งทุก re-render (เราทำถูกไปแล้วในบทเรียน 08 — สร้างไว้นอกคอมโพเนนต์)
  • @tanstack/query/no-rest-destructuring — เตือนการ destructure ผลของ useQuery ด้วย rest spread ซึ่งทำลายการ optimize เรื่อง re-render ของ TanStack Query

ลองรันดู:

npm run lint

ต้องผ่านเงียบ ๆ ไม่มี error — และต่อจากนี้ทุกครั้งที่ใครเขียน query ผิดท่า lint จะฟ้องก่อนโค้ดจะถึงเบราว์เซอร์เสียอีก

Checkpoint: ชั้นข้อมูลเสร็จสมบูรณ์

💡 npm run lint และ npm run typecheck ต้องผ่านทั้งคู่ ส่วนหน้าเว็บ? ยังเหมือนเดิมทุกประการ — และนั่นตั้งใจแล้ว สามบทที่ผ่านมาเราวางท่อครบทั้งเส้น: client.ts คุยกับ server และ normalize error → types.ts ให้รูปร่างข้อมูล → api.ts ให้ฟังก์ชันเรียกแบบ typed → queries.ts ให้ cache ที่มีระเบียบ สิ่งเดียวที่ยังไม่มีคือคนเปิดก๊อก ในบทหน้าเราจะเริ่มสร้างคอมโพเนนต์รายการสินค้า แล้วหลังจากนั้นหน้า Home ทั้งหน้าจะมีชีวิตขึ้นมาด้วยโค้ดสั้นแค่ useQuery(productQueries.list()) — ความง่ายขนาดนั้นคือรางวัลของงานระบบที่เราเพิ่งทำเสร็จ
