สร้าง Button, Input และ RadioInput

Button, Input & RadioInput

โครงแอปของเราพร้อมแล้ว — router พาไปแต่ละหน้าได้, MainLayout มี Header/Footer ครบ และ QueryClient รอให้เราเรียกใช้ ก่อนจะลงมือสร้างหน้าเพจจริง เราจะหยุดสามบทเพื่อสร้างคอมโพเนนต์กลาง (shared components) — ชิ้นส่วน UI ที่หลายหน้าหยิบไปใช้ซ้ำ เหมือนทีมจริงที่มักสร้าง design system เล็ก ๆ ก่อนประกอบหน้าเพจ

ทำไมไม่เขียน <button> สด ๆ ในแต่ละหน้าไปเลย? เพราะปุ่มของเราต้องหน้าตาเหมือนกันทุกหน้า มี loading state เหมือนกัน มี icon ได้เหมือนกัน — ถ้าเขียนซ้ำ 5 ที่ วันที่ดีไซน์เปลี่ยน คุณต้องไล่แก้ 5 ที่ แต่ถ้ามี Button กลางตัวเดียว แก้ที่เดียวจบ ในบทนี้เราจะสร้างสามตัวแรก และแต่ละตัวจะถูกใช้จริงในบทถัด ๆ ไป:

  • Button — ปุ่มหลักของทั้งแอป: Add to Cart ในหน้า Product, ปุ่มในหน้า Cart และปุ่มยืนยันในหน้า Checkout
  • Input — ช่องกรอกข้อความ จะเป็นพระเอกของฟอร์มที่อยู่จัดส่งในบทที่ 23 (คู่กับ react-hook-form)
  • RadioInput — ตัวเลือกแบบ radio สำหรับเลือกวิธีจัดส่งและวิธีชำระเงินในบทที่ 24

ข้อควรรู้ก่อนเริ่ม: บทนี้ (และอีกสองบทถัดไป) สร้างเสร็จแล้วหน้าเว็บจะยังไม่เปลี่ยน เพราะยังไม่มีหน้าไหนเรียกใช้คอมโพเนนต์เหล่านี้ นี่เป็นเรื่องปกติของการทำงานแบบ bottom-up — เราสร้างเครื่องมือให้พร้อมก่อน แล้วบทสร้างหน้าเพจจะไหลลื่นมาก

ติดตั้ง react-spinners

Button ของเราจะมี loading state — ตอนกำลังส่งคำสั่งซื้อ ปุ่มจะเปลี่ยนเป็นวงกลมหมุน ๆ เราไม่ต้องเขียน animation เอง ใช้ไลบรารี react-spinners ที่มี spinner สำเร็จรูปให้เลือกหลายแบบ:

npm i react-spinners

ทางแยกสำคัญ: Vite 8 กับ CJS interop

ก่อนใช้ react-spinners ได้ เราต้องแก้ config หนึ่งจุด และนี่คือบทเรียนของจริงที่คุณจะเจอในงาน: ไลบรารีบางตัวใน npm ยังเผยแพร่เป็น CommonJS (CJS) ซึ่งเป็นระบบ module รุ่นเก่าของ Node (แบบ require/module.exports) ในขณะที่โปรเจกต์เราเป็น ES Modules (ESM แบบ import/export) เต็มตัว — package.json ของเราประกาศ "type": "module" ไว้ตั้งแต่ scaffold

ปัญหาคือไลบรารี CJS ที่ compile มาจาก TypeScript/Babel จะเก็บของที่ export ไว้ที่ module.exports.default (ธรรมเนียมที่เรียกว่า esModuleInterop) — Vite รุ่นก่อน ๆ ใจดี แกะ .default ให้เราอัตโนมัติเวลาเขียน import ClipLoader from "react-spinners/ClipLoader" แต่ Vite 8 (ที่เปลี่ยนมาใช้ Rolldown เป็น bundler) เข้มงวดขึ้น: default import ของ CJS ในโปรเจกต์ ESM จะได้ก้อน module ทั้งก้อนแทนที่จะเป็นตัวคอมโพเนนต์ พอ React พยายาม render object แทนที่จะเป็น function ก็จะพังตอนรันด้วย error หน้าตาแบบนี้:

Uncaught Error: Element type is invalid: expected a string (for built-in components)
or a class/function (for composite components) but got: object.

ทางแก้คือเปิด option ที่ Vite เตรียมไว้ให้สำหรับกรณีนี้โดยเฉพาะ เปิด vite.config.ts แล้วเพิ่ม block legacy เข้าไป ไฟล์ทั้งไฟล์ตอนนี้จะเป็นแบบนี้ (เราเก็บ comment ภาษาอังกฤษไว้ด้วย — เดี๋ยวอธิบายว่าทำไม):

import { fileURLToPath, URL } from "node:url";
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

// https://vite.dev/config/
export default defineConfig({
  plugins: [react()],
  resolve: {
    alias: {
      "@": fileURLToPath(new URL("./src", import.meta.url)),
    },
  },
  // Vite 8 (Rolldown) tightened CJS default-import interop: since this project's
  // package.json has "type": "module", default imports of CJS deps that use the
  // TS/Babel esModuleInterop convention (module.exports.default, e.g.
  // react-spinners, react-paginate) now resolve to the whole module object
  // instead of unwrapping `.default`, breaking those components at runtime
  // ("Element type is invalid"). This restores the pre-Vite-8 unwrapping
  // behavior. See https://vite.dev/guide/migration (CJS interop changes).
  legacy: {
    inconsistentCjsInterop: true,
  },
});

legacy.inconsistentCjsInterop: true บอก Vite ว่า "ขอพฤติกรรมแกะ .default แบบเดิมกลับมา" ซึ่งทำให้ react-spinners (และ react-paginate ที่เราจะติดตั้งบทหน้า) กลับมา render ได้ตามปกติ

ส่วนเหตุผลที่เราเขียน comment ยาว ๆ กำกับไว้: config บรรทัดนี้อ่านแล้วไม่มีทางเดาได้เลยว่ามีไว้ทำไม ถ้าไม่มี comment อีกหกเดือนข้างหน้า (หรือเพื่อนร่วมทีม) อาจลบทิ้งเพราะคิดว่าไม่จำเป็น แล้วแอปจะพังแบบงง ๆ — การจดเหตุผลของ workaround ไว้ตรงที่มันอยู่คือนิสัยที่ทีมจริงคาดหวัง

💡 ไฟล์ vite.config.ts ยังไม่จบแค่นี้ — บทที่ 26 (ติดตั้งชุดทดสอบ) เราจะกลับมาเพิ่ม block test สำหรับ Vitest อีกครั้ง

รู้จัก SCSS Modules ก่อนเขียนคอมโพเนนต์แรก

ในบทที่ 4 เราวางโครง SCSS ส่วนกลางไว้แล้ว (variables, utility classes อย่าง flex, py-15, fw-medium) — พวกนั้นเป็น global CSS คือประกาศครั้งเดียวใช้ได้ทุกที่ ซึ่งเหมาะกับ utility ที่ตั้งใจให้ใช้ร่วมกันทั้งแอป แต่พอเป็น style เฉพาะของคอมโพเนนต์ global CSS มีปัญหาคลาสสิก: class ชนกัน ลองนึกภาพ .button ของเรากับ .button ของอีกไฟล์ที่เพื่อนเขียน — ตัวที่โหลดทีหลังจะทับตัวแรกเงียบ ๆ โดยไม่มีใครเตือน

CSS Modules แก้ปัญหานี้ที่ราก: ตั้งชื่อไฟล์ลงท้ายด้วย .module.scss แล้ว Vite จะเปลี่ยนพฤติกรรมของไฟล์นั้นทันที — แทนที่ class จะไปอยู่ใน scope global ตัว build tool จะเปลี่ยนชื่อ class ให้ไม่ซ้ำใคร เช่น .button ใน Button.module.scss อาจกลายเป็น _button_x7f2k_3 ตอนรันจริง แล้วเราเข้าถึงชื่อที่ถูกแปลงแล้วผ่านการ import:

import styles from "./Button.module.scss";

// styles คือ object เช่น { button: "_button_x7f2k_3", primary: "_primary_x7f2k_11" }
<button className={styles.button}>

ผลคือ style ของแต่ละคอมโพเนนต์ถูก scope อยู่กับตัวเอง 100% — ต่อให้สิบไฟล์ตั้งชื่อ class ว่า .button เหมือนกันหมดก็ไม่มีทางชนกัน และจำได้ไหมว่าบทที่ 4 เราสร้าง src/shared/types/global.d.ts ที่ประกาศ declare module "*.scss" ไว้ — นั่นแหละคือสิ่งที่ทำให้ TypeScript เข้าใจว่าการ import ไฟล์ .module.scss ได้ object กลับมา

สรุปกติกาที่เราจะใช้ทั้งโปรเจกต์: utility class ใช้แบบ global, style เฉพาะตัวใช้ CSS Modules — สองอย่างนี้อยู่ร่วมกันได้สบายมาก และคุณจะเห็นมันผสมกันในคอมโพเนนต์แรกของเราเดี๋ยวนี้เลย

Button

สร้างโฟลเดอร์สำหรับคอมโพเนนต์กลางชุดนี้ ธรรมเนียมของโปรเจกต์เราคือหนึ่งคอมโพเนนต์ = หนึ่งโฟลเดอร์ (เก็บ .tsx คู่กับ .module.scss ของมัน):

mkdir -p src/shared/components/Button

เริ่มจาก style ก่อน สร้าง src/shared/components/Button/Button.module.scss:

@use "../../../styles/variables";

.button {
  border: none;

  &:disabled {
    cursor: not-allowed;
    opacity: 0.6;
  }

  &.primary {
    background-color: variables.$primary-color;
    color: #fff;

    &:hover:not(:disabled) {
      background-color: variables.$blue02;
    }
  }

  .icon {
    font-size: 18px;
  }
}

สังเกตว่าไฟล์ module ก็ยัง @use ตัวแปรกลางจากบทที่ 4 ได้ตามปกติ — ที่ถูก scope คือชื่อ class ไม่ใช่ตัวแปร ส่วน &.primary คือ selector ที่จับตอน element มีทั้งสอง class พร้อมกัน (เราจะประกอบมันใน JSX เดี๋ยวนี้) และ &:hover:not(:disabled) กันไม่ให้ปุ่มที่ถูก disable เปลี่ยนสีตอน hover ให้ผู้ใช้เข้าใจผิดว่ากดได้

ต่อด้วยตัวคอมโพเนนต์ src/shared/components/Button/Button.tsx:

import React from "react";
import { FontAwesomeIcon } from "@fortawesome/react-fontawesome";
import { IconProp } from "@fortawesome/fontawesome-svg-core";
import ClipLoader from "react-spinners/ClipLoader";
import styles from "./Button.module.scss";

interface ButtonProps {
  onClick?: () => void;
  icon?: IconProp; // Accepts FontAwesomeIcon props
  variant?: "primary";
  disabled?: boolean;
  isLoading?: boolean;
  children: React.ReactNode;
  type?: "button" | "reset" | "submit";
  className?: string;
}

const Button: React.FC<ButtonProps> = ({
  type = "button",
  onClick,
  icon,
  children,
  variant = "primary",
  disabled = false,
  isLoading = false,
  className = "",
}) => {
  return (
    <button
      type={type}
      className={`${styles.button} ${styles[variant]} ${className} flex flex-center py-15 px-20 fw-medium pointer`}
      onClick={() => {
        if (onClick) {
          onClick();
        }
      }}
      disabled={disabled}
    >
      {isLoading ? (
        <ClipLoader size={20} aria-label="Loading Spinner" color="white" />
      ) : (
        <>
          {icon && (
            <FontAwesomeIcon icon={icon} className={`${styles.icon} mr-10`} />
          )}
          {children}
        </>
      )}
    </button>
  );
};

export default Button;

ไล่ดูการตัดสินใจสำคัญทีละจุด:

  • ButtonProps เลือก props เอง ไม่รับหมด — เราประกาศ interface ที่คัดเฉพาะ props ที่อยากเปิดให้ใช้: onClick, type, disabled, className บวกของที่เราเพิ่มเอง (icon, variant, isLoading) วิธีนี้ทำให้ API ของปุ่มแคบและควบคุมได้ — ใครจะใช้ปุ่มเราต้องใช้ตามกติกา สังเกตว่า type เรา default เป็น "button" เพราะค่า default จริงของ HTML คือ "submit" ซึ่งเป็นต้นเหตุ bug คลาสสิก "กดปุ่มแล้วฟอร์ม submit เอง" (เดี๋ยวบท Input จะเห็นแนวทางตรงข้าม: รับ props native ทั้งหมด — สองแนวทางนี้ใช้คู่กันได้ตามสถานการณ์)
  • styles[variant] — lookup แบบ dynamic: ถ้า variant คือ "primary" ก็หยิบ styles.primary ตอนนี้เรามี variant เดียว แต่โครงนี้พร้อมรองรับ "secondary" ในอนาคตโดยแก้แค่ type กับ SCSS
  • ผสม class สามชั้น — ใน template literal เดียวมีทั้ง class จาก module (styles.button), class ที่คนเรียกส่งเพิ่มมา (className) และ utility กลางจากบทที่ 4 (flex flex-center py-15 px-20 fw-medium pointer) — นี่คือภาพจริงของกติกา "module สำหรับของเฉพาะตัว, utility สำหรับของทั่วไป"
  • isLoading สลับเนื้อในปุ่ม — ตอนโหลด เนื้อหาปกติ (icon + ข้อความ) หายไป เหลือ ClipLoader จาก react-spinners หมุนแทน พร้อม aria-label ให้ screen reader รู้ว่ากำลังโหลด
  • icon?: IconProp — รับ icon ของ Font Awesome (ที่ติดตั้งไว้บทที่ 7) แบบ optional โดยใช้ type IconProp ของไลบรารีเอง คนเรียกส่ง icon={faCartShopping} มาได้เลยแล้ว TypeScript ตรวจให้ว่าเป็น icon จริง

แล้วสร้าง src/shared/components/Input/Input.tsx:

import React, { forwardRef } from "react";
import styles from "./Input.module.scss";

interface InputProps extends React.InputHTMLAttributes<HTMLInputElement> {
  label?: string;
  error?: string;
}

const Input = forwardRef<HTMLInputElement, InputProps>(
  ({ label, error, ...props }, ref) => {
    return (
      <div className={styles.inputWrapper}>
        {label && <label className="mb-5 inline-block">{label}</label>}
        <input ref={ref} className={styles.input} {...props} />
        {error && <p className={`${styles.error} fs-12 mt-5`}>{error}</p>}
      </div>
    );
  },
);

Input.displayName = "Input";

export default Input;

ไฟล์นี้สั้นแต่อัดแน่นด้วยแพตเทิร์นสำคัญสองเรื่อง:

เรื่องแรก: extend props ของ input จริง — ต่างจาก Button ที่คัด props เอง InputProps ประกาศ extends React.InputHTMLAttributes<HTMLInputElement> แปลว่า Input ของเรารับ prop ทุกตัวที่ <input> ธรรมดารับได้ (placeholder, type, name, value, onChange, autoComplete, …) โดยไม่ต้องประกาศเองสักตัว แล้วเราเติมของเราเพิ่มสองตัว: label (ข้อความกำกับช่อง) กับ error (ข้อความ validation สีแดงใต้ช่อง) ตอน destructure เราดึง label กับ error ออกมาใช้เอง ส่วนที่เหลือ (...props) เททั้งก้อนลง <input> ผ่าน spread — ทำไมช่องกรอกถึงเหมาะกับแนวทางนี้? เพราะ input มี attribute ที่จำเป็นเยอะมากและเดาล่วงหน้าไม่ได้หมด การ extend จึงประหยัดกว่าและไม่ต้องกลับมาแก้ interface ทุกครั้งที่ฟอร์มต้องการ attribute ใหม่

เรื่องที่สอง: forwardRef — โดยปกติ function component รับ ref ตรง ๆ ไม่ได้ ใครพยายามส่ง ref มาจะเข้าไม่ถึง DOM ข้างใน forwardRef คือวิธีบอก React ว่า "ref ที่ส่งมาให้ฉัน ช่วยส่งต่อไปที่ <input> จริง ๆ ข้างในด้วย" แล้วทำไมต้องมี? เฉลยล่วงหน้า: บทที่ 23 เราจะใช้ react-hook-form ซึ่งทำงานกับฟอร์มผ่านการเกาะ ref ของ input จริงในหน้าเว็บ (จำแนวคิด uncontrolled form จากคอร์ส React พื้นฐาน ได้ไหม? react-hook-form คือ uncontrolled แบบจัดเต็ม) ถ้า Input ของเราไม่ forward ref ให้ react-hook-form จะอ่านค่าจากช่องไม่ได้เลย ส่วน Input.displayName = "Input" ช่วยให้ React DevTools แสดงชื่อคอมโพเนนต์สวย ๆ แทนที่จะเป็น ForwardRef เฉย ๆ

💡 React 19 อนุญาตให้ส่ง ref เป็น prop ธรรมดาได้แล้ว แต่ forwardRef ยังใช้ได้ปกติและยังเป็นแพตเทิร์นที่คุณจะเจอบ่อยที่สุดในโค้ดจริงตอนนี้ — อ่านท่านี้ให้ขาด แล้วคุณจะอ่าน codebase ของบริษัทไหนก็รู้เรื่อง

ตัวสุดท้ายของบทนี้เบาที่สุด สร้าง src/shared/components/RadioInput/RadioInput.tsx — สังเกตว่าคอมโพเนนต์นี้ไม่มีไฟล์ .module.scss เพราะหน้าตาของมันจัดได้ครบด้วย utility class ล้วน ๆ ไม่มี style เฉพาะตัวเลย ก็ไม่ต้องสร้างไฟล์เปล่าให้รก:

import React from "react";

interface RadioInputProps {
  id: string;
  name: string;
  checked: boolean;
  onChange: () => void;
  label: React.ReactNode;
  className?: string;
}

const RadioInput: React.FC<RadioInputProps> = ({
  id,
  name,
  checked,
  onChange,
  label,
  className = "",
}) => {
  return (
    <div className={`flex align-item-start ${className}`}>
      <input
        className="mr-10 mt-3"
        type="radio"
        id={id}
        name={name}
        checked={checked}
        onChange={onChange}
      />
      <label htmlFor={id}>{label}</label>
    </div>
  );
};

export default RadioInput;

จุดที่น่าสนใจ:

  • controlled radio เต็มรูปแบบ — เหมือน radio ในบท Hooks ของคอร์ส React พื้นฐาน เป๊ะ: ตัวคอมโพเนนต์ไม่เก็บ state เอง คนเรียกส่ง checked มาบอกว่าติ๊กอยู่ไหม และส่ง onChange มารับเหตุการณ์ตอนผู้ใช้เลือก — state จริงอยู่ที่หน้า Checkout ที่เป็นเจ้าของข้อมูล
  • label: React.ReactNode — ไม่ใช่ string! แปลว่า label ยัด JSX ได้ทั้งก้อน บทที่ 24 เราจะใช้ประโยชน์เต็ม ๆ: ตัวเลือกวิธีจัดส่งมี label เป็นชื่อ + ราคา + คำอธิบาย จัดรูปแบบสวย ๆ ในก้อนเดียว
  • id + htmlFor — ผูก label กับ input เข้าด้วยกัน ผู้ใช้กดที่ข้อความ (ซึ่งพื้นที่ใหญ่กว่าวงกลมเยอะ) แล้ว radio ติ๊กให้ ส่วน name ทำให้ radio หลายตัวรู้ว่าอยู่กลุ่มเดียวกัน — เลือกได้ทีละตัว

มองย้อนกลับไป สามคอมโพเนนต์ = สามแนวทางออกแบบ props ที่ต่างกัน: Button คัด props เองเพื่อคุม API, Input extend props ของ native element เพื่อความยืดหยุ่น, RadioInput ประกาศ contract แบบ controlled ล้วน ทั้งสามท่าถูกหมด — ศิลปะอยู่ที่เลือกท่าให้เข้ากับงาน
