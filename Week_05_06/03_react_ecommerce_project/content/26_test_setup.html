ติดตั้งชุดทดสอบ: Vitest, React Testing Library และ MSW

Test Setup

แอปของเราครบทุกฟีเจอร์แล้ว — ดูสินค้าได้ เพิ่มลงตะกร้าได้ สั่งซื้อได้ แต่ตอนนี้ถ้าถามว่า "กล้าแก้ cartReducer ไหม? กล้าอัปเกรด TanStack Query ไหม?" คำตอบที่ซื่อสัตย์คือ "ไม่ค่อยกล้า เพราะต้องไล่คลิกทุกหน้าเองเพื่อเช็คว่าไม่มีอะไรพัง" ชุดเทสต์ (test suite) คือสิ่งที่เปลี่ยนคำตอบนั้นเป็น "กล้า เพราะกด npm run test แล้วรู้ผลใน 10 วินาที" — และนี่คือสิ่งที่เราจะสร้างกันใน 4 บทสุดท้ายของช่วงนี้

ในคอร์ส React พื้นฐาน คุณเขียนเทสต์ด้วย Vitest และ React Testing Library มาแล้ว บทนี้เราจะติดตั้งเครื่องมือชุดเดิมนั้นเข้าโปรเจกต์นี้ พร้อมเพื่อนใหม่หนึ่งตัวคือ MSW (Mock Service Worker) แล้ววางโครงสร้างพื้นฐานทั้งหมดที่บทถัด ๆ ไปจะใช้: ข้อมูลปลอม, API ปลอม และ helper สำหรับ render ทั้งแอปในเทสต์ บทนี้ยังไม่มีเทสต์จริงสักตัว — แต่พอวางฐานเสร็จ สามบทถัดไปจะไหลลื่นมาก

ทำไมต้อง MSW — mock ที่ชั้น network ไม่ใช่ชั้นโค้ด

ปัญหาคลาสสิกของการเทสต์แอปที่คุยกับ API: เราไม่อยากให้เทสต์ยิง request ไปที่ dummyjson.com จริง ๆ เพราะมันช้า, พังเมื่อเน็ตล่ม และข้อมูลบนเซิร์ฟเวอร์เปลี่ยนได้ตลอดเวลา (เทสต์ที่ assert ว่าสินค้าชื่ออะไรจะพังทันทีที่ dummyjson แก้ข้อมูล) เราจึงต้อง "ปลอม" API — คำถามคือปลอมที่ชั้นไหน

วิธีที่หลายคนนึกถึงก่อนคือ mock ตัว axios ไปเลยด้วย vi.mock — แต่คิดดูว่าเราเสียอะไรไป: apiClient ของเรามี interceptor ที่แปลง error ทุกแบบให้เป็น ApiError (บทที่ 12) ถ้าเรา mock axios ทิ้ง โค้ดส่วนนั้นไม่ได้รันเลยในเทสต์ — interceptor จะพังยับแค่ไหนเทสต์ก็เขียวอยู่ดี เท่ากับเราเทสต์ "ของปลอมที่เราสร้างขึ้นเอง" ไม่ใช่โค้ดจริง

MSW เลือกปลอมที่ชั้นต่ำที่สุดเท่าที่จะทำได้: ชั้น network มันดักจับ HTTP request ตอนที่กำลังจะออกจากโปรเซส แล้วตอบกลับด้วยข้อมูลที่เรากำหนด ผลคือโค้ดฝั่งเราวิ่งครบทั้งสายของจริง — queryOptions → ฟังก์ชันใน api.ts → axios → interceptor — มีแค่ "เซิร์ฟเวอร์ปลายทาง" เท่านั้นที่เป็นของปลอม เทสต์ที่ผ่านจึงบอกได้เต็มปากว่าชั้นข้อมูลทั้งชั้นทำงานถูกจริง

ติดตั้ง dependencies

ทั้งหมดเป็น devDependencies เพราะใช้ตอนพัฒนาเท่านั้น ไม่ถูก bundle ไปกับแอป:

npm install -D vitest jsdom @testing-library/react @testing-library/jest-dom @testing-library/user-event msw @types/node
  • vitest — test runner ตัวเดิมจากคอร์ส React พื้นฐาน ข้อดีใหญ่คือมันใช้ config และ transform pipeline ของ Vite ทำให้ path alias @/ และ SCSS Modules ในโค้ดเราทำงานในเทสต์ได้เลยโดยไม่ต้องตั้งค่าเพิ่ม
  • jsdom — DOM จำลองที่รันใน Node ทำให้ component ของเรา render ได้โดยไม่ต้องเปิดเบราว์เซอร์จริง
  • @testing-library/react — render, screen, renderHook, waitFor สำหรับเทสต์ component และ hook แบบเน้นพฤติกรรมที่ผู้ใช้เห็น
  • @testing-library/jest-dom — matcher เพิ่มเติมอย่าง toBeInTheDocument() ที่ทำให้ assertion อ่านเป็นภาษาคนมากขึ้น
  • @testing-library/user-event — จำลองการพิมพ์และการคลิกแบบเหมือนผู้ใช้จริง (จะได้ใช้หนัก ๆ ในบทที่ 29)
  • msw — พระเอกใหม่ของเรา: เซิร์ฟเวอร์ปลอมที่ชั้น network
  • @types/node — type ของ Node API (เราใช้ node:url ใน vite.config.ts อยู่แล้ว และไฟล์ config ฝั่งเทสต์จะถูกเช็ค type เข้มขึ้น)

เช็คใน package.json — ควรเห็นเจ็ดรายการใหม่แทรกเข้าไปใน devDependencies (เวอร์ชันของคุณอาจใหม่กว่านี้เล็กน้อย):

"@testing-library/jest-dom": "^7.0.0",
"@testing-library/react": "^16.3.2",
"@testing-library/user-event": "^14.6.1",
"@types/node": "^22.20.1",

เพิ่ม test block ใน vite.config.ts

Vitest อ่าน config จากไฟล์เดียวกับ Vite นี่คือครั้งสุดท้ายที่เราแก้ vite.config.ts — เพิ่มบรรทัด /// <reference types="vitest/config" /> ที่บรรทัดแรกสุด และ block test ต่อท้าย legacy จนได้ไฟล์ฉบับสมบูรณ์ดังนี้:

/// <reference types="vitest/config" />
import { fileURLToPath, URL } from "node:url";
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

// https://vite.dev/config/
export default defineConfig({
  plugins: [react()],
  resolve: {
    alias: {
      "@": fileURLToPath(new URL("./src", import.meta.url)),
    },
  },
  // Vite 8 (Rolldown) tightened CJS default-import interop: since this project's
  // package.json has "type": "module", default imports of CJS deps that use the
  // TS/Babel esModuleInterop convention (module.exports.default, e.g.
  // react-spinners, react-paginate) now resolve to the whole module object
  // instead of unwrapping `.default`, breaking those components at runtime
  // ("Element type is invalid"). This restores the pre-Vite-8 unwrapping
  // behavior. See https://vite.dev/guide/migration (CJS interop changes).
  legacy: {
    inconsistentCjsInterop: true,
  },
  test: {
    environment: "jsdom",
    globals: true,
    setupFiles: "./src/test/setup.ts",
    // MSW handlers hardcode the host, so tests must not depend on .env
    env: { VITE_API_BASE_URL: "https://dummyjson.com" },
  },
});

ไล่ดูทีละส่วน:

  • /// <reference types="vitest/config" /> — โดยปกติ type ของ defineConfig ไม่รู้จัก key ชื่อ test (มันเป็นของ Vitest ไม่ใช่ Vite) triple-slash directive บรรทัดนี้ดึง type เสริมของ Vitest เข้ามา ทำให้ทุก field ใน block test มี autocomplete และถูกเช็ค type
  • environment: "jsdom" — ให้ทุกเทสต์รันใน DOM จำลอง เราจะได้ document, window และ localStorage ใช้เหมือนอยู่ในเบราว์เซอร์
  • globals: true — ทำให้ describe, it, expect เป็น global ไม่ต้อง import ในทุกไฟล์เทสต์ (แบบเดียวกับที่คุ้นเคยในคอร์ส React พื้นฐาน)
  • setupFiles — ไฟล์ที่ Vitest รันก่อนไฟล์เทสต์ทุกไฟล์ เดี๋ยวเราจะสร้างมันเพื่อเปิด/ปิด MSW server
  • env: { VITE_API_BASE_URL: "https://dummyjson.com" } — บังคับค่า env ตอนรันเทสต์ให้ตายตัว สังเกต comment ในไฟล์: MSW handlers hardcode the host, so tests must not depend on .env — handler ของ MSW จะ match request ด้วย URL เต็ม https://dummyjson.com/... ถ้าเราปล่อยให้ apiClient อ่าน baseURL จากไฟล์ .env ของแต่ละเครื่อง วันไหนใครแก้ .env ไปชี้ host อื่น request จะไม่ match handler แล้วเทสต์พังทั้งชุดแบบงง ๆ การ hardcode ตรงนี้ทำให้เทสต์ deterministic: รันที่เครื่องไหนก็ได้ผลเหมือนกัน

เพิ่ม scripts

เพิ่มสอง script สุดท้ายเข้าไปใน package.json จน block scripts เป็นแบบนี้:

"scripts": {
  "dev": "vite",
  "build": "tsc -b && vite build",
  "lint": "eslint .",
  "format": "prettier --write .",
  "format:check": "prettier --check .",
  "typecheck": "tsc -b",
  "preview": "vite preview",
  "test": "vitest run",
  "test:watch": "vitest"
},

vitest run รันครบหนึ่งรอบแล้วจบ (เหมาะกับการเช็คก่อน commit และรันบน CI) ส่วน vitest เฉย ๆ คือ watch mode — มันจะรันเฉพาะเทสต์ที่เกี่ยวกับไฟล์ที่เพิ่งแก้ใหม่ทุกครั้งที่กด save เหมาะมากตอนเขียนเทสต์ในสามบทถัดไป

src/test/msw/handlers.ts — endpoint ปลอมรูปร่างเดียวกับ dummyjson

import { http, HttpResponse } from "msw";
import { categories, makeProduct, makeProductsResponse } from "./fixtures";

const BASE = "https://dummyjson.com";

export const handlers = [
  http.get(`${BASE}/products/categories`, () => HttpResponse.json(categories)),

  http.get(`${BASE}/products/category/:slug`, ({ request, params }) => {
    const url = new URL(request.url);
    const limit = Number(url.searchParams.get("limit") ?? 20);
    const skip = Number(url.searchParams.get("skip") ?? 0);
    return HttpResponse.json(
      makeProductsResponse(limit, {
        skip,
        limit,
        products: Array.from({ length: limit }, (_, i) =>
          makeProduct({
            id: skip + i + 1,
            title: `${String(params.slug)} product ${skip + i + 1}`,
            category: String(params.slug),
          }),
        ),
      }),
    );
  }),

  http.get(`${BASE}/products/:id`, ({ params }) =>
    HttpResponse.json(makeProduct({ id: Number(params.id) })),
  ),

  http.get(`${BASE}/products`, ({ request }) => {
    const url = new URL(request.url);
    const limit = Number(url.searchParams.get("limit") ?? 20);
    const skip = Number(url.searchParams.get("skip") ?? 0);
    return HttpResponse.json(makeProductsResponse(limit, { skip, limit }));
  }),

  http.post(`${BASE}/carts/add`, async ({ request }) => {
    const body = (await request.json()) as Record<string, unknown>;
    return HttpResponse.json({ id: 1, ...body }, { status: 201 });
  }),
];

แต่ละ handler คือ endpoint ปลอมหนึ่งตัว หน้าตาเหมือน route ของเซิร์ฟเวอร์เลย: http.get(url, resolver) โดย resolver คืน HttpResponse.json(...) จุดที่ควรสังเกต:

  • handler ไม่ได้แค่คืนของตายตัว — มันอ่าน request จริง ๆ ตัว /products/category/:slug อ่านทั้ง params.slug จาก path และ limit/skip จาก query string แล้วประกอบเป็นชื่อสินค้าอย่าง beauty product 21 (id เริ่มจาก skip + 1) — เท่ากับว่าถ้าเทสต์เห็นข้อความนี้ แปลว่า pagination ของเราคำนวณ skip แล้วส่งไปกับ request ถูกต้องจริง ตลอดทั้งสาย
  • ลำดับใน array มีความหมาย — MSW ลอง match จากบนลงล่าง /products/categories ต้องอยู่ก่อน /products/:id ไม่งั้นคำว่า categories จะถูกจับเป็นค่า :id ไปเสียก่อน
  • POST /carts/add — endpoint ที่ placeOrder ของ checkout ใช้ ตอบ 201 พร้อม echo body กลับมา เหมือนพฤติกรรมของ dummyjson จริง

src/test/msw/server.ts

import { setupServer } from "msw/node";
import { handlers } from "./handlers";

export const server = setupServer(...handlers);

ไฟล์นี้สั้นแต่มีจุดสำคัญ: เรา import จาก msw/node เพราะเทสต์รันใน Node ไม่ใช่เบราว์เซอร์ (ชื่อ "Service Worker" มาจากโหมดที่ MSW รันในเบราว์เซอร์จริง — ใน Node มันใช้วิธีดักจับ request คนละกลไกแต่ API หน้าตาเดียวกัน) setupServer(...handlers) สร้างเซิร์ฟเวอร์ปลอมพร้อม handler ตั้งต้นทั้งห้าตัว

src/test/setup.ts — วงจรชีวิตของเซิร์ฟเวอร์ปลอม

/// <reference types="vitest/globals" />
// Triple-slash directive here (not tsconfig types) because tsconfig.app.json's custom
// typeRoots breaks "types": ["vitest/globals"] resolution (TS2688); ambient globals
// propagate program-wide from this file.
import "@testing-library/jest-dom/vitest";
import { server } from "./msw/server";

beforeAll(() => server.listen({ onUnhandledRequest: "error" }));
afterEach(() => {
  server.resetHandlers();
  localStorage.clear();
});
afterAll(() => server.close());

นี่คือไฟล์ที่ setupFiles ใน vite.config ชี้ถึง — Vitest รันมันก่อนไฟล์เทสต์ทุกไฟล์ แต่ละบรรทัดทำหน้าที่ชัดเจน:

  • triple-slash vitest/globals — TypeScript ต้องรู้จัก describe/it/expect ที่เราเปิดเป็น global ไว้ ทางปกติคือใส่ "types": ["vitest/globals"] ใน tsconfig แต่ comment ในไฟล์อธิบายไว้ว่าโปรเจกต์เรากำหนด typeRoots เอง (เพื่อให้ src/shared/types เป็นที่อยู่ของ global type — บทที่ 4) ซึ่งทำให้วิธีนั้นพังด้วย error TS2688 เราจึงประกาศผ่าน directive ในไฟล์นี้แทน — ambient type ที่ประกาศในไฟล์หนึ่งจะมีผลทั้งโปรแกรม
  • import "@testing-library/jest-dom/vitest" — ลงทะเบียน matcher อย่าง toBeInTheDocument() เข้ากับ expect ของ Vitest ครั้งเดียว ใช้ได้ทุกไฟล์
  • beforeAll — เปิดเซิร์ฟเวอร์ปลอมก่อนเทสต์ทั้งหมด ตัวเลือก onUnhandledRequest: "error" สำคัญมาก: request ไหนที่ไม่ match handler สักตัว เทสต์จะพังทันทีพร้อมบอก URL แทนที่จะเงียบ ๆ หลุดออกอินเทอร์เน็ตจริง — ทำให้ typo ใน URL หรือ endpoint ที่ลืมทำ handler โผล่มาให้เห็นเร็วที่สุด
  • afterEach — ล้างสองอย่างหลังเทสต์ทุกตัว: resetHandlers() ถอด handler ชั่วคราวที่เทสต์นั้นยัดเพิ่มด้วย server.use(...) (จะเจอในบทหน้า) และ localStorage.clear() ล้างตะกร้าที่ค้างอยู่ — จำได้ไหมว่า cart ของเรา persist ลง localStorage ถ้าไม่ล้าง ตะกร้าจากเทสต์หนึ่งจะรั่วไปโผล่ในเทสต์ถัดไป
  • afterAll — คืนระบบ network สู่สภาพปกติเมื่อเสร็จทั้งไฟล์

src/test/utils.tsx — QueryClient สำหรับเทสต์

import { ReactNode } from "react";
import { QueryClient, QueryClientProvider } from "@tanstack/react-query";

export function createTestQueryClient() {
  return new QueryClient({
    defaultOptions: { queries: { retry: false } },
  });
}

export function createQueryWrapper() {
  const queryClient = createTestQueryClient();
  return function Wrapper({ children }: { children: ReactNode }) {
    return (
      <QueryClientProvider client={queryClient}>{children}</QueryClientProvider>
    );
  };
}

โค้ดที่ใช้ TanStack Query ต้องอยู่ใต้ QueryClientProvider เสมอ — ในเทสต์ก็เช่นกัน แต่เราไม่ใช้ queryClient ตัวจริงจาก src/app/queryClient.ts ด้วยสองเหตุผล: หนึ่ง ตัวจริงตั้ง retry: 1 ซึ่งแปลว่าเทสต์กรณี error ต้องรอ query ลองซ้ำจนครบก่อนถึงจะ fail — ช้าและอาจเกิน timeout เราจึงตั้ง retry: false ให้พังทันทีที่ควรพัง สอง createTestQueryClient() สร้าง client ใหม่ทุกครั้งที่ถูกเรียก — เพื่อให้ cache ของแต่ละเทสต์แยกขาดจากกัน (เหตุผลเต็ม ๆ รออยู่บทที่ 28) ส่วน createQueryWrapper() ห่อมันเป็น component สำหรับส่งเข้า option wrapper ของ renderHook

src/test/renderRoute.tsx — render ทั้งแอปในเทสต์

import { QueryClientProvider } from "@tanstack/react-query";
import { render } from "@testing-library/react";
import { createMemoryRouter } from "react-router";
import { RouterProvider } from "react-router/dom";
import { createTestQueryClient } from "./utils";
import { routes } from "@/app/router";
import { CartProvider } from "@/features/cart/store/CartProvider";

export function renderRoute(initialPath: string) {
  const router = createMemoryRouter(routes, {
    initialEntries: [initialPath],
  });

  return {
    router,
    ...render(
      <QueryClientProvider client={createTestQueryClient()}>
        <CartProvider>
          <RouterProvider router={router} />
        </CartProvider>
      </QueryClientProvider>,
    ),
  };
}

helper ตัวสุดท้ายนี้คือหัวใจของ integration test ในบทที่ 29 — เรียก renderRoute("/cart") แล้วได้แอปทั้งแอปเปิดอยู่ที่หน้า Cart:

  • createMemoryRouter(routes, ...) — router ที่เก็บ history ไว้ในหน่วยความจำแทน address bar (ซึ่งไม่มีอยู่จริงใน jsdom) สังเกตว่ามันรับ routes — array เดียวกับที่ createBrowserRouter ตัวจริงใช้ นี่แหละเหตุผลที่บทที่ 6 เรา export routes แยกจาก router: route table จริงทุกเส้นทาง รวมทั้ง MainLayout และ errorElement ถูกเทสต์ด้วย ไม่ใช่ฉบับจำลอง ส่วน initialEntries คือ URL เริ่มต้น
  • provider ครบชุดเหมือนแอปจริง — QueryClientProvider (ฉบับเทสต์) และ CartProvider ตัวจริง ซ้อนกันตามลำดับเดียวกับ providers.tsx — CartProvider จะ lazy init จาก localStorage เหมือนเดิม เปิดช่องให้เทสต์ "แอบใส่ของในตะกร้า" ได้ด้วยการเขียน localStorage ก่อน render
  • คืน router ออกมาด้วย — เทสต์จะได้ assert เรื่อง navigation ได้ เช่น เช็คว่าหลังสั่งซื้อสำเร็จ router.state.location.pathname กลายเป็น /order/success จริง (บทที่ 29 ใช้แน่นอน)
