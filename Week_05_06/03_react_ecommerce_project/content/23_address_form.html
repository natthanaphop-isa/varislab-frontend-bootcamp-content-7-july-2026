บทเรียน 23 · ชำระเงิน (Checkout)

ฟอร์มที่อยู่ด้วย react-hook-form

Address Form

schema พร้อมแล้วจากบทที่แล้ว บทนี้เราจะสร้างฟอร์มที่อยู่จัดส่งตัวจริง — และได้เจอกับ react-hook-form ซึ่งเป็น library จัดการฟอร์มที่ครองตลาด React มาหลายปี ก่อนเขียนโค้ด มาทำความเข้าใจกันก่อนว่ามันแก้ปัญหาอะไร เพราะปรัชญาของมันต่อตรงกับสิ่งที่คุณเรียนมาแล้วในคอร์ส React พื้นฐาน พอดี

ปรัชญาของ react-hook-form: uncontrolled แต่สบายกว่า

ย้อนกลับไปบท Hooks และบท Uncontrolled Forms ของคอร์ส React พื้นฐาน — ตอนนั้นเราสรุปกันว่าฟอร์มมาตรฐานควรเป็น uncontrolled: ปล่อยให้ DOM เก็บค่าของ input เอง แล้วค่อยไปอ่านค่าทีเดียวตอน submit ส่วน controlled form (ผูกทุก input กับ useState) เก็บไว้ใช้เมื่อจำเป็นจริง ๆ เช่นต้องตอบสนองทุกตัวอักษรที่พิมพ์ เหตุผลเรื่อง performance ก็ชัดเจน: controlled form ทำให้ทั้งฟอร์ม re-render ทุกครั้งที่กดคีย์บอร์ดหนึ่งที ในขณะที่ uncontrolled ไม่ re-render อะไรเลยระหว่างพิมพ์

แต่ uncontrolled แบบดิบ ๆ (อ่าน FormData เองตอน submit) ก็มีงานน่าเบื่อ: ต้องแปลงค่าเป็น type ที่ถูกต้องเอง ต้อง validate เอง ต้องจัดการแสดง error ต่อ field เอง react-hook-form คือ uncontrolled form ที่มีคนทำงานน่าเบื่อพวกนั้นให้หมดแล้ว:

  • input ยังเป็น uncontrolled — react-hook-form เกาะกับ DOM ผ่าน ref ค่าอยู่ใน DOM ไม่อยู่ใน state → พิมพ์เร็วแค่ไหนก็ไม่มี re-render
  • ตอน submit มันรวบรวมค่าทุก field, ส่งให้ resolver validate (ของเราคือ zod schema จากบทที่แล้ว), แล้วเรียก callback ของเราพร้อมข้อมูลที่ผ่านการตรวจและมี type ถูกต้องแล้วเท่านั้น
  • ถ้าไม่ผ่าน มันเก็บข้อความ error รายฟิลด์ไว้ใน formState.errors แล้ว re-render เฉพาะตอนที่ชุด error เปลี่ยนจริง ๆ

สร้าง CheckoutAddressForm

สร้างไฟล์ src/features/checkout/components/CheckoutAddressForm/CheckoutAddressForm.tsx:

import React from "react";
import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";
import {
  checkoutAddressSchema,
  CheckoutAddressFormData,
} from "@/features/checkout/schema";
import Input from "@/shared/components/Input/Input";
import Button from "@/shared/components/Button/Button";

export type { CheckoutAddressFormData };

interface CheckoutAddressFormProps {
  onSubmit: (data: CheckoutAddressFormData) => void;
}

const CheckoutAddressForm: React.FC<CheckoutAddressFormProps> = ({
  onSubmit,
}) => {
  const {
    register,
    handleSubmit,
    formState: { errors },
  } = useForm<CheckoutAddressFormData>({
    resolver: zodResolver(checkoutAddressSchema),
  });

  const onFormSubmit = (data: CheckoutAddressFormData) => {
    onSubmit({ ...data });
  };

  return (
    <form onSubmit={handleSubmit(onFormSubmit)}>
      <div className="mb-15">
        <Input
          label="Address"
          type="text"
          placeholder="Enter Address"
          {...register("address")}
          error={errors.address?.message}
        />
      </div>

      <div className="flex gap-15 mb-15">
        <div className="width-50">
          <Input
            label="Email"
            type="email"
            placeholder="Enter Email"
            {...register("email")}
            error={errors.email?.message}
          />
        </div>
        <div className="width-50">
          <Input
            label="Phone Number"
            type="text"
            placeholder="Enter Phone Number"
            {...register("phone")}
            error={errors.phone?.message}
          />
        </div>
      </div>

      <Button type="submit">Submit</Button>
    </form>
  );
};

export default CheckoutAddressForm;

ไฟล์ไม่ยาว แต่ทุกบรรทัดมีเรื่องเล่า ไล่จากบนลงล่าง:

useForm + zodResolver

const {
  register,
  handleSubmit,
  formState: { errors },
} = useForm<CheckoutAddressFormData>({
  resolver: zodResolver(checkoutAddressSchema),
});

useForm คือศูนย์บัญชาการของฟอร์ม เราส่ง generic CheckoutAddressFormData (type ที่ z.infer สกัดให้เมื่อบทที่แล้ว) เพื่อบอกว่าฟอร์มนี้มี field อะไรบ้าง — ผลคือ register("address") จะ autocomplete ชื่อ field ให้ และถ้าพิมพ์ register("adress") TypeScript ฟ้องทันที ส่วน resolver: zodResolver(checkoutAddressSchema) คือการเสียบ schema ของเราเข้าเป็นกติกา validate ของฟอร์ม — สังเกตว่าเราไม่ต้องเขียน logic validate ในคอมโพเนนต์นี้เลยแม้แต่บรรทัดเดียว กติกาทั้งหมดอยู่ใน schema.ts ที่เดียว

register — จุดเชื่อมระหว่าง input กับฟอร์ม

{...register("address")} เป็นท่าที่ดูแปลกตาตอนแรก แต่จริง ๆ ตรงไปตรงมา: register("address") คืน object ที่มี name, ref, onChange, onBlur แล้วเรา spread ทั้งก้อนลงบน <Input /> — เท่ากับสมัคร input ตัวนี้เข้าระบบของ react-hook-form ตัวสำคัญที่สุดในก้อนคือ ref: react-hook-form ใช้มันจับ DOM element ตรง ๆ เพื่ออ่านค่าโดยไม่ต้องพึ่ง state

และตรงนี้เองที่การบ้านเก่าของเราออกดอกผล — จำได้ไหมว่าตอนสร้าง Input ในบทที่ 09 เราห่อมันด้วย forwardRef? เพราะ ref ไม่ใช่ prop ธรรมดา คอมโพเนนต์ที่รับ ref แล้วส่งต่อให้ <input> ข้างในต้องประกาศตัวเป็น forwardRef อย่างชัดเจน ถ้าตอนนั้นเราสร้าง Input แบบธรรมดา วันนี้ register จะจับ input ข้างในไม่ได้ และฟอร์มจะอ่านค่าไม่ออกแบบเงียบ ๆ อาการงง ๆ อันดับหนึ่งของคนใช้ react-hook-form กับ custom component คือเรื่องนี้แหละ

ส่วน error={errors.address?.message} คือปลายทางของ zod: ถ้า validate ไม่ผ่าน ข้อความอย่าง "Address is required" จะมาอยู่ใน errors.address.message แล้ว Input ของเรา (ที่มี prop error เตรียมไว้ตั้งแต่บทที่ 09 เช่นกัน) ก็แสดงเป็นตัวหนังสือสีแดงใต้ช่องกรอก — ใช้ optional chaining (?.) เพราะตอนที่ยังไม่มี error errors.address เป็น undefined

handleSubmit — ด่านตรวจก่อนถึงมือเรา

<form onSubmit={handleSubmit(onFormSubmit)}> ไม่ได้เรียก onFormSubmit ตรง ๆ แต่ห่อไว้ด้วย handleSubmit ซึ่งทำงานตามลำดับนี้ทุกครั้งที่ผู้ใช้กด submit:

  1. กัน default behavior ของเบราว์เซอร์ (ไม่ต้องเขียน e.preventDefault() เอง)
  2. รวบรวมค่าทุก field จาก DOM แล้วส่งให้ zod ตรวจ
  3. ถ้าไม่ผ่าน — เติม formState.errors แล้ว re-render ให้ข้อความ error โผล่ onFormSubmit ไม่ถูกเรียกเลย
  4. ถ้าผ่าน — เรียก onFormSubmit(data) โดย data เป็น CheckoutAddressFormData ที่การันตีแล้วว่าครบและถูกต้อง

แปลว่าโค้ดฝั่งเราไม่มีทางได้รับข้อมูลครึ่ง ๆ กลาง ๆ — ทุกเส้นทางที่ onSubmit ของ parent ถูกเรียก ข้อมูลผ่าน schema มาแล้วเสมอ ส่วนใน onFormSubmit เรา spread เป็น object ใหม่ ({ ...data }) ก่อนส่งขึ้นไป เพื่อให้ parent ได้สำเนาของตัวเอง ไม่แชร์ reference กับ object ภายในของ library

เกร็ดอีกสองจุด: export type { CheckoutAddressFormData }; เป็นการ re-export type จาก schema ให้ไฟล์อื่น import ได้จากคอมโพเนนต์นี้โดยตรง (เดี๋ยวเห็น CheckoutAddressBox ใช้ท่านี้) และ class อย่าง mb-15, flex gap-15, width-50 คือ utility classes จาก _utilities.scss ที่เราวางไว้ตั้งแต่บทที่ 04 — สอง input ล่างเลยเรียงเป็นสองคอลัมน์เท่า ๆ กันโดยไม่ต้องมี SCSS module ของตัวเอง

สร้าง CheckoutAddressBox

ฟอร์มอย่างเดียวยังไม่พอ — บนหน้า Checkout จริง เราอยากให้ผู้ใช้กด Submit แล้วเห็นที่อยู่ที่ตัวเองกรอกแสดงยืนยันอยู่ด้านบน พร้อมยังแก้ไขซ้ำได้ นั่นคือหน้าที่ของกล่องห่อชั้นนอก สร้าง src/features/checkout/components/CheckoutAddressBox/CheckoutAddressBox.tsx:

import React from "react";
import styles from "./CheckoutAddressBox.module.scss";
import CheckoutAddressForm, {
  CheckoutAddressFormData,
} from "@/features/checkout/components/CheckoutAddressForm/CheckoutAddressForm";

interface CheckoutAddressBoxProps {
  title: string;
  checkoutAddress: CheckoutAddressFormData | null;
  onUpdateAddress: (data: CheckoutAddressFormData) => void;
}

const CheckoutAddressBox: React.FC<CheckoutAddressBoxProps> = ({
  title,
  checkoutAddress,
  onUpdateAddress,
}) => {
  const onSubmitAddress = (data: CheckoutAddressFormData) => {
    onUpdateAddress(data);
  };

  return (
    <div className={`${styles.container} p-20`}>
      <h3 className="fs-20 pb-10">{title}</h3>
      <hr className="mb-20" />
      {checkoutAddress && (
        <p className="lh-1-5 mb-20">
          <span className="fw-bold">Address</span> : {checkoutAddress.address}
          <br />
          <span className="fw-bold">email</span> : {checkoutAddress.email}
          <br />
          <span className="fw-bold">phone</span> : {checkoutAddress.phone}
        </p>
      )}

      <CheckoutAddressForm onSubmit={onSubmitAddress} />
    </div>
  );
};

export default CheckoutAddressBox;

แล้วก็ style ของกล่อง สร้าง CheckoutAddressBox.module.scss ไว้ข้าง ๆ กัน:

@use "../../../../styles/variables";

.container {

}

อ่านการส่งไม้ต่อของ state ให้ขาด

จุดที่ต้องอ่านให้ขาดคือ state ของ "ที่อยู่ที่ submit แล้ว" อยู่ที่ไหน — คำตอบ: ไม่ได้อยู่ในสองไฟล์นี้เลย ไล่เส้นทางของข้อมูลดู:

  1. ระหว่างพิมพ์ ค่าของแต่ละช่องอยู่ใน DOM ภายใต้การดูแลของ react-hook-form (เรื่องของ CheckoutAddressForm ล้วน ๆ)
  2. กด Submit ผ่าน validation → ฟอร์มเรียก onSubmit → กล่องรับต่อใน onSubmitAddress → ส่งขึ้นไปอีกชั้นผ่าน onUpdateAddress
  3. เจ้าของ state ตัวจริงคือ hook useCheckout ที่เราจะเขียนในบทที่ 25 — มัน setState เก็บที่อยู่ไว้ แล้วส่งกลับลงมาเป็น prop checkoutAddress
  4. กล่องเห็น checkoutAddress ไม่เป็น null แล้ว จึง render บล็อกสรุปที่อยู่ (เงื่อนไข {checkoutAddress && ...}) โผล่เหนือฟอร์ม

นี่คือ pattern lifting state up ที่คุณรู้จักดี: กล่องเป็นแค่ตัวแสดงผลที่ถูกควบคุมจากข้างบน ตัวมันเองไม่มี useState สักตัว ผลพลอยได้ที่เนียนมากคือฟอร์มยัง render อยู่ตลอดแม้ submit ไปแล้ว — ผู้ใช้กรอกใหม่แล้วกด Submit ซ้ำเพื่อแก้ที่อยู่ได้ทุกเมื่อ ค่าที่ submit ล่าสุดจะทับของเดิมเฉย ๆ ไม่ต้องมีปุ่ม Edit ไม่ต้องมี mode สลับไปมา

ส่วนดีไซน์ของกล่อง (พื้นเทา $grey05 + padding จาก utility class p-20 + หัวข้อ + เส้นคั่น) จะกลายเป็นหน้าตามาตรฐานของทุกกล่องบนหน้า Checkout — บทหน้าคุณจะเห็นกล่อง Delivery, Payment และ Summary ใช้สูตรเดียวกันเป๊ะ

🚨 บทนี้ยังทดสอบบนหน้าจอไม่ได้ — Checkout.tsx ของเรายังเป็น stub จากบทที่ 06 อยู่ ยังไม่มีใคร render คอมโพเนนต์ที่เพิ่งสร้าง ทุกอย่างจะถูกประกอบเข้าหน้า Checkout จริงพร้อมกันในบทที่ 25 ตอนนี้ checkpoint ของคุณคือโค้ดต้อง compile ผ่าน ไม่มีเส้นแดง และโครงไฟล์ตรงนี้: features/checkout/components/CheckoutAddressForm/CheckoutAddressForm.tsx, CheckoutAddressBox/CheckoutAddressBox.tsx + .module.scss ถ้าอยากเห็นฟอร์มตอนนี้จริง ๆ จะลองเอา <CheckoutAddressBox title="Shipping Address" checkoutAddress={null} onUpdateAddress={console.log} /> ไปวางชั่วคราวในหน้าไหนสักหน้าก็ได้ แต่อย่าลืมถอดออกก่อนไปบทถัดไป
