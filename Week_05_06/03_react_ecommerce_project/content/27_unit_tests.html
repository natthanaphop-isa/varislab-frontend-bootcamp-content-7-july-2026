Unit Tests: พิสูจน์ logic ทีละฟังก์ชัน

Unit Tests

เราจะเริ่มจากฐานของพีระมิดการทดสอบ: unit test ของฟังก์ชันล้วน ๆ (pure function) — ฟังก์ชันที่รับ input เดิมแล้วคืน output เดิมเสมอ ไม่แตะ DOM ไม่ยิง network เทสต์กลุ่มนี้เขียนง่ายที่สุด รันเร็วที่สุด (หลักมิลลิวินาที) และเวลาพังมันชี้จุดแม่นที่สุด — บอกได้เลยว่าฟังก์ชันไหน กรณีไหน ค่าที่ได้กับค่าที่คาดต่างกันอย่างไร

ธรรมเนียมของโปรเจกต์นี้: ไฟล์เทสต์อยู่ข้างไฟล์ต้นทางเสมอ (co-located) โดยเติม .test เข้าไปในชื่อ เช่น price.utils.ts คู่กับ price.utils.test.ts — เปิดโฟลเดอร์ไหนก็เห็นทันทีว่าไฟล์ไหนมีเทสต์คุ้มกันอยู่ ระหว่างทำบทนี้แนะนำให้เปิด npm run test:watch ทิ้งไว้ จะได้เห็นเทสต์เขียวขึ้นทีละไฟล์

อุ่นเครื่อง: price.utils

เริ่มที่ฟังก์ชันเล็กที่สุดของแอป — calculateOriginalPrice จากบทที่ 15 ที่คำนวณราคาก่อนลดจากราคาปัจจุบันกับเปอร์เซ็นต์ส่วนลด สร้าง src/shared/utils/price.utils.test.ts:

import { calculateOriginalPrice } from "./price.utils";

describe("calculateOriginalPrice", () => {
  it("computes the pre-discount price", () => {
    expect(calculateOriginalPrice(90, 10)).toBeCloseTo(100);
  });

  it("returns the price unchanged when there is no discount", () => {
    expect(calculateOriginalPrice(50, undefined)).toBe(50);
    expect(calculateOriginalPrice(50, 0)).toBe(50);
    expect(calculateOriginalPrice(50, 100)).toBe(50);
  });
});

ทวนโครงสร้างที่เจอมาแล้วในคอร์ส React พื้นฐาน: describe จัดกลุ่มเทสต์ของสิ่งเดียวกัน (ชื่อกลุ่มคือชื่อฟังก์ชัน — เวลาพังจะอ่านรายงานรู้เรื่องทันที), it คือหนึ่งพฤติกรรมที่อยากพิสูจน์ โดยตั้งชื่อให้อ่านต่อกันเป็นประโยค: "calculateOriginalPrice computes the pre-discount price" และ expect คือ assertion — สังเกตว่าทั้งสามอย่างใช้ได้เลยไม่ต้อง import เพราะเราเปิด globals: true ไว้เมื่อบทที่แล้ว

จุดที่น่าสนใจสองจุด:

  • toBeCloseTo(100) ไม่ใช่ toBe(100) — เพราะเลขทศนิยม: 90 / (1 - 10/100) ใน JavaScript ได้ 100.00000000000001 ไม่ใช่ 100 เป๊ะ ๆ ถ้าใช้ toBe เทสต์จะพังทั้งที่ logic ถูก — กฎง่าย ๆ: assertion กับผลหารหรือผลคูณของทศนิยม ให้ใช้ toBeCloseTo
  • เทสต์ที่สองคือเทสต์ขอบเขต (edge case) — ตัวฟังก์ชันเขียน guard ไว้ว่า discount ที่ไม่มีค่า, ≤ 0 หรือ ≥ 100 ให้คืนราคาเดิม เทสต์นี้ยิงทั้งสามกรณีในตาเดียว การเทสต์ edge case พวกนี้แหละคือค่าตัวจริงของ unit test — ทางเดินปกติมักไม่ค่อยพัง ที่พังคือขอบ

pagination.utils

ต่อกันที่คู่ฟังก์ชัน pagination จากบทที่ 13 สร้าง src/shared/utils/pagination.utils.test.ts:

import { calculateOffset, calculateTotalPages } from "./pagination.utils";

describe("calculateOffset", () => {
  it("returns 0 for the first page", () => {
    expect(calculateOffset(1, 20)).toBe(0);
  });

  it("returns limit * (page - 1) for later pages", () => {
    expect(calculateOffset(3, 20)).toBe(40);
  });
});

describe("calculateTotalPages", () => {
  it("rounds up partial pages", () => {
    expect(calculateTotalPages(101, 20)).toBe(6);
  });

  it("handles exact division", () => {
    expect(calculateTotalPages(100, 20)).toBe(5);
  });
});

สองฟังก์ชัน สอง describe ในไฟล์เดียว เคสที่เลือกมาไม่ใช่เคสสุ่ม: calculateOffset เทสต์หน้าแรก (ต้องได้ 0 — off-by-one error ชอบเกิดตรงนี้) กับหน้ากลาง ๆ ส่วน calculateTotalPages เทสต์ทั้งกรณีหารไม่ลงตัว (101 ชิ้น หน้าละ 20 ต้องได้ 6 หน้า — สินค้าชิ้นที่ 101 ต้องมีที่อยู่!) และหารลงตัวพอดี (ต้องได้ 5 ไม่ใช่เผลอปัดขึ้นเป็น 6) ถ้าใครเผลอแก้ Math.ceil เป็น Math.round หรือ Math.floor เทสต์คู่นี้จับได้ทันที

cartReducer — เทสต์ครบทุก action

ถึงตัวสำคัญ: cartReducer คือสมองของตะกร้าสินค้า และมันเป็น pure function เต็มตัว — รับ state กับ action คืน state ใหม่ ไม่มี side effect เลย นั่นทำให้มันเทสต์ง่ายอย่างเหลือเชื่อทั้งที่เป็น logic ที่สำคัญที่สุดชิ้นหนึ่งของแอป สร้าง src/features/cart/store/cartReducer.test.ts:

import { CartActionTypes, CartItem, CartState } from "./CartContext";
import { cartReducer } from "./cartReducer";

const item = (overrides: Partial<CartItem> = {}): CartItem => ({
  id: 1,
  title: "Widget",
  price: 10,
  quantity: 1,
  image: "/widget.png",
  ...overrides,
});

const stateWith = (...items: CartItem[]): CartState => ({ items });

describe("cartReducer", () => {
  it("adds a new item", () => {
    const next = cartReducer(stateWith(), {
      type: CartActionTypes.ADD_TO_CART,
      payload: item(),
    });
    expect(next.items).toEqual([item()]);
  });

  it("merges quantity when the item already exists", () => {
    const next = cartReducer(stateWith(item({ quantity: 2 })), {
      type: CartActionTypes.ADD_TO_CART,
      payload: item({ quantity: 3 }),
    });
    expect(next.items).toEqual([item({ quantity: 5 })]);
  });

  it("removes an item", () => {
    const next = cartReducer(stateWith(item(), item({ id: 2 })), {
      type: CartActionTypes.REMOVE_FROM_CART,
      payload: { id: 1 },
    });
    expect(next.items).toEqual([item({ id: 2 })]);
  });

  it("updates quantity", () => {
    const next = cartReducer(stateWith(item()), {
      type: CartActionTypes.UPDATE_QUANTITY,
      payload: { id: 1, quantity: 7 },
    });
    expect(next.items[0]?.quantity).toBe(7);
  });

  it("clears the cart", () => {
    const next = cartReducer(stateWith(item(), item({ id: 2 })), {
      type: CartActionTypes.CLEAR_CART,
    });
    expect(next.items).toEqual([]);
  });
});

สังเกตว่าเราใช้เทคนิค factory เดียวกับ makeProduct ในบทที่แล้ว แต่ย่อส่วน: item() สร้าง CartItem มาตรฐานที่ override ได้ และ stateWith(...) ประกอบ state จากรายการสินค้ากี่ชิ้นก็ได้ (รวมถึงศูนย์ชิ้น — stateWith() คือตะกร้าว่าง) helper สองตัวนี้ทำให้ห้าเทสต์ที่เหลืออ่านเหมือนตาราง: state ตั้งต้นอะไร ยิง action อะไร คาดหวัง state ไหน

ห้าเทสต์นี้ครอบคลุม action ทั้งสี่ประเภทของ reducer โดย ADD_TO_CART ได้สองเทสต์เพราะมันมีสอง branch: เพิ่มของใหม่ กับเพิ่มของที่มีอยู่แล้ว — อย่างหลังต้องรวมจำนวน (2 + 3 = 5) ไม่ใช่แทรกแถวซ้ำ ซึ่งเป็น bug ที่เจอบ่อยมากในตะกร้าสินค้าจริง ๆ อีกสองรายละเอียดเล็ก ๆ ที่อยากชี้:

  • toEqual ไม่ใช่ toBe — toBe เทียบว่าเป็น object ตัวเดียวกันในหน่วยความจำ ส่วน toEqual เทียบเนื้อหาทีละ field ซึ่งคือสิ่งที่เราต้องการ เพราะ reducer ที่ดีต้องคืน object ใหม่เสมอ (immutability)
  • next.items[0]?.quantity — ใส่ optional chaining กันไว้ เผื่อ reducer มี bug จน items ว่าง เทสต์จะ fail แบบสุภาพ (undefined ไม่เท่ากับ 7) แทนที่จะ crash กลางทาง

cartStorage — เทสต์กับ localStorage จริง (ของ jsdom)

ชั้น persistence จากบทที่ 19 มีของให้เทสต์เยอะกว่าที่คิด เพราะมันต้องทนต่อข้อมูลพัง ๆ ใน localStorage ได้ สร้าง src/features/cart/store/cartStorage.test.ts:

import { CartState } from "./CartContext";
import { CART_STORAGE_KEY, loadCartState, saveCartState } from "./cartStorage";

const sample: CartState = {
  items: [{ id: 1, title: "Widget", price: 10, quantity: 2, image: "/w.png" }],
};

describe("cartStorage", () => {
  it("round-trips cart state", () => {
    saveCartState(sample);
    expect(loadCartState()).toEqual(sample);
  });

  it("returns an empty cart when nothing is stored", () => {
    expect(loadCartState()).toEqual({ items: [] });
  });

  it("returns an empty cart when stored JSON is corrupt", () => {
    localStorage.setItem(CART_STORAGE_KEY, "{not json");
    expect(loadCartState()).toEqual({ items: [] });
  });

  it("returns an empty cart when the stored shape is wrong", () => {
    localStorage.setItem(CART_STORAGE_KEY, JSON.stringify({ items: "nope" }));
    expect(loadCartState()).toEqual({ items: [] });
  });
});

คำถามแรกที่ควรถาม: แล้ว localStorage มาจากไหน? คำตอบคือ jsdom ให้มาฟรี — เพราะเราตั้ง environment: "jsdom" เทสต์จึงมี localStorage จริง ๆ ที่ใช้งานได้ (แค่อยู่ในหน่วยความจำ) เราเลยไม่ต้อง mock อะไรเลย: saveCartState เขียนลง storage จริง loadCartState อ่านกลับมาจริง โค้ด production ทุกบรรทัดได้รันในเทสต์

แต่ storage ที่แชร์กันก็มีความเสี่ยง: ถ้าเทสต์แรก save ค้างไว้ เทสต์ที่สอง ("nothing is stored") จะเจอของเก่าแล้วพัง — นี่คือหน้าที่ของบรรทัด localStorage.clear() ใน afterEach ของ setup.ts ที่เราเขียนไว้บทที่แล้ว ทุกเทสต์จึงเริ่มจาก storage ว่างเสมอ และเป็นเหตุผลที่เทสต์เหล่านี้เซ็ตข้อมูลเองในตัวโดยไม่ต้องเก็บกวาดทีหลัง

สองเทสต์สุดท้ายคือการเทสต์ "โลกจริงที่โหดร้าย": ผู้ใช้อาจมีข้อมูลเก่าจากเวอร์ชันก่อน หรือ extension บางตัวเขียนทับ key ของเรา — เทสต์ที่สามป้อน JSON พัง ๆ ("{not json") เพื่อพิสูจน์ว่า try/catch ทำงาน ส่วนเทสต์ที่สี่ป้อน JSON ที่ parse ได้แต่รูปร่างผิด (items เป็น string) เพื่อพิสูจน์ guard Array.isArray — ทั้งสองกรณีต้อง fallback เป็นตะกร้าว่างเงียบ ๆ ไม่ใช่ทำแอปพังทั้งหน้า

checkout schema — เทสต์ validation ทุกกติกา

zod schema จากบทที่ 22 คือกติกาการ validate ฟอร์มที่อยู่ เทสต์มันตรง ๆ ได้โดยไม่ต้อง render ฟอร์มเลย สร้าง src/features/checkout/schema.test.ts:

import { checkoutAddressSchema } from "./schema";

describe("checkoutAddressSchema", () => {
  const valid = {
    address: "1 Main St",
    email: "jane@example.com",
    phone: "0812345678",
  };

  it("accepts valid data", () => {
    expect(checkoutAddressSchema.safeParse(valid).success).toBe(true);
  });

  it("requires address", () => {
    const result = checkoutAddressSchema.safeParse({ ...valid, address: "" });
    expect(result.success).toBe(false);
    expect(result.error?.issues[0]?.message).toBe("Address is required");
  });

  it("rejects an invalid email", () => {
    const result = checkoutAddressSchema.safeParse({ ...valid, email: "nope" });
    expect(result.success).toBe(false);
    expect(result.error?.issues[0]?.message).toBe(
      "Enter a valid email address",
    );
  });

  it("requires phone", () => {
    const result = checkoutAddressSchema.safeParse({ ...valid, phone: "" });
    expect(result.success).toBe(false);
    expect(result.error?.issues[0]?.message).toBe("Phone number is required");
  });
});

รูปแบบที่ใช้ตรงนี้เป็นสูตรมาตรฐานของการเทสต์ schema และควรจำไปใช้ตลอดชีวิต:

  • เริ่มจาก object ที่ valid หนึ่งตัว แล้วแต่ละเทสต์ invalid ใช้ spread พังมันทีละ field: { ...valid, address: "" } — ถ้าพังหลาย field พร้อมกันเราจะไม่รู้ว่า error มาจากกติกาข้อไหน
  • safeParse ไม่ใช่ parse — parse โยน exception เมื่อไม่ผ่าน แต่ safeParse คืน result object ที่มี success กับ error ให้ assert ได้ตรง ๆ ไม่ต้องเล่นท่า try/catch ในเทสต์
  • assert ตัวข้อความ error ด้วย — ไม่ใช่แค่ success === false เพราะข้อความพวกนี้คือสิ่งที่ผู้ใช้เห็นใต้ช่องฟอร์มจริง ๆ (ผ่าน react-hook-form + zodResolver ในบทที่ 23) ถ้าใครแก้ข้อความใน schema โดยไม่ตั้งใจ เทสต์จะเตือน

API client — unit test ตัวแรกที่ใช้ MSW

ปิดท้ายด้วยไฟล์ที่พิเศษหน่อย: apiClient ไม่ใช่ pure function — มันยิง HTTP — แต่เพราะ MSW ดักที่ชั้น network ให้ เราเทสต์มันได้เหมือน unit test ปกติ และนี่คือเทสต์ที่พิสูจน์ interceptor จากบทที่ 12 ว่าแปลง error ได้ถูกจริง สร้าง src/shared/api/client.test.ts:

import { http, HttpResponse } from "msw";

import { ApiError, apiClient } from "./client";
import { server } from "@/test/msw/server";

describe("apiClient", () => {
  it("returns response data on success", async () => {
    const { data } = await apiClient.get("/products/1");
    expect(data.id).toBe(1);
  });

  it("normalizes server errors into ApiError with the server message", async () => {
    server.use(
      http.get("https://dummyjson.com/products/1", () =>
        HttpResponse.json({ message: "Product not found" }, { status: 404 }),
      ),
    );

    const error = await apiClient.get("/products/1").catch((e) => e);
    expect(error).toBeInstanceOf(ApiError);
    expect(error.message).toBe("Product not found");
    expect(error.status).toBe(404);
  });

  it("falls back to a generic message when the server sends none", async () => {
    server.use(
      http.get("https://dummyjson.com/products/1", () =>
        HttpResponse.json({}, { status: 500 }),
      ),
    );

    const error = await apiClient.get("/products/1").catch((e) => e);
    expect(error).toBeInstanceOf(ApiError);
    expect(error.message).toBe("Something went wrong. Please try again.");
  });
});

ของใหม่ในไฟล์นี้มีสามอย่าง:

  • เทสต์แรกไม่ต้องเตรียมอะไรเลย — GET /products/1 match handler ตั้งต้นใน handlers.ts อยู่แล้ว ซึ่งคืน makeProduct({ id: 1 }) เทสต์นี้จึงพิสูจน์ happy path ของทั้ง baseURL (มาจาก env ที่เรา hardcode ไว้ใน vite.config) และการส่งข้อมูลผ่าน axios
  • server.use(...) คือการ override handler ชั่วคราว — วิธีจำลอง "เซิร์ฟเวอร์ตอบ error" สำหรับเทสต์นั้น ๆ โดยเฉพาะ: handler ที่ยัดเข้าไปด้วย server.use จะถูกลองก่อน handler ตั้งต้น และถูกถอดทิ้งโดย server.resetHandlers() ใน afterEach ของ setup — เทสต์ถัดไปกลับมาเจอเซิร์ฟเวอร์ปกติเสมอ ไม่มี error รั่วข้ามเทสต์
  • ท่า .catch((e) => e) — ปกติ promise ที่ reject จะโยน exception แต่ท่านี้"จับ" error แล้วคืนมันออกมาเป็นค่าธรรมดา ทำให้เรา assert กับตัว error ได้หลายบรรทัดสบาย ๆ: เป็น instance ของ ApiError ไหม (พิสูจน์ว่า interceptor ห่อ error ให้จริง ไม่ใช่ AxiosError ดิบหลุดมา), message ตรงกับที่เซิร์ฟเวอร์ส่งไหม และ status ติดมาไหม เทสต์ที่สามกลับด้าน: เซิร์ฟเวอร์ตอบ 500 แบบไม่มี message — interceptor ต้อง fallback เป็นข้อความกลาง ๆ ที่เราเตรียมไว้
