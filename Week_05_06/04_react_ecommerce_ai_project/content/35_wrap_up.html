บทเรียน 35 · ส่งท้าย (Wrap Up)

Build และส่งท้าย

Wrap Up

มาถึงบทสุดท้ายแล้ว ตอนนี้คุณมีเว็บ E-commerce ที่ทำงานครบทุก flow พร้อมชุดเทสต์ที่พิสูจน์ว่ามันทำงานจริง เหลือขั้นตอนเดียว: ทำให้มันขึ้นไปอยู่บนอินเทอร์เน็ตให้คนอื่นใช้ได้ จากนั้นเราจะถอยออกมาคุยกันเรื่องที่สำคัญกว่าตัวแอป คือสิ่งที่คุณเอากลับไปได้จริงหลังจากปิดหน้านี้

ตรวจสุขภาพโปรเจกต์รอบสุดท้าย

ก่อน build ทุกครั้ง รันเช็กลิสต์คุณภาพให้ครบ นี่คือชุดคำสั่งเดียวกับที่ CI ของทีมจริงจะรันให้อัตโนมัติทุกครั้งที่มีคน push โค้ด:

npm run typecheck    # TypeScript ตรวจ type ทั้งโปรเจกต์
npm run lint         # ESLint ตรวจคุณภาพโค้ด
npm run format:check # Prettier ตรวจรูปแบบโค้ด
npm run test         # เทสต์ทั้งหมดต้องเขียว

มีเรื่องที่ต้องรู้ก่อนรัน เพราะมันทำให้คนเข้าใจผิดกันประจำ: สองคำสั่งแรกไม่พิมพ์อะไรเลยเวลาผ่าน tsc -b กับ eslint . เงียบสนิทถ้าไม่มีอะไรผิด ความว่างเปล่าบนจอคือข่าวดี ไม่ใช่สัญญาณว่าคำสั่งไม่ทำงาน ส่วนอีกสองตัวพูด:

$ npm run format:check
Checking formatting...
All matched files use Prettier code style!

$ npm run test
 Test Files  12 passed (12)
      Tests  34 passed (34)

ตัวเลข 12 ไฟล์ 34 เทสต์ คือตัวเลขเดียวกับที่จบบทเรียน 33 ถ้าของคุณได้น้อยกว่านี้ ให้ย้อนกลับไปดูว่าบทไหนยังไม่ครบก่อน อย่าเพิ่ง build

ถ้าทั้งสี่คำสั่งผ่านหมด ก็พร้อม build:

npm run build

สังเกตว่าใน package.json ของเรา script นี้คือ tsc -b && vite build — TypeScript ตรวจ type ก่อน แล้ว Vite ค่อยแปลงและบีบอัดโค้ดทั้งหมดลงโฟลเดอร์ dist/: JavaScript ถูก minify, SCSS กลายเป็น CSS ไฟล์เดียว, ชื่อไฟล์มี hash ต่อท้ายเพื่อให้ browser cache ได้อย่างปลอดภัย ผลที่ได้หน้าตาแบบนี้:

hash ในชื่อไฟล์กับเวลาที่ใช้ build จะไม่ตรงกับของคุณ ส่วนที่เหลือควรใกล้เคียงกัน ลองเปิดโฟลเดอร์ dist/ ดูว่าข้างในมีอะไรบ้าง — จะเจอ index.html, โฟลเดอร์ assets/ ที่มีสองไฟล์ข้างบน และของทุกอย่างที่เคยอยู่ใน public/ (โฟลเดอร์ images/ กับ vite.svg) ถูกก๊อปมาวางตรง ๆ โดยไม่ผ่านการแปลงอะไรเลย นั่นคือความหมายของโฟลเดอร์ public/: ของที่ต้องมี URL ตายตัวและห้ามมี hash

บรรทัดสุดท้ายเป็นคำเตือนจริงที่ควรอ่าน ไม่ใช่ noise: JavaScript ก้อนเดียว 682 kB (212 kB หลัง gzip) คือทุกอย่างในแอปรวมกันเป็นไฟล์เดียว ผู้ใช้ที่เปิดหน้า Home ต้องโหลดโค้ดของหน้า Checkout, ตัวจัดการฟอร์ม, zod, swiper และไอคอน FontAwesome ทั้งชุดไปด้วย ทั้งที่อาจไม่มีวันไปถึงหน้านั้น ที่มันยังไม่ใช่ปัญหาวันนี้เพราะแอปเรามีหกหน้า ที่มันจะเป็นปัญหาคือวันที่มีหกสิบหน้า ทางแก้ชื่อว่า code splitting และมันอยู่ในรายการ "ก้าวต่อไป" ท้ายบทนี้ — ตอนนี้แค่รู้ว่าตัวเลขนี้มีอยู่และมันแปลว่าอะไร ก็พอ ที่ต้องย้ำคือตัวเลขนี้ไม่ได้โผล่ที่ไหนอีกเลยนอกจากบรรทัดนี้: มันไม่ทำให้ lint แดง ไม่ทำให้เทสต์ตก และไม่มีอะไรบนหน้าเว็บบอกคุณ ในภาษาของบทเรียน 29 มันเป็นฝั่งเงียบที่บังเอิญมีคนตะโกนให้หนึ่งครั้งตอน build เท่านั้น

ทดลองรันเวอร์ชัน production บนเครื่องเราก่อน deploy จริงได้ด้วย:

npm run preview
💡 npm run dev กับ npm run preview ต่างกันสำคัญ: dev รันจาก source โดยตรงพร้อม hot reload ส่วน preview เสิร์ฟไฟล์ที่ build แล้วจาก dist/ จริง ๆ — ปัญหาบางอย่าง (เช่น path รูปภาพผิด หรือ environment variable หาย) โผล่เฉพาะตอน build แล้วเท่านั้น เจอใน preview ดีกว่าเจอบน production

แต่มีข้อที่ต้องรู้คู่กัน ไม่งั้นจะเข้าใจผิด: vite preview ตั้ง SPA fallback ให้เองอยู่แล้ว เปิด http://localhost:4173/categories ตรง ๆ ใน preview จะได้หน้าเว็บปกติ ไม่ใช่ 404 แปลว่ากับดักที่กำลังจะพูดถึงในหัวข้อถัดไปไม่โผล่ใน preview — preview พิสูจน์ได้ว่าไฟล์ที่ build แล้วทำงานถูก แต่พิสูจน์ไม่ได้ว่า server ที่คุณจะเอาไปวางตั้งค่าถูก อย่าเอาความเงียบของมันมาเป็นหลักประกัน

Deploy แบบ SPA

แอปของเราเป็น Single Page Application: มีไฟล์ HTML จริงแค่ไฟล์เดียว แล้ว react-router จัดการ URL ทั้งหมดในฝั่ง browser นั่นแปลว่าตอน deploy มีกับดักหนึ่งที่เจอกันทุกคน: ถ้าผู้ใช้เปิด https://your-app.com/categories ตรง ๆ (หรือกด refresh) server จะมองหาไฟล์ /categories ซึ่งไม่มีอยู่จริง แล้วตอบ 404

ทางแก้คือบอก server ว่า "ทุก URL ที่หาไฟล์ไม่เจอ ให้ส่ง index.html กลับไป" แล้วปล่อยให้ react-router ตัดสินใจว่าจะแสดงหน้าไหน ผู้ให้บริการ hosting ยุคนี้ทำให้เรื่องนี้ง่ายมาก:

  • Vercel — ตรวจพบ Vite อัตโนมัติ แค่ npx vercel หรือเชื่อม GitHub repo ก็จบ SPA fallback ถูกตั้งให้เอง
  • Netlify — ลาก dist/ ไปวางบนหน้าเว็บก็ได้ หรือเชื่อม repo แล้วเพิ่มไฟล์ public/_redirects ที่มีบรรทัดเดียว: /*  /index.html  200
  • GitHub Pages — ใช้ได้แต่ต้องตั้ง base path และทำ 404 fallback เอง เหมาะกับคนอยากเข้าใจกลไกมากกว่าอยากเสร็จเร็ว

อย่าลืมเรื่อง environment variable: ค่า VITE_API_BASE_URL ถูกฝังลงในโค้ดตอน build ไม่ใช่ตอนรัน ดังนั้นถ้า deploy ผ่าน CI ของ Vercel/Netlify ให้ไปตั้งค่านี้ในหน้า Environment Variables ของโปรเจกต์ด้วย (ค่าเดียวกับใน .env ของเรา: https://dummyjson.com) ถ้าลืมข้อนี้ อาการจะเป็นเว็บที่ขึ้นสวยงามทุกหน้าแต่ไม่มีสินค้าสักชิ้น เพราะ apiClient จะยิงไปที่ path ว่าง ๆ บนโดเมนตัวเอง

และเมื่อ deploy เสร็จแล้ว ให้ทำสองอย่างนี้เป็นการตรวจรับ อย่าเช็กแค่หน้าแรก: (1) เปิด URL ของหน้าลึก ๆ ตรง ๆ ในแท็บใหม่ (เช่น /categories และ /cart) แล้วกด refresh ซ้ำอีกรอบ — นี่คือการตรวจ SPA fallback ที่ preview ตรวจให้ไม่ได้ (2) เปิด DevTools แท็บ Network แล้วดูว่า request ของสินค้าวิ่งไปที่ dummyjson.com จริง ไม่ใช่โดเมนของคุณเอง — นี่คือการตรวจ environment variable

สิ่งที่คุณสร้างมาตลอด 35 บท

ถอยออกมามองภาพรวมกันหน่อยว่าตลอดคอร์สนี้คุณผ่านอะไรมาบ้าง:

  • วางรากฐานโปรเจกต์แบบมืออาชีพ — Vite + TypeScript strict, ESLint 10 flat config, Prettier, path alias และโครงสร้างโฟลเดอร์แบบ feature-based ที่โค้ดทุกไฟล์รู้ที่อยู่ของตัวเอง
  • ตั้งวงกับ AI ก่อนใช้งานจริง — แยกโหมด Ask กับ Agent ออกจากกัน, เขียน .cursor/rules ที่ทำให้กติกาของโปรเจกต์ถูกอ่านทุกครั้งโดยไม่ต้องพิมพ์ซ้ำ และวางกายวิภาคสี่ส่วนของ prompt (บริบท / โครงสร้าง / ข้อกำหนดทางเทคนิค / ขอบเขต) กับวงจรตรวจงานห้าขั้นที่ใช้ซ้ำมายี่สิบสี่บท
  • ชั้นข้อมูลที่เป็นระบบ — axios client ตัวเดียวที่ normalize error ให้ทั้งแอป, typed API functions และ query key factory + queryOptions ที่ทำให้ TanStack Query แสดงพลังเต็มที่ทั้ง cache, placeholderData และ declarative data ไม่มี useEffect + refetch() ให้เห็นเลยสักที่
  • UI ที่ประกอบจากชิ้นส่วน — shared components ที่ถูกใช้ซ้ำทุกหน้า, SCSS Modules ที่ไม่มีทาง class ชนกัน และหน้า Home/Category/Product ที่จัดการทั้ง loading, error และ empty state ครบ
  • Client state ที่ถูกออกแบบ — ตะกร้าสินค้าด้วย Context + useReducer + localStorage: reducer ที่เทสต์ได้ล้วน ๆ, lazy initializer และ write-through persistence
  • ฟอร์มระดับ production — react-hook-form + zod ที่ schema เดียวให้ทั้ง validation และ TypeScript type, mutation flow ที่สั่งซื้อ เคลียร์ตะกร้า และนำทางต่ออย่างถูกลำดับ
  • ชุดเทสต์ครบทุกชั้น — 12 ไฟล์ 34 เทสต์: unit tests ของ pure functions, hook tests ผ่าน MSW ที่จำลอง network จริง และ integration tests ที่เล่นบทผู้ใช้ตั้งแต่เปิดหน้าจนจ่ายเงินสำเร็จ
  • ตารางจุดพลาดของ AI ที่มาจากโปรเจกต์นี้เอง — หกตระกูลในบทเรียน 29 ไม่ได้ลอกมาจากบทความไหน ทุกแถวมาจากบรรทัด AI มักพลาดตรงนี้ ของบทที่คุณเดินผ่านมาจริง พร้อมเส้นแบ่งดัง/เงียบที่เปลี่ยนวิธีจัดสรรเวลาตรวจงาน และในบทเรียน 34 คุณเอา AI กลับมาอ่านโค้ดตัวเองแล้วเห็นด้วยว่ามันหาอะไรเจอและหาอะไรไม่เจอ

ที่สำคัญกว่าตัวแอปคือนิสัยที่คุณได้ฝึก: แยก server state ออกจาก client state, ทำ error ให้เป็นเรื่องปกติที่ต้องออกแบบ ไม่ใช่เรื่องเซอร์ไพรส์, เขียน type ให้ตรงกับความจริง และพิสูจน์พฤติกรรมด้วยเทสต์ก่อนจะเชื่อว่ามันเสร็จ — สี่อย่างนี้ไม่ได้เปลี่ยนไปเลยเพราะมี AI มาพิมพ์ให้ มันแค่กลายเป็นสิ่งที่คุณต้องเป็นคนถือไว้ เพราะไม่มีใครในทีมเครื่องมือของคุณถือมันแทนได้

ทักษะที่คุณได้จริง ๆ

คำถามที่ควรตอบให้ตรงก่อนปิดคอร์ส: ถ้าพรุ่งนี้ Cursor ใช้ไม่ได้ คุณเหลืออะไร คำตอบแยกเป็นสองกอง และกองแรกสำคัญกว่ากองที่สองมาก

ทำได้เอง โดยไม่ต้องมี AI

สี่ข้อนี้ไม่ใช่การพูดให้กำลังใจ ทุกข้อชี้กลับไปที่บทที่คุณลงมือทำมันด้วยมือตัวเองได้:

  • อ่าน diff แล้วบอกได้ว่าอะไรผิด — ไม่ใช่ "รู้สึกว่าแปลก ๆ" แต่ชี้เป็นบรรทัดได้ คุณเห็น <BrowserRouter> ครอบ <Routes> แล้วรู้ทันทีว่านี่คือรูปทรงผิดทั้งไฟล์ ไม่ใช่รายละเอียดผิด (บทเรียน 09 และ 29), เห็น push ใน reducer แล้วรู้ว่ามันจะพังตรงไหนและทำไมเทสต์ยังเขียว (บทเรียน 22 และ 31), เห็น clearCart() อยู่ข้าง ๆ ปุ่มแทนที่จะอยู่ใน onSuccess แล้วรู้ว่าใครจะเจ็บ (บทเรียน 28) วงจรตรวจงานห้าขั้นของบทเรียน 08 กับเกณฑ์ตัดสินสามข้อของบทเรียน 29 ทำงานได้เหมือนเดิมทุกประการไม่ว่าโค้ดตรงหน้าจะมาจาก AI จากเพื่อนร่วมทีม หรือจากตัวคุณเองเมื่อสามเดือนก่อน
  • ออกแบบ cache key — บทเรียน 17 คุณพิมพ์ productKeys ทั้งก้อนเอง รวมถึงบรรทัด String(id) ที่มีเหตุผลของมัน คุณตอบได้ว่าทำไม key ต้องเรียงจากกว้างไปแคบ ทำไม params ต้องอยู่ใน key และอะไรจะเกิดขึ้นถ้าสองหน้าใช้ key เดียวกันโดยไม่ตั้งใจ นี่เป็นการตัดสินใจที่บทเรียน 01 บอกไว้ตั้งแต่ต้นว่า AI ตอบแทนไม่ได้ เพราะคำตอบขึ้นกับว่าอีกสามเดือนแอปนี้จะโตไปทางไหน
  • เขียน reducer และ schema — cartReducer.ts ทั้งไฟล์ (บทเรียน 22) และ zod schema ของ checkout ทั้งไฟล์ (บทเรียน 25) ผ่านนิ้วคุณทีละตัวอักษร คุณรู้ว่า spread แต่ละจุดกำลังคัดลอกอะไรและทิ้งอะไร และรู้ว่าข้อความ error แต่ละบรรทัดใน schema จะไปโผล่ที่หน้าจอตอนไหน
  • เขียนเทสต์ที่ล้มเป็น — คำสำคัญของข้อนี้คือคำว่า "ล้มเป็น" ไม่ใช่ "เขียนเทสต์" เพราะเทสต์ที่เขียนให้ผ่านอย่างเดียวนั้นเขียนได้โดยไม่ต้องเข้าใจโค้ดเลยสักบรรทัด บทเรียน 31 คุณพิมพ์ price.utils.test.ts เองแล้วทำขั้นตอน "ทำให้มันแดง" หนึ่งรอบในกล่อง ✍️ แล้วอีกหกรอบในกล่อง ✅ บทเรียน 33 คุณพิมพ์ integration test ตัวแรกเองแล้วทำอีกสี่คู่ โดยคู่สุดท้ายเป็นคู่ที่ต้องยังเขียว คุณจึงรู้จากประสบการณ์ตรง ไม่ใช่จากการอ่าน ว่า assertion ที่คำนวณค่าคาดหวังด้วยสูตรเดียวกับโค้ดที่กำลังทดสอบนั้นไม่มีค่าอะไรเลย
  • ตัดสินว่าอะไรเป็นของกลาง — บทเรียน 05 คุณวางกติกาไว้แล้วว่า src/shared/ ต้องไม่ผูกกับฟีเจอร์ใดฟีเจอร์หนึ่ง บทเรียน 34 เอากติกานั้นมาทดสอบจริง: พอไม่เขียนมันลงใน prompt คำถามเปิดช่องให้ AI ตอบว่ายกทุกอย่างไปรวมไว้ใน shared/utils/ ทั้งก้อน รวมทั้งสูตรยอดรวมตะกร้าที่จริง ๆ ต้องอยู่ใน src/features/cart/ เพราะมันอ่าน cart.items ซึ่งเป็นของฟีเจอร์ cart คุณเป็นคนตัดคำตอบนั้นออกเอง ด้วยเหตุผลว่าคนใช้อยู่สองฟีเจอร์ไม่ได้แปลว่ามันเป็นของกลาง — นี่คือการตัดสินใจข้อที่สองที่บทเรียน 01 บอกไว้ตั้งแต่ต้นว่า AI ตอบแทนไม่ได้

ของที่จับต้องได้ที่สุดคือสิบจุดที่คอร์สนี้ห้าม AI แตะ — โครงโฟลเดอร์ (05), array routes (09), Button (12), interceptor ของ axios (15), query key factory (17), cartReducer (22), zod schema (25), useCheckout (28), unit test ตัวแรก (31) และ integration test ตัวแรก (33) สิบไฟล์นี้เป็นของคุณเต็ม ๆ ไม่มีบรรทัดไหนที่ก๊อปมา และไม่มีบรรทัดไหนที่คุณอธิบายไม่ได้ นั่นคือมาตรฐานที่คุณจะใช้เทียบตอนตรวจงานของคนอื่นในโปรเจกต์หน้า

ทำได้เร็วขึ้น เมื่อมี AI

กองที่สองคืองานที่ AI ทำให้เร็วขึ้นจริง — และทั้งสามข้อนี้เร็วขึ้นได้เพราะกองแรก ไม่ใช่แทนกองแรก:

  • ประกอบ component ตามแบบที่วางไว้แล้ว — Input กับ RadioInput ในบทเรียน 12 ต่อจาก Button ที่คุณพิมพ์เอง, Modal กับ Pagination ในบทเรียน 13, คอมโพเนนต์แสดงผลทั้งชุดในบทเรียน 14 งานพวกนี้คุณสั่งได้ในไม่กี่บรรทัดและตรวจจบได้ในไม่กี่สิบวินาที เพราะคุณมี Button ที่พิมพ์เองอยู่ในหัวเป็นแม่แบบ
  • เขียนไฟล์ที่สี่ที่หน้าตาเหมือนสามไฟล์แรก — กล่อง Delivery กับ Payment ในบทเรียน 27 ที่โครงเหมือนกันเป๊ะต่างกันแค่ข้อมูล, เทสต์ทั้งสี่ตัวใน queries.test.tsx ของบทเรียน 32 ที่โครงเหมือนกันหมดต่างกันแค่ query ที่เรียก นี่คือจุดที่มันคุ้มที่สุดตามที่บทเรียน 01 บอกไว้ และก็ยังจริงหลังผ่านมาสามสิบสี่บท
  • ตรวจงานตัวเอง — บทเรียน 34 ทั้งบท: ชี้มันไปที่โค้ดที่เสร็จแล้วเพื่อหาของที่คุณไม่รู้ว่ามี ในเวลาที่คนอ่านเองไม่ทัน แต่ยืนยันทีละข้อด้วยตัวเอง และตัดสินใจเองว่าข้อไหนคือของจริง

และเพื่อให้ครบถ้วน มีของที่คอร์สนี้ยังไม่ได้ให้คุณ ควรรู้ไว้ก่อนไปคุยกับใคร: คุณยังไม่เคย deploy ของที่มีผู้ใช้จริงแล้วต้องแก้บั๊กที่พบบน production, ยังไม่เคยเข้าไปทำงานในโค้ดที่คนอื่นเขียนและไม่มีใครอธิบายให้ฟัง, และยังไม่เคยต้องรักษาชุดเทสต์ให้เขียวในขณะที่มีคนอีกห้าคน push โค้ดเข้ามาชนกันทุกวัน สามอย่างนี้เรียนจากคอร์สไม่ได้ ต้องไปเจอเอง ที่คอร์สนี้ทำให้ได้คือคุณจะเข้าไปเจอมันโดยมีมาตรฐานในหัวไปด้วย ไม่ใช่เข้าไปมือเปล่า

ก้าวต่อไป

  • ต่อยอดแอปนี้ — เพิ่มช่องค้นหาสินค้า (dummyjson มี endpoint /products/search ให้แล้ว), ทำ URL ให้จำ category และหน้าที่เลือกไว้ (query params), เพิ่มระบบ favorite หรือเปลี่ยน react-modal เป็น <dialog> ของ HTML แท้ ๆ
  • อุดรูที่คุณรู้ว่ามีอยู่ — คอร์สนี้ทิ้งของที่ยังผิดไว้หลายจุดโดยตั้งใจ เพราะมันตรงกับโค้ดอ้างอิงต้นฉบับ: เทสต์ที่ครอบลำดับ "อยู่หน้า 2 แล้วเปลี่ยนหมวด" ที่ยังไม่มีใครเขียน (บทเรียน 33), สเกลคะแนนดาวที่ยังหารสองอยู่ (บทเรียน 21 และ 29), data-testid สี่ตัวที่ไม่มีเทสต์ตัวไหนใช้ (บทเรียน 33), label ที่ไม่ได้ผูกกับ input (บทเรียน 34) เริ่มจากรายการนี้ก่อนคิดฟีเจอร์ใหม่ — การซ่อมของที่รู้ว่าพังเป็นแบบฝึกหัดที่ตรงกับงานจริงมากกว่าการสร้างของใหม่
  • ทำ code splitting — คำเตือน 682 kB ตอน build คือโจทย์ที่มีคำตอบวัดผลได้: เปลี่ยนหน้าเพจใน src/app/router.tsx ให้โหลดแบบ lazy แล้ว build ใหม่ ดูว่าไฟล์ก้อนเดียวแตกเป็นกี่ก้อนและก้อนแรกเล็กลงเท่าไร นี่เป็นงานที่ทั้งเล็กและเห็นผลเป็นตัวเลข เหมาะกับการฝึกวงจร prompt → review อีกรอบด้วยตัวเอง
  • ยกระดับ state — ถ้าตะกร้าเริ่มซับซ้อนกว่านี้ ลอง Zustand หรือ Redux Toolkit แล้วเปรียบเทียบกับ Context + useReducer ที่เราเขียนเอง จะเข้าใจทันทีว่าเครื่องมือพวกนี้แก้ปัญหาอะไร
  • ไปฝั่ง server — Next.js หรือ React Router framework mode จะพา React ไป render บน server ซึ่งเป็นโลกที่ต่อจากคอร์สนี้พอดี
  • สร้างโปรเจกต์ของตัวเอง — เลือกไอเดียที่คุณอยากใช้เองจริง ๆ แล้วเริ่มจาก npm create vite เหมือนบทเรียน 02 ทุกขั้นตอนที่เราเดินมาด้วยกัน คุณเดินเองได้แล้วทั้งหมด

เรียนต่ออย่างไรไม่ให้ทักษะฝ่อ

ความเสี่ยงจริงของการทำงานกับ AI ไม่ใช่มันเขียนโค้ดผิด — บทเรียน 29 กับ 34 จัดการเรื่องนั้นไปแล้ว ความเสี่ยงจริงคือคุณค่อย ๆ เลิกรู้ว่าโค้ดที่ถูกควรหน้าตาเป็นอย่างไร โดยไม่รู้ตัว เพราะทุกครั้งที่คุณกด Accept ของที่ดูโอเค คุณได้โค้ดเพิ่มหนึ่งก้อนแต่ไม่ได้มาตรฐานในหัวเพิ่มขึ้นเลยสักนิด และมาตรฐานในหัวคือด่านเดียวที่เหลืออยู่หลังจากเครื่องมือทุกตัวบอกว่าผ่านแล้ว ตามที่บทเรียน 29 สรุปไว้ ถ้าด่านนั้นฝ่อ ทุกอย่างในคอร์สนี้ฝ่อตามไปหมด

มีนิสัยข้อเดียวที่กันเรื่องนี้ได้ และมันราคาสามสิบวินาทีต่อ prompt:

🚨 ก่อนกดส่ง prompt ทุกครั้ง ให้เดาก่อนว่าโค้ดที่ได้ควรหน้าตาอย่างไร ไม่ใช่เดาลอย ๆ ในหัว แต่เดาให้ชี้ได้: จะได้กี่ไฟล์ ชื่ออะไร อยู่ path ไหน, ฟังก์ชันที่ export ออกมาชื่ออะไรและรับอะไรคืนอะไร, บรรทัดสำคัญที่สุดในไฟล์นั้นคือบรรทัดไหน จดสามข้อนี้ไว้ข้าง ๆ ก่อน แล้วค่อยกดส่ง

พอของกลับมา เอาไปเทียบ ผลจะออกได้สามแบบ และทั้งสามแบบมีประโยชน์คนละอย่าง:

  • ตรงกับที่เดา — คุณเข้าใจเรื่องนี้จริง และเพิ่งประหยัดเวลาพิมพ์ไปได้เต็ม ๆ นี่คือกรณีที่ AI คุ้มที่สุด และเป็นกรณีที่คุณตรวจงานได้เร็วที่สุดด้วย เพราะรู้อยู่แล้วว่าจะมองหาอะไร
  • ไม่ตรง แต่ของมันดีกว่า — กรณีนี้มีค่าที่สุดในสามข้อ ห้ามกด Accept แล้วเดินหน้าต่อเฉย ๆ ให้หาให้เจอก่อนว่าทำไมของมันดีกว่า แล้วเก็บเหตุผลนั้นไว้ใช้ครั้งหน้า ถ้าหาเหตุผลไม่เจอ แปลว่ามันอาจไม่ได้ดีกว่า มันแค่ต่าง
  • เดาไม่ออกเลย — นี่คือสัญญาณ ไม่ใช่ความล้มเหลว มันแปลตรงตัวว่าบทหรือหัวข้อนั้นคุณยังไม่แน่นพอ ทางที่ถูกคือปิดแชทแล้วกลับไปอ่านก่อน ไม่ใช่ส่ง prompt ไปแล้วค่อยอ่านคำตอบเอา เพราะการอ่านคำตอบที่ดูสมเหตุสมผลให้ความรู้สึกเหมือนเข้าใจ ทั้งที่คุณแค่จำหน้าตาของมันได้

ที่นิสัยนี้ได้ผลเพราะมันคือข้อสอบเดียวกับกติกาข้อเดียวของคอร์สนี้ ("AI พิมพ์แทนคุณได้ แต่คุณต้องอธิบายทุกบรรทัดได้") แค่ย้ายจากหลังไปก่อน และการย้ายนั้นเปลี่ยนทุกอย่าง เพราะการถามตัวเองว่า "ของที่ได้มานี้ถูกไหม" ตอนมีคำตอบวางอยู่ตรงหน้าแล้ว เป็นคำถามที่คำตอบตรงหน้ามีอิทธิพลกับมันเสมอ — ทั้งหกตระกูลในบทเรียน 29 คือของที่อ่านแล้วดูถูกทั้งนั้น ส่วนการเดาก่อนเห็นคำตอบไม่มีทางโกงตัวเองได้ คุณเดาออกหรือเดาไม่ออก จบตรงนั้น

แบบทดสอบที่ตรงกว่านั้น: ทำหนึ่งฟีเจอร์โดยไม่ใช้ AI เลย

นิสัยข้างบนวัดได้ทีละ prompt ถ้าอยากเห็นภาพรวมว่ารูของคุณอยู่ตรงไหนบ้าง ให้ทำแบบนี้หนึ่งรอบ: เลือกฟีเจอร์เล็ก ๆ หนึ่งอันแล้วทำให้เสร็จโดยไม่แตะ AI เลย ช่องค้นหาสินค้าจากรายการก้าวต่อไปข้างบนขนาดกำลังดี — มันแตะสี่ชั้นที่คอร์สนี้สอนมาครบพอดี คือ API function ใหม่, จานใหม่ใน query factory, หน้าเพจที่ต้องจัดการ loading กับ error และเทสต์อีกหนึ่งตัว

กติกาสามข้อ: ปิดแผงแชท, ปิด autocomplete ของ Cursor ด้วย (ถ้ากด Tab รับ ก็คือใช้ AI ตามนิยามของกล่อง ✍️ ทั้งสิบกล่อง) และให้เวลาตัวเองแค่หนึ่งบ่าย เปิด MDN เปิดเอกสารของ TanStack Query เปิดโค้ดในโปรเจกต์ตัวเองได้ทุกไฟล์ — สามอย่างนี้ไม่ใช่การโกง มันคือสิ่งที่คนทำงานจริงเปิดกันทุกวัน

สิ่งที่วัดไม่ใช่ว่าทำเสร็จหรือเปล่า แต่คือคุณหยุดไปเปิดหาที่ไหนบ้าง และหยุดกี่ครั้ง จดไว้ทุกครั้งที่หยุด รายการนั้นคือรายการรูของคุณ และมันเป็นหลักฐาน ต่างจากความรู้สึกว่า "บทไหนน่าจะยังไม่แน่น" ซึ่งเป็นการเดา เทียบสองรายการนี้ดูตอนจบ

ปิดท้าย

สามสิบห้าบทที่ผ่านมาคุณให้ AI พิมพ์โค้ดส่วนใหญ่ของแอปนี้ และผลลัพธ์คือเว็บที่ใช้งานได้จริงทั้งเว็บ พร้อมเทสต์ 34 ตัวและ dist/ ที่พร้อม deploy — นั่นคือของที่จับต้องได้ แต่มันไม่ใช่ส่วนที่สำคัญที่สุดที่คุณได้กลับไป

ส่วนที่สำคัญที่สุดวัดได้ด้วยประโยคเดียว: ตอนนี้คุณบอกได้ว่าแอปที่ตัวเองเพิ่งสร้างเสร็จมีอะไรผิดอยู่บ้าง พร้อมชื่อไฟล์และเหตุผล — setPage(1) ที่ไม่มีเทสต์ตัวไหนคุ้ม, ดาวที่ยังหารสองอยู่, label ในฟอร์ม checkout ที่ไม่ได้ผูกกับ input, ก้อน JavaScript 682 kB ที่ยังไม่ได้แบ่ง ทุกข้อชี้เป็นไฟล์เป็นบรรทัดได้ ไม่ใช่ความรู้สึกว่ายังไม่เรียบร้อย — และนั่นคือเกณฑ์ที่สูงกว่า "มันก็รันได้" ซึ่งบทเรียน 29 ขึ้นบัญชีไว้เป็นสัญญาณอันตรายข้อที่สาม การเห็นสิ่งที่ยังไม่ถูกในงานที่ตัวเองเพิ่งทำเสร็จ คือความต่างทั้งหมดระหว่างคนที่ใช้ AI เขียนโค้ดได้ กับคนที่ทีมไว้ใจให้ดูแลโค้ดที่ AI เขียน

เอาแอปนี้ขึ้น deploy จริงสักที่ ส่งลิงก์ให้เพื่อนกดเล่น แล้วเปิดโปรเจกต์ถัดไปได้เลย

🚨 ข้อเดียวที่ควรจำไปจากทั้งคอร์ส — เครื่องมือจะเปลี่ยนไปเรื่อย ๆ ส่วนคำถามว่า "ของที่ได้มานี้ถูกหรือเปล่า" เป็นคำถามเดิมเสมอ และยังเป็นคำถามที่ตอบได้เฉพาะคนที่รู้อยู่ก่อนแล้วว่าคำตอบที่ถูกควรหน้าตาอย่างไร ทักษะนั้นสร้างได้ทางเดียวคือลงมือทำเองในจุดที่มันสำคัญ — สิบจุดในคอร์สนี้เป็นแค่จุดเริ่มต้น เลือกจุดต่อไปเอง
