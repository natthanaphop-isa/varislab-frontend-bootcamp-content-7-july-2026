Query Factories

Query Factories

ชิ้นสุดท้ายของชั้นข้อมูลสินค้ามาถึงแล้ว เรามีฟังก์ชัน typed ครบสี่ตัวจากบทที่แล้ว และมี QueryClientProvider ครอบแอปไว้ตั้งแต่บทเรียน 11 — เหลือแค่ตอบคำถามเดียว: หน้าเพจควรเรียก useQuery อย่างไร? คำตอบแบบที่เราเรียนมาจากคอร์ส React พื้นฐาน คือเขียน queryKey กับ queryFn สด ๆ ในคอมโพเนนต์ ซึ่งใช้ได้ดีในแอปที่มี query สองสามตัว แต่แอปของเรากำลังจะมี query กระจายอยู่หลายหน้า และวิธีนั้นมีกับดักซ่อนอยู่

ปัญหา: query key ที่เขียนด้วยมือจะค่อย ๆ เพี้ยน

ลองดูสถานการณ์สมมติที่เกิดจริงในทุกทีม — สองหน้าต้องการข้อมูลชุดเดียวกัน แต่เขียนคนละวัน:

// หน้า Home — เขียนวันจันทร์
useQuery({
  queryKey: ["products", page],
  queryFn: () => getProducts({ page }),
});

// หน้า Category — เขียนวันพฤหัส
useQuery({
  queryKey: ["product-list", category, page],
  queryFn: () => getProductsByCategory({ category, page }),
});

โค้ดนี้รันได้ ไม่มี error ไม่มี warning แต่มันป่วยแล้ว:

  • ข้อมูลชนิดเดียวกัน สะกด key คนละแบบ — "products" กับ "product-list" ทำให้คำสั่งกวาดล้าง cache อย่าง invalidateQueries({ queryKey: ["products"] }) โดนแค่ตัวแรก ตัวที่สองรอดไปหน้าตาเฉย แสดงข้อมูลเก่าต่อไปเงียบ ๆ
  • สะกดผิดคือ cache ใหม่ ไม่ใช่ error — พิมพ์ "prodcuts" ที่ไหนสักแห่ง TypeScript ไม่ว่าอะไรเลย เพราะ key เป็นแค่ array ธรรมดา ผลคือได้ cache แยกอีกก้อน ยิง request ซ้ำโดยไม่มีใครรู้
  • ลืมใส่ตัวแปรใน key — ถ้า queryFn ใช้ page แต่ key ไม่มี page การเปลี่ยนหน้าจะไม่ refetch เพราะ TanStack Query มองว่า key เดิม = ข้อมูลเดิม นี่คือ bug คลาสสิกที่ debug ยากที่สุดตระกูลหนึ่ง

ต้นตอของทั้งหมดคือ query key เป็น "ข้อความอิสระ" ที่ไม่มีแหล่งความจริงกลาง วิธีแก้แบบมืออาชีพมีสองท่อนประกอบกัน:

  • Query key factory — object เดียวที่เป็นเจ้าของ key ทุกตัวของฟีเจอร์ ใครอยากได้ key ต้องมาขอจากที่นี่ จะไม่มีการสะกดมือกระจายตามหน้าอีกเลย
  • queryOptions() — helper ของ TanStack Query v5 ที่มัด queryKey + queryFn + option อื่น ๆ เป็นก้อนเดียวที่ type ครบสมบูรณ์ หน้าเพจแค่ useQuery(productQueries.list()) แล้วได้ data ที่ TypeScript รู้ type เป๊ะ ๆ โดยไม่ต้องประกาศอะไรเพิ่ม

ทำไมบทนี้ถึงพิมพ์ productKeys เอง

บทนี้สลับลำดับกลับไปเป็นแบบบทเรียน 12: กล่อง ✍️ มาก่อนกล่อง 🤖 และคราวนี้เหตุผลไม่ใช่เรื่อง "ให้ไฟล์ตัวอย่างเป็นบริบท" อย่างเดียว แต่เป็นเรื่องทิศทางการพึ่งพาล้วน ๆ

ทวนกฎจากบทเรียน 12 อีกครั้ง: สิ่งที่พังเมื่อคุณตัดของออกจาก prompt คือสิ่งที่อ้างถึงของชิ้นนั้น ไม่ใช่ตัวมันเอง บทที่แล้วเราเจอกรณีที่ลูกศรชี้ทางเดียว: บล็อก interceptor อ้างถึง apiClient เราจึงต้องให้ Agent สร้าง apiClient ก่อน บทนี้ลูกศรชี้กลับด้าน

เปิดดูโครงของ queries.ts ที่เรากำลังจะได้: ครึ่งบนคือ productKeys ครึ่งล่างคือ productQueries และครึ่งล่างอ้างถึงครึ่งบนทุกจาน — productKeys.list(params), productKeys.byCategory(params), productKeys.categories(), productKeys.detail(id) ถ้าเราสั่งว่า "สร้าง productQueries แต่ห้ามแตะ productKeys" โดยที่ productKeys ยังไม่มีตัวตน สิ่งที่พังไม่ใช่ productKeys แต่คือ productQueries ทั้งก้อน: typecheck ตายที่บรรทัดแรกของทุกจาน แล้วคุณจะเดินวงจรตรวจงานขั้นที่สามไม่ได้เลย

ดังนั้นลำดับของบทนี้จึงถูกบังคับไว้แล้ว: พิมพ์ productKeys เอง ให้ lint กับ typecheck ผ่าน git commit ให้ working tree สะอาด แล้วค่อยส่ง prompt ที่ @-mention ไฟล์นั้น — ไฟล์ต้องมีอยู่จริงก่อน @-mention ถึงจะมีน้ำหนัก และของที่คุณพิมพ์เองก็กลายเป็นบริบทที่แม่นที่สุดของงานถัดไปพอดี

ส่วนเหตุผลว่าทำไมต้องเป็น productKeys ที่พิมพ์เอง ไม่ใช่ productQueries: ทั้งสองก้อนยาวพอ ๆ กัน แต่ก้อนบนคือก้อนที่ผิดแล้วไม่มีใครบอก — ไม่ใช่ compiler ไม่ใช่ lint ไม่ใช่หน้าเว็บ ส่วนก้อนล่างถ้าผิดรูปทรง typecheck จับได้ทันที

ติดตั้ง ESLint plugin ด้วยมือ

factory ป้องกัน key เพี้ยนได้เกือบหมด แต่ "เกือบ" ยังไม่พอสำหรับเรา — TanStack ทำ ESLint plugin ที่ตรวจจับการใช้ query ผิดท่าให้ตั้งแต่ตอนเขียน ตามกติกาเดิม dependency เราติดตั้งเอง ส่วนการต่อสายเข้า config เป็นงานของ Agent เดี๋ยวนี้:

npm install -D @tanstack/eslint-plugin-query
git add -A && git commit -m "chore: install tanstack query eslint plugin"
💡 ตอนเขียน eslint.config.js ทั้งไฟล์ในบทเรียน 03 เราทิ้งท้ายไว้ว่าไฟล์นั้นยังไม่ใช่เวอร์ชันสุดท้าย และจะกลับมาเพิ่ม @tanstack/eslint-plugin-query อีกสองบรรทัดในบทเรียน 17 — นี่คือบทนั้น

สัญญาที่แต่ละส่วนต้องทำให้ได้ — และสิ่งที่มันต้องไม่ทำ:

  • productKeys — ต้องเป็นแหล่งเดียวของ query key ทั้งฟีเจอร์ และทุก key ต้องต่อยอดจาก key ชั้นบนด้วย spread ต้องไม่มี key ไหนเขียนขึ้นมาลอย ๆ
  • productQueries — ต้องคืนผลของ queryOptions() ทุกจาน และหยิบ key จาก productKeys เท่านั้น ต้องไม่เรียก useQuery เอง ต้องไม่เป็น custom hook และต้องไม่มี array ของ key เขียนสด ๆ อยู่ในไฟล์
  • eslint.config.js — ต้องเพิ่มแค่ import ตัว plugin กับ config แนะนำของมันใน extends ต้องไม่แตะกฎเดิมสักข้อ

✍️ ส่วนนี้พิมพ์เอง

✍️ ส่วนนี้พิมพ์เอง — ทำตามลำดับนี้ ห้ามก๊อปวาง ห้ามให้ Agent ช่วยเติม (ถ้าปุ่ม autocomplete ของ Cursor เด้งขึ้นมาแล้วคุณกด Tab รับ นั่นก็คือการก๊อป):

  1. สร้างไฟล์ src/features/products/queries.ts
  2. พิมพ์ทั้งก้อนข้างล่างนี้ — ระหว่างพิมพ์ให้หยุดถามตัวเองที่ String(id) ว่ามันมีไว้ทำไม
  3. npm run lint และ npm run typecheck ให้ผ่านทั้งคู่ (จะผ่าน เพราะ productKeys ถูก export และ type ที่ import มาถูกใช้ครบ)
  4. git commit — ไฟล์ต้องมีอยู่จริงในโปรเจกต์ก่อน prompt ถึงจะ @-mention ได้ และต้อง commit ให้ working tree สะอาด ไม่งั้น git diff ในขั้นตรวจงานจะปนโค้ดที่คุณพิมพ์เองเข้ากับโค้ดของ Agent

src/features/products/queries.ts:

import { CategoryProductsParams, ProductListParams } from "./api";

export const productKeys = {
  all: ["products"] as const,
  lists: () => [...productKeys.all, "list"] as const,
  list: (params: ProductListParams) =>
    [...productKeys.lists(), params] as const,
  byCategory: (params: CategoryProductsParams) =>
    [...productKeys.lists(), "category", params] as const,
  categories: () => [...productKeys.all, "categories"] as const,
  details: () => [...productKeys.all, "detail"] as const,
  detail: (id: string | number) =>
    [...productKeys.details(), String(id)] as const,
};

เหตุผล: cache key ผิด = bug ที่หาไม่เจอ — key ที่สะกดเพี้ยนไม่ทำให้อะไรพัง ไม่มี error ไม่มี warning ไม่มีเส้นแดง มันแค่ทำให้ TanStack Query สร้าง cache ก้อนใหม่เงียบ ๆ แล้วยิง request ซ้ำ หรือหนักกว่านั้นคือแสดงข้อมูลเก่าค้างอยู่ทั้งที่ข้อมูลเปลี่ยนไปแล้ว การพิมพ์ก้อนนี้เองคือวิธีเดียวที่จะทำให้โครงต้นไม้ของ key อยู่ในหัวคุณ และนั่นคือสิ่งเดียวที่ใช้ตรวจได้ เพราะทุกครั้งที่คุณอ่านโค้ดที่แตะ cache หลังจากนี้ — productQueries ที่ Agent กำลังจะเขียนต่อในอีกไม่กี่นาที และเทสต์ของชั้น query ในบทเรียน 32 — สิ่งที่บอกว่า key ถูกหรือผิดคือความจำของคุณ ไม่ใช่เครื่องมือตัวไหน

productKeys — ลำดับชั้นของ key

สังเกตว่าแต่ละ key ไม่ได้เขียนขึ้นมาลอย ๆ แต่ต่อยอดจาก key ชั้นบนด้วย spread (...) เสมอ ทำให้ key ทั้งหมดเรียงเป็นต้นไม้:

  • productKeys.all → ["products"] — รากของทุกอย่างเกี่ยวกับสินค้า
  • productKeys.lists() → ["products", "list"] — กิ่ง "รายการสินค้า" ทุกแบบ
  • productKeys.list({ page: 1 }) → ["products", "list", { page: 1 }] — รายการรวม หน้า 1
  • productKeys.byCategory({ category: "beauty", page: 2 }) → ["products", "list", "category", { category: "beauty", page: 2 }] — รายการตามหมวด
  • productKeys.categories() → ["products", "categories"] — รายชื่อหมวดหมู่
  • productKeys.details() → ["products", "detail"] — กิ่ง "รายละเอียดสินค้า"
  • productKeys.detail(42) → ["products", "detail", "42"] — สินค้าชิ้นเดียว

โครงต้นไม้นี้ไม่ใช่ความสวยงามเปล่า ๆ — มันคือกลไก เพราะเวลา TanStack Query จับคู่ key มันจับแบบ prefix: สั่ง invalidateQueries({ queryKey: productKeys.lists() }) ครั้งเดียว รายการทุกแบบทุกหน้าโดนหมด (ทั้ง list และ byCategory เพราะขึ้นต้นด้วย ["products", "list"] เหมือนกัน) แต่ cache ของหน้ารายละเอียดสินค้าไม่ถูกแตะเลย อยากล้างทุกอย่างของฟีเจอร์นี้ก็ productKeys.all จบ — ระดับความละเอียดของการ invalidate ออกแบบไว้ล่วงหน้าแล้วในโครงต้นไม้

ส่วน as const ที่ห้อยท้ายทุกบรรทัด บอก TypeScript ว่า array เหล่านี้เป็น tuple ค่าตายตัว ไม่ใช่ string[] กว้าง ๆ ซึ่งทำให้ type ของแต่ละ key แม่นยำและ queryOptions นำไป infer ต่อได้เต็มที่

และ String(id) ในบรรทัดสุดท้าย: จำที่ getProduct รับ string | number ได้ไหม? id จาก URL param เป็น string "42" แต่ id จาก object สินค้าเป็น number 42 สำหรับ TanStack Query สองค่านี้คือ key คนละตัว! ถ้าไม่จัดการ เราจะได้ cache สองก้อนของสินค้าชิ้นเดียวกัน และยิง request ซ้ำฟรี ๆ factory จึง normalize ตรงชั้น key — ไม่ว่าใครส่งอะไรมา key ลงเอยเป็น ["products", "detail", "42"] ก้อนเดียวเสมอ ปัญหาทั้งตระกูลถูกปิดที่บรรทัดเดียว

- ต่อท้ายไฟล์ด้วย export const productQueries = { ... } ที่มีสี่จานตามลำดับนี้

  ต่อจาก ...tseslint.configs.recommended

  • AI มักพลาดตรงนี้: เขียนด้วยไวยากรณ์ TanStack Query v4 ซึ่งยังเป็นเวอร์ชันที่มีโค้ดในอินเทอร์เน็ตมากกว่า v5 มาก มีสามอาการ และเส้นแบ่งที่สำคัญคืออันไหน compiler จับได้ อันไหนจับไม่ได้ สองอาการแรกดัง: (1) รูปทรงผิดทั้งก้อน — มันทิ้ง queryOptions แล้วเขียนเป็น custom hook ที่เรียก useQuery(key, fn) แบบส่ง argument สองตัว (v5 รับ options object ก้อนเดียวเท่านั้น) ถ้าเจอให้ git restore . แล้วสั่งใหม่ ไม่ใช่ไล่แก้ทีละบรรทัด (2) เขียน keepPreviousData: true ซึ่งเป็น option ของ v4 ที่ถูกถอดออกไปแล้ว แทนที่จะเป็น placeholderData: keepPreviousData — อาการนี้ typecheck ก็ฟ้องเหมือนกัน เพราะ queryOptions รับ object literal ตรง ๆ TypeScript จึงตรวจ excess property ให้ครบทุก overload ข้อความที่ได้หน้าตาแบบนี้: error TS2769: No overload matches this call. Object literal may only specify known properties, and 'keepPreviousData' does not exist in type 'UndefinedInitialDataOptions<...>'. เจอแล้วแก้ชื่อ option ให้ถูกได้เลย ส่วนอาการที่สามคืออาการที่เงียบสนิทและเป็นตัวที่ต้องใช้ตาคน: ลืมบรรทัดนั้นไปทั้งบรรทัด — ไม่มี property แปลกปลอมให้ compiler ตรวจ lint ผ่าน typecheck ผ่าน หน้าเว็บวันนี้ก็ยังไม่มีอะไรให้ดู แล้วอาการจะไปโผล่ตอนบทเรียน 20 เป็นกริดสินค้าทั้งกริดหายวับกลายเป็น spinner ทุกครั้งที่ผู้ใช้กดเปลี่ยนหน้า — เปิดจาน byCategory นับบรรทัดดูเป็นจุดแรกเสมอ
  • ไม่มีไฟล์ใหม่แม้แต่ไฟล์เดียว — git status ต้องเห็นแค่ queries.ts กับ eslint.config.js ขึ้นสถานะ modified ไม่มี useProducts.ts, index.ts หรือ hook อะไรแถมมา
  • git diff src/features/products/queries.ts ต้องไม่มีบรรทัดไหนใน productKeys ขึ้นเป็นสีแดง เลย มีแค่บรรทัด import ที่ถูกขยาย กับของที่ต่อท้ายไฟล์ — ถ้า Agent จัดรูปแบบ productKeys ใหม่หรือ "ปรับปรุง" ให้ ให้ย้อนเฉพาะส่วนนั้นกลับ
  • ทุกจานใน productQueries คืนผลของ queryOptions({...}) จริง ไม่ใช่ object ธรรมดา — สองแบบนี้หน้าตาเกือบเหมือนกัน ต่างกันตรงที่แบบหลังทำให้ data ในหน้าเพจสูญ type ไปเงียบ ๆ
  • grep -n "queryKey: \[" src/features/products/queries.ts ต้องไม่เจออะไรเลย — ทุก key มาจาก productKeys ทั้งหมด ถ้าเจอ array สด ๆ แม้แต่ที่เดียว แปลว่า factory ถูกข้ามไปแล้วตั้งแต่วันแรก
  • placeholderData: keepPreviousData อยู่ใน byCategory จานเดียว และ keepPreviousData ต้องเป็นค่าที่ import มาจาก @tanstack/react-query ไม่ใช่ true
  • staleTime: 5 * 60 * 1000 อยู่ใน categories จานเดียว และ src/app/queryClient.ts ไม่ขึ้นสถานะ modified — นโยบาย cache ของข้อมูลชนิดหนึ่งต้องไม่ถูกแก้ด้วยการเปลี่ยนค่า default ของทั้งแอป
  • queryFn: getCategories เขียนแบบส่งฟังก์ชันตรง ๆ ไม่ใช่ () => getCategories() — ต่างกันแค่รูปแบบ ไม่ต่างกันที่ผล แต่เป็นข้อที่ diff กับโค้ดอ้างอิงจะไม่ตรงถ้าไม่ตรวจ
  • eslint.config.js: git diff ต้องเห็นบรรทัดใหม่แค่สองบรรทัด (บรรทัด import pluginQuery และบรรทัด ...pluginQuery.configs["flat/recommended"],) บวกกับการที่ array extends ถูกแตกจากบรรทัดเดียวเป็นหลายบรรทัด — อย่างหลังคือฝีมือ Prettier ที่ขึ้นบรรทัดใหม่เมื่อบรรทัดยาวเกิน ไม่ใช่ Agent ทำเกินคำสั่ง กฎใน rules ทุกข้อต้องเหมือนเดิมทุกตัวอักษร
  • สี่จานใน productQueries คั่นกันด้วยบรรทัดว่างหนึ่งบรรทัด เหมือนโค้ดอ้างอิงข้างล่าง — ข้อนี้ prompt ไม่ได้สั่งไว้ และ Prettier ก็ไม่ยุ่งกับบรรทัดว่างที่คนเขียนวางเอง ถ้าของที่ได้มาอัดติดกันหมดก็ไม่ผิดอะไร แค่ diff กับโค้ดอ้างอิงจะไม่ตรง — เป็นตัวอย่างเล็ก ๆ ว่าอะไรที่ prompt ไม่ได้สั่ง คุณจะไม่ได้มันคืนมาเหมือนเดิมทุกครั้ง
  • npm run lint ต้องผ่านเงียบ ๆ — ถ้ามันเริ่มฟ้องกฎที่ขึ้นต้นด้วย @tanstack/query/ นั่นแปลว่า plugin ต่อติดแล้วและกำลังทำงาน ให้อ่านสิ่งที่มันฟ้องจริง ๆ ก่อนแก้
  • ไม่มี any, ไม่มี as กลบ type และไม่มี comment อธิบายสิ่งที่โค้ดบอกอยู่แล้ว

โค้ดอ้างอิง

src/features/products/queries.ts ฉบับเต็มหลังจากรวมสองมือแล้ว (ครึ่งบนคือของที่คุณพิมพ์เอง):

import { keepPreviousData, queryOptions } from "@tanstack/react-query";
import {
  CategoryProductsParams,
  ProductListParams,
  getCategories,
  getProduct,
  getProducts,
  getProductsByCategory,
} from "./api";

export const productKeys = {
  all: ["products"] as const,
  lists: () => [...productKeys.all, "list"] as const,
  list: (params: ProductListParams) =>
    [...productKeys.lists(), params] as const,
  byCategory: (params: CategoryProductsParams) =>
    [...productKeys.lists(), "category", params] as const,
  categories: () => [...productKeys.all, "categories"] as const,
  details: () => [...productKeys.all, "detail"] as const,
  detail: (id: string | number) =>
    [...productKeys.details(), String(id)] as const,
};

export const productQueries = {
  list: (params: ProductListParams = {}) =>
    queryOptions({
      queryKey: productKeys.list(params),
      queryFn: () => getProducts(params),
    }),

  byCategory: (params: CategoryProductsParams) =>
    queryOptions({
      queryKey: productKeys.byCategory(params),
      queryFn: () => getProductsByCategory(params),
      placeholderData: keepPreviousData,
    }),

  categories: () =>
    queryOptions({
      queryKey: productKeys.categories(),
      queryFn: getCategories,
      staleTime: 5 * 60 * 1000,
    }),

  detail: (id: string | number) =>
    queryOptions({
      queryKey: productKeys.detail(id),
      queryFn: () => getProduct(id),
    }),
};

สังเกตว่าไฟล์นี้ import จาก "./api" แบบ relative เพราะอยู่โฟลเดอร์เดียวกัน — ซึ่งตรงตามกติกาในไฟล์ rules และไม่ตรงกับ api.ts ที่ import types ในโฟลเดอร์เดียวกันด้วย @/features/products/types ตามที่ทักไว้ในบทที่แล้ว ตอนนี้คุณเห็นความไม่สม่ำเสมอนั้นครบทั้งสองฝั่งแล้ว

productQueries — เมนูสำเร็จรูปสี่จาน

productQueries คือชั้นที่หน้าเพจจะใช้จริง แต่ละตัว return ผลของ queryOptions() ซึ่งมัด key (จาก factory) + ฟังก์ชัน (จาก api.ts) + พฤติกรรมเฉพาะตัว เป็นก้อนเดียว มาดูการตัดสินใจในแต่ละจาน:

list — จานพื้นฐานที่สุด: key คู่กับ getProducts ตรง ๆ ให้ default = {} เพื่อให้เรียก productQueries.list() เปล่า ๆ ได้เลย สังเกตว่า params ก้อนเดียวกันถูกส่งเข้าทั้ง key และ queryFn — ตัวแปรที่มีผลต่อข้อมูลอยู่ใน key ครบเสมอโดยโครงสร้าง ไม่ใช่โดยความจำของคนเขียน bug "ลืมใส่ตัวแปรใน key" ตายตั้งแต่เกิด จานนี้จะถูกใช้ครั้งแรกในหน้า Home บทเรียน 19 (productQueries.list({ limit: 5 }) สำหรับแถบ Deals of the day)

byCategory กับ placeholderData: keepPreviousData — จานนี้แก้ปัญหา UX ที่ชื่อว่า pagination flash: ลองนึกภาพหน้า Category ตอนผู้ใช้กดไปหน้า 2 — เลขหน้าที่เปลี่ยนทำให้ query key เปลี่ยน กลายเป็น query ใหม่เอี่ยมที่ยังไม่มีข้อมูลใน cache ผลคือ data เป็น undefined ชั่วขณะ รายการสินค้าทั้งกริดหายวับกลายเป็น spinner แล้วค่อยเด้งกลับมา — จอกะพริบ ความสูงหน้ากระโดด scroll หลุด ทุกครั้งที่เปลี่ยนหน้า keepPreviousData สั่งว่า "ระหว่างรอข้อมูลหน้าใหม่ ให้โชว์ข้อมูลหน้าเก่าไปพลาง ๆ" หน้าจอเลยนิ่งสนิท พอของใหม่มาถึงค่อยสลับเนียน ๆ (ข้อมูลเก่าที่ยืมมาโชว์เป็นแค่ placeholder — ไม่ได้ถูกบันทึกเป็น cache ของ key ใหม่) จานนี้ถูกใช้ทั้งในหน้า Home (บทเรียน 19) และหน้า Category (บทเรียน 20) โดยทั้งสองหน้าจะ spread มันแล้วเติม enabled เข้าไปตอนเรียก

categories กับ staleTime: 5 * 60 * 1000 — รายชื่อหมวดหมู่เป็นข้อมูลที่แทบไม่เคยเปลี่ยน แต่ถูกใช้แสดงเมนูซึ่งโผล่บ่อยมาก ถ้าปล่อยตาม default ของแอป (60 วินาที ที่ตั้งไว้ใน queryClient.ts บทเรียน 11) เราจะ refetch รายชื่อหมวดหมู่ถี่เกินเหตุ จานนี้จึง override เป็น 5 นาที: ภายในช่วงนั้นทุกหน้าที่ mount ขึ้นมาได้ข้อมูลจาก cache ทันทีโดยไม่ยิง network เลย นี่คือความสวยของ queryOptions — นโยบาย cache ของข้อมูลแต่ละชนิดถูกประกาศไว้ที่เดียวคู่กับตัว query ไม่ใช่ให้แต่ละหน้าไปตั้งกันเอง

detail — จานเดียวที่ key ผ่านการ normalize มาแล้ว (ด้วย String(id) ที่คุณพิมพ์เอง) หน้า Product ในบทเรียน 21 จะส่ง id ที่ได้จาก useParams() ซึ่งเป็น string เข้ามา ส่วนเทสต์ในบทเรียน 32 เรียกมันด้วย number ตรง ๆ (productQueries.detail(7)) — ทั้งสองทางลงเอยที่ cache ก้อนเดียวกัน เพราะ Product["id"] เป็น number ส่วน URL param เป็น string เสมอ

💡 ตำแหน่งของไฟล์นี้ก็สื่อสารเจตนา: queries.ts อยู่ใน features/products ประกบ api.ts และ types.ts — ฟีเจอร์สินค้าเป็นเจ้าของข้อมูลของตัวเองครบวงจร ตั้งแต่รูปร่างข้อมูล การเรียก ยันนโยบาย cache ภายหลังถ้าเพิ่มฟีเจอร์ที่มีข้อมูลฝั่ง server ของตัวเอง ก็ทำซ้ำแพตเทิร์นเดิมนี้ได้เลย — features/checkout ในบทเรียน 28 จะเป็นตัวอย่างที่สอง

eslint.config.js หลังต่อสาย

ไฟล์ฉบับสมบูรณ์เป็นแบบนี้ — สองบรรทัดที่เพิ่มคือบรรทัด import pluginQuery กับบรรทัด ...pluginQuery.configs["flat/recommended"] ที่เหลือเหมือนเดิมทุกตัวอักษร:

import js from "@eslint/js";
import globals from "globals";
import reactHooks from "eslint-plugin-react-hooks";
import reactRefresh from "eslint-plugin-react-refresh";
import tseslint from "typescript-eslint";
import importX from "eslint-plugin-import-x";
import pluginQuery from "@tanstack/eslint-plugin-query";
import prettierConfig from "eslint-config-prettier";

export default tseslint.config(
  { ignores: ["dist", "coverage"] },
  {
    extends: [
      js.configs.recommended,
      ...tseslint.configs.recommended,
      ...pluginQuery.configs["flat/recommended"],
    ],
    files: ["**/*.{ts,tsx}"],
    languageOptions: {
      ecmaVersion: 2022,
      globals: globals.browser,
    },
    plugins: {
      "react-hooks": reactHooks,
      "react-refresh": reactRefresh,
      "import-x": importX,
    },
    rules: {
      "react-hooks/rules-of-hooks": "error",
      "react-hooks/exhaustive-deps": "warn",
      "react-refresh/only-export-components": [
        "warn",
        { allowConstantExport: true },
      ],
      "import-x/order": "error",
    },
  },
  prettierConfig,
);

ตัวอย่างกฎที่ได้มา:

  • @tanstack/query/exhaustive-deps — ตัวจับ bug คลาสสิกที่เล่าไว้ต้นบท: ถ้า queryFn ใช้ตัวแปรที่ไม่อยู่ใน queryKey จะโดนขีดเส้นเตือนทันทีตั้งแต่ใน editor ไม่ต้องรอไปงงตอนหน้าเว็บไม่ refetch
  • @tanstack/query/stable-query-client — เตือนถ้าเผลอสร้าง QueryClient ข้างในคอมโพเนนต์ ซึ่งจะทำให้ cache ถูกโยนทิ้งทุก re-render (เราทำถูกไปแล้วในบทเรียน 11 — สร้างไว้นอกคอมโพเนนต์ใน queryClient.ts)
  • @tanstack/query/no-rest-destructuring — เตือนการ destructure ผลของ useQuery ด้วย rest spread ซึ่งทำลายการ optimize เรื่อง re-render ของ TanStack Query

สังเกตว่ากฎชุดนี้ยังไม่มีอะไรให้จับในวันนี้ เพราะไฟล์ที่เราเพิ่งเขียนไม่มี useQuery สักตัว มันจะเริ่มทำงานจริงตั้งแต่บทเรียน 19 เป็นต้นไป ตอนที่หน้าเพจเริ่มเรียก query — และนั่นคือจังหวะที่ถูกต้องของการติดตั้ง linter: ก่อนโค้ดที่มันต้องตรวจจะถูกเขียน ไม่ใช่หลัง

🤔 อธิบายให้ได้

  1. เขียนออกมาให้ได้ว่า productKeys.detail(42) กับ productKeys.detail("42") คืน array หน้าตาอย่างไรทั้งคู่ ชี้บรรทัดที่ทำให้มันเท่ากัน แล้วค้นทั้งโปรเจกต์ (รวมบทที่ยังมาไม่ถึง) ว่าที่ไหนบ้างที่เรียก detail ด้วย number และที่ไหนเรียกด้วย string — ถ้าลบการ normalize ออก ที่ไหนจะได้ cache คนละก้อนกับที่ไหน
  2. สั่ง invalidateQueries({ queryKey: productKeys.lists() }) หนึ่งครั้ง จะล้าง cache ของจานไหนบ้างในสี่จาน และไม่ล้างจานไหน ตอบจากโครงของ key ล้วน ๆ โดยไม่ต้องเปิดเอกสาร TanStack Query
  3. categories เขียน queryFn: getCategories แต่ list เขียน queryFn: () => getProducts(params) — อธิบายว่าทำไมสองจานนี้เขียนคนละท่า และจะเกิดอะไรขึ้นถ้าเปลี่ยน list เป็น queryFn: getProducts เฉย ๆ
