ติดตั้ง Swiper

แบนเนอร์ด้านบนสุดของหน้าเป็น carousel — รูปหลายรูปสลับกันเลื่อนอัตโนมัติ พร้อมปุ่มลูกศรและจุดบอกตำแหน่ง การเขียน carousel เองให้ครบทั้ง touch swipe, loop, autoplay และ accessibility เป็นงานใหญ่เกินตัวมาก นี่คือจังหวะที่ควรใช้ library ที่พิสูจน์แล้ว เราใช้ Swiper ซึ่งเป็น carousel library ที่นิยมที่สุดตัวหนึ่งและมี React components ให้ในตัว ตามกติกาเดิม dependency เราติดตั้งเอง:

npm install swiper
git add -A && git commit -m "chore: install swiper"

Banner: carousel ตัวแรกของเรา

Banner เป็นของหน้า Home โดยเฉพาะ ไม่มีหน้าอื่นใช้ เราจึงไม่วางมันใน shared แต่วางเป็นคอมโพเนนต์ลูกของหน้า Home เอง — สังเกต pattern โฟลเดอร์ components ซ้อนอยู่ใต้หน้าเพจ ซึ่งเราจะใช้อีกกับหน้า Category และ Product

วิธีใช้ Swiper ฝั่ง React มีสามส่วน:

  • Components — <Swiper> คือกรอบ carousel และ <SwiperSlide> คือสไลด์แต่ละใบ เรา map จาก array banners ที่ประกาศไว้ในไฟล์ (ใช้แค่รูป 01 กับ 02 — ส่วนรูป 03 เก็บไว้เป็นแบนเนอร์ยาวท้ายหน้า เดี๋ยวเจอใน Home.tsx)
  • Modules — Swiper แยกความสามารถเป็นโมดูลเพื่อไม่ให้ bundle บวม อยากได้อะไรต้องส่งเข้า prop modules เอง: Navigation ให้ปุ่มลูกศรซ้ายขวา, Pagination ให้จุดบอกตำแหน่งด้านล่าง (clickable: true = กดจุดเพื่อกระโดดข้ามสไลด์ได้), Autoplay เลื่อนเองทุก 3 วินาที (delay: 3000 มีหน่วยเป็น millisecond) โดย disableOnInteraction: false แปลว่าถึงผู้ใช้จะปัดเอง autoplay ก็ยังทำงานต่อ ไม่หยุดถาวร ปิดท้ายด้วย loop ให้สไลด์สุดท้ายวนกลับไปสไลด์แรกแบบไร้รอยต่อ
  • CSS — swiper/swiper-bundle.css คือ style ของปุ่ม จุด และ animation ทั้งหมด ไฟล์นี้ Banner import เองเพราะมีแค่คอมโพเนนต์นี้ที่ใช้ ต่างจาก skeleton.css ที่ import กลางใน main.tsx เมื่อบทที่แล้ว เพราะ skeleton โผล่ได้ทั่วแอป
  • ระวังชื่อชนกัน: Pagination ของ Swiper ในไฟล์นี้เป็นคนละตัวกับคอมโพเนนต์ Pagination ของเราจากบทเรียน 13 — อยู่กันคนละไฟล์เลยไม่มีปัญหา แต่ถ้าวันหนึ่งต้อง import ทั้งคู่ในไฟล์เดียว ใช้ import { Pagination as SwiperPagination } แก้ได้ นี่เป็นข้อที่ต้องเขียนไว้ในบริบทของ prompt ด้วย ไม่งั้น Agent ที่เห็นทั้งโปรเจกต์อาจ import ผิดตัว

แบ่ง prompt เป็นสองรอบ

ถ้ารวมทุกอย่างของบทนี้เป็น prompt เดียว สิ่งที่คุณจะได้กลับมาคือ: ไฟล์ใหม่ 2 ไฟล์ + ไฟล์ที่ถูกเขียนทับทั้งไฟล์อีก 1 ไฟล์ รวมแล้วประมาณ 200 บรรทัด ในนั้นมี query สามตัว, hook สองแบบ, ternary ซ้อนสองชั้นสองชุด, คอมโพเนนต์ที่มาจากหกโฟลเดอร์ต่างกัน และรูปภาพเจ็ดไฟล์ที่ path ต้องตรงเป๊ะ ทั้งหมดมาถึงพร้อมกันในหน้าจอเดียว

ปัญหาไม่ใช่ว่า Agent ทำไม่ได้ — มันทำได้ ปัญหาคือคุณจะรีวิวมันไม่ไหว และจะไม่ยอมรับกับตัวเองว่ารีวิวไม่ไหว diff 200 บรรทัดที่มีของไม่ซ้ำกันเลยสักบล็อก คือขนาดที่คนเริ่มเลื่อนผ่านแทนที่จะอ่าน แล้วสิ่งที่หลุดไปได้จะไม่ใช่ของที่มองเห็นบนจอ (พวกนั้นเดี๋ยวก็เจอตอนเปิดเบราว์เซอร์) แต่เป็นของที่มองไม่เห็น — สาขา error ที่หายไปหนึ่งสาขา, enabled ที่หลุด, useMemo ที่กลายเป็น new Date() เปล่า ๆ

เส้นแบ่งที่เราจะใช้ตัดคือความเป็นอิสระ: หน้า Home มีสองส่วนที่ยืนอยู่ได้ด้วยตัวเอง

  • รอบที่ 1 — โครงหน้า: Banner, แถว FeatureCard, section หมวดหมู่ (CategoryMenu + ProductsList) และแบนเนอร์ยาวปิดท้าย จบรอบนี้แล้ว npm run dev ต้องได้หน้า Home ที่ใช้งานได้จริง — กดสลับหมวดได้ คลิกการ์ดไปหน้าสินค้าได้ ไม่ใช่ครึ่งหน้าที่พังรอชิ้นส่วนอีกครึ่ง
  • รอบที่ 2 — โซนดีล: หัวข้อ "DEALS OF THE DAY" พร้อม CountdownTimer, query สินค้าห้าตัวแรก และตารางรูปโปรโมชัน ทั้งก้อนนี้แทรกเข้าไประหว่างสอง section ที่มีอยู่แล้ว

ผลที่ได้จากการตัดตรงนี้มีสามอย่างที่วัดได้จริง อย่างแรก: git diff ของรอบที่ 2 มีไฟล์เดียว คือ Home.tsx และเป็นการเพิ่มล้วน ๆ ไม่ใช่การเขียนทับ — คุณอ่านทีละบรรทัดได้จริงในเวลาที่สมเหตุสมผล อย่างที่สอง: ระหว่างสองรอบมี git commit คั่นอยู่ ถ้ารอบที่ 2 ออกมาไม่เข้าท่า git restore . คืนคุณกลับไปที่หน้า Home ที่ทำงานได้ ไม่ใช่กลับไปที่หน้าว่าง อย่างที่สาม: บริบทของรอบที่ 2 แม่นกว่ารอบที่ 1 มาก เพราะคุณ @-mention Home.tsx ที่มีอยู่จริงแล้วได้ Agent จึงเห็นสไตล์การเขียน การจัด import และชื่อตัวแปรที่ใช้อยู่ แทนที่จะเดาเอง

เกณฑ์ที่ใช้ตัดสินใจได้ทั่วไป: ถ้า prompt เดียวจะทำให้เกิดของที่คุณต้องตรวจเกินหนึ่งหน้าจอ และของนั้นแบ่งเป็นก้อนที่ทดสอบแยกกันได้ ให้แบ่ง เกณฑ์ที่ไม่ควรใช้คือ "รู้สึกว่าเยอะ" — ของสี่คอมโพเนนต์ในบทเรียน 14 ก็ดูเยอะ แต่ทั้งสี่ตัวเป็นอิสระต่อกันสนิทและสั้นตัวละไม่ถึง 40 บรรทัด รอบเดียวจึงรับได้

Home.tsx: เดินดูทีละส่วน

ก่อนส่ง prompt ต้องเข้าใจของสี่อย่างที่จะอยู่ในไฟล์นี้ให้ขาด เพราะสามในสี่อย่างเป็นสิ่งที่ Agent เขียนผิดได้โดยที่ทั้ง lint และ typecheck ผ่านฉลุย

ส่วนที่ 1: state และ queries

หน้านี้ยิงสาม queries และทุกตัวใช้ factory จากบทเรียน 17 — ไม่มีการเขียน queryKey ด้วยมือแม้แต่ตัวเดียว:

  • productQueries.list({ limit: 5 }) — สินค้าขายดี 5 ตัวแรกสำหรับแถว "DEALS OF THE DAY" สังเกตการ rename ตอน destructure: data: bestProductsData, isLoading: isBestProductsLoading — จำเป็นเพราะหน้านี้มีหลาย query ชื่อ data เฉย ๆ จะชนกัน
  • productQueries.categories() — รายชื่อหมวดหมู่สำหรับ CategoryMenu จำได้ไหมว่า factory ตัวนี้ตั้ง staleTime 5 นาทีไว้ เพราะรายชื่อหมวดแทบไม่เปลี่ยน — หน้า Category ในบทเรียน 20 ที่เรียก query เดียวกันจะได้ข้อมูลจาก cache ทันทีโดยไม่ยิง API ซ้ำ
  • productQueries.byCategory(…) — สินค้า 12 ตัวของหมวดที่กำลังเลือก ตัวนี้มีเงื่อนไขพิเศษ: enabled: currentCategory !== null แปลว่า "อย่าเพิ่งยิงจนกว่าจะรู้ว่าหมวดไหน" เพราะตอน mount แรกสุด รายชื่อหมวดยังโหลดไม่เสร็จ currentCategory ยังเป็น null — ถ้าไม่มี enabled เราจะยิง API ด้วย category="" ซึ่งไร้ความหมาย นี่คือ pattern "dependent query" ที่เจอในคอร์ส React พื้นฐาน: query หนึ่งรอผลของอีก query หนึ่ง

บรรทัดที่สำคัญที่สุดของหน้านี้คือบรรทัดสั้น ๆ นี้:

const currentCategory = selectedCategory ?? categories?.[0] ?? null;

โจทย์คือ: ตอนเปิดหน้ามาให้เลือกหมวดแรกโดยอัตโนมัติ แต่พอผู้ใช้คลิกหมวดอื่นก็ให้เปลี่ยนตาม มือใหม่จำนวนมากจะแก้โจทย์นี้ด้วย useEffect ที่คอยเฝ้า categories แล้ว setSelectedCategory(categories[0]) เมื่อโหลดเสร็จ — ซึ่งเป็น anti-pattern ที่บทเรียน Effects ของคอร์ส React พื้นฐาน เตือนไว้ตรง ๆ ว่า "อย่าใช้ effect เพื่อ sync state จาก props/data" เพราะได้ render เพิ่มฟรีหนึ่งรอบ แถมสร้างโอกาสที่ state สอง copy จะขัดแย้งกันเอง วิธีที่ถูกคือคำนวณสด (derive) ระหว่าง render: selectedCategory เก็บเฉพาะ "สิ่งที่ผู้ใช้เลือกเอง" (เริ่มจาก null = ยังไม่เคยเลือก) แล้วค่าที่ใช้จริงคือ "ที่ผู้ใช้เลือก ถ้าไม่มีก็หมวดแรก ถ้ายังโหลดไม่เสร็จก็ null" — nullish coalescing ต่อกันสองชั้นอ่านเป็นภาษาคนได้เลย และไม่มีทาง desync เพราะมันไม่ได้ถูกเก็บไว้ที่ไหนเลย

นี่คือของชิ้นแรกที่ Agent มีสิทธิ์เขียนผิดแบบเงียบ ๆ: useEffect เวอร์ชันนั้นทำงานได้บนจอเหมือนกันทุกประการ

ส่วนที่ 2: targetDate สำหรับตัวนับถอยหลัง

แถวดีลประจำวันมี CountdownTimer จากบทเรียน 14 ซึ่งรับ prop targetDate เป็นเวลาเป้าหมาย เราตั้งไว้ที่ "พรุ่งนี้เวลานี้" ทำไมต้อง useMemo ด้วย dependency ว่าง? เพราะถ้าเขียน new Date() เปล่า ๆ ในตัวคอมโพเนนต์ ทุกครั้งที่ Home re-render (ซึ่งเกิดตลอด — ทุกการคลิกหมวด ทุกครั้งที่ query กลับมา) เป้าหมายจะถูกสร้างใหม่เลื่อนไปเรื่อย ๆ ตัวนับจะค้างที่ 24 ชั่วโมงตลอดกาล useMemo(…, []) ล็อกให้คำนวณครั้งเดียวตอน mount แล้วใช้ค่าเดิมไปตลอดชีวิตของหน้า

ของชิ้นที่สองที่ผิดแบบเงียบ ๆ ได้: ตัวเลขบนจอยังเดินทุกวินาทีเหมือนเดิม ต่างกันแค่มันจะไม่มีวันลดลงต่ำกว่า 23:59:5x

ส่วนที่ 3: pattern แสดงผล error → loading → data

ทั้งแถวดีลและรายการสินค้าตามหมวดใช้ pattern เดียวกันในการแสดงผล ดูตัวอย่างจากแถวดีล:

  <ErrorMessage />

  <ProductsList

  />
)}

ternary ซ้อนสองชั้นอ่านจากบนลงล่าง: พังไหม → แสดง ErrorMessage, ยังโหลดอยู่ไหม → แสดง ClipLoader, ปกติ → แสดงรายการสินค้า ลำดับนี้สำคัญ: เช็ค error ก่อน loading เสมอ เพราะถ้าเช็ค loading ก่อนแล้ว query fail ไปแล้ว (isLoading เป็น false, isError เป็น true) โค้ดที่เช็คสลับลำดับบางแบบจะหลุดไปพยายาม render ข้อมูลที่ไม่มี และที่สำคัญกว่านั้น — การมี error state ในทุกจุดที่ยิง API คือสิ่งที่แยกแอปมืออาชีพจากแอปฝึกหัด: เน็ตล่มแล้วผู้ใช้ต้องเห็นข้อความบอก ไม่ใช่ spinner หมุนค้างตลอดกาลโดยไม่มีวันมีอะไรมา

สังเกตด้วยว่า error ของแต่ละ section เป็น inline — ถ้าแถวดีลโหลดพลาด ผู้ใช้เห็นข้อความ error เฉพาะแถวนั้น แต่แบนเนอร์ รูปโปรโมชัน และรายการหมวดหมู่ยังทำงานปกติ หน้าไม่ล้มทั้งหน้าเพราะ API ตัวเดียวสะดุด
