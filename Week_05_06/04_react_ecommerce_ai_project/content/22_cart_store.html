สร้าง Cart Store ด้วย Context และ useReducer

Cart Store

ถึงตอนนี้หน้า Home, Category และ Product ของเราดึงข้อมูลจริงมาแสดงได้ครบแล้ว แต่ปุ่ม Add To Cart บนหน้า Product ยังกดแล้วเงียบกริบ — เพราะแอปเรายังไม่มี "ตะกร้า" ให้ใส่ของเลย ในบทนี้เราจะสร้างหัวใจของตะกร้าสินค้า: Cart Store ที่เก็บ state, กติกาการแก้ไข state และการบันทึกลง localStorage ให้ตะกร้าอยู่รอดแม้ผู้ใช้ปิดเบราว์เซอร์ไปแล้ว ส่วนการเอา store ไปต่อกับปุ่มและหน้าจอจริง ๆ จะเป็นเรื่องของสองบทถัดไป

และบทนี้เป็นบทที่กลับมาพิมพ์เองอีกครั้งหลังจากห่างหายไปตั้งแต่บทเรียน 17 — ไฟล์ที่จะพิมพ์คือ cartReducer.ts ซึ่งมีที่ทางในลำดับงานแปลกกว่าทุกครั้งที่ผ่านมา เดี๋ยวเราจะไล่เหตุผลกันทีละขั้น

Client state vs Server state — ทำไมตะกร้าไม่ใช้ TanStack Query

ข้อมูลทุกอย่างที่เราจัดการมาจนถึงตอนนี้ — รายการสินค้า, รายละเอียดสินค้า, หมวดหมู่ — เป็น server state: เจ้าของตัวจริงของข้อมูลคือ server (dummyjson) ฝั่งเราแค่ขอสำเนามาแสดง ข้อมูลแบบนี้มีปัญหาเฉพาะตัว เช่น อาจล้าสมัย ต้อง refetch ต้องมี cache — ซึ่ง TanStack Query เกิดมาเพื่อแก้ปัญหาชุดนี้โดยเฉพาะ

แต่ตะกร้าสินค้าไม่เหมือนกัน dummyjson ไม่รู้จักตะกร้าของผู้ใช้แต่ละคน ไม่มี endpoint ให้ sync ตะกร้าขึ้นไป ข้อมูลตะกร้าเกิดและตายในเบราว์เซอร์ของผู้ใช้ล้วน ๆ — นี่คือ client state เจ้าของตัวจริงคือแอปของเราเอง ถ้าเอา TanStack Query มาเก็บมันจะผิดฝาผิดตัวทันที เพราะไม่มีอะไรให้ fetch ไม่มีอะไรให้ stale เครื่องมือที่ถูกต้องคือของที่คุณเรียนมาแล้วในคอร์ส React พื้นฐาน: useReducer + Context

ทำไมไม่ใช้ useState เฉย ๆ? เพราะตะกร้ามีการแก้ไขหลายแบบที่เล่นกับข้อมูลก้อนเดียวกัน — เพิ่มสินค้า (ซึ่งต้องเช็คว่ามีอยู่แล้วหรือยัง), ลบสินค้า, ปรับจำนวน, ล้างตะกร้า ถ้ากระจาย logic พวกนี้ไปตาม event handler ของแต่ละ component กติกาจะซ้ำซ้อนและหลุดง่าย useReducer บังคับให้กติกาทั้งหมดรวมอยู่ในฟังก์ชันเดียวที่ทดสอบได้ ส่วน Context ทำให้ทุก component — ตั้งแต่ Header ยันหน้า Checkout — เห็นตะกร้าใบเดียวกันโดยไม่ต้องส่ง props ทะลุลงไปหลายชั้น

เก็บสามย่อหน้าข้างบนไว้ให้ดี เพราะมันคือเส้นแบ่งที่ตอบคำถามได้ทั้งชีวิตการทำงาน: ข้อมูลก้อนนี้มีเจ้าของอยู่ที่ไหน ถ้าเจ้าของอยู่ที่ server ให้ query library ดูแล ถ้าเจ้าของอยู่ในเบราว์เซอร์ ให้ React ดูแลเอง คำถามข้อนี้ตอบผิดเมื่อไหร่ คุณจะได้ cache ที่ไม่มีอะไรให้ cache หรือ state ที่ล้าสมัยโดยไม่มีใครไป refetch ให้

โครงสร้างไฟล์ของ feature cart

เราจะสร้าง 5 ไฟล์ในบทนี้ วางตามโครง feature-based ที่ตกลงกันไว้ตั้งแต่บทเรียน 05 (ตอนนั้นเรา mkdir โฟลเดอร์ src/features/cart/ ทิ้งไว้ และมันว่างเปล่ามาจนถึงวันนี้):

src/features/cart/
├── store/
│   ├── CartContext.tsx    # types + ตัว context
│   ├── cartReducer.ts     # กติกาการแก้ state (pure function)

สังเกตว่าเราไม่ยัดทุกอย่างลงไฟล์เดียว: types และ context อยู่ที่หนึ่ง, reducer เป็น pure function ล้วน ๆ อยู่อีกไฟล์, ส่วนที่คุย localStorage แยกไปอีกไฟล์ การแบ่งแบบนี้ไม่ใช่ความเยอะ — มันคือเหตุผลที่บทเรียน 31 เราจะเขียน unit test ให้ cartReducer และ cartStorage ได้ง่าย ๆ โดยไม่ต้อง render อะไรเลยสักตัว

ทำไมบทนี้ต้องแบ่งเป็นสองรอบ และทำไม ✍️ ต้องอยู่ตรงกลาง

กฎที่เราได้จากบทเรียน 12 คือ: สิ่งที่พังเมื่อคุณตัดไฟล์ X ออกจาก prompt คือไฟล์ที่ import X ไม่ใช่ตัว X เอง เอากฎนี้มาจับกับ cartReducer.ts ที่เราตั้งใจจะพิมพ์เอง แล้วไล่สายการพึ่งพาของห้าไฟล์ในบทนี้ดู:

  • CartContext.tsx — ไม่ import ไฟล์ไหนในกลุ่มนี้เลย
  • cartStorage.ts — import CartState จาก ./CartContext
  • cartReducer.ts — import CartActionTypes, CartItem, CartState จาก ./CartContext
  • CartProvider.tsx — import ทั้งสามไฟล์ข้างบน
  • useCart.ts — import CartContext จาก ./store/CartContext

ทีนี้ปัญหาก็โผล่ชัด ๆ: ไฟล์ที่เราจะพิมพ์เองอยู่ตรงกลางสาย ไม่ใช่ต้นสายแบบ Button ในบทเรียน 12 ผลคือทั้งสองท่าที่เคยใช้มาใช้ไม่ได้สักท่า

  • พิมพ์ก่อนแล้วค่อยส่ง prompt (ท่าบทเรียน 12) — ทำไม่ได้ เพราะ cartReducer.ts import CartContext ที่ยังไม่มีตัวตน typecheck ตายตั้งแต่บรรทัดแรกของไฟล์ที่คุณเพิ่งพิมพ์
  • ส่ง prompt ก้อนเดียวแล้วสั่งว่า "ห้ามสร้าง cartReducer.ts" — ทำไม่ได้ เพราะสิ่งที่พังไม่ใช่ cartReducer.ts (มันไม่มีอยู่ ก็ไม่มีอะไรให้พัง) แต่คือ CartProvider.tsx ที่ import { cartReducer } from "./cartReducer" — Agent จะได้ไฟล์ที่ import ของที่ไม่มีจริง แล้ววงจรตรวจงานขั้นที่สามเดินไม่ได้ทั้งรอบ

ทางออกคือตัด prompt ตามทิศทางการพึ่งพา เหมือนที่บทเรียน 21 ทำ แล้วเสียบมือของเราเข้าไปตรงรอยตัดพอดี:

  1. รอบที่ 1 — Agent สร้าง CartContext.tsx และ cartStorage.ts สองไฟล์ที่อยู่ต้นสาย ไม่มีตัวไหนต้องการ reducer จบรอบนี้ lint และ typecheck ผ่านสะอาด
  2. ✍️ คุณพิมพ์ cartReducer.ts เอง ตอนนี้ CartContext มีอยู่จริงแล้ว ไฟล์ที่พิมพ์จึง typecheck ผ่านทันที commit ให้ working tree สะอาด
  3. รอบที่ 2 — Agent สร้าง CartProvider.tsx, useCart.ts และแก้ providers.tsx รอบนี้ทุกอย่างที่ปลายสายต้องใช้มีอยู่จริงหมดแล้ว และ prompt @-mention cartReducer.ts ที่คุณเพิ่งพิมพ์ได้เลย

ผลพลอยได้อยู่ที่ขั้นที่ 3: ไฟล์ที่คุณพิมพ์เองกลายเป็นบริบทของรอบถัดไปพอดี — Agent เห็น signature จริงของ cartReducer และ type CartAction ไม่ต้องเดาว่ามันรับอะไรคืนอะไร นี่คือกลไกเดียวกับบทเรียน 12 แค่คราวนี้มันเกิดขึ้นกลางบทแทนที่จะเป็นต้นบท

สัญญาที่แต่ละไฟล์ต้องทำให้ได้ — และสิ่งที่มันต้องไม่ทำ:

  • CartContext.tsx — ต้องประกาศ type ทั้งหมดของ feature และสร้าง context ที่มีค่า default เป็น undefined ต้องไม่มี component ไม่มี provider และต้องไม่รู้จัก localStorage หรือ reducer
  • cartStorage.ts — ต้องกันไม่ให้ error จาก localStorage หลุดออกจากไฟล์นี้ได้เลยแม้แต่ทางเดียว และต้องตรวจรูปร่างของข้อมูลก่อนเชื่อมัน ต้องไม่รู้จัก React และต้องไม่ import reducer
  • cartReducer.ts — ต้องเป็น pure function ที่คืน state ก้อนใหม่ทุก case ต้องไม่แตะ localStorage ไม่ยิง API และต้องไม่ import อะไรจาก react
  • CartProvider.tsx — ต้องอ่าน localStorage ผ่าน lazy initializer ครั้งเดียวตอน mount และต้องเขียนกลับทุกครั้งที่ state เปลี่ยน ต้องไม่ส่ง dispatch ออกไปให้คนนอกเห็น
  • useCart.ts — ต้องโยน error ที่อ่านรู้เรื่องเมื่อถูกเรียกนอก provider และต้องเป็นทางเข้าเดียวของ feature นี้ ต้องไม่ export CartContext ซ้ำออกไป
  • providers.tsx — ต้องเปลี่ยนแค่สองจุด (บรรทัด import และการห่อ children) ต้องไม่แตะ queryClient และ Devtools ต้องอยู่นอก CartProvider เหมือนเดิม

        image,
        originalPrice,
      } = action.payload;

      const existingItem = state.items.find((item) => item.id === id);
      if (existingItem) {
        return {
          ...state,
          items: state.items.map((item) =>
            item.id === id
              ? { ...item, quantity: item.quantity + quantity }
              : item,
          ),
        };
      }

      return {
        ...state,
        items: [
          ...state.items,
          { id, title, price, quantity, image, originalPrice },
        ],
      };
    }
    case CartActionTypes.REMOVE_FROM_CART: {
      return {
        ...state,
        items: state.items.filter((item) => item.id !== action.payload.id),
      };
    }
    case CartActionTypes.UPDATE_QUANTITY: {
      return {
        ...state,
        items: state.items.map((item) =>
          item.id === action.payload.id
            ? { ...item, quantity: action.payload.quantity }
            : item,
        ),
      };
    }
    case CartActionTypes.CLEAR_CART: {
      return { ...state, items: [] };
    }
    default:
      return state;
  }
};

เหตุผล: หัวใจของบทนี้ และเป็นสิ่งที่ AI mutate state พลาดบ่อยที่สุด — โค้ดที่ push ลง array เดิมหรือ item.quantity += 1 นั้น lint ผ่าน typecheck ผ่าน และดูเหมือนถูกทุกตัวอักษร อาการจะไปโผล่เป็น "กด Add To Cart แล้วตัวเลขไม่ขยับ" ในอีกสองบทข้างหน้า ห่างจากต้นเหตุจนตามกลับมาไม่ถูก ถ้าคุณไม่เคยพิมพ์ท่า immutable นี้เองสักครั้ง คุณจะไม่มีอะไรในหัวไว้เทียบตอนอ่าน reducer ของคนอื่น

CartAction เป็น discriminated union แบบเดียวกับที่คุณเจอในคอร์ส React พื้นฐาน: แต่ละ action ประกาศ payload ของตัวเองชัดเจน พอ TypeScript เห็น case CartActionTypes.ADD_TO_CART มันจะ narrow type ให้เองว่า action.payload ในบล็อกนั้นคือ CartItem เต็ม ๆ ส่วน CLEAR_CART ไม่ต้องมี payload เลย

ไล่กติกาทีละ case:

  • ADD_TO_CART — case ที่ฉลาดสุดในนี้ เรา destructure payload พร้อมตั้ง default quantity = 1 กันเหนียว จากนั้นเช็คก่อนว่าสินค้าตัวนี้อยู่ในตะกร้าแล้วหรือยัง ถ้ามีอยู่แล้ว เราไม่เพิ่มแถวใหม่ให้ซ้ำ แต่ map ทั้ง array แล้วบวก quantity เข้าไปในแถวเดิม (กด Add To Cart สินค้าเดิมสองครั้ง = แถวเดียว จำนวน 2) ถ้ายังไม่มี ค่อย spread array เดิมแล้วต่อ item ใหม่ท้ายสุด
  • REMOVE_FROM_CART — filter เอาทุกแถวที่ id ไม่ตรงเก็บไว้ ได้ array ใหม่ที่ไม่มีแถวนั้น
  • UPDATE_QUANTITY — map หาแถวที่ id ตรงแล้วเขียนทับ quantity ด้วยค่าใหม่ตรง ๆ (ไม่ใช่บวกเพิ่ม — ตัวนี้ไว้ใช้กับปุ่ม +/− ในหน้า Cart บทเรียน 24)
  • CLEAR_CART — คืน state ที่ items เป็น array ว่าง เราจะได้ใช้ตัวนี้จริงตอนสั่งซื้อสำเร็จในบทเรียน 28
  • default — action ที่ไม่รู้จักให้คืน state เดิมเฉย ๆ ไม่พัง ไม่เดา
🚨 สังเกตว่าไม่มีบรรทัดไหนแก้ state เดิมเลย — ไม่มี push, ไม่มี item.quantity += 1 ทุก case สร้าง object และ array ใหม่ด้วย spread, map, filter เสมอ นี่ไม่ใช่แค่สไตล์: React เทียบ state เก่า-ใหม่ด้วย reference ถ้าคุณ mutate ของเดิมแล้วคืนก้อนเดิมกลับไป React จะคิดว่าไม่มีอะไรเปลี่ยนและไม่ re-render — bug คลาสสิกที่เจอกันทุกออฟฟิศ

อีกเรื่องที่ควรเห็นค่า: cartReducer เป็น pure function — รับ state กับ action คืน state ใหม่ จบ ไม่แตะ localStorage ไม่ยิง API ไม่รู้จัก React ด้วยซ้ำ ผลคือเราทดสอบมันได้เหมือนทดสอบฟังก์ชันบวกเลข ซึ่งเราจะทำจริงในบทเรียน 31

import { createContext } from "react";

export interface CartItem {
  id: number;
  title: string;
  price: number;
  quantity: number;
  image: string;
  originalPrice?: number;
}

export interface CartState {
  items: CartItem[];
}

export interface CartContextProps {
  cart: CartState;
  addToCart: (item: CartItem) => void;
  removeFromCart: (id: number) => void;
  updateQuantity: (id: number, quantity: number) => void;
  clearCart: () => void;
}

export enum CartActionTypes {
  ADD_TO_CART = "ADD_TO_CART",
  REMOVE_FROM_CART = "REMOVE_FROM_CART",
  UPDATE_QUANTITY = "UPDATE_QUANTITY",
  CLEAR_CART = "CLEAR_CART",
}

export const CartContext = createContext<CartContextProps | undefined>(
  undefined,
);

ไฟล์นี้มีของอยู่ 4 กลุ่ม ไล่ดูทีละตัว:

  • CartItem — สินค้าหนึ่งแถวในตะกร้า สังเกตว่าเราไม่เก็บ Product ทั้งก้อนจาก API แต่คัดเฉพาะที่ตะกร้าต้องใช้จริง: ราคา รูป ชื่อ และ quantity ที่ API ไม่มี (เป็นของที่ผู้ใช้เลือกเอง) ส่วน originalPrice? เป็น optional — เก็บราคาก่อนลดไว้เพื่อให้หน้า Cart โชว์ "You Save" ได้โดยไม่ต้องยิง API ซ้ำ
  • CartState — ทั้ง store คือ object ที่มี items หนึ่ง array ทำไมไม่ใช้ array ตรง ๆ? เพราะห่อเป็น object ไว้ก่อน วันหน้าจะเพิ่ม field อื่น (เช่น coupon code) ได้โดย type ของ state ไม่ต้องเปลี่ยนรูปทรงทั้งยวง
  • CartContextProps — นี่คือ "หน้าสัญญา" (public API) ของ store: component ภายนอกจะเห็นตะกร้าผ่าน cart และแก้ไขผ่าน 4 ฟังก์ชันนี้เท่านั้น ไม่มีใครเห็น dispatch หรือ action โดยตรง
  • CartActionTypes — enum รวมชื่อ action ทุกตัวไว้ที่เดียว ถ้าใช้ string literal หว่านไปตามไฟล์ พิมพ์ผิดหนึ่งตัวอักษร reducer ก็จะเงียบ ๆ ไม่ทำงาน แต่พอเป็น enum การพิมพ์ผิดกลายเป็น compile error ทันที

บรรทัดสุดท้ายคือการสร้าง context ด้วยค่าเริ่มต้น undefined — จงใจครับ ไม่ใช่ขี้เกียจใส่ค่า default ถ้าเราใส่ค่า default ปลอม ๆ ไว้ component ที่เผลอใช้ context นอก provider จะทำงานต่อแบบผิด ๆ โดยไม่มีใครรู้ แต่พอ default เป็น undefined เราจะดักจับพลาดนี้ได้ใน useCart (เดี๋ยวเจอด้านล่าง) แล้วโยน error ที่อ่านรู้เรื่องออกมาแทน

src/features/cart/store/cartStorage.ts — ตะกร้าที่หายเกลี้ยงทุกครั้งที่ refresh คือตะกร้าที่ไล่ลูกค้าหนี:

import { CartState } from "./CartContext";

export const CART_STORAGE_KEY = "ecommerce-cart:v1";

const EMPTY: CartState = { items: [] };

export function loadCartState(): CartState {
  try {
    const raw = localStorage.getItem(CART_STORAGE_KEY);
    if (!raw) return EMPTY;
    const parsed: unknown = JSON.parse(raw);
    if (
      typeof parsed === "object" &&
      parsed !== null &&
      Array.isArray((parsed as CartState).items)
    ) {
      return parsed as CartState;
    }
    return EMPTY;
  } catch {
    return EMPTY;
  }
}

export function saveCartState(state: CartState): void {
  try {
    localStorage.setItem(CART_STORAGE_KEY, JSON.stringify(state));
  } catch {
    // Storage full or unavailable — cart just won't persist.
  }
}

ไฟล์สั้น แต่ทุกบรรทัดคือบทเรียนจากแผลจริง:

  • key มีเลขเวอร์ชัน — "ecommerce-cart:v1" ไม่ใช่แค่ "cart" เพราะข้อมูลใน localStorage อยู่ยาวกว่าโค้ดของเรา ถ้าอนาคตเราเปลี่ยนรูปร่างของ CartState จนไม่ compatible แค่ขยับเป็น :v2 ข้อมูลเก่ารูปแบบเก่าก็จะถูกมองข้ามไปเฉย ๆ แทนที่จะถูก parse มาทำแอปพัง
  • ทำไมต้อง try/catch ตอนโหลด — สองเหตุ: หนึ่ง JSON.parse โยน SyntaxError ทันทีถ้าข้อมูลใน storage เพี้ยน (ผู้ใช้ไปแก้เองใน DevTools, extension บางตัวเขียนทับ, ข้อมูลครึ่ง ๆ กลาง ๆ) สอง แค่แตะ localStorage ก็โยน error ได้แล้วในบางสภาพแวดล้อม เช่น เบราว์เซอร์ที่ผู้ใช้ปิด storage หรือ iframe ที่ถูก block cookie/storage — โค้ดที่ถือว่า localStorage "มีแน่ ๆ" คือโค้ดที่รอวันล้ม
  • เช็ครูปร่างก่อนเชื่อ — ต่อให้ parse ผ่าน เราก็ยังรับค่าเป็น unknown แล้วตรวจว่าเป็น object ที่มี items เป็น array จริงก่อนถึงยอม as CartState — จำที่คอร์ส React พื้นฐาน เตือนเรื่อง as ได้ไหม? ตรงนี้เราใช้มันหลังตรวจสอบด้วยมือแล้ว ไม่ใช่ใช้แทนการตรวจสอบ
  • ตอนบันทึกก็ห้ามพัง — setItem โยน error ได้เมื่อ storage เต็ม (quota) หรือถูกปิด เราเลือกกลืน error เงียบ ๆ เพราะผลลัพธ์ที่แย่ที่สุดคือ "ตะกร้าไม่ถูกจำข้าม session" ซึ่งดีกว่า "ทั้งแอป crash เพราะบันทึกตะกร้าไม่ได้" หลายขุม และ comment บรรทัดเดียวใน catch คือสิ่งที่ทำให้ block ว่าง ๆ นั้นอ่านออกว่าตั้งใจ ไม่ใช่ลืมเขียน — ถ้าไม่มีมัน คนถัดไปที่มาอ่านจะเติมโค้ดลงไปเอง
  • ทุกทางล้มเหลวจบที่ EMPTY — โหลดไม่ได้ด้วยเหตุใดก็ตาม ผู้ใช้ได้ตะกร้าว่างเปล่าที่ใช้งานต่อได้ ไม่ใช่หน้าขาว

src/features/cart/store/CartProvider.tsx — ได้ types, กติกา และที่เก็บของครบแล้ว ทีนี้เอามาต่อกันเป็น component เดียว:

import React, { useEffect, useReducer } from "react";
import { CartActionTypes, CartContext, CartItem } from "./CartContext";
import { cartReducer } from "./cartReducer";
import { loadCartState, saveCartState } from "./cartStorage";

export const CartProvider: React.FC<{ children: React.ReactNode }> = ({
  children,
}) => {
  const [cart, dispatch] = useReducer(cartReducer, undefined, loadCartState);

  useEffect(() => {
    saveCartState(cart);
  }, [cart]);

  const addToCart = (item: CartItem) => {
    dispatch({ type: CartActionTypes.ADD_TO_CART, payload: item });
  };

  const removeFromCart = (id: number) => {
    dispatch({ type: CartActionTypes.REMOVE_FROM_CART, payload: { id } });
  };

  const updateQuantity = (id: number, quantity: number) => {
    dispatch({
      type: CartActionTypes.UPDATE_QUANTITY,
      payload: { id, quantity },
    });
  };

  const clearCart = () => {
    dispatch({ type: CartActionTypes.CLEAR_CART });
  };

  return (
    <CartContext.Provider
      value={{ cart, addToCart, removeFromCart, updateQuantity, clearCart }}
    >
      {children}
    </CartContext.Provider>
  );
};

สองบรรทัดแรกในตัว component คือของสำคัญที่สุดของบทนี้:

  • useReducer(cartReducer, undefined, loadCartState) — นี่คือ useReducer แบบ 3 arguments ตัวที่สามคือ lazy initializer: React จะเรียก loadCartState() แค่ครั้งเดียวตอน mount เพื่อสร้าง state เริ่มต้น (argument ที่สองคือค่าที่จะส่งให้ initializer — เราไม่ต้องการอะไรจึงเป็น undefined) จำ lazy initial state ของ useState จากคอร์ส React พื้นฐาน ได้ไหม? หลักการเดียวกันเป๊ะ: การอ่าน localStorage + JSON.parse เป็นงานที่มีต้นทุน ถ้าเราเขียน useReducer(cartReducer, loadCartState()) แบบสองอาร์กิวเมนต์ ฟังก์ชันนั้นจะถูกเรียกซ้ำทุก render แล้วโยนผลลัพธ์ทิ้งเปล่า ๆ ทุกครั้งที่ไม่ใช่ mount แรก
  • write-through effect — useEffect ที่มี dependency [cart] แปลว่า "ทุกครั้งที่ state ตะกร้าเปลี่ยน ให้เขียนทับลง localStorage ทันที" การ persist จึงเป็นไปเองอัตโนมัติ ไม่มีวันลืม ไม่ต้องให้ action ไหนจำหน้าที่นี้เอง (สังเกตว่า reducer ยังบริสุทธิ์เหมือนเดิม — side effect ทั้งหมดอยู่ใน effect ตามชื่อของมัน) และเนื่องจาก effect รันหลัง render แรกด้วย state เริ่มต้นก็จะถูกเขียนลง storage ตั้งแต่เปิดแอปครั้งแรกเลย

ที่เหลือคือฟังก์ชัน 4 ตัวที่ห่อ dispatch ไว้ให้เรียบร้อย — component ภายนอกจะได้เรียก addToCart(item) สั้น ๆ โดยไม่ต้องรู้จัก action object เลย แล้วทั้งหมดถูกส่งออกผ่าน CartContext.Provider ใน prop value

💡 ของที่ควรถูกทักในรีวิว: prop value ของ provider เป็น object literal ที่ถูกสร้างใหม่ทุก render และฟังก์ชันทั้งสี่ตัวก็ถูกสร้างใหม่ทุก render เช่นกัน ผลคือทุก component ที่เรียก useCart() จะ re-render ทุกครั้งที่ CartProvider re-render ไม่ว่าตะกร้าจะเปลี่ยนจริงหรือไม่ — เพราะ React เทียบค่า context ด้วย reference ทางแก้มาตรฐานคือห่อฟังก์ชันสี่ตัวด้วย useCallback แล้วห่อ value ด้วย useMemo ที่ขึ้นกับ [cart] เราสั่งห้ามไว้ใน prompt เพื่อให้ diff ตรงกับต้นฉบับ และในแอปขนาดนี้ผลกระทบยังวัดไม่ออก (ตัวที่กิน context จริงมีสามตัวเท่านั้นตลอดคอร์ส) แต่ถ้านี่เป็น pull request ในงานจริง นี่คือข้อแรกที่รีวิวเวอร์จะทัก และเป็นข้อที่ถูก จุดที่ต้องระวังคืออย่าใส่ useMemo โดยไม่ใส่ useCallback — ทำครึ่งเดียวจะไม่ได้อะไรเลย เพราะฟังก์ชันสี่ตัวที่สร้างใหม่จะทำให้ object ที่ memo ไว้เปลี่ยนทุกครั้งอยู่ดี ข้อสังเกตพ่วงอีกข้อ: write-through effect ยิงตั้งแต่ mount แรก แปลว่าผู้ใช้ที่เพิ่งเปิดเว็บครั้งแรกและยังไม่ได้แตะอะไรเลย จะมี key ecommerce-cart:v1 ค่า {"items":[]} ถูกเขียนลงเครื่องทันที — ไม่ผิด แต่เป็นการเขียนที่ไม่มีใครขอ

import { ReactNode } from "react";
import { QueryClientProvider } from "@tanstack/react-query";
import { ReactQueryDevtools } from "@tanstack/react-query-devtools";
import { queryClient } from "./queryClient";
import { CartProvider } from "@/features/cart/store/CartProvider";

export function AppProviders({ children }: { children: ReactNode }) {
  return (
    <QueryClientProvider client={queryClient}>
      <CartProvider>{children}</CartProvider>
      {import.meta.env.DEV && <ReactQueryDevtools initialIsOpen={false} />}
    </QueryClientProvider>
  );
}

สังเกตสองจุด: หนึ่ง CartProvider อยู่ข้างใน QueryClientProvider — สำหรับสองตัวนี้ลำดับไม่ได้มีผลอะไรเป็นพิเศษ (ต่างคนต่างไม่พึ่งกัน) แต่หลักคิดคือ provider ที่ "ทั้งแอปต้องเห็น" ให้ซ้อนกันไว้ที่จุดเดียวแบบนี้ ไม่กระจายไปหลายไฟล์ สอง Devtools อยู่นอก CartProvider ได้สบายเพราะมันสนใจแค่ query cache — และตอนนี้ทุกหน้า ทุก component ในแอปเข้าถึงตะกร้าใบเดียวกันได้แล้วผ่าน useCart

และนี่คือจุดขายของ pattern ที่บทเรียน 11 พูดถึงไว้ล่วงหน้า: วันที่ต้องเพิ่ม provider ตัวใหม่ทั้งตัว เราแก้ไฟล์เดียว App.tsx ไม่ต้องรู้เรื่องเลย — git diff ของวันนี้พิสูจน์แล้วว่ามันเป็นจริง สองบรรทัดพอดี
