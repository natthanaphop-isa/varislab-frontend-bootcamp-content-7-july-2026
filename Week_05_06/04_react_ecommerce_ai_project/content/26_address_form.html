ปรัชญาของ react-hook-form: uncontrolled แต่สบายกว่า

ย้อนกลับไปบท Hooks และบท Uncontrolled Forms ของคอร์ส React พื้นฐาน — ตอนนั้นเราสรุปกันว่าฟอร์มมาตรฐานควรเป็น uncontrolled: ปล่อยให้ DOM เก็บค่าของ input เอง แล้วค่อยไปอ่านค่าทีเดียวตอน submit ส่วน controlled form (ผูกทุก input กับ useState) เก็บไว้ใช้เมื่อจำเป็นจริง ๆ เช่นต้องตอบสนองทุกตัวอักษรที่พิมพ์ เหตุผลเรื่อง performance ก็ชัดเจน: controlled form ทำให้ทั้งฟอร์ม re-render ทุกครั้งที่กดคีย์บอร์ดหนึ่งที ในขณะที่ uncontrolled ไม่ re-render อะไรเลยระหว่างพิมพ์

แต่ uncontrolled แบบดิบ ๆ (อ่าน FormData เองตอน submit) ก็มีงานน่าเบื่อ: ต้องแปลงค่าเป็น type ที่ถูกต้องเอง ต้อง validate เอง ต้องจัดการแสดง error ต่อ field เอง react-hook-form คือ uncontrolled form ที่มีคนทำงานน่าเบื่อพวกนั้นให้หมดแล้ว:

  • input ยังเป็น uncontrolled — react-hook-form เกาะกับ DOM ผ่าน ref ค่าอยู่ใน DOM ไม่อยู่ใน state → พิมพ์เร็วแค่ไหนก็ไม่มี re-render
  • ตอน submit มันรวบรวมค่าทุก field, ส่งให้ resolver validate (ของเราคือ zod schema จากบทที่แล้ว), แล้วเรียก callback ของเราพร้อมข้อมูลที่ผ่านการตรวจและมี type ถูกต้องแล้วเท่านั้น
  • ถ้าไม่ผ่าน มันเก็บข้อความ error รายฟิลด์ไว้ใน formState.errors แล้ว re-render เฉพาะตอนที่ชุด error เปลี่ยนจริง ๆ

ประโยคสุดท้ายคือสิ่งที่ทำให้บทนี้มีข้อ AI มักพลาดตรงนี้ ที่ตรวจยากกว่าปกติ: ฟอร์มที่เขียนด้วย useState ผูกทุกช่องแบบ controlled จะทำงานถูกต้องทุกประการบนหน้าจอ — กรอกได้ ตรวจได้ error ขึ้นครบ ผู้ใช้แยกไม่ออก คุณแยกไม่ออกจากภาพหน้าจอเช่นกัน ต่างกันแค่จำนวน re-render ที่ไม่มีใครเห็น และความจริงที่ว่า library ที่เราเพิ่งลงไปทั้งตัวถูกใช้ไปแค่เศษเสี้ยว

งานสองไฟล์ที่ต้องมาคู่กัน

บทนี้จะส่ง promptรอบเดียว เกณฑ์จากบทเรียน 19 บอกให้แบ่งเมื่อของที่ต้องตรวจเกินหนึ่งหน้าจอ และของนั้นแยกเป็นก้อนที่ทดสอบแยกกันได้ — ต้องเข้าทั้งสองข้อถึงจะแบ่ง งานวันนี้ไม่เข้าสักข้อ: CheckoutAddressBox import CheckoutAddressForm ตรง ๆ (แถม import type จากมันด้วย — เดี๋ยวเราจะกลับมาคุยเรื่องนี้) ได้มาไฟล์เดียวก็ประกอบอะไรไม่ได้ และ diff ทั้งหมดสั้นพอที่จะอ่านจบในครั้งเดียว

สิ่งที่ต้องตัดสินใจให้จบก่อนเขียน prompt คือ state ของ "ที่อยู่ที่ submit แล้ว" อยู่ที่ไหน — คำตอบ: ไม่ได้อยู่ในสองไฟล์นี้เลย ไล่เส้นทางของข้อมูลดู:

  1. ระหว่างพิมพ์ ค่าของแต่ละช่องอยู่ใน DOM ภายใต้การดูแลของ react-hook-form (เรื่องของ CheckoutAddressForm ล้วน ๆ)
  2. กด Submit ผ่าน validation → ฟอร์มเรียก onSubmit → กล่องรับต่อใน onSubmitAddress → ส่งขึ้นไปอีกชั้นผ่าน onUpdateAddress
  3. เจ้าของ state ตัวจริงคือ hook useCheckout ที่เราจะเขียนในบทเรียน 28 — มัน setState เก็บที่อยู่ไว้ แล้วส่งกลับลงมาเป็น prop checkoutAddress
  4. กล่องเห็น checkoutAddress ไม่เป็น null แล้ว จึง render บล็อกสรุปที่อยู่ (เงื่อนไข {checkoutAddress && ...}) โผล่เหนือฟอร์ม

นี่คือ pattern lifting state up ที่คุณรู้จักดี: กล่องเป็นแค่ตัวแสดงผลที่ถูกควบคุมจากข้างบน ตัวมันเองไม่มี useState สักตัว ผลพลอยได้ที่เนียนมากคือฟอร์มยัง render อยู่ตลอดแม้ submit ไปแล้ว — ผู้ใช้กรอกใหม่แล้วกด Submit ซ้ำเพื่อแก้ที่อยู่ได้ทุกเมื่อ ค่าที่ submit ล่าสุดจะทับของเดิมเฉย ๆ ไม่ต้องมีปุ่ม Edit ไม่ต้องมี mode สลับไปมา

ข้อนี้ต้องเขียนลง prompt ให้ชัด เพราะ "ฟอร์มที่อยู่ที่กรอกแล้วแก้ได้" เป็นโจทย์ที่มีทางออกมาตรฐานอยู่สามสี่ทาง (มี state isEditing, มีปุ่ม Edit, ซ่อนฟอร์มหลัง submit) และทุกทางนั้นต้องมี useState ในกล่อง ถ้าเราไม่บอกว่าเราเลือกทางไหน Agent จะเลือกให้ แล้วบทเรียน 28 จะมี state สองแหล่งที่ต้อง sync กัน

โค้ดอ้างอิง

src/features/checkout/components/CheckoutAddressForm/CheckoutAddressForm.tsx:

import React from "react";
import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";
import {
  checkoutAddressSchema,
  CheckoutAddressFormData,
} from "@/features/checkout/schema";
import Input from "@/shared/components/Input/Input";
import Button from "@/shared/components/Button/Button";

export type { CheckoutAddressFormData };

interface CheckoutAddressFormProps {
  onSubmit: (data: CheckoutAddressFormData) => void;
}

const CheckoutAddressForm: React.FC<CheckoutAddressFormProps> = ({
  onSubmit,
}) => {
  const {
    register,
    handleSubmit,
    formState: { errors },
  } = useForm<CheckoutAddressFormData>({
    resolver: zodResolver(checkoutAddressSchema),
  });

  const onFormSubmit = (data: CheckoutAddressFormData) => {
    onSubmit({ ...data });
  };

  return (
    <form onSubmit={handleSubmit(onFormSubmit)}>
      <div className="mb-15">
        <Input
          label="Address"
          type="text"
          placeholder="Enter Address"
          {...register("address")}
          error={errors.address?.message}
        />
      </div>

      <div className="flex gap-15 mb-15">
        <div className="width-50">
          <Input
            label="Email"
            type="email"
            placeholder="Enter Email"
            {...register("email")}
            error={errors.email?.message}
          />
        </div>
        <div className="width-50">
          <Input
            label="Phone Number"
            type="text"
            placeholder="Enter Phone Number"
            {...register("phone")}
            error={errors.phone?.message}
          />
        </div>
      </div>

      <Button type="submit">Submit</Button>
    </form>
  );
};

export default CheckoutAddressForm;

ไฟล์ไม่ยาว แต่ทุกบรรทัดมีเรื่องเล่า ไล่จากบนลงล่าง:

useForm + zodResolver

useForm คือศูนย์บัญชาการของฟอร์ม เราส่ง generic CheckoutAddressFormData (type ที่ z.infer สกัดให้เมื่อบทที่แล้ว) เพื่อบอกว่าฟอร์มนี้มี field อะไรบ้าง — ผลคือ register("address") จะ autocomplete ชื่อ field ให้ และถ้าพิมพ์ register("adress") TypeScript ฟ้องทันที ส่วน resolver: zodResolver(checkoutAddressSchema) คือการเสียบ schema ของเราเข้าเป็นกติกา validate ของฟอร์ม — สังเกตว่าเราไม่ต้องเขียน logic validate ในคอมโพเนนต์นี้เลยแม้แต่บรรทัดเดียว กติกาทั้งหมดอยู่ใน schema.ts ที่เดียว ซึ่งเป็นเหตุผลที่บทที่แล้วถึงให้คุณพิมพ์ไฟล์นั้นเอง

register — จุดเชื่อมระหว่าง input กับฟอร์ม

{...register("address")} เป็นท่าที่ดูแปลกตาตอนแรก แต่จริง ๆ ตรงไปตรงมา: register("address") คืน object ที่มี name, ref, onChange, onBlur แล้วเรา spread ทั้งก้อนลงบน <Input /> — เท่ากับสมัคร input ตัวนี้เข้าระบบของ react-hook-form ตัวสำคัญที่สุดในก้อนคือ ref: react-hook-form ใช้มันจับ DOM element ตรง ๆ เพื่ออ่านค่าโดยไม่ต้องพึ่ง state

และตรงนี้เองที่การบ้านเก่าของเราออกดอกผล — จำได้ไหมว่าตอนสร้าง Input ในบทเรียน 12 เราห่อมันด้วย forwardRef? เพราะ ref ไม่ใช่ prop ธรรมดา คอมโพเนนต์ที่รับ ref แล้วส่งต่อให้ <input> ข้างในต้องประกาศตัวเป็น forwardRef อย่างชัดเจน ถ้าตอนนั้นเราสร้าง Input แบบธรรมดา วันนี้ register จะจับ input ข้างในไม่ได้ และฟอร์มจะอ่านค่าไม่ออกแบบเงียบ ๆ อาการงง ๆ อันดับหนึ่งของคนใช้ react-hook-form กับ custom component คือเรื่องนี้แหละ — และเป็นเหตุผลที่ checklist ของบทเรียน 12 มีข้อ "ref ถูกส่งไปที่แท็ก <input> ไม่ใช่ที่ <div> ข้างนอก" รออยู่ตั้งแต่วันนั้น ถ้าคุณกด accept ข้ามข้อนั้นไปเมื่อสิบสี่บทก่อน วันนี้คือวันที่มันมาเก็บเงิน

ส่วน error={errors.address?.message} คือปลายทางของ zod: ถ้า validate ไม่ผ่าน ข้อความอย่าง "Address is required" จะมาอยู่ใน errors.address.message แล้ว Input ของเรา (ที่มี prop error เตรียมไว้ตั้งแต่บทเรียน 12 เช่นกัน) ก็แสดงเป็นตัวหนังสือสีแดงใต้ช่องกรอก — ใช้ optional chaining (?.) เพราะตอนที่ยังไม่มี error errors.address เป็น undefined

handleSubmit — ด่านตรวจก่อนถึงมือเรา

<form onSubmit={handleSubmit(onFormSubmit)}> ไม่ได้เรียก onFormSubmit ตรง ๆ แต่ห่อไว้ด้วย handleSubmit ซึ่งทำงานตามลำดับนี้ทุกครั้งที่ผู้ใช้กด submit:

  1. กัน default behavior ของเบราว์เซอร์ (ไม่ต้องเขียน e.preventDefault() เอง)
  2. รวบรวมค่าทุก field จาก DOM แล้วส่งให้ zod ตรวจ
  3. ถ้าไม่ผ่าน — เติม formState.errors แล้ว re-render ให้ข้อความ error โผล่ onFormSubmit ไม่ถูกเรียกเลย
  4. ถ้าผ่าน — เรียก onFormSubmit(data) โดย data เป็น CheckoutAddressFormData ที่การันตีแล้วว่าครบและถูกต้อง

แปลว่าโค้ดฝั่งเราไม่มีทางได้รับข้อมูลครึ่ง ๆ กลาง ๆ — ทุกเส้นทางที่ onSubmit ของ parent ถูกเรียก ข้อมูลผ่าน schema มาแล้วเสมอ และนั่นคือเหตุผลที่ useCheckout ในบทเรียน 28 เก็บที่อยู่ลง state ได้โดยไม่ต้องตรวจอะไรซ้ำอีก

เกร็ดสุดท้าย: class อย่าง mb-15, flex gap-15, width-50 คือ utility classes จาก _utilities.scss และ _spacing.scss ที่เราวางไว้ตั้งแต่บทเรียน 04 — สอง input ล่างเลยเรียงเป็นสองคอลัมน์เท่า ๆ กันโดยไม่ต้องมี SCSS module ของตัวเอง นี่คือเหตุผลที่ไฟล์นี้เป็นคอมโพเนนต์เดียวในบทที่ไม่มี .module.scss คู่

💡 ของที่ควรถูกทักในรีวิว — สามข้อ และข้อแรกจะตามหลอกหลอนไปถึงบทเรียน 28: บรรทัด export type { CheckoutAddressFormData }; คือการ re-export type ที่ไฟล์นี้ไม่ได้เป็นเจ้าของ ผลคือ CheckoutAddressBox import type ตัวนี้มาจากคอมโพเนนต์ ไม่ใช่จาก schema.ts ที่เป็นต้นทางจริง — ลองเทียบกับสิ่งที่ checklist ของบทที่แล้วเพิ่งปฏิเสธไป: เราห้าม Agent เขียน export type { CheckoutAddressFormData } from "./schema"; ใน types.ts ด้วยเหตุผลว่า "สร้างทางเข้าที่สองให้ของชิ้นเดียว" แล้ววันนี้ต้นฉบับก็สร้างทางเข้าที่สองนั้นเองในไฟล์คอมโพเนนต์ ผลจริงที่ตามมา: หลังบทเรียน 28 คุณจะมีสามไฟล์ที่ import type นี้จากคนละที่กัน — CheckoutAddressBox เอาจากคอมโพเนนต์ ส่วน api.ts กับ useCheckout.ts เอาจาก schema.ts โดยตรง วันที่มีคนย้าย schema ไปไฟล์อื่น เขาจะไล่แก้ไม่ครบเพราะ grep คำว่า "schema" แล้วเจอไม่หมด ทางแก้ในรีวิวจริงคือลบบรรทัดนี้ทิ้งแล้วให้ทุกคน import จาก @/features/checkout/schema เหมือนกันหมด ข้อสองเล็กกว่าแต่อยู่ในสายตาเหมือนกัน: onSubmit({ ...data }) spread เพื่อ "ให้ parent ได้สำเนาของตัวเอง" ซึ่งฟังดูมีเหตุผลจนกระทั่งคุณเปิดดูว่า data ที่ handleSubmit ส่งมาคือ object ที่ react-hook-form สร้างใหม่ทุกครั้งที่ submit อยู่แล้ว ไม่มีใครถือ reference นี้ต่อ การ spread จึงคัดลอกของที่ไม่มีใครแตะ และมันยังเป็น shallow copy ที่ถ้าวันหน้า schema มี field ที่เป็น object ซ้อน ก็จะไม่ได้ป้องกันอะไรอยู่ดี ข้อสามผู้ใช้มือถือเป็นคนจ่าย: ช่องเบอร์โทรประกาศเป็น type="text" ทั้งที่ควรเป็น type="tel" — tel บอกเบราว์เซอร์ว่าช่องนี้รับเบอร์โทร ผลคือคีย์บอร์ดบนมือถือเด้งแป้นตัวเลขขึ้นมาให้แทนแป้นตัวอักษร และ autofill ของระบบเดาถูกว่าจะเติมอะไรลงไป ส่วน validation ไม่เกี่ยวเลย — tel ไม่ได้บังคับรูปแบบอะไรทั้งนั้น กติกายังอยู่ที่ schema ที่เดียวเหมือนเดิม ข้อนี้จึงเป็นการแก้ที่ไม่มีความเสี่ยงและได้ผลกับผู้ใช้จริงทันที เราคงไว้ตามต้นฉบับเพื่อให้ diff ตรง แต่ถ้านี่เป็น pull request จริง มันคือ comment หนึ่งบรรทัดที่ควรถูกทัก และควรถูกแก้

src/features/checkout/components/CheckoutAddressBox/CheckoutAddressBox.tsx — ฟอร์มอย่างเดียวยังไม่พอ บนหน้า Checkout จริงเราอยากให้ผู้ใช้กด Submit แล้วเห็นที่อยู่ที่ตัวเองกรอกแสดงยืนยันอยู่ด้านบน พร้อมยังแก้ไขซ้ำได้:

@use "../../../../styles/variables";

ดีไซน์ของกล่องนี้ (พื้นเทา $grey05 + padding จาก utility class p-20 + หัวข้อ + เส้นคั่น) จะกลายเป็นหน้าตามาตรฐานของทุกกล่องบนหน้า Checkout — บทหน้าคุณจะเห็นกล่อง Delivery, Payment และ Summary ใช้สูตรเดียวกันเป๊ะ ซึ่งฟังดูดีจนกระทั่งคุณอ่านกล่องข้างล่างนี้

💡 ของที่ควรถูกทักในรีวิว — และรีบทักตอนนี้เลย เพราะบทหน้ามันจะถูกคูณสี่: เปิด src/styles/_utilities.scss ที่เราเขียนไว้ตั้งแต่บทเรียน 04 แล้วมองหา class ชื่อ bg-grey05 — มันมีอยู่แล้ว และเนื้อในของมันคือ background-color: variables.$grey05; ตัวอักษรต่อตัวอักษรเดียวกับ .container ที่เราเพิ่งสร้าง แปลว่าไฟล์ .module.scss ทั้งไฟล์นี้แทนได้ด้วยการเปลี่ยน className={`${styles.container} p-20`} เป็น className="bg-grey05 p-20" แล้วลบไฟล์ทิ้ง ค่าใช้จ่ายของการไม่ทำแบบนั้นไม่ได้อยู่ที่วันนี้ (สี่บรรทัด ใครจะสน) แต่อยู่ที่บทเรียน 27: กล่อง Delivery, Payment, Summary Order และ Billing Summary จะได้ไฟล์ .module.scss หน้าตาเหมือนกันเป๊ะไฟล์ละหนึ่งไฟล์ รวมเป็นห้าไฟล์ที่มีเนื้อในเดียวกัน และวันที่ดีไซเนอร์ขอเปลี่ยนสีพื้นกล่องบนหน้า Checkout คนแก้ต้องเปิดห้าไฟล์ — หรือแก้สี่แล้วลืมหนึ่ง ซึ่งจะได้กล่องที่สีเพี้ยนอยู่ใบเดียวบนหน้าจอ นี่คือรูปแบบเดิมที่คอร์สนี้เจอมาตลอด: ของที่ถูกต้องในไฟล์เดียว กลายเป็นปัญหาเมื่อถูกคูณ เราสั่งตามต้นฉบับเพื่อให้ diff ตรง แต่ถ้านี่เป็น pull request จริง ข้อนี้ควรถูกทักในบทนี้ ก่อนที่มันจะขยายพันธุ์ในบทหน้า ข้อพ่วงในไฟล์เดียวกัน: onSubmitAddress เป็น wrapper ที่เรียก onUpdateAddress(data) เฉย ๆ — <CheckoutAddressForm onSubmit={onUpdateAddress} /> ให้ผลเหมือนกันทุกประการ เป็นท่าเดียวกับ onCheckout ในบทเรียน 24 ที่เราทักไปแล้วรอบหนึ่ง และข้อสุดท้ายเป็นเรื่องที่ผู้ใช้เห็นจริง: บล็อกสรุปที่อยู่เขียนหัวข้อว่า Address ตัวใหญ่ แต่อีกสองบรรทัดเป็น email กับ phone ตัวเล็ก ทั้งที่อยู่ในย่อหน้าเดียวกันและ label ของช่องกรอกข้างล่างเขียนว่า Email กับ Phone Number — ความไม่สม่ำเสมอที่ไม่มีเครื่องมือไหนจับได้ และเป็นข้อที่รีวิวเวอร์คนแรกจะเห็นก่อนใครเพราะมันอยู่บนหน้าจอ

🤔 อธิบายให้ได้

  1. ใส่ console.log("render") เป็นบรรทัดแรกของตัวคอมโพเนนต์ CheckoutAddressForm แล้วพิมพ์คำว่า bangkok ลงช่อง Address ทีละตัวอักษร จดจำนวนบรรทัดใน console จากนั้นแปลงช่อง Address ให้เป็น controlled ด้วย useState ชั่วคราวแล้วทำซ้ำ — ตอบว่าสองตัวเลขต่างกันเท่าไรและเพราะอะไร แล้วตอบต่อว่าถ้าฟอร์มนี้มีสิบช่องแทนที่จะเป็นสามช่อง ตัวเลขฝั่ง controlled จะเปลี่ยนไปอย่างไร (เสร็จแล้วแก้กลับ)
  2. ลบ error={errors.email?.message} ออกจากช่อง Email แล้วกด Submit ด้วย email ว่าง — ตอบว่าฟอร์มยังถูกกันไม่ให้ submit หรือไม่ ผู้ใช้เห็นอะไร และอธิบายให้ได้ว่าใครเป็นคน "ตัดสิน" ว่าไม่ผ่าน กับใครเป็นคน "แสดง" ว่าไม่ผ่าน — สองหน้าที่นี้อยู่คนละไฟล์กันตรงไหนบ้าง (เสร็จแล้วเติมกลับ)
  3. CheckoutAddressBox ไม่มี useState เลยสักตัว แต่มันแสดงที่อยู่ที่ผู้ใช้เพิ่งกรอกได้ — ไล่ให้ครบว่าค่านั้นเดินทางจากช่องกรอกไปถึงบล็อกสรุปด้านบนผ่านกี่ทอด ใครเป็นเจ้าของ (ไฟล์ไหน บทไหน) และตอบด้วยว่าถ้ากล่องเก็บสำเนาของตัวเองไว้ด้วย useState อาการที่ผู้ใช้จะเห็นในบทเรียน 28 คืออะไร
