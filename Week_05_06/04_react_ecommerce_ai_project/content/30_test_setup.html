ติดตั้งชุดทดสอบ: Vitest, React Testing Library และ MSW

Test Setup

แอปของเราครบทุกฟีเจอร์แล้ว — ดูสินค้าได้ เพิ่มลงตะกร้าได้ สั่งซื้อได้ แต่ตอนนี้ถ้าถามว่า "กล้าแก้ cartReducer ไหม? กล้าอัปเกรด TanStack Query ไหม?" คำตอบที่ซื่อสัตย์คือ "ไม่ค่อยกล้า เพราะต้องไล่คลิกทุกหน้าเองเพื่อเช็คว่าไม่มีอะไรพัง" ชุดเทสต์ (test suite) คือสิ่งที่เปลี่ยนคำตอบนั้นเป็น "กล้า เพราะกด npm run test แล้วรู้ผลใน 10 วินาที" — และนี่คือสิ่งที่เราจะสร้างกันในสี่บทต่อจากนี้

ในคอร์ส React พื้นฐาน คุณเขียนเทสต์ด้วย Vitest และ React Testing Library มาแล้ว บทนี้เราจะติดตั้งเครื่องมือชุดเดิมนั้นเข้าโปรเจกต์นี้ พร้อมเพื่อนใหม่หนึ่งตัวคือ MSW (Mock Service Worker) แล้ววางโครงสร้างพื้นฐานทั้งหมดที่บทถัด ๆ ไปจะใช้: ข้อมูลปลอม, API ปลอม และ helper สำหรับ render ทั้งแอปในเทสต์ บทนี้ยังไม่มีเทสต์จริงสักตัว — แต่พอวางฐานเสร็จ สามบทถัดไปจะไหลลื่นมาก

และมีอีกเรื่องที่ต้องพูดไว้ตั้งแต่ต้นบท เพราะมันเป็นเหตุผลที่ทั้งสี่บทนี้ต้องอ่านต่างจากยี่สิบบทที่ผ่านมา: บทเรียน 29 จบด้วยสัญญาณอันตรายข้อที่สองว่า "เทสต์ผ่านแต่คุณอธิบายไม่ได้ว่าทำไม" เทสต์เป็นของชนิดเดียวในโปรเจกต์นี้ที่ทำหน้าที่ตัดสินว่าโค้ดอื่นถูกหรือผิด ดังนั้นถ้าตัวมันเองผิด จะไม่มีอะไรอยู่เหนือขึ้นไปคอยจับมันอีกแล้ว บทนี้เราวางฐาน บทถัดไปเราจะพูดเรื่องนี้ให้ครบทั้งบท

ทำไมต้อง MSW — mock ที่ชั้น network ไม่ใช่ชั้นโค้ด

ปัญหาคลาสสิกของการเทสต์แอปที่คุยกับ API: เราไม่อยากให้เทสต์ยิง request ไปที่ dummyjson.com จริง ๆ เพราะมันช้า, พังเมื่อเน็ตล่ม และข้อมูลบนเซิร์ฟเวอร์เปลี่ยนได้ตลอดเวลา (เทสต์ที่ assert ว่าสินค้าชื่ออะไรจะพังทันทีที่ dummyjson แก้ข้อมูล) เราจึงต้อง "ปลอม" API — คำถามคือปลอมที่ชั้นไหน

วิธีที่หลายคนนึกถึงก่อนคือ mock ตัว axios ไปเลยด้วย vi.mock — แต่คิดดูว่าเราเสียอะไรไป: apiClient ของเรามี interceptor ที่แปลง error ทุกแบบให้เป็น ApiError (บทเรียน 15) ถ้าเรา mock axios ทิ้ง โค้ดส่วนนั้นไม่ได้รันเลยในเทสต์ — interceptor จะพังยับแค่ไหนเทสต์ก็เขียวอยู่ดี เท่ากับเราเทสต์ "ของปลอมที่เราสร้างขึ้นเอง" ไม่ใช่โค้ดจริง

MSW เลือกปลอมที่ชั้นต่ำที่สุดเท่าที่จะทำได้: ชั้น network มันดักจับ HTTP request ตอนที่กำลังจะออกจากโปรเซส แล้วตอบกลับด้วยข้อมูลที่เรากำหนด ผลคือโค้ดฝั่งเราวิ่งครบทั้งสายของจริง — queryOptions → ฟังก์ชันใน api.ts → axios → interceptor — มีแค่ "เซิร์ฟเวอร์ปลายทาง" เท่านั้นที่เป็นของปลอม เทสต์ที่ผ่านจึงบอกได้เต็มปากว่าชั้นข้อมูลทั้งชั้นทำงานถูกจริง

ประโยคสุดท้ายนั้นมีน้ำหนักเป็นพิเศษในคอร์สนี้ เพราะสิ่งที่บทเรียน 15 กับ 16 สั่งห้ามไว้ตรง ๆ — ห้ามใส่ try/catch ที่กลืน error ในชั้น api.ts, ห้ามให้ interceptor จบขาล้มเหลวด้วย return null — เป็นข้อที่ตอนนั้นตรวจได้ด้วยการอ่านอย่างเดียว วันนี้มันจะกลายเป็นข้อที่มีเครื่องมือตรวจให้ได้จริงในบทเรียน 31

ติดตั้ง dependencies

ขั้นนี้คุณรันเอง ไม่ต้องให้ Agent รัน — เพราะมันคือคำสั่งเดียวจบ และเพราะเราอยากให้ package.json ในรอบ prompt ข้างล่างมีสถานะที่รู้แน่นอนแล้ว ทั้งหมดเป็น devDependencies เพราะใช้ตอนพัฒนาเท่านั้น ไม่ถูก bundle ไปกับแอป:

npm install -D vitest jsdom @testing-library/react @testing-library/jest-dom @testing-library/user-event msw @types/node
  • vitest — test runner ตัวเดิมจากคอร์ส React พื้นฐาน ข้อดีใหญ่คือมันใช้ config และ transform pipeline ของ Vite ทำให้ path alias @/ และ SCSS Modules ในโค้ดเราทำงานในเทสต์ได้เลยโดยไม่ต้องตั้งค่าเพิ่ม
  • jsdom — DOM จำลองที่รันใน Node ทำให้ component ของเรา render ได้โดยไม่ต้องเปิดเบราว์เซอร์จริง
  • @testing-library/react — render, screen, renderHook, waitFor สำหรับเทสต์ component และ hook แบบเน้นพฤติกรรมที่ผู้ใช้เห็น
  • @testing-library/jest-dom — matcher เพิ่มเติมอย่าง toBeInTheDocument() ที่ทำให้ assertion อ่านเป็นภาษาคนมากขึ้น
  • @testing-library/user-event — จำลองการพิมพ์และการคลิกแบบเหมือนผู้ใช้จริง (จะได้ใช้หนัก ๆ ในบทเรียน 33)
  • msw — พระเอกใหม่ของเรา: เซิร์ฟเวอร์ปลอมที่ชั้น network
  • @types/node — type ของ Node API (เราใช้ node:url ใน vite.config.ts อยู่แล้ว และไฟล์ config ฝั่งเทสต์จะถูกเช็ค type เข้มขึ้น)

เช็คใน package.json — ควรเห็นเจ็ดรายการใหม่แทรกเข้าไปใน devDependencies (เวอร์ชันของคุณอาจใหม่กว่านี้เล็กน้อย):

"@testing-library/jest-dom": "^7.0.0",
"@testing-library/react": "^16.3.2",
"@testing-library/user-event": "^14.6.1",
"@types/node": "^22.20.1",
"jsdom": "^30.0.1",
"msw": "^2.15.0",
"vitest": "^4.1.10"

บรรทัด "msw": "^2.15.0" เป็นบรรทัดที่ต้องมองด้วยตาจริง ๆ ไม่ใช่กวาดผ่าน เพราะมันคือข้อมูลชิ้นเดียวที่กันกับดักใหญ่ที่สุดของบทนี้ได้ — เดี๋ยวเราจะกลับมาที่มันในกล่อง ✅

เป้าหมายของบทนี้

บทนี้แบ่ง prompt เป็นสองรอบตามทิศทางการพึ่งพา: สี่ไฟล์แรกเป็นสายของ MSW ที่จบในตัวเอง ส่วนสองไฟล์หลังเป็น helper ที่ต้อง import ของจากทั้งแอป (router, provider, query client) การแบ่งแบบนี้ทำให้ git diff ของแต่ละรอบอ่านจบได้จริงตามกติกาข้อแรกของสัญญาณอันตรายในบทเรียน 29

vite.config.ts                   # 🤖 รอบที่ 1 — แก้ไฟล์เดิม เพิ่ม block test
package.json                     # 🤖 รอบที่ 1 — แก้ไฟล์เดิม เพิ่มสอง script
src/
└── test/
    ├── msw/
    │   ├── fixtures.ts          # 🤖 รอบที่ 1 — โรงงานข้อมูลปลอม
    │   ├── handlers.ts          # 🤖 รอบที่ 1 — endpoint ปลอม
    │   └── server.ts            # 🤖 รอบที่ 1 — MSW server ฝั่ง Node
    ├── setup.ts                 # 🤖 รอบที่ 1 — รันก่อนไฟล์เทสต์ทุกไฟล์
    ├── utils.tsx                # 🤖 รอบที่ 2 — QueryClient ของเทสต์
    └── renderRoute.tsx          # 🤖 รอบที่ 2 — render ทั้งแอปในเทสต์

สัญญาที่แต่ละไฟล์ต้องทำให้ได้ — และสิ่งที่มันต้องไม่ทำ:

  • vite.config.ts — ต้องเพิ่มแค่สองจุด: บรรทัด triple-slash บนสุด และ block test ต่อท้าย legacy ต้องไม่แตะ plugins, resolve.alias หรือ block legacy และต้องไม่ลบ comment ภาษาอังกฤษที่อยู่เหนือ legacy แม้แต่บรรทัดเดียว
  • package.json — ต้องเพิ่มสองบรรทัดใน scripts เท่านั้น ต้องไม่แตะ dependencies หรือ devDependencies และต้องไม่รัน npm install ซ้ำ
  • fixtures.ts — ต้องคืน Product ที่ครบทุก field ตาม type จริงของโปรเจกต์ ต้องไม่ประกาศ type ของตัวเองขึ้นมาใหม่ ต้องไม่ import อะไรจาก msw และต้องไม่รู้จัก URL ใด ๆ
  • handlers.ts — ต้องอ่านค่าจาก request จริง (path param และ query string) ไม่ใช่คืนก้อนตายตัวให้ทุกคำขอ ต้องไม่ import อะไรจาก @testing-library และต้องไม่มี assertion อยู่ในนั้น
  • server.ts — ต้อง import setupServer จาก msw/node (ไม่ใช่ msw/browser) และต้องไม่มีอย่างอื่นในไฟล์เลย
  • setup.ts — ต้องเปิด/รีเซ็ต/ปิดเซิร์ฟเวอร์ปลอมครบสามจังหวะ และล้าง localStorage หลังทุกเทสต์ ต้องไม่ import ไฟล์เทสต์ไฟล์ไหน และต้องไม่มี describe หรือ it อยู่ในนั้น
  • utils.tsx — ต้องสร้าง QueryClient ก้อนใหม่ทุกครั้งที่ถูกเรียก และตั้ง retry: false ต้องไม่ import queryClient ตัวจริงจาก src/app/queryClient.ts
  • renderRoute.tsx — ต้องใช้ array routes ตัวจริงจาก @/app/router และ CartProvider ตัวจริงจากแอป ต้องคืน router ออกมาให้เทสต์ใช้ต่อ ต้องไม่ประกาศ route ของตัวเองขึ้นมาใหม่แม้แต่เส้นเดียว

แต่ละ handler คือ endpoint ปลอมหนึ่งตัว หน้าตาเหมือน route ของเซิร์ฟเวอร์เลย: http.get(url, resolver) โดย resolver คืน HttpResponse.json(...) จุดที่ควรสังเกต:

  • handler ไม่ได้แค่คืนของตายตัว — มันอ่าน request จริง ๆ ตัว /products/category/:slug อ่านทั้ง params.slug จาก path และ limit/skip จาก query string แล้วประกอบเป็นชื่อสินค้าอย่าง beauty product 21 (id เริ่มจาก skip + 1) — เท่ากับว่าถ้าเทสต์เห็นข้อความนี้ แปลว่า pagination ของเราคำนวณ skip แล้วส่งไปกับ request ถูกต้องจริง ตลอดทั้งสาย

  • afterEach — ล้างสองอย่างหลังเทสต์ทุกตัว: resetHandlers() ถอด handler ชั่วคราวที่เทสต์นั้นยัดเพิ่มด้วย server.use(...) (จะเจอในบทหน้า) และ localStorage.clear() ล้างตะกร้าที่ค้างอยู่ — จำได้ไหมว่า cart ของเรา persist ลง localStorage ถ้าไม่ล้าง ตะกร้าจากเทสต์หนึ่งจะรั่วไปโผล่ในเทสต์ถัดไป

helper ตัวสุดท้ายนี้คือหัวใจของ integration test ในบทเรียน 33 — เรียก renderRoute("/cart") แล้วได้แอปทั้งแอปเปิดอยู่ที่หน้า Cart:

  • createMemoryRouter(routes, ...) — router ที่เก็บ history ไว้ในหน่วยความจำแทน address bar (ซึ่งไม่มีอยู่จริงใน jsdom) สังเกตว่ามันรับ routes — array เดียวกับที่ createBrowserRouter ตัวจริงใช้ นี่แหละเหตุผลที่บทเรียน 09 เรา export routes แยกจาก router: route table จริงทุกเส้นทาง รวมทั้ง MainLayout และ errorElement ถูกเทสต์ด้วย ไม่ใช่ฉบับจำลอง ส่วน initialEntries คือ URL เริ่มต้น
  • provider ครบชุดเหมือนแอปจริง — QueryClientProvider (ฉบับเทสต์) และ CartProvider ตัวจริง ซ้อนกันตามลำดับเดียวกับ providers.tsx — CartProvider จะ lazy init จาก localStorage เหมือนเดิม เปิดช่องให้เทสต์ "แอบใส่ของในตะกร้า" ได้ด้วยการเขียน localStorage ก่อน render
  • คืน router ออกมาด้วย — เทสต์จะได้ assert เรื่อง navigation ได้ เช่น เช็คว่าหลังสั่งซื้อสำเร็จ router.state.location.pathname กลายเป็น /order/success จริง (บทเรียน 33 ใช้แน่นอน)
