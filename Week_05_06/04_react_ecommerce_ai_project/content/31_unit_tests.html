Unit Tests

เราจะเริ่มจากฐานของพีระมิดการทดสอบ: unit test ของฟังก์ชันล้วน ๆ (pure function) — ฟังก์ชันที่รับ input เดิมแล้วคืน output เดิมเสมอ ไม่แตะ DOM ไม่ยิง network เทสต์กลุ่มนี้เขียนง่ายที่สุด รันเร็วที่สุด (หลักมิลลิวินาที) และเวลาพังมันชี้จุดแม่นที่สุด — บอกได้เลยว่าฟังก์ชันไหน กรณีไหน ค่าที่ได้กับค่าที่คาดต่างกันอย่างไร

ธรรมเนียมของโปรเจกต์นี้: ไฟล์เทสต์อยู่ข้างไฟล์ต้นทางเสมอ (co-located) โดยเติม .test เข้าไปในชื่อ เช่น price.utils.ts คู่กับ price.utils.test.ts — เปิดโฟลเดอร์ไหนก็เห็นทันทีว่าไฟล์ไหนมีเทสต์คุ้มกันอยู่ ระหว่างทำบทนี้แนะนำให้เปิด npm run test:watch ทิ้งไว้ จะได้เห็นเทสต์เขียวขึ้นทีละไฟล์

ทำไมบทนี้ต้องอ่านต่างจากบทอื่น

ยี่สิบสองบทที่ผ่านมา เราแบ่งงานกับ Agent ด้วยหลักเดียวกันตลอด: ให้มันเขียน แล้วเราตรวจ และสิ่งที่ทำให้การตรวจของเราเชื่อถือได้คือมีชั้นที่อยู่เหนือโค้ดชั้นนั้นคอยยืนยันอีกที — npm run typecheck อยู่เหนือ type ที่มันเขียน, npm run lint อยู่เหนือสไตล์ที่มันเลือก, หน้าเว็บที่เปิดดูจริงอยู่เหนือ JSX ที่มันวาง และตั้งแต่วันนี้ เทสต์จะอยู่เหนือ logic ทั้งหมดที่เราเขียนมา

คำถามที่ตามมาทันทีคือ: แล้วอะไรอยู่เหนือเทสต์

คำตอบคือ ไม่มี เทสต์เป็นชั้นบนสุด ถ้าเทสต์ผิด จะไม่มีเครื่องมือตัวไหนในโปรเจกต์นี้ตะโกนบอกคุณ — เพราะเครื่องมือทุกตัวที่เรามีจะบอกได้แค่ว่าเทสต์รันผ่าน ไม่ใช่ว่าเทสต์ทดสอบอะไรอยู่ ในภาษาของบทเรียน 29 นี่คือฝั่งเงียบที่เงียบที่สุดในคอร์สนี้ และมันเงียบในทิศทางที่แย่ที่สุด: มันไม่ได้เงียบเฉย ๆ แต่มันส่งเสียงเขียวใส่คุณด้วย

🚨 เทสต์เป็นที่เดียวที่ AI ทำให้คุณ "รู้สึกปลอดภัย" ได้โดยที่ไม่ได้ปลอดภัยจริง เทสต์ที่ assert ว่าฟังก์ชันคืนค่าเท่ากับสิ่งที่ฟังก์ชันคืน คือเทสต์ที่ผ่านเสมอและไม่ได้พิสูจน์อะไรเลย — และมันจะผ่านต่อไปในวันที่ฟังก์ชันนั้นถูกแก้ผิด ในวันที่สูตรถูกสลับ ในวันที่ guard ถูกลบทิ้ง โค้ดชุดนั้นจะยังมีตัวเลขบอกว่า "ผ่าน 22 tests" อยู่ที่เดิม ทุกอย่างอื่นในคอร์สนี้ที่ AI เขียนผิด อย่างน้อยก็ทำให้บางอย่างพัง แต่เทสต์ที่ AI เขียนผิดจะทำให้ทุกอย่างดูเหมือนไม่พัง ซึ่งแพงกว่ากันมาก

ก้อนโค้ดข้างล่างนี้คือหน้าตาของสิ่งที่พูดถึง มันไม่ใช่โค้ดสมมติ — มันคือรูปแบบที่ Agent เขียนออกมาได้เป็นปกติเวลาถูกสั่งว่า "เขียนเทสต์ให้ฟังก์ชันนี้" โดยไม่มีใครบอกว่าค่าที่คาดหวังคืออะไร:

// เทสต์ที่ผ่านเสมอ — และจะผ่านต่อไปแม้สูตรใน price.utils.ts จะถูกแก้ผิด
it("computes the pre-discount price", () => {
  const price = 90;
  const discount = 10;
  expect(calculateOriginalPrice(price, discount)).toBeCloseTo(
    price / (1 - discount / 100),
  );
});

อ่านผ่าน ๆ มันดูดีกว่าของจริงด้วยซ้ำ — มีชื่อตัวแปรบอกความหมาย ไม่มีตัวเลขลอย ๆ ("magic number") ดูเป็นมืออาชีพ แต่ฝั่งขวาของ toBeCloseTo คือสูตรเดียวกับที่อยู่ในตัวฟังก์ชัน เท่ากับเทสต์นี้ถามว่า "สูตรนี้เท่ากับสูตรนี้ไหม" ซึ่งคำตอบคือใช่เสมอ ไม่ว่าสูตรจะถูกหรือผิด ถ้าใครไปแก้ price.utils.ts เป็น price * (1 - discountPercentage / 100) เทสต์ตัวนี้จะยังเขียว ตราบใดที่คนแก้แก้ทั้งสองที่ให้ตรงกัน — และคนที่แก้มักจะแก้ทั้งสองที่ให้ตรงกัน เพราะนั่นคือวิธีที่เร็วที่สุดที่จะทำให้เทสต์ผ่าน

ของจริงเขียนแบบนี้แทน:

// เทสต์ที่แดงได้ — ฝั่งขวาเป็นตัวเลขที่คนตัดสินใจ ไม่ใช่ผลของโค้ดที่กำลังทดสอบ
it("computes the pre-discount price", () => {
  expect(calculateOriginalPrice(90, 10)).toBeCloseTo(100);
});

100 คือคำตอบที่คนคำนวณเองแล้วเขียนลงไป ถ้าสูตรในฟังก์ชันเปลี่ยน เลขนี้ไม่ขยับตาม เทสต์ก็แดง นี่คือเส้นแบ่งทั้งหมดของบทนี้ในหนึ่งบรรทัด: ฝั่งขวาของ assertion ต้องมาจากหัวคุณ ไม่ใช่จากโค้ดที่กำลังถูกทดสอบ

และนั่นคือเหตุผลที่บทนี้เป็นหนึ่งในสิบจุดที่คอร์สนี้บังคับให้พิมพ์เอง เกณฑ์ที่บทเรียน 29 วางไว้ว่า "โค้ดสั้นกว่าคำอธิบาย" ใช้ได้พอดีตรงนี้ — การอธิบายให้ Agent เข้าใจว่าเทสต์ที่ดีต่างจากเทสต์ที่ผ่านอย่างไร ยาวกว่าตัวเทสต์เองหลายเท่า

  • price.utils.test.ts — ต้องมีสอง it: ทางเดินปกติหนึ่งตัว และกรณีขอบสามค่ารวมกันอีกหนึ่งตัว ทุก assertion ต้องเทียบกับตัวเลขที่เขียนตายตัว ต้องไม่มีตัวแปรหรือนิพจน์คำนวณอยู่ฝั่งขวาของ matcher เลย
  • pagination.utils.test.ts — ต้องแยกเป็นสอง describe ตามชื่อฟังก์ชัน ต้องครอบทั้งกรณีหารลงตัวและหารไม่ลงตัว ต้องไม่ import อะไรนอกจากไฟล์ที่มันทดสอบ
  • cartReducer.test.ts — ต้องครอบ action ครบทั้งสี่ประเภท โดย ADD_TO_CART ต้องมีสองเคส (ของใหม่ กับ ของที่มีอยู่แล้ว) ต้องไม่ render อะไรทั้งสิ้น ต้องไม่แตะ localStorage และต้องไม่ import React
  • cartStorage.test.ts — ต้องใช้ localStorage จริงของ jsdom ต้องไม่ vi.mock localStorage และต้องมีเคสข้อมูลพัง (JSON เสีย) กับเคสรูปร่างผิด (parse ได้แต่ items ไม่ใช่ array) แยกกันคนละ it
  • schema.test.ts — ต้อง assert ตัวข้อความ error ไม่ใช่แค่ success === false ต้องใช้ safeParse ไม่ใช่ parse และต้องพังทีละ field จาก object ที่ valid ก้อนเดียว ต้องไม่ import consts.ts หรือ react-hook-form
  • client.test.ts — ต้องพิสูจน์ว่า error ที่หลุดออกมาเป็น instanceof ApiError จริง ต้องใช้ server.use(...) เพื่อจำลอง error ไม่ใช่ vi.mock axios และต้องไม่เรียก server.resetHandlers() เองในไฟล์

✍️ ส่วนนี้พิมพ์เอง

ก่อนลงมือ มีเรื่องหนึ่งที่ต่างจากทุกครั้งที่ผ่านมา และมันเปลี่ยนลำดับงานของบทนี้ทั้งบท กฎที่เราใช้มาตั้งแต่บทเรียน 12 คือ สิ่งที่พังเมื่อคุณตัดไฟล์ X ออกจาก prompt คือไฟล์ที่ import X ไม่ใช่ตัว X เอง เอากฎนี้มาจับกับ price.utils.test.ts แล้วไล่หาว่า "ใคร import ไฟล์นี้":

grep -rn "price.utils.test" src/

ว่างเปล่า และมันจะว่างเปล่าสำหรับไฟล์ .test.* ทุกไฟล์ในโปรเจกต์ เพราะไม่มีอะไรในโค้ดที่ import ไฟล์เทสต์ — Vitest เป็นคนหาไฟล์เหล่านี้เองจากรูปแบบชื่อ ไม่ได้ถูกใครเรียกใช้ผ่าน import สักที่ ผลคือไฟล์เทสต์ทุกไฟล์อยู่ปลายสายเสมอ ไม่มีวันอยู่ตรงกลางแบบ cartReducer.ts ในบทเรียน 22

แปลว่าคราวนี้เป็นครั้งแรกในคอร์สที่ การตัดไฟล์ออกจาก prompt ไม่มีต้นทุนทางโครงสร้างเลย ไม่มีไฟล์ไหนพัง ไม่มี typecheck ตก ไม่ต้องแบ่ง prompt เป็นสองรอบเพื่อเสียบมือเข้าไปตรงรอยตัด เราจึงเลือกลำดับที่ให้ประโยชน์มากที่สุดแทน: พิมพ์เองก่อน แล้วค่อยส่ง prompt ด้วยเหตุผลสองข้อ ข้อแรกคือกลไกเดียวกับรอบที่ 2 ของบทเรียน 22 — ไฟล์ที่คุณพิมพ์กลายเป็นบริบทที่ @-mention ได้ Agent จะเห็นสไตล์จริงของเทสต์ในโปรเจกต์นี้ ไม่ใช่สไตล์ที่มันเดา ข้อที่สองสำคัญกว่า: คุณต้องมีมาตรฐานอยู่ในหัวก่อนที่ของห้าไฟล์จะเข้ามาให้ตรวจ

แต่ถึงไม่มีต้นทุนทางโครงสร้าง ก็มีต้นทุนอีกแบบมาแทนที่ และมันคือต้นทุนที่ทั้งบทนี้พูดถึง: เพราะไม่มีใคร import ไฟล์เทสต์ จึงไม่มีอะไรในเครื่องมือชุดนี้ที่สังเกตได้ว่ามันผิด ไฟล์ที่อยู่ตรงกลางสายอย่าง cartReducer.ts ถ้าเขียนผิด typecheck จะฟ้องจากฝั่ง CartProvider ทันที ส่วนไฟล์เทสต์ที่เขียนผิด ไม่มีฝั่งไหนให้ฟ้อง — ความปลอดภัยที่หายไปจากด้านโครงสร้าง ต้องเอาสายตาคนมาชดเชยทั้งหมด

✍️ ส่วนนี้พิมพ์เอง — ทำตามลำดับนี้ ห้ามก๊อปวาง ห้ามให้ Agent ช่วยเติม (ถ้ามีปุ่ม autocomplete ของ Cursor เด้งขึ้นมาแล้วคุณกด Tab รับ นั่นก็คือการก๊อป):

  1. ยืนยันก่อนว่าบทเรียน 30 commit แล้ว — git status ต้องสะอาด ไม่งั้น diff ของ prompt ข้างล่างจะปนโค้ดที่คุณพิมพ์เองเข้ากับโค้ดของ Agent
  2. เปิด src/shared/utils/price.utils.ts วางไว้ข้าง ๆ แล้วพิมพ์ src/shared/utils/price.utils.test.ts ทั้งไฟล์ — ระหว่างพิมพ์ ทุกครั้งที่คุณกำลังจะพิมพ์ตัวเลขฝั่งขวาของ matcher ให้หยุดคำนวณในหัวก่อนหนึ่งวินาที ห้ามลอกจากสูตรในไฟล์ต้นทาง
  3. npm run test ต้องได้ 1 test file, 2 tests ผ่าน จากนั้น npm run lint และ npm run typecheck ให้ผ่านทั้งคู่ แล้ว git commit — ไฟล์ต้องมีอยู่จริงและถูก commit ก่อน prompt ถึงจะ @-mention มันได้
  4. ทำขั้นตอน "ทำให้มันแดง" หนึ่งรอบ ก่อนไปต่อ — วิธีอยู่ในย่อหน้าใต้กล่องนี้ ข้อนี้ห้ามข้าม

src/shared/utils/price.utils.test.ts:

import { calculateOriginalPrice } from "./price.utils";

describe("calculateOriginalPrice", () => {
  it("computes the pre-discount price", () => {
    expect(calculateOriginalPrice(90, 10)).toBeCloseTo(100);
  });

  it("returns the price unchanged when there is no discount", () => {
    expect(calculateOriginalPrice(50, undefined)).toBe(50);
    expect(calculateOriginalPrice(50, 0)).toBe(50);
    expect(calculateOriginalPrice(50, 100)).toBe(50);
  });
});

เหตุผล: ต้องเขียนเทสต์เองให้เป็นก่อน ถึงจะตรวจเทสต์ของ AI ออก สิบสามบรรทัดนี้มีการตัดสินใจของคนอยู่ห้าจุดที่ Agent ไม่มีทางเดาถูกครบ: เลข 100 ที่คำนวณจากหัว, การเลือก toBeCloseTo แทน toBe เพราะรู้ว่าการหารเลขทศนิยมแบบ binary ไม่มีการันตีว่าจะลงตัวเป๊ะเสมอ ต่อให้อินพุตชุดนี้บังเอิญลงตัวพอดีก็ตาม, การรวมค่าขอบสามค่าไว้ใน it เดียวเพราะทั้งสามค่าพิสูจน์กติกาข้อเดียวกัน, การเลือกว่า 100 เป็นค่าขอบที่ต้องเทสต์ (ไม่ใช่ 99) และการเลือกว่าไม่เทสต์อะไร คุณจะไม่มีมาตรฐานในหัวไว้เทียบกับเทสต์ห้าไฟล์ที่กำลังจะเข้ามา ถ้าไม่เคยลากเส้นห้าเส้นนี้ด้วยมือตัวเองสักครั้ง

ทวนโครงสร้างที่เจอมาแล้วในคอร์ส React พื้นฐาน: describe จัดกลุ่มเทสต์ของสิ่งเดียวกัน (ชื่อกลุ่มคือชื่อฟังก์ชัน — เวลาพังจะอ่านรายงานรู้เรื่องทันที), it คือหนึ่งพฤติกรรมที่อยากพิสูจน์ โดยตั้งชื่อให้อ่านต่อกันเป็นประโยค: "calculateOriginalPrice computes the pre-discount price" และ expect คือ assertion — สังเกตว่าทั้งสามอย่างใช้ได้เลยไม่ต้อง import เพราะเราเปิด globals: true ไว้เมื่อบทที่แล้ว

  • toBeCloseTo(100) ไม่ใช่ toBe(100) — 90 / (1 - 10/100) ตัวนี้บังเอิญออกมาเป๊ะ 100 พอดี แต่นั่นคือความบังเอิญของอินพุตชุดนี้ ไม่ใช่การันตีของการหารเลขทศนิยมแบบ binary เปลี่ยนอินพุตนิดเดียวก็คลาดเคลื่อนได้ทันที เช่น 9.99 / (1 - 17/100) ได้ 12.036144578313253 ไม่ใช่เลขลงตัว — กฎง่าย ๆ: assertion กับผลหารหรือผลคูณของทศนิยม ให้ใช้ toBeCloseTo เสมอ เพื่อไม่ต้องพึ่งดวงว่าอินพุตจะลงตัวหรือไม่
  • เทสต์ที่สองคือเทสต์ขอบเขต (edge case) — ตัวฟังก์ชันเขียน guard ไว้ว่า discount ที่ไม่มีค่า, ≤ 0 หรือ ≥ 100 ให้คืนราคาเดิม เทสต์นี้ยิงทั้งสามกรณีในตาเดียว การเทสต์ edge case พวกนี้แหละคือค่าตัวจริงของ unit test — ทางเดินปกติมักไม่ค่อยพัง ที่พังคือขอบ และนั่นคือเหตุผลที่ค่า 100 ในบรรทัดสุดท้ายสำคัญกว่าที่เห็น: มันยืนอยู่บนขอบพอดี ถ้าใครแก้ guard จาก >= 100 เป็น > 100 บรรทัดนั้นจะเป็นบรรทัดเดียวในทั้งไฟล์ที่จับได้ (ลองดูได้เลย — จะได้ Infinity แทน 50)

ตอนนี้ทำขั้นที่ 4 ให้จบ เพราะมันคือกติกาที่จะใช้ซ้ำกับทุกไฟล์ในบทนี้: เปิด src/shared/utils/price.utils.ts แล้วแก้ให้ผิดหนึ่งบรรทัด เปลี่ยน return price / (1 - discountPercentage / 100); เป็น return price * (1 - discountPercentage / 100); แล้วรันเทสต์ใหม่ ต้องเห็น expected 81 to be close to 100 เป็นสีแดง จากนั้น git restore src/shared/utils/price.utils.ts คืนของเดิม แล้วรันซ้ำให้เขียว

import { CartActionTypes, CartItem, CartState } from "./CartContext";
import { cartReducer } from "./cartReducer";

const item = (overrides: Partial<CartItem> = {}): CartItem => ({
  id: 1,
  title: "Widget",
  price: 10,
  quantity: 1,
  image: "/widget.png",
  ...overrides,
});

const stateWith = (...items: CartItem[]): CartState => ({ items });

describe("cartReducer", () => {
  it("adds a new item", () => {
    const next = cartReducer(stateWith(), {
      type: CartActionTypes.ADD_TO_CART,
      payload: item(),
    });
    expect(next.items).toEqual([item()]);
  });

  it("merges quantity when the item already exists", () => {
    const next = cartReducer(stateWith(item({ quantity: 2 })), {
      type: CartActionTypes.ADD_TO_CART,
      payload: item({ quantity: 3 }),
    });
    expect(next.items).toEqual([item({ quantity: 5 })]);
  });

  it("removes an item", () => {
    const next = cartReducer(stateWith(item(), item({ id: 2 })), {
      type: CartActionTypes.REMOVE_FROM_CART,
      payload: { id: 1 },
    });
    expect(next.items).toEqual([item({ id: 2 })]);
  });

  it("updates quantity", () => {
    const next = cartReducer(stateWith(item()), {
      type: CartActionTypes.UPDATE_QUANTITY,
      payload: { id: 1, quantity: 7 },
    });
    expect(next.items[0]?.quantity).toBe(7);
  });

  it("clears the cart", () => {
    const next = cartReducer(stateWith(item(), item({ id: 2 })), {
      type: CartActionTypes.CLEAR_CART,
    });
    expect(next.items).toEqual([]);
  });
});

สังเกตว่าเราใช้เทคนิค factory เดียวกับ makeProduct ในบทที่แล้ว แต่ย่อส่วน: item() สร้าง CartItem มาตรฐานที่ override ได้ และ stateWith(...) ประกอบ state จากรายการสินค้ากี่ชิ้นก็ได้ (รวมถึงศูนย์ชิ้น — stateWith() คือตะกร้าว่าง) helper สองตัวนี้ทำให้ห้าเทสต์ที่เหลืออ่านเหมือนตาราง: state ตั้งต้นอะไร ยิง action อะไร คาดหวัง state ไหน

ห้าเทสต์นี้ครอบคลุม action ทั้งสี่ประเภทของ reducer โดย ADD_TO_CART ได้สองเทสต์เพราะมันมีสอง branch: เพิ่มของใหม่ กับเพิ่มของที่มีอยู่แล้ว — อย่างหลังต้องรวมจำนวน (2 + 3 = 5) ไม่ใช่แทรกแถวซ้ำ ซึ่งเป็น bug ที่เจอบ่อยมากในตะกร้าสินค้าจริง ๆ อีกสองรายละเอียดเล็ก ๆ ที่อยากชี้:

  • toEqual ไม่ใช่ toBe — toBe เทียบว่าเป็น object ตัวเดียวกันในหน่วยความจำ ส่วน toEqual เทียบเนื้อหาทีละ field ซึ่งคือสิ่งที่เราต้องการ เพราะ reducer ที่ดีต้องคืน object ใหม่เสมอ (immutability)
  • next.items[0]?.quantity — ใส่ optional chaining กันไว้ เผื่อ reducer มี bug จน items ว่าง เทสต์จะ fail แบบสุภาพ (undefined ไม่เท่ากับ 7) แทนที่จะ crash กลางทาง
💡 ของที่ควรถูกทักในรีวิว — ช่องโหว่ที่ใหญ่ที่สุดในบทนี้ อยู่ในไฟล์ที่ดูสมบูรณ์ที่สุด: ห้าเทสต์ข้างบนครอบ action ครบทั้งสี่ประเภท แต่ไม่มีเทสต์ตัวไหนพิสูจน์ immutability เลยแม้แต่ตัวเดียว — ซึ่งเป็นสัญญาข้อเดียวที่ทำให้ cartReducer.ts ถูกจัดเป็นไฟล์พิมพ์เองในบทเรียน 22 ตั้งแต่แรก ลองคิดตาม: ถ้ามีคนเขียน reducer ใหม่เป็น state.items.push(action.payload); return state; ในเคส ADD_TO_CART เทสต์ "adds a new item" จะยังเขียว เพราะ toEqual เทียบเนื้อหา ไม่ได้เทียบว่าเป็นคนละ object และเคส "merges quantity" ที่เขียนเป็น existingItem.quantity += quantity; return state; ก็เขียวเช่นกันด้วยเหตุผลเดียวกัน พูดอีกอย่างคือ reducer ที่ mutate state เดิมทั้งไฟล์จะผ่านเทสต์ชุดนี้ครบห้าตัว แล้วอาการจะไปโผล่ในบทเรียน 33 เป็นหน้า Cart ที่กดปุ่มแล้วตัวเลขไม่ขยับ ซึ่งเป็นบั๊กเดียวกับที่ตระกูล 6 ของบทเรียน 29 ระบุไว้ว่าเป็นเหตุผลที่ไฟล์นี้ต้องพิมพ์เอง สิ่งที่ขาดคือสองบรรทัดเท่านั้น — expect(next.items).not.toBe(prev.items) และ expect(prev.items[0]?.quantity).toBe(2) (ยืนยันว่า state ตั้งต้นไม่ถูกแก้) เราสั่งตามต้นฉบับเพื่อให้ diff ตรง แต่ในรีวิวจริงนี่คือข้อแรกที่ควรถูกทัก และเป็นตัวอย่างที่ตรงที่สุดของหัวข้อทั้งบท: เทสต์ที่ครบทุก case ไม่ได้แปลว่าครบทุกสัญญา จำนวนเทสต์เป็นตัวเลขที่วัดง่ายและวัดผิดที่สุดในงานนี้ ข้อพ่วงเล็ก ๆ ในไฟล์ข้าง ๆ: cartReducer.test.ts ใช้รูปสินค้า /widget.png ส่วน cartStorage.test.ts ใช้ /w.png ทั้งที่เป็นสินค้าสมมติตัวเดียวกันชื่อ Widget — ไม่มีผลอะไรทั้งสิ้น แต่เป็นความไม่สม่ำเสมอที่มีอยู่จริงในต้นฉบับ และเป็นรูปแบบเดิมที่คอร์สนี้เจอมาตลอด: สิ่งที่ไม่มีเครื่องมือบังคับจะเพี้ยนไปทีละไฟล์

คำถามแรกที่ควรถาม: แล้ว localStorage มาจากไหน? คำตอบคือ jsdom ให้มาฟรี — เพราะเราตั้ง environment: "jsdom" เทสต์จึงมี localStorage จริง ๆ ที่ใช้งานได้ (แค่อยู่ในหน่วยความจำ) เราเลยไม่ต้อง mock อะไรเลย: saveCartState เขียนลง storage จริง loadCartState อ่านกลับมาจริง โค้ด production ทุกบรรทัดได้รันในเทสต์

แต่ storage ที่แชร์กันก็มีความเสี่ยง: ถ้าเทสต์แรก save ค้างไว้ เทสต์ที่สอง ("nothing is stored") จะเจอของเก่าแล้วพัง — นี่คือหน้าที่ของบรรทัด localStorage.clear() ใน afterEach ของ setup.ts ที่เราเขียนไว้บทที่แล้ว ทุกเทสต์จึงเริ่มจาก storage ว่างเสมอ และเป็นเหตุผลที่เทสต์เหล่านี้เซ็ตข้อมูลเองในตัวโดยไม่ต้องเก็บกวาดทีหลัง สังเกตว่าเทสต์ที่สองเป็นเทสต์ที่จะเปลี่ยนผลทันทีถ้าบรรทัดนั้นหายไป — นี่คือคู่ที่ควรจำ: เทสต์หนึ่งตัวในไฟล์นี้ทำหน้าที่เฝ้าบรรทัดหนึ่งบรรทัดในอีกไฟล์หนึ่งอยู่โดยที่ไม่มีอะไรเขียนไว้

สองเทสต์สุดท้ายคือการเทสต์ "โลกจริงที่โหดร้าย": ผู้ใช้อาจมีข้อมูลเก่าจากเวอร์ชันก่อน หรือ extension บางตัวเขียนทับ key ของเรา — เทสต์ที่สามป้อน JSON พัง ๆ ("{not json") เพื่อพิสูจน์ว่า try/catch ทำงาน ส่วนเทสต์ที่สี่ป้อน JSON ที่ parse ได้แต่รูปร่างผิด (items เป็น string) เพื่อพิสูจน์ guard Array.isArray — ทั้งสองกรณีต้อง fallback เป็นตะกร้าว่างเงียบ ๆ ไม่ใช่ทำแอปพังทั้งหน้า และสองเคสนี้คือเหตุผลที่บทเรียน 22 สั่งใน checklist ว่า grep -c "catch" ต้องได้ 2 — วันนี้ข้อนั้นมีเครื่องมือตรวจให้แล้ว

  • เริ่มจาก object ที่ valid หนึ่งตัว แล้วแต่ละเทสต์ invalid ใช้ spread พังมันทีละ field: { ...valid, address: "" } — ถ้าพังหลาย field พร้อมกันเราจะไม่รู้ว่า error มาจากกติกาข้อไหน (และ issues[0] จะชี้ไปที่ field ไหนก็ได้แล้วแต่ลำดับใน schema)
  • safeParse ไม่ใช่ parse — parse โยน exception เมื่อไม่ผ่าน แต่ safeParse คืน result object ที่มี success กับ error ให้ assert ได้ตรง ๆ ไม่ต้องเล่นท่า try/catch ในเทสต์ นี่คือสิ่งที่บทเรียน 25 บอกไว้ล่วงหน้าว่าจะกลับมาใช้ในบทนี้
  • assert ตัวข้อความ error ด้วย — ไม่ใช่แค่ success === false เพราะข้อความพวกนี้คือสิ่งที่ผู้ใช้เห็นใต้ช่องฟอร์มจริง ๆ (ผ่าน react-hook-form + zodResolver ในบทเรียน 26) ถ้าใครแก้ข้อความใน schema โดยไม่ตั้งใจ เทสต์จะเตือน

เรื่องรูปแบบหนึ่งข้อ: บรรทัด toBe( ในเทสต์ที่สามถูกตัดเป็นสามบรรทัดขณะที่อีกสองเทสต์เขียนจบในบรรทัดเดียว นั่นคือฝีมือ Prettier ไม่ใช่ความไม่สม่ำเสมอของคนเขียน — ข้อความ "Enter a valid email address" ยาวกว่าอีกสองก้อนพอดีจนเลย 80 ตัวอักษร ถ้าโค้ดที่ Agent ส่งมาต่างจากนี้ ให้รัน npm run format แล้วเทียบใหม่ก่อนสรุปว่ามันเขียนต่าง

src/shared/api/client.test.ts — unit test ตัวแรกที่ใช้ MSW

ปิดท้ายด้วยไฟล์ที่พิเศษหน่อย: apiClient ไม่ใช่ pure function — มันยิง HTTP — แต่เพราะ MSW ดักที่ชั้น network ให้ เราเทสต์มันได้เหมือน unit test ปกติ และนี่คือเทสต์ที่พิสูจน์ interceptor จากบทเรียน 15 ว่าแปลง error ได้ถูกจริง

import { http, HttpResponse } from "msw";

import { ApiError, apiClient } from "./client";
import { server } from "@/test/msw/server";

describe("apiClient", () => {
  it("returns response data on success", async () => {
    const { data } = await apiClient.get("/products/1");
    expect(data.id).toBe(1);
  });

  it("normalizes server errors into ApiError with the server message", async () => {
    server.use(
      http.get("https://dummyjson.com/products/1", () =>
        HttpResponse.json({ message: "Product not found" }, { status: 404 }),
      ),
    );

    const error = await apiClient.get("/products/1").catch((e) => e);
    expect(error).toBeInstanceOf(ApiError);
    expect(error.message).toBe("Product not found");
    expect(error.status).toBe(404);
  });

  it("falls back to a generic message when the server sends none", async () => {
    server.use(
      http.get("https://dummyjson.com/products/1", () =>
        HttpResponse.json({}, { status: 500 }),
      ),
    );

    const error = await apiClient.get("/products/1").catch((e) => e);
    expect(error).toBeInstanceOf(ApiError);
    expect(error.message).toBe("Something went wrong. Please try again.");
  });
});

ของใหม่ในไฟล์นี้มีสามอย่าง:

  • เทสต์แรกไม่ต้องเตรียมอะไรเลย — GET /products/1 match handler ตั้งต้นใน handlers.ts อยู่แล้ว ซึ่งคืน makeProduct({ id: 1 }) เทสต์นี้จึงพิสูจน์ happy path ของทั้ง baseURL (มาจาก env ที่เรา hardcode ไว้ใน vite.config) และการส่งข้อมูลผ่าน axios
  • server.use(...) คือการ override handler ชั่วคราว — วิธีจำลอง "เซิร์ฟเวอร์ตอบ error" สำหรับเทสต์นั้น ๆ โดยเฉพาะ: handler ที่ยัดเข้าไปด้วย server.use จะถูกลองก่อน handler ตั้งต้น และถูกถอดทิ้งโดย server.resetHandlers() ใน afterEach ของ setup — เทสต์ถัดไปกลับมาเจอเซิร์ฟเวอร์ปกติเสมอ ไม่มี error รั่วข้ามเทสต์
  • ท่า .catch((e) => e) — ปกติ promise ที่ reject จะโยน exception แต่ท่านี้ "จับ" error แล้วคืนมันออกมาเป็นค่าธรรมดา ทำให้เรา assert กับตัว error ได้หลายบรรทัดสบาย ๆ: เป็น instance ของ ApiError ไหม (พิสูจน์ว่า interceptor ห่อ error ให้จริง ไม่ใช่ AxiosError ดิบหลุดมา), message ตรงกับที่เซิร์ฟเวอร์ส่งไหม และ status ติดมาไหม เทสต์ที่สามกลับด้าน: เซิร์ฟเวอร์ตอบ 500 แบบไม่มี message — interceptor ต้อง fallback เป็นข้อความกลาง ๆ ที่เราเตรียมไว้

บรรทัด expect(error).toBeInstanceOf(ApiError) คือบรรทัดที่บทเรียน 15 สั่งไว้ล่วงหน้าว่าต้องเขียน class ApiError extends Error ไม่ใช่ interface หรือ type — ถ้าตอนนั้นทำอีกแบบ บรรทัดนี้จะเขียนไม่ได้เลยและเทสต์ทั้งไฟล์จะเหลือแค่การเช็คข้อความ ซึ่งอ่อนกว่ากันมาก นี่คือตัวอย่างที่ชัดของ "การตัดสินใจในบทที่ 15 ไปเก็บดอกในบทที่ 31"

อีกเรื่องรูปแบบ: สังเกตบรรทัดว่างหลัง import { http, HttpResponse } from "msw"; — ไฟล์นี้เป็นไฟล์เดียวในหกไฟล์ของบทนี้ที่แยกกลุ่ม import ด้วยบรรทัดว่าง อีกห้าไฟล์เขียนติดกันหมด ไม่มีกฎ lint ตัวไหนบังคับเรื่องนี้และ Prettier ก็ไม่ยุ่ง (มันเก็บบรรทัดว่างที่คุณเขียนไว้ตามเดิม) เราจึงต้องสั่งมันลงไปใน prompt ตรง ๆ ไม่งั้น diff จะต่างจากโค้ดอ้างอิงหนึ่งบรรทัดโดยที่ไม่มีใครผิด — ในรีวิวจริงข้อนี้คือ comment หนึ่งบรรทัดว่าให้เลือกสไตล์เดียวทั้งโปรเจกต์
