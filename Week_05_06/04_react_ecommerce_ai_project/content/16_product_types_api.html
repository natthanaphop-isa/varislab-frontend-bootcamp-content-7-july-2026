บทเรียน 16 · ชั้นข้อมูลสินค้า (Products Data Layer)

Types และ Products API

Product Types & API

บทที่แล้วเราได้ apiClient ที่ต่อกับ dummyjson และจัดการ error ให้เรียบร้อยแล้ว แต่ข้อมูลที่ได้กลับมายังเป็นก้อน JSON ไร้ type — TypeScript ไม่รู้ว่าข้างในมีอะไร autocomplete ไม่ทำงาน สะกด field ผิดก็ไม่มีใครเตือน บทนี้เราจะแก้ทั้งหมดนั้นด้วยไฟล์สามตัว: types ที่บรรยายหน้าตาข้อมูลสินค้า, pagination utils สำหรับคณิตศาสตร์ของการแบ่งหน้า และ api.ts ที่รวมฟังก์ชันเรียก API แบบ typed ครบทุก endpoint

และบทนี้มีเรื่องที่ต้องระวังเป็นพิเศษเรื่องหนึ่ง ซึ่งจะกลายเป็นข้อแรกของ checklist: งานนี้คือการคัดลอกความจริงของ API ภายนอกลงมาเป็นโค้ด ซึ่งเป็นงานประเภทเดียวที่ Agent เดาแทนเราไม่ได้เลย — มันไม่เคยเห็น payload จริง

ทวนก่อน: Pagination จากบทเรียน 05

ตอนที่เราวางสถาปัตยกรรมในบทเรียน 05 เราสร้าง src/shared/types/generic.type.ts ทิ้งไว้ ซึ่งวันนี้ได้ใช้จริงแล้ว:

export interface Pagination {
  total: number;
  skip: number;
  limit: number;
}

ทำไมสามฟิลด์นี้? เพราะ endpoint แบบ "รายการ" ของ dummyjson ทุกตัวตอบข้อมูลกำกับการแบ่งหน้ากลับมาด้วยเสมอ ลองดูผลจาก GET /products?limit=1 (ตัดฟิลด์ของตัวสินค้าออกไปหลายตัวให้อ่านง่าย — ของจริงมีมากกว่า 20 ฟิลด์ต่อชิ้น และตัวเลขอาจต่างไปเล็กน้อยตามข้อมูลบน server):

{
  "products": [
    {
      "id": 1,
      "title": "Essence Mascara Lash Princess",
      "category": "beauty",
      "price": 9.99,
      "thumbnail": "https://cdn.dummyjson.com/..."
    }
  ],
  "total": 194,
  "skip": 0,
  "limit": 1
}

total คือจำนวนสินค้าทั้งหมดที่มี, skip คือจำนวนที่ถูกข้ามไป และ limit คือจำนวนต่อหน้า — สามค่านี้คือวัตถุดิบที่หน้า Category จะใช้คำนวณว่ามีทั้งหมดกี่หน้า ที่เราวาง type นี้ไว้ใน shared ไม่ใช่ใน features/products ก็เพราะรูปแบบ pagination แบบนี้ไม่ได้ผูกกับสินค้า — API ไหน ๆ ก็นิยมใช้โครงเดียวกัน

โมเดลข้อมูลอย่างซื่อสัตย์

หลักการสำคัญที่สุดของบทนี้: type ต้องบรรยายสิ่งที่ API ตอบกลับมาจริง ๆ ไม่ใช่สิ่งที่เราอยากให้มันเป็น ทุกฟิลด์ใน Product ต้องลอกมาจาก JSON จริงของ dummyjson ตรง ๆ — object ซ้อนอย่าง dimensions และ meta ก็แยกออกมาเป็น interface ของตัวเอง (ProductDimensions, ProductMeta) เพื่อให้อ่านง่ายและหยิบไปใช้ซ้ำได้

เราจะประกาศแม้กระทั่งฟิลด์ที่ตอนนี้ยังไม่มีแผนจะแสดงผล เช่น barcode, qrCode หรือ sku — ทำไม? เพราะการประกาศไว้แทบไม่มีต้นทุน แต่ให้ผลตอบแทนตลอดทาง: autocomplete เห็นครบทุกฟิลด์, มีเอกสารบรรยาย API อยู่ในโค้ดเราเอง และเมื่อฟีเจอร์ใหม่ต้องใช้ฟิลด์ไหนเพิ่ม ก็ไม่ต้องกลับไปนั่งแกะ JSON ใหม่อีกรอบ ถ้าเราตัด type ให้เหลือแค่ที่ใช้วันนี้ เท่ากับโยนความรู้เรื่อง API ทิ้งไปครึ่งหนึ่ง

นี่คือจุดที่ต้องเข้าใจให้ขาดก่อนส่ง prompt: type ที่โกหกจะไม่ทำให้อะไรพังเลยจนกว่าจะถึงหน้าเว็บ ถ้าเราประกาศฟิลด์ที่ API ไม่ได้ส่งมา TypeScript จะไม่บ่นสักคำ (มันเชื่อสิ่งที่เราประกาศ) แล้ว npm run typecheck ก็ผ่าน จนกว่าจะถึงบทเรียน 21 ที่หน้า Product แสดงคำว่า undefined ออกมากลางจอ ความรู้เรื่องหน้าตาของ payload จึงเป็นสิ่งที่ต้องมาจากคุณ ไม่ใช่จาก Agent

มนุษย์คิดเป็น "หน้า" dummyjson คิดเป็น "skip"

ปัญหาถัดมา: มนุษย์คิดเป็นหน้า (หน้า 1, หน้า 2, หน้า 3...) แต่ dummyjson คิดเป็น skip กับ limit เราต้องมีตัวแปลระหว่างสองโลกนี้ ซึ่งจะอยู่ในไฟล์ src/shared/utils/pagination.utils.ts และมีสองฟังก์ชัน

calculateOffset แปลงเลขหน้าเป็นจำนวนที่ต้องข้าม: อยู่หน้าไหน แปลว่าข้ามสินค้าของหน้าก่อน ๆ ไปแล้วกี่ชิ้น ลองแทนค่าที่ limit = 20 ดู:

  • หน้า 1 → (1 - 1) * 20 = 0 — ไม่ข้ามเลย เริ่มจากชิ้นแรก
  • หน้า 2 → (2 - 1) * 20 = 20 — ข้าม 20 ชิ้นแรกที่หน้า 1 แสดงไปแล้ว
  • หน้า 3 → (3 - 1) * 20 = 40

calculateTotalPages ทำงานขากลับ: รู้จำนวนสินค้าทั้งหมดกับจำนวนต่อหน้า แล้วตอบว่ามีกี่หน้า ที่ต้องใช้ Math.ceil (ปัดขึ้นเสมอ) เพราะเศษที่เหลือไม่เต็มหน้าก็ยังต้องมีหน้าให้มันอยู่ — สินค้า 194 ชิ้น หน้าละ 20 คือ 194 / 20 = 9.7 ปัดขึ้นเป็น 10 หน้า โดยหน้าสุดท้ายมีของแค่ 14 ชิ้น ถ้าเผลอใช้ Math.floor สินค้า 14 ชิ้นสุดท้ายจะไม่มีวันถูกเห็นเลย

สองฟังก์ชันนี้จะถูกใช้จริงในหน้า Category (บทเรียน 20): เอา data.total จาก API มาเข้า calculateTotalPages เพื่อบอกคอมโพเนนต์ Pagination ที่เราสร้างไว้บทเรียน 13 ว่าต้องวาดปุ่มกี่หน้า ส่วน calculateOffset จะได้ใช้ในไฟล์ api.ts ของบทนี้เลย และเพราะทั้งคู่เป็น pure function ที่ไม่แตะ DOM ไม่แตะ network มันจึงเป็นเป้าเทสต์ที่ง่ายที่สุดในแอป — บทเรียน 31 เราจะเขียน unit test ให้มันเป็นกลุ่มแรก ๆ

เป้าหมายของบทนี้

สามไฟล์ใหม่ ไม่มีไฟล์ไหนพิมพ์เอง — บทนี้เป็นงานที่ Agent ทำได้ดีถ้าเราป้อนความจริงของ API ให้มันครบ:

src/
├── features/
│   └── products/
│       ├── types.ts              # 🤖 รูปร่างข้อมูลสินค้าตาม dummyjson
│       └── api.ts                # 🤖 สี่ฟังก์ชัน หนึ่งตัวต่อหนึ่ง endpoint
└── shared/
    └── utils/
        └── pagination.utils.ts   # 🤖 คณิตศาสตร์ของการแบ่งหน้า

ทั้งสองโฟลเดอร์ (src/features/products/ และ src/shared/utils/) เราสั่ง mkdir ทิ้งไว้ตั้งแต่บทเรียน 05 และยังว่างอยู่จนถึงตอนนี้

สัญญาที่แต่ละไฟล์ต้องทำให้ได้ — และสิ่งที่มันต้องไม่ทำ:

  • types.ts — ต้องมีหก interface ที่ export ครบ (ProductDimensions, ProductReview, ProductMeta, Product, Category, FetchProductsResponse) และชื่อฟิลด์ทุกตัวต้องสะกดตรงกับ payload จริงของ dummyjson ต้องไม่มี any, ไม่มี index signature แบบ [key: string]: unknown และต้องไม่ทำให้ทุกฟิลด์เป็น optional เพื่อความปลอดภัย
  • pagination.utils.ts — ต้องเป็น pure function สองตัวที่รับ number คืน number ต้องไม่รู้จัก axios, ไม่รู้จัก Product และไม่มี state ใด ๆ
  • api.ts — ต้องมีสี่ฟังก์ชันตรงกับสี่ endpoint แต่ละตัวคืน data ที่ typed แล้ว และรับพารามิเตอร์เป็น page ไม่ใช่ skip ต้องไม่มี try/catch ไม่มีการแปลง error เอง และต้องไม่มีคำว่า skip โผล่ในหน้าตาของฟังก์ชันที่คนอื่นเรียก

🤖 Prompt ที่ส่งให้ Cursor

prompt ของบทนี้ยาวกว่าทุกบทที่ผ่านมา และความยาวนั้นอยู่ที่รายชื่อฟิลด์เกือบทั้งหมด นั่นถูกแล้ว — รายชื่อฟิลด์คือข้อมูลที่ Agent ไม่มีทางรู้ ส่วนรูปทรงของไฟล์นั้นมันรู้อยู่แล้ว

🤖 Prompt ที่ส่งให้ Cursor — แชทใหม่ โหมด Agent ก่อนกดส่ง เปิด https://dummyjson.com/products?limit=5 ในเบราว์เซอร์ค้างไว้อีกแท็บหนึ่ง เดี๋ยวตอนตรวจงานจะได้ไม่ต้องหา:

สร้าง type ของสินค้า ฟังก์ชันคำนวณการแบ่งหน้า และฟังก์ชันเรียก API ของ dummyjson

บริบท: @src/shared/api/client.ts @src/shared/types/generic.type.ts @src/features/products @src/shared/utils
src/shared/api/client.ts export apiClient (axios instance ที่ตั้ง baseURL ไว้แล้ว) และ class ApiError
baseURL ชี้ไปที่ https://dummyjson.com แล้ว ทุก path ในงานนี้จึงเขียนแบบสั้น เช่น /products
src/shared/types/generic.type.ts มี interface Pagination ที่มีสามฟิลด์ total, skip, limit
src/features/products/ และ src/shared/utils/ ยังเป็นโฟลเดอร์ว่างทั้งคู่
alias @/ ชี้ไปที่ src/ ตั้งค่าไว้แล้วทั้งใน vite.config.ts และ tsconfig.app.json
โปรเจกต์นี้ไม่ได้เปิด verbatimModuleSyntax ให้ใช้ import แบบธรรมดา ไม่ต้องใช้ import type

โครงสร้าง: สร้างไฟล์ตามนี้ ไม่มากไม่น้อยกว่านี้
- src/features/products/types.ts
- src/shared/utils/pagination.utils.ts
- src/features/products/api.ts

ข้อกำหนดทางเทคนิค:
- types.ts: import { Pagination } from "@/shared/types/generic.type";
  แล้ว export interface ตามลำดับนี้ ห้ามเพิ่มหรือลดฟิลด์
  ProductDimensions: width, height, depth ทั้งหมดเป็น number
  ProductReview: rating (number), comment, date, reviewerName, reviewerEmail (string ทั้งสี่)
  ProductMeta: createdAt, updatedAt, barcode, qrCode เป็น string ทั้งหมด
  Product เรียงฟิลด์ตามนี้เป๊ะ:
    id: number, title: string, description: string, category: string, price: number,
    discountPercentage?: number, rating: number, stock: number, tags: string[],
    brand: string, sku: string, weight: number, dimensions: ProductDimensions,
    warrantyInformation: string, shippingInformation: string, availabilityStatus: string,
    reviews: ProductReview[], returnPolicy: string, minimumOrderQuantity: number,
    meta: ProductMeta, images: string[], thumbnail: string
    ฟิลด์เดียวที่เป็น optional คือ discountPercentage นอกนั้นบังคับทั้งหมด
  Category: slug, name, url เป็น string ทั้งสาม
  FetchProductsResponse extends Pagination แล้วเพิ่ม products: Product[]
- pagination.utils.ts: export function สองตัว ไม่มี default export
  calculateOffset(page: number, limit: number): number คืน (page - 1) * limit
  calculateTotalPages(total: number, limit: number): number คืน Math.ceil(total / limit)
- api.ts: บรรทัด import สามบรรทัด ตามลำดับนี้
    import { apiClient } from "@/shared/api/client";
    import { Category, FetchProductsResponse, Product } from "@/features/products/types";
    import { calculateOffset } from "@/shared/utils/pagination.utils";
  export interface ProductListParams { page?: number; limit?: number }
  export interface CategoryProductsParams extends ProductListParams { category: string }
  ทุกฟังก์ชันเป็น async function ที่ประกาศ return type ชัดเจน และจบด้วย return data
  โดย destructure ผลจาก axios ด้วย const { data } = await apiClient.get<T>(...)
  getProducts({ page = 1, limit = 20 }: ProductListParams = {}): Promise<FetchProductsResponse>
    GET /products พร้อม params { skip: calculateOffset(page, limit), limit }
  getProductsByCategory({ category, page = 1, limit = 20 }: CategoryProductsParams): Promise<FetchProductsResponse>
    GET /products/category/${category} พร้อม params ชุดเดียวกับข้างบน
  getCategories(): Promise<Category[]>  GET /products/categories ไม่มี params
  getProduct(id: string | number): Promise<Product>  GET /products/${id} ไม่มี params
  ห้ามใส่ try/catch ห้าม log error และห้ามแปลง error เอง
  ห้ามให้ฟังก์ชันไหนรับพารามิเตอร์ชื่อ skip การแปลง page เป็น skip เกิดขึ้นในไฟล์นี้เท่านั้น

ขอบเขต:
- ห้ามติดตั้ง dependency ใหม่
- ห้ามแก้ src/shared/api/client.ts หรือ src/shared/types/generic.type.ts
- ห้ามสร้าง queries.ts, custom hook หรือ index.ts/ไฟล์ barrel ใด ๆ
- ห้ามสร้าง price.utils.ts หรือ util อื่นที่ไม่ได้สั่ง
- ยังไม่ต้องเอาฟังก์ชันเหล่านี้ไปใช้ในหน้าไหน

✅ ตรวจโค้ดที่ AI สร้าง

✅ ตรวจโค้ดที่ AI สร้าง — git status และ git diff ก่อน แล้วไล่ทีละข้อ ข้อแรกคือข้อที่ใช้เวลานานที่สุดและคุ้มที่สุด:

  • AI มักพลาดตรงนี้: แต่งฟิลด์ที่ dummyjson ไม่ได้ส่งมาจริง ตัวยอดฮิตคือ discountPrice, originalPrice, imageUrl, inStock หรือเปลี่ยน title เป็น name — ทุกตัวเป็นชื่อที่ "ฟังดูสมเหตุสมผลสำหรับเว็บขายของ" ซึ่งเป็นเหตุผลเดียวที่โมเดลเลือกมัน และไม่มีเครื่องมือตัวไหนในโปรเจกต์จับได้เลย: TypeScript เชื่อ type ที่เราประกาศ มันไม่เคยเห็น payload จริง npm run typecheck จึงผ่านฉลุย แล้วอาการจะไปโผล่ตอนบทเรียน 21 เป็นคำว่า undefined กลางหน้า Product วิธีจับมีทางเดียว: เปิด https://dummyjson.com/products?limit=5&skip=15 ในเบราว์เซอร์ แล้ววางคู่กับ types.ts ไล่ชื่อฟิลด์ทีละตัวด้วยตา ทั้ง Product, ProductDimensions, ProductMeta และ ProductReview (กาง reviews[0] ใน JSON ดู) ส่วน Category ให้เทียบกับ https://dummyjson.com/products/categories อีกแท็บ ฟิลด์ที่ไม่มีใน JSON = ฟิลด์ที่ต้องลบทิ้ง ฟิลด์ที่มีใน JSON แต่ไม่มีใน type = ความรู้ที่หายไป ให้เติมกลับ สังเกต skip=15 ให้ดี — เราจงใจไม่ดูสินค้าห้าชิ้นแรก เพราะสินค้าชิ้นต้น ๆ ของ dummyjson ครบฟิลด์เกินไปจนไม่เห็นของจริง (กล่อง 💡 ใต้ types.ts บอกว่ามันซ่อนอะไรไว้) การเลือก sample ให้กว้างพอคือส่วนหนึ่งของงานตรวจ ไม่ใช่รายละเอียดปลีกย่อย
  • ไฟล์ใหม่ 3 ไฟล์พอดี ไม่มี index.ts, queries.ts, price.utils.ts หรือ hook แถมมา และไม่มีไฟล์เดิมไฟล์ไหนขึ้นสถานะ modified
  • discountPercentage เป็นฟิลด์เดียวใน Product ที่มี ? ตรงตามที่ prompt สั่ง — ถ้า Agent โปรย ? ให้ฟิลด์อื่นทั่วไปหมด (โมเดลชอบทำเพื่อ "ความปลอดภัย") ให้เอาออก เพราะ type ที่ทุกอย่าง optional คือ type ที่ไม่ได้บอกอะไรเลย ยกเว้นข้อเดียว: ถ้ามันใส่ brand?: string มา อย่าเพิ่งลบ ให้ไปอ่านกล่อง 💡 ใต้โค้ดอ้างอิงของ types.ts ก่อนแล้วค่อยตัดสินใจ — นั่นเป็นฟิลด์ที่ payload จริงมีเรื่องจะบอก และเป็นข้อที่ Agent มีสิทธิ์ถูกกว่าต้นฉบับ
  • FetchProductsResponse เขียนว่า extends Pagination จริง ไม่ใช่พิมพ์ total, skip, limit ซ้ำลงไปเอง — และ Pagination ถูก import มาจาก @/shared/types/generic.type ไม่ใช่ประกาศใหม่ในไฟล์นี้
  • calculateTotalPages ใช้ Math.ceil ไม่ใช่ Math.round หรือ Math.floor — ข้อนี้ต่างกันแค่คำเดียวแต่ทำให้สินค้าหน้าสุดท้ายหายไปทั้งหน้า
  • ทั้งสี่ฟังก์ชันใน api.ts ไม่มี try/catch สักตัว — grep -n "catch" src/features/products/api.ts ต้องไม่เจออะไร (เหตุผลอยู่ใต้โค้ดอ้างอิง)
  • คำว่า skip โผล่ที่เดียวคือใน params ของ request ไม่ใช่ในหน้าตาของ ProductListParams — ถ้า Agent ทำ ProductListParams เป็น { skip?: number; limit?: number } แปลว่ามันยกภาษาของ server ขึ้นมาให้ UI ต้องพูดตาม ซึ่งผิดทิศทางที่เราออกแบบไว้
  • ทุก apiClient.get มี generic กำกับ (get<FetchProductsResponse>, get<Category[]>, get<Product>) — ถ้าขาด data จะเป็น any เงียบ ๆ แล้วทุกอย่างหลังจากนั้นก็ไร้ type ตามไปด้วย
  • getProduct รับ id: string | number ไม่ใช่ string อย่างเดียว หรือ number อย่างเดียว (เหตุผลอยู่ใต้โค้ดอ้างอิง และบทหน้าจะใช้มันเต็ม ๆ)
  • api.ts มีบรรทัด import สามคำสั่ง เรียงตามที่ prompt สั่ง — แต่คำสั่งกลาง (Category, FetchProductsResponse, Product) จะกลับมาเป็นห้าบรรทัดไม่ใช่บรรทัดเดียว เพราะเขียนติดกันแล้วยาว 85 ตัวอักษร เกิน 80 ที่ Prettier ตั้งไว้ มันจึงตัดขึ้นบรรทัดใหม่ให้เอง นี่คือฝีมือ Prettier ไม่ใช่ Agent ทำผิดคำสั่ง สิ่งที่ต้องตรงคือมีสามคำสั่งและเรียงตามลำดับนั้น ไม่ใช่จำนวนบรรทัด (บทหน้าจะเจอเรื่องเดียวกันอีกครั้งกับ array extends ใน eslint.config.js)
  • ไม่มี any และไม่มี as ที่ใช้กลบ type error ทั้งสามไฟล์ — ผิดกติกาในไฟล์ rules
  • ไม่มี comment แบบ // product interface หรือ JSDoc ที่เขียนซ้ำสิ่งที่ signature บอกอยู่แล้ว

เหมือนบทก่อน ๆ: npm run lint อาจตกเรื่อง import-x/order ก่อน แก้ด้วย npx eslint . --fix แล้วรันซ้ำให้ผ่านเงียบ ๆ จากนั้นค่อย npm run typecheck

มีจุดตัดสินใจที่น่าสนใจอยู่สองสามจุด:

  • discountPercentage?: number — ฟิลด์เดียวใน Product ที่เป็น optional เพราะเราไม่อยากให้ทั้งแอปตั้งอยู่บนสมมติฐานว่าสินค้าทุกชิ้นต้องมีส่วนลด การประกาศเป็น optional บังคับให้โค้ดฝั่ง UI ต้องรองรับกรณีไม่มีส่วนลดเสมอ — เดี๋ยวบทเรียน 18 ตอนเขียน price utils คุณจะเห็นว่า TypeScript ไล่บี้เราเรื่องนี้อย่างไร (เหตุผลนี้ฟังขึ้น แต่ข้อเท็จจริงที่มันตั้งอยู่ไม่ตรงกับ payload จริง — อ่านกล่อง 💡 ถัดจากรายการนี้)
  • ProductReview แยกออกมา — เพราะหน้า Product detail (บทเรียน 21) มีทั้ง ReviewSection และ ReviewCard ที่ต้องรับ review เป็น props การมี type ชื่อชัด ๆ ให้ import ดีกว่า Product["reviews"][number] เยอะ
  • Category เป็น object ไม่ใช่ string — GET /products/categories ของ dummyjson ตอบ array ของ object { slug, name, url }: slug เอาไว้ประกอบ URL (เช่น /products/category/beauty) ส่วน name คือชื่อสวย ๆ ไว้แสดงผล (เช่น "Beauty") ชื่อ Category นี้จะไปชนกับชื่อคอมโพเนนต์หน้า Category ในบทเรียน 20 ซึ่งแก้ด้วยการ import แบบ Category as CategoryType (หน้า Home ในบทเรียน 19 ไม่ได้ชนกับใคร แต่ใช้ alias เดียวกันเพื่อความสม่ำเสมอ) — ไม่ใช่ปัญหา แต่รู้ไว้ก่อนจะได้ไม่งง
  • FetchProductsResponse extends Pagination — รูปแบบคำตอบของ endpoint รายการสินค้า คือ products บวกสามฟิลด์ pagination ที่ทวนไปเมื่อครู่ การ extends ทำให้เราประกอบ type จากชิ้นส่วนที่มีอยู่แล้วโดยไม่ต้องพิมพ์ซ้ำ
💡 ของที่ควรถูกทักในรีวิว — และมันคือประเด็นทั้งหมดของบทนี้: ต้นฉบับประกาศ brand: string แบบบังคับ และ discountPercentage?: number แบบไม่บังคับ ซึ่งกลับกันกับความจริงของ dummyjson จากสินค้าทั้ง 194 ชิ้น discountPercentage มีครบทุกชิ้น ส่วน brand หายไป 92 ชิ้น — ทั้งหมวด groceries, home-decoration, kitchen-accessories, sports-accessories, tops, womens-dresses และ womens-jewellery ตั้งแต่ id 16 ขึ้นไป ลองเปิด https://dummyjson.com/products?limit=5&skip=15 ที่ checklist บอกให้เปิด แล้วค้นคำว่า brand ในหน้านั้นดู — ไม่เจอสักตัว การประกาศอย่างซื่อสัตย์จึงเป็น brand?: string และของที่ควรบังคับคือ discountPercentage เราสั่งตามต้นฉบับเพราะโค้ดอ้างอิงของคอร์สนี้คือแอปจริง แต่ผลของมันมีจริง: brand ถูก render ตรง ๆ ทั้งใน ProductsList (บทเรียน 18) และ ProductDetailInfo (บทเรียน 21) แปลว่าสินค้าเกือบครึ่งร้านจะมีช่องว่างเปล่าตรงนั้น โดยที่ TypeScript รับประกันกับคุณตลอดทางว่ามันเป็น string แน่นอน — นี่คืออาการ "type โกหก" ที่บทนี้ทั้งบทเตือนไว้ เกิดขึ้นบน type ของบทนี้เอง และไม่มี lint, typecheck หรือ npm run dev ตัวไหนบอกคุณได้ มีแต่การเปิด payload จริงที่กว้างพอ
💡 ในคอร์ส React พื้นฐาน เราเขียน import type เพราะโปรเจกต์นั้นเปิด verbatimModuleSyntax ไว้ แต่ template ของโปรเจกต์นี้ไม่ได้เปิด option นั้น import { Pagination } แบบธรรมดาจึงใช้ได้ — TypeScript รู้เองว่าเป็น type แล้วตัดทิ้งตอน build ให้ นี่เป็นอีกข้อที่ต้องบอก Agent ตรง ๆ ในบริบท ไม่งั้นมันจะเลือกท่าที่พบบ่อยกว่าให้

src/shared/utils/pagination.utils.ts:

export function calculateOffset(page: number, limit: number): number {
  return (page - 1) * limit;
}

export function calculateTotalPages(total: number, limit: number): number {
  return Math.ceil(total / limit);
}

สองฟังก์ชันที่รวมกันแล้วไม่ถึงสิบบรรทัด แต่มันคือเส้นแบ่งระหว่างภาษาของผู้ใช้กับภาษาของ server ทั้งเส้น — และเพราะมันเป็น pure function ล้วน คุณพิสูจน์ความถูกต้องของมันได้ในหัวโดยไม่ต้องเปิดเบราว์เซอร์

src/features/products/api.ts — ได้เวลาประกอบทุกอย่างเข้าด้วยกัน: client จากบทที่แล้ว + types + offset math กลายเป็นฟังก์ชันเรียก API หนึ่งตัวต่อหนึ่ง endpoint:

import { apiClient } from "@/shared/api/client";
import {
  Category,
  FetchProductsResponse,
  Product,
} from "@/features/products/types";
import { calculateOffset } from "@/shared/utils/pagination.utils";

export interface ProductListParams {
  page?: number;
  limit?: number;
}

export interface CategoryProductsParams extends ProductListParams {
  category: string;
}

export async function getProducts({
  page = 1,
  limit = 20,
}: ProductListParams = {}): Promise<FetchProductsResponse> {
  const { data } = await apiClient.get<FetchProductsResponse>("/products", {
    params: { skip: calculateOffset(page, limit), limit },
  });
  return data;
}

export async function getProductsByCategory({
  category,
  page = 1,
  limit = 20,
}: CategoryProductsParams): Promise<FetchProductsResponse> {
  const { data } = await apiClient.get<FetchProductsResponse>(
    `/products/category/${category}`,
    { params: { skip: calculateOffset(page, limit), limit } },
  );
  return data;
}

export async function getCategories(): Promise<Category[]> {
  const { data } = await apiClient.get<Category[]>("/products/categories");
  return data;
}

export async function getProduct(id: string | number): Promise<Product> {
  const { data } = await apiClient.get<Product>(`/products/${id}`);
  return data;
}

สี่ฟังก์ชัน ตรงกับสี่ endpoint ที่แนะนำไปในบทที่แล้วเป๊ะ ๆ มาดูรายละเอียดที่ซ่อนอยู่

💡 ของที่ควรถูกทักในรีวิว: บรรทัดที่สองของไฟล์ import types ด้วย @/features/products/types ทั้งที่ types.ts นั่งอยู่โฟลเดอร์เดียวกันกับ api.ts — กติกาในไฟล์ rules เขียนไว้ว่า "import ข้ามโฟลเดอร์ใช้ alias @/ เสมอ" ซึ่งแปลว่าไฟล์ในโฟลเดอร์เดียวกันควรใช้ ./types และคุณจะเห็นในบทหน้าว่า queries.ts ใช้ ./api จริง ๆ — สองไฟล์ในโฟลเดอร์เดียวกัน สองธรรมเนียม เราสั่งตามต้นฉบับเพราะโค้ดอ้างอิงของคอร์สนี้คือแอปจริง ไม่ใช่แอปในอุดมคติ แต่ถ้านี่เป็น pull request ในงานจริง นี่คือ comment ที่ควรเขียนทิ้งไว้ และสังเกตว่าไม่มีเครื่องมือตัวไหนจับได้ เพราะทั้งสองแบบ resolve ไปที่ไฟล์เดียวกัน

Params ที่คิดเป็น "หน้า" ตั้งแต่ต้นทาง

ProductListParams รับ page กับ limit — ภาษาที่ UI คิด — แล้วให้ calculateOffset แปลงเป็น skip ภาษาที่ dummyjson คิด ตอนส่ง request วิธีนี้ทำให้ความรู้เรื่อง skip/limit ถูกกักไว้ในไฟล์นี้ไฟล์เดียว หน้าเพจไม่ต้องรู้จักมันเลย ส่วน CategoryProductsParams ก็แค่ extends เพิ่ม category ที่จำเป็นเข้าไป

ตรง signature ของ getProducts มีท่า TypeScript ที่ควรอ่านให้ขาด: { page = 1, limit = 20 }: ProductListParams = {} ทำงานสองชั้น — = {} ด้านนอกทำให้เรียก getProducts() โดยไม่ส่งอะไรเลยก็ได้ ส่วน page = 1, limit = 20 ด้านในคือ default ของแต่ละฟิลด์ที่ผู้เรียกไม่ได้ระบุ ผลคือฟังก์ชันเดียวรองรับตั้งแต่ "ขอหน้าแรกแบบมาตรฐาน" ยัน "ขอหน้า 3 หน้าละ 12 ชิ้น" โดย type ปลอดภัยทุกทาง

Generic ที่ทำให้ทุกอย่าง typed

apiClient.get<FetchProductsResponse>(...) คือการใช้ generic ของ axios บอกว่า "response.data ของ request นี้มีหน้าตาแบบนี้นะ" จากนั้นเรา destructure const { data } = ... แล้ว return เฉพาะ data ออกไป — ผู้เรียกไม่ต้องรู้ด้วยซ้ำว่าเบื้องหลังเป็น axios ที่ห่อของไว้ใน response object ได้ของ typed สะอาด ๆ ไปใช้เลย และ return type ที่ประกาศไว้ (Promise<FetchProductsResponse>) ก็ทำหน้าที่เป็นสัญญาสองชั้น: ถ้าวันไหนเราแก้ไส้ในแล้วของที่ return ไม่ตรงสัญญา TypeScript ฟ้องทันที

ย้ำอีกครั้งว่า generic ตัวนี้คือคำประกาศ ไม่ใช่การตรวจสอบ — axios ไม่ได้ไปเทียบ payload จริงกับ type ให้ ถ้า types.ts โกหก generic ก็ส่งคำโกหกนั้นต่อไปทั้งแอปอย่างมั่นใจ นี่คือเหตุผลที่ข้อแรกของ checklist ต้องทำด้วยตาคน

ส่วน getProduct(id: string | number) ที่รับได้ทั้งสอง type ไม่ใช่ความหละหลวม แต่เป็นความจงใจ: id ที่มาจาก URL param จะเป็น string ("42") แต่ id ที่มาจาก object สินค้าจะเป็น number (42) — รับได้ทั้งคู่ที่นี่ แล้วเดี๋ยวบทหน้าเราจะเห็นวิธีทำให้สอง id นี้ชี้ cache ก้อนเดียวกัน

สังเกตไหมว่าไม่มี try/catch สักตัว

นี่คือดอกผลของบทที่แล้ว: ไฟล์นี้ไม่ต้องจัดการ error เลยแม้แต่บรรทัดเดียว เพราะ interceptor ใน client.ts ที่คุณพิมพ์เองเป็นเจ้าของเรื่อง error แต่เพียงผู้เดียว ถ้า request ล้มเหลว promise ของฟังก์ชันเหล่านี้จะ reject ออกไปเป็น ApiError โดยอัตโนมัติ

และที่จริง การใส่ try/catch ตรงนี้ไม่ใช่แค่ไม่จำเป็น แต่อันตราย: ถ้าเรา catch แล้วไม่ throw ต่อ error จะถูกกลืนหาย TanStack Query จะไม่มีวันรู้ว่า request พัง ไม่ตั้งค่า error state ให้ แล้ว UI ก็ค้างอยู่ในสถานะ loading ตลอดกาล ฟังก์ชันชั้นนี้จึงควร "บาง" ที่สุด: รับ params → ยิง request → คืนข้อมูล typed จบ ความบางนี้ยังทำให้ชั้น query ที่ครอบมันอยู่ถูกเทสต์ด้วย MSW ได้ง่ายมากในบทเรียน 32 เพราะไม่มี logic ซ่อนอยู่ให้ต้อง mock อะไรพิสดาร

สังเกตว่าข้อ "ห้าม try/catch" เป็นข้อที่ Agent ฝ่าฝืนบ่อยมากถ้าไม่สั่งห้ามไว้ในขอบเขต เพราะ "ฟังก์ชันเรียก API ที่ดี" ในโค้ดตัวอย่างทั่วโลกมักมี try/catch ครอบไว้เสมอ — มันไม่ผิดในโปรเจกต์ที่ไม่มี interceptor แต่ในโปรเจกต์นี้มันคือการทำงานซ้ำที่ทำลายของเดิม

  2. ลบ = {} ตัวนอกออกจาก signature ของ getProducts แล้วตอบว่าโค้ดแบบไหนที่เคยเรียกได้จะเรียกไม่ได้อีกต่อไป และ page = 1 ที่อยู่ข้างในยังทำงานอยู่ไหม
  3. ใส่ try/catch ที่ catch แล้ว return { products: [], total: 0, skip: 0, limit: 20 } ครอบ getProducts ดู — typecheck ผ่านสบาย ไล่ให้ได้ว่าผู้ใช้จะเห็นอะไรบนหน้าจอตอน server ล่ม และเทียบกับสิ่งที่เขาควรเห็น (เสร็จแล้วลบทิ้ง)
💡 Checkpoint: บทนี้ยังไม่มีอะไรใหม่ให้ดูในเบราว์เซอร์ — เราสร้างของสามชิ้นที่ยังไม่มีใครเรียกใช้ แต่ความถูกต้องของมันตรวจได้สองทาง: npm run lint กับ npm run typecheck ต้องผ่านทั้งคู่ และตาของคุณต้องผ่านการเทียบ types.ts กับ https://dummyjson.com/products?limit=5&skip=15 ทีละฟิลด์มาแล้วจริง ๆ (ไม่ใช่ห้าชิ้นแรก — เหตุผลอยู่ในกล่อง 💡 ใต้ types.ts) ถ้า TypeScript บ่น ให้อ่านชื่อไฟล์กับบรรทัดที่มันชี้ดี ๆ — จุดพลาดยอดนิยมคือสะกดชื่อฟิลด์ใน types.ts ไม่ตรงกับตอน import ไปใช้ใน api.ts เมื่อผ่านแล้ว commit ได้ ชั้นข้อมูลของเราเหลือชิ้นสุดท้ายชิ้นเดียว: ทำให้ TanStack Query รู้จักฟังก์ชันเหล่านี้อย่างเป็นระบบด้วย query factory ในบทถัดไป — ถ้าข้อ "อธิบายให้ได้" ยังตอบไม่ได้ อย่าเพิ่งไปบทถัดไป
