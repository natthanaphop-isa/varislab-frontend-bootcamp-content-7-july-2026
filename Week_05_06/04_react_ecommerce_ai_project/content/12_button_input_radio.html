Button, Input และ RadioInput

Button, Input & RadioInput

โครงแอปของเราพร้อมแล้ว — router พาไปแต่ละหน้าได้, MainLayout มี Header/Footer ครบ และ QueryClient รอให้เราเรียกใช้ ก่อนจะลงมือสร้างหน้าเพจจริง เราจะหยุดสามบทเพื่อสร้างคอมโพเนนต์กลาง (shared components) — ชิ้นส่วน UI ที่หลายหน้าหยิบไปใช้ซ้ำ เหมือนทีมจริงที่มักสร้าง design system เล็ก ๆ ก่อนประกอบหน้าเพจ

และบทนี้มีอีกเรื่องที่สำคัญกว่าตัวคอมโพเนนต์: มันคือบทที่คุณจะได้เห็นว่า ไฟล์ที่เขียนเสร็จแล้วหนึ่งไฟล์ คือบริบทที่แรงที่สุดที่คุณให้ Agent ได้ — แรงกว่าคำอธิบายยาว ๆ ในช่อง ข้อกำหนดทางเทคนิค: มาก เราจะพิมพ์ Button เองทั้งตัว แล้วสั่งให้ Agent สร้างอีกสองตัวโดยลอกรูปแบบจากไฟล์นั้น

ทำไมต้องมีคอมโพเนนต์กลาง

ทำไมไม่เขียน <button> สด ๆ ในแต่ละหน้าไปเลย? เพราะปุ่มของเราต้องหน้าตาเหมือนกันทุกหน้า มี loading state เหมือนกัน มี icon ได้เหมือนกัน — ถ้าเขียนซ้ำ 5 ที่ วันที่ดีไซน์เปลี่ยน คุณต้องไล่แก้ 5 ที่ แต่ถ้ามี Button กลางตัวเดียว แก้ที่เดียวจบ ในบทนี้เราจะสร้างสามตัวแรก และแต่ละตัวจะถูกใช้จริงในบทถัด ๆ ไป:

  • Button — ปุ่มหลักของทั้งแอป: Add to Cart ในหน้า Product (บทเรียน 21), ปุ่ม Checkout ในหน้า Cart (บทเรียน 24) และปุ่มยืนยันในฟอร์มชำระเงิน (บทเรียน 26 และ 27)
  • Input — ช่องกรอกข้อความ จะเป็นพระเอกของฟอร์มที่อยู่จัดส่งในบทเรียน 26 (คู่กับ react-hook-form)
  • RadioInput — ตัวเลือกแบบ radio สำหรับเลือกวิธีจัดส่งและวิธีชำระเงินในบทเรียน 27

ข้อควรรู้ก่อนเริ่ม: บทนี้ (และอีกสองบทถัดไป) สร้างเสร็จแล้วหน้าเว็บจะยังไม่เปลี่ยน เพราะยังไม่มีหน้าไหนเรียกใช้คอมโพเนนต์เหล่านี้ นี่เป็นเรื่องปกติของการทำงานแบบ bottom-up — เราสร้างเครื่องมือให้พร้อมก่อน แล้วบทสร้างหน้าเพจจะไหลลื่นมาก

ทางแยกสำคัญ: Vite 8 กับ CJS interop

Button ของเราจะมี loading state — ตอนกำลังส่งคำสั่งซื้อ ปุ่มจะเปลี่ยนเป็นวงกลมหมุน ๆ เราไม่ต้องเขียน animation เอง ใช้ไลบรารี react-spinners ที่มี spinner สำเร็จรูปให้เลือกหลายแบบ แต่ก่อนใช้มันได้ เราต้องแก้ config หนึ่งจุด และนี่คือบทเรียนของจริงที่คุณจะเจอในงาน: ไลบรารีบางตัวใน npm ยังเผยแพร่เป็น CommonJS (CJS) ซึ่งเป็นระบบ module รุ่นเก่าของ Node (แบบ require/module.exports) ในขณะที่โปรเจกต์เราเป็น ES Modules (ESM แบบ import/export) เต็มตัว — package.json ของเราประกาศ "type": "module" ไว้ตั้งแต่ scaffold ในบทเรียน 02

ปัญหาคือไลบรารี CJS ที่ compile มาจาก TypeScript/Babel จะเก็บของที่ export ไว้ที่ module.exports.default (ธรรมเนียมที่เรียกว่า esModuleInterop) — Vite รุ่นก่อน ๆ ใจดี แกะ .default ให้เราอัตโนมัติเวลาเขียน import ClipLoader from "react-spinners/ClipLoader" แต่ Vite 8 (ที่เปลี่ยนมาใช้ Rolldown เป็น bundler) เข้มงวดขึ้น: default import ของ CJS ในโปรเจกต์ ESM จะได้ก้อน module ทั้งก้อนแทนที่จะเป็นตัวคอมโพเนนต์ พอ React พยายาม render object แทนที่จะเป็น function ก็จะพังตอนรันด้วย error หน้าตาแบบนี้:

Uncaught Error: Element type is invalid: expected a string (for built-in components)
or a class/function (for composite components) but got: object.

ทางแก้คือเปิด option ที่ Vite เตรียมไว้ให้สำหรับกรณีนี้โดยเฉพาะ เปิด vite.config.ts แล้วเพิ่ม block legacy เข้าไป ไฟล์ทั้งไฟล์ตอนนี้จะเป็นแบบนี้ (เราเก็บ comment ภาษาอังกฤษไว้ด้วย — เดี๋ยวอธิบายว่าทำไม):

import { fileURLToPath, URL } from "node:url";
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

// https://vite.dev/config/
export default defineConfig({
  plugins: [react()],
  resolve: {
    alias: {
      "@": fileURLToPath(new URL("./src", import.meta.url)),
    },
  },
  // Vite 8 (Rolldown) tightened CJS default-import interop: since this project's
  // package.json has "type": "module", default imports of CJS deps that use the
  // TS/Babel esModuleInterop convention (module.exports.default, e.g.
  // react-spinners, react-paginate) now resolve to the whole module object
  // instead of unwrapping `.default`, breaking those components at runtime
  // ("Element type is invalid"). This restores the pre-Vite-8 unwrapping
  // behavior. See https://vite.dev/guide/migration (CJS interop changes).
  legacy: {
    inconsistentCjsInterop: true,
  },
});

legacy.inconsistentCjsInterop: true บอก Vite ว่า "ขอพฤติกรรมแกะ .default แบบเดิมกลับมา" ซึ่งทำให้ react-spinners (และ react-paginate ที่เราจะติดตั้งบทหน้า) กลับมา render ได้ตามปกติ

ส่วนเหตุผลที่เราเขียน comment ยาว ๆ กำกับไว้: config บรรทัดนี้อ่านแล้วไม่มีทางเดาได้เลยว่ามีไว้ทำไม ถ้าไม่มี comment อีกหกเดือนข้างหน้า (หรือเพื่อนร่วมทีม) อาจลบทิ้งเพราะคิดว่าไม่จำเป็น แล้วแอปจะพังแบบงง ๆ — การจดเหตุผลของ workaround ไว้ตรงที่มันอยู่คือนิสัยที่ทีมจริงคาดหวัง สังเกตว่ากติกาในไฟล์ rules ห้าม comment ที่อธิบายสิ่งที่โค้ดบอกอยู่แล้ว — comment ก้อนนี้ตรงข้าม มันอธิบายสิ่งที่โค้ดบอกไม่ได้

และเราแก้ไฟล์นี้เอง ไม่ส่งให้ Agent ด้วยเหตุผลเดียวกับที่เราติดตั้ง dependency เอง: การเปิด flag ของ bundler เป็นการตัดสินใจ ไม่ใช่การพิมพ์ ถ้าปล่อยให้ Agent เจอ error นี้เอง สิ่งที่มักได้กลับมาคือการเปลี่ยนบรรทัด import ไปเป็น import { ClipLoader } from "react-spinners" หรือแย่กว่านั้นคือเขียน spinner เองด้วย CSS — ทั้งสองทางทำให้ error หายจากจอโดยที่ต้นเหตุยังอยู่

💡 ไฟล์ vite.config.ts ยังไม่จบแค่นี้ — บทเรียน 30 (ติดตั้งชุดทดสอบ) เราจะกลับมาเพิ่มบรรทัด /// <reference types="vitest/config" /> ข้างบนสุดและ block test สำหรับ Vitest อีกครั้ง

รู้จัก SCSS Modules ก่อนเขียนคอมโพเนนต์แรก

ในบทเรียน 04 เราวางโครง SCSS ส่วนกลางไว้แล้ว (variables, utility classes อย่าง flex, py-15, fw-medium) — พวกนั้นเป็น global CSS คือประกาศครั้งเดียวใช้ได้ทุกที่ ซึ่งเหมาะกับ utility ที่ตั้งใจให้ใช้ร่วมกันทั้งแอป แต่พอเป็น style เฉพาะของคอมโพเนนต์ global CSS มีปัญหาคลาสสิก: class ชนกัน ลองนึกภาพ .button ของเรากับ .button ของอีกไฟล์ที่เพื่อนเขียน — ตัวที่โหลดทีหลังจะทับตัวแรกเงียบ ๆ โดยไม่มีใครเตือน

CSS Modules แก้ปัญหานี้ที่ราก: ตั้งชื่อไฟล์ลงท้ายด้วย .module.scss แล้ว Vite จะเปลี่ยนพฤติกรรมของไฟล์นั้นทันที — แทนที่ class จะไปอยู่ใน scope global ตัว build tool จะเปลี่ยนชื่อ class ให้ไม่ซ้ำใคร เช่น .button ใน Button.module.scss อาจกลายเป็น _button_x7f2k_3 ตอนรันจริง แล้วเราเข้าถึงชื่อที่ถูกแปลงแล้วผ่านการ import:

import styles from "./Button.module.scss";

// styles คือ object เช่น { button: "_button_x7f2k_3", primary: "_primary_x7f2k_11" }
<button className={styles.button}>

ผลคือ style ของแต่ละคอมโพเนนต์ถูก scope อยู่กับตัวเอง 100% — ต่อให้สิบไฟล์ตั้งชื่อ class ว่า .button เหมือนกันหมดก็ไม่มีทางชนกัน และจำได้ไหมว่าบทเรียน 04 เราสร้าง src/shared/types/global.d.ts ที่ประกาศ declare module "*.scss" ไว้ — นั่นแหละคือสิ่งที่ทำให้ TypeScript เข้าใจว่าการ import ไฟล์ .module.scss ได้ object กลับมา

สรุปกติกาที่เราจะใช้ทั้งโปรเจกต์: utility class ใช้แบบ global, style เฉพาะตัวใช้ CSS Modules — สองอย่างนี้อยู่ร่วมกันได้สบายมาก และคุณจะเห็นมันผสมกันในคอมโพเนนต์แรกของเราเดี๋ยวนี้เลย

ทำไมบทนี้ถึงพิมพ์ Button เอง

บทนี้สลับลำดับกับบทอื่น: กล่อง ✍️ มาก่อนกล่อง 🤖 ไม่ใช่ตามหลัง และการสลับนี้คือประเด็นทั้งหมดของบท

ลองคิดถึงงานสร้าง Input: คุณอยากได้ไฟล์ที่ประกาศ interface ของ props ไว้บนสุด, ประกาศตัวคอมโพเนนต์เป็น React.FC พร้อมค่า default ของ prop ที่ไม่บังคับ, ผสม class จาก module กับ utility class ใน template literal เดียว, และ export default ท้ายไฟล์ ถ้าจะบอกทั้งหมดนี้ด้วยคำพูดใน ข้อกำหนดทางเทคนิค: คุณต้องเขียนอีกสิบกว่าบรรทัด และยังเหลือช่องว่างให้ตีความอีกเยอะ (ลำดับบรรทัด import ล่ะ? วาง interface ก่อนหรือหลัง? ตั้งชื่อตัวแปร styles ว่าอะไร?)

แต่ถ้าในโปรเจกต์มีไฟล์ที่ทำทุกข้อนั้นอยู่แล้ว คุณเขียนแค่บรรทัดเดียว: ทำตามรูปแบบเดียวกับ @src/shared/components/Button/Button.tsx — Agent เปิดไฟล์นั้นอ่านแล้วลอกรูปทรงมาได้ทั้งชุด นี่คือความหมายจริง ๆ ของคำว่า "ให้บริบท": ตัวอย่างที่รันได้จริงหนึ่งไฟล์ มีข้อมูลหนาแน่นกว่าคำบรรยายทั้งย่อหน้า และมันจะไม่เพี้ยนตามการตีความ เพราะมันคือโค้ด ไม่ใช่ข้อความ

เมื่อรู้แบบนี้ คำถามจึงกลายเป็น "ไฟล์ไหนคุ้มที่สุดที่จะพิมพ์เอง" คำตอบคือไฟล์ที่จะถูกลอกมากที่สุด และในโปรเจกต์นี้คือ Button — คอมโพเนนต์ตัวแรกที่มี .module.scss คู่กัน อีกแปดตัวที่เหลือในสามบทนี้จะมีรูปทรงเดียวกับมันทั้งหมด ถ้าแม่แบบผิดตั้งแต่ตัวแรก ของที่ลอกตามก็ผิดทั้งชุด และคุณจะไม่มีมาตรฐานในหัวไว้เทียบเลย

ทำไม Button ถึงตัดออกจาก prompt ได้ แต่ router.tsx ในบทเรียน 09 ตัดไม่ได้

ย้อนกลับไปบทเรียน 09: เราอยากให้ router.tsx เป็นของเราเอง แต่กลับปล่อยให้ Agent สร้างมันมาก่อนแล้วค่อยพิมพ์ทับ เพราะถ้าสั่งว่า "สร้างทุกไฟล์ยกเว้น router.tsx" สิ่งที่พังไม่ใช่ router.tsx (มันไม่มีอยู่ ก็ไม่มีอะไรให้พัง) แต่คือ App.tsx ที่ต้อง import ./router — typecheck ไม่ผ่านตั้งแต่บรรทัดแรก และคุณจะเดินวงจรตรวจงานขั้นที่สามไม่ได้เลย

กฎที่ได้จากเรื่องนั้นคือ: สิ่งที่พังเมื่อคุณตัดไฟล์ X ออกจาก prompt คือไฟล์ที่ import X ไม่ใช่ตัว X เอง ดังนั้นก่อนตัดอะไรออก ให้ถามข้อเดียว — ในงานก้อนนี้ มีไฟล์ไหนที่ import ไฟล์นั้นบ้าง

บทนี้คำตอบคือไม่มี Input.tsx ไม่ import Button และ RadioInput.tsx ก็ไม่ import ทั้งสามตัวเป็นอิสระต่อกันสนิท ไฟล์แรกในโปรเจกต์ที่ import Button จริง ๆ คือ ProductDetailInfo ในบทเรียน 21 ซึ่งอยู่อีกเก้าบทข้างหน้า เมื่อไม่มีใครพึ่งพามัน เราจึงพลิกลำดับได้: พิมพ์ Button ให้เสร็จ commit แล้วค่อยส่ง prompt — และของที่พิมพ์เองก็กลายเป็นบริบทให้งานถัดไปพอดี

เป้าหมายของบทนี้

vite.config.ts                          # แก้เอง — เพิ่ม block legacy
src/
└── shared/
    └── components/
        ├── Button/
        │   ├── Button.module.scss       # ✍️ พิมพ์เอง
        │   └── Button.tsx               # ✍️ พิมพ์เอง
        ├── Input/
        │   ├── Input.module.scss        # 🤖 Agent สร้าง
        │   └── Input.tsx                # 🤖 Agent สร้าง
        └── RadioInput/
            └── RadioInput.tsx           # 🤖 Agent สร้าง — ไม่มีไฟล์ .module.scss

สัญญาที่แต่ละไฟล์ต้องทำให้ได้ — และสิ่งที่มันต้องไม่ทำ:

  • Button.tsx — ต้องประกาศ props ที่เปิดให้ใช้เองทีละตัว ต้องตั้งค่า default ของ type เป็น "button" และต้องส่งค่านั้นต่อไปที่แท็ก <button> จริง ๆ ต้องไม่ extend props ของ <button> ทั้งชุด
  • Input.tsx — ต้อง extend React.InputHTMLAttributes และเท props ที่เหลือทั้งหมดลงแท็ก <input> ด้วย spread ต้องส่ง ref ต่อไปถึงแท็ก <input> ผ่าน forwardRef ต้องไม่ประกาศ placeholder, value หรือ onChange เองใน interface
  • RadioInput.tsx — ต้องเป็น controlled ล้วน: checked และ onChange มาจากคนเรียกเท่านั้น ต้องไม่มี useState อยู่ในไฟล์ และต้องไม่มีไฟล์ .module.scss คู่กัน
  • vite.config.ts — ต้องมี legacy.inconsistentCjsInterop: true พร้อม comment อธิบายเหตุผล ต้องไม่มีการแตะ resolve.alias เดิม

src/shared/components/Button/Button.tsx:

import React from "react";
import { FontAwesomeIcon } from "@fortawesome/react-fontawesome";
import { IconProp } from "@fortawesome/fontawesome-svg-core";
import ClipLoader from "react-spinners/ClipLoader";
import styles from "./Button.module.scss";

interface ButtonProps {
  onClick?: () => void;
  icon?: IconProp; // Accepts FontAwesomeIcon props
  variant?: "primary";
  disabled?: boolean;
  isLoading?: boolean;
  children: React.ReactNode;
  type?: "button" | "reset" | "submit";
  className?: string;
}

const Button: React.FC<ButtonProps> = ({
  type = "button",
  onClick,
  icon,
  children,
  variant = "primary",
  disabled = false,
  isLoading = false,
  className = "",
}) => {
  return (
    <button
      type={type}
      className={`${styles.button} ${styles[variant]} ${className} flex flex-center py-15 px-20 fw-medium pointer`}
      onClick={() => {
        if (onClick) {
          onClick();
        }
      }}
      disabled={disabled}
    >
      {isLoading ? (
        <ClipLoader size={20} aria-label="Loading Spinner" color="white" />
      ) : (
        <>
          {icon && (
            <FontAwesomeIcon icon={icon} className={`${styles.icon} mr-10`} />
          )}
          {children}
        </>
      )}
    </button>
  );
};

export default Button;

เหตุผล: เป็นแม่แบบที่ AI จะลอกไปใช้กับทุก component หลังจากนี้ — อีกแปดตัวในสามบทนี้จะมีรูปทรงเดียวกับไฟล์นี้ และตั้งแต่บทเรียน 18 เป็นต้นไป component ของแต่ละฟีเจอร์ก็จะลอกตามอีกชั้น ถ้าคุณไม่เคยพิมพ์รูปทรงนี้เองสักครั้ง คุณจะไม่มีอะไรในหัวไว้เทียบตอนที่ของที่ Agent ส่งกลับมา "หน้าตาคล้าย ๆ" แต่ผิดจุดสำคัญไปหนึ่งจุด

ไล่ดูการตัดสินใจสำคัญทีละจุด — ทุกข้อนี้คือสิ่งที่ Agent จะลอกไปใช้ต่อ:

  • ไฟล์ module ยัง @use ตัวแปรกลางได้ตามปกติ — สังเกตว่า Button.module.scss ดึงตัวแปรจากบทเรียน 04 มาใช้ได้เหมือนไฟล์ SCSS ธรรมดา เพราะสิ่งที่ถูก scope คือชื่อ class ไม่ใช่ตัวแปร ส่วน &.primary คือ selector ที่จับตอน element มีทั้งสอง class พร้อมกัน (เราประกอบมันใน JSX ด้วย ${styles.button} ${styles[variant]}) และ &:hover:not(:disabled) กันไม่ให้ปุ่มที่ถูก disable เปลี่ยนสีตอน hover ให้ผู้ใช้เข้าใจผิดว่ากดได้
  • ButtonProps เลือก props เอง ไม่รับหมด — เราประกาศ interface ที่คัดเฉพาะ props ที่อยากเปิดให้ใช้: onClick, type, disabled, className บวกของที่เราเพิ่มเอง (icon, variant, isLoading) วิธีนี้ทำให้ API ของปุ่มแคบและควบคุมได้ — ใครจะใช้ปุ่มเราต้องใช้ตามกติกา สังเกตว่า type เรา default เป็น "button" เพราะค่า default จริงของ HTML คือ "submit" ซึ่งเป็นต้นเหตุ bug คลาสสิก "กดปุ่มแล้วฟอร์ม submit เอง" (เดี๋ยวส่วน Input จะเห็นแนวทางตรงข้าม: รับ props native ทั้งหมด — สองแนวทางนี้ใช้คู่กันได้ตามสถานการณ์)
  • type={type} บนแท็ก <button> — สองบรรทัดนี้ (type = "button" ตอน destructure และ type={type} ตอน render) ต้องมาคู่กันเสมอ ขาดตัวแรกปุ่มทุกตัวที่อยู่ในฟอร์มจะ submit ฟอร์มเอง ขาดตัวหลัง <Button type="submit"> ที่ฟอร์มบทเรียน 26 ส่งมาจะไม่มีผลอะไรเลย กดแล้วฟอร์มไม่ส่ง
  • styles[variant] — lookup แบบ dynamic: ถ้า variant คือ "primary" ก็หยิบ styles.primary ตอนนี้เรามี variant เดียว แต่โครงนี้พร้อมรองรับ "secondary" ในอนาคตโดยแก้แค่ type กับ SCSS
  • ผสม class สามชั้น — ใน template literal เดียวมีทั้ง class จาก module (styles.button), class ที่คนเรียกส่งเพิ่มมา (className) และ utility กลางจากบทเรียน 04 (flex flex-center py-15 px-20 fw-medium pointer) — นี่คือภาพจริงของกติกา "module สำหรับของเฉพาะตัว, utility สำหรับของทั่วไป"
  • isLoading สลับเนื้อในปุ่ม — ตอนโหลด เนื้อหาปกติ (icon + ข้อความ) หายไป เหลือ ClipLoader จาก react-spinners หมุนแทน พร้อม aria-label ให้ screen reader รู้ว่ากำลังโหลด
  • icon?: IconProp — รับ icon ของ Font Awesome (ที่ติดตั้งไว้บทเรียน 10) แบบ optional โดยใช้ type IconProp ของไลบรารีเอง คนเรียกส่ง icon={faCartShopping} มาได้เลยแล้ว TypeScript ตรวจให้ว่าเป็น icon จริง
  • จุดที่ต้นฉบับไม่สม่ำเสมอ — บรรทัด color: #fff; ใน .primary เป็นค่า hex ทั้งที่ _variables.scss มี $white อยู่แล้ว (Footer ในบทเรียน 10 ใช้ variables.$white) เราพิมพ์ตามต้นฉบับ แต่ให้สังเกตไว้ว่านี่คือของที่ควรถูกทักในรีวิว — และเป็นตัวอย่างว่าทำไม checklist ถึงต้องดูด้วยตา ไม่ใช่ดูแค่ว่า lint ผ่านไหม

✅ ตรวจโค้ดที่ AI สร้าง — git status และ git diff ก่อน แล้วไล่ทีละข้อ:

  • AI มักพลาดตรงนี้: prop ที่คนเรียกส่งมาแล้วไม่ถูกส่งต่อไปถึง element จริง — ใน Input.tsx อาการคือหาย {...props} บนแท็ก <input> (มักมาพร้อมกับการประกาศ placeholder, type, value, onChange เองทีละตัวใน interface ซึ่งดูขยันแต่ผิดโจทย์) ผลคือ <Input placeholder="อีเมล" /> ในบทเรียน 26 จะได้ช่องเปล่าที่ไม่มี placeholder ไม่มีค่า และพิมพ์แล้วไม่มีอะไรเกิดขึ้น โดยที่ lint และ typecheck ผ่านทั้งคู่ ญาติสนิทของอาการนี้อยู่ในไฟล์ที่คุณเพิ่งพิมพ์เอง: ถ้า type={type} หลุดจากแท็ก <button> ปุ่มจะกลับไปใช้ค่า default ของ HTML คือ submit แล้วปุ่มทุกตัวที่นั่งอยู่ในฟอร์มจะ submit ฟอร์มนั้นทันทีที่ถูกกด — เปิดสองไฟล์นี้ดูจุดนั้นเป็นจุดแรกเสมอ
  • ไฟล์ใหม่ 3 ไฟล์พอดี ไม่มี RadioInput.module.scss ไม่มี index.ts และไม่มีไฟล์ในโฟลเดอร์ Button/ ขึ้นสถานะ modified
  • InputProps เขียนว่า extends React.InputHTMLAttributes<HTMLInputElement> จริง ไม่ใช่ประกาศ prop ของ input ซ้ำเอง
  • ref ถูกส่งไปที่แท็ก <input> ไม่ใช่ที่ <div> ข้างนอก — ถ้าส่งผิดที่ typecheck ผ่าน แต่ react-hook-form ในบทเรียน 26 จะอ่านค่าจากช่องไม่ได้
  • มีบรรทัด Input.displayName = "Input"; อยู่ — ไม่มีเครื่องมือตัวไหนในโปรเจกต์นี้บังคับข้อนี้ (ESLint ที่ตั้งไว้บทเรียน 03 ไม่มีกฎ react/display-name) ถ้าขาดไปก็ไม่มีใครบ่น แค่ React DevTools จะแสดงชื่อคอมโพเนนต์เป็น ForwardRef — เป็นข้อที่ต้องดูด้วยตาล้วน ๆ
  • RadioInput ไม่มี useState, ไม่มี defaultChecked และไม่มี onChange ที่ไปแก้ค่าอะไรภายในตัวเอง — controlled แปลว่า state อยู่ที่คนเรียกทั้งหมด
  • type ของ prop label ใน RadioInput เป็น React.ReactNode ไม่ใช่ string — บทเรียน 27 ต้องยัด JSX ทั้งก้อนเข้าไปตรงนี้
  • id ที่ส่งให้ <input> กับ htmlFor ของ <label> ใน RadioInput เป็นค่าเดียวกัน
  • ข้อยกเว้นที่ให้ผ่านได้: ถ้า Input.tsx ที่ได้มามี <label htmlFor={props.id}> ขึ้นมาเอง อย่าลบทิ้ง — โค้ดอ้างอิงข้างล่างไม่มีบรรทัดนั้น (ต้นฉบับผูก label กับช่องกรอกไว้ไม่ครบ) แต่การผูกมันเข้าด้วยกันคือสิ่งเดียวกับที่ RadioInput ทำถูกอยู่แล้ว และเป็นข้อได้เปรียบจริงสำหรับผู้ใช้: กดที่ข้อความแล้วเคอร์เซอร์เข้าช่อง กรณีนี้คือของที่ Agent ทำดีกว่าต้นฉบับ ซึ่งเกิดขึ้นได้และควรเก็บไว้ — สิ่งที่ต้องระวังคือของที่มันทำต่างจากคำสั่งโดยไม่มีเหตุผล ไม่ใช่ของที่มันทำดีกว่า
  • Input.module.scss ขึ้นต้นด้วย @use "../../../styles/variables"; และใช้ตัวแปรทุกจุดที่เป็นสี — ไม่มี hex โผล่มาสักค่า
  • ค้นทุกชื่อ class ที่โผล่ใน className ของสองไฟล์ใหม่ว่ามีอยู่จริงใน src/styles/ ครบไหม (grep -rn "ชื่อ-class" src/styles/) — โดยเฉพาะ mt-3 ที่หน้าตาเหมือนพิมพ์ผิดแต่มีจริง (ตัวสร้าง spacing ในบทเรียน 04 มีค่า 3 อยู่ในลิสต์)
  • ไม่มี comment แบบ {/* Label */} หรือ // error message คั่นในไฟล์ — ผิดกติกาข้อสุดท้ายในไฟล์ rules
  • import ในไฟล์ .tsx ไม่มี ../../ โผล่มาแม้แต่บรรทัดเดียว

เหมือนสองบทที่แล้ว: npm run lint อาจตกเรื่อง import-x/order ก่อน แก้ด้วย npx eslint . --fix แล้วรันซ้ำให้ผ่านเงียบ ๆ จากนั้นค่อย npm run typecheck

src/shared/components/Input/Input.tsx:

import React, { forwardRef } from "react";
import styles from "./Input.module.scss";

interface InputProps extends React.InputHTMLAttributes<HTMLInputElement> {
  label?: string;
  error?: string;
}

const Input = forwardRef<HTMLInputElement, InputProps>(
  ({ label, error, ...props }, ref) => {
    return (
      <div className={styles.inputWrapper}>
        {label && <label className="mb-5 inline-block">{label}</label>}
        <input ref={ref} className={styles.input} {...props} />
        {error && <p className={`${styles.error} fs-12 mt-5`}>{error}</p>}
      </div>
    );
  },
);

Input.displayName = "Input";

export default Input;

ไฟล์นี้สั้นแต่อัดแน่นด้วยแพตเทิร์นสำคัญสองเรื่อง:

เรื่องแรก: extend props ของ input จริง — ต่างจาก Button ที่คัด props เอง InputProps ประกาศ extends React.InputHTMLAttributes<HTMLInputElement> แปลว่า Input ของเรารับ prop ทุกตัวที่ <input> ธรรมดารับได้ (placeholder, type, name, value, onChange, autoComplete, …) โดยไม่ต้องประกาศเองสักตัว แล้วเราเติมของเราเพิ่มสองตัว: label (ข้อความกำกับช่อง) กับ error (ข้อความ validation สีแดงใต้ช่อง) ตอน destructure เราดึง label กับ error ออกมาใช้เอง ส่วนที่เหลือ (...props) เททั้งก้อนลง <input> ผ่าน spread — ทำไมช่องกรอกถึงเหมาะกับแนวทางนี้? เพราะ input มี attribute ที่จำเป็นเยอะมากและเดาล่วงหน้าไม่ได้หมด การ extend จึงประหยัดกว่าและไม่ต้องกลับมาแก้ interface ทุกครั้งที่ฟอร์มต้องการ attribute ใหม่

เรื่องที่สอง: forwardRef — โดยปกติ function component รับ ref ตรง ๆ ไม่ได้ ใครพยายามส่ง ref มาจะเข้าไม่ถึง DOM ข้างใน forwardRef คือวิธีบอก React ว่า "ref ที่ส่งมาให้ฉัน ช่วยส่งต่อไปที่ <input> จริง ๆ ข้างในด้วย" แล้วทำไมต้องมี? เฉลยล่วงหน้า: บทเรียน 26 เราจะใช้ react-hook-form ซึ่งทำงานกับฟอร์มผ่านการเกาะ ref ของ input จริงในหน้าเว็บ (จำแนวคิด uncontrolled form จากคอร์ส React พื้นฐาน ได้ไหม? react-hook-form คือ uncontrolled แบบจัดเต็ม) ถ้า Input ของเราไม่ forward ref ให้ react-hook-form จะอ่านค่าจากช่องไม่ได้เลย ส่วน Input.displayName = "Input" ช่วยให้ React DevTools แสดงชื่อคอมโพเนนต์สวย ๆ แทนที่จะเป็น ForwardRef เฉย ๆ

💡 React 19 อนุญาตให้ส่ง ref เป็น prop ธรรมดาได้แล้ว แต่ forwardRef ยังใช้ได้ปกติและยังเป็นแพตเทิร์นที่คุณจะเจอบ่อยในโค้ดจริงตอนนี้ — อ่านท่านี้ให้ขาด แล้วคุณจะอ่าน codebase ของบริษัทไหนก็รู้เรื่อง และนี่เป็นอีกจุดที่ไฟล์ตัวอย่างชนะคำอธิบาย: ถ้าคุณไม่ระบุ Agent มีสิทธิ์เลือกท่า React 19 ให้ ซึ่งไม่ตรงกับโค้ดที่เหลือของโปรเจกต์

src/shared/components/RadioInput/RadioInput.tsx — สังเกตว่าคอมโพเนนต์นี้ไม่มีไฟล์ .module.scss เพราะหน้าตาของมันจัดได้ครบด้วย utility class ล้วน ๆ ไม่มี style เฉพาะตัวเลย ก็ไม่ต้องสร้างไฟล์เปล่าให้รก:

import React from "react";

interface RadioInputProps {
  id: string;
  name: string;
  checked: boolean;
  onChange: () => void;
  label: React.ReactNode;
  className?: string;
}

const RadioInput: React.FC<RadioInputProps> = ({
  id,
  name,
  checked,
  onChange,
  label,
  className = "",
}) => {
  return (
    <div className={`flex align-item-start ${className}`}>
      <input
        className="mr-10 mt-3"
        type="radio"
        id={id}
        name={name}
        checked={checked}
        onChange={onChange}
      />
      <label htmlFor={id}>{label}</label>
    </div>
  );
};

export default RadioInput;

จุดที่น่าสนใจ:

  • controlled radio เต็มรูปแบบ — เหมือน radio ในบท Hooks ของคอร์ส React พื้นฐาน เป๊ะ: ตัวคอมโพเนนต์ไม่เก็บ state เอง คนเรียกส่ง checked มาบอกว่าติ๊กอยู่ไหม และส่ง onChange มารับเหตุการณ์ตอนผู้ใช้เลือก — state จริงอยู่ที่หน้า Checkout ที่เป็นเจ้าของข้อมูล
  • label: React.ReactNode — ไม่ใช่ string! แปลว่า label ยัด JSX ได้ทั้งก้อน บทเรียน 27 เราจะใช้ประโยชน์เต็ม ๆ: ตัวเลือกวิธีจัดส่งมี label เป็นชื่อ + คำอธิบาย ที่คั่นด้วยขีดตั้ง ส่วนตัวเลือกวิธีจ่ายเงินเป็นชื่อตัวหนาขึ้นบรรทัดใหม่แล้วตามด้วยคำอธิบายสีจาง — สอง markup คนละทรงในก้อนเดียว
  • id + htmlFor — ผูก label กับ input เข้าด้วยกัน ผู้ใช้กดที่ข้อความ (ซึ่งพื้นที่ใหญ่กว่าวงกลมเยอะ) แล้ว radio ติ๊กให้ ส่วน name ทำให้ radio หลายตัวรู้ว่าอยู่กลุ่มเดียวกัน — เลือกได้ทีละตัว

มองย้อนกลับไป สามคอมโพเนนต์ = สามแนวทางออกแบบ props ที่ต่างกัน: Button คัด props เองเพื่อคุม API, Input extend props ของ native element เพื่อความยืดหยุ่น, RadioInput ประกาศ contract แบบ controlled ล้วน ทั้งสามท่าถูกหมด — ศิลปะอยู่ที่เลือกท่าให้เข้ากับงาน และสังเกตว่า Agent ลอกรูปทรงของไฟล์มาจาก Button ได้ แต่ท่าเลือก props เป็นสิ่งที่คุณต้องสั่ง เพราะมันคือการตัดสินใจเชิงออกแบบ ไม่ใช่ธรรมเนียมการจัดหน้าไฟล์
