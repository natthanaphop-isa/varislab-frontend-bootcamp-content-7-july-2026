บทเรียน 20 · สร้างหน้าเพจ (Pages)

หน้า Category: เลือกดูสินค้าพร้อมระบบแบ่งหน้า

Category Page

หน้า Home โชว์สินค้าได้แค่หมวดละ 12 ตัว ถ้าผู้ใช้อยากไล่ดูสินค้าทั้งหมวดจริง ๆ ต้องมีหน้าที่ทำเรื่องนี้เต็มตัว — นั่นคือหน้า Category ที่เราจะสร้างในบทนี้: เมนูหมวดหมู่ด้านซ้าย รายการสินค้าด้านขวา และแถบ Pagination ด้านล่างสำหรับกดเปลี่ยนหน้า

ข่าวดีคือของหนัก ๆ ถูกสร้างไว้หมดแล้ว: CategoryMenu กับ ProductsList มาจากบทเรียน 18, Pagination มาจากบทเรียน 13, calculateTotalPages มาจากบทเรียน 16 และ query byCategory พร้อม placeholderData: keepPreviousData ตั้งรอไว้ตั้งแต่บทเรียน 17 บทนี้จึงเป็นบทประกอบร่างที่ค่อนข้างสั้น prompt กลับมาเป็นรอบเดียวเหมือนเดิม — แต่มีแนวคิดสำคัญสามเรื่องซ่อนอยู่: derived state (อีกครั้ง — คราวนี้กับ pagination), ประสบการณ์เปลี่ยนหน้าที่ไม่กะพริบ และคำถามว่าเลขหน้าควรอยู่ที่ไหน ซึ่งเป็นคำถามที่ต้นฉบับตอบไว้แบบหนึ่ง และเราจะรีวิวคำตอบนั้นกันตรง ๆ

CategoryBanner: แถบหัวเรื่องของหน้า

เริ่มจากชิ้นเล็กก่อน: แถบสีเทาด้านบนสุดที่แสดงชื่อหมวดหมู่ตัวใหญ่กลางจอ เรียบง่ายมาก — รับ name ที่เป็น optional และเป็น null ได้ (รองรับจังหวะที่หมวดหมู่ยังโหลดไม่เสร็จ) ถ้าไม่มีชื่อก็ fallback เป็นคำว่า "Category" ไปก่อน จะได้ไม่มีแถบว่างเปล่าโผล่มา

💡 ถึงไฟล์นี้จะอยู่ใต้โฟลเดอร์ของหน้า Category แต่มันจะถูก reuse อีกสามครั้ง: หน้า Product detail ในบทถัดไปใช้มันแสดงชื่อสินค้า ส่วนหน้า Cart (บทเรียน 24) กับหน้า Checkout (บทเรียน 28) ใช้มันเป็นแถบหัวเรื่องโดยส่งข้อความคงที่เข้าไป — พอเป็นแค่ "แถบเทา ๆ กับตัวหนังสือหนึ่งบรรทัด" มันเลยกลางพอที่ใครจะหยิบไปใช้ก็ได้ นี่เป็นเหตุผลที่ prompt ของบทนี้ต้องระบุตำแหน่งไฟล์ให้ชัด: อีกสามบทข้างหน้าจะ import มันด้วย path เต็ม @/pages/Category/components/CategoryBanner/CategoryBanner ถ้าวันนี้วางผิดที่ อีกสามบทต้องตามแก้

หมวดปัจจุบัน: derived ไม่ใช่ synced

สองบรรทัดนี้หน้าตาเหมือนที่เพิ่งเขียนในหน้า Home เป๊ะ:

const { data: categories } = useQuery(productQueries.categories());
const currentCategory = selectedCategory ?? categories?.[0] ?? null;

และนั่นไม่ใช่เรื่องบังเอิญ — มันคือคำตอบมาตรฐานของโจทย์ "ค่าเริ่มต้นมาจากข้อมูลที่โหลดทีหลัง": เก็บใน state เฉพาะสิ่งที่ผู้ใช้เลือกเอง แล้วคำนวณค่าที่ใช้จริงระหว่าง render ทวนอีกครั้งจากบทเรียน Effects ของคอร์ส React พื้นฐาน ว่าทำไมเราไม่เขียน useEffect ให้ setSelectedCategory(categories[0]) ตอนข้อมูลมาถึง: (1) ได้ render ที่เสียเปล่าเพิ่มหนึ่งรอบ (2) มี state สอง copy ที่ต้องเฝ้าให้ตรงกัน — ถ้ารายชื่อหมวดใน cache ถูก refresh แล้วหมวดแรกเปลี่ยน state เก่าที่ sync ค้างไว้ก็จะผิดทันที (3) โค้ด effect + เงื่อนไขกันการ set ซ้ำอ่านยากกว่า ?? บรรทัดเดียวหลายเท่า และข้อดีแถม: query categories() ตัวนี้ยิงจาก cache — ถ้าคุณเพิ่งมาจากหน้า Home ข้อมูลหมวดถูกโหลดไว้แล้วด้วย staleTime 5 นาที เมนูจึงโผล่ทันทีไม่ต้องรอ

Query แบบมีเลขหน้า และ totalPages ที่คำนวณสด

ความต่างจากหน้า Home อยู่ที่ query สินค้า: คราวนี้เราส่ง page เข้าไปด้วย และ limit ขยับเป็น 20 ตัวต่อหน้า:

const [page, setPage] = useState(1);

const { data, isLoading, isError } = useQuery({
  ...productQueries.byCategory({
    category: currentCategory?.slug ?? "",
    page,
    limit: PAGE_LIMIT,
  }),
  enabled: currentCategory !== null,
});

const totalPages = data ? calculateTotalPages(data.total, PAGE_LIMIT) : 0;

จำกลไกจากบทเรียน 16–17 ได้ไหม: page กับ limit เป็นส่วนหนึ่งของ params ที่ฝังอยู่ใน queryKey ดังนั้นการ setPage(2) ทำให้ queryKey เปลี่ยน TanStack Query มองเป็นคนละ query แล้วไปดึงข้อมูลหน้า 2 มาให้เอง (ฝั่ง API ตัว getProductsByCategory แปลง page เป็น skip ด้วย calculateOffset ให้แล้ว) — ไม่มี effect ไม่มีการเรียก refetch ด้วยมือ state เปลี่ยนแล้วข้อมูลไหลตาม

ส่วน totalPages เป็น derived state อีกตัวของหน้านี้: dummyjson ตอบจำนวนสินค้าทั้งหมดมาใน data.total เราหารด้วย PAGE_LIMIT ปัดขึ้นด้วย calculateTotalPages เสร็จในหนึ่ง expression สังเกตว่าเราไม่เอาค่านี้ไปเก็บใน useState — มันคำนวณจาก data ได้เสมอ การ mirror ค่าที่คำนวณได้ลง state คือการสร้างสำเนาที่รอวัน desync แบบเดียวกับเคส currentCategory ข้างบน กฎง่าย ๆ ที่ใช้ได้ตลอด: ถ้าเขียนเป็น const จาก state/data ที่มีอยู่ได้ ก็อย่าเอาไปใส่ useState

เปลี่ยนหมวดแล้วต้องกลับหน้า 1

const onCategoryClick = (category: CategoryType) => {
  setSelectedCategory(category);
  setPage(1);
};

ตรงนี้คือเหตุผลที่หน้า Category ไม่ส่ง setSelectedCategory ให้เมนูตรง ๆ แบบหน้า Home: การเปลี่ยนหมวดต้องทำสองอย่าง คิดภาพผู้ใช้ที่ไล่ดู kitchen accessories อยู่หน้า 2 แล้วสลับไป beauty — ถ้าไม่รีเซ็ต ผู้ใช้จะไปโผล่ "หน้า 2 ของ beauty" ซึ่งไม่มีอยู่จริง (beauty มีสินค้า 5 ชิ้น จบในหน้าเดียว) ผลคือหน้าว่างเปล่า นี่คือ bug คลาสสิกของหน้า list ที่มีทั้ง filter และ pagination — เจอได้ในเว็บจริงบ่อยกว่าที่คิด และเป็นข้อที่ Agent จะทำหล่นบ่อยมากในบทนี้ ด้วยเหตุผลที่ฟังขึ้นมาก: มันเพิ่งเขียนหน้า Home ที่ส่ง setSelectedCategory ตรง ๆ ไปเมื่อบทที่แล้ว

keepPreviousData: ทำไมเปลี่ยนหน้าแล้วไม่กะพริบ

ลองสังเกตพฤติกรรมตอนกดปุ่ม Next: รายการสินค้าหน้าเดิมยังแสดงค้างอยู่ครู่หนึ่ง แล้วสินค้าหน้าใหม่ค่อยสลับเข้ามาแทน — ไม่มี spinner คั่นกลาง ไม่มีจอขาววูบ ทำไม? ทั้งที่โค้ดเราก็มี isLoading ? <ClipLoader /> : … อยู่ตรงนั้น

คำตอบอยู่ในบรรทัดเดียวที่เราสั่งไว้ใน queries.ts ตั้งแต่บทเรียน 17:

byCategory: (params: CategoryProductsParams) =>
  queryOptions({
    queryKey: productKeys.byCategory(params),
    queryFn: () => getProductsByCategory(params),
    placeholderData: keepPreviousData,
  }),

keepPreviousData บอก TanStack Query ว่า: เวลา queryKey เปลี่ยน (เปลี่ยนหน้า หรือเปลี่ยนหมวด) ระหว่างรอข้อมูลชุดใหม่ ให้เอาข้อมูลของ key เก่ามาใส่ใน data เป็น placeholder ไปพลาง ๆ ผลที่ตามมาสำคัญมาก: isLoading จะเป็น true เฉพาะครั้งแรกสุดที่ยังไม่มีข้อมูลอะไรเลย — การเปลี่ยนหน้าครั้งถัด ๆ ไปมี placeholder ให้แสดง จึงไม่นับเป็น loading สาขา ClipLoader ของเราเลยทำงานแค่ตอนเปิดหน้าครั้งแรกครั้งเดียว หลังจากนั้นผู้ใช้เห็นเนื้อหาเดิมจนกว่าเนื้อหาใหม่จะพร้อม

เทียบสอง timeline ให้เห็นภาพ — แบบไม่มี keepPreviousData: เนื้อหาหน้า 1 → จอกลายเป็น spinner ทั้งคอลัมน์ layout ยุบ → เนื้อหาหน้า 2 กับแบบที่เราได้: เนื้อหาหน้า 1 → เนื้อหาหน้า 1 (ค้างไว้) → เนื้อหาหน้า 2 อย่างหลังให้ความรู้สึก "เร็ว" กว่าอย่างชัดเจนทั้งที่ network ใช้เวลาเท่ากันเป๊ะ เพราะสิ่งที่ทำร้ายความรู้สึกผู้ใช้ไม่ใช่การรอ แต่คือการเห็นของที่มีอยู่แล้วหายไป และโบนัสอีกชั้น: ถ้ากดกลับมาหน้าที่เคยดูแล้ว ข้อมูลหน้านั้นอยู่ใน cache อยู่แล้ว — โผล่ทันทีไม่ต้องรออะไรเลย

นี่คือจุดที่คำเตือนจากบทเรียน 17 มาเก็บเกี่ยวผล: บรรทัด placeholderData: keepPreviousData เป็นบรรทัดที่หายไปได้แบบเงียบสนิท ตอนบทที่ 17 ไม่มีอะไรให้ดูเลย เพราะยังไม่มีหน้าไหนเปลี่ยนหน้าได้ วันนี้คือวันที่อาการปรากฏ และมันปรากฏบนหน้าจอเท่านั้น — npm run lint ผ่าน npm run typecheck ผ่าน ไม่มีเครื่องมือตัวไหนบอกคุณได้ ให้แยกสองกรณีนี้ออกจากกันให้ขาด: ถ้ามีคนเขียน keepPreviousData: true (ไวยากรณ์ v4) ลงไปแทน typecheck จะฟ้อง ทันทีด้วย TS2769 เพราะ queryOptions ตรวจ excess property ให้ครบทุก overload — อาการนั้นดังและแก้ง่าย ส่วนกริดที่กะพริบทุกครั้งที่กดเปลี่ยนหน้า แปลว่าบรรทัดนั้นไม่มีอยู่เลย ไม่ใช่เขียนผิด กลับไปเปิด queries.ts จาน byCategory แล้วนับบรรทัดดู

เลขหน้าอยู่ใน state ไม่ได้อยู่ใน URL

อีกเรื่องที่ต้องเข้าใจก่อนส่ง prompt: หน้านี้เก็บเลขหน้าไว้ใน useState(1) และเก็บหมวดที่เลือกไว้ใน useState<CategoryType | null>(null) — ทั้งสองอย่างไม่ปรากฏใน URL เลย URL ของหน้านี้คือ /categories เฉย ๆ ตั้งแต่ต้นจนจบ ไม่ว่าผู้ใช้จะกดอะไรไปแล้วบ้าง

นี่คือสิ่งที่ต้นฉบับทำ และ prompt ของเราจะสั่งตามนั้น เพราะโค้ดอ้างอิงของคอร์สนี้คือแอปจริง แต่มันมีราคาที่จ่ายจริงและควรถูกพูดถึงตั้งแต่ตอนนี้ ไม่ใช่ปล่อยผ่าน — รายละเอียดว่าราคานั้นคืออะไรและพิสูจน์อย่างไร อยู่ในกล่อง 💡 ใต้โค้ดอ้างอิงของ Category.tsx

เป้าหมายของบทนี้

src/
└── pages/
    └── Category/
        ├── components/

        │       └── CategoryBanner.tsx    # 🤖 ใหม่ — ไม่มีไฟล์ .module.scss
        └── Category.tsx                  # 🤖 เขียนทับ stub

สองไฟล์ ไม่มี SCSS module สักไฟล์ — layout ของหน้านี้ยืมคลาส category-list-container กับ category-list-box จาก _components.scss (บทเรียน 04) ที่หน้า Home ใช้อยู่แล้ว

สัญญาที่แต่ละไฟล์ต้องทำให้ได้ — และสิ่งที่มันต้องไม่ทำ:

  • CategoryBanner.tsx — ต้องรับ prop เดียวที่เป็น optional และเป็น null ได้ ต้องไม่รู้จัก Category, ไม่รู้จัก query และไม่มี state — มันต้องกลางพอที่หน้า Cart กับ Checkout จะหยิบไปใช้ได้โดยไม่ต้องแก้
  • Category.tsx — ต้องมี state สองตัวคือหมวดที่ผู้ใช้เลือกกับเลขหน้า และต้องไม่มี state ตัวที่สาม โดยเฉพาะ totalPages ต้องไม่มี useEffect ต้องยิง query ผ่าน productQueries เท่านั้น และการเปลี่ยนหมวดต้องรีเซ็ตเลขหน้าเสมอ

src/pages/Category/Category.tsx:

import React, { useState } from "react";
import ClipLoader from "react-spinners/ClipLoader";
import { useQuery } from "@tanstack/react-query";
import CategoryBanner from "./components/CategoryBanner/CategoryBanner";
import CategoryMenu from "@/features/products/components/CategoryMenu/CategoryMenu";
import ProductsList from "@/features/products/components/ProductsList/ProductsList";
import Pagination from "@/shared/components/Pagination/Pagination";
import { calculateTotalPages } from "@/shared/utils/pagination.utils";
import useProductRoute from "@/shared/hooks/useProductRoute";
import { productQueries } from "@/features/products/queries";
import { Category as CategoryType } from "@/features/products/types";
import ErrorMessage from "@/shared/components/ErrorMessage/ErrorMessage";

const PAGE_LIMIT = 20;

const Category: React.FC = () => {
  const [selectedCategory, setSelectedCategory] = useState<CategoryType | null>(
    null,
  );
  const [page, setPage] = useState(1);
  const { goToProductDetails } = useProductRoute();

  const { data: categories } = useQuery(productQueries.categories());
  const currentCategory = selectedCategory ?? categories?.[0] ?? null;

  const { data, isLoading, isError } = useQuery({
    ...productQueries.byCategory({
      category: currentCategory?.slug ?? "",
      page,
      limit: PAGE_LIMIT,
    }),
    enabled: currentCategory !== null,
  });

  const totalPages = data ? calculateTotalPages(data.total, PAGE_LIMIT) : 0;

  const onCategoryClick = (category: CategoryType) => {
    setSelectedCategory(category);
    setPage(1);
  };

  const onProductClick = (productId: number) => {
    goToProductDetails(productId);
  };

  return (
    <>
      <CategoryBanner name={currentCategory?.name} />
      <div className="container pt-60 pb-60">
        <section>
          <div className="flex gap-25">
            <CategoryMenu
              activeCategory={currentCategory?.slug}
              categories={categories || []}
              onCategoryClick={onCategoryClick}
            />
            <div className="category-list-container">
              {isError ? (
                <ErrorMessage />
              ) : isLoading ? (
                <div className="text-center">
                  <ClipLoader
                    size={40}
                    aria-label="Loading Spinner"
                    data-testid="loader"
                  />
                </div>
              ) : (
                <>
                  <div className="category-list-box mb-30">
                    <ProductsList
                      products={data?.products}
                      onProductClick={onProductClick}
                    />
                  </div>
                  {totalPages > 0 && (
                    <Pagination
                      currentPage={page}
                      totalPages={totalPages}
                      onPageChange={setPage}
                    />
                  )}
                </>
              )}
            </div>
          </div>
        </section>
      </div>
    </>
  );
};

export default Category;

สองข้อสังเกตเรื่องรูปทรงที่ควรเทียบกับหน้า Home ที่เพิ่งเขียนเมื่อบทที่แล้ว:

  • fragment ตัวนอกสุดที่นี่จำเป็นจริง — ต่างจากหน้า Home ที่ fragment ครอบ <div className="container"> ตัวเดียวแบบไม่มีความหมาย ที่นี่มีสองพี่น้อง: CategoryBanner ที่ต้องกินความกว้างเต็มจอ (แถบสีเทาเต็มความกว้าง) และ <div className="container"> ที่จำกัดความกว้างเนื้อหา ถ้าเอา CategoryBanner เข้าไปไว้ใน container แถบเทาจะหดตามความกว้าง 1200px ทันที นี่คือตัวอย่างที่ดีว่าโครงสร้าง JSX ที่ดู "ไม่จำเป็น" กับที่จำเป็นจริงต่างกันอย่างไร — และเป็นสิ่งที่ตัดสินได้จากการเปิดดูหน้าจริงเท่านั้น
  • <section> ที่ไม่มี className — ห่อ <div className="flex gap-25"> ไว้อีกชั้นโดยไม่ได้ทำอะไรกับ layout เลย มันมีค่าในเชิงความหมายของ HTML อยู่บ้าง (บอกว่านี่คือ section หนึ่งของหน้า) แต่ที่นี่ไม่มี heading อยู่ข้างในเลยสักตัว ซึ่งเป็นเงื่อนไขที่ทำให้ <section> มีประโยชน์จริง ๆ — เป็นอีกบรรทัดที่รีวิวจริงจะทัก
💡 ของที่ควรถูกทักในรีวิว: เลขหน้าถูกเก็บไว้ใน component state โดยไม่ผูกกับ URL เลย — และข้อนี้ต่างจากข้อบกพร่องอื่นในคอร์ส เพราะต้นฉบับก็ทำแบบนี้ และ prompt ของเราก็สั่งแบบนี้ ดังนั้นสิ่งที่คุณกำลังตรวจไม่ใช่ "Agent ทำผิดคำสั่งไหม" แต่คือ "คุณมองออกไหมว่าคำสั่งนี้แลกอะไรไป" พิสูจน์ด้วยตัวเองสามข้อ หลังหน้าเสร็จ: (1) เปิด /categories เลือกหมวด Kitchen Accessories แล้วกดไปหน้า 2 — มองแถบที่อยู่ของเบราว์เซอร์ มันยังเป็น /categories เฉย ๆ ก๊อป URL นั้นส่งให้เพื่อน เพื่อนจะเปิดมาเจอหน้า 1 ของหมวดแรกเสมอ ไม่ใช่สิ่งที่คุณตั้งใจส่ง (2) กด F5 ตอนอยู่หน้า 2 — กลับไปหน้า 1 ของหมวด Beauty งานที่ผู้ใช้ทำมาหายหมด (3) กดปุ่ม Back ของเบราว์เซอร์หลังสลับหมวดและเปลี่ยนหน้ามาหลายครั้ง — คุณจะออกจากหน้า Category ไปเลย ไม่ใช่ถอยกลับไปทีละขั้น เพราะไม่เคยมีรายการใน history เกิดขึ้น ทางแก้ที่ถูกในงานจริงคือย้าย page กับ slug ของหมวดไปอยู่ใน query string ด้วย useSearchParams ของ react-router (มีให้ใช้ตั้งแต่บทเรียน 09) แล้ว derive state จาก URL แทน — ซึ่งจะทำให้ทั้งสามอาการหายไปพร้อมกัน แต่อย่าเพิ่งทำในบทนี้ เก็บไว้เป็นข้อสังเกตในรีวิวของคุณก่อน ประเด็นของข้อนี้คือ: ของที่ Agent ทำ "ถูกตามสั่ง" ไม่ได้แปลว่ามันเป็นการออกแบบที่ดีที่สุด และไม่มี lint ตัวไหนบอกคุณเรื่องนี้ได้เลย มีแต่การลองใช้เว็บอย่างที่ผู้ใช้จริงใช้

  2. เปลี่ยน const totalPages = data ? … : 0; ให้กลายเป็น useState ที่ถูก set ใน useEffect ที่เฝ้า data — โค้ดจะยาวขึ้นกี่บรรทัด ผู้ใช้เห็นความต่างไหม และมีช่วงเวลาไหนบ้างที่ totalPages กับ data ไม่ตรงกัน (เสร็จแล้วย้อนกลับ)
  3. เปิด queries.ts ลบ placeholderData: keepPreviousData ออกหนึ่งบรรทัด แล้วกดเปลี่ยนหน้าในหน้า Category — บอกให้ได้ว่า isLoading เปลี่ยนค่าตอนไหนบ้างในสองกรณี และตอบด้วยว่าถ้าแทนที่จะลบ เราเขียน keepPreviousData: true ลงไปแทน จะเกิดอะไรขึ้นและใครเป็นคนบอกเรา (เสร็จแล้วเติมกลับ)
💡 Checkpoint: รัน npm run dev แล้วกดเมนู Category ที่ Header (path /categories) — แถบ CategoryBanner ต้องแสดงคำว่า Beauty (หมวดแรกที่ dummyjson ตอบมา) โดยอัตโนมัติ พร้อมสินค้า 5 ชิ้นและแถบเลขหน้าที่มีปุ่มเดียว — ที่ PAGE_LIMIT = 20 หมวดที่มีมากกว่าหนึ่งหน้ามีอยู่แค่สองหมวด ให้กด Kitchen Accessories (30 ชิ้น) หรือ Groceries (27 ชิ้น) เพื่อเห็นสองหน้าจริง ๆ แล้วทดสอบสี่อย่าง: (1) กดเลขหน้า 2 / Next — สินค้าหน้าเดิมต้องค้างอยู่แล้วสลับเป็นหน้าใหม่แบบไม่มี spinner ไม่มีจอว่างคั่น (2) อยู่ที่หน้า 2 แล้วสลับหมวด — ต้องเด้งกลับมาหน้า 1 ของหมวดใหม่เสมอ และชื่อบนแบนเนอร์ต้องเปลี่ยนตาม (3) คลิกการ์ดสินค้า — ต้องพาไป /products/<id> ซึ่งยังเป็น stub อยู่ (บทถัดไปจัดการ) (4) ไปหน้า 2 แล้วกด F5 — ต้องกลับมาหน้า 1 ซึ่งเป็นข้อจำกัดที่เราคุยกันไว้ในกล่อง 💡 ใต้โค้ดอ้างอิง ไม่ใช่บั๊กที่ต้องแก้วันนี้ แต่เป็นข้อที่ควรอยู่ในบันทึกรีวิวของคุณ ถ้าข้อ (1) ล้มเหลว — เห็น spinner ทุกครั้งที่เปลี่ยนหน้า — แปลว่า placeholderData: keepPreviousData ใน queries.ts หายไป กลับไปเช็คบทเรียน 17 ปิดท้ายด้วย npm run lint, npm run typecheck แล้ว commit สองหน้าหลักของฝั่ง "เลือกซื้อ" เสร็จแล้ว เหลือหน้าสุดท้ายของ chapter นี้: หน้า Product detail ที่จะเป็นหน้าที่มีคอมโพเนนต์ประกอบเยอะที่สุดในแอป — แกลเลอรีรูป, ข้อมูลราคา, กราฟรีวิว และปุ่ม Add to Cart ที่จะกลายเป็นสะพานเชื่อมไปสู่ chapter ตะกร้าสินค้า — ถ้าข้อ "อธิบายให้ได้" ยังตอบไม่ได้ อย่าเพิ่งไปบทถัดไป
