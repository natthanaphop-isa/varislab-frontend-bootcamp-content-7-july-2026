API Client

API Client

ถึงตอนนี้เปลือกของแอปเราครบแล้ว: router พาไปหน้าต่าง ๆ ได้, Header/Footer แสดงทุกหน้า, และเรามีคลังคอมโพเนนต์กลางตั้งแต่ Button ยัน ImageZoom แต่ทุกหน้ายังว่างเปล่า เพราะยังขาดสิ่งสำคัญที่สุดของเว็บขายของ นั่นคือข้อมูลสินค้า

สามบทต่อจากนี้คือการสร้าง "ชั้นข้อมูลสินค้า" (products data layer) ทีละชั้นจากล่างขึ้นบน: บทนี้เราสร้าง API client กลางที่ทุก request ในแอปต้องวิ่งผ่าน บทหน้าเราใส่ type และฟังก์ชันเรียก API และบทถัดไปเราประกอบทุกอย่างเป็น query factory ให้ TanStack Query จบชั้นนี้แล้ว หน้าเพจในบทต่อ ๆ ไปจะแทบไม่ต้องคิดเรื่องข้อมูลเลย — แค่หยิบไปใช้

รู้จัก dummyjson.com

แอปของเราไม่มี backend ของตัวเอง เราดึงข้อมูลจาก dummyjson.com ซึ่งเป็น API ปลอมฟรีสำหรับฝึกซ้อม — ไม่ต้องสมัครสมาชิก ไม่ต้องขอ API key มีข้อมูลสินค้าจริงจังราว 200 ชิ้นพร้อมรูปภาพ ราคา ส่วนลด รีวิว และหมวดหมู่ ครบพอจะสร้างหน้าร้านทั้งเว็บ endpoint ที่เราจะใช้มีสี่ตัว:

  • GET /products — รายการสินค้าทั้งหมด แบ่งหน้าได้ด้วยพารามิเตอร์ limit และ skip
  • GET /products/category/:slug — สินค้าเฉพาะหมวดหมู่
  • GET /products/categories — รายชื่อหมวดหมู่ทั้งหมด
  • GET /products/:id — รายละเอียดสินค้าชิ้นเดียว

ลองเปิด dummyjson.com/products/1 ในเบราว์เซอร์ดูตอนนี้เลยก็ได้ — คุณจะเห็น JSON ของสินค้าหนึ่งชิ้นเต็ม ๆ นี่แหละคือข้อมูลที่อีกไม่กี่บทจะกลายเป็นหน้า Product ของเรา

ยังจำได้ไหมว่าในบทเรียน 02 เราสร้างไฟล์ .env ไว้แล้ว:

# .env
VITE_API_BASE_URL=https://dummyjson.com

ค่านี้อ่านได้ในโค้ดผ่าน import.meta.env.VITE_API_BASE_URL (Vite เปิดเผยเฉพาะตัวแปรที่ขึ้นต้นด้วย VITE_ ให้ฝั่งเบราว์เซอร์) การแยก URL ออกมาเป็น environment variable แปลว่าวันหนึ่งถ้าเราย้ายไปใช้ backend จริง เราแก้ไฟล์เดียวโดยไม่ต้องแตะโค้ดสักบรรทัด

ทำไมต้อง axios ในเมื่อมี fetch

ในคอร์ส React พื้นฐาน เราเรียก API ด้วย fetch ที่มากับเบราว์เซอร์ ซึ่งใช้งานได้ดีในโปรเจกต์เล็ก แต่พอแอปโตขึ้น จุดอ่อนของมันจะเริ่มกวนใจ:

  • fetch ไม่ถือว่า HTTP error เป็น error — server ตอบ 404 หรือ 500 กลับมา promise ก็ยัง resolve ปกติ! คุณต้องจำไปเช็ค response.ok เองทุกครั้ง ลืมเมื่อไหร่ bug เงียบเมื่อนั้น ส่วน axios จะ reject ให้ทันทีเมื่อ status ไม่ใช่ 2xx
  • ต้องแปลง JSON เอง — fetch ต้อง await response.json() ทุกครั้ง axios แปลงให้อัตโนมัติใน response.data
  • ไม่มี baseURL — fetch ต้องพิมพ์ URL เต็มทุกจุดที่เรียก axios ตั้ง baseURL ครั้งเดียวแล้วเขียนแค่ path สั้น ๆ เช่น /products
  • ไม่มี interceptor — นี่คือเหตุผลข้อใหญ่ที่สุดของเรา interceptor คือ "ด่านตรวจ" ที่ request/response ทุกตัวต้องผ่าน ทำให้เราจัดการ error ของทั้งแอปได้ในที่เดียว เดี๋ยวได้เห็นพลังของมันในบทนี้เลย
  • typed generics — axios ให้เราบอกได้ว่า apiClient.get<Product>(...) แล้ว response.data จะมี type เป็น Product ทันที (เราจะใช้จริงจังในบทหน้า)

เป้าหมายของบทนี้

บทนี้มีไฟล์ใหม่ไฟล์เดียว และมันสั้นมาก — แต่เราจะแบ่งมันเป็นสองส่วน:

src/
└── shared/
    └── api/
        └── client.ts     # 🤖 Agent สร้าง ApiError + apiClient
                          # ✍️ เราพิมพ์ response interceptor ต่อท้ายเอง

ไฟล์นี้อยู่ใน shared ไม่ใช่ features เพราะมันไม่ได้เป็นของฟีเจอร์ใดฟีเจอร์หนึ่ง — products, cart, checkout ทุกฟีเจอร์จะยิง request ผ่าน client ตัวเดียวกันนี้ (โฟลเดอร์ src/shared/api/ เราสั่ง mkdir ทิ้งไว้ตั้งแต่บทเรียน 05 แล้ว ตอนนี้ยังว่างอยู่)

สัญญาที่ไฟล์นี้ต้องทำให้ได้ — และสิ่งที่มันต้องไม่ทำ:

  • ApiError — ต้องเป็น class ที่ extends Error จริง (ไม่ใช่ interface หรือ object ธรรมดา) ต้องตั้ง name เป็น "ApiError" และเก็บ status แบบไม่บังคับ ต้องไม่รับ field อื่นเพิ่ม
  • apiClient — ต้องเป็น instance ที่สร้างจาก axios.create() และอ่าน baseURL จาก environment variable ต้องไม่มี URL ของ dummyjson พิมพ์ตรง ๆ อยู่ในไฟล์ และต้องไม่ตั้ง timeout หรือ headers อะไรเพิ่มที่เราไม่ได้สั่ง
  • response interceptor — ต้องแปลงทุกความล้มเหลวเป็น ApiError แล้วโยนต่อ ต้องไม่กลืน error ไว้เอง และต้องไม่แตะขาที่สำเร็จ

ทำไม interceptor ถึงมาทีหลัง prompt

กฎที่เราได้จากบทเรียน 12 คือ สิ่งที่พังเมื่อคุณตัดไฟล์ X ออกจาก prompt คือไฟล์ที่ import X ไม่ใช่ตัว X เอง บทนี้เป็นกรณีที่ต่างออกไปหนึ่งชั้น เพราะเราไม่ได้ตัดทั้งไฟล์ เราตัดบล็อกเดียวที่อยู่ในไฟล์ และไม่มีใคร import บล็อกได้ — interceptor เป็น side effect ระดับ module ที่ทำงานตอนไฟล์ถูกโหลด ไม่ใช่ของที่ export ออกไป

คำถามจึงเปลี่ยนเป็นสองข้อ ข้อแรก: ถ้าไม่มีบล็อกนี้ ของที่เหลือยังคอมไพล์และรันได้ไหม คำตอบคือได้สบาย ๆ ApiError กับ apiClient ไม่ได้พึ่งพา interceptor เลย ดังนั้นเราสั่ง Agent สร้างสองชิ้นนั้นก่อนได้ แล้ววงจรตรวจงานขั้นที่สาม (npm run lint และ npm run typecheck) ก็ยังเดินได้ครบ

ข้อสอง: มีไฟล์ไหนในโปรเจกต์ที่ import client.ts อยู่บ้าง ตอนนี้ยังไม่มีสักไฟล์ — ค้นดูได้ด้วย grep -rn "shared/api/client" src/ แล้วจะไม่เจออะไรเลย ไฟล์แรกที่จะ import มันคือ src/features/products/api.ts ในบทหน้า ตามด้วย src/features/checkout/api.ts ในบทเรียน 28 และ src/shared/api/client.test.ts ในบทเรียน 31 ทั้งสามที่นั้นตั้งอยู่บนสัญญาข้อเดียวกัน: error ที่หลุดออกมามี .message ที่พร้อมแสดงผลเสมอ ซึ่งเป็นสัญญาที่ interceptor เป็นคนทำให้เป็นจริง

เทียบกับบทเรียน 12 ที่พลิกลำดับได้ (พิมพ์ Button เองก่อน แล้วค่อยส่ง prompt) บทนี้พลิกไม่ได้ เพราะบล็อกที่เราจะพิมพ์เองอ้างถึง apiClient และ ApiError ที่ยังไม่มีตัวตน ทิศทางการพึ่งพาชี้กลับด้าน ลำดับจึงต้องเป็น 🤖 ก่อน ✍️ ทีหลัง — ส่วนบทเรียน 17 คุณจะเจอกรณีที่ลูกศรชี้กลับด้านอีกครั้ง แล้วลำดับจะพลิกกลับไปเป็นแบบบทเรียน 12

โครงสร้าง: สร้างไฟล์ตามนี้ ไม่มากไม่น้อยกว่านี้
- src/shared/api/client.ts

ข้อกำหนดทางเทคนิค:
- บรรทัด import บนสุดต้องเป็น import axios from "axios"; เท่านั้น
  ห้าม import type อื่นของ axios มาในรอบนี้ เพราะยังไม่มีอะไรใช้มัน
- export class ApiError extends Error
  ประกาศ field readonly status?: number; ไว้บนสุดของ class
  constructor(message: string, status?: number)
  ในตัว constructor เรียก super(message) แล้วตั้ง this.name = "ApiError"
  จากนั้น this.status = status
  ห้ามเพิ่ม field หรือ method อื่นนอกเหนือจากนี้
- export const apiClient = axios.create({ baseURL: import.meta.env.VITE_API_BASE_URL })
  ห้ามใส่ option อื่นใน axios.create เช่น timeout, headers หรือ withCredentials
  ห้ามพิมพ์ URL ของ dummyjson ลงในไฟล์นี้ตรง ๆ
- ห้ามใส่ interceptor ใด ๆ ในรอบนี้ ทั้ง request และ response
- ห้ามมี try/catch ในไฟล์นี้
- ห้ามมี default export ไฟล์นี้ export แบบ named ทั้งหมด

ขอบเขต:
- ห้ามติดตั้ง dependency ใหม่
- ห้ามแก้ .env, vite.config.ts, tsconfig หรือไฟล์อื่นนอกจากที่ระบุ
- ห้ามสร้าง index.ts หรือไฟล์ barrel ใด ๆ
- ยังไม่ต้องสร้าง type ของสินค้า ฟังก์ชันเรียก API หรือเอา apiClient ไปใช้ในหน้าไหน

บรรทัด @src/shared/components/ErrorMessage/ErrorMessage.tsx ใน บริบท: ไม่ได้อยู่ตรงนั้นเพราะงานนี้ต้องแก้ไฟล์นั้น — เราสั่งห้ามแตะไปแล้วในขอบเขต มันอยู่ตรงนั้นเพราะข้อความ fallback ที่ Agent จะเห็นในไฟล์นั้นคือข้อความเดียวกับที่เราจะใช้ในอีกสองนาที และเดี๋ยวเราจะกลับมาคุยกันว่าการที่ข้อความเดียวกันอยู่สองไฟล์คือเรื่องที่ควรถูกทักในรีวิว

✅ ตรวจโค้ดที่ AI สร้าง

✅ ตรวจโค้ดที่ AI สร้าง — git status และ git diff ก่อน แล้วไล่ทีละข้อ:

  • AI มักพลาดตรงนี้: เติม response interceptor มาให้เองทั้งที่เราสั่งห้าม (axios + interceptor เป็นคู่ที่มาด้วยกันในโค้ดตัวอย่างทั้งอินเทอร์เน็ต) และตัวที่มันเติมมามักกลืน error ทิ้ง อาการมีสองแบบ แบบแรกคือขาที่ล้มเหลวจบด้วย console.error(error) เฉย ๆ หรือ return null — ผลคือ promise กลับไป resolve สำเร็จพร้อมค่า undefined TanStack Query จะไม่มีวันรู้ว่า request พัง หน้าเว็บค้างอยู่ที่ loading หรือแสดงกริดเปล่า แบบที่สองคือมันโยน new Error("Request failed") ก้อนเดียวกันทุกกรณี ทิ้ง error.response.data.message กับ status ของจริงไป — ผลคือ 404 "ไม่พบสินค้า", 500 ของเซิร์ฟเวอร์ และเน็ตหลุด แสดงข้อความเดียวกันหมดจนแยกไม่ออกว่าเกิดอะไรขึ้น ถ้าเจอ interceptor ในไฟล์ ให้ลบทิ้งทั้งบล็อก ไม่ต้องไล่แก้ — เดี๋ยวคุณพิมพ์ตัวที่ถูกเองในกล่อง ✍️ ข้างล่าง
  • ไฟล์ใหม่ 1 ไฟล์พอดี ไม่มี index.ts, types.ts หรือ api.ts แถมมา และไม่มีไฟล์เดิมไฟล์ไหนขึ้นสถานะ modified
  • ApiError เขียนว่า class ApiError extends Error จริง — ไม่ใช่ interface ApiError และไม่ใช่ type ApiError = { message: string; status?: number } ทั้งสองแบบหลังทำให้ error instanceof ApiError ในเทสต์บทเรียน 31 เขียนไม่ได้เลย
  • ในตัว constructor มีบรรทัด this.name = "ApiError"; อยู่จริง — ถ้าขาด error ที่ log ออกมาจะขึ้นว่า Error เฉย ๆ แยกไม่ออกว่ามาจากชั้นไหนของแอป
  • status เป็น optional (status?: number) ไม่ใช่ number ตรง ๆ — เน็ตหลุดคือกรณีที่ไม่มี status จริง ๆ
  • baseURL อ่านจาก import.meta.env.VITE_API_BASE_URL — ลอง grep -rn "dummyjson" src/ ต้องไม่เจอสักบรรทัด ถ้าเจอแปลว่ามันพิมพ์ URL ทับลงไปตรง ๆ ซึ่ง lint และ typecheck ผ่านสบาย แต่ทำให้ .env กลายเป็นไฟล์หลอก
  • บรรทัด import เป็น import axios from "axios"; บรรทัดเดียว — ถ้ามี AxiosError ติดมาด้วยโดยที่ยังไม่มี interceptor npm run lint จะฟ้อง unused ทันที (กฎ @typescript-eslint/no-unused-vars มาจาก tseslint.configs.recommended ที่เราตั้งไว้บทเรียน 03)
  • ไม่มี default export และไม่มี any โผล่ในไฟล์
  • ไม่มี comment อธิบายสิ่งที่โค้ดบอกอยู่แล้ว เช่น // create axios instance — ผิดกติกาข้อสุดท้ายในไฟล์ rules

โค้ดอ้างอิง

ของที่ควรได้กลับมาจากรอบนี้ — สังเกตว่ามันยังไม่ครบไฟล์ ยังขาดท่อนสำคัญที่สุดอยู่:

import axios from "axios";

export class ApiError extends Error {
  readonly status?: number;

  constructor(message: string, status?: number) {
    super(message);
    this.name = "ApiError";
    this.status = status;
  }
}

export const apiClient = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL,
});

ApiError — error หนึ่งรูปแบบของทั้งแอป

ApiError เป็น class ที่ extends Error ธรรมดา เพิ่มของแค่สองอย่าง: ตั้ง name เป็น "ApiError" เพื่อให้เวลา log ออกมาแล้วรู้ทันทีว่า error นี้มาจากชั้น API และเก็บ status (HTTP status code) ไว้เผื่อโค้ดฝั่ง UI อยากแยกกรณี เช่น 404 แสดง "ไม่พบสินค้า" สังเกตว่า status เป็น optional (?) — เพราะบางความผิดพลาดไม่มี status เลย เช่น เน็ตหลุด server ไม่ได้ตอบอะไรกลับมาสักไบต์

การใช้ class แทน object ธรรมดายังทำให้เราเช็ค error instanceof ApiError ได้ ซึ่งจะมีประโยชน์ตอนเขียนเทสต์ในบทเรียน 31

axios.create — instance ของเราเอง

axios.create() สร้าง instance แยกที่มีการตั้งค่าของตัวเอง แทนที่จะใช้ axios ตัว global เราตั้ง baseURL จาก environment variable ที่เตรียมไว้ ต่อจากนี้ทุกที่ในแอป import apiClient ตัวนี้ไปใช้ แล้วเขียนแค่ apiClient.get("/products") — axios ต่อ URL เต็มให้เอง

✍️ ส่วนนี้พิมพ์เอง

ตอนนี้ไฟล์มี "ท่อ" แล้ว แต่ยังไม่มี "ด่าน" ท่อนที่เหลือคือหัวใจของบท และเป็นของที่ต้องผ่านมือคุณ

✍️ ส่วนนี้พิมพ์เอง — เมื่อวงจรตรวจงานถึงขั้นที่สามและ npm run lint กับ npm run typecheck ผ่านแล้ว ให้ทำตามนี้ตามลำดับ ห้ามก๊อปวาง ห้ามกด Tab รับ autocomplete ของ Cursor:

  1. เปิด src/shared/api/client.ts
  2. แก้บรรทัดบนสุดจาก import axios from "axios"; เป็น import axios, { AxiosError } from "axios"; — ตอนนี้เรามีที่ใช้มันแล้ว
  3. เว้นบรรทัดว่างหนึ่งบรรทัดต่อจาก }); ของ axios.create แล้วพิมพ์บล็อก interceptor ต่อท้ายไฟล์ทั้งก้อน — ระหว่างพิมพ์ให้หยุดถามตัวเองที่คำว่า Promise.reject ว่าถ้าเปลี่ยนเป็น return เฉย ๆ จะเกิดอะไรขึ้น
  4. npm run lint และ npm run typecheck ให้ผ่านทั้งคู่ แล้วทดสอบสองขาตามหัวข้อถัดไป จากนั้นค่อย git commit

src/shared/api/client.ts — ต่อท้ายไฟล์:

apiClient.interceptors.response.use(
  (response) => response,
  (error: AxiosError<{ message?: string }>) =>
    Promise.reject(
      new ApiError(
        error.response?.data?.message ??
          "Something went wrong. Please try again.",
        error.response?.status,
      ),
    ),
);

เหตุผล: กติกาการแปลง error ของทั้งแอปอยู่ตรงนี้จุดเดียว — ทุกความล้มเหลวของทุก request ในทุกหน้า ตั้งแต่หน้า Home ยันการยิงคำสั่งซื้อในบทเรียน 28 จะไหลผ่านฟังก์ชันเจ็ดบรรทัดนี้ก่อนถึงมือคนเรียกเสมอ ถ้าคุณไม่เคยพิมพ์มันเอง วันที่ error ในแอปเริ่มมีหน้าตาแปลก ๆ คุณจะไม่รู้ด้วยซ้ำว่าต้องไปเปิดไฟล์ไหน

Response interceptor — ด่านแปลง error

interceptors.response.use รับ function สองตัว: ตัวแรกทำงานเมื่อ request สำเร็จ (เราส่ง response ผ่านไปเฉย ๆ ไม่ยุ่ง) ตัวที่สองทำงานเมื่อล้มเหลว และตรงนี้คือหัวใจของบทนี้: ไม่ว่าความล้มเหลวจะหน้าตาแบบไหน เราแปลงมันเป็น ApiError รูปแบบเดียวเสมอ

  • server ตอบ error พร้อมข้อความ (dummyjson ส่ง { "message": "..." } กลับมาเวลา 404) — เราใช้ข้อความนั้น: error.response?.data?.message
  • server ตอบ error แต่ไม่มีข้อความ หรือเน็ตหลุดจนไม่มี response เลย — optional chaining ทำให้ค่าเป็น undefined แล้ว ?? ถอยไปใช้ข้อความกลาง "Something went wrong. Please try again."
  • มี status ก็แนบไปด้วย ไม่มีก็ปล่อยเป็น undefined

แล้วส่งต่อด้วย Promise.reject(...) — จุดนี้สำคัญ: interceptor ไม่ได้ "กลืน" error ให้หายไป มันแค่เปลี่ยนรูปแล้วโยนต่อ ฝั่งที่เรียกยังเห็นว่า request ล้มเหลวเหมือนเดิม แค่ได้ error ที่หน้าตาสะอาดและคาดเดาได้

ส่วน AxiosError<{ message?: string }> ที่เพิ่งเติมเข้าไปในบรรทัด import คือการบอก TypeScript ว่า "ก้อน data ที่ server ส่งมาตอน error มีฟิลด์ message ที่เป็น string หรือไม่มีก็ได้" — ถ้าไม่ประกาศ generic ตัวนี้ error.response?.data จะมี type เป็น unknown แล้วบรรทัด ?.message จะคอมไพล์ไม่ผ่าน

💡 ของที่ควรถูกทักในรีวิว: ข้อความ "Something went wrong. Please try again." ในไฟล์นี้ เป็นข้อความเดียวกันตัวอักษรต่อตัวอักษรกับค่า default ของ prop message ใน ErrorMessage.tsx ที่เราสร้างไว้บทเรียน 09 (ลอง grep -rn "Something went wrong. Please try again." src/ ดู จะเจอสองที่) ในโค้ดที่จัดระเบียบดีแล้ว ข้อความที่ผูกกันแบบนี้ควรอยู่ที่เดียวแล้วอีกฝั่ง import ไปใช้ ของจริงคือถ้าวันหนึ่งมีคนแก้ข้อความในไฟล์หนึ่ง อีกไฟล์จะเงียบสนิทและข้อความในแอปจะไม่ตรงกันโดยไม่มีเครื่องมือตัวไหนบอก เราพิมพ์ตามต้นฉบับ แต่ถ้านี่เป็น pull request ในงานจริง นี่คือ comment ที่ควรเขียนทิ้งไว้

ทำไมการ normalize error ถึงเปลี่ยนชีวิต

ลองนึกภาพแอปที่ไม่มีด่านนี้: ทุกคอมโพเนนต์ที่เรียก API ต้องเขียน catch (e: any) แล้วนั่งเดาเอาเองว่า error ก้อนนี้เป็นชนิดไหน — e.response?.data?.message หรือ e.message หรือ string เปล่า ๆ? โค้ดเดา ๆ แบบนี้จะโผล่ซ้ำ ๆ กระจายไปทุกไฟล์ และแต่ละไฟล์เดาไม่เหมือนกัน พอ backend เปลี่ยนรูปแบบ error ทีเดียว ต้องไล่แก้ทั้งแอป

แต่พอทุกความล้มเหลวถูกบีบให้เป็น ApiError ตั้งแต่ต้นทาง สัญญาที่เหลือของทั้งแอปจะเรียบง่ายมาก: error ที่หลุดออกจากชั้น API มี .message ที่พร้อมแสดงผลเสมอ TanStack Query จะเก็บ error ก้อนนี้ไว้ให้ แล้วคอมโพเนนต์แค่เช็ค isError แล้ว render ErrorMessage ได้อย่างมั่นใจโดยไม่ต้องมี try/catch สักตัว — เดี๋ยวคุณจะเห็นในบทเรียน 19 ว่าหน้า Home จัดการ error ทั้งหน้าด้วยเงื่อนไขบรรทัดเดียว และถ้าวันหนึ่งอยากเพิ่มของอย่าง auth token หรือส่ง error เข้าระบบ logging ก็มาเพิ่มที่ด่านนี้ที่เดียว ทุก request ได้รับผลทันที

ทดสอบ client ด้วยตาตัวเอง

เรายังไม่มีหน้าไหนใช้ client จริง แต่เราพิสูจน์ได้ว่ามันทำงาน เปิด src/pages/Home/Home.tsx แล้ววางโค้ดชั่วคราวนี้ไว้บนสุดของไฟล์ (นอกตัว component — โค้ดระดับ module จะทำงานทันทีที่ไฟล์ถูกโหลด):

// TEMP: ทดสอบ apiClient — ลบทิ้งเมื่อเช็คเสร็จ
import { apiClient } from "@/shared/api/client";

apiClient
  .get("/products", { params: { limit: 1 } })
  .then((response) => console.log("API OK:", response.data))
  .catch((error) => console.error("API ERROR:", error));

รัน npm run dev เปิดหน้า Home แล้วดู console ในเบราว์เซอร์ — คุณควรเห็น API OK: ตามด้วย object ที่มีสินค้าหนึ่งชิ้น แปลว่า baseURL ต่อถูก, .env อ่านได้ และ JSON ถูกแปลงให้อัตโนมัติ

ทีนี้ทดสอบขาที่สำคัญกว่า — ขา error เปลี่ยน path เป็นสินค้าที่ไม่มีอยู่จริง:

  .get("/products/0", { params: { limit: 1 } })

รีเฟรชแล้วดู console อีกครั้ง: คราวนี้ควรเห็น API ERROR: ตามด้วย ApiError ที่มี message เป็นข้อความจาก server และ status: 404 — นี่คือ interceptor ที่คุณเพิ่งพิมพ์ทำงานให้แล้ว ความล้มเหลวดิบ ๆ ของ axios ถูกแปลงเป็นรูปแบบเดียวที่เราออกแบบไว้ ถ้าเห็นเป็น AxiosError แทน แปลว่า interceptor ไม่ถูกโหลดหรือพิมพ์ผิดที่

🚨 เช็คครบทั้งสองขาแล้ว อย่าลืมลบโค้ดชั่วคราวทั้งก้อนออกจาก Home.tsx ให้ไฟล์กลับไปเป็นเหมือนเดิมก่อนไปบทถัดไป — การยิง API ระดับ module แบบนี้เหมาะแค่กับการทดลองเท่านั้น ของจริงเราจะให้ TanStack Query เป็นคนเรียกเสมอ และถ้าลืมลบ git diff ของบทหน้าจะมีของแปลกปนมาทันที

🤔 อธิบายให้ได้

  1. เปลี่ยน Promise.reject(new ApiError(...)) ในบล็อกที่คุณพิมพ์เอง เป็น new ApiError(...) เฉย ๆ (ไม่ห่อ Promise.reject) แล้วรัน npm run lint กับ npm run typecheck — ทั้งคู่ยังผ่าน อธิบายว่าโค้ดทดสอบใน Home.tsx จะพิมพ์อะไรออก console แทน และหน้าเว็บในบทเรียน 19 จะแสดงอะไรให้ผู้ใช้เห็น
  2. error.response?.data?.message มีเครื่องหมาย ? อยู่สองจุด ยกกรณีจริงมาหนึ่งกรณีต่อหนึ่งจุด ว่าอะไรที่ทำให้ค่าตรงนั้นเป็น undefined ได้ และบอกว่าถ้าลบ ? ทั้งสองตัวออก จะพังตอนไหน — ตอนคอมไพล์หรือตอนรัน
  3. prompt สั่งให้ import แค่ axios ตัวเดียว ทั้งที่เรารู้อยู่แล้วว่าโค้ดสุดท้ายต้องมี AxiosError ด้วย อธิบายว่าถ้าสั่งให้ import มาตั้งแต่รอบแรก npm run lint จะฟ้องอะไร และกฎตัวไหนเป็นคนฟ้อง
